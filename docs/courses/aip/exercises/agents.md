# AgentCore とエージェントの問題集

対象の解説: [AgentCore のアーキテクチャ](../../../services/genai-apps.md#agentcore)、[エージェントのパターンと MCP](../../../services/genai-apps.md#agent-patterns)

### 問1 {#q1}

AgentCore Runtime で動く旅行手配のエージェントが、次回の来訪時に利用者の好みを忘れていると報告されました。エージェントはメモリ上の変数に好みを保存しています。利用者ごとに分けて、セッションをまたいで残す必要があります。最も適切な修正はどれですか。

- A. AgentCore Memory の長期記憶を使い、`actorId` は全利用者で同じ値にして管理を簡単にする
- B. `idleRuntimeSessionTimeout` を最大にして、microVM のメモリに好みを残し続ける
- C. AgentCore Memory の長期記憶を使い、`actorId` を利用者ごとに分ける
- D. Runtime の実行ロールのポリシーに好みを記録し、次回の起動時に読み出す

??? success "答えと解説"
    **正解: C**

    Runtime のデータは既定で揮発します。セッションをまたぐ知識は長期記憶に置きます。

    - A: 誤り。`actorId` を分けないと別の利用者の記憶が混ざる。
    - B: 誤り。最大でも 8 時間で停止し、セッションが終わるとメモリは消える。
    - C: 正しい。
    - D: 誤り。IAM のポリシーはデータの保存先ではない。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [セッションの分離](../../../services/ai.md#session-isolation)、[Memory の設計](../../../services/genai-apps.md#agentcore-memory)

### 問2 {#q2}

独自のフレームワークで書いた調査エージェントを動かします。セッションは利用者ごとに分離し、処理は長くても 3 時間です。サーバーの管理はしたくありません。利用者とセッションの対応について、セキュリティ担当から確認がありました。正しい設計はどれですか。

- A. Harness で動かせば独自のフレームワークもそのまま動くので、セッションの管理も任せる
- B. Runtime の microVM で動かし、利用者とセッション ID の対応はバックエンドで管理する
- C. Runtime の microVM で動かし、利用者とセッション ID の対応は AgentCore が自動で強制するので何もしない
- D. ECS の 1 つのタスクで全利用者を処理し、変数の名前を利用者ごとに分けて分離する

??? success "答えと解説"
    **正解: B**

    microVM はセッションごとに分離され、最大 8 時間です。利用者との対応はバックエンドの責任です。

    - A: 誤り。Harness はモデル、プロンプト、ツールを指定する方式で、独自のフレームワークには Runtime を使う。
    - B: 正しい。
    - C: 誤り。AgentCore は対応を強制しない。
    - D: 誤り。変数の名前では分離にならず、サーバーの管理も増える。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [Runtime の選び方](../../../services/genai-apps.md#agentcore-runtime)、[セッションの分離](../../../services/ai.md#session-isolation)

- A. 社内の振り分けは A2A、別の基盤のエージェントとの通信は Agent Squad
- B. 社内の振り分けも別の基盤との通信も、1 つの巨大なシステムプロンプトにまとめて処理する
- C. 社内の振り分けは MCP のリソース、別の基盤との通信は Bedrock Flows の Condition ノード
- D. 社内の振り分けは Agent Squad、別の基盤のエージェントとの通信は A2A

    - D: 誤り。原因を調べずに容量を増やしており、費用も増える。

### 問16 {#q16}

マルチエージェントのシステムで、処理が遅い原因がどのエージェントの引き継ぎにあるのかが分かりません。各エージェントは AgentCore Runtime で動いています。最も適切な手段はどれですか。

- A. `AWS/Bedrock` の `InvocationLatency` の全体の平均と、エージェントごとの呼び出しの回数を比べる
- B. AgentCore Observability のトレースで、スパンの親子関係と引き継ぎの回数を見る
- C. CloudTrail の管理イベントで、エージェントの作成の時刻を比べる
- D. 各エージェントのシステムプロンプトに、処理時間を応答に書くよう指示する

??? success "答えと解説"

    - B: 正しい。
    - C: 誤り。実行時の協調は分からない。

カスタマーサポートのエージェントは最終回答の評価が高いものの、費用が想定の 5 倍です。チームは最終回答の評価のジョブだけを実行しています。原因を測るには何を追加しますか。

- A. 最終回答の評価データの件数を 2 倍にして、スコアの信頼度を高める
- B. 判定モデルの `Faithfulness` のしきい値を上げて、費用の高い回答を不合格にする

### 問18 {#q18}

Strands で作ったエージェントの品質を、新しいバージョンごとに継続して確かめます。独自の評価基盤は作りたくありません。Bedrock Agents（Classic）は使っていません。最も適切なものはどれですか。

- A. CloudWatch の `Invocations` を毎週比べて、回数が減っていれば品質が上がったと判断する
- B. Bedrock Evaluations のプログラムのジョブで、BLEU と ROUGE を計算する

??? success "答えと解説"

### 問19 {#q19}

注文処理のエージェントを評価する指標を決めます。経営層は「仕事を完了できたか」、開発チームは「正しいツールを正しい引数で呼んだか」「無駄がないか」を知りたいと考えています。組み合わせとして適切なものを選んでください。（3つ選択）

- A. `InvocationThrottles` の合計だけ
- B. ステップ数、トークン、時間の効率
- C. タスク完了率
- D. Harmfulness の平均だけ

    - B: 正しい。
    - C: 正しい。
    - D: 誤り。安全の指標で、仕事の完了やツールの正しさは測れない。
    - E: 正しい。
    - F: 誤り。検索の設定で、エージェントの性能の指標ではない。
