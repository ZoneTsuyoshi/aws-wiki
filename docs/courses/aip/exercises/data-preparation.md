### 問1 {#q1}

Data Catalog に登録した顧客の問い合わせ履歴を、毎週 FM の要約に使います。必須列の欠損や ID の重複が混ざると要約の品質が落ちるので、ルールを宣言して検査し、不合格が増えたら担当者に通知したいと考えています。コードの保守は増やしたくありません。最も適切な構成はどれですか。

- A. Glue Data Quality に DQDL でルールを書いて検査し、結果を CloudWatch のアラームにつなぐ
- B. Bedrock のガードレールの拒否トピックに「欠損したデータ」を定義して、要約の入力を止める
- C. SageMaker Data Wrangler の画面で毎週データを開き、担当者が目視で欠損を探す
- D. Lambda で全件を読み込んで検査するコードを書き、結果を S3 に保存して週に 1 回人が確認する

??? success "答えと解説"
    **正解: A**

    宣言的なルールなら Glue Data Quality です。Data Catalog の保存済みデータを評価でき、結果をアラームにつなげます。

    - A: 正しい。
    - B: 誤り。ガードレールは内容の安全性を見るもので、列の欠損や重複は検査できない。
    - C: 誤り。前処理を画面で試す機能で、定期的な自動の検査と通知にならない。
    - D: 誤り。全件の検査コードの保守が増え、通知の要件も満たさない。

    **スキル:** [1.3.1](../domain1.md#skill-1-3-1) / **参照:** [Glue Data Quality](../../../services/data-engineering.md#glue-data-quality)、[非同期と統合](../../../services/genai-apps.md#async-integration)

### 問2 {#q2}

API で届く文書を 1 件ずつ FM に渡す前に検査します。要件は、文字数が上限以内であること、社内の案件番号の形式に合うこと、禁止された語句を含まないことです。不合格はその場で利用者に返します。最も適切な手段はどれですか。

- A. Glue Data Quality の ETL ジョブを API のリクエストごとに起動し、DQDL で判定して結果を待つ
- B. 検査を行わずに FM に渡し、エラーの応答が返ったときだけ利用者に通知する
- C. Lambda で独自の検査を実装し、不合格の件数をカスタムメトリクスで CloudWatch に送る
- D. 検査の内容をシステムプロンプトに書き、FM に判定させて結果の文章を解析する

??? success "答えと解説"
    **正解: C**

    独自の形式を 1 件ずつ同期で検査するなら Lambda です。不合格の件数を指標にして傾向も追います。

    - A: 誤り。ジョブの起動に時間がかかり、1 件ずつの同期の検査に向かない。
    - B: 誤り。FM は不正な案件番号でもエラーにしないので、品質ゲートにならない。
    - C: 正しい。
    - D: 誤り。決まった規則の判定に FM の費用をかける必要がなく、結果も決定的にならない。

    **スキル:** [1.3.1](../domain1.md#skill-1-3-1) / **参照:** [非同期と統合](../../../services/genai-apps.md#async-integration)、[Lambda](../../../services/lambda.md)

### 問3 {#q3}

データサイエンティストが、埋め込みに渡す前のデータの傾向を調べ、前処理の案を画面で試したいと考えています。一方、運用チームは確定したルールを毎日のパイプラインで検査し、ロード前に悪いデータを止めたいと考えています。役割の組み合わせとして最も適切なものはどれですか。

- A. どちらも CloudWatch Logs Insights のクエリで行い、傾向もルールも同じ画面で確認する
- B. どちらも Bedrock のモデル評価のジョブで行い、スコアが低いデータを手で除く
- C. 試行は Glue Data Quality、毎日の検査は SageMaker Data Wrangler の画面での手動の実行
- D. 試行は SageMaker Data Wrangler、毎日の検査は Glue Data Quality の ETL 組み込み

??? success "答えと解説"
    **正解: D**

    Data Wrangler は ML の前処理を画面で試す機能、Glue Data Quality の ETL 組み込みはロード前に悪いデータを止める機能です。

    - A: 誤り。ログの分析の機能で、データの前処理やロードの制御はできない。
    - B: 誤り。モデルの評価であり、データの検証ではない。
    - C: 誤り。役割が逆で、画面での手動実行は毎日の自動の検査に向かない。
    - D: 正しい。

    **スキル:** [1.3.1](../domain1.md#skill-1-3-1) / **参照:** [Data Wrangler](../../../services/sagemaker.md#data-wrangler)、[Glue Data Quality](../../../services/data-engineering.md#glue-data-quality)

### 問4 {#q4}

ある保険会社は、形式の決まった請求書を毎日 10 万枚処理します。抽出する項目は決まっており、結果は決定的で、費用を抑えることが重要です。一方、医師の所見が書かれた図入りの報告書は少数で、図の意味の解釈が必要です。処理の選択として最も適切なものはどれですか。

- A. どちらも Transcribe の Call Analytics に渡し、項目の抽出と分析を任せる
- B. 請求書は Textract で抽出し、図入りの報告書はマルチモーダルの FM で解釈する
- C. どちらも Textract の `DetectDocumentText` で文字だけを取り、文字列から正規表現で項目と解釈を得る
- D. どちらもマルチモーダルの FM に画像を渡し、プロンプトで項目と解釈を指示する

??? success "答えと解説"
    **正解: B**

    - B: 正しい。
    - C: 誤り。図の意味は文字の抽出では得られない。

コールセンターの録音を FM で要約します。誰の発言かを区別する必要があり、自社の製品名が誤認識されて要約に誤りが出ています。録音は S3 に保存され、当日中に要約できれば十分です。最も適切な前処理はどれですか。

- A. 音声ファイルをそのままテキスト向けの FM に渡し、話者の区別と製品名の修正を指示する
- B. Comprehend のカスタム固有表現で音声を解析し、製品名を抽出して FM に渡す
- C. Transcribe のバッチで話者の分離とカスタム語彙を使い、文字起こしを FM に渡す

- A. Lambda を S3 のイベントで起動し、数 TB のデータを 1 回の実行で変換する
- B. SageMaker Processing のジョブで、ライブラリを入れたコンテナを実行する

### 問7 {#q7}

あるアプリは `InvokeModel` で提供者 A のモデルを呼んでいます。本文に別の提供者の形式のまま `messages` を渡したところ `ValidationException` が返りました。モデルは今後も増える予定です。最も適切な修正はどれですか。

- A. `ConverseStream` の代わりに `InvokeModelWithResponseStream` を使い、本文はそのまま送る
- B. IAM ポリシーに `bedrock:Converse` を追加して、本文の検証を無効にする
- C. 同じ本文のまま SDK の再試行を `adaptive` にして、成功するまで繰り返す
- D. `Converse` に変更し、`messages` と `system` の共通の形式で渡す

??? success "答えと解説"
    **正解: D**

    `InvokeModel` の本文はモデルごとに異なります。`Converse` ならモデルをまたいで共通の形式で渡せます。

    - A: 誤り。応答の受け取り方の違いで、本文の形式の誤りは直らない。
    - B: 誤り。`bedrock:Converse` というアクションはなく、権限は形式の検証と関係ない。
    - C: 誤り。`ValidationException` は入力の誤りなので再試行しても成功しない。
    - D: 正しい。

    **スキル:** [1.3.3](../domain1.md#skill-1-3-3) / **参照:** [API の選び方](../../../services/ai.md#invoke-apis)、[InvokeModel](../../../services/ai.md#invoke-model)

### 問8 {#q8}

10 万件の要約をバッチ推論で実行します。ジョブが入力の形式の検証で失敗しました。入力の用意の仕方として正しいものはどれですか。

- A. S3 の JSONL に、1 行ずつ `recordId` と `modelInput` を書く
- B. S3 の CSV に、1 行ずつ `prompt` と `completion` を書く
- C. `messages` の配列を `Converse` に順に渡し、`recordId` はレスポンスのヘッダーから受け取る
- D. 全件を 1 つの JSON 配列にして、`CreateModelInvocationJob` の本文に直接入れる

    - A: 正しい。
    - B: 誤り。ファインチューニングの形式に似ているが、バッチ推論の形式ではない。
    - C: 誤り。バッチ推論の入力ではなく、同期呼び出しの説明になっている。
    - D: 誤り。入力は S3 に置いた JSONL で渡す。
