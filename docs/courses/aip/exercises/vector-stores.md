# ベクトルストアの問題集

### 問1 {#q1}

小さなチームが社内文書の RAG を作ります。ベクトル DB の運用担当はおらず、SharePoint と Confluence の文書も取り込みます。生成は自分たちのアプリで別に行うので、検索結果だけが返れば十分です。最も適切な構成はどれですか。

- A. Customer-managed のナレッジベースと OpenSearch Serverless を作り、SharePoint は専用のコネクタで接続する
- B. OpenSearch Service のドメインに k-NN インデックスを作り、取り込みのコードを自分で書いて運用する
- C. Managed Knowledge Base を作り、`Retrieve` で検索結果を取得する
- D. Managed Knowledge Base を作り、`RetrieveAndGenerate` で検索と生成をまとめて行う

??? success "答えと解説"
    **正解: C**

    Managed はストアの運用を任せられ、コネクタも多く使えます。呼び出しは `Retrieve` や `AgenticRetrieveStream` です。

    - A: 誤り。Customer-managed のコネクタは S3 と Custom だけで、運用の手間も増える。
    - B: 誤り。運用の担当がいないという条件に合わない。
    - C: 正しい。
    - D: 誤り。Managed では `RetrieveAndGenerate` を使えない。

    **スキル:** [1.4.1](../domain1.md#skill-1-4-1) / **参照:** [Managed と Customer-managed](../../../services/genai-apps.md#managed-kb)、[選び方の比較](../../../services/genai-apps.md#choosing)

### 問2 {#q2}

ある企業は業務データを Aurora PostgreSQL に持っています。契約の状態や期限と文書の埋め込みを SQL で結合して検索したいと考えています。新しいデータストアの運用は増やしたくありません。文書数は数十万件です。最も適切なベクトルストアはどれですか。

- A. S3 Vectors を使い、業務データは別途 Aurora から取得して、アプリの中で結合する
- B. 既存の Aurora PostgreSQL に pgvector を追加して、業務データと同じ SQL で結合する
- C. OpenSearch Serverless のコレクションを作り、業務データを定期的に同期して検索する
- D. Neptune Analytics に業務データも移し、グラフと埋め込みをまとめて検索する

??? success "答えと解説"
    **正解: B**

    既存の PostgreSQL に拡張を入れれば、業務データと同じ SQL で結合できます。

    - A: 誤り。新しいストアが増え、SQL での結合もできない。
    - B: 正しい。
    - C: 誤り。運用が増え、同期のずれも生じる。
    - D: 誤り。関係をたどる質問向けで、業務データの移行も必要になる。

    **スキル:** [1.4.1](../domain1.md#skill-1-4-1) / **参照:** [pgvector](../../../services/genai-apps.md#pgvector)、[ベクトルストア](../../../services/genai-apps.md#vector-stores)

### 問3 {#q3}

10 億件の古い技術文書を、低頻度の検索用に低コストで保管します。一方、この 1 年分の文書は頻繁に検索され、製品番号での検索も重要です。アクセスの傾向ははっきり分かれています。最も適切な構成はどれですか。

- A. 古い文書は S3 Vectors、直近の文書はハイブリッド検索できる OpenSearch に置く
- B. すべてを MemoryDB に置き、インメモリの低遅延で両方の要件を満たす
- C. すべてを OpenSearch のドメインに置き、シャードを増やして 10 億件を常時メモリに載せる
- D. すべてを S3 Vectors に置き、製品番号はハイブリッド検索の設定で探す

??? success "答えと解説"
    **正解: A**

    S3 Vectors は大量で低頻度のデータに向きます。頻繁に検索し、キーワードも必要なものは OpenSearch に置きます。

    - A: 正しい。
    - B: 誤り。大量で低頻度のデータにインメモリは費用が合わない。
    - C: 誤り。低頻度の大量データとしては費用が大きい。
    - D: 誤り。Knowledge Bases で S3 Vectors を使うとハイブリッド検索はできない。

    **スキル:** [1.4.1](../domain1.md#skill-1-4-1) / **参照:** [S3 Vectors](../../../services/genai-apps.md#s3-vectors)、[DynamoDB Streams](../../../services/dynamodb.md#streams)

### 問4 {#q4}

文書の属性（所有部署、公開範囲）を DynamoDB でキー検索し、埋め込みは別のベクトル DB に置く構成にしました。属性を更新しても、ベクトル DB 側のメタデータが古いままになることが問題です。更新は 1 日に数千件で、数分以内に揃えたいと考えています。最も適切な方法はどれですか。

- A. DynamoDB をグローバルテーブルにして、ベクトル DB を同期先のレプリカとして登録する
- B. DynamoDB の TTL で古い項目を削除すれば、ベクトル DB も自動で同じ状態になる
- C. 毎週ベクトル DB を全件削除し、全文書を再び埋め込んで作り直す
- D. DynamoDB Streams の変更を Lambda で受け、ベクトル DB のメタデータを更新する

??? success "答えと解説"
    **正解: D**

    2 つのストアに分けると更新のずれが問題になります。変更のストリームで同期します。

    - A: 誤り。グローバルテーブルは DynamoDB 同士の複製で、ベクトル DB はレプリカにできない。
    - B: 誤り。TTL は DynamoDB の項目を消すだけで、別のストアには反映されない。
    - C: 誤り。数分以内の要件を満たさず、費用も大きい。
    - D: 正しい。

    **スキル:** [1.4.1](../domain1.md#skill-1-4-1) / **参照:** [DynamoDB Streams](../../../services/dynamodb.md#streams)、[ベクトルストア](../../../services/genai-apps.md#vector-stores)

### 問5 {#q5}

社内規定の RAG で、旧版の規定が返ることと、他部署の文書が返ることが問題になっています。文書は S3 にあり、部署と施行年は分かっています。検索の品質は保ったまま、部署と年で絞りたいと考えています。最も適切な実装はどれですか。

- A. 文書と同じ場所に `<ファイル名>.metadata.json` を置き、検索時の `filter` で絞る
- B. 部署ごとにナレッジベースを分け、施行年はチャンクの本文に書いて、ベクトルの近さで判定する
- C. プロンプトに「他部署の文書と旧版を無視してください」と書き、モデルに判断させる
- D. S3 のオブジェクトタグを付けるだけで、`Retrieve` が自動でタグを読み取って絞り込む

??? success "答えと解説"
    **正解: A**

    メタデータファイルの属性は検索時の `filter` で使えます。`andAll` で条件を組み合わせられます。

    - A: 正しい。
    - B: 誤り。年をベクトルの近さで判定するのは確実でなく、分割の管理も増える。
    - C: 誤り。モデルに渡った時点で他部署の内容が見えており、確実でもない。
    - D: 誤り。オブジェクトタグは自動ではフィルターに使われない。

### 問6 {#q6}

Knowledge Bases のベクトルストアに OpenSearch Serverless を使っています。`.metadata.json` を置いて同期は成功しましたが、`filter` を付けると結果が返りません。ファイル名は `規定.pdf.metadata.json` で正しく、属性の値も合っています。最初に確認すべきことはどれですか。

- A. 埋め込みモデルの次元が 1,024 でないか
- B. データソースの `dataDeletionPolicy` が `DELETE` でないか
- C. インデックスのエンジンが `nmslib` でないか
- D. `numberOfResults` が 100 を超えていないか

??? success "答えと解説"
    **正解: C**

    `nmslib` エンジンではメタデータファイルが無視されます。`faiss` を使います。

    - A: 誤り。次元が合わなければ取り込みでエラーになり、成功している状況と合わない。
    - B: 誤り。データソースを消したときのベクトルの扱いで、フィルターとは関係がない。
    - C: 正しい。
    - D: 誤り。範囲は検索の件数の話で、フィルターの無効とは関係がない。

    **スキル:** [1.4.2](../domain1.md#skill-1-4-2) / **参照:** [メタデータ](../../../services/genai-apps.md#kb-metadata)、[OpenSearch](../../../services/genai-apps.md#opensearch-vectors)

### 問7 {#q7}

カスタム変換の Lambda で、チャンクごとに章番号のメタデータを付けました。同じ文書の `.metadata.json` には `chapter: 0` という値が残っています。検索時に章番号で絞ると何が起きますか。

- A. ファイル単位の値が優先され、すべてのチャンクが章 0 として扱われる
- B. 値が衝突するので取り込みジョブが失敗し、統計に理由が記録される

??? success "答えと解説"
    **正解: D**

    チャンク単位のメタデータは Lambda で付けられ、ファイル単位より優先されます。

    - A: 誤り。チャンク単位のメタデータがファイル単位より優先される。
    - B: 誤り。衝突そのものでは失敗しない。
    - C: 誤り。自動で配列にはまとめられない。
    - D: 正しい。

    **スキル:** [1.4.2](../domain1.md#skill-1-4-2) / **参照:** [メタデータ](../../../services/genai-apps.md#kb-metadata)、[同期と鮮度](../../../services/genai-apps.md#kb-sync)

### 問8 {#q8}

OpenSearch Service のドメインで検索の遅延を重視したベクトル索引を設計します。元データは 60 GiB で増加分が 6 GiB、索引のオーバーヘッドは 10% と見積もり、1 シャードを 30 GiB にします。プライマリシャードの数として最も適切なものはどれですか。

### 問9 {#q9}

1,000 万チャンクのベクトル索引でメモリの費用が問題です。Titan Text Embeddings V2 の 1,024 次元を使っています。品質の低下が小さいことを確認できれば、構成の変更を受け入れます。生データの大きさを最も大きく減らす変更と、そのときの手順はどれですか。

- A. 256 次元の新しい索引を作って全データを再度埋め込み、取得の評価で比べる
- B. シャードの数を 2 倍にして、1 シャードあたりの生データの大きさを半分にする
- C. HNSW の `ef_search` を下げて、ベクトルの大きさを小さくする
- D. 既存の索引の `dimension` を 256 に変更し、差分の同期を実行して切り替える

??? success "答えと解説"

    1,024 次元から 256 次元で生データは 4 分の 1 になります。次元を変えるなら全データの再埋め込みと評価が必要です。

    - A: 正しい。
    - B: 誤り。全体の大きさは減らない。
    - C: 誤り。`ef_search` は検索時の候補の数で、保存の大きさを変えない。
    - D: 誤り。次元の変更は全データの再埋め込みが必要で、差分の同期では足りない。

### 問15 {#q15}

- A. ベクトルのスコアに固定の定数を掛けるコードをアプリに書き、毎回の結果から定数を手で調整する

- C. シャードを増やして、キーワードとベクトルの検索を別々のシャードで実行させる
