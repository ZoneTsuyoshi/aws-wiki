### 問1 {#q1}

同じアカウントで 5 つのアプリが同じモデルを呼んでいます。月額が増え、どのアプリの費用かが分かりません。アプリのコードの変更は `modelId` の差し替えだけにしたいと考えています。最も適切な方法はどれですか。

- A. アプリごとにアプリケーション推論プロファイルを作ってタグを付け、ARN を `modelId` に指定する
- B. アプリごとに別のアカウントを作り、請求を分ける
- C. `requestMetadata` にアプリ名を入れれば、Cost Explorer にアプリ別の費用が自動で出る
- D. 全アプリの呼び出しをバッチ推論に変えて、ジョブ名から費用を推定する

??? success "答えと解説"
    **正解: A**

    アプリケーション推論プロファイルのタグで、アプリごとの費用を追跡します。

    - A: 正しい。
    - B: 誤り。`modelId` の差し替えだけでは済まず、移行の手間が大きい。
    - C: 誤り。ログの絞り込み用で、費用の配分にはならない。
    - D: 誤り。同期の処理を変えることになり、費用の配分としても不正確。

    **スキル:** [4.1.1](../domain4.md#skill-4-1-1) / **参照:** [トークンの削減](../../../services/genai-apps.md#token-efficiency)、[推論の容量とプロファイル](../../../services/genai-apps.md#inference-profiles)

### 問2 {#q2}

RAG の入力トークンの大半が、検索で取得した 20 件のチャンクです。回答に使われているのは多くても数件です。検索の網羅性を大きく落とさず、入力を減らしたいと考えています。最も効果的な変更はどれですか。

- A. `numberOfResults` を 100 に増やして、確実に正しい文書を入れる
- B. `maxTokens` を小さくして、入力トークンを減らす
- C. 候補はそのまま取得し、リランクで 5 件に絞って渡す
- D. `temperature` を 0 にして、チャンクの読み取りを効率化する

??? success "答えと解説"
    **正解: C**

    リランクで絞ると、モデルに渡すトークンが減ります。

    - A: 誤り。トークンがさらに増える。
    - B: 誤り。`maxTokens` は応答の上限で、入力を減らさない。
    - C: 正しい。
    - D: 誤り。トークンは変わらない。

    **スキル:** [4.1.1](../domain4.md#skill-4-1-1) / **参照:** [トークンの削減](../../../services/genai-apps.md#token-efficiency)、[検索の改善](../../../services/genai-apps.md#retrieval-optimization)

### 問3 {#q3}

長文の分析を受け付ける API で、上限を超える入力が FM まで届き、エラーと費用の無駄が発生しています。入力の長さは文字数では正確に見積もれません。呼び出しの前に判定し、超えるものは利用者に返したいと考えています。最も適切なものはどれですか。

- A. `InputTokenCount` のアラームで、超えるものを止める
- B. 文字数を 4 で割った固定の計算で判定する
- C. FM を呼んで `model_context_window_exceeded` が返ったら利用者に返す
- D. `CountTokens` で判定し、超えるものは返す

??? success "答えと解説"
    **正解: D**

    `CountTokens` は `InvokeModel` と `Converse` の形式を受け付け、呼び出しの前に確認できます。

    - A: 誤り。集計の指標で、個々の呼び出しを事前に止められない。
    - B: 誤り。正確に見積もれないという前提に反する。
    - C: 誤り。FM まで届いており、事前の判定にならない。
    - D: 正しい。

    **スキル:** [4.1.1](../domain4.md#skill-4-1-1) / **参照:** [クォータとトークンの数え方](../../../services/ai.md#quotas-detail)、[トークンの削減](../../../services/genai-apps.md#token-efficiency)

### 問4 {#q4}

次の 3 つの処理の費用と応答を最適化します。(a) 画面で待つ質問応答。(b) 数時間かかってもよい評価の処理で、同期の API のままにしたい。(c) 翌朝までに終わればよい 100 万件の要約で、S3 に入出力を置ける。最も適切な組み合わせはどれですか。

- A. (a) Flex、(b) Priority、(c) Standard
- B. (a) Standard、(b) Flex、(c) バッチ推論
- C. (a)〜(c) すべて Reserved
- D. (a) バッチ推論、(b) Standard、(c) Priority

??? success "答えと解説"
    **正解: B**

    時間に余裕があれば Flex、非同期の大量処理はバッチです。

    - A: 誤り。(a) に割引の層は遅く、(b) に割高の層を使っており、(c) もバッチの割引を逃す。
    - B: 正しい。
    - C: 誤り。最小の容量を確保する必要があり、断続的な処理には無駄が大きい。
    - D: 誤り。(a) は画面で待てず、(c) に割高の層は不要。

    **スキル:** [4.1.2](../domain4.md#skill-4-1-2) / **参照:** [Bedrock の料金](../../../services/cost-management.md#bedrock-pricing)、[スループットの選択肢](../../../services/ai.md#throughput-options)

### 問5 {#q5}

安いモデル X は上位のモデル Y の 10 分の 1 の単価ですが、X の回答は正解率が低く、再試行と人の修正が多く発生しています。経営層は「単価が安い X に統一」を求めています。最も適切な判断の方法はどれですか。

- A. 再試行と修正も含めた、1 件の成功あたりの費用で比べる

- C. 同じ月の呼び出しの回数だけを比べて、少ない方を選ぶ
- D. 単価だけを比べて X を選び、品質の問題は運用でカバーする

??? success "答えと解説"
    **正解: A**

    価格性能比は 1 件の成功あたりの費用で比べます。

    - A: 正しい。
    - B: 誤り。費用の条件を無視している。
    - C: 誤り。回数は費用と品質を示さない。
    - D: 誤り。再試行や修正が増えると、かえって高くつく。

### 問6 {#q6}

英語の問い合わせの多くは簡単ですが、一部に難しいものがあります。同じ提供者の 2 つのモデルで、複雑さに応じて費用を下げたいと考えています。分類のコードの保守は増やしたくありません。最も適切な機能はどれですか。

- A. Provisioned Throughput を 2 つのモデルに分けて買う
- B. プロンプトキャッシュで難しい質問の応答を保存する
- C. 自前のカスケードを Step Functions で組み、判定のモデルも自分で評価する
- D. Intelligent Prompt Routing

??? success "答えと解説"
    **正解: D**

    Intelligent Prompt Routing は同じ系統のモデルの間で応答品質を予測して選びます。英語のプロンプトに最適化されています。

    - A: 誤り。複雑さによる振り分けにならない。
    - B: 誤り。入力の前半の再利用で、応答は保存せず振り分けもしない。
    - C: 誤り。分類の保守が増える。
    - D: 正しい。

    **スキル:** [4.1.2](../domain4.md#skill-4-1-2) / **参照:** [動的なモデル切り替え](../../../services/genai-apps.md#dynamic-model-selection)、[Bedrock の料金](../../../services/cost-management.md#bedrock-pricing)

### 問7 {#q7}

Provisioned Throughput を 1 か月のコミットメントで購入しましたが、夜間の使用率は 5% です。費用を下げたいと考えています。カスタムモデルではなく、基盤モデルを使っています。今すぐ削除しようとしたところ、できませんでした。最も適切な進め方はどれですか。

- A. モデルユニットを 0 に更新して、課金を止める
- B. コミットメント中でも API の `DeleteProvisionedModelThroughput` を繰り返せば削除できる
- C. コミットメントの終了後にオンデマンドなどへ切り替え、夜間の処理はバッチや Flex に回す
- D. 夜間だけ `InvocationThrottles` を増やして費用を下げる

??? success "答えと解説"
    **正解: C**

    使用率が低いと無駄です。コミットメントの期間中は削除できません。

    - A: 誤り。モデルユニットを 0 にして課金を止めることはできない。
    - B: 誤り。期間中は削除できない。
    - C: 正しい。
    - D: 誤り。スロットリングで費用は下がらない。

    **スキル:** [4.1.3](../domain4.md#skill-4-1-3) / **参照:** [推論の容量とプロファイル](../../../services/genai-apps.md#inference-profiles)、[スループットの選択肢](../../../services/ai.md#throughput-options)

### 問11 {#q11}

FAQ のチャットで、同じ意味の言い換えの質問が多く、FM の費用を減らしたいと考えています。回答には顧客ごとの契約情報が含まれることがあります。低遅延の検索が必要です。最も適切な設計はどれですか。

- A. しきい値を低くしたセマンティックキャッシュで全回答を共有し、ヒット率を上げる
- B. MemoryDB で埋め込みの近さを検索し、契約情報を含む回答はキャッシュしないかキーを分ける

- A. `cachePoint` を増やせば、TTL が切れていても読み込みになる

長い会話を続けるサポートのチャットで、入力トークンが費用の大半を占めています。システムプロンプトは長く固定で、会話の履歴は全文を毎回渡しています。質問は毎回違い、回答には利用者ごとの情報が入ります。入力の費用を下げる方法として適切なものを選んでください。（2つ選択）
