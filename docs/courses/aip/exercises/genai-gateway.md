# GenAI ゲートウェイと CI/CD の問題集

### 問1 {#q1}

全社のアプリが FM、ツール、エージェントを呼ぶ入口を 1 つにして、認証と監視を集約したいと考えています。ゲートウェイのコードを細かく作り込む要件はなく、運用も減らしたいです。さらに、アプリがゲートウェイを迂回できないようにする必要があります。最も適切な構成はどれですか。

- A. 全アプリを 1 つのアカウントに集め、Bedrock の API キーを共有する
- B. API Gateway と Lambda で自作し、迂回を防ぐためにアプリのコードレビューを強化する
- C. AgentCore Gateway を入口にし、IAM でアプリの直接の呼び出しを制限する
- D. AgentCore Gateway を入口にし、迂回の防止は利用規約で定める

??? success "答えと解説"
    **正解: C**

    ゲートウェイは迂回されると意味がありません。IAM で直接の呼び出しを制限します。

    - A: 誤り。認証情報の共有になり、入口の集約にもならない。
    - B: 誤り。保守が増え、レビューだけでは迂回を防げない。
    - C: 正しい。
    - D: 誤り。迂回されるとゲートウェイの統制が効かない。

    **スキル:** [2.3.5](../domain2.md#skill-2-3-5) / **参照:** [GenAI ゲートウェイと CI/CD](../../../services/genai-apps.md#genai-gateway)、[Gateway](../../../services/genai-apps.md#agentcore-gateway)

### 問2 {#q2}

生成 AI アプリの CI/CD を作ります。コードの変更に加え、プロンプトやモデルの設定の変更でも評価を実行し、基準を満たさなければ止めます。セキュリティスキャンも必要です。最も適切な構成はどれですか。

- A. 全変更を本番に出してから、利用者の低評価を見て手で戻す
- B. CodeDeploy の Canary を入れれば、プロンプトの評価は不要になる
- C. コードだけをパイプラインに通し、プロンプトはコンソールで直接本番に反映する
- D. プロンプトと設定もリポジトリで管理し、CodeBuild でスキャンと評価を行い、基準を満たさなければ止める

??? success "答えと解説"
    **正解: D**

    コードに加えて、プロンプト、モデルの設定、評価データも管理します。

    - A: 誤り。問題が利用者に届いてから気づく。
    - B: 誤り。段階的なデプロイと事前の評価は別の役割。
    - C: 誤り。プロンプトの変更が評価を通らない。
    - D: 正しい。

    **スキル:** [2.3.5](../domain2.md#skill-2-3-5) / **参照:** [GenAI ゲートウェイと CI/CD](../../../services/genai-apps.md#genai-gateway)、[CodePipeline](../../../services/cicd.md#codepipeline)、[CodeBuild](../../../services/cicd.md#codebuild)

### 問3 {#q3}

GenAI ゲートウェイで Guardrails を適用していますが、一部のチームがゲートウェイを通さずに Bedrock を呼ぶ可能性があります。組織の安全策として、どのアカウントでも呼び出し側の指定なしで適用したいと考えています。最も適切なものはどれですか。

- A. CloudWatch のアラームで、ガードレールの指定がない呼び出しを見つけて担当者に通知する
- B. Organizations の Bedrock ポリシーで、OU やアカウントに適用する
- C. 各チームのコードに `guardrailConfig` の指定を追加するよう依頼する
- D. ゲートウェイの Lambda の予約済み同時実行を増やして、通さない理由をなくす

??? success "答えと解説"
    **正解: B**

    Organizations の Bedrock ポリシーなら、呼び出し側が指定しなくても適用できます。

    - A: 誤り。検知だけで、適用にならない。
    - B: 正しい。
    - C: 誤り。呼び出し側の対応に依存する。
    - D: 誤り。同時実行は適用の仕組みではない。

    **スキル:** [2.3.5](../domain2.md#skill-2-3-5) / **参照:** [組織での強制](../../../services/genai-apps.md#guardrail-org-enforcement)、[GenAI ゲートウェイと CI/CD](../../../services/genai-apps.md#genai-gateway)

### 問4 {#q4}

問い合わせを、法務、技術、一般に分類して、それぞれに最適なモデルと異なるプロンプトで処理します。モデルは別の提供者のものも含みます。分岐の結果を実行履歴に残す必要があります。最も適切な方式はどれですか。

- A. Step Functions で小さなモデルに分類させ、Choice で分岐する
- B. ロードバランサーのパスベースのルーティングで振り分ける
- C. API Gateway のマッピングテンプレートで、本文の意味を判定して分岐する
- D. Intelligent Prompt Routing で、提供者をまたいで振り分ける

??? success "答えと解説"
    **正解: A**

    内容による振り分けは、分類してから分岐します。

    - A: 正しい。
    - B: 誤り。パスで決まる振り分けで、内容の分類ではない。
    - C: 誤り。マッピングテンプレートは意味の判定ができない。
    - D: 誤り。同じ系統のモデルの中でしか振り分けられない。

    **スキル:** [2.4.4](../domain2.md#skill-2-4-4) / **参照:** [動的なモデル切り替え](../../../services/genai-apps.md#dynamic-model-selection)、[Choice などの状態](../../../services/step-functions.md#state-types)

### 問5 {#q5}

パートナーごとに使うモデルが契約で決まっており、API のパス（`/partner-a`、`/partner-b`）で判別できます。切り替えは年に 1 回程度です。内容の判定や指標による切り替えは不要です。バックエンドのコードは増やしたくありません。最も適切なものはどれですか。

- A. AppConfig と CloudWatch の指標で、遅延の小さいモデルへ自動で切り替える
- B. API Gateway のマッピングテンプレートで、パスに応じたモデルの値を渡す
- C. Intelligent Prompt Routing の既定のルーターに任せ、応答品質で選ばせる
- D. Step Functions で本文を FM に分類させ、パートナーを判定する

??? success "答えと解説"
    **正解: B**

    パスやヘッダーで決まるなら、API の変換で足ります。

    - A: 誤り。指標で変えると契約のモデルと異なってしまう。
    - B: 正しい。
    - C: 誤り。契約で決まるモデルの指定にならない。
    - D: 誤り。パスで決まるものに FM の費用をかける必要がない。

    **スキル:** [2.4.4](../domain2.md#skill-2-4-4) / **参照:** [マッピングテンプレート](../../../services/api-gateway.md#mapping-templates)、[動的なモデル切り替え](../../../services/genai-apps.md#dynamic-model-selection)

### 問6 {#q6}

日本語中心のチャットの費用を下げるため、同じ提供者のモデルの間で Intelligent Prompt Routing を試すことになりました。正しい進め方はどれですか。

- A. 代替モデルを指定せずに自分で設定するルーターを作り、基準も空のままにする
- B. Bedrock が言語を自動で判定して最適化するので、評価せずに本番で有効にする
- C. 英語のプロンプトに最適化されているので、自社の日本語のデータで効果を確かめる
- D. 別の提供者のモデルを代替モデルに設定して、コストの差を大きくする

??? success "答えと解説"
    **正解: C**

    Intelligent Prompt Routing は同じ系統で費用と品質の均衡を取ります。日本語なら効果を測ってから使います。

    - A: 誤り。自分で設定するルーターでは代替モデルと基準を指定する。
    - B: 誤り。公式に英語のプロンプトに最適化されているとされる。
    - C: 正しい。
    - D: 誤り。同じ系統のモデルの中でしか振り分けられない。

    **スキル:** [2.4.4](../domain2.md#skill-2-4-4) / **参照:** [動的なモデル切り替え](../../../services/genai-apps.md#dynamic-model-selection)、[AppConfig](../../../services/secrets.md#appconfig)

### 問7 {#q7}

第一候補のモデルの遅延が悪化したときに、トラフィックの 50% を別のモデルへ自動で移します。切り替えの条件は CloudWatch の指標です。モデルの呼び出しのコードは変えたくありません。最も適切な構成はどれですか。

- A. 振り分けの割合を AppConfig に置き、アラームを受けて更新する
- B. Lambda の環境変数を毎回手で変えて、関数の新しいバージョンを公開する
- C. API Gateway のステージ変数を変更して、API を毎回デプロイする
- D. Bedrock のプロビジョニング済みの容量の設定で、遅延が増えると自動で別のモデルへ移す

??? success "答えと解説"
    **正解: A**

    指標による切り替えは AppConfig と CloudWatch で組みます。

    - A: 正しい。
    - B: 誤り。自動の切り替えにならず、更新の手間もかかる。
    - C: 誤り。API のデプロイが要り、遅延に応じた自動の切り替えも別に必要。
    - D: 誤り。そのような機能はない。

    **スキル:** [2.4.4](../domain2.md#skill-2-4-4) / **参照:** [AppConfig](../../../services/secrets.md#appconfig)、[動的なモデル切り替え](../../../services/genai-apps.md#dynamic-model-selection)

### 問8 {#q8}

新しいプロンプトを本番へ出す前に、品質の悪化を自動で止めたいと考えています。本番の利用者には影響させません。基準は `Faithfulness` が 0.8 以上です。最も適切な構成はどれですか。

- A. `AWS/Bedrock` の `InvocationLatency` が 0.8 秒以下なら昇格する
- B. A/B テストで新旧を本番に出し、1 か月後の解決率で判定する
- C. カナリアで利用者の 5% に出して、低評価が増えたら止める
- D. CodeBuild でゴールデンデータセットを評価し、基準未満ならパイプラインを止める

??? success "答えと解説"
    **正解: D**

    品質ゲートは CI/CD に組み込みます。判定モデルは Bedrock Evaluations を使えます。

    - A: 誤り。遅延の指標で、品質は判定できない。
    - B: 誤り。利用者に影響し、自動のゲートにもならない。
    - C: 誤り。利用者に影響する。この段階の答えではない。
    - D: 正しい。

    **スキル:** [5.1.4](../domain5.md#skill-5-1-4) / **参照:** [テスト](../../../services/genai-apps.md#testing)、[CodeBuild](../../../services/cicd.md#codebuild)、[ステージ条件](../../../services/cicd.md#stage-conditions)

### 問9 {#q9}

プロンプトとモデルは半年間変えていないのに、回答の品質が下がったと報告がありました。パイプラインの回帰テストは変更時にしか動きません。文書は週に数回更新されており、利用者の質問の傾向も変わっています。追加すべきものはどれですか。

- A. `temperature` を毎週少しずつ下げて、品質の低下を吸収する
- B. 変更時の回帰テストのしきい値を上げて、次の変更まで待つ
- C. プロンプトを変更しない限り品質は変わらないので、報告は利用者の主観と判断する
- D. EventBridge のスケジュールで定期的に評価を実行する

??? success "答えと解説"
    **正解: D**

    文書や質問は変わるので、定期の評価も必要です。

    - A: 誤り。品質の低下の検知にも原因の対処にもならない。
    - B: 誤り。変更がなければテストは動かない。
    - C: 誤り。文書の更新や質問の変化で、モデルを変えなくても品質は変わる。
    - D: 正しい。

    **スキル:** [5.1.4](../domain5.md#skill-5-1-4) / **参照:** [テスト](../../../services/genai-apps.md#testing)、[EventBridge](../../../services/messaging.md#eventbridge)

### 問10 {#q10}

チームがゴールデンデータセットを作ります。CI の回帰テストに使い、本番の変化も検出したいと考えています。作り方として適切なものを選んでください。（2つ選択）

- A. テストのたびに質問をランダムに作り直し、結果を前回と比べる
- B. 本番の代表的な質問と、確認した正解の組を固定して版で管理する
- C. 本番で見つかった失敗の例を追加して、再発を検出できるようにする
- D. テストに通りやすいよう、合格した質問だけを残す
- E. 正解を持たず、FM の今の応答を毎回正解として保存し直す

??? success "答えと解説"
    **正解: B, C**

    ゴールデンデータセットは質問と正解の固定の集合です。失敗の例を加えて育てます。

    - A: 誤り。固定でなければ比較できない。
    - B: 正しい。
    - C: 正しい。
    - D: 誤り。テストの意味がなくなる。
    - E: 誤り。悪化しても差分が見えない。

    **スキル:** [5.1.4](../domain5.md#skill-5-1-4) / **参照:** [テスト](../../../services/genai-apps.md#testing)、[プロンプトの管理](../../../services/genai-apps.md#prompt-management)

チャットのデプロイのあと、`5xx` は増えていませんが、回答の傾向が変わったと報告がありました。今後は早く検知したいと考えています。HTTP の監視はすでにあります。最も適切な追加はどれですか。

- A. Synthetics のカナリアで固定の質問を流し、応答の内容を検証する
- B. ヘルスチェックの間隔を 10 秒に短くする

- D. ALB のアクセスログを増やして、200 の割合を比べる

??? success "答えと解説"
    **正解: A**

    HTTP の死活監視だけでは足りません。スクリプトで応答の内容も検証します。

    - A: 正しい。

### 問12 {#q12}

AppConfig で新しいモデルに段階的に切り替えます。切り替えの途中で品質が落ちたら自動で戻したいと考えています。固定の質問の評価は 5 分ごとに実行できます。また、新しいモデルの応答が前の版と意味的にどの程度変わったかも測ります。最も適切な構成はどれですか。

- A. `InvocationClientErrors` だけを監視し、0 なら品質に問題がないと判断する
- B. 評価と埋め込みの差をカスタムメトリクスにし、アラームを AppConfig の環境に設定する

- D. 新しいモデルに一度に切り替え、翌週の利用者の評価を見て手で戻す

??? success "答えと解説"

    意味のドリフトは応答の埋め込みを前の版と比べて測ります。段階的なデプロイとアラームで自動で戻します。
