### 問1 {#q1}

基幹の受注システムから、受注ごとに FM で備考を分類します。FM の遅延やスロットリングで基幹システムの受注処理を遅らせてはなりません。分類の結果は数分後に反映されれば十分です。基幹システムの変更は小さくします。最も適切な設計はどれですか。

- A. 基幹システムに `ConverseStream` を組み込み、受注の画面で応答を順に表示する
- B. 基幹システムから `Converse` を同期で呼び、失敗したら受注をエラーにする
- C. 基幹システムを Bedrock と同じリージョンに移し、同期で呼ぶ遅延を短くする
- D. 基幹システムからは SQS に送るだけにし、Lambda が FM を呼んで結果を書き戻す

??? success "答えと解説"
    **正解: D**

    FM は遅く、スロットリングもあります。間にキューを置くと影響を抑えられます。

    - A: 誤り。基幹の処理が FM の応答に結びついたまま。
    - B: 誤り。FM の遅延と失敗が基幹システムに波及する。
    - C: 誤り。変更が大きく、スロットリングの波及も残る。
    - D: 正しい。

    **スキル:** [2.3.1](../domain2.md#skill-2-3-1) / **参照:** [疎結合](../../../services/messaging.md#coupling)、[非同期と統合](../../../services/genai-apps.md#async-integration)

### 問2 {#q2}

古い業務システムは XML の API しか話せず、変更もできません。このシステムから新しい生成 AI の API を呼べるようにします。新しい API は JSON を受け取ります。独自のサーバーは増やしたくありません。最も適切な方法はどれですか。

- A. FM に XML をそのまま渡し、プロンプトで API の形式の変換も任せる
- B. API Gateway のマッピングテンプレートで XML と JSON を変換する
- C. EC2 に変換用の常駐のプロキシを立て、XML を JSON に変える
- D. 業務システムを JSON に対応するよう書き換える

??? success "答えと解説"
    **正解: B**

    レガシーシステムを変更できないなら、API Gateway の変換や Lambda でアダプターを置きます。

    - A: 誤り。形式の変換を FM に任せると費用と誤りが増え、決定的でもない。
    - B: 正しい。
    - C: 誤り。独自のサーバーが増える。
    - D: 誤り。変更できないという条件に反する。

    **スキル:** [2.3.1](../domain2.md#skill-2-3-1) / **参照:** [変換](../../../services/api-gateway.md#transformations)、[疎結合](../../../services/messaging.md#coupling)

### 問4 {#q4}

開発チームが IDE でのコード生成とテスト作成を効率化したいと考えています。新規に Amazon Q Developer の IDE 向けのサブスクリプションを契約する予定です。2026 年 10 月の時点での判断として最も適切なものはどれですか。

- A. Kiro は AWS のサービスではないので、選択肢から外す
- B. IDE 向けは Kiro を検討する。Q Developer の IDE 部分は Kiro へ移行中である
- C. Q Developer のコンソールとチャットの機能も同時に終了するので、AWS の支援ツールは使わない
- D. Q Developer の Free Tier を新規に作り、IDE のプラグインを長期の標準にする

### 問17 {#q17}

AI 開発ツールで生成したコードを本番に入れる運用を決めます。生産性は上げたいものの、品質と安全性を落とせません。最も適切な運用はどれですか。

- A. AI が生成したテストが通れば、人のレビューと他の検査をすべて省略する
- B. AI が生成したコードは検査済みとみなし、レビューを省略してそのまま本番に入れる
- C. 生成したコードもレビューとテスト、セキュリティスキャンを通す
- D. AI が書いたコードは本番では禁止し、開発環境でも使わない

??? success "答えと解説"
    **正解: C**

    AI の出力はレビューとテストを通します。同じ品質ゲートを適用します。

    - A: 誤り。テスト自体の誤りもありえる。
    - B: 誤り。AI の出力にも誤りがある。
    - C: 正しい。
    - D: 誤り。生産性を上げる目的に反する。

### 問18 {#q18}

生成 AI の API を使う既存の Python のコードがあります。チームは、API の使い方の提案、古いコードのリファクタリング、遅い処理の改善案を開発の中で得たいと考えています。最も適切な手段はどれですか。

- A. Guardrails の拒否トピックに古い API の名前を登録して、古いコードを止める
- B. Bedrock の Provisioned Throughput を購入して、コードの遅い処理を速くする
- C. Kiro や Q Developer などの AI 開発ツールに、コードの文脈を渡して提案を得る
- D. CloudTrail の記録を読み、コードの改善案を手で書く

??? success "答えと解説"
    **正解: C**

    コードの生成、リファクタリング、API の提案、性能の改善案は AI 開発ツールの典型の用途です。

    - A: 誤り。内容の検査で、リファクタリングにはならない。
    - B: 誤り。容量の話で、コードの改善案にはならない。
    - C: 正しい。
    - D: 誤り。API の操作の記録で、コードの改善案を得る手段として効率が悪い。

    **スキル:** [2.5.4](../domain2.md#skill-2-5-4) / **参照:** [AI 開発ツール](../../../services/ai.md#ai-dev-tools)、[最適化](../../../services/ai.md#ai-optimization)
