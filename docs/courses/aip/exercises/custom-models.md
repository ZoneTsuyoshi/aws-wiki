# カスタムモデルとモデルのホストの問題集

### 問1 {#q1}

同じ基盤モデルから LoRA で調整した用途別のモデルが 20 個あり、SageMaker AI で提供します。各モデルの利用は多くありません。GPU の費用を最も抑えて、モデルごとに直接呼び出せるようにするには、どう載せますか。

- A. 全 LoRA を 1 つの重みにマージして再学習し、1 つのモデルとして 20 用途の指示をプロンプトで切り替える
- B. モデルごとに専用のリアルタイムエンドポイントを作り、全重みを 20 回読み込んで個別にスケールする
- C. 基盤モデルを推論コンポーネントで載せ、S3 のアダプターを指すアダプター推論コンポーネントを 20 個作る
- D. 20 個をサーバーレスエンドポイントにデプロイし、呼び出しのない間は 0 に戻す

??? success "答えと解説"
    **正解: C**

    LoRA のアダプターは基盤モデルの計算資源を共有します。アダプターごとに直接呼び出せます。

    - A: 誤り。用途別の調整が失われ、再学習の費用もかかる。
    - B: 誤り。基盤モデルの重みを 20 回載せるので GPU の費用が大きい。
    - C: 正しい。
    - D: 誤り。GPU が必要な大きな FM の提供に向かない。

    **スキル:** [1.2.4](../domain1.md#skill-1-2-4) / **参照:** [推論コンポーネントと LoRA](../../../services/sagemaker.md#multi-model)、[SageMaker AI での FM](../../../services/genai-apps.md#sagemaker-fm)

### 問2 {#q2}

調整済みモデルの新しい版を、審査役が承認した時点で本番へ自動でデプロイしたいと考えています。承認の記録も必要です。承認後に問題が分かったら、前の承認済みの版へ戻します。最も適切な構成はどれですか。

- A. CloudTrail のログを毎日検索し、`CreateModelPackage` の呼び出しがあれば本番へデプロイする
- B. Model Registry の `ModelApprovalStatus` で管理し、変更を EventBridge で検知して CodePipeline を起動する
- C. 承認の結果を Slack に投稿してもらい、担当者が内容を読んでエンドポイントを手で更新する
- D. 版の情報を S3 のファイル名に書き、審査役が名前を変更したら S3 イベントで Lambda を起動する

??? success "答えと解説"
    **正解: B**

    状態の変更を EventBridge で検知できます。`Approved` から `Rejected` への変更で、前の承認済みの版を再デプロイする形にもできます。

    - A: 誤り。作成の記録であって承認の状態ではない。審査の前にデプロイされる。
    - B: 正しい。
    - C: 誤り。自動化の要件を満たさず、記録も別に要る。
    - D: 誤り。承認の記録やモデルの版の管理にならず、誤操作も防げない。

    **スキル:** [1.2.4](../domain1.md#skill-1-2-4) / **参照:** [Model Registry](../../../services/sagemaker.md#model-registry)、[EventBridge](../../../services/messaging.md#eventbridge)

### 問3 {#q3}

SageMaker AI のエンドポイントで動く調整済みモデルを更新します。新しい版に問題があれば利用者への影響を小さくして自動で元に戻したいと考えています。追加のインスタンスの費用は短時間なら許容されます。最も適切な方式はどれですか。

- A. デプロイガードレールの Canary で一部を移し、CloudWatch アラームで自動で戻す
- B. 同じエンドポイントを削除して作り直し、作成が終わるまでメンテナンス画面を表示する
- C. デプロイガードレールの All at once で全トラフィックを一度に移し、問題があれば手で古い設定に戻す
- D. シャドウテストを本番の配信に切り替える手順として使い、応答の返却先を新しい版だけにする

??? success "答えと解説"
    **正解: A**

    Canary は小さな範囲で試し、ベイク期間のアラームで自動ロールバックします。

    - A: 正しい。
    - B: 誤り。停止が発生し、自動で戻す仕組みにもならない。
    - C: 誤り。一度に全利用者へ影響が出て、手作業の復旧になる。
    - D: 誤り。シャドウテストは応答を返さない検証で、本番の切り替え手順ではない。

### 問4 {#q4}

外部で調整した Hugging Face 形式の Llama の重みを、Bedrock の API から使いたいと考えています。利用は不定期なので、容量を常時買いたくありません。同時に、夜間の大量処理をバッチ推論で行う案も出ています。正しい説明はどれですか。

- A. 重みをファインチューニングのジョブに渡せば、バッチ推論とオンデマンドの両方を使えるモデルになる
- B. Custom Model Import のモデルは Provisioned Throughput を買わないと呼べないが、バッチ推論は使える
- C. Hugging Face 形式は Bedrock で扱えないので、SageMaker JumpStart の公開モデルに置き換える必要がある
- D. Custom Model Import でオンデマンドに呼べるが、インポートしたモデルにバッチ推論は使えない

??? success "答えと解説"
    **正解: D**

    Custom Model Import は `InvokeModel` 系をオンデマンドで呼びます。バッチ推論と CloudFormation には対応しません。

    - A: 誤り。外部の重みをそのまま持ち込む機能は Custom Model Import で、ファインチューニングのジョブではない。
    - B: 誤り。インポートしたモデルはオンデマンドで呼び、バッチ推論には対応しない。
    - C: 誤り。Custom Model Import は Hugging Face の重みの形式を S3 から取り込む。
    - D: 正しい。

ある SaaS は、平日の日中に毎分大量のトークンを安定して消費します。ダウンタイムは契約上許されず、入力は毎分 50 万トークン、出力は毎分 5 万トークンです。独自のモデルは不要で、容量の確保はアカウントチームを通じて進められます。最も適切な方式はどれですか。

- A. バッチ推論を 5 分ごとに起動し、結果を S3 からポーリングする

- C. オンデマンドの Reserved ティアで必要な容量を確保する

SageMaker AI で LLM を自前でホストしています。CPU 使用率でターゲット追跡を設定していますが、応答が遅くなってもスケールアウトしません。ストリーミングの応答が多く、応答時間は入力と出力の長さで大きく変わります。最も適切な指標はどれですか。

- A. `SageMakerVariantConcurrentRequestsPerModelHighResolution`
- B. `ModelLatency` の平均が短くなったらスケールアウトするステップスケーリング
- C. `CPUUtilization` のしきい値を 70% から 20% に下げる

    - A: 正しい。

    - C: 誤り。LLM の負荷は GPU に現れ、CPU 使用率には表れにくい。下げても実態を反映しない。
    - D: 誤り。1 件の処理時間が安定している場合の指標で、応答時間が大きく変わる LLM には向かない。

### 問14 {#q14}

Bedrock の容量を計画します。担当者は `Invocations` の平均から必要な処理量を見積もりましたが、ピーク時にスロットリングが続きました。プロンプトの長さは呼び出しごとに大きく違います。見積もりの直し方として最も適切なものはどれですか。

- A. CPU 使用率の指標を見て、70% を超えない範囲に呼び出しを抑える
- B. `Invocations` の平均を 2 倍にして安全率とし、リクエスト数のクォータの増加を申請する
- C. `TimeToFirstToken` の平均から同時実行数を逆算して容量とする
- D. 呼び出しログからプロンプトと応答の長さの分布を取り、トークン数のピークで見積もる

??? success "答えと解説"
    **正解: D**

    FM の容量の単位はトークンです。平均ではなくピーク、リクエスト数ではなくトークン数で考えます。

    - A: 誤り。オンデマンドの Bedrock では CPU 使用率を見られず、容量の単位も違う。
    - B: 誤り。FM の容量の単位はトークンで、平均の 2 倍でも長さの分布を反映しない。
    - C: 誤り。遅延の指標で、トークンの消費量を示さない。
    - D: 正しい。

    **スキル:** [4.2.5](../domain4.md#skill-4-2-5) / **参照:** [スループット](../../../services/genai-apps.md#throughput)、[モデル呼び出しログ](../../../services/ai.md#invocation-logging)

### 問15 {#q15}

自前でホストした LLM の推論コンポーネントを、負荷に合わせて増減します。1 つのエンドポイントに複数のモデルを載せており、モデルごとに増減したいと考えています。適切な指標はどれですか。

- A. `CacheReadInputTokenCount`
- B. `ConcurrentRequestsPerCopy`
- C. `InvocationThrottles`
- D. `SageMakerVariantInvocationsPerInstance`

??? success "答えと解説"
    **正解: B**

    推論コンポーネントのコピーごとの同時リクエスト数を使います。モデル単位で増減できます。

    - A: 誤り。Bedrock のプロンプトキャッシュの指標で、スケーリングの指標にならない。
    - B: 正しい。Application Auto Scaling では `SageMakerInferenceComponentConcurrentRequestsPerCopyHighResolution` を指定する。
    - C: 誤り。Bedrock のメトリクスで、SageMaker AI のモデルの負荷を示さない。
    - D: 誤り。バリアント単位の呼び出し数で、モデルごとの負荷を表さない。

    **スキル:** [4.2.5](../domain4.md#skill-4-2-5) / **参照:** [自動スケーリング](../../../services/sagemaker.md#autoscaling)、[スループット](../../../services/genai-apps.md#throughput)

### 問16 {#q16}

ある月から、呼び出しの回数は同じなのに入力トークンが急に増え、スロットリングも出始めました。プロンプトは先週更新され、利用者の増加はありません。資源の計画を担当するあなたが、利用パターンの監視から最初に取るべき行動はどれですか。

- A. 入出力トークンの比率の変化を確かめ、プロンプトの変更や不正利用の可能性を調べる
- B. 呼び出しの回数が同じなので問題なしと判断し、クォータの増加を申請して様子を見る
- C. SageMaker AI のエンドポイントに移行し、自前の容量でトークンの増加を吸収する
- D. `temperature` を下げて応答のばらつきを減らし、入力トークンの増加を止める

??? success "答えと解説"
    **正解: A**

    入出力の比率の変化は、プロンプトの変更や不正利用の兆候です。容量を増やす前に原因を確認します。

    - A: 正しい。
    - B: 誤り。原因を調べずに容量を増やしており、不正利用も見逃す。
    - C: 誤り。原因を調べないまま運用を増やしている。
    - D: 誤り。推論パラメータは入力トークンを減らさない。

    **スキル:** [4.2.5](../domain4.md#skill-4-2-5) / **参照:** [スループット](../../../services/genai-apps.md#throughput)、[見るべき指標](../../../services/genai-apps.md#genai-metrics)
