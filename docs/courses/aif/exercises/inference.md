# 推論とモデルの入手の問題集

対象の解説: [推論の種類](../../../services/ai-fundamentals.md#inference-types)、[エンドポイントと推論](../../../services/sagemaker.md#endpoints)、[JumpStart](../../../services/sagemaker.md#jumpstart)

### 問1 {#q1}

EC サイトの画面を開いた瞬間に、おすすめのスコアを返す必要があります。呼び出しは一日中続きます。適切な推論の種類はどれですか。

- A. 夜間の一括スコアリング
- B. リアルタイム推論
- C. 非同期推論
- D. バッチ推論

??? success "答えと解説"
    **正解: B**

    常時起動して低遅延で返すのがリアルタイム推論です。

    - A: 誤り。事前の計算なので、その場の入力に応じた結果を返せません。
    - B: 正しい。
    - C: 誤り。キューに入れて処理する方式で、結果を待つ前提です。
    - D: 誤り。データセットをまとめて処理する方式で、画面表示中の応答には使えません。

    **スキル:** [1.1.3](../domain1.md#obj-1-1-3) / **参照:** [推論の種類](../../../services/ai-fundamentals.md#inference-types)

### 問2 {#q2}

社内ツールのモデルが 1 日に数回しか呼ばれません。最初の呼び出しが少し遅くてもよく、待機中の費用はかけたくありません。適切な推論の種類はどれですか。

- A. サーバーレス推論
- B. インスタンスを常時 2 台起動した推論
- C. バッチ推論
- D. リアルタイム推論

??? success "答えと解説"
    **正解: A**

    サーバーレス推論は待機コストがなく、呼び出しが断続的でコールドスタートを許容できる場面に向きます。

    - A: 正しい。
    - B: 誤り。待機の費用がかかるので要件に反します。
    - C: 誤り。利用者の呼び出しに応じて結果を返す用途には向きません。
    - D: 誤り。インスタンスが常時起動するので、呼ばれない時間にも費用がかかります。

    **スキル:** [1.1.3](../domain1.md#obj-1-1-3) / **参照:** [推論の種類](../../../services/ai-fundamentals.md#inference-types)、[サーバーレス](../../../services/sagemaker.md#serverless)

### 問3 {#q3}

1 件あたり数百 MB の動画を推論にかけ、処理に数分から数十分かかります。利用者は結果が後から届いてもかまいません。適切な推論の種類はどれですか。

- A. リアルタイム推論
- B. プロンプトキャッシュ
- C. サーバーレス推論
- D. 非同期推論

??? success "答えと解説"
    **正解: D**

    非同期推論はリクエストをキューに入れて処理し、入力 1 GB、処理 1 時間までを扱えます。

    - A: 誤り。SageMaker AI のリアルタイム推論は入力が数十 MB 以内で、処理も通常 60 秒までなので、超えてしまいます。
    - B: 誤り。入力の再利用の仕組みで、推論の種類ではありません。
    - C: 誤り。断続的な短い呼び出し向けで、大きな入力の長い処理には向きません。
    - D: 正しい。

    **スキル:** [1.1.3](../domain1.md#obj-1-1-3) / **参照:** [推論の種類](../../../services/ai-fundamentals.md#inference-types)、[非同期](../../../services/sagemaker.md#async)

### 問4 {#q4}

200 万件の商品のスコアを毎晩計算し、翌朝の画面で使います。費用を抑えるのに適した推論の種類はどれですか。

- A. サーバーレス推論
- B. リアルタイム推論
- C. 夜間のバッチ推論ジョブ
- D. ストリーミング応答

??? success "答えと解説"
    **正解: C**

    結果をすぐ返す必要がなく、データセット全体を処理するならバッチ推論です。ジョブの間だけ起動します。

    - A: 誤り。1 件ずつの断続的な呼び出し向けで、データセットの一括処理には向きません。
    - B: 誤り。使わない時間にも費用がかかります。
    - C: 正しい。
    - D: 誤り。応答を少しずつ返す方式で、一括処理の答えになりません。

    **スキル:** [1.1.3](../domain1.md#obj-1-1-3) / **参照:** [推論の種類](../../../services/ai-fundamentals.md#inference-types)、[バッチ変換](../../../services/sagemaker.md#batch-transform)

### 問5 {#q5}

推論の種類の説明として正しいものを選んでください。（2つ選択）

- A. サーバーレス推論は、呼び出しのない時間のコンピュートの費用がかからない
- B. リアルタイム推論は、データセット全体をまとめて処理する方式である
- C. 非同期推論は、リクエストをキューに入れて順に処理する
- D. サーバーレス推論には、コールドスタートがない
- E. バッチ推論は、1 件ずつ即座に応答を返す方式である

??? success "答えと解説"
    **正解: A, C**

    応答の速さ、入力の大きさ、呼び出しの頻度で推論の種類を選びます。

    - A: 正しい。
    - B: 誤り。それはバッチ推論の説明です。
    - C: 正しい。
    - D: 誤り。しばらく呼ばれないと、資源の準備に時間がかかるコールドスタートがあります。
    - E: 誤り。それはリアルタイム推論の説明です。

    **スキル:** [1.1.3](../domain1.md#obj-1-1-3) / **参照:** [推論の種類](../../../services/ai-fundamentals.md#inference-types)、[エンドポイントと推論](../../../services/sagemaker.md#endpoints)

### 問6 {#q6}

スタートアップが要約機能を作ります。ML エンジニアがおらず、インスタンスの管理もしたくありません。負荷も読めません。モデルの使い方として適切なものはどれですか。

- A. EC2 に GPU インスタンスを立てて公開モデルを動かす
- B. 自社のデータでゼロからモデルを学習する
- C. マネージド API として Bedrock の FM を呼ぶ
- D. SageMaker AI のエンドポイントに自分でモデルをホストする

??? success "答えと解説"
    **正解: C**

    マネージド API はインスタンスの管理が不要で、主にトークン単位で課金されるので変動する負荷に合います。

    - A: 誤り。管理の負担が最も大きくなります。
    - B: 誤り。費用が最大で、要件に対して過剰です。
    - C: 正しい。
    - D: 誤り。インスタンスの管理が必要になります。

    **スキル:** [1.3.3](../domain1.md#obj-1-3-3) / **参照:** [JumpStart](../../../services/sagemaker.md#jumpstart)

### 問7 {#q7}

自社で調整したオープンソースのモデルを、インスタンスの種類まで細かく指定して動かしたいと考えています。適切な使い方はどれですか。

- A. Amazon Quick のチャットから使う
- B. Amazon Comprehend の API を呼ぶ
- C. Bedrock のプロンプト管理にモデルの重みを登録して呼び出す
- D. SageMaker AI のエンドポイントで自前でホストする

??? success "答えと解説"
    **正解: D**

    自前のホストは管理の手間がかかる代わりに、細かく制御できます。

    - A: 誤り。業務ユーザー向けのアプリケーションで、ホスティングを制御するものではありません。
    - B: 誤り。学習済みの NLP 機能を呼ぶサービスで、自分のモデルは動きません。
    - C: 誤り。プロンプトを管理する機能で、モデルをホストするものではありません。
    - D: 正しい。

    **スキル:** [1.3.3](../domain1.md#obj-1-3-3) / **参照:** [選び方の比較](../../../services/sagemaker.md#choosing)

### 問8 {#q8}

Bedrock のオンデマンド利用と、JumpStart で自分のアカウントにデプロイする場合の違いとして正しいものはどれですか。

- A. Bedrock は主にトークン課金で、JumpStart はインスタンスの課金である
- B. どちらも呼び出しのない時間に費用が発生しない
- C. どちらも利用者がインスタンスの種類と台数を管理する
- D. Bedrock はインスタンスの課金で、JumpStart はトークン課金である

??? success "答えと解説"
    **正解: A**

    JumpStart は自分のインスタンスで動かすので起動時間に、Bedrock は API の利用量に課金されます。

    - A: 正しい。
    - B: 誤り。JumpStart のエンドポイントはインスタンスの起動時間で課金されます。
    - C: 誤り。Bedrock のオンデマンドでは管理しません。
    - D: 誤り。逆です。

    **スキル:** [1.3.3](../domain1.md#obj-1-3-3) / **参照:** [JumpStart](../../../services/sagemaker.md#jumpstart)、[料金の形とコスト管理](../../../services/ai-fundamentals.md#ai-pricing)

### 問9 {#q9}

企業が FM を用意する方法を検討しています。費用と手間が最も大きく、ほとんどの場合に不要なものはどれですか。

- A. 提供者のモデルを API で使う
- B. 自社のデータでゼロからモデルを学習する
- C. 既存のモデルをプロンプトで業務に合わせる
- D. 公開された事前学習済みモデルをデプロイする

??? success "答えと解説"
    **正解: B**

    ゼロからの学習は大量のデータと計算資源が必要で、既存のモデルで足りないときだけ検討します。

    - A: 誤り。学習が不要で、手間と費用は最も小さい方法です。
    - B: 正しい。
    - C: 誤り。推論の費用だけで試せる、最も軽い方法です。
    - D: 誤り。学習は済んでいるので、ゼロからの学習より大幅に軽くなります。

    **スキル:** [1.3.2](../domain1.md#obj-1-3-2) / **参照:** [モデルを業務に合わせる方法](../../../services/ai-fundamentals.md#customization-options)、[FM のライフサイクル](../../../services/ai-fundamentals.md#fm-lifecycle)

### 問10 {#q10}

公開された事前学習済みの FM を選び、数回の操作で自分のエンドポイントにデプロイしたいと考えています。適切な機能はどれですか。

- A. Amazon Bedrock Knowledge Bases
- B. SageMaker Pipelines
- C. SageMaker JumpStart
- D. SageMaker Model Cards

??? success "答えと解説"
    **正解: C**

    JumpStart は事前学習済みモデルのハブで、Studio の画面から設定済みのエンドポイントへデプロイできます。

    - A: 誤り。文書を検索して答える機能で、モデルをデプロイする機能ではありません。
    - B: 誤り。ML のワークフローを自動化する機能で、モデルのハブではありません。
    - C: 正しい。
    - D: 誤り。モデルの情報を記録する機能で、デプロイの機能ではありません。

    **スキル:** [1.3.2](../domain1.md#obj-1-3-2) / **参照:** [JumpStart](../../../services/sagemaker.md#jumpstart)

### 問11 {#q11}

FM の入手元とその特徴の対応として正しいものはどれですか。

- A. 提供者のモデル: API ですぐ使える
- B. 自社で学習したモデル: 学習の費用がかからない
- C. 提供者のモデル: 使う前に必ず自社で事前学習が必要である
- D. オープンソースのモデル: 重みが公開されないので、自分では制御できない

??? success "答えと解説"
    **正解: A**

    入手元は、提供者のモデル、オープンソースの事前学習済みモデル、自社での学習の 3 つで考えます。

    - A: 正しい。
    - B: 誤り。学習の費用は最も大きくなります。
    - C: 誤り。事前学習は提供者が済ませています。
    - D: 誤り。公開された重みを使うので、自分で制御しやすい入手元です。

    **スキル:** [1.3.2](../domain1.md#obj-1-3-2) / **参照:** [FM のライフサイクル](../../../services/ai-fundamentals.md#fm-lifecycle)
