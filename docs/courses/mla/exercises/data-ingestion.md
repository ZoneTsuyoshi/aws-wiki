# データの収集と保存の問題集

対象の解説: [S3](../../../services/s3.md)、[ストレージの比較](../../../services/storage-advanced.md#storage-comparison)、[Glue](../../../services/data-engineering.md#glue)

### 問1 {#q1}

ある EC サイトの注文データは DynamoDB にあり、本番の読み書きに余裕がありません。週に 1 回、全件を S3 に出力して学習に使います。本番への影響を最小にする方法はどれですか。

- A. PITR を有効にして、テーブルを S3 へエクスポートする
- B. DynamoDB Streams を Lambda で読み、過去の全件を S3 へ再生する
- C. Glue ジョブからテーブルを直接 Scan して、Parquet に変換して S3 に書き込む
- D. Lambda で全件を Scan して、結果を S3 に書き込む

??? success "答えと解説"
    **正解: A**

    S3 へのエクスポートは PITR を使う非同期の処理で、読み取りキャパシティを消費しません。出力は DynamoDB JSON か Amazon Ion です。

    - A: 正しい。
    - B: 誤り。Streams は変更の記録で、過去の全件を取り出す手段ではありません。
    - C: 誤り。これも読み取りキャパシティを消費します。
    - D: 誤り。Scan は読み取りキャパシティを消費し、本番に負荷がかかります。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [DynamoDB のバックアップ](../../../services/dynamodb.md#backup)

### 問2 {#q2}

学習データは 2 TB で S3 にあります。データをすべて読むのではなく一部の読み取りが中心で、ジョブの開始までの時間を短くしたいです。学習ジョブの入力モードはどれですか。

- A. EBS ボリュームへの事前コピーを行う File モード
- B. FastFile モード
- C. データをまとめて 1 つの gzip にした File モード
- D. File モード

??? success "答えと解説"
    **正解: B**

    FastFile は開始時にファイルを確認するだけで、読むときに S3 から取得します。開始を待たずにファイルとしてアクセスできます。

    - A: 誤り。コピーの分だけ開始が遅れ、File モードと同じ問題が残ります。
    - B: 正しい。
    - C: 誤り。全量のダウンロードは変わらず、gzip は分割して読むこともできません。
    - D: 誤り。開始前に全データをダウンロードするので、開始が遅くなります。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [入力モード](../../../services/sagemaker.md#input-modes)

### 問3 {#q3}

共有の EFS にある学習データを、SageMaker AI の学習ジョブで読みます。S3 にコピーせず、チャネルとして渡します。チャネルの入力モードはどれにしますか。

- A. オフラインストアモード
- B. Pipe モード
- C. File モード
- D. FastFile モード

??? success "答えと解説"
    **正解: C**

    EFS と FSx for Lustre をチャネルに指定するときは File モードを使います。ファイルシステムをマウントして読みます。

    - A: 誤り。そのような入力モードはありません。オフラインストアは Feature Store の機能です。
    - B: 誤り。Pipe は S3 から直接ストリームする方式です。
    - C: 正しい。
    - D: 誤り。FastFile は S3 のデータソース向けです。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [入力モード](../../../services/sagemaker.md#input-modes)

### 問4 {#q4}

読み取りが頻繁で、1 桁ミリ秒の応答が必要な特徴量のファイルを S3 に置きます。単一の AZ でも許容できます。どのストレージクラスを選びますか。

- A. S3 Intelligent-Tiering
- B. S3 Glacier Instant Retrieval
- C. S3 Standard-IA
- D. S3 Express One Zone

??? success "答えと解説"
    **正解: D**

    S3 Express One Zone は、単一の AZ で 1 桁ミリ秒の読み書きを提供します。

    - A: 誤り。アクセスの傾向が不明なデータのコストを下げる選択で、1 桁ミリ秒を目的としていません。
    - B: 誤り。長期保管のデータ向けで、頻繁な読み取りにはコストが合いません。
    - C: 誤り。低頻度のアクセス向けで、頻繁な読み取りには合いません。
    - D: 正しい。

    **スキル:** [1.1.2](../domain1.md#skill-1-1-2) / **参照:** [ストレージクラス](../../../services/s3.md#storage-classes)

### 問5 {#q5}

学習が終わった実験データを規制で 7 年保管します。読み出すのは年 1 回未満で、取り出しに時間がかかっても問題ありません。保管コストを最小にするには、どの組み合わせが適切ですか。

- A. S3 Standard に置き、バージョニングで保護する
- B. 1 台の EC2 に EBS を付けて保管する
- C. EFS の Elastic スループットで保管する
- D. ライフサイクルで S3 Glacier Deep Archive へ移す

??? success "答えと解説"
    **正解: D**

    読むことがまれな長期保管には Glacier Deep Archive が合います。ライフサイクルで自動的に移せます。

    - A: 誤り。保管単価が高く、コスト最小になりません。
    - B: 誤り。運用の手間とコストが増え、長期保管に向きません。
    - C: 誤り。共有ファイルシステムの選択で、長期保管の単価は高くなります。
    - D: 正しい。

    **スキル:** [1.1.2](../domain1.md#skill-1-1-2) / **参照:** [ライフサイクル](../../../services/s3.md#lifecycle)、[ストレージクラス](../../../services/s3.md#storage-classes)

### 問6 {#q6}

GPU のインスタンスを多数使う学習で、S3 の大量の学習データを高いスループットで読ませたいです。データの本体は S3 に残します。最も適切なストレージはどれですか。

- A. S3 と連携させた FSx for Lustre
- B. EFS の Bursting スループット
- C. S3 Glacier Flexible Retrieval
- D. 各インスタンスの EBS に毎回コピーする

??? success "答えと解説"
    **正解: A**

    FSx for Lustre は S3 と連携でき、大量のデータを GPU へ高速に渡す場面に向きます。

    - A: 正しい。
    - B: 誤り。大量の読み取りでクレジットが切れると遅くなります。
    - C: 誤り。長期保管のクラスで、学習データの読み取りには使えません。
    - D: 誤り。1 台の低遅延ディスクの選択で、多数のノードで共有できません。

    **スキル:** [1.1.2](../domain1.md#skill-1-1-2) / **参照:** [Lustre と S3](../../../services/storage-advanced.md#fsx-lustre-s3)、[ストレージの比較](../../../services/storage-advanced.md#storage-comparison)

### 問7 {#q7}

取り込みジョブが 1 つの S3 プレフィックスに短時間で書き込みを集中させ、HTTP 503（Slow Down）を受けています。最初に行う対応として適切なものはどれですか。

- A. バケットのデフォルトの暗号化を SSE-KMS に変える
- B. ストレージクラスを S3 Standard-IA に変える
- C. キーを複数のプレフィックスに分散し、指数バックオフで再試行する
- D. バケットのバージョニングを有効にする

??? success "答えと解説"
    **正解: C**

    S3 のリクエストレートはプレフィックスごとにスケールします。書き込み先を分散し、再試行にバックオフを入れます。

    - A: 誤り。暗号化の方式は 503 の原因ではなく、解決にもなりません。
    - B: 誤り。ストレージクラスの変更はリクエストレートに関係しません。
    - C: 正しい。
    - D: 誤り。リクエストレートは改善しません。バージョニングはむしろ負荷の要因になることがあります。

    **スキル:** [1.1.3](../domain1.md#skill-1-1-3) / **参照:** [S3 のリクエストレート](../../../services/s3.md#request-rate)

### 問8 {#q8}

EFS をデータ置き場にした学習で、数時間後からファイルの読み取りが急に遅くなりました。スループットモードは Bursting です。原因と対応の組み合わせとして正しいものはどれですか。

- A. ライフサイクルが原因です。バージョニングを有効にします
- B. クレジット切れが原因です。Elastic か Provisioned に変更します
- C. 入力モードが原因です。Pipe に変更します
- D. チャネル名の誤りが原因です。学習ジョブを作り直します

??? success "答えと解説"
    **正解: B**

    Bursting のクレジットが切れるとスループットが下がります。継続して読むなら Elastic か Provisioned に変えます。

    - A: 誤り。EFS の遅さをバージョニングでは解決できません。
    - B: 正しい。
    - C: 誤り。EFS のチャネルは File モードで使います。数時間後に遅くなる症状とも合いません。
    - D: 誤り。チャネル名の誤りなら開始時に失敗します。途中から遅くなる症状と合いません。

    **スキル:** [1.1.3](../domain1.md#skill-1-1-3) / **参照:** [EFS のスループット](../../../services/storage.md#efs-throughput-mode)

### 問9 {#q9}

Hive 形式で S3 に日付パーティションを毎日追加しています。データはあるのに、Athena で新しい日付の行が返りません。追加の ETL を増やさずに直す方法はどれですか。

- A. Parquet を CSV に変換する
- B. S3 のライフサイクルで新しいデータを別のストレージクラスへ移す
- C. Athena のワークグループを作り直す
- D. `MSCK REPAIR TABLE` かクローラーでカタログへ登録する

??? success "答えと解説"
    **正解: D**

    新しいパーティションはカタログに未登録だとクエリの対象になりません。`MSCK REPAIR TABLE` やクローラーで同期します。

    - A: 誤り。形式は原因ではありません。
    - B: 誤り。登録の問題は解決せず、コストの設定を変えるだけです。
    - C: 誤り。ワークグループはカタログの登録状態を変えません。
    - D: 正しい。

    **スキル:** [1.1.3](../domain1.md#skill-1-1-3) / **参照:** [パーティションの同期](../../../services/data-engineering.md#partition-sync)

### 問10 {#q10}

列が 150 ある CSV のログを Athena で集計しています。クエリはいつも 5 列だけ読みますが、スキャン料金が高いです。最も効果のある変更はどれですか。

- A. CSV 全体を gzip の 1 ファイルにまとめる
- B. S3 Standard-IA に移して、保管料金を下げる
- C. Parquet に変換して、日付でパーティションを切る
- D. JSON Lines に変換して、キー名でも検索できるようにする

??? success "答えと解説"
    **正解: C**

    列指向の Parquet なら必要な列だけ読め、パーティションで範囲も絞れます。変換は Athena の CTAS や Glue のジョブで行います。

    - A: 誤り。圧縮でスキャン量は減りますが、列を選んで読めず、1 ファイルの gzip は分割もできません。
    - B: 誤り。スキャン料金は変わりません。
    - C: 正しい。
    - D: 誤り。行指向のままで、不要な列まで読みます。

    **スキル:** [1.1.5](../domain1.md#skill-1-1-5) / **参照:** [データ形式](../../../services/data-engineering.md#data-formats)、[パーティション](../../../services/data-engineering.md#partitioning)

### 問11 {#q11}

外部の取引先から入れ子の JSON ログを毎日受け取ります。学習の前に分析しやすくしたいです。データの扱いとして適切なものはどれですか。（2つ選択）

- A. 検索を速くするため、JSON を EBS に置く
- B. 分析と学習の用途には Parquet に変換する
- C. 原本は JSON のまま S3 に保存する
- D. 分析の速度を上げるため、1 つの大きな gzip にまとめる
- E. すべての列を CSV に平坦化し、原本は削除する

??? success "答えと解説"
    **正解: B, C**

    原本は残し、分析用には列指向の形式に変換します。JSON はログや API、入れ子のデータに向く行指向の形式です。

    - A: 誤り。1 台からの利用に限られ、データレイクの選択になりません。
    - B: 正しい。列指向の形式で、必要な列だけ読めます。
    - C: 正しい。受け取った形式を残しておけば、再処理できます。
    - D: 誤り。gzip の大きな 1 ファイルは分割して読めません。
    - E: 誤り。スキーマがなくなり、入れ子の情報も再現できません。

    **スキル:** [1.1.5](../domain1.md#skill-1-1-5) / **参照:** [データ形式](../../../services/data-engineering.md#data-formats)

### 問12 {#q12}

Glue のジョブを Parquet で出力します。後続の Spark でファイルを並列に読みたいです。圧縮の選択として適切なものはどれですか。

- A. 圧縮率を優先して、全データを zip の 1 ファイルにする
- B. Parquet の中で Snappy を使う
- C. ORC と CSV を同じ場所に混在させる
- D. ファイル全体を gzip で 1 つに圧縮した CSV を出力する

??? success "答えと解説"
    **正解: B**

    Parquet は内部の圧縮に Snappy などを使えます。ファイル全体を圧縮する方法と違い、分割して並列に読めます。

    - A: 誤り。1 つの圧縮ファイルは並列の読み取りに向きません。
    - B: 正しい。
    - C: 誤り。形式が混ざるとスキーマの扱いが難しくなり、圧縮の解決にもなりません。
    - D: 誤り。大きな gzip は分割して読めないので、並列に処理できません。

    **スキル:** [1.1.5](../domain1.md#skill-1-1-5) / **参照:** [データ形式](../../../services/data-engineering.md#data-formats)

### 問13 {#q13}

複数の S3 のカタログテーブルと RDS のマスターを結合します。Spark のコードは書けますが、クラスターは管理したくありません。データは数 TB です。どれを選びますか。

- A. Glue の Spark ジョブ
- B. Processing ジョブの pandas で全件をメモリに読み込む
- C. EMR に長時間動くクラスターを作る
- D. Data Wrangler の画面で毎回手で結合する

??? success "答えと解説"
    **正解: A**

    Glue はカタログと連携するサーバーレスの Spark です。クラスターを管理せずに大規模な結合ができます。

    - A: 正しい。
    - B: 誤り。数 TB はメモリに載りません。
    - C: 誤り。クラスターの管理が増えます。既存の Spark コードや細かな調整が要る場面の選択です。
    - D: 誤り。画面で試す用途で、定期的な大規模処理には向きません。

    **スキル:** [1.1.6](../domain1.md#skill-1-1-6) / **参照:** [Glue のジョブ](../../../services/data-engineering.md#glue-jobs)、[変換エンジンの選び方](../../../services/data-engineering.md#choosing-transform)

### 問14 {#q14}

大きなテーブルを結合する Glue の Spark ジョブで、エグゼキューターのメモリ不足が起きています。処理の内容は変えたくありません。最も直接の対応はどれですか。

- A. 出力の形式を Parquet から CSV に変える
- B. ジョブのブックマークを有効にして、処理の位置を記録する
- C. メモリの多い `R` タイプか大きなワーカーに変える
- D. タイムアウトを延ばして、同じ構成で再実行する

??? success "答えと解説"
    **正解: C**

    結合が重いジョブでエグゼキューターが OOM になるなら、メモリの多いワーカーに変えます。

    - A: 誤り。結合時のメモリには関係しません。
    - B: 誤り。ブックマークは処理済みの追跡で、メモリ不足を解決しません。
    - C: 正しい。
    - D: 誤り。時間を延ばしてもメモリは増えません。

    **スキル:** [1.1.6](../domain1.md#skill-1-1-6) / **参照:** [Glue のジョブ](../../../services/data-engineering.md#glue-jobs)

### 問15 {#q15}

過去の取引から翌月の解約を予測します。顧客マスターと取引履歴を結合したところ、検証の結果だけが異常によくなりました。最も疑うべき原因と対応はどれですか。

- A. 結合のキーが多すぎる。キーを 1 つに減らして結合する
- B. 予測の時点より後の値を結合している。時点をそろえて結合する
- C. データ形式が CSV である。Parquet に変えて結合する
- D. インスタンスが小さすぎる。大きいインスタンスで学習し直す

    **正解: B**

    時系列の結合で未来の情報が混ざると、検証の結果だけがよくなります。予測の時点までの値だけを結合します。

    - A: 誤り。キーを減らすと、誤った行が結合されるおそれがあります。
    - B: 正しい。
    - C: 誤り。形式の変更は読み取りの効率の問題で、指標とは無関係です。
    - D: 誤り。インスタンスのサイズは検証の指標を不自然によくする原因になりません。

本番の RDS のデータを学習用に定期的に取り出します。本番への負荷に注意しつつ、S3 に Parquet で出力します。適切な方法はどれですか。
