# Bedrock の FM の選択とデプロイの問題集

対象の解説: [FM の選定の観点](../../../services/genai-apps.md#fm-criteria)、[デプロイ戦略](../../../services/genai-apps.md#deployment)、[スループットの選択肢](../../../services/ai.md#throughput-options)

### 問1 {#q1}

図表を含む提案書を読ませて、要点をすぐ返す対話アプリです。FM を絞り込むときに見る観点の組み合わせとして適切なものはどれですか。

- A. マルチモーダルの対応と `TimeToFirstToken`
- B. `ContextCoverage` と `Faithfulness`
- C. 量子化の対応とモデルユニットの数
- D. `schemaVersion` と蒸留の対応

??? success "答えと解説"
    **正解: A**

    図表を読むならマルチモーダル、対話なら最初のトークンまでの時間を見ます。

    - A: 正しい。
    - B: 誤り。RAG の評価指標で、FM を絞り込む観点ではありません。
    - C: 誤り。自前のホストや容量の話で、要件のモデルの能力を絞り込む観点ではありません。
    - D: 誤り。カスタマイズの観点で、この要件に関係しません。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [FM の選定の観点](../../../services/genai-apps.md#fm-criteria)

### 問2 {#q2}

使っているモデルが End-of-Life（EOL）に達すると、どうなりますか。

- A. Provisioned Throughput があれば、期限なく使える
- B. 最新のモデルへ自動で移行される
- C. 料金が半額になり、そのまま使える
- D. リクエストは失敗する。自動の移行はない

??? success "答えと解説"
    **正解: D**

    EOL に達するとリクエストは失敗し、自動の移行はありません。状態を確認し、モデル ID は設定で変えられるようにします。

    - A: 誤り。EOL に達すれば使えません。
    - B: 誤り。自動の移行はありません。
    - C: 誤り。EOL に達するとリクエストは失敗します。
    - D: 正しい。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [モデルのライフサイクル](../../../services/genai-apps.md#model-lifecycle)

### 問3 {#q3}

長期運用するアプリで FM の状態を定期的に確認します。正しい運用はどれですか。（2つ選択）

- A. 全モデルを Provisioned Throughput にしておく
- B. `ListFoundationModels` で Active、Legacy、EOL の状態を確認する
- C. モデル ID をコードに固定せず、設定で変えられるようにする
- D. EOL のあとも動くので、確認しなくてよい
- E. Legacy になったら再学習が自動で始まるので、待つ

??? success "答えと解説"
    **正解: B, C**

    ライフサイクルを確認し、移行しやすいようにモデル ID を設定に出します。

    - A: 誤り。EOL の対策になりません。
    - B: 正しい。
    - C: 正しい。
    - D: 誤り。EOL に達するとリクエストは失敗します。
    - E: 誤り。自動の処理はありません。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [モデルのライフサイクル](../../../services/genai-apps.md#model-lifecycle)

### 問4 {#q4}

問い合わせの 8 割は定型で、残りは難しい質問です。品質を保ちつつ FM のコストを下げます。Nova の系統のモデルだけを使います。最も管理の手間が少ない方法はどれですか。

- A. 判定の処理を自分で作って、モデルカスケードにする
- B. Intelligent Prompt Routing
- C. 全問い合わせを最上位のモデルに送る
- D. Provisioned Throughput を 2 つ買う

??? success "答えと解説"
    **正解: B**

    Intelligent Prompt Routing は、同じ系統のモデルから Bedrock が選びます。

    - A: 誤り。実現できますが、判定の処理を作る手間があります。
    - B: 正しい。
    - C: 誤り。コストが下がりません。
    - D: 誤り。モデルの選択の機能ではなく、コストも下がりません。

    **スキル:** [2.1.7](../domain2.md#skill-2-1-7) / **参照:** [動的なモデル切り替え](../../../services/genai-apps.md#dynamic-model-selection)

### 問5 {#q5}

対話アプリで、全体の処理時間は変えずに体感の待ち時間を減らします。適切な変更はどれですか。

- A. バッチ推論に切り替える
- B. Flex 層に切り替える
- C. ストリーミングで返す
- D. `maxTokens` を最大にする

??? success "答えと解説"
    **正解: C**

    ストリーミングは最初の応答が早く届くので、体感の待ち時間が減ります。全体の時間は変わりません。

    - A: 誤り。遅くなります。対話には向きません。
    - B: 誤り。安くなりますが遅くなります。
    - C: 正しい。
    - D: 誤り。体感の待ち時間は減らず、スロットリングの原因になります。

    **スキル:** [2.1.7](../domain2.md#skill-2-1-7) / **参照:** [遅延の短縮](../../../services/genai-apps.md#latency)

### 問6 {#q6}

毎晩の 100 万件の文書の要約です。翌朝に終わればよく、できるだけ安くします。どれを選びますか。

- A. Provisioned Throughput を 24 時間動かす
- B. Priority 層
- C. 対象モデルのバッチ推論
- D. モデルカスケードだけを使う

??? success "答えと解説"
    **正解: C**

    急がない大量処理はバッチ推論です。対象のモデルでオンデマンドの 50% 引きです。

    - A: 誤り。時間課金で、夜間だけの処理には無駄が多くなります。
    - B: 誤り。割増で、急ぐ処理向けです。
    - C: 正しい。
    - D: 誤り。難しい質問の振り分けで、夜間の処理の割引にはなりません。

    **スキル:** [2.1.7](../domain2.md#skill-2-1-7) / **参照:** [Bedrock の料金](../../../services/cost-management.md#bedrock-pricing)

### 問7 {#q7}

利用者の増減が読めない新規の社内アプリで、FM を素早く使い始めます。どのデプロイ方式ですか。

- A. Bedrock のオンデマンド
- B. Bedrock の Provisioned Throughput の長期コミットメント
- C. SageMaker JumpStart で GPU を常時動かす
- D. HyperPod のクラスターを作る

??? success "答えと解説"
    **正解: A**

    変動する負荷で小さく始めるなら、トークン課金のオンデマンドです。

    - A: 正しい。
    - B: 誤り。固定の大きな処理量向けです。
    - C: 誤り。運用の手間とアイドルのコストがかかります。
    - D: 誤り。大規模な FM の学習や推論のクラスターで、小さく始める選択ではありません。

    **スキル:** [3.1.4](../domain3.md#skill-3-1-4) / **参照:** [デプロイ戦略](../../../services/genai-apps.md#deployment)

### 問8 {#q8}

モデルの重みやサーバーの GPU を細かく制御し、VPC の中で FM をホストします。どの方式ですか。

- A. Bedrock のバッチ
- B. SageMaker JumpStart
- C. Comprehend のカスタムモデル
- D. Bedrock のオンデマンド

??? success "答えと解説"
    **正解: B**

    モデルと GPU を細かく制御するなら SageMaker JumpStart です。起動の遅さや高価なアイドルへの対応は必要です。

    - A: 誤り。GPU を制御できません。
    - B: 正しい。
    - C: 誤り。FM のホスティングではありません。
    - D: 誤り。GPU を制御できません。

    **スキル:** [3.1.4](../domain3.md#skill-3-1-4) / **参照:** [JumpStart](../../../services/sagemaker.md#jumpstart)、[デプロイ戦略](../../../services/genai-apps.md#deployment)

### 問9 {#q9}

カスタムモデルを常に一定の大きな処理量で動かします。Bedrock の中で選ぶ方式はどれですか。

- A. バッチ変換
- B. Flex 層
- C. オンデマンドのスポット
- D. Provisioned Throughput

??? success "答えと解説"
    **正解: D**

    固定の大きな処理量やカスタムモデルには、モデルユニットで時間課金の Provisioned Throughput を選びます。

    - A: 誤り。SageMaker AI の機能です。
    - B: 誤り。遅くても安い層で、カスタムの固定の処理量向けの方式ではありません。
    - C: 誤り。Bedrock にそのような方式はありません。
    - D: 正しい。

    **スキル:** [3.1.4](../domain3.md#skill-3-1-4) / **参照:** [推論の容量](../../../services/genai-apps.md#inference-profiles)

### 問10 {#q10}

複数の FM を 1 台の GPU のエンドポイントで共有し、モデルごとに資源を割り当てます。SageMaker AI のどの機能ですか。

- A. マルチモデルエンドポイント
- B. マルチコンテナエンドポイント
- C. 推論コンポーネント
- D. 推論パイプライン

??? success "答えと解説"
    **正解: C**

    推論コンポーネントは、モデルごとに CPU、GPU、メモリを割り当てます。

    - A: 誤り。同じフレームワークの似たモデルを多数載せる機能で、モデルごとに資源を割り当てません。
    - B: 誤り。別のコンテナを同居させる機能で、モデルごとの資源の割り当てとは別です。
    - C: 正しい。
    - D: 誤り。コンテナを順に実行する機能です。

    **スキル:** [3.1.7](../domain3.md#skill-3-1-7) / **参照:** [マルチモデルと推論コンポーネント](../../../services/sagemaker.md#multi-model)

### 問11 {#q11}

LLM の GPU メモリが足りません。多少の精度の低下は許容できます。インスタンスのサイズは変えません。どの最適化が適切ですか。

- A. 量子化
- B. コンパイルだけを行う
- C. スペキュレイティブデコーディング
- D. 推論コンポーネントのコピーを増やす

??? success "答えと解説"
    **正解: A**

    量子化はメモリを減らせますが、精度が少し落ちることがあります。コンパイルは精度が落ちません。

    - A: 正しい。
    - B: 誤り。精度は落ちませんが、この場面の直接の対策ではありません。
    - C: 誤り。生成を速くする手法で、メモリの不足は解決しません。
    - D: 誤り。多くのメモリが必要になります。

    **スキル:** [3.1.7](../domain3.md#skill-3-1-7) / **参照:** [推論の最適化](../../../services/sagemaker.md#inference-optimization)

### 問12 {#q12}

Bedrock の Provisioned Throughput のモデルユニット数を見積もります。使う情報はどれですか。

- A. `ModelLatency` の平均
- B. `InputTokenCount` と `OutputTokenCount` のピーク
- C. `TimeToFirstToken` の p99
- D. `Invocations` の月間の合計

??? success "答えと解説"
    **正解: B**

    モデルユニットの数は `InputTokenCount` と `OutputTokenCount` のピークから見積もります。

    - A: 誤り。SageMaker AI の指標で、容量の見積もりに使うものではありません。
    - B: 正しい。
    - C: 誤り。遅延の指標で、必要な処理量を示しません。
    - D: 誤り。月の合計ではピークの処理量が分かりません。

    **スキル:** [3.1.7](../domain3.md#skill-3-1-7) / **参照:** [推論の容量](../../../services/genai-apps.md#inference-profiles)

### 問13 {#q13}

需要が読めず、平均の使用率が低い Bedrock のアプリがあります。Provisioned Throughput を削除するまで課金が続くと分かりました。どの判断が適切ですか。

- A. 長期コミットメントに変えて、割引の分だけ使用率を下げる
- B. Provisioned Throughput はアイドルなら課金されないので、そのままにする
- C. 使用率が低いので、モデルユニットを増やす
- D. オンデマンドに戻す

??? success "答えと解説"
    **正解: D**

    Provisioned Throughput は一定で大きな負荷向けです。変動する負荷にはオンデマンドが合います。

    - A: 誤り。使用率が低いと無駄になり、期間中は削除もできません。
    - B: 誤り。削除するまで時間課金です。
    - C: 誤り。無駄がさらに増えます。
    - D: 正しい。

    **スキル:** [3.2.1](../domain3.md#skill-3-2-1) / **参照:** [スループットの選択肢](../../../services/ai.md#throughput-options)

### 問14 {#q14}

Bedrock の Provisioned Throughput で 1 か月のコミットメントを選びました。2 週間後に不要になりました。どうなりますか。

- A. 使わない間は課金が止まる
- B. すぐに削除でき、残りの料金は返金される
- C. 期間が終わるまで削除できない
- D. 自動でオンデマンドに切り替わる

??? success "答えと解説"
    **正解: C**

    コミットメントの期間中は削除できません。コミットなしなら、いつでも削除できます。

    - A: 誤り。時間課金は続きます。
    - B: 誤り。コミットメントの期間中は削除できません。
    - C: 正しい。
    - D: 誤り。自動の切り替えはありません。

    **スキル:** [3.2.1](../domain3.md#skill-3-2-1) / **参照:** [スループットの選択肢](../../../services/ai.md#throughput-options)

### 問15 {#q15}

SageMaker AI のエンドポイントの負荷が、予測できるバーストを持ちます。サーバーレス推論で、コールドスタートを抑えます。どの機能ですか。

- A. Savings Plans
- B. Provisioned Concurrency
- C. シャドウバリアント
- D. バッチ変換

??? success "答えと解説"
    **正解: B**

    予測できるバーストには、サーバーレスの Provisioned Concurrency を使います。

    - A: 誤り。割引の仕組みで、コールドスタートに関係しません。
    - B: 正しい。
    - C: 誤り。テストの機能です。
    - D: 誤り。データセット全体を処理する方式です。

    **スキル:** [3.2.1](../domain3.md#skill-3-2-1) / **参照:** [サーバーレス](../../../services/sagemaker.md#serverless)
