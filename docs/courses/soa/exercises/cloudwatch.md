### 問1 {#q1}

アプリケーションのログは CloudWatch Logs に届いています。ログに `ERROR` が 5 分間で 10 件を超えたら、担当者へ通知したいと考えています。最も運用負荷の小さい方法はどれですか。

- A. サブスクリプションフィルターの送信先に SNS トピックを直接指定し、件数はメールの本文で数える
- B. ロググループを 5 分おきに S3 へエクスポートし、Athena のクエリで件数を数えて判定する
- C. メトリクスフィルターで `ERROR` を数えてメトリクスにし、そのメトリクスのアラームから SNS へ通知する
- D. Logs Insights のクエリを担当者が 5 分おきにコンソールで実行し、件数を目視で確かめて連絡する

??? success "答えと解説"
    **正解: C**

    ログの文字列を数えてアラームの元にするのが、メトリクスフィルターの用途です。

    - A: 誤り。SNS はサブスクリプションフィルターの送信先にできず、件数のしきい値も判定できない。
    - B: 誤り。エクスポートはリアルタイムの監視向けではなく、仕組みも複雑になる。
    - C: 正しい。
    - D: 誤り。調査用の機能で、手作業が続くので運用負荷が高い。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [メトリクスフィルター](../../../services/observability.md#metric-filters)、[アラーム](../../../services/observability.md#alarms)

### 問2 {#q2}

監査担当者から、ルートユーザーの API 利用を検知してアラームで通知するよう求められました。組み合わせとして適切なものはどれですか。

- A. CloudTrail の証跡を CloudWatch Logs へ送り、メトリクスフィルターとアラームを作る
- B. `AWS/EC2` の既定メトリクスに含まれる API 呼び出し数のメトリクスでアラームを作って通知する
- C. Compute Optimizer の推奨をオプトインし、ルートユーザーによる変更を推奨の結果から読み取る
- D. CloudWatch エージェントをすべての EC2 に入れ、OS の認証ログを CloudWatch Logs へ送ってアラームを作る

??? success "答えと解説"
    **正解: A**

    誰が何をしたかは CloudTrail で記録します。CloudWatch Logs へ送れば、メトリクスフィルターで数えてアラームにできます。

    - A: 正しい。
    - B: 誤り。`AWS/EC2` は性能のメトリクスで、誰が操作したかは分からない。
    - C: 誤り。Compute Optimizer はリソースのサイズの推奨で、監査には使えない。
    - D: 誤り。ルートユーザーの AWS API の利用は OS の認証ログには現れない。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [CloudWatch と CloudTrail の違い](../../../services/observability.md#cloudtrail-vs-cloudwatch)、[メトリクスフィルター](../../../services/observability.md#metric-filters)

### 問3 {#q3}

ロググループに届くログを、ほぼリアルタイムで Data Firehose へ流し、分析用の S3 に保存したいと考えています。どの機能を使いますか。

- A. Logs Insights のクエリの結果をダッシュボードに表示するウィジェット
- B. `CreateExportTask` による S3 へのエクスポート
- C. メトリクスフィルター
- D. サブスクリプションフィルター

??? success "答えと解説"
    **正解: D**

    サブスクリプションフィルターは、ログをほぼリアルタイムで Lambda や Firehose などへ送ります。

    - A: 誤り。調査や表示の機能で、ログの転送はしない。
    - B: 誤り。リアルタイムではなく、Firehose にも送らない。
    - C: 誤り。ログを数えてメトリクスにする機能で、ログそのものは転送しない。
    - D: 正しい。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [サブスクリプションフィルター](../../../services/observability.md#subscription-filters)

### 問4 {#q4}

Amazon Bedrock を使うアプリケーションのプロンプトと応答を、監査のために残すよう求められました。設定を変えていないアカウントの状態と対処として正しいものはどれですか。

- A. `AWS/Bedrock` のメトリクスの詳細モニタリングを有効にすると、プロンプトの全文が取得できるようになる
- B. モデル呼び出しログは既定で無効なので有効にし、送信先に CloudWatch Logs か S3 を指定する
- C. CloudWatch エージェントを Bedrock のエンドポイントに導入して、呼び出しの内容を収集する設定を加える
- D. プロンプトと応答は既定で CloudTrail の管理イベントに全文が記録されるので、追加の設定は不要である

??? success "答えと解説"
    **正解: B**

    モデル呼び出しログは既定で無効です。送信先は CloudWatch Logs と S3 です。

    - A: 誤り。メトリクスは数値であり、プロンプトの本文は入らない。
    - B: 正しい。
    - C: 誤り。Bedrock はマネージドサービスで、エージェントを入れる場所がない。
    - D: 誤り。既定では全文は残らないため、モデル呼び出しログを有効にする必要がある。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [モデル呼び出しログ](../../../services/ai.md#invocation-logging)、[CloudWatch のメトリクス](../../../services/ai.md#bedrock-metrics)

EKS のクラスターで PromQL のクエリと Grafana のダッシュボードをすでに運用しています。Prometheus のサーバーの管理をやめ、既存のクエリとダッシュボードをできるだけ流用したいと考えています。最も適切なものはどれですか。

- A. Managed Service for Prometheus と Managed Grafana を使う
- B. Container Insights に統一し、PromQL のクエリを Logs Insights の構文へ書き換えて移行する
- C. X-Ray のサービスマップに切り替え、ダッシュボードをすべて作り直して運用を一本化する

??? success "答えと解説"
    **正解: A**

    - C: 誤り。トレースの機能で、Prometheus のメトリクスの代わりにはならない。

### 問7 {#q7}

Auto Scaling グループの EC2 のメモリ使用率でスケールしたいと考えています。`AWS/EC2` にメモリのメトリクスが見つかりません。詳細モニタリングは有効です。どう対応しますか。

- A. Compute Optimizer をオプトインし、そのメモリの推奨値をスケーリングのメトリクスに指定する
- B. ハイパーバイザーの情報を読む `DescribeInstanceStatus` の結果から、メモリの使用率を計算する
- C. 詳細モニタリングの間隔を 1 秒に短くすると、メモリのメトリクスが自動的に追加される
- D. CloudWatch エージェントでメモリを送り、`aggregation_dimensions` に `AutoScalingGroupName` を指定する

??? success "答えと解説"
    **正解: D**

    OS の中の値はエージェントで送ります。`aggregation_dimensions` で、グループ単位に集約したメトリクスを作れます。

    - A: 誤り。推奨値はスケーリングのメトリクスにならない。
    - B: 誤り。ステータスチェックの API で、OS の中の値は得られない。
    - C: 誤り。詳細モニタリングは間隔を 1 分にするだけで、メモリは増えない。

数百台の EC2 に CloudWatch エージェントを導入し、同じ設定を使いたいと考えています。手順として適切なものを選んでください。（2つ選択）

- A. インスタンスのロールに `CloudWatchAgentServerPolicy` を付ける

### 問13 {#q13}

1 分間隔の CPU のアラームが、短いスパイクのたびに鳴ります。5 分のうち 3 回以上しきい値を超えたときだけ鳴らしたいと考えています。どの設定を使いますか。

- A. 期間を 1 秒にして、高解像度のアラームへ変更する
- B. 評価期間を 5、アラームを発生させるデータポイントを 3 にする

- D. 統計を `Maximum` に変更し、最も高い値で判定するようにする

    - B: 正しい。
    - C: 誤り。欠落データの扱いであり、スパイクへの反応は変わらない。
    - D: 誤り。最大値で判定すると、スパイクの影響が大きくなる。

    **スキル:** [1.1.3](../domain1.md#skill-1-1-3) / **参照:** [評価の仕組みと M out of N](../../../services/observability.md#alarm-evaluation)

### 問17 {#q17}

アラームと呼び出せるアクションの組み合わせとして正しいものを選んでください。（2つ選択）

- A. 異常検知のアラームから Auto Scaling のポリシーを実行する
- B. メトリクスアラームから EC2 インスタンスを再起動する
- C. 複合アラームから Auto Scaling のポリシーを実行する

### 問18 {#q18}

組織の 30 アカウントのメトリクスとログを、監視用の 1 アカウントのダッシュボードで見たいと考えています。今後追加するアカウントも自動で対象にしたいです。どの方法を選びますか。

- A. 各アカウントの CloudWatch を CSV にエクスポートし、監視アカウントの S3 に集める処理を組む
- B. クロスアカウントオブザーバビリティで監視アカウントを設定し、Organizations の組織か OU をソースとしてリンクする

クロスアカウントオブザーバビリティを東京リージョンで設定しました。監視アカウントで、ソースアカウントのオレゴンのメトリクスが見えません。原因として正しいものはどれですか。

- A. ソースアカウントが X-Ray を有効にしていないと、メトリクスも共有されないため

### 問20 {#q20}

AWS アカウントを持たない社外の監査担当 3 名に、1 つのダッシュボードだけを見せたいと考えています。誰でも見られるリンクは禁止です。どの方法を選びますか。

- A. ダッシュボードの公開リンクを作り、3 名にメールで案内する
- B. 組織の SSO を設定して、すべてのダッシュボードを共有する
