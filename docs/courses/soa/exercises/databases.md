# RDS、Aurora、DynamoDB の問題集

対象の解説: [RDS](../../../services/databases.md#rds)、[Aurora](../../../services/databases.md#aurora)、[RDS Proxy](../../../services/databases.md#rds-proxy)、[キャパシティモードと RCU/WCU](../../../services/dynamodb.md#capacity)、[バックアップと復元](../../../services/dynamodb.md#backup)

### 問1 {#q1}

Lambda から RDS for MySQL に接続するアプリケーションで、同時実行が増えると `Too many connections` が出ます。アプリケーションの変更を最小にする対策はどれですか。

- A. リードレプリカを追加して、すべての書き込みをレプリカへ向ける
- B. `gp3` の IOPS を増やす
- C. Multi-AZ を有効にして、スタンバイにも接続を分散させる
- D. RDS Proxy で接続をプールして再利用する

??? success "答えと解説"
    **正解: D**

    接続の急増には RDS Proxy が向きます。

    - A: 誤り。レプリカは書き込めない。
    - B: 誤り。接続数の上限は IOPS で変わらない。
    - C: 誤り。スタンバイは読めず、接続は分散できない。
    - D: 正しい。

    **スキル:** [1.3.5](../domain1.md#skill-1-3-5) / **参照:** [RDS Proxy](../../../services/databases.md#rds-proxy)

### 問2 {#q2}

RDS Proxy を導入しましたが、接続の再利用の効果が低いです。何を確認しますか。

- A. `BurstBalance` のメトリクスを見て、ストレージのクレジットが十分に残っているかどうかを確認する
- B. `DatabaseConnectionsCurrentlySessionPinned` を確認する
- C. `ReadLatency` のメトリクスを見て、読み取りの遅延が増えていないかを確認する
- D. `ReplicaLag` のメトリクスを見て、レプリケーションが遅れていないかを確認する

??? success "答えと解説"
    **正解: B**

    セッションの状態を変える処理でピン留めが起きると、接続を再利用できません。

    - A: 誤り。EBS のクレジットは接続の再利用と関係がない。
    - B: 正しい。
    - C: 誤り。読み取りの遅延は、ピン留めの指標ではない。
    - D: 誤り。レプリカの遅れの指標である。

    **スキル:** [1.3.5](../domain1.md#skill-1-3-5) / **参照:** [RDS Proxy の設定](../../../services/databases.md#rds-proxy-settings)

### 問3 {#q3}

RDS Proxy の制約として正しいものを選んでください。（2つ選択）

- A. DB と同じ VPC に置く
- B. レプリケーション構成の RDS では、全リードレプリカに個別に関連付ける
- C. DB と別のリージョンに置く構成が推奨である
- D. 認証情報は必ずアプリケーションのコードに書く
- E. インターネットからのパブリックアクセスはできない

??? success "答えと解説"
    **正解: A, E**

    プロキシは VPC の中から使います。

    - A: 正しい。
    - B: 誤り。ライターだけに関連付ける。
    - C: 誤り。同じ VPC に置く。
    - D: 誤り。Secrets Manager か IAM 認証を使う。
    - E: 正しい。

    **スキル:** [1.3.5](../domain1.md#skill-1-3-5) / **参照:** [RDS Proxy の設定](../../../services/databases.md#rds-proxy-settings)

### 問4 {#q4}

`CPUUtilization` は高いものの、DB の負荷の分析によると原因は読み取りのレポートの SQL です。SQL は最適化済みです。アプリケーションの接続先は変更できます。適切な対策はどれですか。

- A. リードレプリカを作り、レポートの接続先を変える
- B. Enhanced Monitoring を有効にして、OS のプロセスを確認し続ける
- C. ストレージの自動スケーリングを有効にする
- D. Multi-AZ のスタンバイを作り、レポートの接続先に使う

??? success "答えと解説"
    **正解: A**

    読み取りが多いならリードレプリカです。接続先はアプリで変えます。

    - A: 正しい。
    - B: 誤り。監視であり、負荷は減らない。
    - C: 誤り。ストレージの容量の機能で、CPU の負荷は減らない。
    - D: 誤り。DB インスタンスのスタンバイは読めない。

    **スキル:** [1.3.5](../domain1.md#skill-1-3-5) / **参照:** [リードレプリカと Multi-AZ](../../../services/databases.md#read-replicas)

### 問5 {#q5}

DB 全体が遅いときの調査です。DB の負荷が Max vCPU の線を頻繁に超え、主な待機が CPU になっています。OS のプロセスごとの CPU も確認したいです。使う機能の組み合わせはどれですか。

- A. `DatabaseConnections` のメトリクスと、S3 へエクスポートしたログの全文を Athena で検索する処理の組み合わせ
- B. CloudTrail のデータイベントと Config のレコーダー
- C. Database Insights と Enhanced Monitoring
- D. Trusted Advisor と Compute Optimizer の推奨

??? success "答えと解説"
    **正解: C**

    DB 負荷は待機や SQL で分解し、OS の値は Enhanced Monitoring で見ます。Performance Insights は 2026 年 7 月 31 日に提供を終了し、Database Insights へ移行しました。

    - A: 誤り。接続数は分かるが、待機や SQL の分解はできない。
    - B: 誤り。API の記録と設定の記録で、DB の負荷は分からない。
    - C: 正しい。
    - D: 誤り。助言と推奨で、DB の待機を分解しない。

    **スキル:** [1.3.5](../domain1.md#skill-1-3-5) / **参照:** [RDS](../../../services/databases.md#rds)

### 問6 {#q6}

本番の RDS で空き容量が減り、人手で容量を増やしています。停止を避けて自動化します。正しいものを選んでください。（2つ選択）

- A. 空き容量の条件を満たすと、回数の制限なしに何度でも増やせる
- B. 空き容量が 10% 以下の状態が 5 分以上続くと、増やす処理が始まる
- C. ストレージの自動スケーリングを有効にし、最大ストレージしきい値を指定する
- D. 増やすには DB インスタンスを再起動する
- E. 最大ストレージしきい値は、現在の割り当てと同じ値を指定する

??? success "答えと解説"
    **正解: B, C**

    自動スケーリングの条件は、空き容量、継続時間、変更の間隔です。

    - A: 誤り。過去 24 時間の変更は 4 回未満という条件がある。
    - B: 正しい。
    - C: 正しい。
    - D: 誤り。停止を伴う再起動は不要である。
    - E: 誤り。現在の割り当てより 10% 以上大きくする。

    **スキル:** [2.1.3](../domain2.md#skill-2-1-3) / **参照:** [RDS](../../../services/databases.md#rds)

### 問7 {#q7}

Aurora のレポートの負荷が平日の昼だけ増えます。読み取りの容量を自動で増減したいと考えています。何を設定しますか。

- A. ライターのインスタンスクラスを、スケジュールで大きくする処理を組む
- B. RDS のストレージの自動スケーリングを、Aurora でも有効に設定する
- C. Multi-AZ のスタンバイを読み取りのエンドポイントとして追加する
- D. Aurora Auto Scaling のレプリカのポリシー

??? success "答えと解説"
    **正解: D**

    Aurora Auto Scaling は読み取りのレプリカだけを増減します。

    - A: 誤り。書き込みの容量の変更で、読み取りのレプリカの増減ではない。
    - B: 誤り。Aurora のストレージは自動で増える。
    - C: 誤り。Aurora の読み取りの増減の方法ではない。
    - D: 正しい。

    **スキル:** [2.1.3](../domain2.md#skill-2-1-3) / **参照:** [Aurora](../../../services/databases.md#aurora)

### 問8 {#q8}

Aurora のライターの CPU が高くなりました。Aurora Auto Scaling を設定しましたが、書き込みの性能が改善しません。正しい説明と対策はどれですか。

- A. Auto Scaling はライターに効かないので、ライターのクラスを大きくするか Serverless v2 を検討する
- B. 1 AZ に全レプリカを集めて、書き込みの遅延を短くするように配置を変える
- C. Auto Scaling の対象のメトリクスをストレージの空き容量に変えて、書き込みの多いときにレプリカを増やす
- D. レプリカを増やすと書き込みも分散されるので、最大レプリカ数を増やして様子を見る

??? success "答えと解説"
    **正解: A**

    Aurora Auto Scaling は読み取りのレプリカだけが対象です。

    - A: 正しい。
    - B: 誤り。可用性を下げるだけで、ライターの負荷は変わらない。
    - C: 誤り。ストレージの空き容量は書き込みの CPU を改善しない。
    - D: 誤り。レプリカは書き込みを受けない。

    **スキル:** [2.1.3](../domain2.md#skill-2-1-3) / **参照:** [Aurora Serverless v2](../../../services/databases.md#aurora-serverless-v2)、[Aurora](../../../services/databases.md#aurora)

### 問9 {#q9}

CloudFormation で作成したプロビジョンドの DynamoDB テーブルに、Auto Scaling が効いていません。正しい説明はどれですか。

- A. 目標使用率の既定は 100% なので、容量が増えるのを待つ
- B. CLI や CloudFormation では Auto Scaling は自動で入らないので、自分で設定する
- C. GSI の設定がテーブルから自動で引き継がれて反映されるので、テーブルの値だけを確認すれば足りる
- D. オンデマンドに変更しないと Auto Scaling は設定できない

??? success "答えと解説"
    **正解: B**

    コンソールと違い、CLI や CloudFormation では自分で設定します。

    - A: 誤り。目標の推奨は 70% で、範囲は 20〜90% である。
    - B: 正しい。
    - C: 誤り。GSI は別に設定する。
    - D: 誤り。Auto Scaling はプロビジョンドの機能である。

    **スキル:** [2.1.3](../domain2.md#skill-2-1-3) / **参照:** [プロビジョンドと Auto Scaling](../../../services/dynamodb.md#provisioned-auto-scaling)、[キャパシティモードと RCU/WCU](../../../services/dynamodb.md#capacity)

### 問10 {#q10}

DynamoDB で短い急増のたびに `ProvisionedThroughputExceededException` が出ます。Auto Scaling は有効です。パーティションキーの偏りはありません。トラフィックの予測もできません。容量の計画をなくしたいです。どうしますか。

- A. Auto Scaling の目標の使用率を 90% に上げ、余裕を減らして反応を遅くする
- B. パーティションキーを変更する
- C. テーブルをオンデマンドモードへ変更する
- D. 読み取りのレプリカを Aurora で別に作り、書き込みはそのまま流す

??? success "答えと解説"
    **正解: C**

    容量の計画が不要で、読めない負荷にはオンデマンドが向きます。

    - A: 誤り。反応は速くならず、余裕も減る。
    - B: 誤り。キーは変更できず、偏りも原因ではない。
    - C: 正しい。
    - D: 誤り。DynamoDB のスケーリングの機能ではない。

    **スキル:** [2.1.3](../domain2.md#skill-2-1-3) / **参照:** [キャパシティモードと RCU/WCU](../../../services/dynamodb.md#capacity)、[DAX](../../../services/dynamodb.md#dax)

### 問11 {#q11}

RDS で 10 分前に誤ってテーブルを削除しました。自動バックアップは有効です。Aurora ではありません。復旧の方法として正しいものはどれですか。

- A. リードレプリカを昇格させて、削除の前の状態に戻す
- B. 既存の DB インスタンスへ、PITR で直接上書きして戻す
- C. Multi-AZ でフェイルオーバーしてスタンバイのデータへ切り替える
- D. PITR で新しい DB インスタンスを作り、接続先を切り替える

??? success "答えと解説"
    **正解: D**

    RDS の PITR の復元先は新しい DB インスタンスで、エンドポイントが変わります。

    - A: 誤り。誤削除もレプリカへ複製されている。
    - B: 誤り。PITR は新しい DB インスタンスを作る。
    - C: 誤り。スタンバイにも同期で複製されている。
    - D: 正しい。

    **スキル:** [2.3.2](../domain2.md#skill-2-3-2) / **参照:** [リードレプリカと Multi-AZ](../../../services/databases.md#read-replicas)、[バックアップと復元](../../../services/dynamodb.md#backup)

### 問12 {#q12}

Aurora MySQL で、数分前の誤った更新を素早く戻したいです。クラスターはバックトラックを有効にして作成してあります。新しいクラスターを作らず、接続先も変えたくありません。何を使いますか。

- A. グローバルデータベースのセカンダリを昇格させる方法
- B. スナップショットを新しいクラスターに復元する方法
- C. バックトラックでクラスターを巻き戻す
- D. PITR で新しいクラスターを作る

??? success "答えと解説"
    **正解: C**

    バックトラックは同じクラスターのまま、ウィンドウ内の時点へ戻します。作成か復元のときに有効にする必要があり、戻す間は短時間の中断があります。

    - A: 誤り。誤った更新も複製されている可能性が高く、接続先も変わる。
    - B: 誤り。新しいクラスターになり、接続先が変わる。
    - C: 正しい。
    - D: 誤り。新しいクラスターになり、接続先が変わる。

    **スキル:** [2.3.2](../domain2.md#skill-2-3-2) / **参照:** [Aurora](../../../services/databases.md#aurora)

    - B: 正しい。

### 問14 {#q14}

RDS で RPO を数分に短くするよう求められました。現在は毎晩の手動スナップショットだけです。どう変えますか。

- A. 自動バックアップを有効にして PITR を使う

### 問15 {#q15}

スナップショットから復元した RDS で、最初のクエリだけが遅くなっています。インスタンスクラスは元と同じです。正しい説明と対策はどれですか。

- A. スナップショットが破損しているので、別のスナップショットから新しいインスタンスを作り直す

    - A: 誤り。破損の症状ではない。

RDS の可用性の構成について正しいものはどれですか。

- A. Multi-AZ のフェイルオーバーでは IP アドレスが引き継がれるので、DNS は使わない
