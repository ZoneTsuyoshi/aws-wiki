# Route 53 のゾーンとレコードの問題集

対象の解説: [Route 53](../../../services/networking.md#route53), [レコード](../../../services/networking.md#route53-records), [プライベートホストゾーン](../../../services/network-connectivity.md#private-hosted-zones)

### 問1 {#q1}

ある企業は `www.example.com`（TTL は 86400 秒）の宛先を、明日の夜に新しい環境へ切り替えます。切り替えの後は数分で大半の利用者を新しい環境へ移したいと考えています。追加の費用は一時的なものなら許容できます。最も適切な手順はどれですか。

- A. 切り替えと同時に値と TTL を両方変更し、リゾルバーがすぐに新しい TTL を読むことを期待する
- B. SOA レコードのシリアル番号を上げて、リゾルバーにキャッシュの無効化を通知する
- C. 切り替えの直前に Route 53 のネームサーバーを別のものへ変更して、全リゾルバーのキャッシュを消す
- D. 前日までに TTL を 60 秒に下げ、古い 86400 秒のキャッシュが切れてから値を変更する

??? success "答えと解説"
    **正解: D**

    応答はリゾルバーに前の TTL の間だけ残ります。先に TTL を下げ、その前の TTL が切れるのを待ってから値を変えます。

    - A: 誤り。キャッシュ済みの応答は古い TTL が切れるまで使われるので、最大 1 日残る。
    - B: 誤り。シリアルはセカンダリ DNS のゾーン転送用で、キャッシュの無効化には使えない。
    - C: 誤り。ネームサーバーを変えても他者のリゾルバーのキャッシュは消せない。
    - D: 正しい。

    **スキル:** [DNS プロトコルの基礎](../domain1.md#t1-2-dns-protocol) / **参照:** [TTL とエイリアスの違い](../../../services/networking.md#route53-ttl)

### 問2 {#q2}

社内の担当者が「`api.example.com` を別のチームのゾーンに任せたい」と言っています。`example.com` のゾーンは Route 53 にあり、`api.example.com` のレコードは今後すべてそのチームが管理します。DNS の仕組みとして、親のゾーンに必要なものはどれですか。

- A. `api.example.com` の `NS` レコードを追加して、子のゾーンのネームサーバーを指す
- B. `api.example.com` の `CNAME` レコードで、子のゾーンのネームサーバーの名前を指す
- C. `api.example.com` の `TXT` レコードに、子のゾーンのホストゾーン ID を書く
- D. `example.com` の `SOA` レコードに、`api` の管理者のメールアドレスを追記する

??? success "答えと解説"
    **正解: A**

    委任は親のゾーンの `NS` レコードで行います。

    - A: 正しい。
    - B: 誤り。`CNAME` は別名で、ゾーンの権限の委任にはならない。
    - C: 誤り。`TXT` は解決の経路に使われない。
    - D: 誤り。SOA はそのゾーン自身の情報で、委任の情報を持たない。

    **スキル:** [DNS プロトコルの基礎](../domain1.md#t1-2-dns-protocol) / **参照:** [レコード](../../../services/networking.md#route53-records)

### 問3 {#q3}

Web サイトの障害時に Route 53 のフェイルオーバーで切り替える構成で、TTL を 3600 秒の通常のレコードから 60 秒へ下げる提案がありました。TTL を短くしたときの影響として正しいものはどれですか。

- A. 切り替えは速くなるが、リゾルバーからの問い合わせが増えて、料金も増えることがある
- B. 応答の署名が短い周期で更新されるので、DNSSEC の検証の失敗が減る
- C. Route 53 のヘルスチェックの間隔も連動して短くなり、検出が速くなる
- D. 利用者のリゾルバーの再帰問い合わせが不要になるので、名前解決の遅延が小さくなる

??? success "答えと解説"
    **正解: A**

    TTL はキャッシュの秒数です。短いと切り替えは速くなり、問い合わせの数は増えます。

    - A: 正しい。
    - B: 誤り。TTL は署名の周期を決めない。
    - C: 誤り。ヘルスチェックの間隔は TTL とは別に設定する。
    - D: 誤り。TTL が短いとキャッシュが効かず、再帰問い合わせはむしろ増える。

    **スキル:** [DNS プロトコルの基礎](../domain1.md#t1-2-dns-protocol) / **参照:** [TTL とエイリアスの違い](../../../services/networking.md#route53-ttl)

### 問4 {#q4}

企業は他社のレジストラで管理するドメインを Route 53 へ移管します。現在の DNS サービスも他社で、移管の間も止められません。登録の移管と DNS サービスの関係について、最も適切な進め方はどれですか。

- A. 先に DNS を Route 53 へ移して安定させ、その後にレジストラの登録を移管する
- B. ドメインのロックを有効にした状態で認証コードを取得し、移管中は DNS サービスを停止して整合を保つ
- C. 登録の移管の完了までは Route 53 にホストゾーンを作れないので、移管後に急いでレコードを登録する
- D. 登録を移管すると DNS のレコードも自動で Route 53 へ移る

??? success "答えと解説"
    **正解: A**

    登録（レジストラ）と DNS サービスは別です。DNS を先に移しておくと、登録の移管で解決が止まることを避けられます。

    - A: 正しい。
    - B: 誤り。移管にはロックの解除が必要で、DNS を止める必要もない。
    - C: 誤り。登録がどこにあってもホストゾーンは作れる。
    - D: 誤り。登録と DNS サービスは別物で、レコードは移らない。

    **スキル:** [ドメイン登録](../domain1.md#t1-2-domains) / **参照:** [Route 53](../../../services/networking.md#route53)

### 問5 {#q5}

他社のレジストラから Route 53 へ `.com` のドメインを移管しようとしたところ、移管を開始できません。このドメインは 30 日前に別のレジストラから移管されたものです。ロックは解除し、認証コードも取得済みです。原因として最も可能性が高いものはどれですか。

- A. 認証コードの有効期限は発行から 24 時間に固定されており、取り直しが必要になっている
- B. Route 53 のホストゾーンがまだなく、ホストゾーンの作成が移管の前提になっている
- C. `.com` は Route 53 が移管を受け付けない TLD である
- D. 登録または前回の移管から 60 日以内なので、期間が過ぎるまで移管を開始できない

??? success "答えと解説"
    **正解: D**

    登録または前回の移管から 60 日以内のドメインは移管できません。

    - A: 誤り。根拠のない条件で、問題文の経緯にも合わない。
    - B: 誤り。ホストゾーンは移管の前提ではない。
    - C: 誤り。`.com` は移管できる TLD。
    - D: 正しい。

    **スキル:** [ドメイン登録](../domain1.md#t1-2-domains) / **参照:** [Route 53](../../../services/networking.md#route53)

### 問6 {#q6}

グループ会社の再編で、Route 53 に登録したドメインとそのホストゾーンを、別の AWS アカウントへ移します。移行後は新しいアカウントで DNS も管理します。正しい理解はどれですか。

- A. 組織の RAM でドメインを共有すれば移転と同じ効果があり、受け取り側で更新もできる
- B. ドメインの移転とホストゾーンの移行は別の作業で、ホストゾーンは自分で移す必要がある
- C. 受け取り側の承認は不要で、送り側の操作だけで即座に移転が完了する
- D. ドメインを移転すると、ホストゾーンも同じ操作で受け取り側のアカウントへ移る

??? success "答えと解説"
    **正解: B**

    ドメインの移転は受け取り側の承認で完了します。ホストゾーンは別途移します。

    - A: 誤り。ドメインの登録は RAM の共有の対象ではない。
    - B: 正しい。
    - C: 誤り。受け取る側が 3 日以内に承認する。
    - D: 誤り。ホストゾーンは一緒に移らない。

    **スキル:** [ドメイン登録](../domain1.md#t1-2-domains) / **参照:** [Route 53](../../../services/networking.md#route53)

### 問7 {#q7}

VPC に PHZ `corp.example.com` を関連付け、レコードも登録しました。しかし EC2 から `db.corp.example.com` が解決できません。この VPC では既定の DNS サーバーを使っており、SG と NACL に問題はありません。最初に確認する設定はどれですか。

- A. PHZ を同じ名前の公開ホストゾーンに関連付けて権限を委任しているか
- B. VPC の `enableDnsHostnames` と `enableDnsSupport` が両方 `true` か
- C. VPC に IGW がアタッチされ、ルートテーブルにデフォルトルートがあるか
- D. PHZ のレコードに CloudWatch アラーム型のヘルスチェックが付いているか

??? success "答えと解説"
    **正解: B**

    PHZ を使うには、VPC の 2 つの DNS 属性が `true` である必要があります。

    - A: 誤り。PHZ と公開ゾーンを関連付ける操作はない。
    - B: 正しい。
    - C: 誤り。PHZ の解決に IGW は不要。
    - D: 誤り。ヘルスチェックはレコードの解決の必須条件ではない。

    **スキル:** [公開とプライベート、VPC との統合](../domain1.md#t1-2-public-private) / **参照:** [プライベートホストゾーン](../../../services/network-connectivity.md#private-hosted-zones), [VPC の DNS 属性](../../../services/networking.md#vpc-dns-attributes)

### 問8 {#q8}

公開ゾーン `example.com` に `www` があり、社内向けに同名の PHZ `example.com` を作って `intranet` だけを登録しました。すると、その VPC の EC2 から `www.example.com` が引けなくなりました。インターネットからは引けます。最小の変更で直す方法はどれですか。

- A. PHZ にも `www` のレコードを登録して、VPC の中からも解決できるようにする
- B. 公開ゾーンの NS を PHZ のネームサーバーへ変更して、参照先を統一する
- C. `www` の TTL を短くして、VPC Resolver が次回は公開 DNS を参照するのを待つ
- D. VPC の `enableDnsSupport` を無効にして、外部のリゾルバーへ問い合わせを逃がす

??? success "答えと解説"
    **正解: A**

    名前に一致する PHZ があるとそのゾーンだけを探し、レコードがなければ NXDOMAIN を返します。

    - A: 正しい。
    - B: 誤り。PHZ は公開の委任先にならず、外部の解決が壊れる。
    - C: 誤り。PHZ に一致すると公開 DNS へは流れず、TTL の問題ではない。
    - D: 誤り。VPC の名前解決そのものが止まる。

### 問9 {#q9}

PHZ のレコードにフェイルオーバーを設定します。プライマリは VPC 内の内部 ALB の背後ではなく、プライベート IP の EC2 です。エンドポイント型のヘルスチェックを付けましたが、常に異常になります。原因と対策の組み合わせで正しいものはどれですか。

- A. チェッカーの IP が SG で拒否されているので、SG に Route 53 の範囲を追加すれば正常になる

### 問10 {#q10}

VPC に PHZ `example.com` を関連付けています。別のチームが、オンプレミスの DNS へ `example.com` を転送する Forward ルールを作り、同じ VPC に関連付けました。その後 `app.example.com`（PHZ にだけ存在）が NXDOMAIN になりました。原因として正しいものはどれですか。

- A. PHZ が優先されるが、PHZ の TTL が切れるまで古い否定応答がキャッシュされている

    - D: 誤り。共存はでき、優先順位に従って処理される。

### 問15 {#q15}

企業はオンプレミスの DNS を権威としつつ、サブドメイン `cloud.corp.example.com` の権限をオンプレミス側で NS レコードにより AWS へ渡す構成を検討しています。受ける側は VPC Resolver のインバウンドエンドポイントで、ゾーンは PHZ です。この委任の前提として適切なものはどれですか。

- A. PHZ に DNSSEC 署名を有効にし、オンプレミスの親に DS レコードを登録していること
- B. DX か VPN の経路で、NS の先のインバウンドエンドポイントへ問い合わせが届くこと
- C. 公開ホストゾーンを同じ名前で作り、公開 DNS の NS をオンプレミスの親に登録していること
- D. インバウンドエンドポイントに Elastic IP を付け、インターネット経由で NS レコードの先へ到達できること
