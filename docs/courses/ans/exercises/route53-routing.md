# Route 53 のルーティングと高可用性の問題集

対象の解説: [ルーティングポリシー](../../../services/networking.md#routing-policies), [ルーティングポリシーの設定](../../../services/networking.md#routing-settings), [Route 53 ヘルスチェック](../../../services/networking.md#route53-health-checks), [Route 53 のフェイルオーバー設計](../../../services/resilience.md#route53-failover)

### 問1 {#q1}

Web アプリのフェイルオーバーで「ALB の 5xx の割合が高い」または「依存する DynamoDB の失敗が多い」ときに切り替えたいと考えています。単なる HTTP の疎通では判断できません。Route 53 のヘルスチェックとして最も適切な構成はどれですか。

- A. 複数値回答のレコードを追加して、異常な値だけをヘルスチェックなしで自動的に除外する
- B. エンドポイント型の HTTP チェックで `/health` を監視し、失敗のしきい値を 1 に下げて検出を早める
- C. 2 つの CloudWatch アラームを監視するチェックを作り、計算ヘルスチェックで組み合わせる
- D. エンドポイント型のチェックの文字列マッチングで、ALB の応答に含まれるメトリクスの値を判定する

??? success "答えと解説"
    **正解: C**

    メトリクスで判定するならアラーム型、複数の条件は計算型で組み合わせます。

    - A: 誤り。除外にはヘルスチェックが必要。
    - B: 誤り。アプリの依存まで見るなら `/health` の実装が別途要り、問題文の指標を直接扱えない。
    - C: 正しい。
    - D: 誤り。ALB は応答にメトリクスの値を含めない。

    **スキル:** [Route 53 の機能](../domain1.md#t1-2-features) / **参照:** [Route 53 ヘルスチェック](../../../services/networking.md#route53-health-checks)

### 問2 {#q2}

5 リージョンの構成で、レイテンシー、加重、フェイルオーバーを組み合わせた DNS の木を複数のドメインで使い回します。変更の履歴を残し、問題があれば前の版へ戻したいと考えています。最も適切な機能はどれですか。

- A. Global Accelerator のエンドポイントグループとトラフィックダイヤル
- B. VPC Resolver の System ルールと Route 53 Profiles
- C. Traffic Flow のトラフィックポリシーとポリシーレコード
- D. CloudFormation の `AWS::Route53::RecordSet` を手で複製するだけの構成

??? success "答えと解説"
    **正解: C**

    Traffic Flow は木をバージョン付きのポリシーとして管理し、複数のレコードへ適用できます。

    - A: 誤り。DNS のレコードの木を管理する機能ではない。
    - B: 誤り。VPC の中の解決の管理で、公開の木の管理ではない。
    - C: 正しい。
    - D: 誤り。動くが、問題文の使い回しと版の管理は別に作り込むことになる。

    **スキル:** [Route 53 の機能](../domain1.md#t1-2-features) / **参照:** [ルーティングポリシー](../../../services/networking.md#routing-policies), [Route 53 ヘルスチェック](../../../services/networking.md#route53-health-checks)

### 問3 {#q3}

Route 53 のエイリアスレコードで ALB を指し、ALB の配下のターゲットが全滅したときはレコードを異常として扱いたいと考えています。ヘルスチェックは追加したくありません。設定はどれですか。

- A. ALB の属性で `routing.http.dns_health` を有効にする
- B. `MaxItems` を 1 にして、ALB の IP を 1 個だけ返すようにする
- C. エイリアスの TTL を 0 にして、毎回 ALB の状態を確認する
- D. エイリアスレコードの `Evaluate Target Health` を `Yes` にする

??? success "答えと解説"
    **正解: D**

    `Evaluate Target Health` により、エイリアス先の正常性をレコードの評価に反映します。

    - A: 誤り。問題文の要件に対応する ALB の属性ではなく、設定する場所が違う。
    - B: 誤り。応答の個数の設定で、正常性の判定にならない。
    - C: 誤り。AWS リソース向けのエイリアスに TTL は指定できない。
    - D: 正しい。

    **スキル:** [Route 53 の機能](../domain1.md#t1-2-features) / **参照:** [レコード](../../../services/networking.md#route53-records), [Route 53 ヘルスチェック](../../../services/networking.md#route53-health-checks)

### 問4 {#q4}

新バージョンのアプリへ、最初に全体の 1% だけを流します。旧環境と新環境はどちらも同じリージョンの別の ALB です。問題があれば DNS の操作だけで 0% に戻します。最も適切なレコードの設定はどれですか。

- A. 複数値回答で両方の ALB を登録し、ヘルスチェックの閾値で比率を調整する
- B. 地理的近接性で新の `Bias` を `-99` にして、担当範囲を全体の 1% へ狭める
- C. レイテンシーレコードで新のリージョンを同じにし、応答の比率を 1% に指定する
- D. 加重レコードで旧を `99`、新を `1` にする。戻すときは新の重みを `0` にする

??? success "答えと解説"
    **正解: D**

    比率は重み / 合計です。

    - A: 誤り。比率を制御できない。
    - B: 誤り。地理で分けるので比率にならない。
    - C: 誤り。レイテンシーに比率の設定はない。
    - D: 正しい。

    **スキル:** [グローバルなトラフィック管理](../domain1.md#t1-2-global) / **参照:** [ルーティングポリシーの設定](../../../services/networking.md#routing-settings)

### 問5 {#q5}

利用者を国ごとに決められたリージョンへ固定します（法的な要件）。位置情報レコードで日本とドイツだけを登録したところ、それ以外の国の利用者が接続できなくなりました。IP の位置を判定できない問い合わせにも答える必要があります。対処はどれですか。

- A. 位置情報のレコードのヘルスチェックを外して、常に答えるようにする
- B. 位置情報のレコードの TTL を長くし、最後に成功した答えをリゾルバーに残す
- C. 日本のレコードの `Bias` を増やして、登録していない国の担当も広げる
- D. 既定（`Default`）の位置のレコードを追加する

??? success "答えと解説"
    **正解: D**

    既定のレコードがないと、対応のない場所には応答のデータがありません。

    - A: 誤り。登録のない場所には答えが返らない。
    - B: 誤り。新しいリゾルバーには答えが返らない。
    - C: 誤り。`Bias` は地理的近接性の設定。
    - D: 正しい。

    **スキル:** [グローバルなトラフィック管理](../domain1.md#t1-2-global) / **参照:** [ルーティングポリシーの設定](../../../services/networking.md#routing-settings)

### 問6 {#q6}

グローバルな API を 2 リージョンで運用しています。切り替えは数十秒以内で確実に行いたい一方、取引先のクライアントの中には DNS の応答を長時間キャッシュするものがあります。Route 53 のフェイルオーバーと比較したとき、最も適切な判断はどれですか。

- A. TTL を 1 秒にすれば、クライアントのキャッシュの設定によらず同じ速さで切り替わる
- B. 複数値回答に変えて、クライアントに 2 リージョンの IP を返し、再試行に任せる
- C. DNS のキャッシュに左右されない Global Accelerator を前に置く
- D. 計算ヘルスチェックに変えて、検出時間を短くすればキャッシュの問題は解消する

??? success "答えと解説"
    **正解: C**

    エッジの固定 IP で受ける Global Accelerator は、DNS のキャッシュに影響されません。

    - A: 誤り。TTL を守らないクライアントには効かない。
    - B: 誤り。クライアントのキャッシュの問題は残る。
    - C: 正しい。
    - D: 誤り。検出が速くてもキャッシュは残る。

    **スキル:** [グローバルなトラフィック管理](../domain1.md#t1-2-global) / **参照:** [ルーティングポリシー](../../../services/networking.md#routing-policies), [Global Accelerator](../../../services/network-connectivity.md#global-accelerator)

### 問7 {#q7}

地理的近接性ルーティングで東京と大阪の 2 つのリソースを設定しています。大阪の担当範囲を広げて、より多くの利用者を大阪へ流します。設定はどれですか。

- A. 大阪のレコードの `Bias` を正の値にする
- B. 大阪のレコードの `Weight` を `255` にする
- C. 東京のレコードの `SetIdentifier` を大阪と同じ値にする
- D. 大阪のレコードの `Bias` を負の値にする

??? success "答えと解説"
    **正解: A**

    `Bias` は -99〜99 で、正の値で範囲が広がります。

    - A: 正しい。
    - B: 誤り。加重の設定で、地理的近接性のものではない。
    - C: 誤り。`SetIdentifier` は識別子で、範囲を変えない。
    - D: 誤り。負の値は範囲を狭める。

    **スキル:** [トラフィック管理](../domain2.md#t2-3-traffic) / **参照:** [ルーティングポリシーの設定](../../../services/networking.md#routing-settings)

### 問8 {#q8}

加重レコードを 3 つ作り、重みを `10`、`30`、`60` にしました。さらに 60 のレコードの先が異常になり、ヘルスチェックで除外されました。その場合の比率として正しいものはどれですか。

- A. 異常なレコードの 60% は応答なしのまま返され、残りの 40% だけが正常に答える
- B. 全レコードの比率が均等に戻り、残りの 2 つに 50% ずつ流れる
- C. 残りのレコードで合計 40 として、1:3 の割合になる
- D. 重みの最も大きいレコードの異常でゾーン全体が異常になり、全部の値を返す

??? success "答えと解説"
    **正解: C**

    ヘルスチェックのあるレコードは、異常なら比率の計算から除かれます。

    - A: 誤り。異常なレコードは計算から除かれる。
    - B: 誤り。均等になるのは重みが全部 0 のとき。
    - C: 正しい。
    - D: 誤り。全部が異常のときの動作で、問題文には当たらない。

    **スキル:** [トラフィック管理](../domain2.md#t2-3-traffic) / **参照:** [ルーティングポリシーの設定](../../../services/networking.md#routing-settings)

### 問9 {#q9}

地域の IP 位置ではなく、提携する特定の ISP からの利用者だけを専用のエッジへ送りたいと考えています。ISP の CIDR は把握しています。最も適切なルーティングポリシーはどれですか。

- A. 位置情報ルーティングで ISP の国を指定する
- B. 複数値回答で ISP の数だけレコードを作成する
- C. IP ベースルーティングで CIDR のコレクションを使う
- D. レイテンシールーティングで ISP に近いリージョンを指定する

??? success "答えと解説"
    **正解: C**

    送信元の CIDR で宛先を変えるなら IP ベースです。

    - A: 誤り。同じ国の他の ISP も含まれてしまう。
    - B: 誤り。問い合わせの送信元で値を分けない。
    - C: 正しい。
    - D: 誤り。測定値で決まるので、ISP を指定できない。

    **スキル:** [トラフィック管理](../domain2.md#t2-3-traffic) / **参照:** [ルーティングポリシーの設定](../../../services/networking.md#routing-settings), [Route 53 ヘルスチェック](../../../services/networking.md#route53-health-checks)

### 問10 {#q10}

PHZ の中で、2 つの AZ の内部ロードバランサーに 50% ずつ問い合わせを分け、1 つが異常なら切り離します。設定として正しいものはどれですか。

- A. PHZ ではルーティングポリシーを使えないので、公開ゾーンに移して設定する
- B. PHZ の加重レコードに、ロードバランサーのプライベート IP を監視するエンドポイント型のチェックを付ける
- C. PHZ の複数値回答を使うが、PHZ のヘルスチェックは使えないので Lambda で手動で更新する
- D. PHZ に加重レコードを作り、それぞれにアラームを監視するヘルスチェックを付ける

??? success "答えと解説"
    **正解: D**

    PHZ のヘルスチェックはアラーム型を使います。

    - A: 誤り。PHZ でも主要なポリシーを使える。
    - B: 誤り。公開のチェッカーはプライベート IP に届かない。
    - C: 誤り。PHZ でもヘルスチェックを関連付けられる。
    - D: 正しい。

    **スキル:** [トラフィック管理](../domain2.md#t2-3-traffic) / **参照:** [ルーティングポリシーの設定](../../../services/networking.md#routing-settings)

### 問11 {#q11}

ある企業は「リージョンの障害時に、Route 53 のコンソールや API が使えなくても切り替えられる」ことを求めています。切り替えの操作は運用者が明示的に行います。最も適切な構成はどれですか。

- A. TTL を 60 秒にして、障害時に CloudFormation のスタックを更新してレコードを変更する
- B. 障害時に担当者が `ChangeResourceRecordSets` でレコードの値を書き換える手順を自動化する
- C. ARC のルーティングコントロールに紐づくヘルスチェックで、データプレーンから切り替える
- D. 別のアカウントにコピーしたホストゾーンのネームサーバーへ、登録情報を変更して切り替える

??? success "答えと解説"
    **正解: C**

    Route 53 のヘルスチェックの評価はデータプレーンで働きます。

    - A: 誤り。これもコントロールプレーンに依存する。
    - B: 誤り。コントロールプレーンの API に依存する。
    - C: 正しい。
    - D: 誤り。登録情報の変更も障害時に当てにできず、反映も遅い。

    **スキル:** [Route 53 の高可用性](../domain3.md#t3-3-route53-ha) / **参照:** [フェイルオーバーはデータプレーンで](../../../services/resilience.md#failover-data-plane), [Amazon Application Recovery Controller(ARC)](../../../services/resilience.md#arc)

### 問12 {#q12}

2 リージョンの構成で、リージョンはレイテンシーで選び、各リージョンの中では 2 つの ALB を 80:20 で分けます。ALB の障害時は同じリージョンの他方へ、両方の障害時は別のリージョンへ切り替えます。正しいレコードの構成はどれですか。

- A. 加重のエイリアスがレイテンシーレコードを指し、レイテンシーに ALB を置く。ヘルスチェックは最上位だけにする
- B. 複数値回答に 4 つの ALB を登録し、重みをレコードの順序で表現する
- C. フェイルオーバーのプライマリに 2 つの ALB を指定し、セカンダリに残りの 2 つを指定する
- D. レイテンシーのエイリアスが加重レコードを指し、加重に ALB を置く。すべて `Evaluate Target Health` を有効にする

??? success "答えと解説"
    **正解: D**

    木の評価を子まで伝えるには、エイリアスで `Evaluate Target Health` を有効にします。

    - A: 誤り。比率をリージョンの中に適用できない。
    - B: 誤り。複数値回答に重みはない。
    - C: 誤り。比率もレイテンシーの選択も実現できない。
    - D: 正しい。

    **スキル:** [Route 53 の高可用性](../domain3.md#t3-3-route53-ha) / **参照:** [ルーティングポリシーの設定](../../../services/networking.md#routing-settings), [Route 53 ヘルスチェック](../../../services/networking.md#route53-health-checks)

### 問13 {#q13}

S3 以外の AWS サービスへのインターフェイスエンドポイントを 3 つの AZ に持っています。AZ 間のデータ転送の費用を減らすため、同じ AZ の ENI へ送りたいと考えています。AZ の障害時の切り替えについても検討しています。正しい理解はどれですか。

- A. zonal DNS 名は AZ の障害時に別の AZ の ENI を自動で返すので、切り替えの設計は不要になる
- B. zonal DNS 名を使うと同じ AZ の ENI へ送れるが、AZ の障害時の切り替えは自分で設計する必要がある
- C. Regional DNS 名を使えば常に同じ AZ の ENI が返るので、切り替えの設計も不要になる
- D. プライベート DNS を有効にすると、zonal DNS 名が無効になって Regional の名前だけが使える

??? success "答えと解説"
    **正解: B**

    zonal DNS 名は特定の AZ の ENI を指します。

    - A: 誤り。特定の AZ の ENI を指す名前で、自動の切り替えはしない。
    - B: 正しい。
    - C: 誤り。Regional の名前は特定の AZ に固定する名前ではない。
    - D: 誤り。zonal の名前はプライベート DNS と併用できる。

### 問14 {#q14}

Active-Passive の Route 53 フェイルオーバーで、セカンダリのヘルスチェックを付けずに運用しています。プライマリが異常になると、セカンダリへ切り替わりました。その後、セカンダリも実は停止していることが分かりました。この構成で起きる動作と、改善策の組み合わせはどれですか。

- A. セカンダリは正常とみなされて応答が返り続ける。セカンダリにもヘルスチェックを付けて状態を把握する

- D. Route 53 がセカンダリの ALB を自動で再起動する。改善策として EventBridge で通知する

??? success "答えと解説"
    **正解: A**

    ヘルスチェックのないレコードは正常として扱われます。

    - A: 正しい。
    - B: 誤り。ヘルスチェックがないと異常を検知できない。
    - C: 誤り。設定していないレコードへは切り替わらない。
    - D: 誤り。Route 53 はリソースを操作しない。

    **スキル:** [Route 53 の高可用性](../domain3.md#t3-3-route53-ha) / **参照:** [Route 53 のフェイルオーバー設計](../../../services/resilience.md#route53-failover), [Route 53 ヘルスチェック](../../../services/networking.md#route53-health-checks)
