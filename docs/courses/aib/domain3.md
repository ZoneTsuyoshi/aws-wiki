# 分野3: AI ガバナンスと責任ある AI のリーダーシップ

配点は **24%** です。責任ある AI の原則を事業の判断に当てはめ、統治の体制を作り、リスクへの対策を指示する力を問います。

受験者が暗号化やアクセス権を実装することはありません。何を要求し、誰に任せ、どの程度の統制を選ぶかを判断します。

この分野に限らず、コース全体で使うサービスは[サービス一覧](services.md)から確認できます。

## タスク 3.1: 責任ある AI の原則を事業の判断に適用する {#task-3-1}

### 3.1.1 責任ある AI の原則と観点 {#skill-3-1-1}

場面から、どの観点の問題かを見分けます。

| 観点 | 意味 | 問題になる場面 |
|---|---|---|
| 公平性 | 集団ごとの影響を考える | 採用スコアが性別で偏る |
| 説明可能性 | 出力の理由を理解できる | 融資を断る理由を示せない |
| プライバシーとセキュリティ | データとモデルを適切に扱い、保護する | 個人情報がプロンプトから漏れる |
| 安全性 | 有害な出力と悪用を防ぐ | 危険な助言を返す |
| 制御可能性 | 挙動を監視し、操作できる | 問題が起きても止められない |
| 正確性と堅牢性 | 予期しない入力でも正しく動く | 誤字のある質問で誤答する |
| ガバナンス | 提供者と導入者を含む供給網に実践を組み込む | 外部モデルの評価の責任者がいない |
| 透明性 | 関係者が情報に基づいて判断できる | AI と知らずに対話させている |

説明可能性と透明性は混同しやすいです。説明可能性は「なぜその出力になったか」、透明性は「AI を使っていること、その能力や限界を伝えているか」です。

**Responsible AI Lens:** 試験ガイドが推奨知識に挙げる、AWS Well-Architected Framework のガイダンスです（2025年11月19日公開）。

| 項目 | 内容 |
|---|---|
| 目的 | 特定のユースケースの AI を、便益とリスクのバランスを取って責任ある形で作り、運用する |
| 構成 | ML ライフサイクルの段階に沿った 8 つのフォーカスエリア。各エリアに問いとベストプラクティスがある |
| 対象読者 | AI の開発者、技術リーダー、責任ある AI の専門家 |
| 注意 | コンプライアンスのチェックリストではありません。法的な義務は法務に確認します |

Lens では、プライバシーとセキュリティ、正確性と堅牢性を分けて、観点を 10 個に数えています。[AWS の責任ある AI のページ](https://aws.amazon.com/ai/responsible-ai/)は 8 つにまとめています。内容は同じなので、個数よりも意味を押さえます。

詳細: [AWS の 8 つの観点](../../services/ai-fundamentals.md#rai-dimensions)、[説明可能性と透明性](../../services/ai-fundamentals.md#explainability)、[Well-Architected Framework](../../services/cloud-foundations.md#well-architected)、[Responsible AI Lens（公式）](https://docs.aws.amazon.com/wellarchitected/latest/responsible-ai-lens/responsible-ai-lens.html)

### 3.1.2 事業目標と原則の対立 {#skill-3-1-2}

対立は必ず起きます。原則だけ、または事業だけで決めず、リスクの高さに沿って判断します。

| 対立 | 判断の例 |
|---|---|
| 精度と説明可能性 | 融資の審査では、精度が少し下がっても説明できるモデルを選ぶ |
| 速度と人の確認 | 影響の大きい判断は人の確認を残す。低リスクは自動化する |
| 個人化とプライバシー | 目的に必要な最小限のデータにとどめ、同意を得る |
| 発売時期と評価 | 高リスクの機能は評価を終えてから出す。低リスクの範囲で先に出す |

機能を範囲で分ける、対象を絞って先に出すなど、全面的な可否以外の選択肢も考えます。判断の理由と責任者は記録します。

詳細: [人による監督](../../services/ai-fundamentals.md#human-oversight)、[説明可能性と透明性](../../services/ai-fundamentals.md#explainability)

### 3.1.3 ガバナンス・バイ・デザイン {#skill-3-1-3}

責任ある AI は、企画の段階から組み込みます。公開直前の確認では、やり直しの費用が大きくなります。

| 段階 | 組み込むこと |
|---|---|
| 企画 | 目的、影響を受ける人、リスク分類、成功の基準 |
| データの選定 | 権利、代表性、個人情報の扱い |
| 開発と評価 | 公平性、安全性、正確性の評価 |
| 導入 | 人の監督、記録、利用者への説明 |
| 運用 | 監視、苦情の受付、見直し |

詳細: [役割と責任](../../services/ai-fundamentals.md#governance-roles)

### 3.1.4 人の監督と安全策 {#skill-3-1-4}

| 人の監督が必要な場面 | 安全策 |
|---|---|
| 医療、融資、採用のように影響が大きい判断 | 人が最終判断する |
| AI の信頼度が低い | エスカレーションの基準を決めて人に回す |
| 送金や削除のような不可逆な操作 | 実行前に承認する |
| 有害な内容のリスク | ガードレールで入出力を制御する |
| 事実の誤りが問題になる | ハルシネーションの検出、根拠の提示 |

| 安全策 | 役割 | AWS の例 |
|---|---|---|
| ガードレール | 有害な内容、拒否するトピック、個人情報を制御する | Amazon Bedrock Guardrails |
| ハルシネーションの検出 | 参照元に基づく回答かを確認する | コンテキストグラウンディングの検査 |
| エスカレーションの基準 | どの条件で人に渡すかを決める | 信頼度、金額、話題で定義する |

エスカレーションの基準は、担当者の裁量に任せず事前に決めて、文書にします。

詳細: [人による監督](../../services/ai-fundamentals.md#human-oversight)、[ハルシネーションへの対策](../../services/ai-fundamentals.md#hallucinations)、[Guardrails](../../services/ai.md#guardrails)、[コンテキストグラウンディング](../../services/genai-apps.md#contextual-grounding)

## タスク 3.2: 統治の体制を作り、規制を順守する {#task-3-2}

### 3.2.1 部門横断の統治体制 {#skill-3-2-1}

IT 部門だけでも、法務だけでも足りません。部門横断で構成し、誰が何を決めるかを明確にします。

| 役割 | 責任 |
|---|---|
| 経営層のスポンサー | 目標と予算、最終責任 |
| AI ガバナンス委員会 | 方針、リスク分類、承認 |
| ビジネスオーナー | ユースケースと成果の責任 |
| データ責任者 | データの品質と権限 |
| データサイエンス、ML エンジニア | モデルの開発と評価 |
| 法務、コンプライアンス | 規制、知的財産の確認 |
| セキュリティ | 脅威への対応と統制 |
| AI CoE | 標準、共通基盤、ノウハウの共有 |

責任が委員会全体に分散すると、誰も責任を取らなくなります。ユースケースごとに、1 人の責任者を決めます。

詳細: [役割と責任](../../services/ai-fundamentals.md#governance-roles)

### 3.2.2 規制上のリスク {#skill-3-2-2}

| 枠組み | 内容 | 事業での意味 |
|---|---|---|
| EU AI 法 | リスクを 4 段階に分類 | 用途によって義務が変わる |
| GDPR | 個人データの保護 | 同意、目的の制限、データの所在 |
| HIPAA | 米国の医療情報の保護 | 医療分野のデータの扱い |
| NIST AI RMF | Govern、Map、Measure、Manage | 法律ではなくリスク管理の指針 |
| ISO/IEC 42001 | AI マネジメントシステム | 組織の仕組みを認証できる |

進め方は次のとおりです。

1. どの業務で AI を使っているかを一覧にします。
2. 業務の場所と扱うデータから、適用される規制を法務と確認します。
3. 記録、説明、データの所在といった必要な対応を決めます。
4. 規制の変更を継続して確認します。

ベンダーの AI を使っても、自社の法的な責任はなくなりません。AWS は自社のインフラの監査レポートを AWS Artifact で提供しますが、自社の AI の利用に関する順守は自社の責任です。

詳細: [標準と規制](../../services/ai-fundamentals.md#standards)、[AWS Artifact](../../services/cloud-foundations.md#artifact)

### 3.2.3 アクセス制御とデータセキュリティ {#skill-3-2-3}

実装は範囲外です。何を要求すべきかを判断します。

| 要求すること | 理由 |
|---|---|
| 最小権限 | AI やエージェントが必要以上のデータに触れないようにする |
| 元の文書の権限を守る | RAG で見てはいけない文書が回答に出ないようにする |
| データの暗号化 | 保存中と通信中のデータを守る |
| 操作の記録 | 誰が何に使ったかを監査する |
| データの所在の確認 | 規制が求める地域で処理する |
| 入力データの扱いの確認 | 学習に使われないことを契約や仕様で確認する |

**AWS 責任共有モデル:** AWS は基盤、サービス、Bedrock のモデルの運用を担当し、利用者はデータ、アクセス権、プロンプト、ガードレールの設定、アプリのセキュリティ、出力の扱いを担当します。

自社の責任の範囲は、利用の形で変わります。Generative AI Security Scoping Matrix は、公開のチャットサービス（スコープ 1）から自社での学習（スコープ 5）までを分類します。番号が大きいほど、自社の制御と責任が増えます。

Amazon Bedrock の入出力は、モデルの学習に使われず、モデル提供者とも共有されません。

詳細: [責任共有モデル](../../services/ai-fundamentals.md#shared-responsibility)、[Generative AI Security Scoping Matrix](../../services/ai-fundamentals.md#scoping-matrix)、[AI システムを守るサービス](../../services/ai-fundamentals.md#security-services)、[入出力は学習に使われるか](../../services/ai.md#training-use)

### 3.2.4 リスク分類の枠組み {#skill-3-2-4}

用途の影響度で分類し、高リスクほど統制を厳しくします。すべてに同じ審査を課すと、低リスクの取り組みが止まり、高リスクへの目配りも薄くなります。

| リスク | 例 | 統制の例 |
|---|---|---|
| 低 | 社内文書の要約 | 利用ルール、定期的な確認 |
| 中 | 顧客向けの FAQ | AI の使用の明示、ガードレール、監視 |
| 高 | 採用の選考、融資の審査 | 委員会の承認、公平性の評価、人の最終判断、記録 |
| 許容できない | 法律で禁じられた用途 | 実施しない |

EU AI 法の 4 段階は、許容できない、高、限定的、最小です。分類は導入時だけでなく、用途やデータが変わるたびに見直します。

詳細: [標準と規制](../../services/ai-fundamentals.md#standards)

## タスク 3.3: 企業の AI リスクを特定し、対策を指示する {#task-3-3}

### 3.3.1 本番のリスク管理と監視 {#skill-3-3-1}

AI は本番に出した後もリスクが変わります。監視項目、しきい値、対応する責任者を導入前に決めます。

| 監視の対象 | 例 | 対応の例 |
|---|---|---|
| モデルドリフト | 精度の低下 | 再学習、モデルの見直し |
| データ品質 | 欠損の増加 | データの提供元の修正 |
| バイアスドリフト | 集団間の差の拡大 | 影響の調査、利用の制限 |
| ハルシネーションの率 | 根拠のない回答の増加 | 文書の修正、検査の強化 |
| コスト | トークンの急増 | 原因の調査、上限の設定 |

問題が起きたときの停止や切り戻しの手順も、事前に決めておきます。

詳細: [本番での監視](../../services/ai-fundamentals.md#production-monitoring)、[統治の仕組み](../../services/genai-apps.md#governance-controls)

### 3.3.2 ライフサイクル全体のバイアス {#skill-3-3-2}

バイアスは、データだけでなくどの段階でも入ります。導入時の検査だけでは足りません。

| 段階 | 例 | 対策 |
|---|---|---|
| データ収集 | 特定の属性が少ない | データの追加 |
| ラベル付け | 判定者の偏見 | 複数人のレビュー |
| 学習 | 多数派に最適化される | 集団別の評価 |
| 運用 | 時間とともに偏りが変わる（バイアスドリフト） | 継続的な監視、人の監査 |

全体の精度が高くても、特定の集団では低いことがあります。集団ごとに比較します。

!!! note "関連する AWS の機能の状況（2026年10月時点）"
    バイアスの検出に使われてきた SageMaker Clarify と、監視の Model Monitor は、新規顧客の受付を終了しています。既存の顧客は引き続き使えます。AIB-C01 の対象一覧にこれらの名前はありません。

詳細: [バイアスと公平性](../../services/ai-fundamentals.md#fairness)、[ドリフトの種類](../../services/sagemaker.md#drift)

### 3.3.3 有害な内容と知的財産 {#skill-3-3-3}

| リスク | 例 | 対策 |
|---|---|---|
| 有害な内容 | 差別的な回答、危険な助言 | ガードレール、公開前の評価、苦情の窓口 |
| 他者の権利の侵害 | 生成物が他者の著作物に似る | 人の確認、利用条件の確認 |
| 学習データの権利 | ライセンスのないデータで学習した | データの出所の記録、ライセンスの確認 |
| 自社の知的財産の流出 | 社外の AI に機密の設計を入力した | 承認済みツールの指定、入力ルール |
| 生成物の権利 | 生成物の権利の扱いが不明確 | 法務の確認、ベンダーとの契約の確認 |

技術の対策だけでは足りません。法務を交えて、契約と利用ルールを決めます。

詳細: [法的なリスク](../../services/ai-fundamentals.md#legal-risks)、[Guardrails](../../services/ai.md#guardrails)

### 3.3.4 信頼性のリスク {#skill-3-3-4}

| リスク | 意味 | 対策 |
|---|---|---|
| ハルシネーション | もっともらしい誤り | RAG による根拠づけ、引用の提示、検査、人のレビュー |
| データ品質の低下 | 入力や文書の質が落ちる | データの責任者の任命、品質の監視 |
| モデルドリフト | 環境の変化で精度が落ちる | 監視、再学習 |

ハルシネーションを完全になくす方法はありません。誤りが起きる前提で業務を設計し、影響の大きい出力は人が確認します。temperature を下げるとばらつきは減りますが、誤りをなくす手段ではありません。

詳細: [ハルシネーションへの対策](../../services/ai-fundamentals.md#hallucinations)、[本番での監視](../../services/ai-fundamentals.md#production-monitoring)

## 確認問題 {#self-check}

??? question "問1: 銀行が融資審査に AI を使います。高精度だが理由を説明できないモデルと、精度は 2 ポイント低いが判断の根拠を示せるモデルがあります。規制当局と顧客への説明が必要です。どちらを選びますか。"
    根拠を示せるモデルを選びます。融資は個人への影響が大きく、説明責任が求められる高リスクの用途です。少しの精度を犠牲にしても説明可能性を優先します。担当者が判断を確認する体制も設けます。

??? question "問2: 製品チームが、顧客向けの生成 AI 機能の公開 1 週間前に法務とリスク部門へ初めて相談しました。多くの指摘で公開が遅れそうです。今後の再発防止として最も効果的なのはどれですか。"
    ガバナンス・バイ・デザインを取り入れます。企画の段階でリスク分類を行い、法務、リスク、セキュリティを早くから参加させます。評価の基準も初めに決めます。最後の段階の確認では、大きなやり直しになるからです。

??? question "問3: 全社の AI 利用を統治する組織を作ります。案 A は IT 部門だけで構成し、案 B は事業、法務、コンプライアンス、セキュリティ、データの責任者で委員会を作り、案件ごとに責任者を決めます。どちらが適切ですか。"
    案 B です。AI のリスクは技術だけでなく、法規制、事業、データにまたがるからです。さらに案件ごとの責任者を決めることで、責任の所在が曖昧になるのを防ぎます。

??? question "問4: 社内文書の要約と、応募者の選考補助の 2 つの AI 案件があります。審査の人員は限られています。どう審査を配分しますか。"
    リスク分類に基づいて配分します。選考補助は人の機会に影響する高リスクなので、公平性の評価、委員会の承認、人の最終判断、記録を求めます。社内文書の要約は低リスクなので、利用ルールと定期的な確認にとどめ、早く進めます。

??? question "問5: 導入時の公平性の検査に合格したレコメンドの AI が、1 年後に一部の顧客層で著しく悪い結果を出していました。全体の精度は保たれています。何が欠けていましたか。"
    継続的なバイアスの監視です。時間とともにデータと利用が変わり、バイアスドリフトが生じたと考えられます。全体の指標では隠れるので、顧客層ごとの指標を定期的に比較し、しきい値を超えたら対応する責任者を決めておきます。

??? question "問6: 自社のチャットボットが存在しない返金規定を顧客に案内し、苦情になりました。経営層は、再発を確実にゼロにする方法を求めています。どう説明し、何を指示しますか。"
    ハルシネーションを完全にゼロにする方法はないと説明します。そのうえで、正式な規定を根拠に回答させる RAG、参照元に基づくかの検査、引用の提示を指示します。返金のように影響の大きい案内は、人に回す基準を決めます。誤答を監視する仕組みも整えます。
