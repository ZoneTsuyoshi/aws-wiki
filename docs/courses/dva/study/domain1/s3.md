## 学習の順番 {#study-order}

1. [基本と整合性](../../../../services/s3.md#basics)、[リクエストレートとプレフィックス](../../../../services/s3.md#request-rate): 整合性と、503 が出るときの考え方を押さえます。
2. [ストレージクラス](../../../../services/s3.md#storage-classes): アクセス頻度、最小保存期間、最小課金サイズから選べるようにします。
3. [ライフサイクル](../../../../services/s3.md#lifecycle)、[ライフサイクルのルール要素](../../../../services/s3.md#lifecycle-elements): 移行と失効の書き方を覚えます。
4. [バージョニング](../../../../services/s3.md#versioning)、[状態ごとの動作と削除マーカー](../../../../services/s3.md#delete-markers): 削除の動きと、戻し方を理解します。
5. [Event Notifications](../../../../services/s3.md#event-notifications): イベントタイプ、フィルターの規則、送信先の制約を確認します。
6. [署名付き URL](../../../../services/s3.md#presigned-urls)、[マルチパートアップロード](../../../../services/s3.md#multipart-upload)、[Transfer Acceleration](../../../../services/s3.md#transfer-acceleration): コードからの大きなファイルの扱いを学びます。
7. [Object Lock](../../../../services/s3.md#object-lock)、[S3 Glacier のデータ取得](../../../../services/s3.md#glacier-retrieval): 削除の禁止とアーカイブの取得時間を押さえます。
8. [Object Lambda と S3 Select の現在の状況](../../../../services/s3.md#retired-features): 新規には使えない機能を確認します。

## 覚える値 {#values}

| 項目 | 値 | 判断のポイント |
|---|---|---|
| Standard-IA、One Zone-IA | 最小 30 日、128 KB | 10 KB でも 128 KB 分の課金です |
| Glacier IR | 最小 90 日、128 KB | |
| Flexible Retrieval、Deep Archive | 最小 90 日、180 日、追加 40 KB | 復元が必要です |
| ライフサイクルの最小サイズ | 128 KB 未満はデフォルトで移行しない | サイズフィルターで変更できます |
| 1 回の `PUT`、マルチパートの上限 | 5 GB、48.8 TiB | 5 GB を超えるならマルチパートが必須です |
| マルチパートの推奨 | 100 MB 以上 | パートは最大 10,000 です |
| リクエストレート | プレフィックスごとに毎秒 3,500 書き込み、5,500 読み取り | |
| 署名付き URL | コンソール 1 分〜12 時間、CLI と SDK は最長 7 日 | 7 日は IAM ユーザーの認証情報のときです。ロールなら認証情報の期限で切れます |
| イベント通知の配信 | 少なくとも 1 回 | 処理は冪等にします |
| Deep Archive の取得 | Standard は 12 時間以内、Bulk は 48 時間以内 | Expedited は使えません |

## こう問われたらこう考える {#decisions}

| 状況 | 判断 |
|---|---|
| 古いログを安くし、1 年で削除する | ライフサイクルの `Transitions` と `Expiration` を設定します |
| アクセスパターンが読めない | Intelligent-Tiering を選びます。128 KB 未満は自動で移動しません |
| 平均 20 KB のログを大量に保存する | Standard-IA は不利です。Standard のままにするか、まとめて 1 つのオブジェクトにします |
| 消したはずのデータの容量が減らない | `NoncurrentVersionExpiration` と `AbortIncompleteMultipartUpload` を設定します |
| 消したオブジェクトを戻す | 削除マーカーをバージョン ID 指定で削除します |
| `uploads/` の `.jpg` だけを Lambda で処理する | `s3:ObjectCreated:*` に `prefix=uploads/`、`suffix=.jpg` を指定します |
| イベントを SQS FIFO で処理する | EventBridge を経由します |
| ブラウザから S3 に直接アップロードする | `PUT` の署名付き URL と CORS を使います |
| 世界中から大きなファイルを速くアップロードする | Transfer Acceleration を使います |
| 規制で誰も削除できないようにする | Object Lock のコンプライアンスモードにします |
| 毎秒多数のリクエストで 503 が出る | プレフィックスに分散し、バックオフします |
| 既存のオブジェクトを別リージョンにコピーする | S3 Batch Replication を使います |

## 引っかかりやすい点 {#traps}

- バージョニングが有効なバケットの `Expiration` は、削除マーカーを付けるだけです。実データは残ります。
- 未完了のマルチパートのパートは一覧に見えませんが課金されます。
- `s3:ObjectCreated:Put` だけを指定すると、マルチパートで届く `CompleteMultipartUpload` を取り逃がします。
- 通知のフィルターにワイルドカードは使えません。同じイベントタイプでは、`images/` と `images/thumb/` のように重なるルールは作れません。
- 通知を受けた Lambda が同じバケットに書き込むと無限ループになります。別のバケットに書くか、入力用のプレフィックスだけを通知の対象にします。
- ピリオドを含むバケット名では Transfer Acceleration を使えません。
