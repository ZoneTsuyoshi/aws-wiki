# データベースとキャッシュの問題集

対象の解説: [データベースとキャッシュ](../../../services/databases.md)

### 問1 {#q1}

開発者が RDS for MySQL にリードレプリカを作ろうとすると、作成できません。ソースの DB インスタンスはバックアップ保持期間が 0 に設定されています。最も適切な対応はどれですか。

- A. ソースを Multi-AZ に変更する
- B. RDS Proxy をソースに関連付ける
- C. ソースの自動バックアップを有効にする
- D. `require_secure_transport` を `ON` にする

??? success "答えと解説"
    **正解: C**

    リードレプリカの作成には、ソースの自動バックアップが有効である必要があります。保持期間を 0 以外にします。

    - A: Multi-AZ はレプリカ作成の前提ではありません。
    - B: RDS Proxy はレプリカの作成とは関係ありません。
    - C: 作成の前提を満たす正しい対応です。
    - D: TLS の設定はレプリカの作成とは関係ありません。

    **スキル:** C03 1.3.2 / **参照:** [リードレプリカと Multi-AZ](../../../services/databases.md#read-replicas)

### 問2 {#q2}

Lambda 関数がパスワードを使わずに RDS for PostgreSQL に接続できるように、IAM データベース認証を設定します。正しい説明はどれですか。（2つ選択）

- A. Route 53 のカスタム DNS 名を指定してトークンを生成する
- B. 実行ロールには `rds:Connect` の許可が必要である
- C. 認証トークンの有効期間は 12 時間で、切れると接続も切れる
- D. 実行ロールには `rds-db:connect` の許可が必要である
- E. 認証トークンの有効期間は 15 分で、確立済みの接続はその後も切れない

??? success "答えと解説"
    **正解: D, E**

    IAM 認証の権限は `rds-db:connect` です。トークンは 15 分で失効しますが、接続の確立にだけ使うので既存の接続には影響しません。

    - A: カスタム DNS 名ではトークンを生成できません。
    - B: `rds:` ではなく `rds-db:` の接頭辞です。
    - C: 有効期間が誤っています。
    - D: IAM データベース認証の正しいアクションです。
    - E: 正しい有効期間と動作です。

    **スキル:** C03 2.1.5 / **参照:** [IAM データベース認証](../../../services/databases.md#rds-iam-auth)

### 問3 {#q3}

マスターユーザーのパスワードをコードに書かず、定期的に自動で変更したいと考えています。運用負荷が最も低い方法はどれですか。

- A. Lambda で新しいパスワードを生成し、Parameter Store と DB に毎週書き込む
- B. RDS の `--manage-master-user-password` を指定する
- C. パスワードを KMS で暗号化し、Lambda の環境変数に保存して手動で更新する
- D. パスワードを S3 に SSE-KMS で保存し、起動時にダウンロードする

??? success "答えと解説"
    **正解: B**

    このオプションを使うと、RDS がパスワードを生成して Secrets Manager で管理し、デフォルトで 7 日ごとにローテーションします。

    - A: 動きますが、ローテーションの実装と運用を自分で行います。
    - B: マネージドで最も運用負荷が低い方法です。
    - C: 暗号化はできますが、ローテーションができません。
    - D: ローテーションの仕組みがなく、管理の手間も残ります。

    **スキル:** C03 2.2.7 / **参照:** [Secrets Manager との統合](../../../services/databases.md#rds-secrets-manager)

### 問4 {#q4}

RDS for PostgreSQL 14 のインスタンスで、すべてのクライアント接続に SSL を強制する必要があります。最も適切な方法はどれですか。

- A. セキュリティグループで 443 番だけを許可する
- B. インスタンスの暗号化を有効にする
- C. パラメータグループで `rds.force_ssl` を 1 にする
- D. 接続元の IAM ポリシーの条件で `aws:SecureTransport` を指定する

??? success "答えと解説"
    **正解: C**

    `rds.force_ssl` のデフォルトは PostgreSQL 15 以降で 1、14 以前では 0 です。デフォルトのパラメータグループは変更できないので、カスタムのグループで設定します。

    - A: DB の接続はポート 5432 などで、ポートでは SSL を強制できません。
    - B: 保存時の暗号化は転送中の暗号化とは別です。
    - C: 正しい設定です。
    - D: このキーは AWS API のリクエストの条件で、DB の接続には効きません。

    **スキル:** C03 2.2.1 / **参照:** [SSL/TLS](../../../services/databases.md#rds-ssl)

### 問5 {#q5}

Aurora クラスターのレプリカが 3 台あります。アプリは起動時に接続プールを作り、リーダーエンドポイントに長時間接続し続けます。読み取りが 1 台に偏っています。最も適切な説明はどれですか。

- A. リーダーエンドポイントは接続単位で分散し、クエリ単位では分散しない
- B. リーダーエンドポイントはクラスターで 1 台だけを固定して指す
- C. レプリカの優先度が同じだと負荷は分散されない
- D. レプリカの遅延が 100 ミリ秒を超えると、そのレプリカだけが使われる

??? success "答えと解説"
    **正解: A**

    分散されるのは接続を作るときです。接続を長く持ち続けると、作成時の偏りが続きます。接続の作り直しを考慮します。

    - A: リーダーエンドポイントの動作を正しく説明しています。
    - B: 接続ごとに複数のレプリカに分散します。
    - C: 優先度はフェイルオーバーの順序で、分散とは関係ありません。
    - D: 遅延によってこのように切り替わる仕組みはありません。

    **スキル:** C03 4.3.1 / **参照:** [エンドポイントの動作](../../../services/databases.md#aurora-endpoints)

### 問6 {#q6}

Aurora クラスターに、夜間レポート用の大きなインスタンス 2 台と、Web 用の小さなインスタンス 3 台があります。レポートを大きなインスタンスだけで実行したいとします。フェイルオーバーやインスタンスの入れ替えに強く、最も適切な方法はどれですか。

- A. レポートのコードに大きなインスタンスのエンドポイントを書く
- B. カスタムエンドポイントを作り、大きなインスタンスを登録する
- C. クラスターエンドポイントに接続し、読み取りだけを実行する
- D. リーダーエンドポイントの重み付けを大きなインスタンスに寄せる

??? success "答えと解説"
    **正解: B**

    カスタムエンドポイントは、指定したインスタンスのグループに接続を分散します。1 クラスターに最大 5 個作れます。

    - A: インスタンスの障害や入れ替えに追従できません。
    - B: 用途別にインスタンスを分ける機能です。
    - C: クラスターエンドポイントは現在のプライマリに接続します。
    - D: リーダーエンドポイントに重み付けの設定はありません。

    **スキル:** C03 1.3.2 / **参照:** [エンドポイントの動作](../../../services/databases.md#aurora-endpoints)

### 問7 {#q7}

開発環境の Aurora Serverless v2 を、夜間に接続がないときに最も安くしたいと考えています。設定として最も適切なものはどれですか。

- A. `MinCapacity=0.5`、`MaxCapacity=0.5` に固定し、夜間の容量を最小に保つ
- B. `MinCapacity=0`、`SecondsUntilAutoPause=600`
- C. `MaxCapacity=0` にする
- D. `SecondsUntilAutoPause=60` にする

??? success "答えと解説"
    **正解: B**

    対応するバージョンでは、最小を 0 ACU にして自動一時停止できます。間隔は 300〜86,400 秒です。ここでは 10 分で停止します。

    - A: 0.5 ACU の費用がかかり続け、昼間の性能も足りません。
    - B: 接続がなくなると停止し、接続が来ると再開します。
    - C: 上限を 0 にすることはできず、これでは DB が動きません。
    - D: 300 秒が最小で、60 秒は設定できません。

    **スキル:** C03 4.3.2 / **参照:** [Aurora Serverless v2](../../../services/databases.md#aurora-serverless-v2)

### 問8 {#q8}

Aurora グローバルデータベースのセカンダリリージョンのアプリが、書き込みも行います。プライマリリージョンのエンドポイントをアプリに設定する手間を減らしたいとします。最も適切な機能はどれですか。

- A. カスタムエンドポイント
- B. RDS Proxy のリードオンリーエンドポイント
- C. セカンダリ同士のマルチマスターレプリケーション
- D. セカンダリクラスターの書き込み転送

??? success "答えと解説"
    **正解: D**

    書き込み転送を有効にすると、セカンダリが受けた書き込みをプライマリに転送します。書けるのはプライマリのクラスターだけという原則は変わりません。

    - A: カスタムエンドポイントはクラスター内のインスタンスのグループです。
    - B: 読み取り専用のエンドポイントでは書き込みはできません。
    - C: グローバルデータベースのセカンダリは読み取り専用です。
    - D: 目的に合う機能です。

    **スキル:** C03 1.3.2 / **参照:** [Aurora グローバルデータベース](../../../services/databases.md#aurora-global-database)

### 問9 {#q9}

`max_connections` が 1,000 の RDS for MySQL に、2 つのアプリがそれぞれ別の RDS Proxy で接続します。管理者用の接続を残しつつ、両方が同時に上限まで使っても DB の接続が枯渇しないようにします。最も適切な設定はどれですか。

- A. 両方のプロキシで `MaxConnectionsPercent` をデフォルトの 100 のままにする
- B. 両方のプロキシで `MaxIdleConnectionsPercent` を 100 にする
- C. 両方のプロキシで `MaxConnectionsPercent` を 40 にする
- D. 両方のプロキシで `IdleClientTimeout` を 40 秒にする

??? success "答えと解説"
    **正解: C**

    `MaxConnectionsPercent` は `max_connections` に対する割合です。40% ずつなら合計 800 接続で、200 接続が残ります。

    - A: 合計で最大 200% になり、枯渇します。
    - B: アイドル接続を残す割合で、上限は決まりません。
    - C: 合計を上限より低くできます。
    - D: クライアント接続のアイドル時間で、DB の接続数の上限にはなりません。

    **スキル:** C03 4.3.1 / **参照:** [RDS Proxy の設定](../../../services/databases.md#rds-proxy-settings)

### 問10 {#q10}

Lambda から RDS Proxy 経由で接続すると、ときどき `Timed-out waiting to acquire database connection` が発生します。どの設定の待ち時間を超えたことを示していますか。

- A. `IdleClientTimeout`
- B. `InitQuery`
- C. `SecondsUntilAutoPause`
- D. `ConnectionBorrowTimeout`

??? success "答えと解説"
    **正解: D**

    プールが上限で接続が空かないとき、`ConnectionBorrowTimeout`(デフォルト 120 秒、最大 300 秒)を待ちます。超えるとこのエラーになります。ピン留めや長いトランザクションを確認します。

    - A: アイドルのクライアント接続を閉じるまでの時間です。
    - B: 新しい DB 接続を開いたときに実行する SQL です。
    - C: Aurora Serverless v2 の自動一時停止の設定です。
    - D: 接続を待つ時間の設定です。

    **スキル:** C03 4.1.1 / **参照:** [RDS Proxy の設定](../../../services/databases.md#rds-proxy-settings)

### 問11 {#q11}

RDS Proxy を導入しましたが、DB の接続数が減りません。`DatabaseConnectionsCurrentlySessionPinned` が高い値です。アプリは接続のたびに同じ `SET` 文を実行し、プリペアドステートメントも使っています。正しい対応はどれですか。（2つ選択）

- A. `MaxIdleConnectionsPercent` を 100 に上げる
- B. リードレプリカにプロキシを関連付ける
- C. プリペアドステートメントの使用を減らす
- D. `IdleClientTimeout` を 1 時間に延ばす
- E. 共通の `SET` 文をプロキシの初期化クエリに移す

??? success "答えと解説"
    **正解: C, E**

    `SET` 文とプリペアドステートメントはピン留めの原因です。接続ごとの `SET` は `InitQuery` に移し、プリペアドステートメントを減らします。

    - A: アイドル接続が増えるだけで、ピン留めは減りません。
    - B: RDS Proxy はリードレプリカには関連付けられません。
    - C: ピン留めの原因を減らせます。
    - D: 接続を長く持つだけで、原因は解消しません。
    - E: セッション状態の変更をなくせます。

    **スキル:** C03 4.3.1 / **参照:** [RDS Proxy](../../../services/databases.md#rds-proxy)

### 問12 {#q12}

Valkey のキャッシュで、データが 1 ノードのメモリに収まらなくなりました。読み取りだけでなく書き込みも増えています。最も適切な構成はどれですか。

- A. クラスターモードを無効のまま、レプリカを 5 台にする
- B. Memcached に変更して、既存のバックアップから復元する
- C. クラスターモードを有効にして、シャードに分割する
- D. リーダーエンドポイントをロードバランサーの後ろに置く

??? success "答えと解説"
    **正解: C**

    クラスターモードを有効にすると、最大 500 シャードにデータを分割でき、書き込みもメモリも水平に増やせます。

    - A: レプリカは読み取りを増やすだけで、メモリと書き込みは増えません。
    - B: Memcached にはレプリケーションがなく、バックアップと復元もサーバーレスだけです。
    - C: 要件に合う構成です。
    - D: リーダーエンドポイントは読み取り用で、容量は増えません。

    **スキル:** C03 4.3.4 / **参照:** [クラスターモード](../../../services/databases.md#cluster-mode)

### 問13 {#q13}

ノードベースの Redis OSS のクラスターに AUTH を有効にしようとしましたが、設定できません。また、後で接続を止めずにトークンを変更したいと考えています。正しい内容はどれですか。

- A. AUTH には転送中の暗号化が必要で、変更は `ROTATE` の後に `SET` で行う
- B. AUTH には保存時の暗号化が必要で、変更は `SET` の後に `ROTATE` で行う
- C. AUTH には Multi-AZ が必要で、変更はクラスターの再作成で行う
- D. AUTH にはクラスターモードが必要で、変更はノードの再起動で行う

??? success "答えと解説"
    **正解: A**

    AUTH は転送中の暗号化を有効にしたクラスターでのみ使えます。`ROTATE` は新旧両方のトークンを受け付け、`SET` は新しいトークンだけにします。

    - A: 正しい条件と手順です。
    - B: 必要なのは転送中の暗号化で、手順の順序も逆です。
    - C: Multi-AZ は AUTH の条件ではなく、再作成も不要です。
    - D: クラスターモードは AUTH の条件ではなく、再起動も不要です。

    **スキル:** C03 2.2.1 / **参照:** [認証と暗号化](../../../services/databases.md#elasticache-security)

### 問14 {#q14}

ElastiCache のキャッシュでメモリが一杯になると、`SET` がエラーになります。アプリはキーに TTL を付けておらず、`maxmemory-policy` はデフォルトのままです。純粋なキャッシュの用途で、最も適切な対応はどれですか。

- A. `maxmemory-policy` を `noeviction` にして、書き込みを守る
- B. `maxmemory-policy` を `allkeys-lru` にする
- C. `reserved-memory-percent` を 0 にする
- D. リードレプリカを 1 台追加する

??? success "答えと解説"
    **正解: B**

    デフォルトの `volatile-lru` は TTL 付きのキーだけを追い出します。TTL がなければ追い出せるキーがありません。`allkeys-lru` なら全キーが対象です。

    - A: `noeviction` はメモリが一杯のときに書き込みをエラーにする設定です。
    - B: 純粋なキャッシュに適した設定です。
    - C: データ以外に必要なメモリが足りなくなるおそれがあり、根本的な解決にもなりません。
    - D: レプリカでプライマリのメモリは増えません。

    **スキル:** C03 4.3.4 / **参照:** [追い出しとメモリ](../../../services/databases.md#eviction)

### 問15 {#q15}

アプリは遅延読み込みだけでキャッシュしています。DB を更新しても古い値が返り、キャッシュには読まれないデータも残り続けます。この 2 つの問題を解決する変更はどれですか。（2つ選択）

- A. キャッシュミスのときは DB を読まず、エラーを返す
- B. すべての書き込みに TTL を付ける(例: `ex=300`)
- C. すべてのデータをアプリの起動時にキャッシュへ読み込む
- D. ノードを増やして、すべてのデータを保持する
- E. DB を更新するときにキャッシュも書き込むライトスルーを追加する

??? success "答えと解説"
    **正解: B, E**

    ライトスルーで更新を反映すれば古い値が減ります。TTL を付ければ読まれないデータが自動で消え、古さの上限も決まります。これが基本の組み合わせです。

    - A: キャッシュ障害やミスで機能が止まります。
    - B: 不要なデータが残らず、古さの上限を決められます。
    - C: 読まれないデータがさらに増え、更新の問題も解決しません。
    - D: 費用が増えるだけで、古い値の問題は解決しません。
    - E: 更新時にキャッシュも最新にします。

    **スキル:** C03 1.3.3 / **参照:** [キャッシュ戦略](../../../services/databases.md#caching-strategies)

### 問16 {#q16}

DynamoDB の `GetItem` が中心の商品ページで、読み取りの遅延を数ミリ秒からマイクロ秒の単位に縮めたいと考えています。結果整合性で問題ありません。キャッシュの更新処理は自分で実装せず、コードの変更を最小にします。最も適切なものはどれですか。

- C. DAX クラスターを作成し、アプリを DAX クライアントに切り替える
- D. RDS Proxy を DynamoDB の前に置き、読み取りの接続を再利用する

??? success "答えと解説"

    - A: 誤り。動きますが、キャッシュの処理をアプリに実装する必要があります。
    - B: 誤り。GSI はアクセスパターンのためのもので、キャッシュではありません。
    - C: 正しい。データストアが DynamoDB のときの選択肢です。
    - D: 誤り。RDS Proxy は RDS と Aurora のためのもので、DynamoDB には使えません。

### 問17 {#q17}

データストアとキャッシュの組み合わせとして、適切なものはどれですか。（2つ選択）

- A. Aurora の頻出クエリの結果を、DAX にキャッシュする
- B. RDS の頻出クエリの結果を、ElastiCache にキャッシュする
