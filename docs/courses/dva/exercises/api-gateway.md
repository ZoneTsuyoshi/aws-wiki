# API Gateway の問題集

対象の解説: [Amazon API Gateway](../../../services/api-gateway.md)

### 問1 {#q1}

REST API の本番ステージで次の変更をしました。変更を反映するために、ステージへの再デプロイが必要なものはどれですか。（2つ選択）

- A. リソースポリシーの変更
- B. ステージのスロットリングの変更
- C. Lambda オーソライザーの設定（アイデンティティソースなど）の変更
- D. ステージ変数の値の変更
- E. ステージのキャッシュ TTL の変更

??? success "答えと解説"
    **正解: A, C**

    再デプロイが必要なのは、ステージの設定以外の変更です。ルート、メソッド、統合、オーソライザー、リソースポリシーが該当します。

    - A: リソースポリシーは再デプロイが必要です。
    - B: ステージの設定なので、再デプロイなしで反映されます。
    - C: オーソライザーの設定の変更は再デプロイが必要です。
    - D: ステージの設定です。
    - E: ステージの設定です。

    **スキル:** C03 3.1.5 / **参照:** [デプロイとステージ](../../../services/api-gateway.md#stages)

### 問2 {#q2}

リージョン API の REST API で、Lambda の処理に約 40 秒かかり、クライアントに 504 が返ります。同期の応答を維持したまま解決するには、どうするのが最も適切ですか。

- A. Lambda 関数のタイムアウトを 60 秒にする
- B. エッジ最適化エンドポイントに変更する
- C. HTTP API に移行し、統合タイムアウトを 45 秒に設定し直す
- D. クォータの引き上げを申請し、`timeoutInMillis` を増やす

??? success "答えと解説"
    **正解: D**

    リージョン API とプライベート API は、統合タイムアウトを 29 秒より長くできます。アカウントのスロットリングの枠が減ることがあります。古い教材の「29 秒で固定」は現在は当てはまりません。

    - A: API Gateway の待ち時間は変わらないので、504 のままです。
    - B: エッジ最適化は 29 秒のまま引き上げられません。
    - C: HTTP API の上限は 30 秒です。
    - D: リージョン API で使える方法です。

    **スキル:** C03 1.1.4 / **参照:** [統合の共通設定](../../../services/api-gateway.md#integration-settings)

### 問3 {#q3}

ペイロード形式バージョン 2.0 の Lambda 統合を使う HTTP API で、関数が `{"message": "ok"}` だけを返しました。クライアントが受け取る結果はどれですか。

- A. 200 で、本文は `{"message": "ok"}` になる
- B. 502 Bad Gateway になる
- C. 500 Internal Server Error が返り、実行ログに記録される
- D. 204 No Content で、本文は空になる

??? success "答えと解説"
    **正解: A**

    形式 2.0 では、有効な JSON が返り `statusCode` がなければ、ステータスを 200、`content-type` を `application/json`、本文をその JSON と推定します。

    - A: 2.0 の推定の動きです。
    - B: 形式 1.0 や REST API のプロキシ統合で起きる結果です。
    - C: この応答は有効で、設定のエラーにもなりません。
    - D: 本文は返されます。

    **スキル:** C03 1.1.4 / **参照:** [プロキシ統合](../../../services/api-gateway.md#proxy-integration)

### 問4 {#q4}

REST API の非プロキシ統合に、`application/json` のマッピングテンプレートだけを定義しました。`passthroughBehavior` は `WHEN_NO_TEMPLATES` です。クライアントが `application/xml` の本文を送ると、どうなりますか。

- A. 変換せずにバックエンドへ送られる
- B. JSON のテンプレートで変換される
- C. 415 が返る
- D. 400 が返る

??? success "答えと解説"
    **正解: C**

    `WHEN_NO_TEMPLATES` は、テンプレートが一つもないときだけ通します。定義があって一致しなければ 415 です。

    - A: `WHEN_NO_MATCH` の動きです。
    - B: `Content-Type` が一致しないのでこのテンプレートは使われません。
    - C: この設定の動きで、415 は Unsupported Media Type です。
    - D: 400 はリクエスト検証の失敗で返るコードです。

    **スキル:** C03 1.1.4 / **参照:** [テンプレートがないときの動き](../../../services/api-gateway.md#passthrough)

### 問5 {#q5}

Lambda プロキシ統合の REST API で JPEG を返しています。関数は Base64 と `isBase64Encoded: true` を返し、`binaryMediaTypes` に `image/jpeg` を登録しました。ブラウザの `<img>` では画像が表示されません。ブラウザは `Accept: image/webp,image/*,*/*;q=0.8` を送ります。`Accept` の順序は制御できません。最も適切な対応はどれですか。

- A. `contentHandling` を `CONVERT_TO_TEXT` にする
- B. `binaryMediaTypes` を `*/*` にする
- C. 関数の `Content-Type` を `text/plain` にする
- D. ステージのキャッシュを有効にする

??? success "答えと解説"
    **正解: B**

    API Gateway は最初の `Accept` だけを見てバイナリかどうかを判断します。順序を制御できないときは `*/*` にします。

    - A: Lambda プロキシ統合の設定ではなく、バイナリを文字列にする方向の変換です。
    - B: AWS が案内している対応です。
    - C: 画像として表示できなくなります。
    - D: キャッシュは本文の変換に関係しません。

    **スキル:** C03 1.1.4 / **参照:** [バイナリメディア](../../../services/api-gateway.md#binary-media)

### 問6 {#q6}

REST API のメソッドで `limit` を必須のクエリパラメーターにし、パラメーターのバリデーターを有効にしました。`?limit=abc` がバックエンドに届きます。原因として最も適切なものはどれですか。

- A. クエリパラメーターにはバリデーターを使えない
- B. パススルーの設定が `WHEN_NO_MATCH` になっている
- C. モデルの `limit` の型が `string` になっている
- D. パラメーターの検証は存在と空でないことだけを確認する

??? success "答えと解説"
    **正解: D**

    パラメーターの検証は、必須の項目があって空でないことだけを見ます。形式はバックエンドで確認します。

    - A: クエリパラメーターも検証の対象です。`limit` がないリクエストは 400 で弾かれます。
    - B: パススルーは本文のテンプレートの設定です。
    - C: モデルは本文の検証に使い、クエリには適用されません。
    - D: バリデーターの仕様です。

    **スキル:** C03 1.1.4 / **参照:** [リクエストの検証](../../../services/api-gateway.md#request-validation)

### 問7 {#q7}

REST API の統合の URI で `${stageVariables.alias}` を使い、ステージごとに Lambda エイリアスを切り替えています。新しい `test` ステージから呼ぶと、権限のエラーで失敗します。最も適切な修正はどれですか。

- A. 関数の実行ロールに `execute-api:Invoke` を追加する
- B. API のリソースポリシーで `lambda:InvokeFunction` を許可する
- C. `add-permission` で API Gateway に呼び出しを許可する
- D. ステージ変数の値に関数の完全な ARN を指定する

??? success "答えと解説"
    **正解: C**

    ステージ変数で関数を指定すると、権限は自動で付きません。呼び出す関数やエイリアスごとに `aws lambda add-permission` で許可します。

    - A: 実行ロールは関数が他を呼ぶ権限です。API を呼ぶ権限でもありません。
    - B: API のリソースポリシーは API を呼ぶ側を制御します。
    - C: `test` エイリアスのリソースベースポリシーに許可を追加します。
    - D: ARN にしても権限は付きません。

    **スキル:** C03 3.2.4 / **参照:** [ステージ変数](../../../services/api-gateway.md#stage-variables)

### 問8 {#q8}

REST API の `prod` ステージにカナリアリリースを設定しました。開発者はカナリアへのリクエストの実行ログだけを確認したいと考えています。どのロググループを見ますか。

- A. `API-Gateway-Execution-Logs/{rest-api-id}/{stage-name}/Canary`

- C. `/aws/apigateway/executions/{rest-api-id}/{stage-name}/canary-release`

    **正解: A**

    カナリアのログは本番のロググループと、末尾に `/Canary` が付く専用のグループに出力されます。

    - A: 実行ログの専用グループです。
    - B: アクセスログのグループは自分で作ります。この名前の決まりはありません。
    - C: 実行ログの名前の形式ではありません。
    - D: Lambda のログで、カナリアごとに分かれません。

### 問9 {#q9}

REST API に使用量プランと API キーを設定しました。次のリクエストに対するステータスコードの組み合わせとして正しいものはどれですか。（2つ選択）

- A. 無効な API キーのリクエストは 403 になる
- B. 無効な API キーのリクエストは 401 になる
- C. プランの月間クォータを使い切ったリクエストは 429 になる
- D. プランの月間クォータを使い切ったリクエストは 403 になる
- E. プランの月間クォータを使い切ったリクエストは 503 になる

??? success "答えと解説"
    **正解: A, C**

    無効なキーは `INVALID_API_KEY` で 403、クォータ超過は `QUOTA_EXCEEDED` で 429 です。

    - A: `INVALID_API_KEY` の既定のコードです。
    - B: 401 は `UNAUTHORIZED` で、オーソライザーの認証失敗に使います。
    - C: `QUOTA_EXCEEDED` の既定のコードです。
    - D: クォータ超過は 429 です。
    - E: クォータ超過で 503 は返りません。

    **スキル:** C03 4.1.1 / **参照:** [エラーコード](../../../services/api-gateway.md#errors)

### 問10 {#q10}

顧客の端末は `X-API-Key` ヘッダーを送れません。そこで Lambda オーソライザーがトークンから顧客を識別し、使用量プランで制限したいと考えています。最も適切な設定はどれですか。

- A. HTTP API に移行し、ルートのスロットリングを設定する
- B. `apiKeySource` を `HEADER` のままにし、`Authorization` ヘッダーにキーを入れる
- C. マッピングテンプレートで `X-API-Key` を追加する
- D. `apiKeySource` を `AUTHORIZER` にし、`usageIdentifierKey` を返す

??? success "答えと解説"
    **正解: D**

    キーソースを `AUTHORIZER` にすると、オーソライザーの応答の `usageIdentifierKey` を API キーとして使います。

    - A: HTTP API には使用量プランがありません。
    - B: `HEADER` は `X-API-Key` ヘッダーを読みます。
    - C: 統合リクエストの変換は使用量プランの判定の後で、効果がありません。
    - D: 公式に用意された方法です。

    **スキル:** C03 2.1.2 / **参照:** [使用量プランと API キー](../../../services/api-gateway.md#usage-plans)

### 問11 {#q11}

API の `Latency` が 2,000 ms で、`IntegrationLatency` が 100 ms です。ユーザーからは遅いという報告があります。最初に調べる対象として最も適切なものはどれですか。

- A. バックエンドの Lambda 関数のコードとレイヤー
- B. バックエンドのデータベースのクエリ
- C. オーソライザーなど API Gateway 側の処理
- D. Lambda 関数のメモリの設定

??? success "答えと解説"
    **正解: C**

    `IntegrationLatency` はバックエンドとのやり取りの時間で、`Latency` はそれに API Gateway の処理を足した全体です。差の 1,900 ms はバックエンドの外にあります。

    - A: バックエンドの時間は 100 ms です。
    - B: データベースもバックエンドの時間に含まれます。
    - C: 差の大きい部分です。オーソライザーの実行時間は確認すべき候補です。
    - D: バックエンドの関数の設定なので、差の説明になりません。

    **スキル:** C03 4.1.2 / **参照:** [ログとメトリクス](../../../services/api-gateway.md#logging-metrics)

### 問12 {#q12}

REST API のステージでキャッシュを有効にしました。`GET` は速くなりましたが、検索用の `POST /search` はキャッシュされていません。結果は同じ検索語なら同じです。最も適切な対応はどれですか。

- A. `POST /search` のメソッドの設定で、キャッシュを有効にする
- B. ステージのキャッシュ容量を増やす
- C. ステージの既定の TTL を 3,600 秒にする
- D. `Cache-Control: max-age=3600` をクライアントに送らせる

??? success "答えと解説"
    **正解: A**

    ステージのキャッシュの既定で有効なのは `GET` だけです。他のメソッドはメソッドの設定で上書きします。検索語はキャッシュキーにも入れます。

    - A: メソッドごとの上書きが正しい方法です。
    - B: 容量は対象のメソッドを変えません。
    - C: TTL も対象のメソッドを変えません。
    - D: このヘッダーで `POST` がキャッシュされるようにはなりません。

    **スキル:** C03 4.3.4 / **参照:** [キャッシュ](../../../services/api-gateway.md#caching)

### 問13 {#q13}

REST API のキャッシュで、`Cache-Control: max-age=0` を送れるのは特定の IAM ロールだけにしたいと考えています。権限のないクライアントのヘッダーは無視して通常どおり応答し、応答には警告を付けます。正しい設定はどれですか。

- A. `unauthorizedCacheControlHeaderStrategy` を `FAIL_WITH_403` にする
- B. `unauthorizedCacheControlHeaderStrategy` を `SUCCEED_WITHOUT_RESPONSE_HEADER` にする
- C. `unauthorizedCacheControlHeaderStrategy` を `SUCCEED_WITH_RESPONSE_HEADER` にする
- D. `requireAuthorizationForCacheControl` を `false` にする

??? success "答えと解説"
    **正解: C**

    権限のあるロールに `execute-api:InvalidateCache` を与え、未承認のときの動きを `SUCCEED_WITH_RESPONSE_HEADER` にします。

    - A: 403 を返すので、通常どおりの応答になりません。
    - B: 警告ヘッダーが付きません。
    - C: ヘッダーを無視して処理し、警告を付けます。
    - D: 誰でも無効化できるようになります。

    **スキル:** C03 4.3.4 / **参照:** [キャッシュの無効化](../../../services/api-gateway.md#cache-invalidation)

### 問14 {#q14}

外部の決済 API がまだ利用できない状態で、REST API の開発を進めます。バックエンドなしで決まった JSON を返したいと考えています。最も適切な統合はどれですか。

- A. `HTTP_PROXY` 統合で外部 API の URL を指定する
- B. `MOCK` 統合で統合レスポンスに本文を定義する

    **正解: B**

    - B: この場面のための統合です。
    - C: 関数の作成と管理が必要で、運用負荷が増えます。

    **スキル:** C03 3.2.2 / **参照:** [モック統合](../../../services/api-gateway.md#mock-integration)

### 問15 {#q15}

`TOKEN` タイプの Lambda オーソライザーで TTL を 300 秒にしています。関数は `event["methodArn"]` だけを許可するポリシーを返します。`GET /orders` のあとに同じトークンで `POST /orders` を呼ぶと 403 になります。最も適切な修正はどれですか。

- B. API の全メソッドに適用できるポリシーを返す
- C. `identityValidationExpression` を削除する
- D. オーソライザーのタイムアウトを延ばす

??? success "答えと解説"
    **正解: B**

    キャッシュされたポリシーは同じトークンの他のメソッドにも使われます。全メソッドに適用できるポリシーを返すか、TTL を 0 にしてメソッドごとに判定します。

    - A: トークンは有効で、問題はキャッシュされたポリシーの範囲です。
    - B: AWS が案内している対応です。
    - C: 正規表現の検証で、ポリシーの範囲とは関係ありません。
    - D: 時間切れによる問題ではありません。

    **スキル:** C03 2.1.2 / **参照:** [Lambda オーソライザー](../../../services/api-gateway.md#lambda-authorizer)

`REQUEST` タイプの Lambda オーソライザーで、キャッシュを有効にし、アイデンティティソースをヘッダー `Authorization` とクエリ `tenant` にしました。`tenant` のないリクエストはどうなりますか。

### 問17 {#q17}

HTTP API に CORS 設定を追加しています。開発者が Lambda の応答の `Access-Control-Allow-Origin` を変更しましたが、ブラウザに届く値は変わりません。原因として最も適切なものはどれですか。

### 問18 {#q18}

新しいリージョンの REST API で、ステージの実行ログを `INFO` にしましたが、CloudWatch Logs に何も出ません。確認する項目として適切なものはどれですか。（2つ選択）

### 問19 {#q19}

HTTP API で運用中の API に新しい要件が追加されました。REST API に移行しないと実現できないものはどれですか。（3つ選択）

- A. AWS WAF によるリクエストの保護
- B. API キーによるクライアントごとのスロットリング
- C. JWT オーソライザーによるトークンの検証
- D. マッピングテンプレートによる本文の変換
- E. Cloud Map を使ったプライベート統合
- F. 変更の自動デプロイ

??? success "答えと解説"
    **正解: A, B, D**

    WAF、使用量プランと API キー、本文の変換は REST API の機能です。

    - A: HTTP API は AWS WAF に対応していません。
    - B: HTTP API に API キーはありません。
    - C: JWT オーソライザーは HTTP API の機能で、REST API にはありません。
    - D: HTTP API はパラメーターのマッピングのみです。
    - E: Cloud Map は HTTP API の機能で、REST API にはありません。
    - F: 自動デプロイは HTTP API の機能です。

### 問20 {#q20}

チャットアプリの WebSocket API で、メッセージのないクライアントの接続が約 10 分で切れます。通信が続くクライアントも 2 時間で切れます。最も適切な対応はどれですか。

- A. クライアントが定期的にメッセージを送り、切れたら再接続する
- B. API Gateway のサービスクォータでアイドルタイムアウトを引き上げる
- C. `$disconnect` ルートに Lambda 統合を追加して切断を止める
- D. `$connect` ルートの統合タイムアウトを 29 秒に増やす

??? success "答えと解説"
    **正解: A**

    アイドル 10 分と接続 2 時間は変更できない上限で、1001 で閉じます。クライアント側で定期的に ping メッセージを送り、再接続を実装します。

    - A: 上限に合わせた実装です。
    - B: どちらの上限も引き上げられません。
    - C: `$disconnect` は切断の通知で、切断を止められません。
    - D: 統合の時間で、接続の持続時間には関係しません。

    **スキル:** C03 1.1.4 / **参照:** [WebSocket API](../../../services/api-gateway.md#websocket)

### 問21 {#q21}

REST API のモック統合で、決まった JSON を 200 で返します。必要な設定はどれですか。（2つ選択）

- A. HTTP API に作り直して、統合タイプにモックを指定する
- B. ステージ変数に、応答の本文の JSON を設定する
- C. 統合リクエストのマッピングテンプレートで `{"statusCode": 200}` を返す
- D. 200 の統合レスポンスのマッピングテンプレートに本文の JSON を書く
- E. 統合リクエストのマッピングテンプレートに本文の JSON だけを書く

??? success "答えと解説"
    **正解: C, D**

    統合リクエストのテンプレートで、どの統合レスポンスを返すかを `statusCode` で決めます。クライアントに返す本文は、対応する統合レスポンスのテンプレートに書きます。

    - A: 誤り。モック統合は REST API の機能で、HTTP API にはありません。
    - B: 誤り。ステージ変数は応答の本文を作る仕組みではありません。
    - C: 正しい。返すレスポンスを選びます。
    - D: 正しい。ここに書いた内容が本文になります。
    - E: 誤り。ここには `statusCode` を書きます。本文は統合レスポンスに書きます。

    **スキル:** C03 3.2.2 / **参照:** [モック統合](../../../services/api-gateway.md#mock-integration)

### 問22 {#q22}

外部 API のモックを REST API で作り、結合テストで成功と失敗の両方を再現します。クエリパラメーター `scenario` が `ok` なら 200、それ以外は 500 を返します。バックエンドは作りません。最も適切な設定はどれですか。

- A. ステージ変数でステージごとに 200 と 500 を固定し、テストごとに呼ぶステージを切り替える
- B. メソッドレスポンスに 500 だけを定義し、ゲートウェイレスポンスで 200 に変換して返す
- C. Lambda 関数を統合に指定し、関数の中で `scenario` の値を見てステータスコードを分ける
- D. テンプレートで `statusCode` を分岐し、200 と 500 の統合レスポンスを定義する

??? success "答えと解説"
    **正解: D**

    モック統合の統合リクエストのテンプレートでは、`$input.params('scenario')` を使って条件を書けます。`#if` で `statusCode` を分けると、それに対応する統合レスポンスが返ります。

    - A: 誤り。リクエストの内容では切り替えられず、要件に合いません。
    - B: 誤り。ゲートウェイレスポンスは、API Gateway のエラーの応答をカスタマイズする機能です。
    - C: 誤り。動きますが、バックエンドを作らないという要件に反します。
    - D: 正しい。リクエストごとに結果を変えられます。

    **スキル:** C03 3.2.2 / **参照:** [モック統合](../../../services/api-gateway.md#mock-integration)

### 問23 {#q23}

REST API の `DELETE /items/{id}` を、コンソールのメソッドの Test タブから試しました。ログの欄に記録が表示されましたが、CloudWatch Logs には何も増えていません。このテストの説明として正しいものはどれですか。

- A. バックエンドを呼ばず、モックの応答とログだけが画面に返される
- B. 呼び出しの結果は本物で、表示されるログは模擬である
- C. 呼び出しの結果は模擬で、ログは実際に CloudWatch Logs に送られる
- D. Test タブは、ステージにデプロイ済みのメソッドにだけ使用できる

??? success "答えと解説"
    **正解: B**

    Test タブの呼び出しは、コンソールの外から呼ぶのと同じです。削除のメソッドが成功すれば、データは実際に削除され、元に戻せません。ログの欄は、外から呼んだときに記録される内容を模擬したものです。

    - A: 誤り。バックエンドは実際に呼ばれます。
    - B: 正しい。本番のデータに向けて試すときは注意が必要です。
    - C: 誤り。結果とログの説明が逆です。
    - D: 誤り。手順でステージは選ばず、リソースのメソッドに対して実行します。

    **スキル:** C03 3.2.3 / **参照:** [テスト用エンドポイントとテストイベント](../../../services/api-gateway.md#test-endpoints)
