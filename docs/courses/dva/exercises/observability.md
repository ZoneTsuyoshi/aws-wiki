# オブザーバビリティの問題集

対象の解説: [オブザーバビリティ（CloudWatch / X-Ray / CloudTrail）](../../../services/observability.md)

### 問1 {#q1}

ある開発者は、1 日に数回だけ動くバッチの Lambda 関数の `Errors` メトリクスにアラームを作りました。周期は 300 秒です。エラーがない日はアラームが `INSUFFICIENT_DATA` のままで、運用担当者が状態を判断しづらいと言っています。最も適切な変更はどれですか。

- A. `TreatMissingData` を `breaching` に変更する
- B. `TreatMissingData` を `notBreaching` に変更する
- C. `EvaluationPeriods` を 288 に増やす
- D. アラームの統計を `SampleCount` に変更する

??? success "答えと解説"
    **正解: B**

    エラーが起きたときだけ値が増える用途では、データがない期間を正常として扱います。`notBreaching` にすると、全期間が欠落しても状態は `OK` です。

    - A: 欠落を異常とみなすので、平常時に `ALARM` になります。
    - B: 正しい設定です。既定の `missing` では、全欠落で `INSUFFICIENT_DATA` になります。
    - C: 評価する期間を増やしても、欠落の扱いは変わりません。
    - D: 統計を変えても、データポイントがない事実は変わりません。

    **スキル:** C03 4.2.3 / **参照:** [欠落データの扱い](../../../services/observability.md#treat-missing-data)

### 問2 {#q2}

ある API の遅延を監視するアラームを作ります。単発のスパイクでは通知せず、直近 5 分のうち 3 分でしきい値を超えたときに通知します。連続である必要はありません。設定として最も適切なものはどれですか。

- A. `Period=300`、`EvaluationPeriods=3`、`DatapointsToAlarm=1`
- B. `Period=60`、`EvaluationPeriods=3`、`DatapointsToAlarm=5`
- C. `Period=60`、`EvaluationPeriods=3`、`DatapointsToAlarm=3`
- D. `Period=60`、`EvaluationPeriods=5`、`DatapointsToAlarm=3`

??? success "答えと解説"
    **正解: D**

    M out of N では、`EvaluationPeriods` が N、`DatapointsToAlarm` が M です。1 分周期で N=5、M=3 にすると、直近 5 分のうち 3 回の超過で `ALARM` になります。超過は連続でなくて構いません。

    - A: 15 分のうち 1 回の超過で鳴るので、単発のスパイクでも通知します。
    - B: M を N より大きくする設定は意味をなしません。
    - C: 3 分連続の超過が条件になり、要件の「連続でなくてよい」に合いません。
    - D: 要件どおりです。

    **スキル:** C03 4.2.3 / **参照:** [評価の仕組みと M out of N](../../../services/observability.md#alarm-evaluation)

### 問3 {#q3}

開発者は、注文処理の遅延を `PutMetricData` の `StatisticValues` で 1 分ごとに集計して送っています。`SampleCount` は約 500 で、`Minimum` と `Maximum` は異なります。ダッシュボードに `p99` を表示したいのですが、値が取得できません。最も適切な対応はどれですか。

- A. `StorageResolution` を 1 にして送り直す
- B. `Values` と `Counts` の配列で分布を送る
- C. ダッシュボードの期間を 300 秒に変更する
- D. 詳細モニタリングをアカウントで有効にする

??? success "答えと解説"
    **正解: B**

    パーセンタイルの計算には生のデータが必要です。統計セットでは、一定の条件（`SampleCount` が 1 など）を満たす場合を除いて取得できません。`Values` と `Counts` なら、1 メトリクスあたり 150 個の値で分布を送れ、パーセンタイルも取得できます。

    - A: 解像度を上げても、統計セットの制約は解消しません。
    - B: 正しい方法です。
    - C: 期間を変えても、もとのデータに分布の情報がありません。
    - D: 詳細モニタリングは EC2 の機能で、カスタムメトリクスには関係ありません。

    **スキル:** C03 4.2.2 / **参照:** [統計とパーセンタイル](../../../services/observability.md#statistics)

### 問4 {#q4}

Lambda 関数からカスタムメトリクスを出すために、EMF で次の 1 行を標準出力へ出しています。ログには残りますが、メトリクスが CloudWatch に現れません。

`[INFO] {"_aws":{"Timestamp":1767225600000,"CloudWatchMetrics":[{"Namespace":"MyApp","Dimensions":[["Service"]],"Metrics":[{"Name":"Latency","Unit":"Milliseconds"}]}]},"Service":"orders","Latency":120}`

最も可能性の高い原因はどれですか。

- A. `Metrics` に `StorageResolution` が指定されていない
- B. `Dimensions` は二重の配列にしてはいけない
- C. メッセージ全体が 1 つの JSON になっていない
- D. EMF を使うには `cloudwatch:PutMetricData` が必要である

??? success "答えと解説"
    **正解: C**

    EMF のログイベントは、前後に余分な文字のない有効な JSON オブジェクトである必要があります。`[INFO] ` が先頭に付いていると、JSON として扱われず抽出されません。

    - A: `StorageResolution` は任意で、省略すると標準解像度です。
    - B: `Dimensions` はディメンションセットの配列で、二重の配列が正しい形です。
    - C: これが原因です。
    - D: EMF はログから抽出されるので、関数からこの API を呼ぶ必要はありません。

    **スキル:** C03 4.2.2 / **参照:** [EMF の JSON 構造](../../../services/observability.md#emf-structure)

### 問5 {#q5}

EC2 インスタンスがメモリ不足で停止する疑いがあります。運用担当者は詳細モニタリングを有効にしましたが、`AWS/EC2` 名前空間にメモリのメトリクスが見つかりません。最も適切な対応はどれですか。

- A. CloudWatch エージェントを導入して `mem_used_percent` を送る
- B. ステータスチェックのメトリクスの期間を 1 分に変更する
- C. 詳細モニタリングを再度有効にしてから 15 分待つ
- D. インスタンスを高解像度メトリクスに対応する種類へ変更する

??? success "答えと解説"
    **正解: A**

    メモリは OS の内部の値なので、EC2 の既定のメトリクスには含まれません。詳細モニタリングは間隔を 1 分にするだけです。CloudWatch エージェントで収集します。

    - A: 正しい対応です。
    - B: ステータスチェックはメモリ使用率を示しません。基本モニタリングでも 1 分です。
    - C: 待っても、もともと収集されていない値は現れません。
    - D: インスタンスの種類は、メモリのメトリクスの有無に関係しません。

    **スキル:** C03 4.2.2 / **参照:** [EC2 の既定メトリクスとエージェント](../../../services/observability.md#ec2-metrics)

### 問6 {#q6}

REST API の応答が遅いと報告がありました。CloudWatch で `Latency` の p99 が 3,100 ms、`IntegrationLatency` の p99 が 3,050 ms でした。次に調査すべき対象として最も適切なものはどれですか。

    **正解: C**

    `Latency` には `IntegrationLatency` が含まれます。差が 50 ms と小さいので、時間の大半はバックエンドの応答待ちです。

    - A: オーソライザーの時間は差の側に現れるので、ここでは小さいはずです。
    - B: マッピングも同様に、差の側に現れます。
    - C: 正しい調査対象です。

### 問7 {#q7}

Lambda 関数の利用者から「ときどきエラーになる」と報告がありますが、`Errors` は 0 で、`Invocations` のグラフも平らです。呼び出し側のログには `TooManyRequestsException` が記録されています。最初に確認すべきメトリクスはどれですか。

- A. `DeadLetterErrors`
- B. `IteratorAge`
- C. `AsyncEventAge`
- D. `Throttles`

??? success "答えと解説"
    **正解: D**

    スロットリングされた呼び出しはコードが動かないので、`Invocations` にも `Errors` にも数えられません。`Throttles` で確認します。

    - A: 非同期呼び出しで DLQ への送信に失敗した回数で、この症状とは合いません。
    - B: ストリームの処理の遅れを示します。
    - C: 非同期イベントの待ち時間を示します。例外を受け取る呼び出しの説明になりません。
    - D: 正しいメトリクスです。

    **スキル:** C03 4.1.2 / **参照:** [Lambda の既定メトリクス](../../../services/observability.md#lambda-metrics)

### 問8 {#q8}

開発チームは、アプリのログを取り込み料金の安いクラスで作ったロググループに送っています。その後、特定のエラー文字列を数えてアラームを作るよう求められました。ロググループのクラスは `INFREQUENT_ACCESS` です。最も適切な対応はどれですか。

- A. ロググループのクラスを Standard に変更して、メトリクスフィルターを作る
- B. Standard のロググループを新しく作り、そこへ送ってメトリクスフィルターを作る
- C. 今のロググループにメトリクスフィルターを作り、`Live Tail` で確認する
- D. 今のロググループにサブスクリプションフィルターを作り、Lambda で数える

??? success "答えと解説"
    **正解: B**

    Essentials（旧 Infrequent Access）クラスではメトリクスフィルターを使えません。クラスは作成後に変更できないので、Standard のロググループを新しく作ります。

    - A: クラスは作成後に変更できません。
    - B: 正しい対応です。
    - C: メトリクスフィルターも Live Tail も、このクラスでは使えません。
    - D: サブスクリプションフィルターもこのクラスでは使えません。

    **スキル:** C03 4.2.1 / **参照:** [ログクラス](../../../services/observability.md#log-classes)

### 問9 {#q9}

ログを指定の KMS キーで暗号化するため、開発者は `aws logs associate-kms-key` を実行しましたが、権限のエラーになりました。IAM ユーザーには必要な権限があります。最も可能性の高い修正はどれですか。

- A. キーポリシーで `logs.<region>.amazonaws.com` に使用を許可する

- C. ロググループのクラスを Standard に変更する
- D. 既存のログを S3 へエクスポートしてから再実行する

??? success "答えと解説"
    **正解: A**

    - A: 正しい修正です。

    - C: KMS 暗号化は Standard と Essentials の両方で使えます。

### 問10 {#q10}

開発者は、複数のロググループを同じアカウントの S3 へ `CreateExportTask` で並行してエクスポートするスクリプトを書きました。2 つ目以降の呼び出しが `LimitExceededException` で失敗します。最も適切な説明はどれですか。

- A. S3 バケットが別のリージョンにあるため
- B. S3 バケットの暗号化が AES-256 であるため
- C. アカウントでアクティブなエクスポートタスクは 1 つだけであるため
- D. エクスポートは Essentials のロググループでしか使えないため

??? success "答えと解説"
    **正解: C**

    `RUNNING` か `PENDING` のエクスポートタスクは、アカウントで 1 つまでです。`DescribeExportTasks` で完了を確認してから次を開始します。

    - A: リージョンの違いは最初のタスクでも問題になり、2 つ目以降だけの失敗を説明しません。
    - B: AES-256 と SSE-KMS には対応しています。
    - C: 正しい説明です。
    - D: エクスポートは両方のクラスで使えます。

    **スキル:** C03 1.3.1 / **参照:** [S3 へのエクスポート](../../../services/observability.md#logs-export)

### 問11 {#q11}

JSON のログを、平均 200 バイトで 5,000 件ずつ `PutLogEvents` で送っています。リクエストがサイズ超過で失敗することがあります。原因の説明として最も適切なものはどれですか。

- A. 1 回のイベント数の上限が 1,000 件である
- B. 1 イベントの上限が 256 バイトである
- C. 各イベントの 26 バイトを足すと 1,048,576 バイトを超える
- D. バッチ内のイベントの時間幅が 24 時間を超えている

??? success "答えと解説"
    **正解: C**

    バッチのサイズは、メッセージのバイト数と各イベント 26 バイトの合計で計算します。`(200 + 26) × 5,000 = 1,130,000` バイトで、上限の 1,048,576 バイトを超えます。

    - A: イベント数の上限は 10,000 件です。
    - B: 1 イベントの上限は 1 MB です。
    - C: 正しい説明です。
    - D: 時間幅の超過はサイズの超過とは別の失敗です。

    **スキル:** C03 1.1.5 / **参照:** [PutLogEvents の制限](../../../services/observability.md#put-log-events)

### 問12 {#q12}

メトリクスフィルターの設定について、正しい説明はどれですか。（2つ選択）

- A. ログの `requestId` をディメンションにしてリクエストごとの値を見るのが推奨である
- B. 値の種類が 1,000 に達すると、そのフィルターは無効化されることがある
- C. 作成前に取り込まれたログにも遡って適用される
- D. ディメンションを付けたメトリクスには `defaultValue` を指定できない
- E. ディメンションは 1 つのフィルターに最大 30 個指定できる

??? success "答えと解説"
    **正解: B, D**

    ディメンションの値ごとにカスタムメトリクスとして課金されるので、高カーディナリティの値を避けます。1,000 種類の名前と値の組が生成されると、CloudWatch Logs はフィルターを無効にします。また、ディメンションと `defaultValue` は併用できません。

    - A: 値ごとにメトリクスが増え、料金が跳ね上がるので避けます。
    - B: 正しい説明です。
    - C: フィルターは過去のログに適用されません。
    - D: 正しい説明です。
    - E: メトリクスフィルターのディメンションは 3 個までです。30 個は `PutMetricData` の上限です。

    **スキル:** C03 4.2.2 / **参照:** [メトリクスフィルターの設定](../../../services/observability.md#metric-filter-settings)

ログストリームが少数のロググループを、サブスクリプションフィルターで Kinesis Data Streams へ送っています。特定のシャードに偏り、`DeliveryThrottling` が増えています。ストリームを変更せずに偏りを減らす設定はどれですか。

### 問14 {#q14}

Logs Insights で、各サーバーの最新のログを 1 件ずつ表示したいと考えています。最も適切なクエリはどれですか。

- A. `sort @timestamp desc | dedup server`
- B. `dedup server | sort @timestamp desc`
- C. `stats latest(@timestamp) | limit 1`
- D. `fields server | display @timestamp | limit 1`

??? success "答えと解説"
    **正解: A**

    `dedup` は並べ替えの順で先頭の結果を残すので、先に新しい順へ並べます。`dedup` の後に使えるコマンドは `limit` だけです。

    - A: 正しいクエリです。
    - B: `dedup` の後に `sort` は使えません。
    - C: サーバーごとに分かれておらず、全体で 1 件になります。
    - D: 全体で 1 件だけになり、サーバーごとになりません。

    **スキル:** C03 4.1.3 / **参照:** [コマンドの詳細](../../../services/observability.md#insights-commands)

A、B の順に呼び出すマイクロサービスを X-Ray でトレースしています。開発者は、サービス B の `FixedRate` を 0.01 に下げるルールを作りましたが、B のトレース数が減りません。ルールの優先度は最も高くしてあります。最も可能性の高い原因はどれですか。

### 問16 {#q16}

毎秒 100 リクエストを受ける API で、X-Ray のルールを `ReservoirSize=10`、`FixedRate=0.1` にしました。毎秒おおよそ何件のリクエストがトレースされますか。

- A. 10 件
- B. 19 件
- C. 20 件
- D. 110 件

??? success "答えと解説"
    **正解: B**

    リザーバーの 10 件を先に使い、残りの 90 件に 10% を適用します。`10 + 90 × 0.1 = 19` 件です。

    - A: リザーバーの分だけで、超過分の割合を無視しています。
    - B: 正しい計算です。
    - C: 100 件全体に 10% を適用してリザーバーを足した値で、計算が重複しています。
    - D: 全リクエスト数を超えることはありません。

    **スキル:** C03 4.2.4 / **参照:** [サンプリングルールの全項目](../../../services/observability.md#xray-sampling-rule)

### 問18 {#q18}

ECS でアプリと X-Ray デーモンを別のコンテナで動かしています。アプリはバックグラウンドのスレッドからも記録しようとして、セグメントが開いていないために例外で停止することがあります。デーモンのホスト名は `xray-daemon` です。設定すべき環境変数の組み合わせはどれですか。（2つ選択）

- A. `AWS_XRAY_DAEMON_ADDRESS=xray-daemon:2000`
- B. `AWS_XRAY_CONTEXT_MISSING=LOG_ERROR`
- C. `AWS_XRAY_CONTEXT_MISSING=RUNTIME_ERROR`
- D. `_X_AMZN_TRACE_ID=xray-daemon:2000`
- E. `AWS_XRAY_SDK_ENABLED=false`

??? success "答えと解説"
    **正解: A, B**

    デーモンの場所は `AWS_XRAY_DAEMON_ADDRESS` で指定します。既定は `127.0.0.1:2000` です。セグメントがないときに例外にしないためには、`AWS_XRAY_CONTEXT_MISSING=LOG_ERROR` を設定します。

    - A: 正しい設定です。
    - B: 正しい設定です。
    - C: 例外を投げる設定で、問題の原因そのものです。
    - D: 現在のトレースヘッダーを持つ変数で、デーモンの場所ではありません。
    - E: SDK 自体が無効になり、トレースが記録されません。

    **スキル:** C03 4.2.4 / **参照:** [環境変数](../../../services/observability.md#xray-env-vars)

### 問19 {#q19}

長時間かかる処理のセグメントが 64 KB を超え、X-Ray に届かないことがあります。また、処理の途中でもトレースを確認したいと考えています。最も適切な実装はどれですか。

- A. 大きな情報をアノテーションへ移す
- B. `FixedRate` を下げて送信量を減らす
- C. デーモンの `--buffer-memory` を増やす
- D. `in_progress` で先に送り、サブセグメントを別送する

??? success "答えと解説"
    **正解: D**

    セグメント文書の上限は 64 KB です。サブセグメントを別送すれば分割できます。`end_time` の代わりに `in_progress: true` で送ると、処理中でも見えます。

    - A: アノテーションも同じ文書に入るので、サイズは減りません。
    - B: サンプリングを下げても、1 文書のサイズは変わりません。
    - C: デーモンのバッファの大きさは、文書の上限を変えません。
    - D: 正しい実装です。

    **スキル:** C03 4.2.4 / **参照:** [セグメントのフィールド](../../../services/observability.md#xray-segment-fields)

### 問20 {#q20}

監査担当者から「先月、この S3 オブジェクトを削除した人を調べてほしい」と依頼されました。組織には管理イベントのみを記録する証跡があります。CloudTrail の記録について正しい説明はどれですか。（2つ選択）

- A. S3 の `DeleteObject` はデータイベントで、既定では記録されない
- B. `DeleteObject` はイベント履歴で 90 日間確認できる
- C. データイベントを今有効にすると、先月の分も取得できる
- D. 今後のためにデータイベントを有効にする必要がある
- E. 証跡のログは API の呼び出しと同時に必ず届く

??? success "答えと解説"
    **正解: A, D**

    オブジェクトレベルの操作はデータイベントで、証跡でもイベントデータストアでも既定では記録されません。今後のために有効にします。

    - A: 正しい説明です。
    - B: イベント履歴は管理イベントのみです。
    - C: 有効化以前の分は遡れません。
    - D: 正しい説明です。
    - E: 配信は平均で約 5 分かかり、保証もありません。

    **スキル:** C03 4.1.2 / **参照:** [イベントの種類](../../../services/observability.md#cloudtrail-events)

### 問21 {#q21}

Lambda 関数のロググループで、`ERROR` を含むログの件数を 5 分ごとに集計したいと考えています。最も適切な Logs Insights のクエリはどれですか。

- A. `fields @timestamp, @message | sort @timestamp desc | limit 5`
- B. `stats count(*) by bin(5m) | filter @message like /ERROR/`
- C. `parse @message "ERROR" | stats sum(@message) by bin(5m)`
- D. `filter @message like /ERROR/ | stats count(*) by bin(5m)`

??? success "答えと解説"
    **正解: D**

    コマンドはパイプの順に処理します。先に `filter` で絞り込み、次に `stats` と `bin` で時間ごとに数えます。

    - A: 誤り。新しいログを 5 件表示するだけです。
    - B: 誤り。`stats` の後には集計の結果しか残らず、`@message` で絞り込めません。
    - C: 誤り。文字列のフィールドは `sum` で集計できません。
    - D: 正しい。要件のとおりに集計できます。

    **スキル:** C03 4.1.3 / **参照:** [Logs Insights でログを検索する](../../../services/observability.md#logs-insights)

### 問22 {#q22}

Python の Lambda 関数は標準の `logging` でテキストのログを出しています。Logs Insights でレベルやリクエスト ID で絞り込むには、毎回 `parse` を書く必要があります。コードの変更は最小にしたいと考えています。最も適切な対応はどれですか。

- A. メトリクスフィルターを作成し、テキストのログを JSON に変換して保存する
- B. 関数のログの形式（`LogFormat`）を `JSON` にする
- C. `ApplicationLogLevel` を `DEBUG` にして、記録する情報を増やす
- D. ロググループを、取り込みの料金が安いログクラスに変更する

??? success "答えと解説"
    **正解: B**

    `LogFormat` を `JSON` にすると、対応するランタイムの標準のロギングの出力が、`level` や `requestId` などのキーを持つ JSON になります。Python の `logging` なら、コードの変更は不要です。`filter level = "ERROR"` のように絞り込めます。

    - A: 誤り。メトリクスフィルターはログからメトリクスを作る機能で、ログの形式は変えません。
    - B: 正しい。構造化されたログになります。
    - C: 誤り。形式は変わらず、ログの量だけが増えます。また `ApplicationLogLevel` は JSON 形式のときの設定です。
    - D: 誤り。ログの形式は変わりません。また、ロググループのクラスは作成後に変更できません。

    **スキル:** C03 4.2.1 / **参照:** [構造化ログ](../../../services/observability.md#structured-logging)
