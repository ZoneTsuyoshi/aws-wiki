# SDK と耐障害性の問題集

対象の解説: [SDK と耐障害性](../../../services/sdk-resilience.md)

### 問1 {#q1}

ある開発者は boto3 で次の設定を書きました。一時的なエラーが続いた場合、1 回の API 呼び出しで最大何回のリクエストが送られますか。

```python
Config(retries={"mode": "standard", "max_attempts": 3})
```

- A. 2 回
- B. 3 回
- C. 4 回
- D. 5 回

??? success "答えと解説"
    **正解: C**

    boto3 の `Config` の `max_attempts` は再試行の回数で、最初のリクエストを含みません。1 + 3 = 4 回です。環境変数や設定ファイルの `max_attempts` は総数なので、同じ `3` でも 3 回になります。

    - A: 再試行が 1 回の場合の値で、この設定には当てはまりません。
    - B: `total_max_attempts=3` や `AWS_MAX_ATTEMPTS=3` のときの値です。
    - C: 最初の 1 回に再試行 3 回を足した値です。
    - D: `legacy` モードの既定の総数です。

    **スキル:** C03 1.1.3 / **参照:** [SDK の再試行モード](../../../services/sdk-resilience.md#retry-modes)

### 問2 {#q2}

開発者が Lambda の環境変数に `AWS_RETRY_MODE=adaptive` を設定し、`~/.aws/config` 相当の設定に `retry_mode=standard` を、コードに `Config(retries={"mode": "legacy"})` を書きました。実際に使われるモードはどれですか。

- A. `standard`
- B. `adaptive`
- C. `legacy`
- D. 矛盾するのでクライアントの作成時にエラーになる

??? success "答えと解説"
    **正解: C**

    優先順位はコードのクライアント設定、環境変数、共有設定ファイル、SDK の既定の順です。

    - A: 設定ファイルの値で、優先順位は低いです。
    - B: 環境変数の値で、コードの設定に負けます。
    - C: コードの指定が最も優先されます。
    - D: 優先順位で解決され、エラーにはなりません。

    **スキル:** C03 1.1.5 / **参照:** [クライアントの設定と優先順位](../../../services/sdk-resilience.md#client-config)

### 問3 {#q3}

1 つの DynamoDB テーブルに大量に書き込むバッチ処理で、スロットリングが頻発しています。追加のコードを最小にして、SDK が送信速度を自動で調整するようにしたいと考えています。最も適切な設定はどれですか。

- A. 再試行モードを `legacy` にする
- B. 再試行モードを `adaptive` にする
- C. `read_timeout` を 120 秒にする
- D. `max_pool_connections` を 100 にする

??? success "答えと解説"
    **正解: B**

    `adaptive` は `standard` にクライアント側のレート制限を加えたものです。1 つのリソースに集中し、スロットリングが多いバッチ処理に向いています。複数のリソースやテナントを扱うクライアントには向きません。

    - A: 古い動きで、レートの調整はありません。
    - B: スロットリングに応じて送信速度を調整します。
    - C: 応答を長く待つだけで、送信速度は変わりません。
    - D: 接続数が増え、スロットリングが増える恐れがあります。

    **スキル:** C03 1.1.3 / **参照:** [SDK の再試行モード](../../../services/sdk-resilience.md#retry-modes)

### 問4 {#q4}

API Gateway の背後にある Lambda 関数（タイムアウト 10 秒）が、遅い下流サービスを boto3 の既定のタイムアウトのまま呼んでいます。下流が止まると `Task timed out` になり、コードのフォールバック処理が動きません。最も適切な対応はどれですか。

- A. 関数のタイムアウトを 15 分に延ばす
- B. 接続と読み取りを 1〜2 秒にし、再試行の総数も絞る
- C. API Gateway の統合タイムアウトを短くする
- D. SDK の再試行の総数を 10 回に増やす

??? success "答えと解説"
    **正解: B**

    boto3 の既定は接続、読み取りとも 60 秒で、再試行も加わるので関数より長くかかります。内側を外側より短くすれば、例外がコードに届き、残りの時間でフォールバックを実行できます。

    - A: 処理時間が伸びるだけで、API Gateway の統合タイムアウトも先に切れます。
    - B: 呼び出しの最悪時間を関数のタイムアウト内に収められます。
    - C: 関数がタイムアウトする問題は残ります。
    - D: 待ち時間がさらに長くなります。

    **スキル:** C03 1.1.3 / **参照:** [タイムアウト](../../../services/sdk-resilience.md#timeouts)

### 問5 {#q5}

次のエラーのうち、AWS SDK の再試行の対象になるものはどれですか。（2つ選択）

- A. DynamoDB の `ProvisionedThroughputExceededException`（HTTP 400）
- B. `ValidationException`（HTTP 400）
- C. `AccessDeniedException`（HTTP 400）
- D. `ConditionalCheckFailedException`（HTTP 400）
- E. コードのない HTTP 503

??? success "答えと解説"
    **正解: A, E**

    SDK はまずエラーコードを見ます。同じ HTTP 400 でも、スロットリングのコードは再試行します。コードのない 5XX は一時的なエラーとして再試行します。

    - A: HTTP 400 ですが、スロットリングとして再試行します。
    - B: 入力の問題で、何度試しても失敗します。
    - C: 権限の問題で、再試行しても解決しません。
    - D: アプリケーションのロジックで扱うエラーです。
    - E: 一時的なエラーとして再試行します。

    **スキル:** C03 1.1.3 / **参照:** [リトライ](../../../services/sdk-resilience.md#retries)

### 問6 {#q6}

多数のクライアントが同じサービスを呼んでいます。サービスの一時的な障害の後、すべてのクライアントが同じタイミングで再試行し、負荷の波が繰り返されます。指数バックオフはすでに実装済みです。最も適切な追加の対応はどれですか。

- A. 再試行の回数を増やす
- B. 待ち時間を固定にする
- C. 再試行の待ち時間にジッターを加える
- D. クライアントのタイムアウトを長くする

??? success "答えと解説"
    **正解: C**

    バックオフだけだと、同時に失敗したクライアントは同じタイミングで再試行します。ランダムな揺らぎを加えると分散します。

    - A: 負荷がさらに増えます。
    - B: タイミングがそろったままで、負荷も下がりにくくなります。
    - C: 再試行のタイミングが分散します。
    - D: 同時に再試行する問題は変わりません。

    **スキル:** C03 1.1.3 / **参照:** [指数バックオフとジッター](../../../services/sdk-resilience.md#backoff-jitter)

### 問7 {#q7}

Python の Lambda 関数がハンドラーの中で毎回 `boto3.client("dynamodb")` を作っています。呼び出しごとの遅延が大きくなっています。この遅延の原因を解消する方法はどれですか。

- A. クライアントをハンドラーの外で作り、実行環境で使い回す
- B. 関数のメモリーを最大の値に増やす
- C. `read_timeout` を短くする
- D. リソース API の `boto3.resource` に変更する

??? success "答えと解説"
    **正解: A**

    ハンドラーの外で作ると、同じ実行環境の呼び出しでクライアントと接続を再利用できます。

    - A: 認証情報の解決と接続の確立の繰り返しがなくなります。
    - B: 初期化は速くなり得ますが、毎回作り直す原因は残ります。
    - C: 遅延の原因はタイムアウトではありません。
    - D: 中でクライアントを作ることに変わりはなく、ハンドラーの中なら同じ問題が残ります。

    **スキル:** C03 4.3.1 / **参照:** [接続の再利用](../../../services/sdk-resilience.md#connection-reuse)

### 問8 {#q8}

boto3 のアプリケーションが 50 スレッドで同じクライアントを共有しています。ログに `Connection pool is full` という警告が出て、接続を作り直しています。適切な対応はどれですか。

- A. `tcp_keepalive` を無効にする
- B. 再試行モードを `legacy` にする
- C. `max_pool_connections` を増やす
- D. スレッドごとにリージョンを変える

??? success "答えと解説"
    **正解: C**

    `max_pool_connections` の既定は 10 です。50 スレッドなら足りないので、増やします。

    - A: 既定で無効で、プールの大きさとは関係ありません。
    - B: 再試行の設定で、接続プールは変わりません。
    - C: 接続を再利用できる数が増えます。
    - D: 別のエンドポイントに接続するだけで、解決になりません。

    **スキル:** C03 4.3.1 / **参照:** [接続の再利用](../../../services/sdk-resilience.md#connection-reuse)

### 問9 {#q9}

`list_objects_v2` を 1 回だけ呼ぶコードで、バケットのオブジェクトを処理しています。オブジェクトが増えてから、一部が処理されていないことが分かりました。エラーは出ていません。最も適切な修正はどれですか。

- A. `MaxKeys` を 100,000 に指定して 1 回で全件を取る
- B. ページネーターを使い、すべてのページを処理する
- C. `read_timeout` を長くする
- D. ウェイターで全件の取得を待つ

??? success "答えと解説"
    **正解: B**

    一覧の API は結果を分割して返し、エラーにはなりません。ページネーターならトークンの処理を任せて全ページを読めます。

    - A: 1 回の応答の件数には上限があり、全件は取れません。
    - B: 正しい方法です。
    - C: 応答は成功しているので、タイムアウトの問題ではありません。
    - D: ウェイターはリソースの状態を待つ機能です。

    **スキル:** C03 1.1.5 / **参照:** [ページネーション](../../../services/sdk-resilience.md#pagination)

### 問10 {#q10}

`dynamodb.get_waiter("table_exists").wait(TableName="orders")` を既定のまま呼びます。テーブルの準備ができない場合、エラーになるまでの時間はおよそどのくらいですか。

- A. 30 秒
- B. 60 秒
- C. 300 秒
- D. 500 秒

??? success "答えと解説"
    **正解: D**

    `table_exists` の既定は 20 秒間隔で 25 回なので、20 × 25 = 500 秒です。Lambda の中では関数のタイムアウトに注意します。

    - A: 既定の値ではありません。
    - B: boto3 の接続や読み取りのタイムアウトの既定値です。
    - C: 間隔か回数を取り違えた値です。
    - D: 既定の間隔と回数から計算した値です。

    **スキル:** C03 1.1.5 / **参照:** [ウェイター](../../../services/sdk-resilience.md#waiters)

### 問11 {#q11}

注文の支払いを DynamoDB の `TransactWriteItems` で書き込みます。アプリケーションがネットワークエラーの後で再度呼び出しても、二重に実行されないようにします。正しい説明はどれですか。（2つ選択）

- A. 操作ごとにトークンを 1 つ作り、再試行でも同じ `ClientRequestToken` を使う
- B. 再試行のたびに新しい `uuid4()` を `ClientRequestToken` にする
- C. トークンの有効期間はリクエストの完了から 10 分である
- D. 同じトークンで内容を変えて再試行する
- E. トークンをリージョンごとに分けて保存する

??? success "答えと解説"
    **正解: A, C**

    トークンはリクエストの完了から 10 分有効です。同じトークンを使えば、その間の呼び出しは同じ結果になります。10 分を過ぎると新しいリクエストとして扱われます。

    - A: 再試行でも同じ値にすることが冪等の条件です。
    - B: 毎回別のリクエストとして扱われ、冪等になりません。
    - C: 10 分を過ぎた再試行は新しいリクエストとして実行されます。
    - D: `IdempotentParameterMismatch` エラーになります。
    - E: 要件には関係ありません。

    **スキル:** C03 1.1.3 / **参照:** [冪等性](../../../services/sdk-resilience.md#idempotency)

### 問12 {#q12}

Step Functions の Standard ワークフローで、同じ注文の処理を二重に始めないようにしたいと考えています。最も簡単な方法はどれですか。

- A. 実行のロールに条件を付ける
- B. 入力を DynamoDB にも保存する
- C. Express ワークフローに変更する
- D. `name` に注文 ID を使う

??? success "答えと解説"
    **正解: D**

    Standard では同じ名前の実行は一意です。実行中に同じ名前と入力なら成功して同じ応答が返り、閉じた実行や入力の違いでは `ExecutionAlreadyExists` になります。

    - A: 権限の制御で、重複の判定にはなりません。
    - B: 自前の実装が増えます。
    - C: `StartExecution` は Express では冪等になりません。
    - D: 標準の機能で実現できます。

    **スキル:** C03 1.1.3 / **参照:** [冪等性](../../../services/sdk-resilience.md#idempotency)

### 問13 {#q13}

boto3 の `Table.put_item` で次のコードを実行するとエラーになります。原因と修正の組み合わせとして正しいものはどれですか。

```python
price = 19.99
table.put_item(Item={"id": "a", "price": price})
```

- A. float は使えない。`Decimal(str(price))` にする
- B. 数値はそのまま使えない。`{"N": 19.99}` と書く
- C. float は使えない。`Decimal(price)` にする
- D. 属性名が予約語である。`ExpressionAttributeNames` を使う

??? success "答えと解説"
    **正解: A**

    boto3 の変換は float を受け付けません。`Decimal` に変えますが、float から直接作ると誤差を引き継ぐので、文字列を経由します。

    - A: 正しい原因と修正です。
    - B: `Table` の API に型の記述子は書きません。
    - C: `Decimal(19.99)` は誤差を含む長い値になり、失敗します。
    - D: `put_item` の属性名に予約語の制限はありません。

    **スキル:** C03 1.1.7 / **参照:** [Decimal の扱い](../../../services/sdk-resilience.md#decimal)

### 問14 {#q14}

DynamoDB の `PutItem` で HTTP 500 が返りました。SDK の再試行を使い切った後のアプリケーションの処理として、AWS の説明に最も沿っているものはどれですか。

- A. 書き込みは失敗しているので、そのまま同じ内容で再実行する
- B. 書き込みは成功しているので、何もしない
- C. アイテムの状態を読むか、条件式を付けて再試行する
- D. `ClientRequestToken` を付けて `PutItem` を再実行する

??? success "答えと解説"
    **正解: C**

    書き込みの 500 は、成功か失敗か分かりません。単一アイテムの書き込みは、状態を確かめるか、条件式を付けて再試行します。`TransactWriteItems` はそのまま再試行できます。

    - A: 成功していた場合に、二重の処理になり得ます。
    - B: 失敗している可能性があります。
    - C: AWS の説明に沿っています。
    - D: `ClientRequestToken` は `TransactWriteItems` のパラメーターです。

    **スキル:** C03 1.1.3 / **参照:** [コードでのエラー処理](../../../services/sdk-resilience.md#error-handling)

### 問15 {#q15}

EC2 インスタンスにインスタンスプロファイルを付けましたが、boto3 のアプリケーションが別の権限で動いているようです。原因として考えられるものはどれですか。（2つ選択）

- A. 環境変数 `AWS_ACCESS_KEY_ID` に古いキーが設定されている
- B. インスタンスプロファイルは EC2 からは使えない
- C. `~/.aws/credentials` に古いキーが残っている
- D. `max_attempts` の値が小さすぎる
- E. リージョンが `ap-northeast-1` になっている

??? success "答えと解説"
    **正解: A, C**

    認証情報のチェーンで、環境変数と共有認証情報ファイルはインスタンスメタデータより先に見られます。`aws sts get-caller-identity` で実際の ID を確認します。

    - A: チェーンの上位なので優先されます。
    - B: EC2 では、インスタンスプロファイルは IMDS から使います。
    - C: チェーンの上位なので優先されます。
    - D: 再試行の回数で、認証情報は変わりません。
    - E: リージョンと ID は関係ありません。

    **スキル:** C03 2.1.3 / **参照:** [認証情報](../../../services/sdk-resilience.md#credentials)
