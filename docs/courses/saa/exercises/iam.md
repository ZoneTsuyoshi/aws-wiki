# IAM と STS の問題集

対象の解説: [AWS IAM](../../../services/iam.md)、[IAM Identity Center と Directory Service](../../../services/identity-directory.md)

### 問1 {#q1}

EC2 上のアプリが、1 つの S3 バケットのオブジェクトだけを読みます。最小権限で、長期の認証情報を置かない設計はどれですか。

- A. `AmazonS3ReadOnlyAccess` を付けた IAM ユーザーのアクセスキーを環境変数に設定する
- B. 該当バケットの `s3:*` を許可した IAM ユーザーのキーを AMI に埋め込む
- C. バケットポリシーで `Principal` に `*` を指定して全員に読み取りを許可する
- D. 該当バケットの `s3:GetObject` だけを許可したロールをインスタンスプロファイルで渡す

??? success "答えと解説"
    **正解: D**

    ロールなら認証情報は一時的で自動更新されます。`Action` と `Resource` を具体的に書くのが最小権限です。

    - A: 誤り。長期の認証情報で、権限もすべてのバケットに及ぶ。
    - B: 誤り。長期の認証情報を AMI に残し、操作も広すぎる。
    - C: 誤り。公開になり、最小権限に反する。
    - D: 正しい。

    **スキル:** [認可モデル](../domain1.md#t1-1-authz-model) / **参照:** [最小権限](../../../services/iam.md#least-privilege)、[インスタンスプロファイル](../../../services/iam.md#instance-profile)

### 問2 {#q2}

開発チームに IAM ロールの作成を任せますが、作られるロールが持てる権限には上限を設けたいと考えています。何を使いますか。

- A. 信頼ポリシーの `Principal` を開発者のアカウントに限定する
- B. 権限境界の付与を条件にロールの作成を許可する
- C. インラインポリシーを開発者のユーザーに直接付ける
- D. IAM グループのポリシーで開発者の権限をまとめる

??? success "答えと解説"
    **正解: B**

    権限境界は権限の上限を定めるもので、それ自体は権限を与えません。作成時に境界の付与を条件にすれば、開発者が上限を超えるロールを作れません。

    - A: 誤り。誰が引き受けるかを決めるだけで、権限の上限にならない。
    - B: 正しい。
    - C: 誤り。開発者自身の権限で、作るロールの上限にはならない。
    - D: 誤り。グループは権限の配布の手段で、作るロールの上限を決めない。

    **スキル:** [認可モデル](../domain1.md#t1-1-authz-model) / **参照:** [権限境界の設定](../../../services/iam.md#permissions-boundary)

### 問3 {#q3}

IAM ポリシーでバケットへの `s3:GetObject` を Allow し、同じユーザーが属するグループのポリシーでは同じバケットへの `s3:*` を Deny しています。このユーザーが `GetObject` を呼んだ結果はどれですか。

- A. 明示的な Deny が優先されるので拒否される
- B. より具体的なアクションの Allow が優先されるので許可される
- C. ユーザーに直接付けたポリシーが優先されるので許可される
- D. 先に作成されたポリシーが優先されるので、作成順で結果が変わる

??? success "答えと解説"
    **正解: A**

    評価は「明示的な Deny が最優先、次に Allow、どちらもなければ暗黙の拒否」です。

    - A: 正しい。
    - B: 誤り。具体性は関係せず、Deny が優先される。
    - C: 誤り。直接かグループ経由かで優先順位は変わらない。
    - D: 誤り。作成順は評価に関係しない。

    **スキル:** [認可モデル](../domain1.md#t1-1-authz-model) / **参照:** [ポリシー評価](../../../services/iam.md#policy-evaluation)

### 問4 {#q4}

複数の IAM ロールに同じ権限のセットを付け、更新も 1 か所で済ませたいと考えています。最も適切なものはどれですか。

- A. ロールごとにインラインポリシーを作り、同じ内容を貼り付ける
- B. リソースベースポリシーの `Principal` にグループを指定する
- C. カスタマー管理ポリシーを作り、各ロールにアタッチする
- D. IAM グループにポリシーを付け、ロールをそのグループに入れる

??? success "答えと解説"
    **正解: C**

    管理ポリシーは複数のプリンシパルで再利用でき、更新も 1 か所で済みます。

    - A: 誤り。再利用できず、更新はロールの数だけ必要になる。
    - B: 誤り。グループはプリンシパルになれない。
    - C: 正しい。
    - D: 誤り。グループに入れられるのはユーザーだけで、ロールは入れられない。

    **スキル:** [認可モデル](../domain1.md#t1-1-authz-model) / **参照:** [管理ポリシーとインラインポリシー](../../../services/iam.md#managed-vs-inline)

### 問5 {#q5}

正しい記述を選んでください。（2つ選択）

- A. IAM グループは、ポリシーの `Principal` 要素に指定できない
- B. 明示的な Allow は、別のポリシーの明示的な Deny より優先される
- C. 権限境界だけを付けても、それ自体で権限は与えられない
- D. 暗黙の拒否は、明示的な Deny と同様に Allow を上書きする
- E. インラインポリシーは、複数のプリンシパルで共有して再利用できる

??? success "答えと解説"
    **正解: A, C**

    グループはユーザーの集まりで、認証されるプリンシパルではありません。権限境界は上限を決めるだけです。

    - A: 正しい。
    - B: 誤り。明示的な Deny が最優先。
    - C: 正しい。
    - D: 誤り。暗黙の拒否は Allow があれば解消される。
    - E: 誤り。インラインは 1 つのプリンシパルと 1 対 1 で、再利用できない。

    **スキル:** [認可モデル](../domain1.md#t1-1-authz-model) / **参照:** [プリンシパルと権限の定義](../../../services/iam.md#principals)、[権限境界の設定](../../../services/iam.md#permissions-boundary)

### 問6 {#q6}

AWS アカウントのルートユーザーの扱いとして、ベストプラクティスに合うものはどれですか。

- A. ルートユーザーのアクセスキーを作り、自動化スクリプトで定期的に入れ替える
- B. パスワードだけで保護し、担当者全員で共有して不在時に備える
- C. 日常の管理作業はルートユーザーで行い、操作を CloudTrail で監視する
- D. MFA を有効にし、アクセスキーを作らず、日常の作業は別の ID で行う

??? success "答えと解説"
    **正解: D**

    ルートユーザーは制限を受けにくい強い ID なので、MFA で保護し、日常には使いません。

    - A: 誤り。アクセスキーは作らない。
    - B: 誤り。MFA がなく、共有も不適切。
    - C: 誤り。日常の作業には使わない。
    - D: 正しい。

    **スキル:** [ルートユーザーの保護](../domain1.md#t1-1-root-mfa) / **参照:** [プリンシパルと権限の定義](../../../services/iam.md#principals)

### 問7 {#q7}

外部ツールのためにやむを得ず IAM ユーザーのアクセスキーを使っています。キーを無停止で入れ替えるにはどうしますか。

- A. 2 つ目のキーを作ってツールを切り替え、古いキーを無効にしてから削除する
- B. 同じユーザーに 3 つ目のキーを作り、古いキーは残しておく
- C. 既存のキーのシークレットだけを再生成して、ツールの設定を変えずに使う
- D. 既存のキーを無効にしてから新しいキーを作り、ツールに設定する

??? success "答えと解説"
    **正解: A**

    キーは 1 ユーザーにつき 2 つまで持てるので、新旧を重ねて切り替えられます。

    - A: 正しい。
    - B: 誤り。キーは 1 ユーザーにつき最大 2 つまで。
    - C: 誤り。シークレットの再生成の機能はない。
    - D: 誤り。切り替えまでの間、ツールが止まる。

    **スキル:** [ルートユーザーの保護](../domain1.md#t1-1-root-mfa) / **参照:** [アクセスキーとプロファイル](../../../services/iam.md#access-keys-profiles)

### 問8 {#q8}

特定の IAM ロールの削除は、MFA で認証したセッションでだけ許可したいと考えています。IAM ユーザーのポリシーに書く条件キーはどれですか。

- A. `aws:SecureTransport`
- B. `sts:ExternalId`
- C. `aws:MultiFactorAuthPresent`
- D. `aws:PrincipalOrgID`

??? success "答えと解説"
    **正解: C**

    `aws:MultiFactorAuthPresent` で、一時的な認証情報が MFA で認証されたかを判定できます。

    - A: 誤り。TLS の利用を判定するキーで、MFA とは関係ない。
    - B: 誤り。第三者によるロールの引き受けで使うキー。
    - C: 正しい。
    - D: 誤り。組織の所属を判定するキー。

    **スキル:** [ルートユーザーの保護](../domain1.md#t1-1-root-mfa) / **参照:** [GetSessionToken と MFA](../../../services/iam.md#mfa)

### 問9 {#q9}

従業員 200 人が複数の AWS アカウントのコンソールを使います。IAM ユーザーを増やさず、MFA も一元的に求めたいと考えています。最も適切な構成はどれですか。

- A. アカウントごとに IAM ユーザーを作り、各ユーザーに MFA を設定する
- B. Identity Center の権限セットとサインイン時の MFA
- C. 全員で 1 つの IAM ユーザーを共有し、そのユーザーに MFA を設定する
- D. ルートユーザーの MFA を全員に配布して、必要なときだけ使わせる

??? success "答えと解説"
    **正解: B**

    サインイン時に MFA を求められます。Identity Center は人の入口を一元化し、一時的な認証情報を使います。MFA の設定も 1 か所で管理できます。

    - A: 誤り。長期の認証情報が増え、管理も分散する。
    - B: 正しい。
    - C: 誤り。共有は監査ができず、許されない。
    - D: 誤り。ルートユーザーは日常の作業に使わない。

    **スキル:** [ルートユーザーの保護](../domain1.md#t1-1-root-mfa) / **参照:** [MFA](../../../services/identity-directory.md#idc-mfa)、[IAM Identity Center](../../../services/identity-directory.md#identity-center)

### 問10 {#q10}

開発アカウントのエンジニアに、本番アカウントの DynamoDB を読ませます。IAM ユーザーを増やさない設計はどれですか。

- A. 本番と開発を VPC ピアリングでつなぎ、開発のインスタンスプロファイルでそのまま読ませる
- B. 本番に読み取りのロールを作って開発アカウントを信頼し、開発側で `sts:AssumeRole` を許可する
- C. 開発にロールを作り、本番の DynamoDB テーブルのキーポリシーで開発アカウントを許可する
- D. 本番に IAM ユーザーを作り、エンジニアごとのアクセスキーを開発側の Secrets Manager で管理する

??? success "答えと解説"
    **正解: B**

    信頼ポリシーで誰が引き受けるかを、権限ポリシーで何ができるかを定めます。別アカウントなら、呼ぶ側の許可も必要です。

    - A: 誤り。ネットワーク接続では IAM の認可は解決しない。
    - B: 正しい。
    - C: 誤り。DynamoDB の読み取りにキーポリシーは使わない。KMS の仕組み。
    - D: 誤り。IAM ユーザーが増え、長期の認証情報になる。

    **スキル:** [ロール](../domain1.md#t1-1-rbac) / **参照:** [クロスアカウントアクセス](../../../services/iam.md#cross-account)、[信頼ポリシー](../../../services/iam.md#trust-policy)

### 問11 {#q11}

第三者の監視 SaaS に自社アカウントの読み取りを許可します。SaaS 事業者が他の顧客の依頼で誤って自社のロールを使う、混乱した代理問題を防ぐにはどうしますか。

- A. SaaS 事業者のアカウント用に IAM ユーザーを作り、キーを暗号化して渡す
- B. 信頼ポリシーの `Principal` に `*` を指定し、`aws:SourceIp` で制限する
- C. 信頼ポリシーで事業者のアカウントを指定し、`sts:ExternalId` を条件にする
- D. 権限ポリシーのアクションを読み取りだけに絞り、信頼ポリシーは変更しない

??? success "答えと解説"
    **正解: C**

    顧客ごとに一意の外部 ID を条件にすると、他の顧客の依頼で自社のロールを引き受けられません。

    - A: 誤り。長期の認証情報で、混乱した代理問題の対策にならない。
    - B: 誤り。広く開けることになり、IP は対策の本質ではない。
    - C: 正しい。
    - D: 誤り。最小権限ではあるが、混乱した代理問題は残る。

### 問12 {#q12}

`AssumeRole` で得た認証情報の説明として正しいものを選んでください。（2つ選択）

- A. IAM ユーザーとして記録され、そのユーザーのアクセスキーの一覧に表示される
- B. セッションの長さは、ロールの最大セッション時間の範囲で指定できる
- C. アクセスキー、シークレットキー、セッショントークンの組で、期限が切れると使えなくなる

- E. ロールの信頼ポリシーを変更すると、自動で新しいキーが配布される

??? success "答えと解説"
    **正解: B, C**

    STS が返す一時的な認証情報は 3 つの値の組で、期限があります。

    - A: 誤り。ユーザーのキーとしては表示されない。
    - B: 正しい。
    - C: 正しい。
    - D: 誤り。一時的な認証情報には期限がある。
    - E: 誤り。そのような配布はない。

    **スキル:** [ロール](../domain1.md#t1-1-rbac) / **参照:** [ロールの引き受け](../../../services/iam.md#assume-role)、[API の比較](../../../services/iam.md#sts-api-compare)

### 問13 {#q13}

監査チームが 30 のアカウントを読み取ります。アカウントが増えても手間が増えにくい設計を選んでください。（2つ選択）

- A. 各アカウントに監査者の IAM ユーザーを作り、パスワードポリシーを揃える
- B. 各アカウントに読み取り専用のロールを置き、監査アカウントのロールから引き受ける

EC2 と Lambda に AWS の権限を与える方法の組み合わせで、正しいものはどれですか。

### 問15 {#q15}

GitHub Actions のような外部の CI から AWS にデプロイします。長期のアクセスキーを保管しない方法はどれですか。

- A. IAM の OIDC プロバイダーとロールで一時的な認証情報を得る
- B. ルートユーザーの MFA を無効にして、CI からパスワードでサインインする
- C. デプロイ専用の IAM ユーザーのアクセスキーを CI のシークレットに保存する
- D. Identity Center の権限セットを CI のサービスアカウントに割り当てる

??? success "答えと解説"

    `AssumeRoleWithWebIdentity` を使います。OIDC トークンを信頼ポリシーで検証し、一時的な認証情報を受け取ります。アクセスキーの保管が要りません。

    - A: 正しい。
    - B: 誤り。ルートユーザーを使い、MFA も外すので不適切。
    - C: 誤り。長期の認証情報を保管することになる。
    - D: 誤り。Identity Center は人のサインインが主な用途で、この要件の方式ではない。

    **スキル:** [フェデレーション](../domain1.md#t1-1-federation) / **参照:** [フェデレーション](../../../services/iam.md#federation)

### 問18 {#q18}

AWS 上で動く Microsoft SharePoint に、本物の AD の機能が必要です。さらにオンプレミスの AD との信頼関係も結びます。どれを選びますか。

- A. IAM の SAML プロバイダー
- B. Simple AD
- C. AD Connector
- D. AWS Managed Microsoft AD

??? success "答えと解説"
    **正解: D**

    AWS Managed Microsoft AD は AWS 上で本物の AD を動かし、オンプレミスと信頼関係を結べます。

    - A: 誤り。コンソールなどへのフェデレーションで、AD の機能を提供しない。
    - B: 誤り。小規模な基本機能だけで、信頼関係は結べない。
    - C: 誤り。オンプレミスへの中継だけで、AWS 上に AD はできない。
    - D: 正しい。

    **スキル:** [フェデレーション](../domain1.md#t1-1-federation) / **参照:** [Directory Service](../../../services/identity-directory.md#directory-service)

### 問19 {#q19}

1 つのアカウントだけで、既存の SAML 2.0 の IdP からコンソールと API にフェデレーションします。組織全体のシングルサインオンは不要です。必要な部品はどれですか。（2つ選択）

- A. AD Connector
- B. SAML プロバイダーを信頼する IAM ロール
- C. フェデレーションする人数分の IAM ユーザー
- D. IAM の SAML プロバイダー
- E. Cognito ユーザープールのアプリクライアント

??? success "答えと解説"
    **正解: B, D**

    認証は IdP が行い、`AssumeRoleWithSAML` でロールの一時的な認証情報を受け取ります。

    - A: 誤り。既存の AD へ中継する部品で、SAML 連携には不要。
    - B: 正しい。
    - C: 誤り。フェデレーションでは IAM ユーザーは作らない。
    - D: 正しい。
    - E: 誤り。一般の利用者のアプリ向けの部品。

    **スキル:** [フェデレーション](../domain1.md#t1-1-federation) / **参照:** [フェデレーション](../../../services/iam.md#federation)

### 問20 {#q20}

別のアカウント 111122223333 のロールに、自社の S3 バケットのオブジェクトを読ませます。必要な許可を選んでください。（2つ選択）

- A. バケットポリシーで相手のロールを許可する
- B. バケットポリシーだけで許可すれば、相手側の IAM ポリシーは不要
- C. バケットの ACL を公開にして、相手のアカウントからの読み取りを許す
- D. 相手のロールの IAM ポリシーで読み取りを許可する
- E. 相手のロールの IAM ポリシーだけで許可すれば、バケットポリシーは不要

??? success "答えと解説"
    **正解: A, D**

    別アカウントでは原則として両方の許可が必要です。同じアカウントなら、どちらか一方の許可で足ります。

    - A: 正しい。
    - B: 誤り。相手側でも許可が必要。
    - C: 誤り。公開になり不適切。
    - D: 正しい。
    - E: 誤り。別アカウントではリソース側の許可もいる。

    **スキル:** [リソースポリシー](../domain1.md#t1-1-resource-policy) / **参照:** [アイデンティティベースとリソースベース](../../../services/iam.md#identity-vs-resource)、[バケットポリシーとアクセス制御](../../../services/s3.md#bucket-policies)

### 問21 {#q21}

S3 のイベントで Lambda 関数を呼びます。S3 に呼び出しを許可するのはどれですか。

- A. S3 のバケットポリシーで関数の ARN を `Principal` に指定する
- B. Lambda の実行ロールに `lambda:InvokeFunction` を付ける
- C. 関数のリソースベースポリシーで `s3.amazonaws.com` を許可する
- D. S3 のライフサイクルルールで呼び出し先の関数を指定する

??? success "答えと解説"
    **正解: C**

    サービスから Lambda を呼ぶときは、関数側のリソースベースポリシーで許可します。`aws:SourceArn` で対象のバケットも絞れます。

    - A: 誤り。バケットへのアクセスの制御で、関数の呼び出しの許可ではない。
    - B: 誤り。実行ロールは関数が使う権限で、呼び出し元の許可ではない。
    - C: 正しい。
    - D: 誤り。ライフサイクルはオブジェクトの移行と失効の設定。

    **スキル:** [リソースポリシー](../domain1.md#t1-1-resource-policy) / **参照:** [リソースベースポリシー](../../../services/lambda.md#resource-policy)

### 問22 {#q22}

REST API を特定の VPC エンドポイントからだけ呼べるようにしたいと考えています。アプリのコードは変えません。何を使いますか。

- A. Lambda オーソライザーで呼び出し元の IP を判定する
- B. 使用量プランと API キーを VPC ごとに発行する
- C. プライベート API のリソースポリシーの条件
- D. WAF のレートベースルールで呼び出し元を絞る

??? success "答えと解説"
    **正解: C**

    プライベート API にはリソースポリシーが必須で、`aws:SourceVpce` などを条件に許可できます。

    - A: 誤り。独自のコードが要り、最小の方法ではない。
    - B: 誤り。キーは識別のためのもので、経路の制限にならない。
    - C: 正しい。
    - D: 誤り。レートの制限で、エンドポイントの制限ではない。

    **スキル:** [リソースポリシー](../domain1.md#t1-1-resource-policy) / **参照:** [リソースポリシー](../../../services/api-gateway.md#resource-policy)

### 問23 {#q23}

別アカウントのアプリに Secrets Manager のシークレットを読ませます。正しい組み合わせを選んでください。（3つ選択）

- A. カスタマー管理キーのキーポリシーで相手を許可する
- B. シークレットのリソースポリシーと `aws/secretsmanager` の AWS 管理キー
- C. 相手の IAM ポリシーでシークレットとキーを許可する
- D. シークレットの値を S3 にコピーして、バケットポリシーで相手を許可する
- E. シークレットのリソースポリシーで相手を許可する
- F. 相手の IAM ポリシーだけで許可し、シークレットは既定のまま使う

??? success "答えと解説"
    **正解: A, C, E**

    別アカウントでは、シークレット、KMS キー、相手の IAM の 3 か所で許可します。AWS 管理キーは共有できません。

    - A: 正しい。
    - B: 誤り。AWS 管理キーのキーポリシーは変更できず、別アカウントに許可できない。
    - C: 正しい。
    - D: 誤り。機密情報の複製で、ローテーションも追従しない。
    - E: 正しい。
    - F: 誤り。リソース側の許可と、キーの許可がない。

    **スキル:** [リソースポリシー](../domain1.md#t1-1-resource-policy) / **参照:** [リソースポリシー](../../../services/secrets.md#secret-resource-policy)
