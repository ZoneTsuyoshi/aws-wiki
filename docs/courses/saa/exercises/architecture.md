### 問1 {#q1}

ログインのたびに同じ EC2 に戻らないとセッションが切れるアプリで、スケールインで利用者が切断されます。アプリを改修できます。どの設計が適切ですか。

- A. Auto Scaling のスケールインを無効にして台数を固定にする
- B. セッションをインスタンスストアに保存して読み出しを速くする
- C. セッションを ElastiCache か DynamoDB に出す
- D. インスタンスを大きくして台数を減らし、切断の回数を減らす

??? success "答えと解説"
    **正解: C**

    スケールする層をステートレスにすれば、どのインスタンスでも処理できます。

    - A: 誤り。スケールの利点を失う。
    - B: 誤り。サーバーの中に状態が残る。
    - C: 正しい。
    - D: 誤り。スケールの問題が残る。

    **スキル:** [多層とマイクロサービス](../domain2.md#t2-1-architectures) / **参照:** [ステートフルとステートレス](../../../services/sdk-resilience.md#stateful-stateless)

### 問2 {#q2}

機能ごとに別のチームが独立してデプロイし、負荷の高い機能だけをスケールします。どのパターンが合いますか。

- A. 全機能を含む 1 つのイメージを、大きな EC2 に載せる構成
- B. すべての機能を 1 つの Lambda 関数にまとめる構成
- C. EC2 の 1 台の中に機能ごとのプロセスを増やす構成
- D. マイクロサービス（API Gateway と Lambda、または ECS）

??? success "答えと解説"
    **正解: D**

    機能ごとに独立してデプロイし、スケールできます。

    - A: 誤り。デプロイとスケールを分けられない。
    - B: 誤り。機能ごとに分離されない。
    - C: 誤り。独立性もスケールの分離もない。
    - D: 正しい。

    **スキル:** [多層とマイクロサービス](../domain2.md#t2-1-architectures) / **参照:** [アーキテクチャパターン](../../../services/sdk-resilience.md#architectural-patterns)

### 問3 {#q3}

表示、処理、データを分けて守り、インターネットからは入口だけを見せます。AWS での基本の形はどれですか。

- A. ALB、Auto Scaling の EC2、RDS を別のサブネットの層に置く
- B. CloudFront のオリジンにパブリックな RDS を直接指定する
- C. S3 の静的ウェブサイトから SQL を直接実行する
- D. パブリックサブネットの 1 台の EC2 にアプリと DB を載せる

??? success "答えと解説"
    **正解: A**

    多層にすると、各層を SG で区切り、別々にスケールできます。

    - A: 正しい。
    - B: 誤り。DB を公開することになり、配信の用途でもない。
    - C: 誤り。静的ホスティングから DB へ直接接続はしない。
    - D: 誤り。層が分かれず、単一障害点にもなる。

    **スキル:** [多層とマイクロサービス](../domain2.md#t2-1-architectures) / **参照:** [アーキテクチャパターン](../../../services/sdk-resilience.md#architectural-patterns)

### 問4 {#q4}

画像が S3 に置かれたら、サムネイルの作成と検索の登録を自動で行います。発生元は処理の追加を意識したくありません。どのパターンですか。

- A. 1 台の EC2 で S3 を監視するプログラムを常時動かす
- B. S3 のイベントを EventBridge や SNS に送り、複数の処理が受け取るイベント駆動
- C. 毎分のバッチで全オブジェクトを一覧して差分を処理する
- D. 画像を置くアプリがサムネイルの API と検索の API を順に同期で呼ぶ

??? success "答えと解説"
    **正解: B**

    発生元と処理側を切り離すので、処理を増やしても発生元は変わりません。

    - A: 誤り。単一障害点で、管理も必要。
    - B: 正しい。
    - C: 誤り。遅く、無駄が多い。
    - D: 誤り。発生元が処理を知っており、密結合。

    **スキル:** [多層とマイクロサービス](../domain2.md#t2-1-architectures) / **参照:** [アーキテクチャパターン](../../../services/sdk-resilience.md#architectural-patterns)、[EventBridge](../../../services/messaging.md#eventbridge)

### 問5 {#q5}

部品ごとのスケーリングの方法の組み合わせとして、正しいものはどれですか。

- A. RDS の読み取りはリードレプリカ、EC2 は Auto Scaling
- B. RDS の書き込みはリードレプリカを増やしてスケールする
- C. Lambda は Auto Scaling グループの最大数を増やしてスケールする
- D. DynamoDB はインスタンスのサイズを上げてスケールする

??? success "答えと解説"
    **正解: A**

    部品ごとに方法が違います。書き込みはインスタンスのサイズを上げるか Aurora へ移す選択です。

    - A: 正しい。
    - B: 誤り。レプリカは読み取りの分散で、書き込みは増えない。
    - C: 誤り。Lambda は自動で、上限は同時実行数。
    - D: 誤り。インスタンスの概念はなく、容量のモードで調整する。

    **スキル:** [水平と垂直のスケーリング](../domain2.md#t2-1-scaling) / **参照:** [EC2 Auto Scaling](../../../services/ec2-beanstalk.md#auto-scaling)、[同時実行とスケーリング](../../../services/lambda.md#concurrency)

### 問6 {#q6}

水平スケーリングの説明として正しいものはどれですか。

- A. サイズを大きくするので、上限があり、変更時に停止することがある
- B. 台数を増やす方法で、ステートレスにしておく必要がある
- C. 1 台で動くアプリならコード変更なしで必ず動く
- D. 常にデータベースの書き込みの性能を線形に上げられる

??? success "答えと解説"
    **正解: B**

    水平は台数、垂直はサイズです。

    - A: 誤り。それは垂直スケーリング。
    - B: 正しい。
    - C: 誤り。セッションを持つアプリでは問題になる。
    - D: 誤り。DB の書き込みには単純に使えない。

    **スキル:** [水平と垂直のスケーリング](../domain2.md#t2-1-scaling) / **参照:** [EC2 Auto Scaling](../../../services/ec2-beanstalk.md#auto-scaling)

### 問7 {#q7}

既存の EC2 上の 1 台の DB の負荷が書き込みで上がっており、今夜すぐに対応します。短い停止は許されます。最も直接の対応はどれですか。

??? success "答えと解説"
    **正解: C**

    水平に分けられない部品は垂直に上げます。長期にはシャーディングや Aurora を検討します。

    - A: 誤り。書き込みはキャッシュしない。
    - B: 誤り。書き込み先は 1 台のまま。
    - C: 正しい。
    - D: 誤り。レプリカは書き込みを受けない。

    **スキル:** [水平と垂直のスケーリング](../domain2.md#t2-1-scaling) / **参照:** [最小のメモリとコンピューティングを決める](../../../services/ec2-beanstalk.md#sizing)

`/api/*` と `/images/*` を別のサービスに振り分け、1 つの入口で受けます。どれが適切ですか。

### 問9 {#q9}

ロードバランサーを間に置くと疎結合になる理由として、最も適切なものはどれですか。

    - C: 誤り。キューの役割。
    - D: 正しい。

### 問21 {#q21}

決済 API の呼び出しが、ネットワークのタイムアウトで再試行されます。二重に課金しないためには何が必要ですか。

- A. SQS の可視性タイムアウトを 0 秒にして再試行を早くする
- B. 応答がないときは再試行をやめて、失敗として扱う
- C. API Gateway のキャッシュですべての POST をキャッシュする
- D. 冪等性キーで同じリクエストの再処理を防ぐ

??? success "答えと解説"
    **正解: D**

    冪等にすると、再試行しても結果が変わりません。

    - A: 誤り。重複を増やす方向で、課金の問題を解決しない。
    - B: 誤り。処理が終わったか不明で、再試行の問題を避けただけ。
    - C: 誤り。POST のキャッシュは対策にならない。
    - D: 正しい。

    **スキル:** [分散設計のパターン](../domain2.md#t2-2-distributed) / **参照:** [冪等性](../../../services/sdk-resilience.md#idempotency)

### 問22 {#q22}

推薦機能の依存先が止まり、商品ページの全体が遅くなりました。推薦が止まっても商品ページを返します。正しい組み合わせはどれですか。（2つ選択）

- A. 推薦の API の呼び出しのタイムアウトをなくして待ち続ける
- B. 推薦の部分を省いて返す機能の縮退を入れる
- C. サーキットブレーカーで止まった依存先の呼び出しをやめる
- D. 推薦のサービスをページのサーバーと同じプロセスで動かす
- E. 再試行の回数を増やして、依存先の回復を待ち続ける

??? success "答えと解説"
    **正解: B, C**

    依存先の障害を局所化し、主な機能を残します。

    - A: 誤り。スレッドが詰まり、ページ全体が遅くなる。
    - B: 正しい。
    - C: 正しい。
    - D: 誤り。分離を失い、影響が広がる。
    - E: 誤り。負荷が増え、遅さも続く。

    **スキル:** [分散設計のパターン](../domain2.md#t2-2-distributed) / **参照:** [サーキットブレーカー](../../../services/sdk-resilience.md#circuit-breaker)、[グレースフルデグラデーション](../../../services/sdk-resilience.md#graceful-degradation)
