# 暗号化と鍵の問題集

対象の解説: [AWS KMS](../../../services/kms.md)、[証明書と WAF](../../../services/certificates.md)

### 問1 {#q1}

S3 の暗号化で、鍵の利用を CloudTrail で監査し、部門ごとに使える人を分けたいと考えています。どれを選びますか。

- A. SSE-S3 の既定の暗号化
- B. SSE-C で顧客の用意した鍵をリクエストごとに渡す
- C. SSE-KMS とカスタマー管理キー
- D. 暗号化をやめ、バケットポリシーだけで部門を分ける

??? success "答えと解説"
    **正解: C**

    カスタマー管理キーならキーポリシーを自分で書けて、利用も記録されます。

    - A: 誤り。鍵の権限を分けられない。
    - B: 誤り。鍵の保管と配布を自分で行い、KMS の監査の仕組みに乗らない。
    - C: 正しい。
    - D: 誤り。暗号化の要件を満たさない。

    **スキル:** [保存時の暗号化](../domain1.md#t1-3-at-rest) / **参照:** [暗号化](../../../services/s3.md#encryption)、[KMS キーの種類](../../../services/kms.md#key-types)

### 問2 {#q2}

東京リージョンの SSE-KMS のバケットに大量の PUT があり、KMS の費用とスロットリングが問題です。暗号化の方式は変えません。どうしますか。

- A. パートのサイズを 5 MB に揃える
- B. 新しいオブジェクトから SSE-S3 に切り替えて KMS の呼び出しをなくす
- C. KMS キーを増やして、書き込みのたびにランダムに切り替える
- D. SSE-KMS のまま S3 バケットキーを有効にする

??? success "答えと解説"
    **正解: D**

    バケットキーで、KMS の呼び出しとコストを大きく減らせます。既存のオブジェクトは対象外です。

    - A: 誤り。KMS の呼び出しの削減策にならない。
    - B: 誤り。方式を変えないという条件に反する。
    - C: 誤り。複雑で、呼び出しの回数は減らない。
    - D: 正しい。

    **スキル:** [保存時の暗号化](../domain1.md#t1-3-at-rest) / **参照:** [S3 Bucket Key の動作](../../../services/s3.md#bucket-key)

### 問3 {#q3}

暗号化されていない RDS インスタンスを暗号化します。手順として正しいものはどれですか。

- A. スナップショットを取り、暗号化してコピーし、そこから復元する
- B. インスタンスの変更で暗号化を有効にし、次のメンテナンス時間に適用する
- C. リードレプリカを作るときに暗号化を指定して、昇格させる
- D. ストレージのタイプを `io2` に変更すると、自動で暗号化が有効になる

??? success "答えと解説"
    **正解: A**

    復元した新しいインスタンスにアプリの接続先を切り替えます。ブルー/グリーンデプロイで暗号化する方法もあります。

    - A: 正しい。
    - B: 誤り。既存のインスタンスはそのまま暗号化できない。
    - C: 誤り。未暗号化のインスタンスから暗号化されたレプリカは作れない。
    - D: 誤り。タイプと暗号化は関係ない。

    **スキル:** [保存時の暗号化](../domain1.md#t1-3-at-rest) / **参照:** [RDS](../../../services/databases.md#rds)

### 問4 {#q4}

暗号化スナップショットを別のアカウントに共有します。どの種類のキーで暗号化する必要がありますか。

- A. AWS 管理キー（`aws/rds`）をキーポリシーの変更で共有したもの
- B. カスタマー管理キー（自分で作成した KMS キー）
- C. AWS 所有キー
- D. 平文のスナップショットを相手のキーで暗号化したあとに戻したもの

??? success "答えと解説"
    **正解: B**

    カスタマー管理キーならキーポリシーで相手のアカウントを許可できます。

    - A: 誤り。AWS 管理キーのポリシーは変更できず、共有できない。
    - B: 正しい。
    - C: 誤り。利用者には見えないキーで、共有の設定はできない。
    - D: 誤り。手順として成り立たない。

    **スキル:** [保存時の暗号化](../domain1.md#t1-3-at-rest) / **参照:** [KMS キーの種類](../../../services/kms.md#key-types)

### 問5 {#q5}

新しいアカウントで作る EBS ボリュームとスナップショットを、すべて暗号化された状態にします。最も確実で手間の少ない方法はどれですか。

- A. リージョンごとに EBS の既定の暗号化を有効にする
- B. 作成者に手順書を配り、作成時のチェックを毎回確認させる
- C. 既存のボリュームをそのまま修正して暗号化する設定をスクリプトで回す
- D. EBS の利用をやめる

??? success "答えと解説"
    **正解: A**

    既定の暗号化はリージョンごとの設定で、以後の新しいボリュームに適用されます。

    - A: 正しい。
    - B: 誤り。人に依存し、確実ではない。
    - C: 誤り。既存を直接暗号化はできず、新規の強制にもならない。
    - D: 誤り。永続化の要件を失う。

    **スキル:** [保存時の暗号化](../domain1.md#t1-3-at-rest) / **参照:** [EBS の暗号化](../../../services/storage.md#ebs-encryption)

### 問6 {#q6}

CloudFront のディストリビューションで独自ドメインの HTTPS を使います。ACM の証明書をどのリージョンで発行しますか。

- A. オリジンの ALB と同じリージョンで発行してそのまま関連付ける
- B. 東京で発行し、各エッジへ配布する
- C. 利用者の多いリージョンごとに発行して、複数を関連付ける
- D. `us-east-1` のリージョン

??? success "答えと解説"
    **正解: D**

    CloudFront とエッジ最適化の API Gateway は `us-east-1` の証明書を使います。

    - A: 誤り。CloudFront には `us-east-1` の証明書が必要。
    - B: 誤り。ACM の証明書はリージョン間でコピーできない。
    - C: 誤り。関連付けるのは `us-east-1` の 1 つ。
    - D: 正しい。

    **スキル:** [転送時の暗号化](../domain1.md#t1-3-in-transit) / **参照:** [リージョンのルール](../../../services/certificates.md#region-rules)

### 問7 {#q7}

S3 バケットへの HTTP のアクセスを拒否します。どう設定しますか。

- A. S3 ブロックパブリックアクセスをすべて有効にする
- B. バケットの既定の暗号化を SSE-KMS に変更する
- C. `aws:SecureTransport` が `false` のリクエストを Deny するバケットポリシー
- D. ACM の証明書を S3 バケットに関連付ける

??? success "答えと解説"
    **正解: C**

    バケットポリシーの条件で TLS を強制します。

    - A: 誤り。公開の防止で、HTTP の拒否ではない。
    - B: 誤り。保存時の暗号化で、転送時ではない。
    - C: 正しい。
    - D: 誤り。バケットに証明書は関連付けられない。

    **スキル:** [転送時の暗号化](../domain1.md#t1-3-in-transit) / **参照:** [転送時の TLS](../../../services/certificates.md#tls-in-transit)

### 問8 {#q8}

東京の ALB で HTTPS を終端します。ACM の公開証明書の扱いとして正しいものはどれですか。

- A. `us-east-1` で発行して東京の ALB に付ける。ALB は全リージョンで共通である
- B. 東京で発行して ALB に付ける。統合サービスで使う分の追加料金はない
- C. 発行した秘密鍵を各 EC2 に手で配置してから ALB に登録する
- D. 発行後に毎年手作業で入れ替えて、ALB を再作成する

??? success "答えと解説"
    **正解: B**

    ALB や NLB の証明書は同じリージョンに置きます。

    - A: 誤り。ALB と同じリージョンに置く。
    - B: 正しい。
    - C: 誤り。ALB で終端するなら鍵の配置は要らない。
    - D: 誤り。DNS 検証なら自動で更新され、再作成も要らない。

    **スキル:** [転送時の暗号化](../domain1.md#t1-3-in-transit) / **参照:** [統合サービス](../../../services/certificates.md#integrated-services)、[リージョンのルール](../../../services/certificates.md#region-rules)

### 問9 {#q9}

ALB の背後の EC2 まで通信を暗号化したいと考えています。EC2 のサーバーにも証明書が要ります。ACM を使うなら、どの方法が適切ですか。

- A. エクスポート可能な公開証明書を発行してサーバーに置く
- B. S3 の SSE-KMS を有効にしてサーバーの鍵を保護する
- C. CloudFront 用の証明書の秘密鍵をコンソールからコピーする
- D. NACL で 443 番以外を拒否する

??? success "答えと解説"
    **正解: A**

    EC2 に直接置くなら、エクスポート可能な公開証明書か ACME を使います。

    - A: 正しい。
    - B: 誤り。保存時の話で、サーバーの TLS とは関係ない。
    - C: 誤り。統合サービス用の証明書の秘密鍵は取り出せない。
    - D: 誤り。ポートの制限は暗号化ではない。

    **スキル:** [転送時の暗号化](../domain1.md#t1-3-in-transit) / **参照:** [転送時の TLS](../../../services/certificates.md#tls-in-transit)

### 問10 {#q10}

IAM ポリシーで `kms:Decrypt` を許可したのに、`AccessDeniedException` になります。キーポリシーはカスタムです。原因として最も可能性が高いのはどれですか。

- A. キーが対称キーで、`Decrypt` に対応していないため
- B. キーのローテーションの期限が切れたため
- C. キーポリシーでアカウントへの委任か、その主体の許可がないため
- D. IAM ポリシーに `kms:ViaService` の条件がないため

??? success "答えと解説"
    **正解: C**

    KMS ではキーポリシーが必須です。既定のキーポリシーにはアカウントへの委任がありますが、カスタムでは消えていることがあります。

    - A: 誤り。対称キーは `Decrypt` に対応する。
    - B: 誤り。ローテーションに期限切れの動作はない。
    - C: 正しい。
    - D: 誤り。必須の条件ではない。

    **スキル:** [キーポリシー](../domain1.md#t1-3-key-policies) / **参照:** [キーポリシー、IAM、グラント](../../../services/kms.md#access-control)、[既定のキーポリシー](../../../services/kms.md#default-key-policy-details)

### 問11 {#q11}

鍵の管理者は暗号化されたデータを読めないようにし、アプリのロールは暗号操作だけできるようにします。どう設定しますか。

- A. 管理者とアプリに同じ管理ポリシーを付けて、CloudTrail で監視する
- B. キーポリシーで管理操作と暗号操作の主体を分ける
- C. 同じアカウントでは分離ができないので、アカウントを分ける
- D. アプリのロールに削除の権限を与える

??? success "答えと解説"
    **正解: B**

    職務の分離は、キーポリシーの文を主体ごとに分けて実現します。

    - A: 誤り。権限を分けられない。
    - B: 正しい。
    - C: 誤り。同じアカウントでも分けられる。
    - D: 誤り。アプリに管理操作を与えるのは逆。

    **スキル:** [キーポリシー](../domain1.md#t1-3-key-policies) / **参照:** [既定のキーポリシー](../../../services/kms.md#default-key-policy-details)

### 問12 {#q12}

カスタマー管理キーを、S3 の暗号化のときだけ使わせ、アプリからの直接の `Decrypt` は拒否します。どの条件キーを使いますか。

- A. `aws:MultiFactorAuthPresent` で MFA を要求する
- B. `aws:SourceVpce` で VPC エンドポイントを指定する
- C. `kms:GrantIsForAWSResource` だけを文に追加する
- D. `kms:ViaService`

??? success "答えと解説"
    **正解: D**

    `kms:ViaService` は、特定のサービス経由のリクエストに限定します。値にリージョンを含めます。

    - A: 誤り。MFA の判定で、サービス経由の制限にならない。
    - B: 誤り。経路の条件で、サービスの条件ではない。
    - C: 誤り。グラントの作成の条件。
    - D: 正しい。

    **スキル:** [キーポリシー](../domain1.md#t1-3-key-policies) / **参照:** [kms:ViaService](../../../services/kms.md#via-service)

### 問13 {#q13}

別のアカウントのアプリに KMS キーで復号させます。設定として正しいものはどれですか。（2つ選択）

- A. 相手のアカウントでエイリアスのみを指定してキーを呼び出す
- B. キーポリシーで相手のアカウントかロールを許可する
- C. キーを相手のリージョンにコピーして、同じ ID で呼び出す
- D. 相手の IAM ポリシーでキーの ARN に `kms:Decrypt` を許可する
- E. AWS 管理キーのポリシーを編集して相手を追加する

??? success "答えと解説"
    **正解: B, D**

    アカウントをまたぐときは、キーと IAM の両方で許可します。

    - A: 誤り。別アカウントのキーは、キー ARN か別名 ARN で指定する。
    - B: 正しい。
    - C: 誤り。キーはコピーできない。
    - D: 正しい。
    - E: 誤り。AWS 管理キーのポリシーは変更できない。

    **スキル:** [キーポリシー](../domain1.md#t1-3-key-policies) / **参照:** [アカウントをまたぐ暗号化](../../../services/kms.md#cross-account)

### 問14 {#q14}

カスタマー管理キーの自動ローテーションを有効にしました。正しい説明はどれですか。

- A. 有効にできる周期は 30 日から 60 日までに限られている
- B. キーの ID と ARN は変わらず、古い鍵素材も保持されて既存の暗号文を復号できる
- C. キーの ARN が変わるので、アプリの設定を更新する必要がある
- D. 古い暗号文は新しい鍵素材で一括して再暗号化される

??? success "答えと解説"
    **正解: B**

    コードの変更は要りません。

    - A: 誤り。90〜2,560 日で、既定は 365 日。
    - B: 正しい。
    - C: 誤り。ID も ARN も変わらない。
    - D: 誤り。再暗号化はされない。

    **スキル:** [ローテーション](../domain1.md#t1-3-rotation) / **参照:** [キーのローテーション](../../../services/kms.md#key-rotation)、[ローテーションの設定](../../../services/kms.md#rotation-settings)

### 問15 {#q15}

外部の HSM で作った鍵素材を KMS にインポートしたキーがあります。定期的に入れ替えるにはどうしますか。

- A. AWS 管理キーに切り替えて、年次の入れ替えに任せる
- B. 自動ローテーションを有効にする
- C. 新しい鍵素材をインポートしてオンデマンドでローテーションする
- D. `GenerateRandom` で得た値を既存のキーの鍵素材として上書きする

??? success "答えと解説"
    **正解: C**

    インポートした鍵素材のキーは自動ローテーションに対応しませんが、対称キーならオンデマンドローテーションに対応します。新しい鍵素材を先にインポートしてから `RotateKeyOnDemand` を実行します。キーの ID と ARN は変わりません。新しいキーを作ってエイリアスを切り替える手動の方法もあります。

    - A: 誤り。自社の鍵素材を使う要件を失う。
    - B: 誤り。自動ローテーションは KMS が生成した鍵素材のキーだけ。
    - C: 正しい。
    - D: 誤り。素材の上書きの機能はない。

    **スキル:** [ローテーション](../domain1.md#t1-3-rotation) / **参照:** [鍵素材のインポート](../../../services/kms.md#imported-key-material)

ACM にインポートした外部の CA の証明書を ALB で使っています。正しいものはどれですか。

ACM の公開証明書の更新を、人の作業なしで続けたいと考えています。発行時に選ぶ方法はどれですか。
