# メッセージングと API の問題集

対象の解説: [メッセージング](../../../services/messaging.md)、[Step Functions](../../../services/step-functions.md)、[API Gateway](../../../services/api-gateway.md)

### 問1 {#q1}

セールの時に注文が急増し、注文処理のサーバーが追いつかずに注文を失っています。注文を失わず、後段のペースで処理します。何を間に置きますか。

- A. SQS キューとワーカーのポーリング
- B. SNS トピックに直接ワーカーの HTTP エンドポイントを購読させる構成
- C. ALB を追加して既存のサーバーの前でリクエストを分散する構成
- D. ElastiCache クラスター

??? success "答えと解説"
    **正解: A**

    キューが急増を吸収し、ワーカーは自分のペースで取り出します。保持は最大 14 日です。

    - A: 正しい。
    - B: 誤り。プッシュなので、後段の処理のペースに合わせられない。
    - C: 誤り。急増を溜めることはできない。
    - D: 誤り。キューの代わりにならず、確実な保持の仕組みでもない。

    **スキル:** [メッセージング](../domain2.md#t2-1-messaging) / **参照:** [密結合と疎結合](../../../services/messaging.md#coupling)

### 問2 {#q2}

1 つの注文イベントを、在庫、請求、通知の 3 つの処理に並列に渡します。各処理は別々に失敗しても再試行できるようにします。どの構成が適切ですか。

- A. 1 つの SQS 標準キューを 3 つの処理で共有して読み取る
- B. Kinesis のシャードを処理ごとに 1 つずつ割り当てる構成
- C. 注文のサービスから 3 つの API を順に同期で呼び出す構成
- D. SNS トピックを 3 つの SQS キューに購読させるファンアウト

??? success "答えと解説"
    **正解: D**

    SNS で 1 対多に配信し、各 SQS がそれぞれの処理の待ち行列になります。

    - A: 誤り。1 つのメッセージは 1 つのコンシューマーが処理するので、全員に届かない。
    - B: 誤り。シャードは処理ごとに分けるものではない。
    - C: 誤り。同期で密結合になり、失敗の影響が広がる。
    - D: 正しい。

    **スキル:** [メッセージング](../domain2.md#t2-1-messaging) / **参照:** [ファンアウト](../../../services/messaging.md#fanout)

### 問3 {#q3}

銀行の取引の更新を、口座ごとに順番どおりに、重複なく処理します。どの設定が適切ですか。（2つ選択）

- A. 標準キューで、アプリが順序を保証するように遅延を入れる
- B. FIFO キューを使う
- C. 口座 ID をメッセージグループ ID にする
- D. 標準キューの可視性タイムアウトを最大の 12 時間にする
- E. SNS 標準トピックの配信ポリシーで再試行を無効にする

??? success "答えと解説"
    **正解: B, C**

    FIFO キューはメッセージグループごとに順序を保ち、重複を排除します。

    - A: 誤り。標準キューは順序を保証しない。
    - B: 正しい。
    - C: 正しい。
    - D: 誤り。順序と重複の問題は解決しない。
    - E: 誤り。順序の保証にならない。

    **スキル:** [メッセージング](../domain2.md#t2-1-messaging) / **参照:** [標準と FIFO](../../../services/messaging.md#standard-fifo)

### 問4 {#q4}

SQS のワーカーの処理に平均 2 分かかります。可視性タイムアウトは既定の 30 秒のままです。起きる症状と対策はどれですか。

- A. 2 分以上のメッセージがデッドレターキューに直接入るので、DLQ を外す
- B. 別のワーカーが同じメッセージを受け取るので、タイムアウトを処理時間より長くする
- C. メッセージが 30 秒で完全に削除されるので、保持期間を延ばす
- D. キューが自動で FIFO に変わるので、標準キューを作り直す

??? success "答えと解説"
    **正解: B**

    可視性タイムアウトの間は他のワーカーに見えません。処理より短いと重複して処理されます。

    - A: 誤り。時間で DLQ には入らない。
    - B: 正しい。
    - C: 誤り。保持期間は別の設定で、既定は 4 日。
    - D: 誤り。種類は変わらない。

    **スキル:** [メッセージング](../domain2.md#t2-1-messaging) / **参照:** [可視性タイムアウト](../../../services/messaging.md#visibility-timeout)

### 問5 {#q5}

形式の不正なメッセージがキューに残り、ワーカーが何度も失敗して他の処理を妨げます。どう対応しますか。

- A. 保持期間を 14 日に延ばし、自然に消えるのを待つ
- B. ポーリングの間隔を伸ばす
- C. デッドレターキューを設定して隔離する
- D. 可視性タイムアウトを 0 にしてすぐに再試行させる

??? success "答えと解説"
    **正解: C**

    `maxReceiveCount` で指定した回数を超えて受信されたメッセージを別のキューに隔離し、調査できます。

    - A: 誤り。長く残るだけで、問題が解決しない。
    - B: 誤り。根本の解決にならない。
    - C: 正しい。
    - D: 誤り。失敗の繰り返しが速くなる。

    **スキル:** [メッセージング](../domain2.md#t2-1-messaging) / **参照:** [デッドレターキュー](../../../services/messaging.md#sqs-dlq)

### 問6 {#q6}

複数の SaaS とアプリのイベントを受け、内容で別々の処理に振り分けます。毎日 3 時の定期実行も 1 か所で扱います。どれが適切ですか。

- A. EventBridge のルールとスケジュール
- B. SNS の標準トピック
- C. Amazon MQ のブローカーを Multi-AZ で構築して連携する
- D. SQS FIFO キュー1 つにすべてのイベントを入れて、アプリで分ける

??? success "答えと解説"
    **正解: A**

    EventBridge は内容によるルーティング、SaaS 連携、スケジュールを提供します。

    - A: 正しい。
    - B: 誤り。SaaS のイベントの連携とスケジュールの機能がない。
    - C: 誤り。既存の JMS などの移行に向き、SaaS 連携の機能はない。
    - D: 誤り。振り分けを自作することになる。

    **スキル:** [メッセージング](../domain2.md#t2-1-messaging) / **参照:** [EventBridge](../../../services/messaging.md#eventbridge)

### 問7 {#q7}

オンプレミスの JMS を使うアプリをコードの変更なしで AWS に移します。ブローカーの管理は減らしたいと考えています。どれを選びますか。

- A. SQS に移すために送受信のコードを SDK に書き換える
- B. Amazon MQ のマネージドブローカー
- C. EC2 に ActiveMQ を構築して自分でパッチを当てる
- D. SNS のトピックに接続する

??? success "答えと解説"
    **正解: B**

    Amazon MQ は ActiveMQ と RabbitMQ のマネージドブローカーで、標準のプロトコルをそのまま使えます。

    - A: 誤り。コードの変更が必要になる。
    - B: 正しい。
    - C: 誤り。管理が減らない。
    - D: 誤り。SNS は JMS に対応しない。

    **スキル:** [メッセージング](../domain2.md#t2-1-messaging) / **参照:** [Amazon MQ](../../../services/other-services.md#mq)

### 問8 {#q8}

Lambda が別の Lambda を呼び、再試行と分岐を自前で書いています。保守が難しくなりました。人の承認が入り、数日かかる業務フローです。どう改善しますか。

- A. SQS の遅延キューに、次のステップをすべて手で書いて入れる
- B. Step Functions の Express ワークフローに移す
- C. Step Functions の Standard ワークフローに移す
- D. Lambda のタイムアウトを最大の 15 分に揃え、1 つの関数にまとめる

??? success "答えと解説"
    **正解: C**

    Standard は最大 1 年の実行ができ、人の承認や再試行もステートマシンで管理できます。

    - A: 誤り。分岐と再試行を結局自作する。
    - B: 誤り。最大 5 分で、数日のフローに合わない。
    - C: 正しい。
    - D: 誤り。数日のフローは 1 つの関数では動かせない。

    **スキル:** [ワークフロー](../domain2.md#t2-1-workflow) / **参照:** [Standard と Express](../../../services/step-functions.md#standard-express)、[人の承認](../../../services/step-functions.md#human-approval)

### 問9 {#q9}

毎秒数千件の短いイベントの処理を、ワークフローで 1 件ずつ数秒で実行します。実行回数あたりの費用を抑えたいと考えています。どれを選びますか。

- A. AWS Batch の配列ジョブでイベントを 1 件ずつ実行する
- B. EMR のステップ
- C. Standard ワークフローで、状態遷移のたびに課金を受ける
- D. Step Functions の Express ワークフロー

??? success "答えと解説"
    **正解: D**

    Express は大量で短いイベント処理に向きます。最大 5 分です。

    - A: 誤り。短いイベントの処理に向かない。
    - B: 誤り。大規模なデータ処理向け。
    - C: 誤り。大量で短い処理には費用が大きくなる。
    - D: 正しい。

    **スキル:** [ワークフロー](../domain2.md#t2-1-workflow) / **参照:** [Standard と Express](../../../services/step-functions.md#standard-express)

### 問10 {#q10}

ワークフローの途中の外部 API 呼び出しが一時的に失敗することがあります。再試行とエラー時の分岐をコードを書かずに定義します。どれを使いますか。

- A. Step Functions のステートの `Retry` と `Catch`
- B. CloudWatch アラームで失敗を検知して手動で再実行する
- C. SQS のデッドレターキューを各ステップの前に自分で挟む
- D. Lambda の予約済み同時実行を 1 に設定する

??? success "答えと解説"
    **正解: A**

    `Retry` でバックオフ付きの再試行、`Catch` でエラー時の遷移を宣言できます。

    - A: 正しい。

    - C: 誤り。分岐の定義にならない。
    - D: 誤り。同時実行の制限で、再試行の定義ではない。

### 問13 {#q13}

API の処理に 3 分かかることがあり、呼び出し側でタイムアウトします。既定の統合タイムアウトは 29 秒です。アーキテクチャの改善として適切なものはどれですか。

- A. 呼び出し側で 10 分待つ
- B. API のステージのキャッシュを有効にして長い処理を隠す
- C. 受付で SQS に入れてすぐに応答する
- D. Lambda のメモリを増やして 29 秒に収まることを祈る

??? success "答えと解説"
    **正解: C**

    長い処理は受付と処理を分けます。受付の ID で進み具合を確認させます。

    - A: 誤り。API Gateway 側は変わらない。
    - B: 誤り。同じリクエストの再利用で、処理時間は変わらない。
    - C: 正しい。
    - D: 誤り。3 分の処理の根本の解決にならない。

プライベートサブネットの ALB の後ろのサービスを、REST API で公開します。ALB はインターネットから見えません。どう接続しますか。

- A. VPC リンクでプライベート統合にする

- C. ALB をパブリックに変更して、IP を API に許可する
- D. プライベートサブネットに NAT ゲートウェイを追加する

??? success "答えと解説"

    - A: 正しい。
    - B: 誤り。入口の種類で、VPC 内への到達は解決しない。
    - C: 誤り。ALB の公開が必要になり、要件に反する。

### 問15 {#q15}

動画のアップロードの受付と変換が同じサーバーにあり、変換の CPU で受付まで遅くなります。部品を別々にスケールさせる設計はどれですか。

- A. ALB のルールで受付と変換を同じターゲットグループに振り分ける
- B. 受付と変換を SQS で分け、ワーカーを別にする
- C. より大きなインスタンスに変更する
- D. 受付のサーバーの Auto Scaling を CPU で増やして両方の処理を続ける

??? success "答えと解説"
    **正解: B**

    受付は S3 に置いてキューに入れます。キューが間に入ると、前段と後段を独立してスケールできます。

    - A: 誤り。同じ組み合わせのままで分離にならない。
    - B: 正しい。
    - C: 誤り。垂直に上げるだけで、結合が残る。
    - D: 誤り。変換の負荷に引きずられる。

    **スキル:** [ワークロードの分離](../domain3.md#t3-2-decoupling) / **参照:** [密結合と疎結合](../../../services/messaging.md#coupling)

### 問17 {#q17}

注文イベントに新しい分析の処理をあとから追加します。既存の処理を変更せず、新しい処理は別にスケールさせます。SNS と SQS のファンアウトで何をしますか。

- A. 新しい SNS トピックを発行元ごとに作り、発行元のコードを変える
- B. 既存の SQS キューの可視性タイムアウトを伸ばして両方の処理が読めるようにする

??? success "答えと解説"

    購読を足すだけで、発行元と既存の処理は変わりません。

    - A: 誤り。発行元の変更が要る。
    - B: 誤り。同じメッセージを両方に確実に届けられない。
    - C: 誤り。既存の処理を変更することになる。
    - D: 正しい。

    **スキル:** [ワークロードの分離](../domain3.md#t3-2-decoupling) / **参照:** [ファンアウト](../../../services/messaging.md#fanout)
