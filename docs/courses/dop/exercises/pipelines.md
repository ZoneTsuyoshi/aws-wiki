# CodePipeline と複数アカウントの問題集

対象の解説: [CodePipeline と複数アカウント](../../../services/cicd.md#codepipeline)

### 問1 {#q1}

金融系の社内システムでは、監査の要件として、本番への反映の前に変更管理の担当者が内容を確認して記録を残す必要があります。一方で開発チームは、コミットのたびにビルドとテストを自動で回し、いつでもリリースできる状態を保ちたいと考えています。この要件に合う進め方と実装はどれですか。

- A. 継続的インテグレーションだけを自動化し、本番環境へのデプロイは担当者が手元のスクリプトで行う
- B. 継続的デプロイにして、テストを通ったコミットを本番へそのまま反映し、後から CloudTrail で確認する
- C. 継続的デリバリーにして、本番ステージの前に CodePipeline の手動承認アクションを置く
- D. ウォーターフォールに戻し、四半期ごとの工程の完了時にまとめて担当者が承認する

??? success "答えと解説"
    **正解: C**

    テストまで自動で進め、本番の前で人が承認する形が継続的デリバリーです。承認アクションの結果はパイプラインの履歴に残ります。

    - A: 誤り。いつでも出せる状態を自動で保てず、手作業の誤りも残る。
    - B: 誤り。人の確認が反映の前に入らないので、監査の要件を満たせない。
    - C: 正しい。
    - D: 誤り。コミットごとに回すという開発チームの要件に合わない。

    **スキル:** [SDLC の概念とモデル](../domain1.md#t1-1-sdlc) / **参照:** [手動承認](../../../services/cicd.md#manual-approval)、[サービスの役割](../../../services/cicd.md#overview)

### 問2 {#q2}

あるチームは、コミットごとにビルドと単体テストを実行し、失敗をすぐに開発者へ返しています。ただし、成果物は保存しておらず、検証環境への反映は月に一度、担当者が手順書を見ながら行っています。月次の反映のたびに環境の差で障害が起きます。SDLC の改善として最も効果が高いものはどれですか。

- A. ブランチを環境の数だけ作り、環境ごとに別々のビルドを実行して差を吸収する
- B. ビルドした成果物を保存し、同じ成果物を自動で検証環境へデプロイするところまでパイプラインを広げる
- C. 単体テストの数を増やし、ビルド時間を延ばしてでもカバレッジを 90% 以上に引き上げて品質を確保する
- D. 月次の反映を四半期ごとに減らし、1 回の反映に含める変更をまとめて手順書を詳しくする

??? success "答えと解説"
    **正解: B**

    継続的インテグレーションで止まっているので、検証環境までの自動デプロイへ広げます。小さく頻繁に反映すると、環境の差も早く見つかります。

    - A: 誤り。環境ごとのビルドは、テストしたものと本番のものが変わる原因になる。
    - B: 正しい。
    - C: 誤り。テストの追加では、手作業の反映と環境の差という原因が残る。
    - D: 誤り。変更を大きくすると失敗の影響と調査の範囲が増える。

    **スキル:** [SDLC の概念とモデル](../domain1.md#t1-1-sdlc) / **参照:** [サービスの役割](../../../services/cicd.md#overview)

### 問3 {#q3}

SaaS を運営するチームは、`main` にマージされた変更を、テストに通れば人の操作なしで本番へ出したいと考えています。失敗時は自動で前の版に戻すことも求められています。パイプラインには GitHub を接続済みです。どの構成が合いますか。

- A. すべてのブランチのプッシュでパイプラインを起動し、本番へのデプロイは夜間の定期実行にまとめる
- B. `main` ではなく `release` ブランチへ毎週まとめてマージし、そのときだけパイプラインを起動する
- C. 本番ステージの直前に手動承認を置き、当番の担当者が 15 分以内に承認する運用にする
- D. `main` へのプッシュを起動の条件とし、承認アクションを置かず、失敗時のステージのロールバックを設定する

??? success "答えと解説"
    **正解: D**

    人の操作なしで本番まで進むのが継続的デプロイです。トリガーを `main` に絞り、ステージのロールバックで失敗に備えます。

    - A: 誤り。未レビューのブランチまで本番系が動き、マージごとの反映にもならない。
    - B: 誤り。変更をためる運用で、マージごとに出すという要件に合わない。
    - C: 誤り。人の操作が入るので継続的デリバリーになり、要件に合わない。
    - D: 正しい。

    **スキル:** [SDLC の概念とモデル](../domain1.md#t1-1-sdlc), [バージョン管理](../domain1.md#t1-1-version-control) / **参照:** [手動承認](../../../services/cicd.md#manual-approval)、[リポジトリからの起動](../../../services/cicd.md#pipeline-triggers)

### 問4 {#q4}

ツール用アカウントの CodePipeline から、本番アカウントの CloudFormation へデプロイします。本番側のロールの信頼ポリシーは正しく、パイプラインのロールは `sts:AssumeRole` を許可されています。それでも本番のアクションが、入力アーティファクトを読めずに失敗します。アーティファクトは既定の `aws/s3` キーで暗号化されています。必要な変更はどれですか。（2つ選択）

- A. アーティファクトをカスタマー管理の KMS キーで暗号化し、キーポリシーで本番アカウントに復号を許可する
- B. アーティファクト用バケットのポリシーで、本番アカウントのロールに読み取りを許可する
- C. 本番アカウントのロールに `AdministratorAccess` を付けて、S3 と KMS の権限不足を解消する
- D. 本番アカウントにも同じ名前のパイプラインを作り、ソースのステージを共有する設定に変える
- E. `aws/s3` キーのキーポリシーを編集して、本番アカウントのロールに `kms:Decrypt` を許可する

??? success "答えと解説"
    **正解: A, B**

    別アカウントから読むには、カスタマー管理キーのキーポリシーとバケットポリシーの両方で許可します。

    - A: 正しい。
    - B: 正しい。
    - C: 誤り。別アカウントのキーとバケットは相手側の許可も必要で、広い権限でも解決しない。
    - D: 誤り。アカウントをまたぐ読み取りの問題は解決しない。
    - E: 誤り。AWS 管理キーのポリシーは変更できない。

    **スキル:** [単一アカウントと複数アカウント](../domain1.md#t1-1-multi-account) / **参照:** [アカウントをまたぐ暗号化](../../../services/kms.md#cross-account)、[複数環境への展開](../../../services/cicd.md#multi-environment)

### 問5 {#q5}

ある組織は、開発、検証、本番のアカウントを分け、パイプラインも 1 か所で管理したいと考えています。東京とオレゴンの 2 リージョンの本番へ順にデプロイします。開発者が本番アカウントに権限を持たないことも条件です。最も適切な構成はどれですか。

- A. 開発アカウントのパイプラインで全リージョンのスタックを更新し、アーティファクトバケットは東京に 1 つだけ置く
- B. 環境ごとのアカウントに別々のパイプラインを作り、同じソースから環境ごとにビルドする
- C. ツール用アカウントにパイプラインを置き、各アカウントのロールを引き受け、リージョンごとにアーティファクトバケットを用意する
- D. 本番アカウントにパイプラインを置き、開発者には本番のパイプラインを起動する権限だけを与える

??? success "答えと解説"
    **正解: C**

    パイプラインは専用のアカウントに置き、宛先のロールを引き受けます。リージョンをまたぐアクションには、リージョンごとのアーティファクトバケットが必要です。

    - A: 誤り。別リージョンのアクションにはそのリージョンのアーティファクトストアが必要で、開発アカウントに本番の権限を集めるのも不適切。
    - B: 誤り。管理が分散し、環境ごとのビルドで成果物も変わる。
    - C: 正しい。
    - D: 誤り。本番アカウントへの権限が開発者に必要になり、条件に反する。

    **スキル:** [単一アカウントと複数アカウント](../domain1.md#t1-1-multi-account) / **参照:** [複数環境への展開](../../../services/cicd.md#multi-environment)、[マルチアカウントのパターン](../../../services/governance.md#multi-account-patterns)

### 問6 {#q6}

パイプライン用アカウントの CodePipeline から本番アカウントの CodeDeploy を呼ぶと、`AccessDenied` で失敗します。KMS のキーポリシーとバケットポリシーは確認済みです。CloudTrail を見ると、`sts:AssumeRole` の呼び出しが本番アカウントのロールに対して拒否されています。原因として最も可能性が高いものはどれですか。

- A. 本番アカウントのロールの信頼ポリシーが、パイプラインのサービスロールを許可していない
- B. パイプラインのアーティファクトバケットでバージョニングが有効になっていない
- C. 本番アカウントで CodeDeploy エージェントのバージョンが古く、ロールの引き受けに失敗している
- D. パイプラインが V1 タイプなので、別のアカウントのアクションを実行できない

??? success "答えと解説"
    **正解: A**

    `AssumeRole` には、呼び出し側の許可と、引き受けられる側の信頼ポリシーの両方が必要です。CloudTrail で拒否されているのはこの段階です。

    - A: 正しい。
    - B: 誤り。バージョニングの有無は `AssumeRole` の拒否と関係がない。
    - C: 誤り。エージェントはロールの引き受けを行わず、拒否の主体にならない。
    - D: 誤り。どちらのタイプでも別アカウントのアクションを実行できる。

    **スキル:** [単一アカウントと複数アカウント](../domain1.md#t1-1-multi-account) / **参照:** [複数環境への展開](../../../services/cicd.md#multi-environment)、[クロスアカウントアクセス](../../../services/iam.md#cross-account)

### 問7 {#q7}

1 つの GitHub リポジトリに 12 個のマイクロサービスがあります。現在はどのディレクトリを変更しても全サービスのパイプラインが動き、ビルドの費用が増えています。各サービスのパイプラインを、そのサービスのファイルが変わったときだけ、かつ `main` へのプッシュでだけ動かします。独自のコードは書きません。何を使いますか。

- A. V2 パイプラインのトリガーフィルターで、ブランチとファイルパスを指定する
- B. サービスごとにリポジトリを分割し、それぞれに V1 パイプラインのソースアクションを設定する
- C. EventBridge のルールで GitHub の Webhook を受け、Lambda で変更ファイルを判定してパイプラインを開始する
- D. CodeBuild の `buildspec.yml` の先頭で変更ファイルを調べ、対象外なら `exit 0` で早く終わらせる

??? success "答えと解説"
    **正解: A**

    V2 パイプラインのトリガーフィルターは、ブランチ、タグ、ファイルパスで起動の条件を絞れます。

    - A: 正しい。
    - B: 誤り。効果はあるが、リポジトリの移行という大きな変更が必要で最小の手段ではない。
    - C: 誤り。独自のコードが必要になり、条件に合わない。
    - D: 誤り。パイプラインとビルドの起動は止まらず、スクリプトも必要になる。

    **スキル:** [バージョン管理](../domain1.md#t1-1-version-control) / **参照:** [リポジトリからの起動](../../../services/cicd.md#pipeline-triggers)、[ブランチとタグでバージョンとリリースを管理する](../../../services/cicd.md#branches-tags)

### 問8 {#q8}

リリースの運用を変更します。`main` へのマージでは検証環境まで進め、`v1.2.0` のようなタグが付いたときに本番まで進めます。検証で確認したものと本番のものを確実に同じにすることも条件です。最も適切な方法はどれですか。

- A. タグが付いたときに、本番向けの設定で改めてビルドし直して、そのイメージを本番へ出す
- B. 検証環境のサーバーの中身をそのまま AMI にして、本番の Auto Scaling グループへ手動で登録する
- C. `main` と `production` の 2 つのブランチに同じコードを置き、それぞれのパイプラインで個別にビルドする
- D. コミットごとに成果物を 1 回だけビルドしてダイジェストで記録し、タグのトリガーではその成果物を本番へ昇格する

??? success "答えと解説"
    **正解: D**

    同じ成果物を次の環境へ進めるのが基本です。環境の差はパラメータで吸収します。

    - A: 誤り。ビルドし直すと、検証したものと本番のものが変わるおそれがある。
    - B: 誤り。手作業が残り、タグによるリリースの条件も満たせない。
    - C: 誤り。ブランチごとのビルドでは同じ成果物にならない。
    - D: 正しい。

    **スキル:** [バージョン管理](../domain1.md#t1-1-version-control) / **参照:** [リポジトリからの起動](../../../services/cicd.md#pipeline-triggers)、[アプリケーション環境の作成と管理](../../../services/cicd.md#app-environments)

### 問9 {#q9}

組織の方針で、GitHub Enterprise Cloud のリポジトリと CodePipeline を接続します。個人の長期トークンをパイプラインの設定に残さないことが条件です。ある日、ソースアクションが失敗するようになりました。設定は変えていません。最初に確認する場所と、推奨の接続方式の組み合わせはどれですか。

- A. CodeCommit へのミラーリングを設定し、ミラーの Lambda のログを確認する
- B. S3 にソースを ZIP で定期的に置く運用へ切り替え、`aws s3 sync` の結果を確認する
- C. GitHub の個人アクセストークンを Secrets Manager に置き、OAuth の V1 ソースアクションで参照する。トークンの期限を確認する
- D. CodeConnections の接続を使い、接続の状態が `AVAILABLE` か、GitHub 側のアプリの権限が残っているかを確認する

??? success "答えと解説"
    **正解: D**

    - A: 誤り。接続の問題の切り分けにならず、不要な部品を増やす。
    - B: 誤り。バージョン管理との統合がなくなり、要件を満たさない。
    - C: 誤り。個人のトークンに依存する方式で、条件に合わない。
    - D: 正しい。

### 問10 {#q10}

パイプラインのテストステージで Lambda の呼び出しアクションを使い、デプロイした API を確認します。関数は 2 分で正常に終わりログにも成功と出ていますが、アクションは最後にタイムアウトで失敗します。最も可能性の高い原因はどれですか。

- A. CodePipeline の Lambda アクションは同期呼び出しなので、関数の戻り値の JSON の形式が誤っている
- B. テストステージの前のステージの出力アーティファクトを、関数の環境変数に指定していない
- C. 関数の予約済み同時実行が設定されていないので、CodePipeline からの呼び出しが調整されている
- D. 関数が `PutJobSuccessResult` を呼んでいないか、実行ロールにその権限がない

??? success "答えと解説"
    **正解: D**

    Lambda アクションは、関数が `PutJobSuccessResult` か `PutJobFailureResult` を呼ぶまで完了しません。

    - A: 誤り。戻り値では結果を伝えられない。結果は API で返す。
    - B: 誤り。入力の指定の問題はアクションのタイムアウトの原因にならない。
    - C: 誤り。関数は実行されて正常に終わっており、同時実行の問題ではない。
    - D: 正しい。

    **スキル:** [AWS サービスの呼び出し](../domain1.md#t1-2-invoke-services) / **参照:** [アクションの設定](../../../services/cicd.md#pipeline-actions)

### 問11 {#q11}

本番ステージのデプロイの後、30 分間のアラームの状態を見て、問題があればそのステージをロールバックし、なければ次のリージョンへ進めたいと考えています。独自のポーリングのコードは避けます。どの仕組みが合いますか。

- A. CodeBuild アクションで `sleep 1800` を実行し、最後に `describe-alarms` で状態を確認する
- B. 本番ステージの最後に Lambda アクションを置き、関数の中で 30 分間アラームをポーリングする
- C. ステージの `OnSuccess` の条件に `CloudWatchAlarm` のルールと `WaitTime` を設定し、結果を `ROLLBACK` にする
- D. 本番ステージの後に手動承認を置き、担当者がアラームを見て 30 分後に承認または却下する

??? success "答えと解説"
    **正解: C**

    ステージ条件の `OnSuccess` には `CloudWatchAlarm` のルールを置けます。`WaitTime` でアラームの状態の変化を待ち、ルールが失敗したときの結果にロールバックを指定できます。

    - A: 誤り。ビルド時間の費用がかかり、独自のスクリプトも残る。
    - B: 誤り。Lambda の上限は 15 分で、独自のコードも必要になる。
    - C: 正しい。
    - D: 誤り。人の判断に頼る形で、自動化の要件を満たさない。

    **スキル:** [AWS サービスの呼び出し](../domain1.md#t1-2-invoke-services) / **参照:** [ステージ条件](../../../services/cicd.md#stage-conditions)、[アクションの設定](../../../services/cicd.md#pipeline-actions)

### 問12 {#q12}

結合テストは、テストデータの投入、3 つの API の並列の検証、10 分ごとの結果の確認、最後の後片付けからなり、最大で 2 時間かかります。失敗しても後片付けは必ず実行します。CodePipeline から呼ぶ手段として最も適切なものはどれですか。

- A. Step Functions の Express ワークフローを呼び、2 時間の間は再試行で待ち続ける
- B. Step Functions の呼び出しアクションで、並列と待機と `Catch` を持つ Standard ワークフローを実行する
- C. Lambda の呼び出しアクションで 1 つの関数にまとめ、その中で各工程を順に実行する
- D. ステージの中に手動承認を並べ、工程の完了ごとに担当者が結果を確認して承認する

??? success "答えと解説"
    **正解: B**

    分岐、並列、待機を含む長い処理には Standard ワークフローが向きます。`Catch` で後片付けに進められます。

    - A: 誤り。Express の実行時間は最大 5 分で、この処理に使えない。
    - B: 正しい。
    - C: 誤り。上限の 15 分を超え、分岐と待機の実装も自前になる。
    - D: 誤り。人の作業が増え、後片付けの自動実行も保証できない。

    **スキル:** [AWS サービスの呼び出し](../domain1.md#t1-2-invoke-services) / **参照:** [アクションの設定](../../../services/cicd.md#pipeline-actions)、[Standard と Express](../../../services/step-functions.md#standard-express)
