# IaC と StackSetsの問題集

対象の解説: [IaC と StackSets](../../../services/iac.md#cloudformation-template)

### 問1 {#q1}

プラットフォームチームが、50 個のサービスに同じ形の VPC、ALB、ECS サービスを提供します。サービスの数に応じてループで生成し、構成の条件を単体テストで確認し、最終的な変更は CloudFormation の差分で確認します。どのツールが合いますか。

- A. SAM のテンプレートに `Globals` を書き、サービスの数だけ手でコピーして `sam validate` で確認する
- B. AWS CLI のシェルスクリプトで各リソースを順に作成し、結果の JSON を別のスクリプトで比較する
- C. 素の CloudFormation の YAML をサービスごとに置き、`Mappings` に 50 個の値を並べて更新する
- D. CDK のコンストラクトと `assertions` のテスト、`cdk diff`

??? success "答えと解説"
    **正解: D**

    プログラミング言語でループや抽象化を書き、`aws-cdk-lib/assertions` でテストできます。`cdk diff` で差分も確認できます。

    - A: 誤り。サーバーレス向けで、ループも構成のテストも書きにくい。
    - B: 誤り。継続的な管理と差分の確認ができない。
    - C: 誤り。ループや抽象化を書けず、テストもしにくい。
    - D: 正しい。

    **スキル:** [IaC の選択肢](../domain2.md#t2-1-iac-options) / **参照:** [どれを使うか](../../../services/iac.md#choosing)、[CDK](../../../services/iac.md#cdk)

### 問2 {#q2}

CloudFormation で作る Auto Scaling グループの更新で、次を満たします。新しい AMI の全インスタンスが、アプリの導入完了を知らせてから次のバッチへ進むこと。失敗したら自動で元に戻ること。テンプレートでの指定はどれですか。

- A. カスタムリソースの Lambda で、インスタンスを 1 台ずつ `terminate-instances` する
- B. `DependsOn` で ALB への依存を指定して `DeletionPolicy: Retain` を付ける
- C. `UpdatePolicy` の `AutoScalingRollingUpdate` で `WaitOnResourceSignals: true` にし、`cfn-signal` を送る
- D. `UpdateReplacePolicy` で `Snapshot` を指定して、`cfn-init` の設定を `Metadata` に書く

??? success "答えと解説"
    **正解: C**

    `WaitOnResourceSignals` でシグナルを待ちながらバッチで更新します。シグナルが届かなければ更新は失敗し、ロールバックします。

    - A: 誤り。標準の機能で足りるのに、更新と戻す処理の両方を自作することになる。
    - B: 誤り。依存の順番と削除時の扱いの設定で、更新の進め方を決めない。
    - C: 正しい。
    - D: 誤り。置き換え時のデータの扱いで、バッチの進行を制御しない。

    **スキル:** [IaC の選択肢](../domain2.md#t2-1-iac-options) / **参照:** [CreationPolicy](../../../services/iac.md#creation-policy)、[UpdatePolicy](../../../services/iac.md#update-policy)

### 問3 {#q3}

ある CloudFormation スタックで、(1) スタックの作成時に外部の SaaS の API へ登録する処理、(2) スタックの削除でも監査ログ用の S3 バケットを残す、の 2 つが必要です。テンプレートの機能の組み合わせとして適切なものはどれですか。（2つ選択）

- A. (2) はスタックの削除保護を有効にしてバケットだけを別に消せるようにする
- B. (2) は `DeletionPolicy: Retain` を指定する
- C. (2) はスタックポリシーで `Update:Delete` を拒否する
- D. (1) はカスタムリソースで、Lambda から応答 URL へ結果を返す
- E. (1) は `Outputs` の `Export` で SaaS へ値を送る

??? success "答えと解説"
    **正解: B, D**

    CloudFormation が扱えない処理はカスタムリソースで挟みます。データを残すなら `DeletionPolicy` です。

    - A: 誤り。削除保護はスタックの削除自体を止める設定で、バケットだけを残す機能ではない。
    - B: 正しい。
    - C: 誤り。スタックポリシーは更新の制御で、スタックの削除でバケットを残す機能ではない。
    - D: 正しい。
    - E: 誤り。エクスポートは他のスタックとの値の共有で、外部の API を呼ばない。

    **スキル:** [IaC の選択肢](../domain2.md#t2-1-iac-options) / **参照:** [カスタムリソース](../../../services/iac.md#custom-resources)、[リソースの属性: DeletionPolicy](../../../services/iac.md#deletion-policy)

### 問4 {#q4}

本番のスタックの更新は、影響の確認と責任者の承認の後に実行します。特に、データベースが置き換えられる変更を見逃さないようにします。CodePipeline での進め方として適切なものはどれですか。

- A. 変更セットの作成、手動承認、変更セットの実行の順に置き、`Replacement` を確認する
- B. `CREATE_UPDATE` のアクションで直接更新して、失敗したときにスタックイベントを確認する
- C. `cfn-lint` だけで検査して、問題がなければ本番のスタックをそのまま更新する
- D. ドリフト検出を実行してから、結果が `IN_SYNC` なら本番のスタックをそのまま更新する

??? success "答えと解説"
    **正解: A**

    変更セットで `Replacement` を確認してから承認します。

    - A: 正しい。
    - B: 誤り。実行の前に影響を確認できない。
    - C: 誤り。構文の検査で、実際の環境への影響は分からない。
    - D: 誤り。実際の構成とテンプレートの差の確認で、今回の変更の影響は分からない。

    **スキル:** [変更管理](../domain2.md#t2-1-change-management) / **参照:** [変更セット](../../../services/iac.md#change-sets)、[アクションの設定](../../../services/cicd.md#pipeline-actions)

### 問5 {#q5}

本番のスタックに、次の 2 つの保護を入れます。(1) RDS のインスタンスの置き換えや削除を伴う更新を禁止する。(2) 更新の後 15 分以内に 5xx のアラームが鳴ったら、スタックを自動で前の状態に戻す。適切な組み合わせはどれですか。

- A. (1) に削除保護、(2) に CodeDeploy の自動ロールバック
- B. (1) に `DeletionPolicy: Snapshot`、(2) に EventBridge と Lambda による `cancel-update-stack`
- C. (1) に IAM の権限境界、(2) に `cfn-signal` のタイムアウト
- D. (1) にスタックポリシー、(2) にモニタリング時間付きのロールバックトリガー

??? success "答えと解説"
    **正解: D**

    スタックポリシーはリソースごとの更新を制御します。ロールバックトリガーは指定のアラームを監視して戻します。

    - A: 誤り。削除保護はスタック全体の削除の防止で、更新を止めない。CodeDeploy はスタックを戻さない。
    - B: 誤り。スナップショットは更新を禁止しない。自作の処理も不要。
    - C: 誤り。権限境界はリソースごとの更新の制御に向かず、シグナルは更新の後の監視にならない。
    - D: 正しい。

    **スキル:** [変更管理](../domain2.md#t2-1-change-management) / **参照:** [スタックポリシー](../../../services/iac.md#stack-policy)、[ロールバックトリガー](../../../services/iac.md#rollback-triggers)

### 問6 {#q6}

担当者がコンソールからセキュリティグループを直接変更することがあり、次の更新で意図せず戻っています。100 個のスタックで手作業の変更を自動で見つけ、担当へ通知します。修正は担当者が判断します。適切な構成はどれですか。

- A. Config のマネージドルール `cloudformation-stack-drift-detection-check` と EventBridge、SNS
- B. CloudTrail の全イベントを Athena で毎日検索し、変更者のロール名で手作業を判定する
- C. ドリフト検出の結果に基づいて、CloudFormation にテンプレートの内容へ自動で修復させ、結果を SNS で通知する
- D. スタックポリシーで全リソースの更新を拒否して、コンソールからの手作業の変更を止められるようにする

??? success "答えと解説"
    **正解: A**

    ドリフト検出は見つけるだけです。定期的に実行するには Config のルールを使い、準拠の変化を通知します。

    - A: 正しい。
    - B: 誤り。差分そのものが分からず、手間も大きい。
    - C: 誤り。ドリフト検出は見つけるだけで、直す機能ではない。
    - D: 誤り。スタックポリシーはスタックの更新の制御で、コンソールからの直接の変更を止めない。

    **スキル:** [変更管理](../domain2.md#t2-1-change-management) / **参照:** [ドリフト検出](../../../services/iac.md#drift)、[ドリフトの運用](../../../services/operations.md#drift-operations)

### 問7 {#q7}

組織の全アカウントに、監査用のロールを配ります。新しいアカウントが OU に入ると自動で作り、アカウントが抜けるとスタックを消します。管理と実行のロールは自分で作りたくありません。どの設定が適切ですか。

- A. 各アカウントに同じスタックを手で作り、Config のルールで存在を確認する
- B. ネストされたスタックの子として各アカウントのロールを定義し、親スタックを更新する
- C. サービスマネージド権限で、自動デプロイを有効にし、`RetainStacksOnAccountRemoval` を `false` にする
- D. セルフマネージド権限で `AWSCloudFormationStackSetAdministrationRole` を作り、アカウントを追加するたびに手で指定する

??? success "答えと解説"
    **正解: C**

    サービスマネージド権限なら、必要なロールが自動で作られ、OU の新しいアカウントへ自動で展開されます。

    - A: 誤り。新しいアカウントで自動にならない。
    - B: 誤り。ネストされたスタックはアカウントをまたげない。
    - C: 正しい。
    - D: 誤り。ロールの作成と追加の作業が残る。

    **スキル:** [StackSets](../domain2.md#t2-1-stacksets) / **参照:** [StackSets の設定](../../../services/iac.md#stacksets-settings)

### 問8 {#q8}

StackSets で 200 アカウントの基盤を更新します。誤りがあっても影響を最小にしたいので、1 アカウントずつ進め、最初の失敗で止めます。費やす時間は問いません。また、リージョンも順番に処理します。適切な設定はどれですか。

- A. 最大同時アカウント数 1、失敗の許容数 199、リージョンの処理は順次
- B. 最大同時アカウント数 100%、失敗の許容数 100%、リージョンの処理は順次
- C. 最大同時アカウント数 1、失敗の許容数 0、リージョンの処理は順次
- D. 最大同時アカウント数 200、失敗の許容数 0、リージョンの処理は並列

??? success "答えと解説"
    **正解: C**

    同時実行を 1、失敗の許容数を 0 にすると、最初の失敗で止まります。

    - A: 誤り。ほとんど失敗しても止まらない。
    - B: 誤り。影響の抑制にならない。
    - C: 正しい。
    - D: 誤り。全アカウントが一度に更新され、失敗に気づく前に広がる。

    **スキル:** [StackSets](../domain2.md#t2-1-stacksets) / **参照:** [StackSets の設定](../../../services/iac.md#stacksets-settings)、[StackSets の運用](../../../services/operations.md#stacksets-operations)

### 問9 {#q9}

StackSets の更新で、3 つのアカウントのスタックインスタンスが `OUTDATED` のまま残りました。テンプレートは S3 バケットに固定の名前を付けています。セルフマネージド権限で運用しています。確認すべき項目はどれですか。（2つ選択）

- A. 対象アカウントの Service Catalog のポートフォリオと共有の状態
- B. 管理アカウントの Organizations で、すべての機能が有効になっているか
- C. 管理アカウントの CloudTrail の保存先と、ログファイルの検証の有効化
- D. 固定の名前のリソースが、対象アカウントの既存のものと衝突していないか
- E. 対象アカウントの実行ロールと、管理アカウントからの信頼関係

??? success "答えと解説"
    **正解: D, E**

    `OUTDATED` は実行ロール、固定名の衝突、クォータなどが典型です。

    - A: 誤り。StackSets の更新とは別の仕組みで、関係がない。
    - B: 誤り。セルフマネージド権限では Organizations の連携を前提としない。
    - C: 誤り。監査の設定で、スタックインスタンスの更新の失敗の原因にならない。
    - D: 正しい。
    - E: 正しい。

    **スキル:** [StackSets](../domain2.md#t2-1-stacksets) / **参照:** [StackSets の運用](../../../services/operations.md#stacksets-operations)、[StackSets の設定](../../../services/iac.md#stacksets-settings)

### 問10 {#q10}

セキュリティチームは、暗号化とログ設定を組み込んだ S3 バケットの定義を各チームへ配ります。各チームのテンプレートに部品として入れ、作成されるリソースはアプリのスタックの中に含めます。版も管理します。何を使いますか。

- A. Service Catalog の製品にして、各チームのポートフォリオへ共有する
- B. CloudFormation レジストリに登録したモジュールを各テンプレートで参照する
- C. ネストされたスタックを S3 に置いて、各チームの親スタックから `TemplateURL` で呼ぶ
- D. `Outputs` の `Export` でバケット名を共有し、全チームが 1 つのバケットを使う

??? success "答えと解説"
    **正解: B**

    モジュールはテンプレートに部品として入り、レジストリで版を管理できます。

    - A: 誤り。製品は別のプロビジョニングになり、アプリのスタックの中に含まれない。
    - B: 正しい。
    - C: 誤り。別のスタックになるので、アプリのスタックの中に含めるという条件に合わない。
    - D: 誤り。定義の配布にならず、共有のバケットが 1 つできるだけ。

    **スキル:** [再利用できる部品](../domain2.md#t2-1-reusable) / **参照:** [ネストとエクスポートの比較](../../../services/iac.md#nested-vs-exports)、[AWS Service Catalog](../../../services/governance.md#service-catalog)

### 問11 {#q11}

開発者に EC2 や IAM の権限を与えずに、承認済みの構成だけを自分で作らせます。インスタンスタイプは `t3.medium` か `t3.large` に限ります。必要な仕組みはどれですか。（2つ選択）

- A. 開発者に CloudFormation の権限だけを与えて、`--role-arn` に管理者のロールを自由に指定させる
- B. CDK の L3 コンストラクトを配布して、開発者が自分の権限で `cdk deploy` する
- C. Service Catalog の起動制約で、製品を作るときに引き受けるロールを指定する
- D. 開発者のロールに `AdministratorAccess` を付けて、SCP で高価なインスタンスタイプを拒否する
- E. Service Catalog のテンプレート制約で、`InstanceType` の値を限定する

??? success "答えと解説"
    **正解: C, E**

    起動制約なら利用者に下位のサービスの権限が要りません。テンプレート制約でパラメータを限定します。

    - A: 誤り。承認済みの構成に限定できない。
    - B: 誤り。開発者に各リソースの権限が必要になる。
    - C: 正しい。
    - D: 誤り。権限を与えないという条件に反する。
    - E: 正しい。

    **スキル:** [再利用できる部品](../domain2.md#t2-1-reusable) / **参照:** [AWS Service Catalog](../../../services/governance.md#service-catalog)

### 問12 {#q12}

プラットフォームチームが、社内標準の暗号化、ログ、アラームを組み込んだ「標準の API」の部品を配ります。利用者は TypeScript で書いており、新しいバージョンをパッケージとして取り込みます。基準を破る変更は配布の前にテストで止めます。適切な手段はどれですか。

- A. `sam init` の社内テンプレートをメールで配布して、利用者の変更を Config のルールで確認する運用にする
- B. `cdk bootstrap` のテンプレートに全リソースを書き、全アカウントで同じ構成を作る
- C. L1 コンストラクトの一覧を Wiki に載せて、利用者にコピーして使ってもらう
- D. L3 コンストラクトを CodeArtifact で配布し、`assertions` のテストをパイプラインに置く

??? success "答えと解説"
    **正解: D**

    L3 コンストラクトに基準を組み込み、パッケージとして配布します。テンプレートのアサーションで基準を確認できます。

    - A: 誤り。版の配布になりにくく、テストも配布の前に入らない。
    - B: 誤り。ブートストラップはデプロイの準備で、アプリの部品の配布ではない。
    - C: 誤り。再利用の部品にならず、基準の更新も伝わらない。
    - D: 正しい。

    **スキル:** [再利用できる部品](../domain2.md#t2-1-reusable) / **参照:** [コンストラクト](../../../services/iac.md#cdk-constructs)、[assertions によるテスト](../../../services/iac.md#cdk-testing)
