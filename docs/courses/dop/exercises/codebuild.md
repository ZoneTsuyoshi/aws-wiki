# CodeBuild とテストの問題集

対象の解説: [CodeBuild とテスト](../../../services/cicd.md#codebuild)

### 問1 {#q1}

CodeBuild でコンテナイメージをビルドし、続けて VPC の中の RDS に接続する結合テストを実行します。`docker build` が `Cannot connect to the Docker daemon` で失敗し、テストはデータベースに接続できません。修正の組み合わせとして正しいものはどれですか。

- A. コンピュートを Lambda に変えて Docker を不要にし、RDS のセキュリティグループを `0.0.0.0/0` に開く
- B. プロジェクトの特権モードを有効にし、VPC とプライベートサブネットとセキュリティグループを設定する
- C. buildspec の `install` フェーズで Docker を入れ直し、RDS をパブリックアクセス可能に変更する
- D. サービスロールに `ecr:*` と `rds:*` を追加して、イメージのビルドと接続の権限を与える

??? success "答えと解説"
    **正解: B**

    Docker のビルドには特権モード、VPC の中の接続にはプロジェクトの VPC 設定が必要です。

    - A: 誤り。Lambda コンピュートは Docker のビルドも VPC 接続もできない。
    - B: 正しい。
    - C: 誤り。特権モードがないとデーモンは動かず、データベースの公開も不適切。
    - D: 誤り。IAM の権限ではデーモンの起動も経路の問題も解決しない。

    **スキル:** [ビルドプロセス](../domain1.md#t1-1-build) / **参照:** [プロジェクトの設定](../../../services/cicd.md#codebuild-project)、[VPC の設定](../../../services/cicd.md#codebuild-vpc)

### 問2 {#q2}

Java のビルドで依存関係の取得に毎回 8 分かかります。同じプロジェクトを複数の担当者が 1 日中並行で実行し、ビルド用のホストが変わることもあります。さらに、3 つの JDK のバージョンで同じテストを同時に実行したいと考えています。適切な設定はどれですか。

- A. 依存関係を毎回 EFS にコピーする処理を `post_build` に書き、JDK はイメージに 3 つ入れて順にテストする
- B. コンピュートを最大サイズに変え、`buildspec.yml` の `phases` にテストのコマンドを JDK の数だけ並べる
- C. ローカルキャッシュの `LOCAL_CUSTOM_CACHE` だけを使い、JDK ごとにプロジェクトを 3 つ作って順に起動する
- D. `cache` に依存関係のパスを指定して S3 キャッシュを使い、buildspec の `batch` で JDK ごとのビルドを並行で実行する

??? success "答えと解説"
    **正解: D**

    ホストをまたいで共有するなら S3 キャッシュです。複数の構成を同時に動かすには `batch` を使います。

    - A: 誤り。同時実行にならず、自前の処理も増える。
    - B: 誤り。依存関係の取得は短くならず、順次の実行のままになる。
    - C: 誤り。ローカルキャッシュは同じホストの再利用が前提で、効果が安定しない。プロジェクトを増やす必要もない。
    - D: 正しい。

    **スキル:** [ビルドプロセス](../domain1.md#t1-1-build) / **参照:** [キャッシュ](../../../services/cicd.md#build-cache)、[batch](../../../services/cicd.md#buildspec-batch)

### 問3 {#q3}

ビルド後のテストで失敗しても、テスト結果のファイルをアップロードして、一時リソースを必ず削除する必要があります。現在の buildspec は `build` フェーズのテストが失敗すると `post_build` の片付けが想定どおりに動かないことがあります。最も適切な修正はどれですか。

- A. すべてのコマンドの末尾に `|| true` を付け、どのフェーズも失敗しないようにする
- B. 片付けの処理を別の CodeBuild プロジェクトに分け、CodePipeline の次のアクションとして常に実行されるように並べる
- C. `artifacts` セクションに片付けのスクリプトを含め、次のステージで手動で実行する
- D. 片付けのコマンドをフェーズの `finally` ブロックに書き、失敗の扱いは `on-failure` で明示する

??? success "答えと解説"
    **正解: D**

    `finally` ブロックは、そのフェーズのコマンドが失敗しても実行されます。

    - A: 誤り。テストが失敗してもビルドが成功に見えるようになる。
    - B: 誤り。前のアクションが失敗すると、次のアクションは実行されない。
    - C: 誤り。成果物を渡すだけで実行されず、必ず片付くとは言えない。
    - D: 正しい。

    **スキル:** [ビルドプロセス](../domain1.md#t1-1-build) / **参照:** [ビルドフェーズ](../../../services/cicd.md#build-phases)、[on-failure と finally](../../../services/cicd.md#buildspec-on-failure)

### 問4 {#q4}

ビルドでプライベートレジストリのパスワードを使います。現在はプロジェクトの環境変数に平文で設定しており、CodeBuild のコンソールで見えることが監査で指摘されました。値は 30 日ごとに自動で変更する必要があります。最も適切な方法はどれですか。

- A. パスワードをカスタムのビルドイメージに焼き込み、ECR のリポジトリポリシーでアクセスを絞る
- B. Secrets Manager に保存して自動ローテーションを設定し、`env.secrets-manager` で参照する。ロールに取得と復号の権限を与える
- C. パラメータストアの `String` パラメータへ移し、`env.parameter-store` で参照して 30 日ごとに手で更新する
- D. パスワードを KMS で暗号化した文字列にしてリポジトリへコミットし、`pre_build` で `aws kms decrypt` を実行する

??? success "答えと解説"
    **正解: B**

    自動ローテーションが必要なら Secrets Manager です。buildspec で参照すれば、値はビルド時に取得されます。

    - A: 誤り。イメージにシークレットが残り、変更のたびに再ビルドが必要になる。
    - B: 正しい。
    - C: 誤り。平文の種類で、自動ローテーションもない。
    - D: 誤り。自動の変更ができず、リポジトリに暗号文と手順が残る。

    **スキル:** [シークレット](../domain1.md#t1-1-secrets) / **参照:** [secrets-manager の指定](../../../services/cicd.md#buildspec-secrets)、[環境変数とシークレット](../../../services/cicd.md#build-env)

### 問5 {#q5}

CloudFormation でデプロイする RDS のマスターパスワードと、CodeBuild で使う社内 API のエンドポイントの URL を管理します。パスワードはテンプレートにもスタックのパラメータの履歴にも残さず、自動でローテーションします。URL は秘密ではなく、環境ごとに違う値で、費用をかけたくありません。適切な組み合わせはどれですか。

- A. どちらも Parameter Store の `SecureString` に置き、パスワードは EventBridge の定期実行で変更する
- B. どちらもテンプレートの `Mappings` に環境ごとの値として書き、リポジトリの権限で保護する
- C. パスワードは Secrets Manager の動的参照で渡し、URL は Parameter Store の標準パラメータに置く
- D. パスワードは `NoEcho` のテンプレートパラメータで渡し、URL は Secrets Manager に置く

??? success "答えと解説"
    **正解: C**

    データベースの認証情報は Secrets Manager、秘密でない設定値は無料の標準パラメータが向きます。

    - A: 誤り。`SecureString` に自動ローテーションの機能はなく、自作が必要になる。
    - B: 誤り。パスワードがテンプレートとリポジトリに残る。
    - C: 正しい。
    - D: 誤り。`NoEcho` では自動ローテーションができず、URL に Secrets Manager の費用がかかる。

    **スキル:** [シークレット](../domain1.md#t1-1-secrets) / **参照:** [3 つのサービスの比較](../../../services/secrets.md#comparison)、[secrets-manager の指定](../../../services/cicd.md#buildspec-secrets)

### 問6 {#q6}

CodeBuild が `env.secrets-manager` でシークレットを取得するとき、ビルドの開始直後に `AccessDeniedException` になります。サービスロールには `secretsmanager:GetSecretValue` が付いています。シークレットはカスタマー管理の KMS キーで暗号化されています。次に確認するものはどれですか。

- A. ビルドが VPC で動くように設定され、NAT ゲートウェイの経路があるか
- B. サービスロールに `kms:Decrypt` があり、キーポリシーでも許可されているか
- C. シークレットの自動ローテーションが有効か、最後のローテーションが成功しているか
- D. プロジェクトの特権モードが無効になっていないか、`install` フェーズの `runtime-versions` が指定されているか

??? success "答えと解説"
    **正解: B**

    カスタマー管理キーで暗号化されたシークレットを読むには、取得の権限に加えて復号の権限が必要です。

    - A: 誤り。経路の問題なら権限の拒否ではなく接続のタイムアウトになる。
    - B: 正しい。
    - C: 誤り。ローテーションの状態は `AccessDenied` の原因にならない。
    - D: 誤り。どちらもシークレットの取得の権限と関係がない。

    **スキル:** [シークレット](../domain1.md#t1-1-secrets) / **参照:** [secrets-manager の指定](../../../services/cicd.md#buildspec-secrets)、[キーポリシー、IAM、グラント](../../../services/kms.md#access-control)

### 問7 {#q7}

あるパイプラインでは 40 分の UI テストを最初に実行し、その後に 2 分の単体テストと 1 分の静的解析を実行しています。開発者へのフィードバックが遅く、テスト環境の費用も高くなっています。また、検証環境で単体テストまで動かす意味がないと指摘されました。配置の見直しとして最も適切なものはどれですか。

- A. 静的解析と単体テストをコミットや PR の段階に置き、UI テストはデプロイ後の検証環境に置く
- B. UI テストをやめて、単体テストのカバレッジを 100% に引き上げる
- C. 3 種類を並列で同時に実行し、すべて終わるまで 40 分待ってからまとめて結果を PR へ返す
- D. すべてのテストを本番デプロイの後に移し、失敗したらロールバックで戻す

??? success "答えと解説"
    **正解: A**

    速くて安いテストを先に、遅くて高いテストを後に置きます。失敗を早く見つけ、無駄な費用を抑えられます。

    - A: 正しい。
    - B: 誤り。単体テストでは画面や環境の結合の問題を確認できない。
    - C: 誤り。速いテストの失敗でも、UI テストの費用と待ち時間がかかる。
    - D: 誤り。本番の利用者に欠陥が届いてから見つける形になる。

    **スキル:** [テストの種類と配置](../domain1.md#t1-2-test-types) / **参照:** [サービスの役割](../../../services/cicd.md#overview)、[単体テスト](../../../services/sdk-resilience.md#unit-testing)

パイプラインに次の 3 つの検査を組み込みます。自作コードの脆弱なパターン、ビルド後のコンテナイメージの CVE、本番前の外形の確認です。AWS のマネージドサービスを優先します。段階とサービスの組み合わせとして適切なものはどれですか。

- A. PR で FIS、ビルド後に GuardDuty、本番前に Macie を使う
- B. PR で Macie、ビルド後に Config、本番前に Device Farm を使う

### 問10 {#q10}

`main` へ向けた PR が作られたとき、または更新されたときだけ CodeBuild を動かします。Webhook のフィルターグループをどう設定しますか。

- A. 1 つのグループに `EVENT = PULL_REQUEST_CREATED, PULL_REQUEST_UPDATED` と `BASE_REF = ^refs/heads/main$` を置く
- B. グループ 1 に `EVENT = PUSH`、グループ 2 に `BASE_REF = ^refs/heads/main$` を置く
- C. グループ 1 に PR のイベント、グループ 2 に `BASE_REF = ^refs/heads/main$` を置く
- D. 1 つのグループに `EVENT = PULL_REQUEST_CREATED, PULL_REQUEST_UPDATED` と `HEAD_REF = main` を置く

??? success "答えと解説"
    **正解: A**

    1 つのグループの中は AND、グループどうしは OR です。宛先は `BASE_REF` で絞ります。

    - A: 正しい。
    - B: 誤り。グループどうしは OR なので、すべてのプッシュでも動く。
    - C: 誤り。別のグループは OR で評価され、他のブランチへの PR やプッシュまで動く。
    - D: 誤り。`HEAD_REF` は PR の元のブランチで、宛先の条件にならない。部分一致でもある。

    **スキル:** [PR とマージでのビルド](../domain1.md#t1-2-pr-builds) / **参照:** [Webhook とフィルターグループ](../../../services/cicd.md#codebuild-webhook)

### 問11 {#q11}

`HEAD_REF` のフィルターに `release` と書いたところ、`release-old` や `pre-release` へのプッシュでもビルドが動くようになりました。`release` ブランチだけで動かすにはどう修正しますか。

### 問14 {#q14}

検証環境の負荷テストでは問題がありませんでしたが、本番のキャンペーンで Lambda の 429 と Auto Scaling の起動の失敗が起きました。検証環境は本番の 5 分の 1 の構成で、負荷も本番想定の 5 分の 1 です。次回に同じ問題を見つけるには、何を変えますか。

- A. 検証環境の負荷テストの時間を 4 倍に延ばし、構成と負荷はそのままにする
- B. 本番と同じ規模とクォータの環境で、本番想定の負荷をかける
- C. CloudWatch の詳細モニタリングを検証環境で有効にして、1 秒単位でデータを見る
- D. 単体テストにクォータの値を確認するテストを追加して、カバレッジで判定する

??? success "答えと解説"
    **正解: B**

    クォータやスケーリングの上限は、本番に近い規模でかけて初めて当たります。検証環境のクォータも本番に合わせます。

    - B: 正しい。
    - C: 誤り。細かく見ても、上限に届かない負荷では問題は現れない。
    - D: 誤り。単体テストでは実際の同時実行や起動の失敗を再現できない。

### 問15 {#q15}

新しいサービスのリリース前に、負荷がかかった状態で AZ を 1 つ失っても応答時間の目標を守れるかを確かめます。アプリのコードは変更せず、テストが影響を広げたら自動で止めます。適切な組み合わせはどれですか。

- A. CodeBuild の負荷テストの中で `aws ec2 terminate-instances` を実行し、応答時間はログを後で集計する
- B. Device Farm で負荷をかけ、Route 53 のヘルスチェックを Inverted にして切り替える
- C. 負荷テストのツールだけを実行し、応答時間が伸びたら AZ の障害に強いと判断する
- D. 負荷テストと同時に FIS の実験を実行し、応答時間のアラームを停止条件に指定する

### 問16 {#q16}

buildspec の `build` フェーズで `npm test | tee results.log` を実行しています。テストが失敗してもビルドが `SUCCEEDED` になり、不具合のあるイメージが本番まで進みました。根本的な修正はどれですか。

- A. `post_build` フェーズで `cat results.log` を実行して、結果をビルドログに残す
- B. CodeBuild のタイムアウトを短くして、テストが長引いたらビルドを失敗にする
- C. `reports` セクションでテスト結果のファイルを指定すれば、失敗時に自動でビルドが止まる
- D. `set -o pipefail` などで `npm test` の終了コードをビルドの結果へ伝える

??? success "答えと解説"
    **正解: D**

    パイプの終了コードは最後のコマンド（`tee`）のものになります。テストの結果を伝えるようにします。

    - A: 誤り。ログを見られるようになるだけで、失敗の判定は変わらない。
    - B: 誤り。時間の問題ではなく、失敗のテストでも速く終われば通る。
    - C: 誤り。レポートは結果を表示するだけで、ビルドの成否を変えない。
    - D: 正しい。

### 問17 {#q17}

CloudFormation で作る Auto Scaling グループの起動スクリプトで、アプリの導入に失敗することがあります。現在は `cfn-signal -e 0` を末尾で常に実行しており、失敗してもスタックが `CREATE_COMPLETE` になります。どう修正しますか。

- A. `CreationPolicy` を削除して、起動スクリプトの結果を CloudFormation に待たせないようにする
- B. ターゲットグループのヘルスチェックの間隔を短くして、CloudFormation の更新を早く失敗させる
- C. 導入コマンドの終了コードを `cfn-signal -e $?` で渡し、`CreationPolicy` のタイムアウト内にシグナルを受けるようにする

- A. ビルドのコマンドの中でレポートからカバレッジを計算し、基準未満なら 0 以外で終了する
- B. レポートの形式を JaCoCo XML から Cobertura XML へ変更して、判定の機能を使う

### 問19 {#q19}

監査の要件で、単体テストの結果を 1 年間保管します。CodeBuild のレポートグループには JUnit の結果を送っています。ところが、数か月前のレポートをコンソールで確認できなくなっていました。どう構成しますか。

- A. テストの結果を毎回 Parameter Store へ保存し、履歴を 1 年保持する
- B. ビルドログを CloudWatch Logs に残し、ログの保持期間を 1 年に設定する
