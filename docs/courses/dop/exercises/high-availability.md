# 高可用性の問題集

対象の解説: [高可用性](../../../services/resilience.md#patterns-by-service)

### 問1 {#q1}

社内の業務システムは東京リージョンだけで動かす規制があります。要件は AZ の障害でも数分以内に自動で復旧することで、リージョン障害は対象外です。費用は最小にします。Web 層は EC2、データは MySQL です。適切な構成はどれですか。

- A. 1 つの AZ の EC2 に Elastic IP を割り当て、障害時に手で付け替えて RDS のスナップショットから復元する
- B. 複数 AZ の Auto Scaling と ALB、RDS の Multi-AZ
- C. Aurora Global Database で別のリージョンにセカンダリを置いて、昇格の手順を自動化する
- D. 東京と大阪に同じ構成を置いて、Route 53 のフェイルオーバーで切り替える

??? success "答えと解説"
    **正解: B**

    Multi-AZ は多くの障害に効き、費用も小さく済みます。Multi-Region は明確な要件があるときに選びます。

    - A: 誤り。自動の復旧にならず、数分にも収まらない。
    - B: 正しい。
    - C: 誤り。リージョンをまたぐ構成は要件に合わず、費用も増える。
    - D: 誤り。規制に反し、対象外のリージョン障害の費用もかかる。

    **スキル:** [Multi-AZ と Multi-Region](../domain3.md#t3-1-multi-az-region) / **参照:** [サービスごとの Multi-AZ と Multi-Region](../../../services/resilience.md#patterns-by-service)

### 問2 {#q2}

次のサービスの可用性の設定を見直します。担当者が追加の対応を計画している中で、不要な作業はどれですか。（2つ選択）

- A. RDS の DB インスタンスの Multi-AZ を有効にする作業
- B. DynamoDB のテーブルを複数の AZ に広げる作業
- C. EC2 の Auto Scaling グループのサブネットを複数の AZ に広げる作業
- D. ECS のサービスのタスクを複数の AZ のサブネットに配置する作業
- E. Lambda の関数を複数の AZ に配置する作業（VPC 接続なし）

??? success "答えと解説"
    **正解: B, E**

    DynamoDB と Lambda は標準で複数 AZ で動きます。EC2、RDS、ECS は設定で分散します。

    - A: 誤り。既定で単一 AZ のことがあり、指定が必要。
    - B: 正しい。
    - C: 誤り。明示の指定が必要で、不要ではない。
    - D: 誤り。サブネットの指定が必要で、不要ではない。
    - E: 正しい。

    **スキル:** [Multi-AZ と Multi-Region](../domain3.md#t3-1-multi-az-region) / **参照:** [サービスごとの Multi-AZ と Multi-Region](../../../services/resilience.md#patterns-by-service)、[コンテナのマルチクラスター戦略](../../../services/resilience.md#multi-cluster)

### 問3 {#q3}

3 AZ で動く EC2 の Web アプリで、AZ 障害でもスケールの処理を待たずに容量を保ちます。必要な容量は 12 台です。Auto Scaling の最小台数はいくつにしますか。

- A. 14 台
- B. 12 台
- C. 18 台
- D. 36 台

??? success "答えと解説"
    **正解: C**

    残りの 2 AZ で 12 台なら AZ あたり 6 台で、合計 18 台です。

    - A: 誤り。AZ あたり端数になり、失った後に 12 台に届かない。
    - B: 誤り。AZ を 1 つ失うと 8 台になり、追加の起動を待つ必要がある。
    - C: 正しい。
    - D: 誤り。AZ あたり 12 台で、要件に対して過大な費用になる。

    **スキル:** [Multi-AZ と Multi-Region](../domain3.md#t3-1-multi-az-region) / **参照:** [静的安定性](../../../services/resilience.md#static-stability)、[高可用性のための Auto Scaling](../../../services/resilience.md#auto-scaling-ha)

### 問4 {#q4}

API のリクエストは、ALB、ECS、RDS の 3 つを順に通ります。それぞれの可用性を 99.9% とします。全体の可用性はおおよそいくつで、どう読みますか。

- A. 約 99.7%。依存先が直列に増えるほど下がる
- B. 99.9%。最も低い部品の値がそのまま全体の値になる
- C. 99.9999%。3 つが並列に働くので 1 - 0.1% の 3 乗になる
- D. 99.97%。部品が多いほど失敗の確率が分散されて上がる

??? success "答えと解説"
    **正解: A**

    直列は掛け算で、0.999 の 3 乗は約 99.7% です。

    - A: 正しい。
    - B: 誤り。直列は掛け算で、部品が増えるほど下がる。
    - C: 誤り。直列の構成に並列の式を使っている。
    - D: 誤り。直列では上がらない。

    **スキル:** [SLA](../domain3.md#t3-1-sla) / **参照:** [静的安定性](../../../services/resilience.md#static-stability)、[疎結合と耐障害性](../../../services/resilience.md#loose-coupling)

### 問5 {#q5}

2 つのリージョンで同じ API をアクティブ/アクティブで動かします。1 リージョンの可用性を 99.9% とし、どちらか一方で動けばよく、障害が独立であるとします。全体の可用性はおおよそいくつですか。

- A. 99.9999%
- B. 99.95%
- C. 99.8%
- D. 99.9%

??? success "答えと解説"
    **正解: A**

    並列は 1 - (0.001 × 0.001) で、99.9999% です。ただし、切り替えの仕組みなどの共通の依存先があれば、実際は下がります。

    - A: 正しい。
    - B: 誤り。計算の根拠がなく、式に合わない。
    - C: 誤り。直列の計算で、並列の構成に合わない。
    - D: 誤り。冗長の効果を計算していない。

    **スキル:** [SLA](../domain3.md#t3-1-sla) / **参照:** [静的安定性](../../../services/resilience.md#static-stability)

### 問6 {#q6}

ある担当者は、利用する AWS サービスの SLA が 99.99% なので、自社の API も障害時に自動で補償され、サービスの停止は年に 1 時間未満になると説明しました。正しい理解はどれですか。

- A. SLA は提供者の約束で、未達のときの補償はサービスクレジット。実際の稼働を保証しない
- B. SLA を満たせないときは、AWS が自社の利用者への補償を代行する
- C. SLA が高いサービスを使えば、冗長の設計やリトライの実装は不要になる
- D. SLA は Trusted Advisor の設定やサポートプランで、自社の要件に合わせて引き上げられる

??? success "答えと解説"
    **正解: A**

    SLA は実際の稼働を保証しません。全体の可用性は自社の設計で作ります。

    - A: 正しい。
    - B: 誤り。補償は AWS の利用者へのサービスクレジットで、自社の顧客への補償ではない。
    - C: 誤り。部品の障害に備える設計は利用者の責任。
    - D: 誤り。SLA は設定で変えるものではない。

    **スキル:** [SLA](../domain3.md#t3-1-sla) / **参照:** [RTO と RPO](../../../services/resilience.md#rto-rpo)

### 問7 {#q7}

経営層の要件は次のとおりです。「決済の記録は 1 件も失えない。AZ の障害では 2 分以内に再開する。リージョン全体の障害は想定しない」。技術的な要件と構成はどれですか。

- A. RPO 0、RTO 2 分。同期レプリケーションの RDS Multi-AZ
- B. RPO 0、RTO 24 時間。S3 への毎日のエクスポート
- C. RPO 数分、RTO 1 時間。別リージョンのリードレプリカの手動での昇格
- D. RPO 15 分、RTO 2 分。5 分間隔の AWS Backup と Lambda による復元

??? success "答えと解説"
    **正解: A**

    「1 件も失えない」は RPO 0 で、同期レプリケーションが必要です。

    - A: 正しい。
    - B: 誤り。毎日のエクスポートでは RPO 0 にならず、RTO も長すぎる。
    - C: 誤り。非同期でデータを失うおそれがあり、対象の障害も違う。
    - D: 誤り。復元に時間がかかり、データも失う。

    **スキル:** [ビジネス要件](../domain3.md#t3-1-business-requirements) / **参照:** [RTO と RPO](../../../services/resilience.md#rto-rpo)、[達成できるかの計算](../../../services/resilience.md#rto-rpo-budget)

### 問8 {#q8}

小売業の経営層は、リージョンが丸ごと使えなくなったときの要件を「1 時間以内にサービスを再開し、失うデータは 5 分以内にする。普段の費用はできるだけ抑える」としました。Aurora と EC2 で動いています。適切な構成はどれですか。

- A. パイロットライト。Aurora Global Database とコピー済みの AMI を用意する
- B. マルチサイトのアクティブ/アクティブ。両方のリージョンで全規模を動かし続ける
- C. バックアップと復元。夜間の AWS Backup のコピーだけを別リージョンに残して費用を最小にする
- D. 単一 AZ の構成で Route 53 のヘルスチェックを短くする

??? success "答えと解説"
    **正解: A**

    RTO 1 時間、RPO 数分はパイロットライトが目安です。データは複製し、コンピュートは止めておきます。

    - A: 正しい。
    - B: 誤り。費用を抑える条件に合わない。
    - C: 誤り。RPO の 5 分を満たせない。
    - D: 誤り。リージョン障害からの復旧にならない。

    **スキル:** [ビジネス要件](../domain3.md#t3-1-business-requirements) / **参照:** [RTO と RPO](../../../services/resilience.md#rto-rpo)、[パイロットライト](../../../services/resilience.md#pilot-light)

### 問9 {#q9}

複数のチームが RTO と RPO の目標を持ちます。アプリの構成を定期的に評価し、目標を満たすか、足りない構成は何かを、CloudFormation スタックを入力に確認します。どのサービスが最も適切ですか。

- A. FIS の実験テンプレート
- B. Trusted Advisor の耐障害性のチェック
- C. Compute Optimizer の推奨事項
- D. Resilience Hub

??? success "答えと解説"
    **正解: D**

    Resilience Hub はアプリの構成を評価し、RTO と RPO の目標を満たすかを示します。

    - A: 誤り。障害を注入する道具で、目標の評価の結果を出す機能ではない。
    - B: 誤り。目標の RTO と RPO に対する評価は行わない。
    - C: 誤り。サイズの最適化で、回復力の目標の評価ではない。
    - D: 正しい。

    **スキル:** [ビジネス要件](../domain3.md#t3-1-business-requirements) / **参照:** [AWS Resilience Hub](../../../services/resilience.md#resilience-hub)

### 問10 {#q10}

3 つの AZ のプライベートサブネットが、AZ-a の NAT ゲートウェイを 1 つ共有しています。AZ-a の障害で、他の AZ のインスタンスも外部の API を呼べなくなりました。適切な修正はどれですか。

- A. AZ ごとに NAT ゲートウェイを作り、AZ ごとのルートテーブルで同じ AZ へ向ける
- B. プライベートサブネットのインスタンスにパブリック IP を割り当て、NAT を介さず外へ直接出す
- C. NAT ゲートウェイのサイズを大きくして、帯域幅を増やす
- D. インターネットゲートウェイを AZ ごとに 1 つずつ VPC に追加する

??? success "答えと解説"
    **正解: A**

    NAT ゲートウェイは AZ のリソースです。AZ ごとに作り、ルートテーブルも分けます。

    - A: 正しい。
    - B: 誤り。ルートの変更とセキュリティの問題が残り、NAT の役割を置き換えられない。
    - C: 誤り。容量の問題ではなく、AZ への依存が残る。
    - D: 誤り。VPC にアタッチできるのは 1 つで、問題の原因でもない。

    **スキル:** [単一障害点](../domain3.md#t3-1-spof) / **参照:** [NAT ゲートウェイ](../../../services/network-connectivity.md#nat-gateway)

### 問11 {#q11}

EC2 の Web 層を増やしたところ、利用者のログイン状態が消える問題が起きました。セッションはサーバーのメモリにあります。スティッキーセッションを使っても、インスタンスの置き換えでログインが切れます。適切な修正はどれですか。

- A. インスタンスのメモリを増やして、セッションの保持の上限を上げる
- B. スティッキーセッションの期間を 7 日に延ばして、利用者を同じインスタンスへ送り続ける
- C. ALB のクロスゾーン負荷分散を有効にして、セッションを AZ 間で共有できるようにする
- D. セッションを ElastiCache か DynamoDB へ移し、サーバーをステートレスにする

??? success "答えと解説"
    **正解: D**

    サーバーの外にセッションを置けば、どのインスタンスでも処理できます。

    - A: 誤り。インスタンスの障害でセッションが消える問題は残る。
    - B: 誤り。インスタンスが消えるとセッションも失う。
    - C: 誤り。負荷分散の設定はセッションを共有しない。
    - D: 正しい。

    **スキル:** [単一障害点](../domain3.md#t3-1-spof) / **参照:** [ステートフルとステートレス](../../../services/sdk-resilience.md#stateful-stateless)、[ElastiCache](../../../services/databases.md#elasticache)

### 問12 {#q12}

既存のワークロードを確認したところ、次の点が見つかりました。単一障害点を解消する変更はどれですか。（2つ選択）

- A. 全インスタンスの EBS の種類を `gp3` へ変更する
- B. 1 台の EC2 の EBS で共有していたファイルを EFS へ移す
- C. CloudWatch の詳細モニタリングを有効にする
- D. VPN の 2 本のトンネルを両方とも使えるようルーターを設定する
- E. Multi-AZ の RDS のインスタンスクラスを大きくする

??? success "答えと解説"
    **正解: B, D**

    ファイルを 1 台に持つ構成と、1 本だけ使う VPN は単一障害点です。

    - A: 誤り。性能と費用の変更で、単一障害点の解消にならない。
    - B: 正しい。
    - C: 誤り。監視の粒度の変更で、障害点は残る。
    - D: 正しい。
    - E: 誤り。性能の変更で、すでに Multi-AZ の冗長の構成を変えない。

    **スキル:** [単一障害点](../domain3.md#t3-1-spof) / **参照:** [AWS Resilience Hub](../../../services/resilience.md#resilience-hub)、[比較](../../../services/storage.md#comparison)、[Site-to-Site VPN](../../../services/network-connectivity.md#site-to-site-vpn)

### 問13 {#q13}

Aurora のフェイルオーバーで、アプリの接続が切れ、再接続が一斉に発生してエラーが数分続きます。アプリの変更を最小にし、切り替えの間の接続を保ちたいと考えています。何を追加しますか。

- A. Lambda の Provisioned Concurrency を全関数に設定する
- B. ElastiCache の Global Datastore
- C. Route 53 のフェイルオーバーレコードと 60 秒の TTL

??? success "答えと解説"

    RDS Proxy は接続をプールし、フェイルオーバーの間の接続の切断を減らします。

    - A: 誤り。接続の管理に関係しない。
    - B: 誤り。キャッシュの複製で、データベース接続の切り替えを助けない。
    - C: 誤り。Aurora の切り替えはクラスターエンドポイントで行われ、接続の問題は残る。

    - A: 誤り。コントロールプレーンへの依存が残る。
    - B: 誤り。切り替えが遅くなり、逆効果。

### 問15 {#q15}

取引先がファイアウォールの許可リストに IP を登録するので、固定の IP が必要です。別のリージョンへの切り替えは DNS のキャッシュの影響を受けないようにします。また、AZ の異常なときは、その AZ への通信を素早く避けます。適切な組み合わせはどれですか。

- A. NLB の Elastic IP と Route 53 のフェイルオーバー、Auto Scaling の AZ の再分散
- B. ALB の DNS 名を取引先へ伝え、TTL を 5 秒に指定する
- C. CloudFront と Lambda@Edge、オリジングループ
- D. Global Accelerator と ARC のゾーンシフトを組み合わせる

??? success "答えと解説"
    **正解: D**

    - A: 誤り。IP がリージョンごとに変わり、DNS の影響も受ける。
    - B: 誤り。ALB の IP は変わり、許可リストの条件に合わない。
    - C: 誤り。固定の IP の要件を満たせない。
    - D: 正しい。

    **スキル:** [ダウンタイムを抑える](../domain3.md#t3-1-minimize-downtime) / **参照:** [Global Accelerator との比較](../../../services/resilience.md#global-accelerator)、[ゾーンシフトとオートシフト](../../../services/resilience.md#arc-zonal)
