### 問1 {#q1}

新規プロジェクトで、コード、コンテナイメージ、社内の Python パッケージの置き場所を決めます。条件は、コードレビューの標準に GitHub を使う、イメージのタグの上書きを防ぐ、PyPI からの取得元を一本化する、の 3 つです。適切な組み合わせはどれですか。

- A. GitHub、S3 のバージョニング付きバケット、社内の EC2 に立てた `devpi` にする
- B. CodeConnections で接続した GitHub、不変タグを有効にした ECR、外部接続を持つ CodeArtifact にする
- C. GitHub、タグを変更可能にした ECR、S3 に置いて毎週更新する `requirements.txt` と、社内の EC2 のミラーにする
- D. CodeCommit、ECR Public のリポジトリ、PyPI を開発者のマシンとビルドから直接使う構成にする

??? success "答えと解説"
    **正解: B**

    置くものごとに専用のサービスを選び、不変タグと外部接続で統制します。

    - A: 誤り。イメージの標準の置き場は ECR で、パッケージのために自前のサーバーを運用する必要はない。
    - B: 正しい。
    - C: 誤り。タグの上書きを防げず、パッケージの取得元も統制できない。
    - D: 誤り。GitHub の条件に反し、社内のイメージを公開し、取得元も統制できない。

    **スキル:** [リポジトリ](../domain1.md#t1-1-repositories) / **参照:** [CodeCommit の現状](../../../services/cicd.md#codecommit-status)、[デプロイ環境でコードリポジトリを使う](../../../services/cicd.md#repositories)、[ECR](../../../services/containers.md#ecr)

### 問2 {#q2}

東京とフランクフルトの ECS で同じイメージを動かします。フランクフルトのタスクの起動が遅く、リージョン間のデータ転送の費用もかかっています。イメージは東京の CodeBuild で作ります。パイプラインの変更は最小にします。どうしますか。

- A. フランクフルトにも同じ CodeBuild を作り、同じコミットから別々にイメージをビルドする
- B. ECR Public へプッシュして、両方のリージョンから公開リポジトリを取得する
- C. 東京の ECR にクロスリージョンレプリケーションのルールを設定し、タスク定義はフランクフルトのリポジトリを指す
- D. フランクフルトのタスクを Fargate から EC2 へ変え、東京から取得したイメージをインスタンスにキャッシュする

??? success "答えと解説"
    **正解: C**

    ECR のレプリケーションなら、プッシュの後に自動でコピーされます。タスクは同じリージョンから取得できます。

    - A: 誤り。パイプラインの変更が大きく、ビルドが別になるので同じイメージの保証もない。
    - B: 誤り。社内のイメージを公開することになり、適切でない。
    - C: 正しい。
    - D: 誤り。起動の遅さの原因である転送の距離は残り、運用も増える。

    **スキル:** [リポジトリ](../domain1.md#t1-1-repositories) / **参照:** [レプリケーション](../../../services/containers.md#ecr-replication)、[ECR](../../../services/containers.md#ecr)

- B. CodeCommit は読み取り専用になったので、GitHub へすぐに移行する必要がある

### 問4 {#q4}

本番の ECS タスクが `app:latest` を参照しています。ある日、誰かが同じタグで別のイメージをプッシュし、スケールアウトで起動した新しいタスクだけ動作が変わりました。再発を防ぎ、脆弱なイメージの配布も止めたいと考えています。適切な対応はどれですか。（2つ選択）

- A. ECS サービスの `forceNewDeployment` を毎日実行して、全タスクを同じイメージに揃える
- B. Inspector の拡張スキャンの結果をパイプラインで判定し、重大な脆弱性があれば次へ進めない
- C. ECR のタグを不変にし、タスク定義はダイジェストかバージョンのタグで参照する
- D. `latest` をプッシュできる IAM ユーザーを 1 人に限定し、タグの変更を手順書で管理する
- E. ECR のライフサイクルポリシーで古いイメージを毎日削除し、`latest` だけを残す

??? success "答えと解説"
    **正解: B, C**

    タグの上書きは不変タグとダイジェストで防ぎます。スキャンの結果をパイプラインで判定すれば、配布の前に止められます。

    - A: 誤り。揃うだけで、意図しないイメージを防げない。
    - B: 正しい。
    - C: 正しい。
    - D: 誤り。人の運用に頼り、誤りを機械的に防げない。
    - E: 誤り。タグの上書きは防げず、ロールバック先も失う。

    **スキル:** [用途と安全な管理](../domain1.md#t1-3-security) / **参照:** [タグと不変タグ](../../../services/containers.md#image-tags)、[イメージスキャン](../../../services/containers.md#ecr-scanning)

### 問5 {#q5}

金融機関の方針で、セキュリティチームが承認していないコードの Lambda へのデプロイを、技術的に拒否する必要があります。関数は複数のパイプラインから更新されます。パイプラインの権限を持つ人が別の ZIP を直接アップロードしても拒否します。何を使いますか。

- A. Signer の署名プロファイルと、関数のコード署名設定で、署名されていないデプロイを拒否する
- B. デプロイの後に Config のカスタムルールでハッシュを照合し、不一致なら通知する
- C. S3 のバケットポリシーで ZIP の置き場所を限定して、KMS で暗号化する
- D. `lambda:UpdateFunctionCode` を持つロールを 1 つにまとめ、パイプラインだけが使えるようにする

??? success "答えと解説"
    **正解: A**

    コード署名を強制すると、信頼する署名プロファイルで署名されていないコードのデプロイが失敗します。

    - A: 正しい。
    - B: 誤り。検出だけで、デプロイそのものを拒否できない。
    - C: 誤り。直接のアップロードは S3 を通らないので拒否できない。
    - D: 誤り。そのロールを使える人は別の ZIP を上げられる。

    **スキル:** [用途と安全な管理](../domain1.md#t1-3-security) / **参照:** [コード署名](../../../services/lambda.md#code-signing)

- A. 開発者のマシンに公開レジストリのミラーのリストを配布して、毎週手で更新する

CodeBuild のプロジェクトを Lambda コンピュートへ移すことを検討しています。ビルドの内容は次の 3 つです。(1) 3 分の Node.js のパッケージ作成、(2) `docker build`、(3) VPC の中のデータベースに接続するテスト。キュー待ちを減らしつつ全部を動かすには、どう分けますか。

- A. 3 つとも EC2 コンピュートのままにし、Lambda コンピュートは使わない
- B. 3 つとも Lambda コンピュートにまとめ、メモリを最大にして実行する
- C. (1) を Lambda コンピュートに、(2) と (3) を EC2 コンピュートのプロジェクトに分ける

### 問8 {#q8}

社内の複数アカウントで使うサーバーレスアプリを、版を付けて再利用できるように公開します。依存関係の解決とパッケージ作成もパイプラインで自動化します。どのコマンドの流れが適切ですか。

- A. `sam local invoke`、`sam sync --watch` の順で各アカウントのスタックを更新する
- B. `zip`、`aws lambda publish-layer-version` の順でレイヤーとして配布する
- C. `sam build`、`sam package`、`sam publish` の順で Serverless Application Repository に公開する

### 問10 {#q10}

ECR の費用が増えています。開発用のタグ（`dev-` で始まる）は最新 20 個だけ残し、タグのないイメージは 7 日で消します。本番のタグ（`prod-` で始まる）は、ロールバックのために消しません。適切なライフサイクルポリシーはどれですか。

- A. `imageCountMoreThan` 20 のルールをタグの条件なしで 1 つ作り、`prod-` のイメージは別のリポジトリへ複製して残す
- B. `dev-` のプレフィックスに `imageCountMoreThan` 20、`untagged` に `sinceImagePushed` 7 日を置く
- C. ライフサイクルポリシーは使わず、毎週の Lambda で ECR のタグの条件を判定し、`batch-delete-image` を実行する

    ルールごとに対象のタグの条件と保持の条件を指定します。`prod-` を対象にしなければ削除されません。

    - A: 誤り。同じリポジトリの `prod-` のイメージも消え、複製の運用も増える。
    - B: 正しい。
    - C: 誤り。マネージドの機能で足りるのに、自前の運用が増える。

### 問11 {#q11}

- A. S3 はストレージクラスを Glacier Deep Archive へ即時に移し、Beanstalk はアプリケーションを作り直してバージョンを空にする
