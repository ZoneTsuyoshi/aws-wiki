### 問1 {#q1}

EC2 の Web アプリを更新します。条件は次のとおりです。追加の EC2 の費用はかけない、更新中も容量の一部で応答する、夜間のバッチへの影響はない、切り戻しは再デプロイでよい。CodeDeploy の設定として最も適切なものはどれですか。

- A. Lambda の `LambdaCanary10Percent5Minutes` を EC2 のデプロイグループのデプロイ設定に指定する
- B. インプレースの `CodeDeployDefault.AllAtOnce` で全台を同時に更新する
- C. Blue/Green で新しいインスタンスを全台作り、ALB で切り替える
- D. インプレースのローリングで `CodeDeployDefault.OneAtATime` か `HalfAtATime` を使う

??? success "答えと解説"
    **正解: D**

    追加費用なしで止めずに更新するならローリングです。切り戻しは再デプロイになります。

    - A: 誤り。Lambda 用の設定で、EC2 には使えない。
    - B: 誤り。更新中に全台が止まるおそれがあり、応答を続けられない。
    - C: 誤り。両方の環境の費用が一時的にかかる。
    - D: 正しい。

    **スキル:** [デプロイ戦略の判断](../domain1.md#t1-1-deployment-strategy) / **参照:** [デプロイ戦略の比較](../../../services/cicd.md#deployment-strategies)

### 問2 {#q2}

決済 API を Lambda で動かしています。新しい版を一部の利用者で実データを使って 10 分確認し、問題がなければ全体へ切り替えます。エラーが増えたら即座に戻し、人は介在しません。どの方式を選びますか。

- A. CodeDeploy のカナリア（`LambdaCanary10Percent10Minutes`）と自動ロールバック
- B. 関数の `$LATEST` を更新し、API Gateway のステージを再デプロイして全体を切り替える
- C. 新しい関数を作り、Route 53 の重み付けで DNS を 10% ずつ切り替える
- D. CodeDeploy の一括（`LambdaAllAtOnce`）とデプロイ後のテストを実行し、失敗なら手で戻す

??? success "答えと解説"
    **正解: A**

    一部で確認してから全体へ移すのがカナリアです。アラームで自動ロールバックを設定します。

    - A: 正しい。
    - B: 誤り。段階的な切り替えとロールバックの仕組みがない。
    - C: 誤り。DNS のキャッシュで戻すのが遅く、関数のエイリアスの機能も使わない。
    - D: 誤り。全利用者へ一度に切り替わり、人の確認も必要になる。

    **スキル:** [デプロイ戦略の判断](../domain1.md#t1-1-deployment-strategy) / **参照:** [デプロイ戦略の比較](../../../services/cicd.md#deployment-strategies)、[デプロイ設定](../../../services/cicd.md#deployment-configs)

### 問3 {#q3}

開発環境、検証環境、本番環境で方式を決めます。開発は速さが最優先で短い停止を許容します。本番は切り戻しを 1 分以内にして、2 環境の費用を許容します。適切な組み合わせはどれですか。

- A. 開発はインプレースの一括、本番は Blue/Green にする
- B. 開発は線形、本番はカナリアで数時間かけて段階的に切り替える
- C. 開発はローリング、本番はローリングの追加バッチにする
- D. 開発は Blue/Green で 2 環境を動かし、本番はインプレースの一括にする

??? success "答えと解説"
    **正解: A**

    条件を「ダウンタイム、戻す速さ、追加コスト」で比べます。切り替え先を保つ Blue/Green は戻すのが速い方式です。

    - A: 正しい。
    - B: 誤り。開発には過剰で、本番の条件の切り戻しの速さも担保していない。
    - C: 誤り。本番の切り戻しは再デプロイになり、1 分以内に収まらない。
    - D: 誤り。速さと切り戻しの条件が逆になっている。

    **スキル:** [デプロイ戦略の判断](../domain1.md#t1-1-deployment-strategy) / **参照:** [デプロイ戦略の比較](../../../services/cicd.md#deployment-strategies)、[RTO と RPO](../../../services/resilience.md#rto-rpo)

### 問4 {#q4}

Elastic Beanstalk の本番環境を更新します。条件は次のとおりです。更新の失敗が既存のインスタンスに影響しない、一時的な新しいインスタンスは許容する、一部のリクエストを新しい版で先に試す必要はない。最も適切なポリシーはどれですか。

- A. イミュータブル
- B. ローリング
- C. 追加バッチによるローリング
- D. トラフィック分割

??? success "答えと解説"
    **正解: A**

    イミュータブルは新しい Auto Scaling グループのインスタンスで検証してから入れ替えるので、失敗しても既存に影響しません。

    - A: 正しい。
    - B: 誤り。既存のインスタンスを順に更新するので、失敗が既存のインスタンスに影響する。
    - C: 誤り。既存のインスタンスも順に更新され、失敗の影響が既存に及ぶ。
    - D: 誤り。動くが、一部のリクエストで試す機能が要件にない。費用も増える。

    **スキル:** [デプロイ方式](../domain1.md#t1-4-methods) / **参照:** [デプロイポリシー](../../../services/ec2-beanstalk.md#deployment-policies)、[不変デプロイの流れ](../../../services/ec2-beanstalk.md#immutable)

### 問5 {#q5}

SAM で管理する Lambda を、10 分ごとに 10% ずつ切り替えます。切り替え前に検証用の関数を実行し、切り替え中にエラーのアラームが鳴れば自動で戻します。SAM テンプレートでの指定として正しいものはどれですか。

- A. `AutoPublishAlias` と、`DeploymentPreference` の `Type: Linear10PercentEvery10Minutes`、`Hooks.PreTraffic`、`Alarms` を指定する
- B. `DeploymentPreference` の `Type: Canary10Percent10Minutes` と `Hooks.PostTraffic` だけを指定する
- C. API Gateway のステージの `CanarySetting` で 10% を指定し、ステージ変数で関数を切り替える
- D. `AutoPublishAlias` を省略して `$LATEST` に `DeploymentPreference` を指定する

??? success "答えと解説"
    **正解: A**

    SAM では `AutoPublishAlias` と `DeploymentPreference` で、線形の移行とフック、アラームを指定します。

    - A: 正しい。
    - B: 誤り。カナリアは 2 段階で、10% ずつの線形ではない。切り替え前の検証も入らない。
    - C: 誤り。ステージのカナリアには自動のロールバックや段階の増加がない。
    - D: 誤り。トラフィックの移行にはエイリアスと版が必要。

    **スキル:** [デプロイ方式](../domain1.md#t1-4-methods) / **参照:** [DeploymentPreference によるカナリア](../../../services/iac.md#deployment-preference)、[トラフィックの分割](../../../services/lambda.md#alias-routing)

### 問6 {#q6}

CMS を EC2 の Auto Scaling グループで動かしています。利用者がアップロードした画像は各インスタンスの EBS にあり、イミュータブルな更新のたびに失われます。アプリは POSIX のファイルパスで読み書きし、コードを変更できません。複数 AZ で動かし続けます。どの置き場所に変えますか。

- A. EFS を複数の AZ にマウントする
- B. 各インスタンスのインスタンスストアに置き、起動時に他のインスタンスから同期する
- C. EBS のマルチアタッチで全インスタンスに同じボリュームを接続する
- D. S3 に移して、アプリの保存処理を SDK の呼び出しへ変更する

??? success "答えと解説"
    **正解: A**

    コードを変えずに複数 AZ の複数インスタンスで共有するなら EFS です。インスタンスを入れ替えてもデータが残ります。

    - A: 正しい。
    - B: 誤り。停止や終了で消え、同期の仕組みも自作になる。
    - C: 誤り。同じ AZ に限られ、対応するファイルシステムの制約もある。
    - D: 誤り。コードの変更が必要で、条件に合わない。

    **スキル:** [ストレージパターン](../domain1.md#t1-4-storage) / **参照:** [比較](../../../services/storage.md#comparison)、[EFS を Lambda とコンテナで使う](../../../services/storage.md#efs)

### 問7 {#q7}

単一の EC2 で動くデータベースサーバーの更新で、インスタンスの入れ替え方式を採用します。データは EBS にあり、1 つの AZ で動いています。新しいインスタンスを別の AZ で起動すると、古いボリュームを接続できず失敗しました。適切な対応はどれですか。

- A. ボリュームを別の AZ へ `modify-volume` で移動する
- B. スナップショットを作り、新しい AZ でボリュームを復元して接続する
- C. ALB のクロスゾーン負荷分散を有効にして、別の AZ からボリュームを読めるようにする
- D. ボリュームをインスタンスストアへコピーしてから、新しいインスタンスへ接続する

??? success "答えと解説"
    **正解: B**

    EBS は AZ のリソースです。別の AZ へはスナップショット経由で移します。

    - A: 誤り。`modify-volume` はサイズや種類の変更で、AZ を移せない。
    - B: 正しい。
    - C: 誤り。負荷分散の設定は EBS の接続に関係がない。
    - D: 誤り。インスタンスストアはインスタンスの入れ替えで消え、付け替えもできない。

    **スキル:** [ストレージパターン](../domain1.md#t1-4-storage) / **参照:** [ボリュームの変更と AZ の制約](../../../services/storage.md#ebs-modify)、[比較](../../../services/storage.md#comparison)

### 問8 {#q8}

画像の変換の処理を EC2 から Lambda へ移します。元の画像は Web から直接アップロードされ、1 ファイル最大 2 GB で、変換のあとも永続します。変換の途中の一時ファイルは、複数の関数で共有しません。アプリの配置を変えても保存先は変えないことが条件です。適切な構成はどれですか。

- A. 元の画像と変換後の画像は S3 に置き、一時ファイルは関数の `/tmp` のエフェメラルストレージを使う
- B. 元の画像をコンテナイメージに含めて、変換のたびに関数を再デプロイする
- C. 元の画像と変換後の画像を関数の `/tmp` に 10 GB まで置き、関数のバージョンごとに管理する
- D. EBS のボリュームを関数にアタッチして、すべてのファイルを置く

??? success "答えと解説"
    **正解: A**

    アップロードや永続のデータは S3 が向きます。共有しない一時ファイルはエフェメラルストレージで足ります。

    - A: 正しい。
    - B: 誤り。アップロードされるデータの置き場に使えない。
    - C: 誤り。`/tmp` は実行環境に紐づき、永続しない。
    - D: 誤り。Lambda に EBS は接続できない。

    **スキル:** [ストレージパターン](../domain1.md#t1-4-storage) / **参照:** [Event Notifications](../../../services/s3.md#event-notifications)、[エフェメラルストレージ](../../../services/lambda.md#ephemeral-storage)

### 問9 {#q9}

毎月の OS 更新を Run Command で稼働中のサーバーへ適用しています。サーバーごとに状態の差が生まれ、再現しない障害が続いています。更新の失敗時は既存のサーバーを壊さず戻したいと考えています。運用の手間も減らします。どう変えますか。

- A. サーバーの中で毎晩 `yum update` を cron で実行し、常に最新に保つ
- B. Run Command の `MaxConcurrency` を 1 にして、1 台ずつ確認しながら適用する
- C. State Manager で毎時間 `yum update` を適用し、差を検出したら SSH で手当てする
- D. AMI を作ってインスタンスの更新で入れ替えるイミュータブルな方式に変える

??? success "答えと解説"
    **正解: D**

    新しいものを作って入れ替えれば、構成のずれが起きにくく、失敗しても古いものへ戻せます。

    - A: 誤り。実行のタイミングの差で状態が揃わず、失敗の影響も既存のサーバーに及ぶ。
    - B: 誤り。更新の順番が変わるだけで、差は残る。
    - C: 誤り。動いているサーバーを直接更新する方式のままで、手間も減らない。
    - D: 正しい。

    **スキル:** [ミュータブルとイミュータブル](../domain1.md#t1-4-mutable-immutable) / **参照:** [不変デプロイの流れ](../../../services/ec2-beanstalk.md#immutable)、[インスタンスの更新](../../../services/operations.md#instance-refresh)

### 問11 {#q11}

セキュリティチームが、自社製の監視エージェントの新しいバージョンを 5,000 台の EC2 とオンプレミスのサーバーへ配布し、バージョンを管理して、新しいサーバーにも自動で入れたいと考えています。アプリのデプロイの仕組みは変えません。何を使いますか。

- A. CodeDeploy のアプリケーションとして登録し、全サーバーを 1 つのデプロイグループに入れる

    - D: 正しい。

??? success "答えと解説"
    **正解: D**

    エージェントは CodeDeploy へ外向きの HTTPS で接続します。受信の許可は要りません。

    - A: 誤り。エージェントが外へ接続する方式で、受信は不要。
    - B: 誤り。デプロイのイベントが始まる前の接続エラーで、タイムアウトでは直らない。
    - C: 誤り。ALB はエージェントの通信経路にならない。
    - D: 正しい。

    **スキル:** [エージェント](../domain1.md#t1-4-agents) / **参照:** [CodeDeploy エージェント](../../../services/cicd.md#codedeploy-agent)、[VPC エンドポイントと PrivateLink](../../../services/networking.md#vpc-endpoints)

### 問16 {#q16}

新しい基盤を設計中です。Lambda、Fargate の ECS、EC2、オンプレミスのサーバーに CodeDeploy でデプロイします。エージェントの導入と更新の作業を見積もるとき、対象に含める組み合わせはどれですか。

- A. 4 つすべて
- B. Fargate の ECS と EC2 だけ
- C. EC2 とオンプレミスのサーバーだけ
- D. Lambda と Fargate の ECS だけ

??? success "答えと解説"

    エージェントが要るのは EC2 とオンプレミスだけです。

    - B: 誤り。ECS には要らず、オンプレミスには要る。
    - C: 正しい。

### 問17 {#q17}

EC2 の CodeDeploy で、前回の版のデプロイは成功していましたが、今回は `ApplicationStop` で失敗します。今回のリビジョンのスクリプトは直してあるのに、何度実行しても同じ失敗です。原因と対処はどれですか。

- A. ターゲットグループのヘルスチェックが失敗しているので、パスを修正してから同じリビジョンを再デプロイする
- B. `ApplicationStop` は前回の成功した版のスクリプトで動く。`--ignore-application-stop-failures` で再デプロイするか、前回のスクリプトを直す
- C. `ApplicationStop` は今回のリビジョンの `appspec.yml` で動くので、`files` の配置先の指定を直す
- D. 今回のリビジョンのスクリプトを取得できていないので、インスタンスプロファイルに S3 の権限を追加する

??? success "答えと解説"
    **正解: B**

    `ApplicationStop` は前回の版のスクリプトで動くので、今回のリビジョンの修正は効きません。

    - A: 誤り。ヘルスチェックの問題なら `AllowTraffic` で失敗する。
    - B: 正しい。
    - C: 誤り。`ApplicationStop` はリビジョンを取得する前のイベントで、前回の版のスクリプトで動く。
    - D: 誤り。権限不足なら `DownloadBundle` で失敗する。

### 問18 {#q18}

Blue/Green の EC2 デプロイで、新しいインスタンスへの全イベントは成功するのに、`AllowTraffic` で失敗してデプロイが戻ります。アプリのログにはリクエストが届いていません。何を調べますか。

- A. リビジョンのある S3 バケットのポリシーと、KMS のキーポリシー
- B. デプロイグループのインスタンスのタグと、エージェントのバージョン
- C. ターゲットグループのヘルスチェックのパスとポート、インスタンスのセキュリティグループ
- D. `appspec.yml` の `files` の宛先と、`ApplicationStart` のスクリプトの権限

??? success "答えと解説"
    **正解: C**

    `AllowTraffic` の失敗はターゲットグループのヘルスチェックが典型です。リクエストが届かないならポートとセキュリティグループを確認します。

    - A: 誤り。`DownloadBundle` の問題で、すでに通過している。
    - B: 誤り。対象の選定とエージェントが問題なら、前のイベントが実行されない。
    - C: 正しい。
    - D: 誤り。`AllowTraffic` の前の工程で、すでに成功している。
