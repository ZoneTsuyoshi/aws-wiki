### 問1 {#q1}

決済会社が、SQS 標準キューと Lambda で入金通知を処理しています。入金元のゲートウェイは、応答が遅れると同じ通知を最大 6 時間後に再送します。ピーク時は毎秒 8,000 件で、順序は問いません。二重の入金処理を確実に防ぎつつ、処理量を落とさない設計はどれですか。

- A. キューを FIFO に変更し、コンテンツベースの重複排除を有効にして、再送された通知をキューの段階で取り除く
- B. 通知 ID を DynamoDB へ条件付きで書き込み、既に存在すれば以降の処理を飛ばして成功とする
- C. キューの可視性タイムアウトを 6 時間より長くし、同じ通知が別の Lambda に渡らないようにする
- D. Lambda の予約済み同時実行を 1 にして、通知を 1 件ずつ順番に処理するようにする

??? success "答えと解説"
    **正解: B**

    再送の間隔が重複排除の時間枠より長いので、処理側を冪等にします。冪等キーの条件付き書き込みが定番です。

    - A: 誤り。FIFO の重複排除の時間枠は 5 分で、6 時間後の再送を取り除けない。
    - B: 正しい。
    - C: 誤り。可視性タイムアウトは同じメッセージの再配信を遅らせるだけで、別のメッセージとして送られた再送には効かない。
    - D: 誤り。処理量が大きく落ちるうえ、再送そのものは防げない。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [冪等性](../../../services/sdk-resilience.md#idempotency)

### 問2 {#q2}

小売の注文イベントを、請求、分析、不正検知の 3 チームが別々に読みます。同じ顧客の注文は発生順に処理する必要があり、分析チームは障害のあとで直近 3 日分を読み直すことがあります。顧客の数は多く、全体のスループットも確保したいです。どの構成が要件に最も合いますか。

- A. EventBridge のカスタムバスにアーカイブを設定し、各チームのルールへ配信して、必要なときにリプレイする
- B. SQS FIFO キューを 1 つ作ってメッセージグループ ID を顧客 ID にし、3 チームのコンシューマーで同じキューを読む
- C. Kinesis Data Streams で、すべてのレコードに同じパーティションキーを指定して全件の順序を保つ
- D. Kinesis Data Streams で、パーティションキーを顧客 ID にする

??? success "答えと解説"
    **正解: D**

    シャード内で順序が保たれ、複数のコンシューマーが保持期間内のデータを読み直せます。顧客 ID をキーにすると並列度も保てます。

    - A: 誤り。EventBridge は順序を保証しない。
    - B: 誤り。キューから削除すると読み直せず、同じキューを 3 チームで読むと 1 件を取り合う。
    - C: 誤り。同じキーは 1 つのシャードに集まり、並列度が 1 になる。
    - D: 正しい。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [パーティションキー](../../../services/streaming.md#partition-key)

### 問3 {#q3}

SQS FIFO キューで、全メッセージに同じ `MessageGroupId` を付けて送っています。業務上の順序が必要なのは口座の単位だけです。コンシューマーを 20 台に増やしましたが、処理が追いつかず、バックログが増え続けています。順序の要件を保ったまま処理量を増やすには、どうしますか。

- A. 標準キューに切り替えて、Lambda のイベントソースマッピングの同時実行数を増やす
- B. `MessageGroupId` を口座 ID に変え、口座の単位で順序を保って並列に処理する
- C. 可視性タイムアウトを短くして、処理中のメッセージを別のコンシューマーがすぐに受け取れるようにする
- D. コンシューマーをさらに増やし、ロングポーリングの待ち時間を 20 秒にして受信の回数を減らす

??? success "答えと解説"
    **正解: B**

    同じメッセージグループのメッセージは 1 件ずつ処理されるので、グループが 1 つなら並列度は 1 です。順序の単位をグループ ID にします。

    - A: 誤り。標準キューは順序がベストエフォートになり、要件を満たさない。
    - B: 正しい。
    - C: 誤り。同じメッセージの重複処理が増えるだけで、並列度は上がらない。
    - D: 誤り。グループが 1 つのままなので、台数を増やしても並列に処理されない。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [標準と FIFO](../../../services/messaging.md#standard-fifo)

### 問4 {#q4}

受注イベントを在庫、配送、不正検知の 3 システムへ配ります。各システムは自分のペースで処理し、1 つが停止しても他に影響させません。不正検知には金額が 10 万円以上のイベントだけを渡します。送信側のコードは変更を最小にします。必要な設計を選んでください。（2つ選択）

- A. SNS トピックを 1 つ作り、各システム専用の SQS キューを購読させる
- B. 1 つの SQS キューを 3 システムのコンシューマーで共有し、対象外のメッセージは受信後に捨てる
- C. 不正検知の購読にフィルターポリシーを設定する
- D. 送信側の Lambda が 3 システムの API を順に同期で呼び、失敗したら全体を再試行する

### 問5 {#q5}

EC 事業者の Web 層は、Auto Scaling グループの EC2 上で動いています。カートをインスタンスのメモリに置き、ALB のスティッキーセッションを使っています。スケールインや AZ 障害のたびにカートが消え、売上の損失になっています。カートは数日間保持し、AZ 障害でも失わない必要があります。サーバー管理は増やしたくありません。どの変更が最も適切ですか。

- A. スティッキーセッションの期間を 7 日に延ばす
- B. ElastiCache for Memcached に移し、ノードを複数の AZ に分散して配置する
- C. カートを DynamoDB に保存し、TTL で期限切れの項目を消す
- D. ライフサイクルフックで、終了するインスタンスのカートを別のインスタンスへコピーしてからスケールインする

    - B: 誤り。Memcached にはレプリケーションがなく、ノードの障害でデータが失われる。
    - C: 正しい。
    - D: 誤り。AZ 障害のような突然の停止には間に合わず、独自の仕組みの運用も増える。

### 問6 {#q6}

- A. ECS のタスク保護を常に有効にし、処理中のタスクがスケールインで止まらないようにする
- B. EFS をタスクにマウントし、ファイルと進行状況を共有のファイルに書き込んで、各タスクがロックを取りながら処理する

### 問13 {#q13}

開発チームは Python に習熟し、業務ロジックのほとんどを Lambda に書いています。注文のフローでは、支払いの完了を最長 7 日待ち、その間に途中で障害が起きても、完了済みの段階を再実行せずに続きから再開したいです。待機中のコンピューティング料金は払いたくなく、処理は普段の開発ツールとテストで扱いたいと考えています。何を選びますか。

### 問14 {#q14}

注文、決済、配送はマイクロサービスに分かれ、データベースも Aurora と DynamoDB で別々です。配送の手配が失敗したら、確定済みの決済と在庫の引き当てを取り消す必要があります。途中の状態を追跡でき、独自の調整サーバーは置きたくありません。どの設計が最も適切ですか。

- B. 配送の手配が成功するまで無制限に再試行し、取り消しは発生させない

- A. 各メンバーアカウントのルールに、監査と SOC の両方のバスをターゲットとして設定する
