# ネットワークアーキテクチャの問題集

対象の解説: [ネットワーク接続](../../../services/network-connectivity.md)、[ネットワークと配信](../../../services/networking.md)

### 問1 {#q1}

グローバルな製造業は、7 つのリージョンに数百の VPC とオンプレミス拠点を持ちます。本番、開発、共有サービスのセグメントを全リージョンで統一し、ネットワークの変更を中央のポリシーで管理したいです。リージョンごとの Transit Gateway のピアリングとルートの管理が負担になっています。どれが最も適切ですか。

- A. Cloud WAN のコアネットワークを作り、セグメントを中央のポリシーで定義する
- B. Transit Gateway をリージョンごとに増やし、ピアリングの経路を Lambda で同期する
- C. VPC ピアリングを全 VPC の間にフルメッシュで張る
- D. VPC Lattice のサービスネットワークをリージョンごとに作り、全 VPC を関連付ける

??? success "答えと解説"
    **正解: A**

    Cloud WAN は中央のポリシーでコアネットワークとセグメントを管理します。多数のリージョンで統一するときに向きます。

    - A: 正しい。
    - B: 誤り。ルートの管理の負担を減らせず、独自の仕組みが増える。
    - C: 誤り。数百の VPC では接続の数が膨大で、セグメントの管理もできない。
    - D: 誤り。サービスの接続の仕組みで、オンプレミスを含むネットワーク全体のセグメンテーションではない。

    **スキル:** [1.4.1](../domain1.md#skill-1-4-1) / **参照:** [Cloud WAN](../../../services/network-connectivity.md#cloud-wan)

### 問2 {#q2}

SaaS の事業者が、1 つの API を数百の顧客の VPC へ公開します。顧客の VPC の CIDR は事業者の VPC と重複することがあり、通信は顧客から事業者への一方向だけです。顧客の他のリソースへ経路を作りたくありません。どれを選びますか。

- A. 顧客の VPC と VPC ピアリングを張る
- B. NLB の背後に PrivateLink のエンドポイントサービスを作る
- C. 顧客の VPC を Transit Gateway に接続し、ルートテーブルで分離する
- D. 顧客の VPC の間にサイト間 VPN を張り、経路を限定する

??? success "答えと解説"
    **正解: B**

    PrivateLink は 1 つのサービスを一方向で公開でき、CIDR の重複も問題になりません。

    - A: 誤り。CIDR が重複すると作れない。
    - B: 正しい。
    - C: 誤り。CIDR の重複で経路を作れず、顧客の接続の管理も増える。
    - D: 誤り。CIDR の重複に対応できず、VPN の運用も増える。

    **スキル:** [1.4.1](../domain1.md#skill-1-4-1) / **参照:** [VPC エンドポイントと PrivateLink](../../../services/networking.md#vpc-endpoints)

### 問3 {#q3}

組織のネットワークチームが、VPC、サブネット、ルートテーブルを一元管理します。各アプリのチームは自分のアカウントで EC2 や RDS を動かし、費用も自分のアカウントで持ちますが、ネットワークの設定は変更させません。VPC の数は最小にしたいです。どれを選びますか。

- A. 各チームのアカウントに VPC を作り、SCP でルートテーブルの変更を拒否して、Transit Gateway で接続する
- B. ネットワークチームのアカウントでアプリのリソースをすべて動かす
- C. VPC のサブネットを RAM で共有する
- D. VPC ピアリングで、ネットワークチームの VPC と各チームの VPC を接続する

??? success "答えと解説"
    **正解: C**

    VPC 共有では、所有者がサブネットを管理し、参加者は共有されたサブネットに自分のリソースを作ります。

    - A: 誤り。動くが、VPC の数が減らない。
    - B: 誤り。リソースと費用が各チームのアカウントに分かれない。
    - C: 正しい。
    - D: 誤り。VPC の数が減らず、管理の一元化にもならない。

    **スキル:** [1.4.1](../domain1.md#skill-1-4-1) / **参照:** [VPC サブネットの共有](../../../services/governance.md#ram-vpc-sharing)

### 問4 {#q4}

3 つの VPC（A、B、C）があり、将来も増える予定はありません。A と B、B と C はピアリング済みですが、A から C へ通信できません。通信量は少なく、すべて同じリージョンで、費用を最小にします。どう対処しますか。

- A. B のルートテーブルに A と C の経路を追加し、B を経由させる
- B. Transit Gateway を作り、3 つの VPC を接続する
- C. B の EC2 に NAT のインスタンスを置き、A と C の通信を中継する
- D. A と C の間にピアリングを追加する

??? success "答えと解説"
    **正解: D**

    ピアリングは推移的にルーティングできません。数が少なければ、直接のピアリングが最小の費用です。

    - A: 誤り。推移的なルーティングはできない。
    - B: 誤り。動くが、接続とデータ処理の料金がかかる。
    - C: 誤り。単一障害点と運用が増え、費用もかかる。
    - D: 正しい。

    **スキル:** [1.4.1](../domain1.md#skill-1-4-1) / **参照:** [VPC ピアリング](../../../services/network-connectivity.md#vpc-peering)

### 問5 {#q5}

M&A により、CIDR の重複が接続の障害になっています。今後は組織全体で重複を防ぎ、OU やリージョンごとに割り当てを管理します。各チームが VPC を作るときも、割り当てられた範囲から自動で取得させます。どれを選びますか。

- A. スプレッドシートで範囲を管理し、VPC の作成時に申請と承認を行う
- B. Config のルールで VPC の CIDR を検査し、重複があれば通知する
- C. 全 VPC に同じ CIDR を割り当てて、PrivateLink だけで接続する
- D. IPAM のプールをリージョンや OU に分けて割り当てる

??? success "答えと解説"
    **正解: D**

    IPAM は組織全体の IP アドレスをプールで管理し、VPC の作成時にプールから割り当てられます。

    - A: 誤り。手作業で誤りが起き、自動にならない。
    - B: 誤り。作られた後の検知で、重複を防げない。
    - C: 誤り。VPC 間の経路が必要な通信ができなくなる。
    - D: 正しい。

    **スキル:** [1.4.2](../domain1.md#skill-1-4-2) / **参照:** [IP アドレス設計と IPAM](../../../services/network-connectivity.md#ip-addressing)

### 問6 {#q6}

EKS のクラスターの VPC は `/24` のサブネットしかなく、Pod の IP アドレスが足りなくなっています。VPC を作り直す時間はありません。既存のノードと通信を保ったまま、Pod 用の IP アドレスを増やします。どれが最も適切ですか。

- A. VPC にセカンダリ CIDR を追加し、新しいサブネットを作る
- B. 既存のサブネットの CIDR を拡張する
- C. ノードのインスタンスサイズを小さくして台数を増やす
- D. EKS のクラスターを別のリージョンに作り直す

??? success "答えと解説"
    **正解: A**

    VPC にはセカンダリ CIDR を追加でき、そこから新しいサブネットを作れます。作り直しは不要です。

    - A: 正しい。
    - B: 誤り。作成済みのサブネットの CIDR は変更できない。
    - C: 誤り。ノードが増えるので、IP アドレスの消費がさらに増える。
    - D: 誤り。作り直しに当たり、時間の制約に合わない。

    **スキル:** [1.4.2](../domain1.md#skill-1-4-2) / **参照:** [VPC の CIDR](../../../services/network-connectivity.md#vpc-cidr)

### 問7 {#q7}

本番と開発の VPC が同じ Transit Gateway につながっています。監査で「本番と開発は直接通信できないこと、どちらも共有サービスの VPC には接続できること」が求められました。VPC を減らさずに、変更を最小にします。どれが適切ですか。

- A. 本番と開発の VPC のセキュリティグループで互いの CIDR を拒否する
- B. Transit Gateway の添付を削除し、全 VPC に NAT ゲートウェイを作ってインターネット経由で共有サービスへ接続する
- C. 開発の VPC を別の Transit Gateway に移し、共有サービスの VPC とピアリングを張る
- D. 本番と開発に別のルートテーブルを関連付け、共有サービスの経路だけを伝播する

??? success "答えと解説"
    **正解: D**

    Transit Gateway のルートテーブルを分けて、共有サービスの経路だけを各環境へ伝播すれば、環境間の経路ができません。

    - A: 誤り。セキュリティグループには拒否のルールがない。
    - B: 誤り。インターネットを経由し、公開の範囲が広がる。
    - C: 誤り。変更が大きく、経路の管理も増える。
    - D: 正しい。

    **スキル:** [1.4.2](../domain1.md#skill-1-4-2) / **参照:** [Transit Gateway のルートテーブル](../../../services/network-connectivity.md#tgw-route-tables)

### 問8 {#q8}

Transit Gateway に検査用の VPC をつなぎ、すべての VPC 間の通信をステートフルなファイアウォールに通しています。AZ をまたぐ通信でだけ、接続が断続的に切れます。ファイアウォールのログでは、片方向のパケットしか見えないセッションがあります。どう対処しますか。

- A. 検査用の VPC の添付でアプライアンスモードを有効にする
- B. 検査用の VPC のサブネットのネットワーク ACL で、エフェメラルポートを許可する
- C. 全 VPC の添付で ECMP を無効にする
- D. ファイアウォールをステートレスのルールだけで動かすように設定を変える

??? success "答えと解説"
    **正解: A**

    アプライアンスモードを有効にすると、Transit Gateway はその添付でフローの間ずっと同じ AZ を使います。経路が非対称になるのを防げます。

    - A: 正しい。
    - B: 誤り。AZ をまたぐときだけ起きる症状の説明にならない。
    - C: 誤り。VPC の添付の AZ の選択には関係しない。
    - D: 誤り。ステートフルな検査の要件を失う。

    **スキル:** [1.4.3](../domain1.md#skill-1-4-3) / **参照:** [アプライアンスモード](../../../services/network-connectivity.md#tgw-appliance-mode)

### 問9 {#q9}

規制の要件で、VPC からインターネットへの通信を、許可したドメインだけに制限します。HTTPS の SNI で判定し、IPS のルールでも検査します。第三者の製品は使わず、管理の手間を抑えます。どれを選びますか。

- A. セキュリティグループのアウトバウンドルールで、許可するドメイン名を指定する
- B. 第三者のファイアウォールを Gateway Load Balancer の背後に置く
- C. AWS Network Firewall を VPC の出口に置き、ドメインと IPS のルールを設定する
- D. VPC フローログを CloudWatch Logs に送り、許可していないドメインへの通信を Lambda で検知する

??? success "答えと解説"
    **正解: C**

    Network Firewall はステートフルなルールでドメインのフィルタリングと IPS を行えます。VPC の境界に置くマネージドサービスです。

    - A: 誤り。セキュリティグループは一般にドメイン名でなく IP やプレフィックスで判定し、IPS の機能もない。
    - B: 誤り。第三者の製品を使わないという条件に反する。
    - C: 正しい。
    - D: 誤り。フローログは記録で、通信を止められない。

    **スキル:** [1.4.3](../domain1.md#skill-1-4-3) / **参照:** [Network Firewall](../../../services/network-connectivity.md#network-firewall)

### 問10 {#q10}

銀行は長年使っている第三者のファイアウォール製品のルールと運用を、AWS でも使い続けます。複数の VPC の通信を検査し、機器の増減に自動で対応します。ファイアウォールは複数台に負荷を分散し、ヘルスチェックも行います。どれが適切ですか。

- A. AWS Network Firewall に既存のルールを移植する
- B. NLB の背後にファイアウォールを置き、各 VPC のルートで NLB を指定する
- C. AWS WAF のマネージドルールに、製品のルールを移行する
- D. Gateway Load Balancer の背後にファイアウォールを置く

??? success "答えと解説"
    **正解: D**

    GWLB は第三者のアプライアンスへ通信を透過的に渡し、負荷分散とヘルスチェックを行います。GENEVE で元のパケットを保ちます。

    - A: 誤り。製品のルールと運用を使い続けるという条件に反する。
    - B: 誤り。NLB はルートテーブルの宛先に透過的な検査の形で使えない。
    - C: 誤り。WAF は HTTP の検査で、製品の置き換えになる。
    - D: 正しい。

    **スキル:** [1.4.3](../domain1.md#skill-1-4-3) / **参照:** [GWLB による検査](../../../services/network-connectivity.md#gwlb-inspection)

公開 ALB の Web アプリで、特定の IP アドレスの範囲からの不正なアクセスが発生しています。同時に、ログイン API への SQL インジェクションと、大量のリクエストも観測されています。アプリを変更せず、これらの通信を止める手段を選んでください。（2つ選択）

- B. Web ACL にレートベースルールと、該当の範囲を拒否する IP セットのルールを追加する
- C. ALB のセキュリティグループに、該当の範囲を拒否するルールを追加する

### 問12 {#q12}

プライベートサブネットの EC2 は、IPv6 でインターネット上の API を呼びます。インターネットからインスタンスへの接続は開始させません。IPv4 の通信は NAT ゲートウェイのまま変えません。ルートテーブルの `::/0` は何に向けますか。

- A. NAT ゲートウェイ
- B. インターネットゲートウェイ
- C. Egress-only インターネットゲートウェイ
- D. 仮想プライベートゲートウェイ

??? success "答えと解説"
    **正解: C**

    Egress-only インターネットゲートウェイはステートフルで、IPv6 の内から外への接続と応答だけを通します。

    - A: 誤り。IPv6 のアドレス変換はしない。NAT64 は IPv4 の宛先に使う機能である。
    - B: 誤り。外から接続できてしまう。
    - C: 正しい。
    - D: 誤り。オンプレミスへの接続に使うもので、インターネットの出口ではない。

    **スキル:** [1.4.4](../domain1.md#skill-1-4-4) / **参照:** [IPv6 と EIGW](../../../services/network-connectivity.md#ipv6)

### 問13 {#q13}

パブリック IPv4 の費用を減らすため、新しいサブネットを IPv6 のみで作りました。そのサブネットのアプリは、IPv4 しか持たない外部の API も呼び続ける必要があります。アプリのコードは変更しません。必要な構成はどれですか。

- A. サブネットで DNS64 を有効にし、`64:ff9b::/96` を NAT ゲートウェイへ向ける
- B. サブネットに IPv4 の CIDR を追加し、全インスタンスに Elastic IP を割り当てる
- C. `::/0` を Egress-only インターネットゲートウェイへ向け、IPv4 の API も自動で変換させる
- D. Route 53 の公開ホストゾーンに、外部の API の AAAA レコードを自分で作成する

??? success "答えと解説"
    **正解: A**

    DNS64 が IPv6 アドレスに変換して返し、NAT ゲートウェイの NAT64 が IPv4 へ変換します。

    - A: 正しい。
    - B: 誤り。パブリック IPv4 の費用を減らす目的に反する。
    - C: 誤り。Egress-only インターネットゲートウェイはアドレスの変換をしない。
    - D: 誤り。相手の名前のレコードを勝手に作ることはできず、IPv4 への変換もされない。

    **スキル:** [1.4.4](../domain1.md#skill-1-4-4) / **参照:** [IPv6 と EIGW](../../../services/network-connectivity.md#ipv6)

### 問14 {#q14}

Web サービスをデュアルスタックにします。VPC とサブネットに IPv6 の CIDR を割り当て、インターネットゲートウェイへの `::/0` も追加して、ALB をデュアルスタックにしました。AAAA レコードも追加しましたが、IPv6 の利用者だけ接続がタイムアウトします。IPv4 の利用者は問題ありません。最も可能性の高い原因はどれですか。

- A. Route 53 の AAAA レコードの TTL が短すぎる
- B. VPC の DNS ホスト名の設定が IPv6 に対応していない
- C. ALB のターゲットグループが IPv4 なので、IPv6 の利用者と接続できない
- D. ALB のセキュリティグループに IPv6 の `::/0` の許可がない

??? success "答えと解説"
    **正解: D**

    セキュリティグループと NACL の IPv6 のルールは IPv4 とは別に評価されます。IPv6 のルールを追加します。

    - A: 誤り。TTL が短くても接続のタイムアウトにはならない。
    - B: 誤り。AAAA レコードを既に公開しており、VPC の DNS ホスト名の設定はこの接続に関係しない。
    - C: 誤り。デュアルスタックの ALB は、IPv6 の利用者の通信を IPv4 のターゲットへ渡せる。
    - D: 正しい。

    **スキル:** [1.4.4](../domain1.md#skill-1-4-4) / **参照:** [IPv6 と EIGW](../../../services/network-connectivity.md#ipv6)

### 問15 {#q15}

オンプレミスと AWS の間の Site-to-Site VPN を、IPv6 にも対応させます。現在の VPN は仮想プライベートゲートウェイに接続しています。VPN のトンネルの中で IPv6 の通信を流すには、どうしますか。

- A. 既存の VPN で IPv6 を有効に変更し、VGW に `::/0` の経路を追加する
- B. Transit Gateway に、IPv6 用の新しい VPN 接続を作る
- C. VGW に Egress-only インターネットゲートウェイを関連付ける
- D. VPC の IPv6 CIDR をオンプレミスのルーターに静的に設定する

??? success "答えと解説"
    **正解: B**

    VGW は IPv6 のトラフィックに対応しません。Transit Gateway の VPN なら、新しい接続でトンネル内の通信に IPv6 を指定できます。

    - A: 誤り。VGW は IPv6 のトラフィックに対応しない。
    - B: 正しい。
    - C: 誤り。Egress-only インターネットゲートウェイは VPC のインターネットの出口である。
    - D: 誤り。経路の設定だけでは、VGW の制約は解決しない。

### 問16 {#q16}

ある動画サービスは、法令によりドイツの利用者に EU のリージョンのコンテンツを、その他の国の利用者には米国のリージョンのコンテンツを返します。遅延の大小にかかわらず、利用者の国で決めます。場所を判定できない IP アドレスからの問い合わせにも回答します。適切な設定を選んでください。（2つ選択）

- A. Route 53 の位置情報ルーティングでドイツのレコードを作る
- B. 位置情報のデフォルトレコードを作り、米国のリージョンへ向ける
- C. Route 53 のレイテンシーベースルーティングで、最も近いリージョンへ送る
- D. Global Accelerator のエンドポイントグループのトラフィックダイヤルで、国ごとに配分する
- E. 加重ルーティングで、ドイツの利用者の比率に合わせて重みを設定する

??? success "答えと解説"
    **正解: A, B**

    国で分けるなら位置情報ルーティングです。判定できない問い合わせやその他の国には、デフォルトレコードで答えます。

    - A: 正しい。
    - B: 正しい。
    - C: 誤り。遅延で選ぶので、法令の要件を保証しない。
    - D: 誤り。割合の調整で、国による振り分けではない。
    - E: 誤り。重みは割合で、国を判定しない。

### 問17 {#q17}

決済端末のメーカーは、世界の端末から独自の TCP で 2 つのリージョンへ接続します。端末のファームウェアは接続先の固定 IP を持ち、変更には数か月かかります。障害時は DNS の切り替えに頼らず、数十秒で別のリージョンへ切り替えたいです。どれを選びますか。

- A. Route 53 のフェイルオーバーで TTL を 10 秒にする
- B. CloudFront のオリジンフェイルオーバーで 2 つのリージョンを指定する
- C. Global Accelerator の固定 IP を使い、2 リージョンへ振り分ける
- D. 各リージョンの NLB に Elastic IP を付け、端末に両方の IP を設定する

??? success "答えと解説"
    **正解: C**

    Global Accelerator は固定のエニーキャスト IP の裏側でエンドポイントを切り替えます。TCP と UDP に対応し、DNS に左右されません。

    - A: 誤り。端末は固定 IP へ接続するので、DNS の切り替えが効かない。
    - B: 誤り。CloudFront は HTTP の配信で、独自の TCP を扱えない。
    - C: 正しい。
    - D: 誤り。ファームウェアの変更が必要になり、切り替えも端末側の実装に依存する。

    **スキル:** [1.4.5](../domain1.md#skill-1-4-5) / **参照:** [Global Accelerator](../../../services/network-connectivity.md#global-accelerator)

### 問18 {#q18}

Web サービスを新しいリージョンの構成へ移行します。新しい構成には、まず 5% の利用者を送り、問題がなければ 25%、50% と段階的に増やします。問題があれば数分で戻します。クライアントの変更はできず、DNS の名前は同じです。どの方法が最も適切ですか。

- A. Route 53 の加重ルーティングで、TTL を短くして重みを変える
- B. Route 53 のレイテンシーベースルーティングを使い、新しいリージョンに近い利用者から移す
- C. Route 53 のフェイルオーバーレコードで、新しい構成を待機系に設定する
- D. 位置情報ルーティングで、新しい構成に送る国を毎週増やす

??? success "答えと解説"
    **正解: A**

    加重ルーティングは割合で分けられるので、段階的な移行に向きます。TTL を短くすれば、戻すのも早くなります。

    - A: 正しい。
    - B: 誤り。割合を制御できない。
    - C: 誤り。主系が異常になるまで流れず、段階的に増やせない。
    - D: 誤り。割合が国の利用者数に左右され、細かく制御できない。

    **スキル:** [1.4.5](../domain1.md#skill-1-4-5) / **参照:** [ルーティングポリシー](../../../services/networking.md#routing-policies)
