# AI と ML の組み込みの問題集

### 問1 {#q1}

共有のアカウントで、5 つのアプリが同じ Bedrock の基盤モデルを呼んでいます。経理は、アプリごとのモデルの費用を毎月配分したいと考えています。IAM ロールは共通で、呼び出しの経路を大きく変えたくありません。ゲートウェイの新設は見送ります。どの方法が最も適切ですか。

- A. 基盤モデルの ARN にアプリごとのコスト配分タグを付ける
- B. アプリごとにアプリケーション推論プロファイルを作ってタグを付け、呼び出しの `modelId` に指定する
- C. アプリごとに Provisioned Throughput を購入し、購入した単位で費用を分ける
- D. モデル呼び出しログを S3 に出力し、入力の本文からアプリを推定して料金を計算する

??? success "答えと解説"
    **正解: B**

    アプリケーション推論プロファイルはタグを付けられ、オンデマンドの呼び出しの費用と使用量をアプリごとに追えます。

    - A: 誤り。AWS が提供する基盤モデルは利用者のリソースではなく、タグでアプリを区別できない。
    - B: 正しい。
    - C: 誤り。目的に対して費用が大きく、未使用の分も課金される。
    - D: 誤り。推定の処理を自分で作り、請求とも直接つながらない。

    **スキル:** [1.2.1](../domain1.md#skill-1-2-1) / **参照:** [推論の容量とプロファイル](../../../services/genai-apps.md#inference-profiles)

### 問2 {#q2}

組織の 100 以上のアカウントで、各チームが独自に Bedrock を呼んでいます。セキュリティ部門は、どのチームの呼び出しにも必ず共通のガードレールが適用されるようにしたいと考えています。アプリのコードは変更させず、新しいアカウントにも自動で適用します。どれが最も適切ですか。

- A. 各チームのコードで `guardrailIdentifier` を指定するよう標準を定め、Config のルールで準拠を確かめる
- B. 中央のゲートウェイを新設し、全チームの呼び出しをそこへ移すようにコードを変更してもらう
- C. Organizations の Bedrock ポリシーで、組織全体にガードレールを強制する
- D. SCP の条件に `bedrock:GuardrailIdentifier` を指定し、ガードレールのない呼び出しを拒否する

??? success "答えと解説"
    **正解: C**

    Organizations の Bedrock ポリシーで、OU やアカウントの単位にガードレールを強制できます。呼び出し側の変更は不要です。

    - A: 誤り。コードの変更が必要で、強制にもならない。
    - B: 誤り。統制はできるが、コードの変更が必要である。
    - C: 正しい。
    - D: 誤り。呼び出しに識別子を指定する必要があり、コードの変更なしでは拒否されて失敗する。

    **スキル:** [1.2.1](../domain1.md#skill-1-2-1) / **参照:** [組織での強制](../../../services/genai-apps.md#guardrail-org-enforcement)

### 問3 {#q3}

EU の金融機関が、プライベートサブネットのアプリから Bedrock を呼びます。通信はインターネットを経由させません。ピーク時にスロットリングが起きますが、推論の処理は EU の中にとどめる規定があります。必要な構成を選んでください。（2つ選択）

- A. `bedrock-runtime` のインターフェイス VPC エンドポイントを作る
- B. NAT ゲートウェイを作り、宛先を Bedrock の公開エンドポイントに制限する
- C. EU の地理的なクロスリージョン推論プロファイルを使う
- D. グローバルのクロスリージョン推論プロファイルを使う
- E. 推論プロファイルと Provisioned Throughput を組み合わせて、複数のリージョンの容量を確保する

??? success "答えと解説"
    **正解: A, C**

    PrivateLink で閉域に接続します。地理的なプロファイルなら、ルーティング先をその地域のリージョンにとどめられます。

    - A: 正しい。
    - B: 誤り。インターネットを経由する。
    - C: 正しい。
    - D: 誤り。EU の外のリージョンへ送られる可能性がある。
    - E: 誤り。推論プロファイルは Provisioned Throughput に対応していない。

    **スキル:** [1.2.1](../domain1.md#skill-1-2-1) / **参照:** [VPC エンドポイントでの接続](../../../services/ai.md#privatelink)

### 問4 {#q4}

40 のチームが複数のモデルを使います。プラットフォームチームは、チームごとの利用の制限と全呼び出しの記録を一か所で管理し、将来のモデルの切り替えをアプリから隠したいと考えています。アプリの変更は一度だけ受け入れられます。どの構成が要件に最も合いますか。

- A. 各チームのアカウントから Bedrock を直接呼び、モデル呼び出しログを各アカウントで有効にする
- B. 各チームのアカウントに同じ Lambda のラッパーをデプロイし、モデル名を環境変数で管理する
- C. Organizations の Bedrock ポリシーでガードレールを強制し、モデルの選択は各チームに任せる
- D. 共通の API を提供する中央の GenAI ゲートウェイを作り、制限と記録を集約して高可用に設計する

    **正解: D**

    ゲートウェイがアプリとモデルの間に入り、認証、制限、記録を集約して、モデルの選択を裏に隠します。単一障害点にならないよう設計します。

    - A: 誤り。統制と記録がアカウントごとにばらばらになる。
    - B: 誤り。分散したコピーの更新が必要で、中央の制限にならない。
    - C: 誤り。ガードレールは強制できるが、利用の制限やモデルの隠蔽は実現できない。
    - D: 正しい。

    **スキル:** [1.2.1](../domain1.md#skill-1-2-1) / **参照:** [GenAI ゲートウェイ](../../../services/genai-apps.md#genai-gateway)

### 問5 {#q5}

カスタマーサポートの AI エージェントが、30 個の既存の社内 API をツールとして呼びます。「返金は 1 万円以下のときだけ」「解約 API は管理者の利用者のときだけ」という規則を確実に守らせます。監査のため、モデルの判断に依存しない形にします。既存の API は変更できません。どうしますか。

- A. AgentCore Gateway に Policy を関連付け、Cedar で規則を書く
- B. システムプロンプトに規則を書き、違反しないようモデルに指示する
- C. Bedrock Guardrails の拒否トピックに、返金と解約に関する話題を登録する
- D. エージェントのコードの中で、モデルの出力を正規表現で確認してから API を呼ぶ

??? success "答えと解説"
    **正解: A**

    Policy は Gateway を通るツール呼び出しをエージェントのコードの外で評価し、決定的に制御します。ユーザーの ID とツールの入力値で判定できます。

    - A: 正しい。
    - B: 誤り。モデルの判断に依存し、確実ではない。
    - C: 誤り。Guardrails は入出力の内容の制御で、ツールの入力の値による認可ではない。
    - D: 誤り。エージェントごとの実装になり、コードの外で強制できない。

### 問8 {#q8}

医療画像の解析モデルを SageMaker AI で動かします。入力は 1 件あたり最大 800 MB で、推論に最大 30 分かかります。依頼は不定期に 1 件ずつ届き、結果は後から通知できれば構いません。依頼がない間は費用を最小にします。どの推論の方式を選びますか。

- A. 非同期推論。キューが空なら 0 台まで縮小する
- B. リアルタイム推論。インスタンスの数を最小にして常時待機する
- C. サーバーレス推論。同時実行の数を大きくする
- D. バッチ変換。依頼が届くたびに変換ジョブを 1 件の入力で作る

??? success "答えと解説"

    - C: 誤り。サーバーレス推論は短い処理向けで、大きな入力と 30 分の処理には合わない。

### 問15 {#q15}

SaaS に RAG の機能を追加します。大半のテナントは共有で構いませんが、数社の規制対象のテナントは、文書の保管と埋め込みの索引を他社と分け、契約終了時に丸ごと削除できる必要があります。全テナントの費用はなるべく抑えます。どの設計が最も適切ですか。

- A. 全テナントで 1 つのナレッジベースを共有し、システムプロンプトでテナント以外の情報を使わないよう指示する
- B. 全テナントごとに、別々の OpenSearch Serverless コレクションとナレッジベースを作る
- C. 共有のナレッジベースでメタデータフィルターを使い、規制対象には専用のナレッジベースを作る
- D. 全テナントで 1 つのナレッジベースを共有し、応答の後で他社の情報をアプリのコードで取り除く

??? success "答えと解説"
    **正解: C**

    大半はメタデータフィルターで低コストに分け、規制対象にはナレッジベースを分けます。文書と索引の分離、削除の単位を満たします。

    - A: 誤り。プロンプトの指示は分離を保証しない。
    - B: 誤り。分離はできるが、全テナントの費用が高くなる。
    - C: 正しい。
    - D: 誤り。他社の情報をモデルへ渡してしまい、分離にならない。
