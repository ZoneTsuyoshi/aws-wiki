# CI/CD と DevSecOps の問題集

対象の解説: [CI/CD](../../../services/cicd.md)、[生成 AI アプリの評価](../../../services/genai-apps.md#evaluation)、[Inspector のスキャンの種類](../../../services/threat-detection.md#inspector-scan-types)

### 問1 {#q1}

ある企業のパイプラインは、開発、ステージング、本番の各ステージでソースからコンテナイメージをビルドしています。ステージングで検証したのに、本番だけ依存パッケージの版が変わって障害が起きました。監査部門は、テストした成果物と本番の成果物が同じであることの証明を求めています。環境ごとの設定の違いは残す必要があります。最も適切な変更はどれですか。

- A. 本番のステージのビルドで、ステージングと同じ `buildspec` を使い、キャッシュを無効にする
- B. 本番のビルドの後にステージングと同じ自動テストをもう一度実行し、結果の一致を確かめてからデプロイする
- C. 1 回だけビルドして同じ成果物を昇格し、設定はパラメータで渡す
- D. 環境ごとにブランチを分け、ブランチの間のマージのときに差分を人が確認し、確認の記録を残す

??? success "答えと解説"
    **正解: C**

    同じ成果物を環境ごとのステージへ順に進めます。設定は CloudFormation のパラメータやパイプライン変数で変えます。

    - A: 誤り。ビルドし直す限り、成果物が変わるおそれは残ります。
    - B: 誤り。本番の成果物のテストにはなりますが、ステージングで検証したものと同じという証明になりません。
    - C: 正しい。
    - D: 誤り。ブランチごとにビルドするので、同じ成果物になりません。

    **スキル:** [5.2.1](../domain5.md#skill-5-2-1) / **参照:** [複数環境への展開](../../../services/cicd.md#multi-environment)

### 問2 {#q2}

モノレポに 30 のサービスがあり、CodePipeline の V1 タイプのパイプラインがサービスごとにあります。1 回のプッシュで全パイプラインが起動し、CodeBuild の費用が増えています。`main` ブランチで、`services/payment/` の下のファイルが変わったときだけ、決済のパイプラインを起動したいです。独自のコードは増やしたくありません。最も適切な方法はどれですか。

- A. V2 タイプに変更し、トリガーのフィルターでブランチとファイルパスを指定する
- B. V1 タイプのまま、Webhook を受ける API Gateway と Lambda を作り、変更されたファイルを調べてパイプラインを起動する
- C. V1 タイプのまま、最初の CodeBuild のアクションで変更ファイルを調べ、関係がなければ成功として早めに終わる
- D. サービスごとにリポジトリを分け、共通のコードはパッケージとして配布する

??? success "答えと解説"
    **正解: A**

    Git のタグ、プルリクエスト、ブランチ、ファイルパスでのトリガーのフィルターは V2 タイプの機能です。

    - A: 正しい。
    - B: 誤り。動きますが、独自のコードが増えます。
    - C: 誤り。起動は減らず、CodeBuild の費用も残ります。
    - D: 誤り。要件に対して変更が大きすぎます。

    **スキル:** [5.2.1](../domain5.md#skill-5-2-1) / **参照:** [パイプラインタイプ](../../../services/cicd.md#pipeline-types)、[リポジトリからの起動](../../../services/cicd.md#pipeline-triggers)

### 問3 {#q3}

決済チームのパイプラインは V2 タイプで、1 日に何度もコミットがあります。規制のため、すべてのコミットを順番どおりに本番まで進めた記録が必要です。ところが、前の実行が承認待ちの間に新しい実行が追い越し、途中の実行が本番に届かないことがあります。複数の実行が同じステージで同時に動くことも認められません。どの設定が適切ですか。

- A. `SUPERSEDED` モードのまま、手動承認のタイムアウトを短くして追い越しの機会を減らす
- B. `PARALLEL` モードにして、実行ごとに独立してステージを進める
- C. ステージの Entry 条件に `VariableCheck` のルールを置き、古いコミットの実行を飛ばす
- D. パイプラインの実行モードを `QUEUED` に変更して、実行を順に進める

??? success "答えと解説"
    **正解: D**

    `QUEUED` モードでは、実行は順番を待ち、追い越されずに進みます。V2 タイプで使えます。

    - A: 誤り。`SUPERSEDED` では、新しい実行が古い実行を置き換えることがあります。
    - B: 誤り。同じステージで同時に動くので、要件に反します。
    - C: 誤り。飛ばした実行は本番に届きません。
    - D: 正しい。

    **スキル:** [5.2.1](../domain5.md#skill-5-2-1) / **参照:** [パイプラインタイプ](../../../services/cicd.md#pipeline-types)

### 問4 {#q4}

製造業の企業は、同じ業務アプリを EC2 とオンプレミスのサーバーの両方で動かしています。移行が終わるまでの数年間は、両方に同じ手順でインプレースにデプロイし、失敗すれば前の版に自動で戻したいです。ソースからビルド、承認までの流れも AWS のサービスで統一します。デプロイの部分に最も適したものはどれですか。

- A. CodeBuild のビルドの中で SSH を使い、各サーバーへ成果物をコピーして再起動する
- B. CodeDeploy のエージェントを両方に入れ、デプロイグループで管理する
- C. Elastic Beanstalk の環境をオンプレミスにも作り、ローリングでデプロイする
- D. AWS CDK のカスタムリソースで Run Command を呼び、結果を CloudFormation に返して、失敗ならスタックごと戻す

??? success "答えと解説"
    **正解: B**

    CodeDeploy は EC2 とオンプレミスの両方へデプロイでき、失敗時の自動ロールバックも設定できます。

    - A: 誤り。認証情報の管理と戻す処理を自作することになります。
    - B: 正しい。
    - C: 誤り。Elastic Beanstalk の環境はオンプレミスのサーバーを管理しません。
    - D: 誤り。アプリのデプロイに合わない複雑な構成で、戻す処理も自作です。

    **スキル:** [5.2.1](../domain5.md#skill-5-2-1) / **参照:** [CodeDeploy](../../../services/cicd.md#codedeploy)、[CodeDeploy のロールバック](../../../services/cicd.md#codedeploy-rollback)

### 問5 {#q5}

ある企業は、ECR のイメージへの署名を標準にします。ビルド環境にクライアント側の署名ツールを入れたくありません。レジストリは同じアカウントの東京と大阪のリージョンにあります。セキュリティチームは、署名プロファイルを専用のアカウントで一元管理したいと考えています。正しい設計はどれですか。

- A. セキュリティアカウントの東京のリージョンに 1 つのプロファイルを作り、両方のレジストリの署名ルールから参照する
- B. 各ビルドの `post_build` で Notation を実行し、セキュリティアカウントの KMS キーで署名する
- C. セキュリティアカウントの東京と大阪にそれぞれプロファイルを作り、各リージョンの署名ルールで指定する
- D. レジストリと同じアカウントにしかプロファイルを置けないので、一元管理を諦めて各リージョンに作る

??? success "答えと解説"
    **正解: C**

    ECR マネージド署名は、プッシュ時に AWS Signer で署名します。プロファイルはレジストリと同じリージョンに必要ですが、別のアカウントのものを使えます。

    - A: 誤り。リージョンをまたぐ署名はできません。
    - B: 誤り。クライアント側のツールを入れないという要件に反します。
    - C: 正しい。
    - D: 誤り。アカウントをまたぐ署名に対応しています。

    **スキル:** [5.2.2](../domain5.md#skill-5-2-2) / **参照:** [イメージスキャン](../../../services/containers.md#ecr-scanning)、[ECR マネージド署名（公式）](https://docs.aws.amazon.com/AmazonECR/latest/userguide/managed-signing.html)

### 問6 {#q6}

コンテナのパイプラインに脆弱性の対策を入れます。要件は 2 つです。(1) 重大な脆弱性のあるイメージを ECR へプッシュする前に、CodeBuild のステージを失敗させます。(2) プッシュの後に新しく公開された CVE でも、配布済みのイメージの検出結果を得て通知します。どの組み合わせが適切ですか。（2つ選択）

- A. CodeGuru Security のスキャンをビルドに追加する
- B. Inspector の SBOM Generator と Scan API をビルドで使い、結果でビルドを失敗させる
- C. ECR の基本スキャンをプッシュ時に実行し、結果をビルドの中で確認する
- D. VPC フローログを Athena で分析し、不審な通信のあるイメージを特定する
- E. ECR の拡張スキャンを継続スキャンにし、検出結果を EventBridge で通知する

??? success "答えと解説"
    **正解: B, E**

    Inspector の CI/CD 統合は、SBOM Generator と Scan API でビルド中に検査します。拡張スキャンは Inspector と連携して継続的に検査し、結果は EventBridge に送られます。

    - A: 誤り。CodeGuru Security はサポートが終了し、後継は Inspector の Code Security です。
    - B: 正しい。
    - C: 誤り。プッシュ後の検査なので、プッシュの前に止められません。OS の脆弱性に限られ、継続的でもありません。
    - D: 誤り。フローログで CVE は分かりません。
    - E: 正しい。

    **スキル:** [5.2.2](../domain5.md#skill-5-2-2) / **参照:** [イメージスキャン](../../../services/containers.md#ecr-scanning)、[ECR のスキャン](../../../services/threat-detection.md#inspector-ecr)、[Inspector CI/CD 統合（公式）](https://docs.aws.amazon.com/inspector/latest/user/scanning-cicd.html)

### 問7 {#q7}

本番アカウントの Lambda に、信頼できる発行元のコードだけをデプロイさせます。ただし、現在のパイプラインの中には署名していないものがあり、いきなり止めると業務に影響します。まず対象を洗い出し、その後で強制します。既に動いている関数を止めることはできません。最も適切な進め方はどれですか。

- A. コード署名設定を `Warn` で関連付け、`SignatureValidationErrors` で洗い出してから `Enforce` にする
- B. コード署名設定を `Enforce` で関連付け、動いている未署名の関数が止まったら順に署名する
- C. 未署名のコードを呼び出し時に拒否する SCP を作り、対象のアカウントから順に適用する
- D. Inspector の Lambda のスキャンを有効にし、検出のない関数は信頼できる発行元のものとして扱い、例外を記録する

??? success "答えと解説"
    **正解: A**

    `Warn` はデプロイを許可し、メトリクスと CloudTrail に記録します。`Enforce` はデプロイをブロックします。検証はデプロイ時に行うので、すでに動いている未署名のコードは止まりません。

    - A: 正しい。
    - B: 誤り。動いている関数は止まりません。また、洗い出しの前に強制すると、デプロイが突然失敗します。
    - C: 誤り。検証はデプロイ時のもので、呼び出し時に署名を確かめる SCP は書けません。
    - D: 誤り。脆弱性のスキャンでは、発行元を確かめられません。

    **スキル:** [5.2.2](../domain5.md#skill-5-2-2) / **参照:** [コード署名](../../../services/lambda.md#code-signing)

### 問8 {#q8}

監査で、「レジストリに悪意のあるイメージが置かれた場合でも本番へ入らないこと」と「依存パッケージに既知の脆弱性がないこと」の両方を示すよう求められました。現在は拡張スキャンだけを使っています。担当者は、検出結果がゼロなら両方の説明になると考えています。アーキテクトの判断として正しいものはどれですか。

- A. 拡張スキャンは発行元も検証するので、現状のままで両方を示せる
- B. タグの不変性を有効にすれば発行元を示せるので、署名は不要である
- C. 署名を追加すれば脆弱性も分かるので、スキャンを廃止して費用を減らす
- D. スキャンは脆弱性、署名は発行元と改ざんの確認なので、署名の検証も加える

??? success "答えと解説"
    **正解: D**

    スキャンは「既知の脆弱性がないか」、署名は「信頼できる発行元のもので、改ざんされていないか」を確かめます。別の問いに答える機能なので、組み合わせます。

    - A: 誤り。スキャンは発行元を確かめません。悪意のあるイメージでも、既知の CVE がなければ検出されません。
    - B: 誤り。不変性はタグの上書きを防ぐだけで、誰が作ったかは示しません。
    - C: 誤り。正しく署名されたイメージにも脆弱性はありえます。
    - D: 正しい。

    **スキル:** [5.2.2](../domain5.md#skill-5-2-2) / **参照:** [イメージスキャン](../../../services/containers.md#ecr-scanning)、[タグと不変タグ](../../../services/containers.md#image-tags)

### 問9 {#q9}

ツール用のアカウントにある CodePipeline から、本番のアカウントへデプロイするパイプラインを作ります。パイプラインのウィザードで作成したまま動かすと、本番側でアーティファクトを読めません。修正として必要なものはどれですか。（3つ選択）

- A. ツールアカウントのカスタマー管理キーでアーティファクトを暗号化し、キーポリシーで本番アカウントに許可する
- B. S3 の AWS 管理キーのキーポリシーを編集し、本番アカウントに復号を許可する
- C. アーティファクトのバケットポリシーで本番アカウントの読み取りを許可する
- D. 本番アカウントに、ツールアカウントを信頼するロールを作り、アクションで引き受ける
- E. ツールアカウントに本番用の IAM ユーザーを作り、長期のアクセスキーを本番アカウントの Secrets Manager に保存する
- F. ステージごとにアーティファクトを本番アカウントのバケットへ手動でコピーする

??? success "答えと解説"

    アカウントをまたぐパイプラインでは、カスタマー管理キー、バケットポリシー、対象のアカウントのロールの 3 つが必要です。

    - A: 正しい。
    - B: 誤り。AWS 管理キーのポリシーは編集できず、他のアカウントと共有できません。
    - C: 正しい。
    - D: 正しい。
    - E: 誤り。長期の認証情報は不要で、推奨されません。
    - F: 誤り。自動化されたパイプラインの目的に反します。

    **スキル:** [5.2.3](../domain5.md#skill-5-2-3) / **参照:** [複数環境への展開](../../../services/cicd.md#multi-environment)、[アカウントをまたぐ手順](../../../services/kms.md#cross-account-steps)、[ロールの引き受け](../../../services/iam.md#assume-role)

### 問10 {#q10}

東京のリージョンにあるパイプラインに、バージニア北部へデプロイするアクションを追加します。パイプラインは CloudFormation で定義しており、コンソールは使いません。本番のリソースは別のアカウントにあります。アーティファクトについて正しい設計はどれですか。

- A. 東京のバケットをそのまま使う。CodePipeline がバージニア北部から東京のバケットを直接読む
- B. バージニア北部の本番アカウントに、バケットとキーを作り、`ArtifactStores` に指定する
- C. S3 のリージョン間レプリケーションを東京のバケットに設定し、レプリカのバケットの名前をアクションの環境変数で指定して、デプロイ先に読ませる
- D. パイプラインのアカウントのバージニア北部に、バケットとキーを作り、`ArtifactStores` に指定する

    **正解: D**

    アクションを実行するリージョンごとにアーティファクトのバケットが必要です。バケットとキーは、アクションと同じリージョンで、パイプラインと同じアカウントに作ります。CLI や CloudFormation では自分で指定します。

    - A: 誤り。リージョンごとのバケットが必要です。
    - B: 誤り。パイプラインと同じアカウントに作ります。
    - C: 誤り。CodePipeline が入力の成果物をコピーするので、レプリケーションは不要です。
    - D: 正しい。

    **スキル:** [5.2.3](../domain5.md#skill-5-2-3) / **参照:** [複数環境への展開](../../../services/cicd.md#multi-environment)、[CodePipeline](../../../services/cicd.md#codepipeline)

### 問11 {#q11}

ツールアカウントのパイプラインが、本番アカウントの CodeDeploy で EC2 へデプロイします。カスタマー管理キー、バケットポリシー、クロスアカウントのロールはすでに設定しました。CodeDeploy のデプロイは始まりますが、本番の EC2 のエージェントがリビジョンをダウンロードできず失敗します。次に確認する設定はどれですか。

- A. ツールアカウントの CodePipeline のサービスロールに `codedeploy:*` を追加し、パイプラインの信頼ポリシーを更新する
- B. 本番の EC2 のインスタンスロールで、バケットの読み取りとキーの使用を許可する
- C. ツールアカウントのキーを本番アカウントのキーへ自動で再暗号化する設定を、バケットのレプリケーションに追加する
- D. CodeDeploy のデプロイグループを Blue/Green に変更する

### 問12 {#q12}

複数のアカウントへ順に昇格するパイプラインで、次の条件を満たしてから本番のステージへ進めたいです。ステージング環境の 5XX アラームが `ALARM` でないこと。本番への投入は平日の日中に限ること。条件を満たさなければステージへ入らないこと。独自の Lambda は増やしたくありません。V2 タイプを使っています。最も適切な方法はどれですか。

- A. 本番のステージの前に手動承認を置き、担当者が 2 つの条件を確認してから承認する
- B. 本番のステージの On Success 条件に、2 つのルールを置く
- C. 本番のステージの Entry 条件に、`CloudWatchAlarm` と `DeploymentWindow` のルールを置く
- D. EventBridge Scheduler で平日の日中だけパイプラインを有効にし、アラームは CodeBuild のステージの中で確認する

??? success "答えと解説"
    **正解: C**

    Entry 条件はステージに入る前に評価され、結果は `Fail` や `Skip` です。`CloudWatchAlarm` はアラームの状態、`DeploymentWindow` は配置を許す時間帯を確認します。

    - A: 誤り。人の確認に頼るので、自動の条件になりません。
    - B: 誤り。On Success はステージの成功の後に評価されるので、入る前に止められません。
    - C: 正しい。
    - D: 誤り。パイプラインを有効、無効にする標準の仕組みはなく、CodeBuild のステージも増えます。

    **スキル:** [5.2.3](../domain5.md#skill-5-2-3) / **参照:** [ステージ条件](../../../services/cicd.md#stage-conditions)

### 問13 {#q13}

カスタマーサポートの回答を生成するアプリで、プロンプトの変更が頻繁にあります。変更後に回答の品質が下がったまま本番へ出る事故が起きました。パイプラインで品質を自動で判定し、基準を下回れば止めたいです。回答の文面は実行のたびに変わります。判定に人の作業は入れたくありません。最も適切な方法はどれですか。

複数のサービスを順にデプロイする CodePipeline の V2 タイプのパイプラインがあります。本番のステージの完了後に 5XX のアラームが `ALARM` になったら、前回成功した実行の版へ自動で戻したいです。別のチームは、同じ設計を `PARALLEL` モードのパイプラインにも使おうとしています。正しいものはどれですか。
