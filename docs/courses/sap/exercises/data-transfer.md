# データ転送とネットワーク費用の問題集

対象の解説: [データ転送の費用](../../../services/cost-management.md#data-transfer)

### 問1 {#q1}

ある出版社は、画像をその場で変換するオンプレミスのサーバーをオリジンにして、CloudFront で世界へ配信しています。回線の帯域に余裕がなく、キャンペーンで同じ画像へ世界各地から同時に要求が来ると、オリジンの負荷が急に上がります。オリジンの近くの AWS リージョンは東京です。オリジンへの要求を最も減らす方法はどれですか。

- A. 東京リージョンで Origin Shield を有効にする
- B. 地域ごとに別のディストリビューションを作成し、オリジンへの経路を分散させる
- C. オリジングループを作成し、オリジンの障害時にのみ別のオリジンへ切り替える
- D. Global Accelerator をオリジンの前に置いて、CloudFront からの経路を最適化する

??? success "答えと解説"
    **正解: A**

    Origin Shield はオリジンの前のキャッシュ層です。同じオブジェクトへの要求を束ね、オリジンへの要求を減らします。帯域の限られるオンプレミスのオリジンや、その場の画像変換は公式の想定する用途です。

    - A: 正しい。
    - B: 誤り。キャッシュが分かれ、オリジンへの要求はむしろ増える。
    - C: 誤り。可用性の機能で、要求の量は減らない。
    - D: 誤り。経路の改善で、同じ要求を束ねる機能はない。

    **スキル:** [3.2.1](../domain3.md#skill-3-2-1) / **参照:** [オリジンの設定](../../../services/networking.md#origin-settings)、[Origin Shield（公式）](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/origin-shield.html)

### 問2 {#q2}

ある EC サイトの CloudFront は、すべての Cookie をキャッシュキーに含めています。商品画像の応答は Cookie によって変わりません。ただし、オリジンのアプリは分析のために全 Cookie を受け取る必要があります。キャッシュヒット率が低く、オリジンの費用が増えています。最も適切な変更はどれですか。

- A. Cookie はキーに含めたまま、キャッシュポリシーの TTL を大幅に延ばす
- B. キーから Cookie を外し、オリジンリクエストポリシーで全 Cookie を渡す
- C. Lambda@Edge のビューワーリクエストで Cookie をすべて削除してから処理を続ける
- D. Cookie はキーに含めたまま、Origin Shield を有効にしてオリジンの負荷を減らす

??? success "答えと解説"
    **正解: B**

    キャッシュキーとオリジンへ渡す値は別に設定できます。応答が変わらない値はキーから外し、オリジンが必要なら、オリジンリクエストポリシーで渡します。

    - A: 誤り。利用者ごとにキーが分かれたままなので、ヒット率は上がらない。
    - B: 正しい。
    - C: 誤り。オリジンが Cookie を受け取れなくなる。
    - D: 誤り。キーが分かれたままで、根本の原因が残る。

    **スキル:** [3.2.1](../domain3.md#skill-3-2-1) / **参照:** [キャッシュキーとポリシー](../../../services/networking.md#cache-keys)

### 問3 {#q3}

あるメディア企業の CloudFront には、3 つのオリジンがあります。オリジン X は利用者ごとの結果を返す動的な API で、ほぼキャッシュできません。オリジン Y はその場で画像を変換し、世界の利用者が同じ画像を何度も要求します。オリジン Z は古い記事の保管庫で、要求はまれです。Origin Shield は追加料金がかかるので、効果のあるところだけ有効にします。どれが最も適切ですか。

- A. 3 つのオリジンすべてで有効にする
- B. オリジン X と Z で有効にする
- C. オリジン Y だけで有効にする
- D. オリジン Z だけで有効にする

??? success "答えと解説"
    **正解: C**

    公式は、動的なコンテンツ、キャッシュしにくいもの、まれにしか要求されないものには向かないとしています。効くのは、世界に分散した利用者が同じ変換結果を求める Y です。

    - A: 誤り。X と Z では追加料金に見合わない。
    - B: 誤り。向かない 2 つを選んでいる。
    - C: 正しい。
    - D: 誤り。要求がまれなので、束ねる効果がない。

    **スキル:** [3.2.1](../domain3.md#skill-3-2-1) / **参照:** [オリジンの設定](../../../services/networking.md#origin-settings)、[Origin Shield（公式）](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/origin-shield.html)

### 問4 {#q4}

ある会社のプライベートサブネットのアプリは、NAT ゲートウェイを経由して通信しています。月あたりの量は、同じリージョンの S3 が 30 TB、DynamoDB が 10 TB、SQS が 5 TB です。NAT の処理料金が大きな費用になっています。アプリのコードは変更したくありません。適切なものはどれですか。（2つ選択）

- A. S3 用にインターフェイスエンドポイントを作り、S3 の通信をすべて移す
- B. S3 と DynamoDB のゲートウェイエンドポイントを作り、ルートテーブルに追加する
- C. NAT ゲートウェイを 1 つの AZ に集約して、時間課金を減らす
- D. S3 Transfer Acceleration を有効にして、S3 への経路を高速な経路へ切り替える
- E. SQS は、インターフェイスエンドポイントの費用と NAT の費用を比べて決める

??? success "答えと解説"
    **正解: B, E**

    ゲートウェイエンドポイントは追加料金がかからず、S3 と DynamoDB に使えます。SQS にはインターフェイスエンドポイントがあり、時間とデータの料金がかかるので、通信量で比べます。

    - A: 誤り。時間とデータの料金がかかる。無料のゲートウェイで足りる。
    - B: 正しい。
    - C: 誤り。処理料金は減らず、AZ 間の転送が増えて可用性も落ちる。
    - D: 誤り。遠距離の転送を速くする機能で、NAT の費用は減らない。
    - E: 正しい。

    **スキル:** [3.2.2](../domain3.md#skill-3-2-2) / **参照:** [データ転送の費用](../../../services/cost-management.md#data-transfer)、[VPC エンドポイントと PrivateLink](../../../services/networking.md#vpc-endpoints)

### 問5 {#q5}

ある Web アプリは 3 つの AZ のプライベートサブネットで動いていますが、NAT ゲートウェイは AZ-a に 1 つだけです。外部 API への通信量が多く、データ転送の明細で AZ 間の転送が目立ちます。また、AZ-a の障害時に全 AZ から外部へ出られなくなることも指摘されました。どちらの問題も解決する方法はどれですか。

- A. NAT を AZ-a に残し、帯域の大きい NAT インスタンスを AZ-b に追加する
- B. アプリをすべて AZ-a へ集めて、AZ 間の転送をなくす
- C. 各 AZ に NAT を置き、AZ ごとのルートテーブルで同じ AZ の NAT へ向ける
- D. 外部 API の通信を Transit Gateway 経由にして、別の VPC の NAT から出す

??? success "答えと解説"
    **正解: C**

    AZ ごとに NAT を置くと、AZ 間の転送がなくなり、AZ の障害の影響もその AZ に閉じます。NAT の時間課金は増えますが、要件の両方を満たします。

    - A: 誤り。ルートの偏りが残り、NAT インスタンスの運用も増える。
    - B: 誤り。転送費用は減るが、可用性が大きく落ちる。
    - C: 正しい。
    - D: 誤り。Transit Gateway のデータ処理料金が増え、問題の解決にならない。

    **スキル:** [3.2.2](../domain3.md#skill-3-2-2) / **参照:** [NAT ゲートウェイ](../../../services/network-connectivity.md#nat-gateway)、[データ転送の費用](../../../services/cost-management.md#data-transfer)

### 問6 {#q6}

ある会社は、ECS Service Connect で通信するマイクロサービスを 3 つの AZ で動かしています。AZ 間の転送費用を減らすため、Service Connect の zone-aware routing の動作を確認しました。受信側のサービスは各 AZ に 1 タスクずつ、合計 3 タスクです。明細を見ると、通信は AZ に関係なく均等に流れています。原因として最も適切なものはどれですか。

- A. zone-aware routing は既定で無効で、サービスごとにオプトインが必要である
- B. Service Connect のプロキシは Fargate のタスクでは動作しない
- C. アプリのコードに AZ の情報を渡す処理を追加していない
- D. 受信側のタスクが AZ 数の 2 倍に満たず、ラウンドロビンに戻っている

??? success "答えと解説"
    **正解: D**

    1 つの AZ の過負荷を防ぐため、受信側に AZ 数の 2 倍以上のエンドポイントが必要です。3 AZ なら 6 つ以上で、下回ると無効になり、ラウンドロビンで分散します。

    - A: 誤り。新規と既存の Service Connect のサービスで既定で有効。
    - B: 誤り。Fargate でも動作する。
    - C: 誤り。アプリのコードの変更は不要。
    - D: 正しい。

    **スキル:** [3.2.2](../domain3.md#skill-3-2-2) / **参照:** [データ転送の費用](../../../services/cost-management.md#data-transfer)、[zone-aware routing（公式）](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect-zone-aware-routing.html)

### 問7 {#q7}

ある分析チームは、夜間に Spark のバッチを EMR で実行しています。ジョブは失敗しても次の時間帯に再実行でき、AZ 間のシャッフルの転送費用が目立っています。同じ VPC にある顧客向けの Web 層は、AZ の障害でも止められません。費用と可用性の両方に最も合う構成はどれですか。

- A. バッチのクラスターは 1 つの AZ に置き、Web 層は複数の AZ に置く
- B. バッチと Web 層の両方を 1 つの AZ に集め、AZ 間の転送費用をなくす
- C. バッチと Web 層の両方を複数の AZ に広げ、Compute Savings Plans で相殺する
- D. バッチを別のリージョンで実行して、Web 層と影響を切り離す

??? success "答えと解説"
    **正解: A**

    1 つの AZ に集めると転送費用は下がりますが、可用性は落ちます。再実行できるバッチは許容でき、止められない Web 層は許容できません。ワークロードごとに判断します。

    - A: 正しい。
    - B: 誤り。Web 層の可用性の要件を満たせない。
    - C: 誤り。Savings Plans はデータ転送の費用を割り引かない。
    - D: 誤り。リージョン間の転送費用が増え、データも遠くなる。

    **スキル:** [3.2.2](../domain3.md#skill-3-2-2) / **参照:** [データ転送の費用](../../../services/cost-management.md#data-transfer)

### 問8 {#q8}

ある保険会社は、S3 バケットに 500 TB のデータを持っています。規制で別のリージョンへの保管が必要なのは `reports/` の下の 20 TB だけで、数分から数時間の遅れは許容されます。複製先のデータは監査のときしか読みません。読み取りは数時間待てます。既存のオブジェクトも複製する必要があります。費用を抑えた構成はどれですか。

- A. バケット全体の CRR を設定し、複製先のライフサイクルで `reports/` 以外を削除して、保管の費用を抑えながら全量を一度複製する
- B. `reports/` だけの CRR で複製先を Glacier Flexible Retrieval にし、既存分は Batch Replication
- C. `reports/` に絞った CRR を設定する。設定した時点で既存のオブジェクトも自動で複製される
- D. S3 RTC を付けた CRR を `reports/` に設定し、複製先のクラスは Standard のままにする

??? success "答えと解説"
    **正解: B**

    フィルターで必要なプレフィックスだけ複製し、複製先のクラスを安くします。ライブレプリケーションは設定前のオブジェクトを複製しないので、既存分は Batch Replication を使います。

    - A: 誤り。全量の転送費用がかかる。
    - B: 正しい。
    - C: 誤り。既存のオブジェクトは複製されない。
    - D: 誤り。RTC は 15 分以内の複製が必要なときの機能で、この要件には過剰。読まないデータを Standard に置くのも割高。

    **スキル:** [3.2.3](../domain3.md#skill-3-2-3) / **参照:** [レプリケーション](../../../services/s3.md#replication)

### 問9 {#q9}

ある会社の受発注システムは、DynamoDB のグローバルテーブルと Aurora グローバルデータベースを 2 つのリージョンで運用しています。書き込みは常に 1 つのリージョンだけです。事業部門と合意した DR の目標は、RPO が 24 時間、RTO が 1 日です。費用の大部分が複製先の分で、見直しの指示が出ました。最も費用対効果の高い構成はどれですか。

- A. 複製はそのままにして、複製先のインスタンスを小さいサイズへ変更する
- B. グローバルテーブルは残して、Aurora だけをリードレプリカへ置き換える
- C. 複製をやめ、AWS Backup の日次バックアップを DR リージョンへコピーする
- D. RPO を短くする方向に合意を見直し、現在の複製の費用を正当化する

??? success "答えと解説"
    **正解: C**

    RPO が 24 時間なら、リージョン間の複製は過剰です。定期のバックアップのコピーで足り、保管の倍増と書き込みの複製の費用をなくせます。

    - A: 誤り。費用は減るが、不要な複製とその転送費用が残る。
    - B: 誤り。書き込みの複製の費用が残り、Aurora の複製も続く。
    - C: 正しい。
    - D: 誤り。合意した目標を費用の都合で変えるのは本末転倒。

    **スキル:** [3.2.3](../domain3.md#skill-3-2-3) / **参照:** [リージョン間コピー](../../../services/resilience.md#backup-cross-region)、[4 つの DR 戦略](../../../services/resilience.md#dr-strategies)

### 問10 {#q10}

ある会社は、Aurora グローバルデータベースのセカンダリリージョンに、プライマリと同じ大きさのインスタンスを動かしています。セカンダリで読み取りは行っていません。DR の要件は RPO が小さいことで、切り替え時にインスタンスを追加する時間は許容されます。ストレージのレベルのレプリケーションは維持したまま、費用を下げるにはどうしますか。

- A. グローバルデータベースをやめ、S3 へのエクスポートを定期実行する
- B. プライマリのインスタンスも小さくして、両方の費用を均等に下げる

- D. セカンダリを DB インスタンスのないヘッドレスのクラスターにする

??? success "答えと解説"
    **正解: D**

    - A: 誤り。RPO が大きくなる。
    - B: 誤り。プライマリの性能が下がる。
    - C: 誤り。Aurora のクラスターボリュームにそのような設定はない。

### 問11 {#q11}

ある会社は、DynamoDB の MREC グローバルテーブルを 3 つのリージョンで使っています。1 つのリージョンが書き込みの大半を受け、残りの 2 つのうち 1 つは読み取りがほぼありません。プロビジョンドキャパシティの費用が高く、財務部門は複製分にリザーブドキャパシティの購入を提案しています。アーキテクトの判断として最も適切なものはどれですか。

- A. 複製の書き込みはリザーブドの対象外なので、不要なレプリカの削除を検討する
- B. 提案どおり、全リージョンの複製書き込みの分にリザーブドキャパシティを購入する
- C. Standard-IA テーブルクラスへ変更して、複製書き込みにリザーブドを適用する
- D. 書き込みは書き込み元のリージョンでだけ課金されるので、費用の原因は読み取りである

??? success "答えと解説"
    **正解: A**

    書き込みは各レプリカで課金されます。リザーブドキャパシティは複製書き込み（rWCU）に購入できません。使われないレプリカを減らすのが直接の対策です。

    - A: 正しい。
    - B: 誤り。rWCU には購入できない。
    - C: 誤り。Standard-IA のテーブルにはリザーブドキャパシティがない。
    - D: 誤り。複製先でも書き込みとして課金される。

    **スキル:** [3.2.3](../domain3.md#skill-3-2-3) / **参照:** [グローバルテーブル](../../../services/dynamodb.md#global-tables)、[キャパシティモードと RCU/WCU](../../../services/dynamodb.md#capacity)

### 問12 {#q12}

ある会社は、1 つのリージョンの 40 個の VPC を Transit Gateway でつないでいます。そのうち 2 つの VPC の間で、月 200 TB のデータベースのレプリケーションが流れ、データ処理料金の大半を占めています。他の VPC との接続は今のまま管理を簡単に保ちたいです。最も費用対効果の高い変更はどれですか。

- A. 2 つの VPC の間に VPC ピアリングを足し、その区間のルートをピアリングへ向ける
- B. 2 つの VPC だけ別の Transit Gateway に移し、データ処理の単価を下げる
- C. 全 VPC を PrivateLink の接続に置き換えて、Transit Gateway を削除する
- D. 2 つの VPC の通信を Direct Connect 経由でオンプレミスに折り返す

??? success "答えと解説"
    **正解: A**

    ピアリングには時間課金もデータ処理料金もなく、データ転送だけです。量の多い区間にだけ足せば、全体は Transit Gateway のまま管理できます。

    - A: 正しい。
    - B: 誤り。別の Transit Gateway でもデータ処理料金はかかる。
    - C: 誤り。PrivateLink はサービス単位の一方向の公開で、全 VPC の接続の代わりにならない。
    - D: 誤り。経路が遠回りになり、遅延と費用が増える。

    **スキル:** [3.2.4](../domain3.md#skill-3-2-4) / **参照:** [VPC ピアリング](../../../services/network-connectivity.md#vpc-peering)、[Transit Gateway](../../../services/network-connectivity.md#transit-gateway)

### 問13 {#q13}

ある会社には 60 個の VPC があり、Transit Gateway ですでに接続されています。VPC ごとに複数の NAT ゲートウェイがあります。59 個の VPC はインターネットへの通信がごく少なく、1 つの VPC だけが月 100 TB を外部へ送っています。インターネットへの出口の費用を最も下げる構成はどれですか。（2つ選択）

- A. 通信の少ない 59 個の VPC は、中央の VPC の NAT へ出口を集約する
- B. 通信の多い VPC も中央の VPC へ集約し、すべての出口を 1 か所に統一する
- C. 通信の多い VPC は、自分の VPC の NAT を残す
- D. 全 VPC にインターネットゲートウェイを付けて、NAT をすべて削除する
- E. NAT をすべて削除して、通信を CloudFront のオリジンリクエストとして送る

??? success "答えと解説"
    **正解: A, C**

    集約すると NAT の時間課金は減りますが、Transit Gateway のデータ処理料金が増えます。少量の VPC では時間課金の削減が勝ち、大量の VPC では処理料金が上回ります。通信量で分けます。

    - A: 正しい。
    - B: 誤り。100 TB に Transit Gateway のデータ処理料金がかかる。
    - C: 正しい。
    - D: 誤り。プライベートサブネットの設計が崩れ、公開の IPv4 の費用もかかる。
    - E: 誤り。CloudFront はビューワーへの配信のサービスで、外部への通信の出口ではない。

    **スキル:** [3.2.4](../domain3.md#skill-3-2-4) / **参照:** [Transit Gateway](../../../services/network-connectivity.md#transit-gateway)、[NAT ゲートウェイ](../../../services/network-connectivity.md#nat-gateway)

### 問14 {#q14}

ある会社は、同じ組織の 30 のアカウントで動くアプリを同じリージョンに置いています。アプリ間の通信量が多く、Transit Gateway のアタッチメントとデータ処理の費用が増えています。ネットワークはネットワークチームが一元で管理し、各チームは自分のアカウントでアプリのリソースだけを管理する方針です。最も適切な構成はどれですか。

- A. 各アカウントの VPC を総当たりでピアリングし、Transit Gateway を削除する
- B. Cloud WAN へ移行し、セグメントごとのポリシーで通信を制御する
- C. VPC Lattice のサービスネットワークへ全通信を移して、課金の単位を変える
- D. ネットワークチームの VPC のサブネットを RAM で共有する

??? success "答えと解説"
    **正解: D**

    VPC 共有なら、同じ VPC の中の通信に接続の費用がかかりません。VPC はネットワークチームが所有し、各アカウントはリソースだけを管理できるので、方針にも合います。

    - A: 誤り。30 の VPC の総当たりは接続が 400 を超え、管理が破綻する。
    - B: 誤り。多数のリージョンの統制向けで、1 リージョンの費用は減らない。
    - C: 誤り。VPC 間の通信の料金が残り、全通信の移行の手間も大きい。
    - D: 正しい。

    **スキル:** [3.2.4](../domain3.md#skill-3-2-4) / **参照:** [VPC 同士の接続](../../../services/network-connectivity.md#choosing-multi-vpc)

### 問15 {#q15}

ある会社は、AWS からオンプレミスへ毎月 80 TB を定常的に送っています。現在は Site-to-Site VPN を使い、接続の時間料金と送信データの料金を払っています。帯域の変動も課題です。障害時に備えて費用を抑えた代替経路も必要です。最も適切な構成はどれですか。

- A. VPN のトンネルを増やして帯域を確保し、通信量はそのままにする
- B. Direct Connect を主にし、Site-to-Site VPN をバックアップとして残す
- C. S3 にデータを置いて、オンプレミスから Transfer Acceleration で取得する
- D. Direct Connect を 2 ロケーションに 2 接続ずつ用意し、VPN はすべて解約する

??? success "答えと解説"
    **正解: B**

    定常的な大量の通信には Direct Connect が向きます。ポート料金と送信データの料金がかかりますが、帯域も安定します。バックアップは VPN にすると費用を抑えられます。

    - A: 誤り。インターネット経由の変動と送信データの費用が残る。
    - B: 正しい。
    - C: 誤り。インターネットへの送信の費用に Acceleration の料金が加わる。
    - D: 誤り。可用性は高いが、この要件には過剰で「費用を抑えた代替経路」に反する。

    **スキル:** [3.2.4](../domain3.md#skill-3-2-4) / **参照:** [Direct Connect](../../../services/network-connectivity.md#direct-connect)、[データ転送の費用](../../../services/cost-management.md#data-transfer)

### 問16 {#q16}

ある銀行は、EU の顧客の文書を Bedrock で要約します。規制により、処理は EU の中にとどめる必要があります。単一のリージョンのクォータでは急増に対応できず、費用も抑えたいです。別の部署の社内向けの翻訳には、データの地理的な制約がありません。それぞれに適した推論プロファイルはどれですか。

- A. どちらもグローバルプロファイルにして、費用の割引を受ける
- B. 要約は EU の地理的プロファイル、翻訳はグローバルプロファイルにする
- C. 要約はグローバルプロファイルに SCP を組み合わせ、翻訳は EU の地理的プロファイルにする
- D. どちらも Provisioned Throughput を購入し、推論プロファイル経由で複数のリージョンに分散する

    **正解: B**

    データレジデンシーの要件があれば地理的プロファイルです。制約がなければ、グローバルプロファイルで約 10% 安くなります（モデルによる）。

    - B: 正しい。
    - C: 誤り。組み合わせが逆。グローバルはリージョンを選べない。
    - D: 誤り。推論プロファイルは Provisioned Throughput に対応しない。

### 問17 {#q17}

ある会社のアプリは東京リージョンから APAC の地理的プロファイルで Bedrock を呼び、一部のリクエストは別のリージョンで処理されています。財務の担当者は、リージョン間のルーティングの費用がいくら増えるかを心配しています。監査の担当者は、実際に処理したリージョンの記録を求めています。正しい説明はどれですか。

- A. 処理したリージョンの単価で課金され、記録はそのリージョンの CloudTrail にだけ残る
- B. ルーティングの料金とリージョン間の転送料金が、トークンの料金に上乗せされる

    - D: 正しい。

### 問18 {#q18}

ある会社は、`us-west-2` の S3 に 10 TB の文書を保管しています。それを読むパイプラインは `us-east-1` の Lambda で動き、そこから Bedrock を呼んで要約しています。Bedrock の費用に比べて、S3 からのリージョン間の転送費用が無視できません。使うモデルは `us-west-2` からも利用できます。データの制約は米国内です。最も適切な変更はどれですか。

- A. 文書を CRR で `us-east-1` へ複製し、そこから読む
- B. グローバルプロファイルに変えて、トークンの割引で転送費用を相殺する
- C. パイプラインを `us-west-2` へ移し、同じリージョンでモデルを呼ぶ
- D. Provisioned Throughput を `us-east-1` で購入し、データの読み取りを高速にする

??? success "答えと解説"

    - C: 正しい。
    - D: 誤り。S3 からの転送費用とは関係がない。
