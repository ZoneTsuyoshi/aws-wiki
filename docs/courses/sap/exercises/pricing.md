# 料金モデルの問題集

### 問1 {#q1}

ある製造業の会社は、東京リージョンの EC2 で基幹の API を動かしています。オンデマンド換算の費用は、夜間の最低が 120 USD/時、日中のピークが 300 USD/時です。今後 1 年で一部を Fargate へ移し、拠点の統合に伴って一部を大阪リージョンへ移す計画があります。処理の中断は許されず、容量の確保は要件にありません。3 年間の費用を最も抑えられる購入の組み合わせはどれですか。

- A. 東京の現在のファミリーに、ピーク相当の EC2 Instance Savings Plans を購入する
- B. 最低の利用量に合わせて Compute Savings Plans を購入し、残りはオンデマンドにする
- C. ピーク相当の Compute Savings Plans を購入し、夜間の余りは他の用途に回すことで無駄を減らす
- D. スタンダード RI を 3 年で購入し、構成が変わった時点で不要な分を RI マーケットプレイスで販売する

??? success "答えと解説"
    **正解: B**

    リージョンの変更と Fargate への移行があるので、どちらにも適用される Compute Savings Plans が合います。確約は常に使う量に合わせ、ピークはオンデマンドで受けます。

    - A: 誤り。EC2 Instance Savings Plans は選んだリージョンとファミリーの EC2 に限られ、Fargate と大阪には適用されない。ピーク相当の確約は夜間に余る。
    - B: 正しい。
    - C: 誤り。夜間に余った確約は払い続ける。ピーク相当の確約は過剰。
    - D: 誤り。スタンダード RI は Fargate に適用されない。販売の成立も保証されず手数料がかかる。

    **スキル:** [3.1.1](../domain3.md#skill-3-1-1) / **参照:** [Savings Plans](../../../services/cost-management.md#savings-plans)

### 問2 {#q2}

ある金融機関は、大阪リージョンを DR 先としています。東京の障害時には、大阪の特定の AZ で `r7i.4xlarge` を 20 台、必ず起動できなければなりません。多くの利用者が同時に切り替える状況でも起動に失敗しないことが要件です。組織にはすでに Compute Savings Plans があり、普段の待機コストは許容されています。最も適切なものはどれですか。

- A. 大阪リージョンに追加の Compute Savings Plans を購入する
- B. 大阪リージョンのスコープでリージョナル RI を購入する
- C. 障害時に複数のタイプを指定したスポットフリートを `capacity-optimized` で起動する
- D. その AZ に 20 台分のオンデマンドキャパシティ予約を作成する

??? success "答えと解説"
    **正解: D**

    必要なのは割引ではなく容量です。Capacity Reservation は指定の AZ で容量を確保し、Savings Plans と組み合わせて割引も受けられます。

    - A: 誤り。Savings Plans は割引だけで、容量を確保しない。
    - B: 誤り。リージョナル RI は容量を確保しない。確保するのはゾーナル RI。
    - C: 誤り。スポットは余剰容量の利用で、起動も継続も保証されない。
    - D: 正しい。

    **スキル:** [3.1.1](../domain3.md#skill-3-1-1) / **参照:** [購入オプション](../../../services/cost-management.md#purchase-options)

### 問3 {#q3}

ある動画サービスには 2 つのワークロードがあります。1 つは動画の変換で、ジョブは数分で終わり、失敗しても再実行できます。もう 1 つは注文 API で、今後 3 年は常時稼働します。注文 API は中断できず、来年には Graviton へ移す計画です。費用を最も下げる組み合わせはどれですか。（2つ選択）

- A. 変換ジョブは、複数のインスタンスタイプと AZ を指定したスポットで実行する
- B. 注文 API は、再調整の推奨を処理する仕組みを入れたうえでスポットで実行する
- C. 変換ジョブには、今のタイプのゾーナル RI を購入して容量も確保する
- D. 注文 API の常時稼働の分には、Compute Savings Plans を購入する
- E. 注文 API の常時稼働の分には、今のファミリーの EC2 Instance Savings Plans を購入する

??? success "答えと解説"
    **正解: A, D**

    中断してよい処理はスポットが最も安くなります。複数のタイプと AZ を指定すると、中断の影響を減らせます。ファミリーが変わる常時稼働には Compute Savings Plans が合います。

    - A: 正しい。
    - B: 誤り。再調整の推奨があっても、スポットは中断される。中断できない API には使わない。
    - C: 誤り。短時間で再実行できるジョブに、確約と容量確保は不要。
    - D: 正しい。
    - E: 誤り。Graviton へ移るとファミリーが変わり、確約が適用されなくなる。

    **スキル:** [3.1.1](../domain3.md#skill-3-1-1) / **参照:** [スポットインスタンス](../../../services/cost-management.md#spot)、[向いているものの選び方](../../../services/cost-management.md#purchase-choice)

### 問4 {#q4}

ある会社の組織には、EC2 のリージョナル RI、EC2 Instance Savings Plans、Compute Savings Plans がすべてあります。財務の担当者は、来月の使用量に割引がどの順で適用されるかを把握し、追加購入の判断に使いたいと考えています。AWS の適用の順序として正しいものはどれですか。

- A. Compute Savings Plans、EC2 Instance Savings Plans、RI の順
- B. EC2 Instance Savings Plans、RI、Compute Savings Plans の順
- C. RI、EC2 Instance Savings Plans、Compute Savings Plans の順
- D. 割引率が最も大きいものから順に、購入の種類を問わず適用される

??? success "答えと解説"
    **正解: C**

    Savings Plans は RI の適用後に使用量へ適用されます。Savings Plans の中では、適用範囲の狭い EC2 Instance が、範囲の広い Compute より先です。

    - A: 誤り。順序が逆。
    - B: 誤り。RI が先。
    - C: 正しい。
    - D: 誤り。割引率の大きい使用量から適用するのは Savings Plans の中の動作で、種類の順序は決まっている。

    **スキル:** [3.1.1](../domain3.md#skill-3-1-1) / **参照:** [Savings Plans](../../../services/cost-management.md#savings-plans)

### 問5 {#q5}

ある IoT 事業者は、機器のイベントを正規化する Step Functions の Standard ワークフローを運用しています。毎秒数千回起動され、各実行は 30 秒以内に終わります。処理は冪等で、`.sync` やコールバックのパターンは使っていません。状態遷移の課金が大きいため、費用を下げたいと考えています。最も適切なものはどれですか。

- A. Express のステートマシンを新しく作り、起動元を順に切り替えて古いものを消す
- B. 既存のステートマシンの設定を更新し、タイプを Express に変更する
- C. Standard のまま、Distributed Map の中で各イベントを処理するように変更する
- D. Standard のまま、すべての状態に `Retry` を設定して失敗による再実行を減らす

??? success "答えと解説"
    **正解: A**

    Express は実行回数、時間、メモリで課金されるので、大量で短い処理に向きます。タイプは作成後に変更できないので、作り直します。

    - A: 正しい。
    - B: 誤り。ワークフローのタイプは作成後に変更できない。
    - C: 誤り。Standard の状態遷移の課金は残る。
    - D: 誤り。`Retry` は失敗への対策で、正常な実行の状態遷移は減らない。

    **スキル:** [3.1.2](../domain3.md#skill-3-1-2) / **参照:** [Standard と Express](../../../services/step-functions.md#standard-express)

### 問6 {#q6}

あるチームは、数百の Lambda 関数の価格性能を改善したいと考えています。多くは Python の純粋なコードですが、一部は x86 用にだけ提供されるネイティブライブラリに依存しています。性能の低下は避ける必要があり、影響の大きい変更は段階的に進める方針です。最も適切な方法はどれですか。

- A. Provisioned Concurrency をすべての関数に設定し、コールドスタートの時間を減らす
- B. 依存を調べずに全関数を一度に `arm64` へ変更し、エラーが出た関数を `x86_64` へ戻す
- C. すべての関数のメモリを最小に下げ、1 ミリ秒あたりの単価を抑える
- D. 依存が対応する関数から `arm64` へ移し、メモリも実測で調整する

??? success "答えと解説"
    **正解: D**

    `arm64` は対応するコードなら価格性能を改善できます。ネイティブの依存があるものは移せません。Lambda の CPU はメモリに比例するので、メモリは実測で決めます。

    - A: 誤り。Provisioned Concurrency は待機中も課金され、費用は増える。
    - B: 誤り。本番で障害を起こす方法で、段階的に進める方針にも合わない。
    - C: 誤り。CPU も減り、実行時間が延びる。性能が下がり、費用が増えることもある。
    - D: 正しい。

    **スキル:** [3.1.2](../domain3.md#skill-3-1-2) / **参照:** [アーキテクチャ](../../../services/lambda.md#architecture)、[メモリと CPU の最適化](../../../services/lambda.md#memory-tuning)

- A. Lambda のまま、Compute Savings Plans だけを購入して割引を受ける
- B. Fargate へ移し、常時の分に Compute Savings Plans を適用する

ある会社は、オンプレミスから移行した EC2 を半年運用しました。CPU の平均使用率は 12% で、Compute Optimizer は多くのインスタンスで縮小を推奨しています。財務部門は今月中に 3 年の Savings Plans を購入して、費用をすぐに下げたいと求めています。アーキテクトが提案すべき進め方はどれですか。

- A. 今の使用量に合わせて今月 3 年の確約を購入し、その後で縮小を進める
- B. 推奨に従って縮小し、使用量が安定してから、新しい量に合わせて確約する
- C. 縮小はせず、コンバーティブル RI を購入し、必要になったら交換して調整する

### 問9 {#q9}

ある ECS サービスは、次のキャパシティプロバイダー戦略で動いています。`desiredCount` は 12 です。タスクの配置と、Fargate Spot の容量が不足したときの動作として正しいものはどれですか。

```json
"capacityProviderStrategy": [
  {"capacityProvider": "FARGATE", "base": 2, "weight": 1},
  {"capacityProvider": "FARGATE_SPOT", "weight": 4}
]
```

- A. `FARGATE` が 2、`FARGATE_SPOT` が 10。容量が不足すると Spot のタスクは待たされる
- B. `FARGATE` が 3、`FARGATE_SPOT` が 9。容量が不足すると通常の Fargate に切り替わる
- C. `FARGATE` が 4、`FARGATE_SPOT` が 8。容量が不足すると通常の Fargate に切り替わる
- D. `FARGATE` が 4、`FARGATE_SPOT` が 8。容量が不足しても通常の Fargate にはならない

??? success "答えと解説"
    **正解: D**

    先に `base` の 2 を `FARGATE` に置き、残り 10 を 1:4 に分けます。`FARGATE` は 2 + 2 で 4、`FARGATE_SPOT` は 8 です。Fargate は Spot の容量を自動でオンデマンドへ置き換えません。

    - A: 誤り。`weight` の配分を考えていない。
    - B: 誤り。数も動作も違う。
    - C: 誤り。数は正しいが、自動では切り替わらない。
    - D: 正しい。

    **スキル:** [3.1.3](../domain3.md#skill-3-1-3) / **参照:** [キャパシティプロバイダー](../../../services/containers.md#capacity-providers)

### 問14 {#q14}

- A. 全処理を Flex ティアで実行し、割引を受ける
- B. 全処理を Bedrock のバッチ推論へ移して費用を下げる
- C. 全処理を小さなモデルへ切り替えて単価を下げる
