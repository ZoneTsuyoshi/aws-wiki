### 問1 {#q1}

300 のアカウントを持つ企業が、全アカウントのタグ付きリソースを「毎日、7 日保持」で保護し、Finance の OU にだけ「毎月、1 年保持」を足したいと考えています。各アカウントの管理者が設定を変更できないようにし、新しいアカウントにも自動で適用します。最も適切なものはどれですか。

- A. 各アカウントのバックアッププランを CloudFormation のテンプレートで配布し、IAM ポリシーで変更を禁止する
- B. SCP で `backup:StartBackupJob` を必須にして、計画のないリソースの作成を拒否する
- C. ルートと Finance の OU に Organizations のバックアップポリシーを適用する
- D. 中央のアカウントの Lambda が、毎日すべてのアカウントで `StartBackupJob` を呼び出す

??? success "答えと解説"
    **正解: C**

    バックアップポリシーは組織の階層で継承され、統合されます。実効プランは各アカウントで変更できない形で表示されます。

    - A: 誤り。新しいアカウントへの配布や変更の防止に、別の仕組みが要ります。
    - B: 誤り。SCP は権限の上限を決めるものです。バックアップの実行を強制できません。
    - C: 正しい。
    - D: 誤り。独自の仕組みの運用が増え、保持の管理もできません。

    **スキル:** [4.3.1](../domain4.md#skill-4-3-1) / **参照:** [アカウント間コピーと組織での管理](../../../services/resilience.md#backup-cross-account)

### 問2 {#q2}

AWS Backup で、本番アカウントのバックアップを同じ組織のバックアップ用アカウントへコピーします。送信先のボールトのアクセスポリシーでは、本番アカウントに `backup:CopyIntoBackupVault` を許可しました。コピーを実行するのはカスタムの IAM ロールですが、コピーのジョブは権限のエラーで失敗します。組織の設定は有効です。最初に確認するものはどれですか。

- A. ロールのポリシーに `backup:CopyIntoBackupVault` があるか
- B. 送信先のボールトに Vault Lock のコンプライアンスモードと猶予期間が設定されているか
- C. 本番アカウントと送信先のアカウントが同じリージョンにあるか
- D. 本番アカウントのルートユーザーに MFA が設定されているか

??? success "答えと解説"
    **正解: A**

    アカウントをまたぐ呼び出しなので、`backup:CopyIntoBackupVault` はロールのポリシーと送信先のボールトのポリシーの両方に必要です。

    - A: 正しい。
    - B: 誤り。Vault Lock はコピーの受け入れに必須ではありません。
    - C: 誤り。アカウントはリージョンに属しません。別リージョンへのコピーもできます。
    - D: 誤り。ルートユーザーの MFA はジョブの権限に関係しません。

    **スキル:** [4.3.1](../domain4.md#skill-4-3-1) / **参照:** [アカウント間コピーと組織での管理](../../../services/resilience.md#backup-cross-account)

### 問3 {#q3}

RDS のスナップショットを AWS Backup で別のアカウントへコピーしたいです。RDS は AWS 管理キーの `aws/rds` で暗号化されており、コピーに失敗します。RDS は AWS Backup が完全に管理するリソースではありません。最も適切な対応はどれですか。

- A. `aws/rds` のキーポリシーを編集して、コピー先のアカウントを許可する
- B. カスタマー管理キーで暗号化した RDS に移し、キーをコピー先に共有する
- C. コピー先のボールトのキーを `aws/backup` に変更する
- D. コピー先のアカウントの IAM ロールに `kms:*` を付与する

??? success "答えと解説"
    **正解: B**

    AWS 管理キーのポリシーは変更できず、アカウントをまたいで共有できません。カスタマー管理キーで暗号化し、コピー先のアカウントへ共有します。

    - A: 誤り。AWS 管理キーのポリシーは変更できません。
    - B: 正しい。
    - C: 誤り。問題はコピー元のキーの共有です。
    - D: 誤り。コピー元のキーポリシーで許可されていなければ使えません。

    **スキル:** [4.3.1](../domain4.md#skill-4-3-1) / **参照:** [AWS Backup](../../../services/resilience.md#backup)、[アカウントをまたぐ暗号化](../../../services/kms.md#cross-account)

### 問5 {#q5}

2 つのリージョンのシステムを Route 53 のフェイルオーバーで切り替えています。ヘルスチェックは標準の 30 秒間隔で失敗のしきい値が 3 回、レコードの TTL は 300 秒です。訓練で切り替えに最大 6.5 分かかりました。切り替えの目標は 2 分です。追加の費用は問いません。最も適切な変更はどれですか。

- A. ヘルスチェッカーの場所を増やす
- B. しきい値を 3 回から 5 回に増やし、誤検知を減らす
- C. Route 53 を別のアカウントへ移し、コントロールプレーンの影響を避ける
- D. Fast の 10 秒間隔にし、TTL を 60 秒にする

??? success "答えと解説"
    **正解: D**

    所要時間は検知と TTL の合計です。30 秒 × 3 回 + 300 秒で最大 6.5 分です。10 秒 × 3 回 + 60 秒なら約 1.5 分になります。

    - A: 誤り。検知と TTL の時間は変わりません。
    - B: 誤り。検知がさらに遅くなります。
    - C: 誤り。アカウントを変えても、所要時間は変わりません。
    - D: 正しい。

    **スキル:** [4.3.2](../domain4.md#skill-4-3-2) / **参照:** [設計のポイント](../../../services/resilience.md#route53-design)

### 問6 {#q6}

プライベートホストゾーンのレコードで、VPC 内のプライベート IP にある内部 API をフェイルオーバーさせたいです。Route 53 のエンドポイント監視のヘルスチェックを作りましたが、API は正常なのに異常と判定されます。ヘルスチェックと同じアカウントに、API のエラー率の標準解像度のメトリクスがあります。最も適切な対応はどれですか。

- A. CloudWatch アラームを監視するヘルスチェックに変更する
- B. API を公開サブネットへ移し、ヘルスチェッカーからの通信を全世界に許可する
- C. ヘルスチェックを 10 秒間隔にして、到達できる回数を増やす
- D. 計算ヘルスチェックを親にして、エンドポイントの監視を子にする

??? success "答えと解説"
    **正解: A**

    ヘルスチェッカーは VPC 内のプライベート IP に届きません。CloudWatch アラームの型なら、メトリクスのデータで判定します。アラームは同じアカウントにあり、標準解像度である必要があります。

    - A: 正しい。
    - B: 誤り。内部 API を公開する必要はなく、攻撃の対象を増やします。
    - C: 誤り。届かないことは間隔を変えても解決しません。
    - D: 誤り。子のヘルスチェックが異常のままなので、解決しません。

    **スキル:** [4.3.2](../domain4.md#skill-4-3-2) / **参照:** [設計のポイント](../../../services/resilience.md#route53-design)、[Route 53 ヘルスチェック](../../../services/networking.md#route53-health-checks)

### 問7 {#q7}

監査で、AZ の障害時の RTO 5 分の実測の値を求められました。アプリは ALB、Auto Scaling、Multi-AZ の RDS で動いています。利用者から見た復旧までの時間を、再現できる方法で記録します。最も適切なものはどれですか。

- A. Resilience Hub の推定の RTO を、実測の値として報告する
- B. FIS で AZ の障害を起こし、Synthetics カナリアの失敗から成功までの時間を測る
- C. RDS のフェイルオーバーのイベントの時間を、そのまま全体の RTO として報告する
- D. 本番の障害が次に起きるのを待ち、そのときの CloudWatch のグラフから復旧の時間を読み取る

??? success "答えと解説"
    **正解: B**

    RTO は実測で確かめます。FIS で障害を再現し、利用者と同じ経路で動くカナリアで、失敗から成功に戻るまでの時間を測ります。

    - A: 誤り。評価の値は構成からの推定で、実測ではありません。
    - B: 正しい。
    - C: 誤り。データベースだけの時間で、検知や ALB の振り分けが含まれません。
    - D: 誤り。再現性がなく、障害を待つことになります。

    **スキル:** [4.3.2](../domain4.md#skill-4-3-2) / **参照:** [AWS Fault Injection Service](../../../services/resilience.md#fis)、[Synthetics](../../../services/operations.md#synthetics)

### 問8 {#q8}

Web 層の処理には常に 30 台が必要です。3 つの AZ を使います。AZ の 1 つが障害になっても、スケールを待たずに 30 台を保ちます。Auto Scaling グループの最小容量はいくつにしますか。

### 問14 {#q14}

S3 バケットはバージョニングと Object Lock のコンプライアンスモードで保護しています。攻撃者が盗んだ認証情報でバージョン ID を指定せずに `DeleteObject` を実行し、一覧にオブジェクトが表示されなくなりました。保持期間はまだ残っています。最も適切な説明と対応はどれですか。

- A. 削除マーカーが付いただけなので、削除マーカーを消して元のバージョンを見せる
- B. 保護が失敗してデータが消えたので、AWS サポートにコンプライアンスモードの解除を依頼する
- C. コンプライアンスモードは現行のバージョンを守らないので、ガバナンスモードに変えて復元する

    Object Lock は版を守りますが、削除マーカーの追加は防ぎません。バージョン ID のない削除は削除マーカーを作るだけで、保護された版は残ります。

    - A: 正しい。
    - B: 誤り。データは消えていません。コンプライアンスモードは解除できません。
