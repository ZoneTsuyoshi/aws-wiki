# ID のセキュリティの問題集

対象の解説: [IAM Identity Center と Directory Service](../../../services/identity-directory.md)、[IAM](../../../services/iam.md)、[Cognito](../../../services/cognito.md)

### 問1 {#q1}

ある製造業の会社は 40 の AWS アカウントを Organizations で運用し、各アカウントに IAM ユーザーが残っています。社員の認証にはすでに Microsoft Entra ID を使っています。退職者の AWS へのアクセスは、Entra ID で無効にした時点で自動的に止まる必要があります。IAM ユーザーをなくし、運用の負荷も最小にしたいと考えています。最も適切な設計はどれですか。

- A. 各アカウントに SAML の ID プロバイダーと IAM ロールを作り、退職者の処理は毎晩のスクリプトで各アカウントの信頼ポリシーへ反映する
- B. IAM Identity Center の ID ソースを外部 IdP にして、SAML と SCIM を設定し、権限セットをグループへ割り当てる
- C. IAM Identity Center の既定のディレクトリを使い、人事システムから毎晩 CSV を取り込んでユーザーを作成、削除する
- D. AD Connector を作成して Entra ID へ問い合わせを中継し、IAM ロールをディレクトリのグループに対応付ける

??? success "答えと解説"
    **正解: B**

    既存の IdP があるなら、SAML でサインインを連携し、SCIM でユーザーとグループを同期します。無効化も自動で反映されます。

    - A: 誤り。動作はしますが、アカウントごとの設定とスクリプトの保守が残り、運用の負荷が最小になりません。
    - B: 正しい。
    - C: 誤り。反映が毎晩になり、無効化の即時性がありません。パスワードの管理も二重になります。
    - D: 誤り。AD Connector はオンプレミスの Active Directory へ中継するもので、Entra ID への接続には使いません。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [ID ソース](../../../services/identity-directory.md#idc-identity-sources)、[権限セット](../../../services/identity-directory.md#idc-permission-sets)

### 問2 {#q2}

ある会社はオンプレミスの Active Directory を今後も残します。AWS 側では 8 つのワークロードアカウントで、EC2 の Windows サーバーと RDS for SQL Server をドメインに参加させます。社員は既存の AD アカウントでこれらを使います。AWS 側のサービスアカウントの認証は、Direct Connect が切れても続ける必要があります。最も適切な設計はどれですか。

- A. 共有サービス用アカウントに AD Connector を作り、RAM で 8 つのアカウントへ共有する
- B. 各アカウントに Simple AD を作り、オンプレミスの AD と双方向の信頼を結ぶ
- C. 共有サービス用アカウントに Managed Microsoft AD を置き、オンプレミスの AD と信頼を結んで各アカウントへ共有する
- D. 各アカウントの EC2 にドメインコントローラーを立て、オンプレミスのフォレストへ追加したうえで複製の監視とパッチ適用も自社で行う

??? success "答えと解説"
    **正解: C**

    Managed Microsoft AD は AWS に AD 本体を置くので、回線が切れても AWS 側のアカウントは認証できます。信頼関係で既存のユーザーも使えて、ディレクトリは他のアカウントへ共有できます。

    - A: 誤り。AD Connector は他のアカウントと共有できません。キャッシュを持たない中継なので、回線が切れると認証もできません。
    - B: 誤り。Simple AD は信頼関係に対応していません。
    - C: 正しい。
    - D: 誤り。要件は満たせますが、ドメインコントローラーの運用が自社に残ります。マネージドの選択肢より負荷が大きくなります。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [Directory Service](../../../services/identity-directory.md#directory-service)、[AD Connector](../../../services/identity-directory.md#ad-connector)、[信頼関係](../../../services/identity-directory.md#ad-trust)

### 問3 {#q3}

ある開発組織は SaaS の CI/CD サービスを使っています。このサービスは実行ごとに OIDC トークンを発行します。現在は各パイプラインに IAM ユーザーのアクセスキーを保存していますが、これをなくします。同じ SaaS を使う社内の他のリポジトリから、本番のデプロイ用ロールを引き受けられないようにする必要もあります。最も適切な設計はどれですか。

- A. OIDC プロバイダーを IAM に登録し、ロールの信頼ポリシーで `aud` と `sub` を検証する
- B. OIDC プロバイダーを IAM に登録し、ロールの信頼ポリシーで `aud` だけを検証して、本番環境へのデプロイはパイプラインの定義の中で手動の承認ステップを必須にする
- C. アクセスキーを Secrets Manager に移して 30 日ごとに自動でローテーションし、取得できるパイプラインをリソースポリシーで限定する
- D. 社内の CA で証明書を発行して SaaS の実行環境に保存し、IAM Roles Anywhere で引き受ける

??? success "答えと解説"
    **正解: A**

    OIDC トークンを持つワークロードは `AssumeRoleWithWebIdentity` で一時認証情報を得ます。`sub` にリポジトリやブランチが入るので、ここを条件にすると引き受けられる実行を限定できます。

    - A: 正しい。
    - B: 誤り。`aud` だけでは、同じ SaaS の他のリポジトリのトークンでも引き受けられます。パイプライン側の承認は IAM の制御になりません。
    - C: 誤り。長期の認証情報が残るので、要件を満たしません。
    - D: 誤り。トークンを使えるのに証明書の配布と保護の手間が増えます。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [フェデレーション](../../../services/iam.md#federation)、[STS の API の比較](../../../services/iam.md#sts-api-compare)

### 問4 {#q4}

ある会社は Okta を IAM Identity Center の ID ソースにして、SCIM で同期しています。導入から約 1 年後、既存の社員は問題なくサインインできるのに、新入社員が Identity Center に現れなくなりました。退職者のユーザーも残っています。AWS Health に関連する通知が数週間前から届いていました。最も可能性の高い原因と対処はどれですか。

- A. SAML のメタデータの証明書が期限切れなので、Okta の証明書を更新する
- B. 権限セットのセッション時間が短すぎるので、最大の時間へ延ばしてグループの割り当てをやり直す
- C. 委任管理者の設定が外れているので、管理アカウントで Identity Center の委任管理者を再度指定する
- D. SCIM のアクセストークンの期限が切れているので、再発行して Okta に設定する

??? success "答えと解説"
    **正解: D**

    SCIM のアクセストークンの有効期間は 1 年です。残り 90 日以下で通知が出ます。切れると同期だけが止まるので、既存のユーザーのサインインは続きます。

    - A: 誤り。SAML の証明書が切れると、既存の社員のサインインも失敗します。
    - B: 誤り。セッション時間はユーザーの同期に関係しません。
    - C: 誤り。委任管理者の設定は同期の認証情報ではありません。問題の症状と通知に合いません。
    - D: 正しい。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [ID ソース](../../../services/identity-directory.md#idc-identity-sources)

### 問5 {#q5}

ある動画共有アプリでは、モバイルの利用者が大きなファイルをアプリから S3 へ直接アップロードします。利用者はメールアドレスでサインアップします。自分のプレフィックスにしか書き込めないよう、AWS の権限で強制します。サーバーを経由させず、アプリに長期の認証情報を入れてはいけません。最も適切な組み合わせはどれですか。

- A. ユーザープールのアクセストークンをそのまま SigV4 の署名に使い、バケットポリシーでトークンの `sub` を検証する
- B. ユーザープールで認証し、ID プールで一時認証情報を取得して、ID を変数にしたプレフィックスだけを IAM ロールで許可する
- C. API Gateway の Cognito オーソライザーで認証し、すべてのファイルを Lambda 経由で S3 へ書き込む
- D. 書き込み専用の IAM ユーザーを 1 つ作り、キーを難読化してアプリに同梱し、S3 のプレフィックスはアプリのコードで分ける

??? success "答えと解説"
    **正解: B**

    ユーザープールは「誰か」を確認し、ID プールはその ID トークンを AWS の一時認証情報へ交換します。IAM ポリシーの変数にユーザーの ID を使うと、プレフィックスを分離できます。

    - A: 誤り。ユーザープールのトークンは SigV4 の署名に使えません。
    - B: 正しい。
    - C: 誤り。サーバーを経由するので要件に反します。大きなファイルでは API Gateway のペイロードの上限にも当たります。
    - D: 誤り。長期の認証情報を配布しています。分離もコードに頼っています。

    **スキル:** [2.1.2](../domain2.md#skill-2-1-2) / **参照:** [ユーザープールと ID プール](../../../services/cognito.md#user-vs-identity-pools)

### 問6 {#q6}

ある B2B の SaaS は、20 のマイクロサービスがそれぞれのコードで認可を判定しています。「文書の所有者と、同じ部署の編集者だけが更新できる」のような規則を変えるたびに、全サービスの改修が必要です。監査人は、現在の認可の規則を一か所で確認したいと求めています。認証はすでに Cognito のユーザープールで行っています。最も適切な設計はどれですか。

- A. 利用者ごとに IAM ロールを作り、文書ごとのリソースポリシーに主体を列挙して、各サービスが引き受ける
- B. 規則ごとにユーザープールのカスタムスコープを定義し、API Gateway のオーソライザーでスコープを検証する
- C. Verified Permissions に Cedar でポリシーを置き、各サービスから認可の判定を呼び出す
- D. 共通の認可ライブラリを社内で配布し、規則を設定ファイルにまとめて各サービスのデプロイ時に同梱する

??? success "答えと解説"
    **正解: C**

    Verified Permissions は、カスタムアプリの細かい認可を外に出すサービスです。ポリシーストアに規則が集まるので、規則の変更と監査を一か所で行えます。

    - A: 誤り。アプリの利用者の単位で IAM ロールを作るのは、クォータと運用の面で現実的ではありません。
    - B: 誤り。スコープは粗い権限の区別で、文書の所有者や部署のような属性との関係は判定できません。
    - C: 正しい。
    - D: 誤り。規則の変更に全サービスのデプロイが必要なままで、現在の課題を解決しません。

    **スキル:** [2.1.2](../domain2.md#skill-2-1-2) / **参照:** [Verified Permissions](../../../services/identity-directory.md#verified-permissions)、[アプリケーションレベルの認可](../../../services/cognito.md#app-authorization)

### 問7 {#q7}

ある会社は、Cognito のオーソライザーで保護した REST API を公開しています。新しく、取引先の夜間バッチがこの API を呼びます。バッチには操作する人がおらず、ブラウザもありません。取引先ごとに呼べる操作を制限し、失効もできるようにします。最も適切な方法はどれですか。

- A. 取引先ごとにサービス用のユーザーを作り、パスワードをバッチに設定して認可コードフローでトークンを取得する
- B. ID プールの未認証ロールを取引先に使わせ、API の IAM 認証で呼び出す
- C. 取引先ごとのインプリシットフローのアプリクライアントを作り、取得したトークンを長い有効期限で保存して使い回す
- D. 取引先ごとのアプリクライアントで、カスタムスコープとクライアントクレデンシャルを使う

??? success "答えと解説"
    **正解: D**

    サーバー同士の通信は OAuth 2.0 のクライアントクレデンシャルです。リソースサーバーのカスタムスコープで操作を分け、アプリクライアントを消せば失効できます。

    - A: 誤り。認可コードフローは人のサインインが前提です。サービス用ユーザーのパスワードも管理の対象になります。
    - B: 誤り。未認証ロールは誰でも使えるので、取引先を識別できません。
    - C: 誤り。インプリシットは古い方式で、人のブラウザが前提です。バッチには合いません。
    - D: 正しい。

    **スキル:** [2.1.2](../domain2.md#skill-2-1-2) / **参照:** [OAuth フロー](../../../services/cognito.md#oauth-flows)、[OAuth の設定](../../../services/cognito.md#oauth-settings)

### 問8 {#q8}

ある EKS クラスターでは、Linux の EC2 ノードグループの上で 15 のチームの Pod が動いています。今はノードのロールにすべての権限を付けています。チームごとに異なる IAM ロールを使わせたいと考えています。この会社では OIDC プロバイダーの作成は別の部門の担当で、クラスターの管理者には権限がありません。ロールとクラスターは同じアカウントにあります。最も適切な方法はどれですか。

- A. 各チームのサービスアカウントに IRSA を設定し、OIDC プロバイダーの作成はチケットで別の部門へ毎回依頼する
- B. EKS Pod Identity のアソシエーションを、サービスアカウントごとに作成する
- C. チームごとのアクセスキーを Kubernetes の Secret に保存し、環境変数として Pod に渡す
- D. チームごとにノードグループを分け、ノードのロールで権限を変えて、Taint で Pod の配置先を固定する

    - B: 正しい。
    - C: 誤り。長期の認証情報が残ります。
    - D: 誤り。分離はできますが、ノードグループが増えて費用と運用が増えます。同じノードのチームの Pod にも権限が及ぶ構造は変わりません。

### 問10 {#q10}

ある組織は、開発チームに Lambda の実行ロールを自分で作らせたいと考えています。ただし、開発者が強い権限のロールを作り、それを使って権限を昇格できないようにします。セキュリティチームが毎回レビューする運用は避けます。最も適切な設計はどれですか。

- A. SCP で `iam:CreateRole` を全面的に拒否し、ロールの作成はセキュリティチームへの依頼に一本化する
- B. Access Analyzer の未使用アクセスの検出結果を週次で確認し、強すぎるロールを見つけたら削除する
- C. ロールの作成を許す条件に `iam:PermissionsBoundary` を付け、指定の権限境界を必須にする

    - A: 誤り。開発チームに任せるという要件に反し、依頼の運用が残ります。
    - B: 誤り。検出は事後です。作られたロールを防げません。
    - C: 正しい。
    - D: 誤り。呼び出し側のセッションポリシーは、関数の実行ロールの権限を狭めません。

    **スキル:** [2.1.3](../domain2.md#skill-2-1-3) / **参照:** [権限境界の設定](../../../services/iam.md#permissions-boundary)

### 問11 {#q11}

ある研究機関では 200 のプロジェクトが同じアカウントで S3 と DynamoDB を使い、プロジェクトごとの IAM ロールが増え続けています。プロジェクトは毎月増えます。利用者のサインインには IAM Identity Center を使い、IdP の属性にプロジェクト名があります。ポリシーの数を増やさず、利用者が他のプロジェクトのリソースにアクセスできないようにしたいと考えています。満たすべき対策はどれですか。（2つ選択）

- A. プロジェクトごとの権限セットを作り、対象の ARN を列挙する処理をプロビジョニングで自動化する
- B. プリンシパルのタグとリソースのタグを比べる 1 つのポリシーにする
- C. 利用者が AWS Config のルールで、タグのないリソースを毎週確認して修正する
- D. プロジェクトのタグを利用者が変更できないよう、タグの操作を拒否する
- E. プロジェクトごとにセッションポリシーを渡すポータルを社内で開発し、サインインの代わりに使う

    - A: 誤り。自動化しても、権限セットと ARN の数が増え続ける構造は変わりません。
    - B: 正しい。
    - C: 誤り。Config は検出で、アクセスを防ぎません。
    - D: 正しい。
    - E: 誤り。独自のポータルの開発と運用が増えます。既存のセッションタグで足ります。

    **スキル:** [2.1.3](../domain2.md#skill-2-1-3) / **参照:** [ABAC](../../../services/identity-directory.md#idc-abac)、[セッションタグ](../../../services/iam.md#session-tags)

### 問12 {#q12}

ある SaaS の提供者は、多数の顧客の AWS アカウントのロールを引き受けて、設定の監査を行います。顧客 B が、顧客 A のロール ARN を自分の設定として登録すると、SaaS が A のデータを B に見せてしまう恐れがあります。提供者のアカウント ID を信頼するだけでは防げません。提供者として取るべき設計はどれですか。

- B. 提供者が顧客ごとに一意の外部 ID を発行し、顧客の信頼ポリシーの条件にしてもらって、引き受けのたびに渡す
- C. 顧客の信頼ポリシーで、提供者の特定のロール ARN だけを信頼し、SaaS の中の処理をロールで分ける

    **正解: B**

    混乱した代理問題の対策です。外部 ID は提供者が発行し、顧客が変更できないようにします。提供者は顧客の設定に保存した ID を渡すので、B が A のロールを登録しても条件に一致しません。

    - A: 誤り。顧客が値を決められると、B が A の値を当てて登録する余地があります。
    - B: 正しい。
    - C: 誤り。同じ提供者のロールが全顧客のロールを引き受ける構造は同じで、代理問題は残ります。
    - D: 誤り。SaaS の自動処理に MFA は合いません。代理問題の対策にもなりません。

分析アカウントのロールが、データアカウントの S3 バケットのオブジェクトを読みます。オブジェクトはデータアカウントのカスタマー管理キーによる SSE-KMS で暗号化されています。バケットポリシーとロールの IAM ポリシーでは `s3:GetObject` を許可済みです。それでも `GetObject` が `AccessDenied` になります。CloudTrail には `kms:Decrypt` の拒否が記録されています。最も適切な対処はどれですか。
