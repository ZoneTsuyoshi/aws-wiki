# 運用の自動化の問題集

対象の解説: [運用](../../../services/operations.md)、[耐障害性のパターン](../../../services/sdk-resilience.md)、[EC2 Auto Scaling](../../../services/ec2-beanstalk.md#auto-scaling)

### 問1 {#q1}

ある企業は、主系を東京、DR を大阪としたパイロットライトの構成です。DR の訓練でスケールアウトを実行したところ、大阪で EC2 の起動がクォータの超過で失敗し、RTO を満たせませんでした。大阪では普段ほとんどリソースを動かしていません。同じ問題を防ぐ最も適切な対策はどれですか。

- A. 訓練の結果を受けて、実際の障害のときに AWS サポートへ緊急の引き上げを依頼する手順を整備する
- B. 東京のクォータを引き上げる。クォータは全リージョンで共有されるので大阪にも適用される
- C. 大阪のクォータを主系と同じ値へ事前に引き上げ、使用率を監視する
- D. 大阪でも東京と同じ台数のインスタンスを常時動かして、実績を作ることで上限を自動で上げる

??? success "答えと解説"
    **正解: C**

    クォータの多くはリージョンごとです。障害のときに申請していては間に合わないので、DR のリージョンの値を事前に上げます。

    - A: 誤り。切り替えの最中の申請では RTO を守れません。
    - B: 誤り。リージョンのクォータは共有されません。
    - C: 正しい。
    - D: 誤り。パイロットライトの費用の利点を失い、実績でクォータが自動で上がる保証もありません。

    **スキル:** [5.4.1](../domain5.md#skill-5-4-1) / **参照:** [クォータの上限に近づいたとき](../../../services/observability.md#quota-alerts)、[パイロットライト](../../../services/resilience.md#pilot-light)

### 問2 {#q2}

Lambda の同時実行や EC2 の vCPU の使用率が、上限に近づいた時点で運用チームに通知されるようにします。担当者は毎月の棚卸しで手作業で確認していましたが、キャンペーンの直前に上限へ達した経験があります。上限が引き上げられたら、しきい値も自動で追随させたいです。最も適切な方法はどれですか。

- A. `AWS/Usage` のメトリクスと `SERVICE_QUOTA()` の式で使用率を出し、80% でアラームを設定する
- B. 現在の上限の値を固定のしきい値に書いたアラームを作り、上限が変わるたびに手で更新する
- C. 毎日 Lambda で各サービスのリソースの一覧を取得して数え、スプレッドシートの上限と比べる
- D. Budgets でサービスごとの費用のアラートを作り、費用の増加を上限の接近とみなす

??? success "答えと解説"
    **正解: A**

    対応するサービスの使用量は `AWS/Usage` に記録されます。`m1 / SERVICE_QUOTA(m1) * 100` の式なら、上限が変わっても追随します。

    - A: 正しい。
    - B: 誤り。上限の変更に追随せず、更新の漏れが起きます。
    - C: 誤り。独自の開発と保守が必要で、対応するメトリクスの機能を活かしていません。
    - D: 誤り。費用はクォータの使用率を示しません。

    **スキル:** [5.4.1](../domain5.md#skill-5-4-1) / **参照:** [クォータの上限に近づいたとき](../../../services/observability.md#quota-alerts)

### 問3 {#q3}

組織には 100 のアカウントがあります。セキュリティのアカウントに EventBridge のルールを作り、AWS Health のイベントを受け取りましたが、そのアカウント自身のイベントしか届きません。運用チームは、全アカウントの Health のイベントを 1 か所で見て、通知の流れに載せたいです。管理アカウントでの日常の作業は避けます。最も適切な方法はどれですか。

- A. 各メンバーアカウントのルートユーザーのメールアドレスを、共通のメーリングリストにする
- B. セキュリティのアカウントのバスポリシーを変更すれば、全アカウントの Health のイベントが自動で届く
- C. CloudTrail の組織の証跡を作り、Health のイベントを CloudTrail のログから抽出する
- D. Health の組織ビューを有効にし、委任管理者を使う

??? success "答えと解説"
    **正解: D**

    EventBridge のルールは自分のアカウントのイベントだけを受け取ります。組織全体を見るには、組織ビューと委任管理者を使います。

    - A: 誤り。メールでは自動の処理につながらず、一元管理の仕組みになりません。
    - B: 誤り。バスポリシーは他のアカウントからの受信の許可で、送る側のルールがなければ届きません。
    - C: 誤り。Health のイベントは CloudTrail の API の記録ではありません。
    - D: 正しい。

    **スキル:** [5.4.1](../domain5.md#skill-5-4-1) / **参照:** [AWS Health イベントの自動化](../../../services/operations.md#health-events)

### 問4 {#q4}

EC2 のインスタンスのリタイアの予定が、不規則に通知されます。担当者が気づくのが遅れ、予定の時刻にインスタンスが止まったことがありました。通知を受けたら、対象のインスタンスを自動で停止、再開して別のホストへ移します。対象には EBS をルートとするインスタンスと、インスタンスストアをルートとする古いインスタンスがあります。設計として最も適切なものはどれですか。

- A. CloudWatch の `StatusCheckFailed` のアラームを待ち、失敗したインスタンスを全種類とも再起動する
- B. Health のイベントを EventBridge で受け、EBS をルートとするものだけ Automation で処理し、残りは人に通知する
- C. Health のイベントを EventBridge で受け、すべてのインスタンスを Automation で停止、再開する
- D. Maintenance Windows で毎週すべてのインスタンスを順に再起動する

??? success "答えと解説"
    **正解: B**

    `AWS_EC2_INSTANCE_RETIREMENT_SCHEDULED` のようなイベントで Automation を起動できます。停止と再開で移せるのはルートデバイスが EBS のものです。インスタンスストアのデータは失われます。

    - A: 誤り。障害が起きてからの対応で、再起動では別のホストへ移りません。
    - B: 正しい。
    - C: 誤り。インスタンスストアのルートでは、停止による移動はできません。
    - D: 誤り。不要な再起動が増え、再起動では別のホストへ移りません。

    **スキル:** [5.4.1](../domain5.md#skill-5-4-1) / **参照:** [AWS Health イベントの自動化](../../../services/operations.md#health-events)

### 問5 {#q5}

Automation のランブックで 1,000 台のインスタンスの設定を修復します。`MaxConcurrency` を 50、`MaxErrors` を 3 に設定しました。ある担当者は「失敗は絶対に 3 件までに収まる」と説明しています。実際の動きと、失敗の上限を厳密に守る方法の組み合わせとして正しいものはどれですか。

- A. 4 件目のエラーで新しい対象への送信を止めるが、実行中の分でさらに失敗しうる。厳密に守るには同時実行を 1 にする
- B. 3 件目のエラーで実行中の分もすべて即座に中止して元に戻すので、説明は正しい。追加の設定は不要である
- C. エラーのしきい値は全台の処理が終わった後に評価されるので、失敗は上限を超える。厳密に守るには再試行の回数を増やす
- D. `MaxErrors` はアカウントあたりの値なので、組織全体での上限になる。厳密に守るには委任管理者から実行する

??? success "答えと解説"
    **正解: A**

    `3` を指定すると 4 件目のエラーで止めます。ただし実行中のものは完了するので、失敗はさらに増えることがあります。上限を厳密に守るなら、同時実行を 1 にします。

    - A: 正しい。
    - B: 誤り。実行中の分は中止されません。
    - C: 誤り。しきい値は処理の途中で評価されます。
    - D: 誤り。対象の集合に対する値で、委任管理者とは関係ありません。

    **スキル:** [5.4.2](../domain5.md#skill-5-4-2) / **参照:** [レート制御](../../../services/operations.md#automation-rate-control)、[Run Command](../../../services/operations.md#run-command)

### 問6 {#q6}

共有の SaaS の API で、ある大口顧客の異常なリクエストが全顧客の障害につながりました。アーキテクトはセルベースのアーキテクチャへの移行を計画しています。セルの間の依存を減らし、デプロイの影響の範囲も限定したいです。設計として最も適切なものはどれですか。

- A. セルごとにアプリを分け、データベースは全セルで共有して整合性を保つ
- B. ルーターに顧客ごとの複雑な業務ロジックを集約し、セルを軽くする
- C. 顧客 ID でセルを割り当て、状態を共有せず、セルごとに段階的にデプロイする
- D. 全セルへ同時にデプロイして、セル間のバージョンの差をなくす

??? success "答えと解説"
    **正解: C**

    セルは状態を共有せず、パーティションキーで振り分けます。ルーターは単純に保ち、デプロイはセルごとに段階的に進めます。

    - A: 誤り。共有のデータベースが障害の範囲を全体に広げます。
    - B: 誤り。ルーターは共有の部品なので、複雑にすると障害の影響が大きくなります。
    - C: 正しい。
    - D: 誤り。悪い変更が全セルへ同時に広がります。

    **スキル:** [5.4.2](../domain5.md#skill-5-4-2) / **参照:** [REL10-BP03（公式）](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_fault_isolation_use_bulkhead.html)、[スロットリングの階層](../../../services/api-gateway.md#throttling)

### 問7 {#q7}

同じアカウントに、決済の Lambda と夜間のバッチの Lambda があります。夜間のバッチが急増すると、アカウントの同時実行数の枠を使い切り、決済の関数がスロットリングされます。決済の処理を守りつつ、バッチが決済の枠を奪えないようにしたいです。追加の費用はなるべく抑えます。最も適切な方法はどれですか。

- A. 両方の関数を Provisioned Concurrency で常時起動する
- B. 決済の関数のタイムアウトを延ばし、再試行の回数を増やして、スロットリングを吸収する
- C. バッチの関数のメモリを増やして、処理時間を短くすることで枠の問題を解消する
- D. 決済の関数に予約済み同時実行を設定し、必要ならバッチの関数にも上限を設定する

??? success "答えと解説"
    **正解: D**

    予約済み同時実行はバルクヘッドです。関数に枠を確保し、他の関数に奪われません。同時に上限にもなるので、バッチの暴走も抑えられます。予約に追加料金はかかりません。

    - A: 誤り。常時起動の費用がかかり、要件の枠の分離が目的なら過剰です。
    - B: 誤り。枠が空かない限り解決せず、負荷も増えます。
    - C: 誤り。処理時間が短くなる保証がなく、確実な分離にもなりません。
    - D: 正しい。

    **スキル:** [5.4.2](../domain5.md#skill-5-4-2) / **参照:** [予約済み同時実行](../../../services/lambda.md#reserved-concurrency)

### 問8 {#q8}

あるマイクロサービスが依存先の障害で失敗すると、全インスタンスが同じ間隔ですぐに再試行し、回復しかけた依存先を再び倒してしまいます。障害が長引く間は、無駄な呼び出しもやめて素早く失敗を返したいです。必要な組み合わせはどれですか。（2つ選択）

- A. タイムアウトを無制限にして、応答があるまで接続を保つ
- B. 指数バックオフとジッターで再試行の間隔をずらす
- C. 再試行の回数を増やし、間隔は固定の 1 秒のままにする
- D. 失敗が続いたら呼び出しを一時的に止めるサーキットブレーカーを入れる
- E. 依存先の障害の間は、Auto Scaling で呼び出し側のインスタンスを増やす

??? success "答えと解説"
    **正解: B, D**

    指数バックオフとジッターは再試行の集中を防ぎます。サーキットブレーカーは失敗が続く間の呼び出しを止め、依存先への追加の負荷を防ぎます。

    - A: 誤り。接続とスレッドを消費し続け、素早く失敗を返せません。
    - B: 正しい。
    - C: 誤り。再試行の集中が悪化します。
    - D: 正しい。
    - E: 誤り。呼び出しが増えて、依存先の負荷がさらに増えます。

    **スキル:** [5.4.2](../domain5.md#skill-5-4-2) / **参照:** [サーキットブレーカー](../../../services/sdk-resilience.md#circuit-breaker)、[指数バックオフとジッター](../../../services/sdk-resilience.md#backoff-jitter)

### 問9 {#q9}

Config ルールの自動修復で、許可しないセキュリティグループのルールを削除しています。あるチームのデプロイのツールが、削除されたルールをすぐに作り直すので、修復とデプロイが繰り返され、API の呼び出しも増えました。修復が障害を広げないように、安全の制約を入れます。最も適切な対応はどれですか。

- A. 修復のロールに管理者の権限を付け、失敗をなくして処理を早く終わらせる
- B. 再試行の回数と時間を設定し、結果を OpsItem で人に知らせて、原因のツールを修正する
- C. 修復を EventBridge の 1 分ごとのスケジュールに変え、確実に消し続ける
- D. Config のレコーダーを止めて評価が起きないようにして、修復の連鎖を止める

??? success "答えと解説"

    - A: 誤り。繰り返しの原因は権限ではなく、過大な権限は修復の誤りの影響を広げます。
    - B: 正しい。
    - C: 誤り。繰り返しが増えます。
    - D: 誤り。全リソースの記録と評価が止まり、ガバナンスの統制を失います。

    **スキル:** [5.4.2](../domain5.md#skill-5-4-2) / **参照:** [EventBridge による修復パターン](../../../services/operations.md#eventbridge-remediation)、[Config の修復](../../../services/governance.md#config-remediation)

### 問10 {#q10}

SQS のキューを処理する EC2 の Auto Scaling グループがあります。CPU を基準にしたターゲット追跡では、処理待ちが増えても CPU が高くならないジョブがあり、遅れが出ます。許容できる遅延と 1 件の処理時間から、1 台あたり 20 件の待ちなら許容できると分かりました。最も適切なスケーリングはどれですか。

- A. `ApproximateNumberOfMessagesVisible` を基準にステップスケーリングを作り、件数の範囲ごとに固定の台数を追加する
- B. 1 台あたりの待ち件数を指標にし、20 を目標値にしたターゲット追跡を作る

    - B: 正しい。
    - C: 誤り。CPU が処理の待ちを表さないという問題は変わらず、無駄も増えます。

- A. 最小の台数を朝のピークに合わせて 24 時間固定し、夜と週末も同じ台数のまま運用する

- A. 予測スケーリングだけを有効にして、キャンペーンの負荷も履歴から予測させる
- B. CPU のターゲット追跡だけを使い、放送の開始後に増やす
- C. 手動の容量の変更だけで対応し、放送の間は担当者が画面を見て台数を増やす
- D. 放送前に容量を増やすスケジュールを作り、ターゲット追跡も併用する
