# 移行戦略の問題集

対象の解説: [移行と転送](../../../services/migration.md)。分野4のタスク 4.1 を扱います。

### 問1 {#q1}

製造業の企業が、5 か月後に契約が切れるデータセンターから AWS へ移行します。調査の結果、320 台のサーバーは次のとおりでした。35 台は 90 日間接続がなく、CPU とメモリの平均も 5% 未満です。8 台は工場の専用ハードウェアに依存し、更改の予定もありません。250 台は Web とアプリのサーバーで、27 台は自前で運用している MySQL です。経営層は期限を守ることを最優先とし、モダナイズは移行後に進めると決めています。最も適切な方針はどれですか。

- A. 35 台を Retain、8 台を Relocate、250 台を Refactor、27 台を Rehost にする
- B. 35 台を Retire、8 台を Retain、250 台を Rehost、27 台を Replatform にする
- C. 35 台を Rehost、8 台を Retain、250 台を Replatform、27 台を Refactor にする
- D. 全 320 台を同じ手順にそろえるため、まず Rehost してから不要なサーバーを判断する

??? success "答えと解説"
    **正解: B**

    使われていないサーバーは止め、依存があるものは残し、残りは短期間で移します。AWS の大規模移行の指針でも、最初から Refactor することは推奨されていません。

    - A: 誤り。未使用のサーバーを残すと費用が続きます。250 台の Refactor は 5 か月の期限に間に合いません。
    - B: 正しい。
    - C: 誤り。未使用のサーバーを移す意味がありません。27 台の Refactor も期限に合いません。
    - D: 誤り。不要なサーバーの移行に時間と費用を使います。専用ハードウェアに依存する 8 台は移せません。

    **スキル:** [4.1.1](../domain4.md#skill-4-1-1) / **参照:** [移行の 7 つの R](../../../services/migration.md#seven-rs)

### 問2 {#q2}

これまで AWS の移行サービスを使ったことがない企業が、900 台の VMware と物理サーバーを移します。サーバーの一覧を複数の情報源から集め、アプリのまとまりと依存関係を見つけて、移行ウェーブを作りたいと考えています。計画の専任者は少なく、追加のツールの費用も抑えたい状況です。最も適切なものはどれですか。

- A. Application Discovery Service のエージェントを全台に入れ、Migration Hub で進捗を追跡する
- B. Migration Evaluator の Quick Insights で、依存関係とウェーブの案を作る
- C. 表計算で一覧を管理し、各チームへの聞き取りで依存関係を確認して、ウェーブを手作業で作る
- D. AWS Transform の発見と移行計画で、複数の情報源の一覧から移行ウェーブを作る

??? success "答えと解説"
    **正解: D**

    AWS Transform は複数の情報源からサーバー一覧を集めて分析し、依存関係を見つけて移行ウェーブを作ります。追加料金はかかりません。

    - A: 誤り。Application Discovery Service と Migration Hub は新規受付を終了しており、初めて使う企業は選べません。
    - B: 誤り。Migration Evaluator は費用対効果の比較に使います。依存関係の調査はしません。
    - C: 誤り。900 台では手間がかかり、依存関係の漏れも起きやすくなります。
    - D: 正しい。

    **スキル:** [4.1.1](../domain4.md#skill-4-1-1) / **参照:** [AWS Transform](../../../services/migration.md#transform)、[Migration Hub](../../../services/migration.md#migration-hub)

### 問3 {#q3}

ある企業の CFO は、800 台の x86 サーバーを AWS に移した場合の費用を、取締役会で説明したいと考えています。今回は依存関係の調査は不要です。現在の構成、使用率、OS のライセンスをもとに、EC2 へ対応付けた予想費用を出す必要があります。AWS にはまだワークロードがありません。最も適切なものはどれですか。

- A. Migration Evaluator で現状を収集し、Quick Insights で費用を示す
- B. 全サーバーの仕様を AWS Pricing Calculator に 1 台ずつ手で入力する
- C. AWS Compute Optimizer のサイズ変更の推奨を集計する
- D. Cost Explorer の予測機能で、今後 12 か月の費用を出す

??? success "答えと解説"
    **正解: A**

    Migration Evaluator はオンプレミスの x86 サーバーの構成、ライセンス、使用率を EC2 に対応付けます。Quick Insights で、AWS で購入する場合の予想費用を 1 年の期間で示します。

    - A: 正しい。
    - B: 誤り。使用率を反映できず、800 台の入力は手間がかかります。
    - C: 誤り。Compute Optimizer は AWS 上のリソースを分析します。移行前の環境には使えません。
    - D: 誤り。Cost Explorer の予測は AWS の利用実績にもとづきます。実績がないので使えません。

### 問4 {#q4}

移行ウェーブを計画しています。勤怠システムは他のシステムに依存せず、止まっても影響は小さいです。受注システムと在庫システムは 1 回の処理で数百回の呼び出しを交わし、遅延に敏感です。会計システムは他に依存しませんが、月末の締め処理の期間は止められません。チームには移行の経験がありません。最も適切な計画はどれですか。

- A. 重要度の高い受注システムを最初に移し、問題があれば早く見つけられるようにする
- B. 受注と在庫を別のウェーブに分け、一度に動かす範囲を小さくする。その間は Direct Connect で通信する
- C. 勤怠を最初のウェーブにし、受注と在庫は同じウェーブにまとめ、会計は締めの期間を避ける
- D. 全システムを同じ週末に移して、オンプレミスとの通信が発生しないようにする

??? success "答えと解説"
    **正解: C**

    最初のウェーブは影響が小さく、学びの多いアプリにします。依存関係の強いアプリは同じウェーブにまとめます。

    - A: 誤り。経験のないチームが最も重要なシステムから始めると、失敗の影響が大きくなります。
    - B: 誤り。遅延に敏感な呼び出しが回線をまたぐと、移行の途中で性能が落ちます。
    - C: 正しい。
    - D: 誤り。切り戻しの範囲が全システムになり、経験のないチームには危険です。

    **スキル:** [4.1.1](../domain4.md#skill-4-1-1) / **参照:** [AWS Transform](../../../services/migration.md#transform)、[移行の 7 つの R](../../../services/migration.md#seven-rs)

### 問5 {#q5}

AWS Transform MGN で移行を始めました。元のサーバーにエージェントを入れると、コンソールにサーバーが登録されました。しかし、状態は Not ready のままで、初回の同期が進みません。元のサーバーのあるネットワークからは、VPC 内のステージングエリアのサブネットへの通信を、ファイアウォールで制限しています。最初に確認するものはどれですか。

- A. 元のサーバーから MGN のエンドポイントへの TCP 443
- B. 起動テンプレートのインスタンスタイプ
- C. 元のサーバーからステージングエリアのサブネットへの TCP 1500
- D. カットオーバーインスタンスのサブネットのネットワーク ACL と、そのルートテーブル

??? success "答えと解説"
    **正解: C**

    データの複製は TCP 1500 で、ステージングエリアのレプリケーションサーバーへ送ります。ここが閉じていると、初回の同期が進みません。

    - A: 誤り。登録に成功しているので、443 は通っています。
    - B: 誤り。起動テンプレートはテストとカットオーバーの設定で、同期には関係しません。
    - C: 正しい。
    - D: 誤り。カットオーバーインスタンスはまだ起動していません。同期とは別の話です。

    **スキル:** [4.1.2](../domain4.md#skill-4-1-2) / **参照:** [通信の要件](../../../services/migration.md#mgn-network)

### 問6 {#q6}

小売企業が、物理サーバーと VMware 上の 180 台の Windows と Linux を AWS に移します。アプリの変更はせず、切り替えの停止は分単位に抑えます。本番の前に AWS 上で起動を確かめ、問題があれば元のサーバーで業務を続けながらやり直せるようにします。移行後は DR の複製を続けません。最も適切なものはどれですか。

- A. AWS Transform MGN で継続的に複製し、テストの後にカットオーバーする
- B. AWS Elastic Disaster Recovery で継続的に複製し、全台で恒久的に復旧を実行する
- C. AWS DMS の `full-load-and-cdc` タスクを、全サーバーのボリュームごとに作成する
- D. MGN の vCenter のエージェントレス複製を新たに導入し、物理サーバーだけは別途 AMI を手で作成する

??? success "答えと解説"
    **正解: A**

    MGN はブロック単位の複製で、テストインスタンスで確認してからカットオーバーします。移して終わりなら MGN です。

    - A: 正しい。
    - B: 誤り。DRS は備え続けるためのサービスです。移行後に複製を続けないなら合いません。
    - C: 誤り。DMS はデータベースを移すサービスで、サーバーのボリュームは移せません。
    - D: 誤り。エージェントレス複製は新規のデプロイでは使えません。

    **スキル:** [4.1.2](../domain4.md#skill-4-1-2) / **参照:** [AWS Transform MGN](../../../services/migration.md#mgn)、[選び方の比較](../../../services/migration.md#choosing)

### 問7 {#q7}

金融系の企業が 600 台の VM を AWS へ移します。VMware Cloud Foundation のサブスクリプションがあり、IP アドレス、運用手順、運用チームのスキルを変えたくありません。AWS のサービスとして VPC 内で動かすことを希望しています。VMware のライセンスをやめる予定はありません。最も適切なものはどれですか。

- A. AWS Transform MGN で全台を EC2 へリホストする
- B. AWS Transform で全台をコンテナ化して EKS へ移す
- C. VMware Cloud on AWS を AWS から新規に購入し、AWS の請求にまとめる
- D. Amazon Elastic VMware Service（EVS）へ Relocate する

    **正解: D**

- A. 3 台を MGN から削除せず、起動テンプレートのインスタンスタイプを大きくする

### 問9 {#q9}

オンプレミスの Oracle Database を、ライセンス費用を減らすために Aurora PostgreSQL へ移します。データベースは 24 時間動いており、切り替えの停止は 15 分以内です。ストアドプロシージャも多数あります。最も適切な組み合わせはどれですか。

- A. Oracle Data Pump でダンプを取り、切り替えの週末に Aurora へ読み込む
- B. スキーマを DMS Schema Conversion か SCT で変換し、データは DMS の `full-load-and-cdc` で移す
- C. AWS Transform MGN で DB サーバーを複製し、カットオーバー後にエンジンを PostgreSQL に変える
- D. スキーマの変換は DMS の基本の作成に任せ、ストアドプロシージャは DMS の全ロードで移す

??? success "答えと解説"
    **正解: B**

    異なるエンジンでは、スキーマとコードの変換とデータの移行を分けます。変換は SCT か DMS Schema Conversion、データは DMS です。全ロードの後に変更を流し続ければ、停止を短くできます。

    - A: 誤り。Oracle のダンプは PostgreSQL に読み込めません。週末の停止も要件を超えます。
    - B: 正しい。
    - C: 誤り。MGN はサーバーをそのまま移すだけで、エンジンは変わりません。
    - D: 誤り。DMS が作るのはテーブルと主キーなどの基本だけです。ストアドプロシージャは移せません。

    **スキル:** [4.1.3](../domain4.md#skill-4-1-3) / **参照:** [AWS SCT と DMS Schema Conversion](../../../services/migration.md#sct)、[移行タイプ](../../../services/migration.md#dms-migration-types)

### 問10 {#q10}

RDS for MySQL をソースに、DMS の `full-load-and-cdc` タスクで移行します。全ロードは完了しましたが、その後の変更をタスクが読めません。ソースのパラメータでは `binlog_format` が `STATEMENT` で、自動バックアップの保持期間は 0 日です。CDC を動かすために必要な変更はどれですか。（2つ選択）

- A. ターゲットの DB インスタンスを Multi-AZ にする
- B. `binlog_format` を `ROW` にする
- C. レプリケーションインスタンスを大きなクラスに変更する
- D. タスクの LOB の設定を Full LOB mode にする
- E. ソースの自動バックアップを有効にする

??? success "答えと解説"
    **正解: B, E**

    DMS は MySQL の行形式のバイナリログから変更を読みます。RDS for MySQL では、自動バックアップを有効にするとバイナリログも有効になります。

    - A: 誤り。ターゲットの可用性の設定で、ソースのログには関係しません。
    - B: 正しい。
    - C: 誤り。性能の問題ではなく、読むログがないことが原因です。
    - D: 誤り。LOB 列の扱いの設定で、CDC の前提ではありません。
    - E: 正しい。

    **スキル:** [4.1.3](../domain4.md#skill-4-1-3) / **参照:** [CDC の前提](../../../services/migration.md#dms-cdc)

### 問11 {#q11}

稼働中の NAS にある 400 TB のファイルを、30 日以内に S3 へ移します。回線は 1 Gbps で、利用率は 80% と見込みます。切り替えまで毎日 2 TB の変更があり、差分も同期します。データは可搬の機器にはありません。最も適切な計画はどれですか。

- A. 期間限定で 2 Gbps の Direct Connect ホスト接続を追加し、DataSync で転送する
- B. 今の 1 Gbps のまま DataSync を実行する。1 Gbps なら差分を含めても 30 日に収まる
- C. Transfer Family の SFTP エンドポイントを作り、NAS から順にアップロードする
- D. 今の 1 Gbps のまま S3 Transfer Acceleration を有効にして、転送時間を半分にする

??? success "答えと解説"
    **正解: A**

    1 Gbps、利用率 80%、24 時間では 400 TB に約 46 日かかります。2 Gbps を足すと合計 3 Gbps になり、約 15 日で転送でき、差分も追いつきます。2 Gbps のホスト接続を提供できるのは要件を満たすパートナーに限られるので、提供元を先に確認します。

    - A: 正しい。
    - B: 誤り。計算すると約 46 日かかり、間に合いません。
    - C: 誤り。Transfer Family は取引先の連携向けで、大量の一括移行には向きません。回線の問題も解決しません。
    - D: 誤り。Transfer Acceleration は遠隔地からの HTTPS アップロード向けです。1 Gbps の上限は増えません。

    **スキル:** [4.1.3](../domain4.md#skill-4-1-3) / **参照:** [計算式](../../../services/migration.md#transfer-formula)、[変更の量も確認する](../../../services/migration.md#transfer-change-rate)

### 問12 {#q12}

Direct Connect の 10 Gbps を確保し、DataSync で 2 PB のファイルを移しています。1 つのタスクで 300 MiB/s しか出ておらず、ストレージにも回線にも余裕があります。回線を増やさず、完了までの時間を短くしたいです。最も適切なものはどれですか。

### 問13 {#q13}

DMS で文書管理のデータベースを移行しました。表には最大 2 MB の LOB 列があります。タスクは Limited LOB mode で、上限は 32 KB でした。移行後、長い文書の末尾が欠けていると報告がありました。タスクの速度は重視しません。全行を正しく移すには、タスクをどう変えて移し直しますか。

### 問14 {#q14}
