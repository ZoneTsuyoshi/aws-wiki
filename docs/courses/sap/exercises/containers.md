# コンテナとスケーリングの問題集

対象の解説: [コンテナ](../../../services/containers.md)、[Lambda](../../../services/lambda.md)、[VPC Lattice](../../../services/network-connectivity.md#vpc-lattice)

### 問1 {#q1}

社内業務のアプリをコンテナで動かす新しいプラットフォームを作ります。運用は 3 人のチームで、Kubernetes の経験はなく、他のクラウドへ移す予定もありません。負荷は日中に大きく変わり、OS のパッチ適用はしたくありません。どの構成が最も適切ですか。

- A. EKS にマネージドノードグループを作り、Cluster Autoscaler でノードの数を調整する
- B. EKS Auto Mode を使い、ノードの管理を AWS に任せてチームで Kubernetes を学ぶ
- C. ECS を EC2 のキャパシティプロバイダーで動かし、スポットインスタンスで費用を下げる
- D. ECS を Fargate で動かし、サービスの Auto Scaling でタスク数を調整する

??? success "答えと解説"
    **正解: D**

    Kubernetes の API が不要で、AWS に絞るなら ECS の負荷が小さいです。Fargate ならサーバーの管理もなくなります。

    - A: 誤り。Kubernetes の学習とノードの運用の負荷が大きい。
    - B: 誤り。ノードは任せられるが、Kubernetes の知識は必要で、持ち運びの要件もない。
    - C: 誤り。EC2 のパッチ適用とスケーリングの手間が残る。
    - D: 正しい。

    **スキル:** [1.1.6](../domain1.md#skill-1-1-6) / **参照:** [Fargate と EC2](../../../services/containers.md#fargate-vs-ec2)

### 問2 {#q2}

ある事業者は、自社で作った Helm チャートと Kubernetes のオペレーターを多数持ち、他のクラウドでも同じ定義で運用しています。AWS にも同じ方法で展開しますが、ノードのパッチ適用とスケーリングの運用は減らしたいと考えています。どれを選びますか。

- A. ECS を Fargate で動かし、Helm チャートをタスク定義へ変換する
- B. EKS Auto Mode でクラスターを作り、既存の Helm チャートをそのまま展開する
- C. EKS にセルフマネージドのノードを作り、独自の AMI とスクリプトで更新する
- D. EC2 上に Kubernetes を自分で構築し、コントロールプレーンも複数の AZ に配置する

??? success "答えと解説"
    **正解: B**

    既存の Kubernetes の資産を活かすなら EKS です。Auto Mode ならノードの管理とスケーリングを AWS に任せられます。

    - A: 誤り。ECS では Kubernetes の API やオペレーターを使えない。
    - B: 正しい。
    - C: 誤り。Kubernetes の資産は活かせるが、ノードの運用が減らない。
    - D: 誤り。コントロールプレーンの運用まで増える。

    **スキル:** [1.1.6](../domain1.md#skill-1-1-6) / **参照:** [EKS](../../../services/containers.md#eks)

### 問3 {#q3}

画像の検査バッチを ECS で動かします。タスクは GPU を必要とし、中断されても再実行できます。夜間に数百のタスクを実行するので、費用を大きく下げたいです。既に ECS の運用には慣れています。どの構成が最も適切ですか。

- A. Fargate Spot のキャパシティプロバイダーを使い、タスク定義で GPU を指定する
- B. GPU インスタンスのスポットを使う EC2 キャパシティプロバイダーで、検査のタスクを実行する
- C. Fargate のタスクに最大の vCPU とメモリを割り当て、GPU なしで処理時間を延ばして実行する
- D. GPU のオンデマンドインスタンスを常時起動し、Compute Savings Plans で割引を受ける

??? success "答えと解説"
    **正解: B**

    Fargate のタスク定義では GPU を指定できません。GPU とスポットを使うなら EC2 のキャパシティプロバイダーです。

    - A: 誤り。Fargate は GPU を扱えない。
    - B: 正しい。
    - C: 誤り。GPU が必要という要件を満たさない。
    - D: 誤り。夜間だけの処理に常時起動は無駄で、スポットより割引も小さい。

    **スキル:** [1.1.6](../domain1.md#skill-1-1-6) / **参照:** [キャパシティプロバイダー](../../../services/containers.md#capacity-providers)

### 問4 {#q4}

ある SaaS の 12 個のマイクロサービスは、すべて同じリージョンの ECS にあり、2 つのクラスターに分かれています。サービス間は短い名前で接続し、再試行や標準のメトリクスを、アプリのコードを変えずに使いたいです。通信は TLS で保護し、証明書の更新は自動にします。どれが最も適切ですか。

- A. App Mesh のサイドカーを各タスクに追加し、仮想サービスの定義で通信を制御する
- B. VPC Lattice のサービスネットワークを作り、アプリのリクエストに SigV4 の署名を追加する
- C. ECS Service Connect を Private CA と組み合わせる
- D. 各サービスに内部 ALB を置き、ACM の証明書を付けて、Route 53 のプライベートホストゾーンで名前を解決する

??? success "答えと解説"
    **正解: C**

    ECS で完結するなら Service Connect です。同じ名前空間ならクラスターをまたげ、プロキシが再試行とメトリクスを担当します。Private CA を指定すれば TLS を自動で設定できます。

    - A: 誤り。App Mesh は 2026 年 9 月 30 日にサポートを終了した。
    - B: 誤り。ECS だけなら過剰で、IAM 認可にはアプリの署名の対応も必要になる。
    - C: 正しい。
    - D: 誤り。サービスごとの ALB の費用と管理が増え、再試行も自分で実装する。

    **スキル:** [1.1.7](../domain1.md#skill-1-1-7) / **参照:** [App Mesh の状況](../../../services/network-connectivity.md#app-mesh)

### 問5 {#q5}

グループ会社の 3 つのアカウントに、EC2、Lambda、EKS の Pod で動くサービスがあります。サービス同士を接続し、呼び出し元の IAM プリンシパルで認可します。VPC の CIDR は一部が重複し、サイドカーの運用は増やしたくありません。どれを選びますか。

- A. Transit Gateway ですべての VPC を接続し、セキュリティグループで呼び出し元を制御する
- B. VPC Lattice のサービスネットワークを RAM で共有し、認証ポリシーで認可する
- C. ECS Service Connect の名前空間を RAM で共有し、すべてのサービスを同じ名前空間に登録する
- D. サービスごとに NLB と PrivateLink のエンドポイントサービスを作り、呼び出し元の VPC にエンドポイントを置く

??? success "答えと解説"
    **正解: B**

    VPC Lattice は EC2、Lambda、Pod などをターゲットにでき、サイドカーは不要です。認証ポリシーは IAM のポリシー文書で、CIDR の重複にも対応できます。

    - A: 誤り。CIDR が重複すると経路を作れず、IAM プリンシパルで認可もできない。
    - B: 正しい。
    - C: 誤り。Service Connect は ECS サービス間の機能で、EC2 や Lambda は参加できない。
    - D: 誤り。サービスごとの設定が多く、IAM プリンシパルでの認可も別途必要になる。

    **スキル:** [1.1.7](../domain1.md#skill-1-1-7) / **参照:** [VPC Lattice](../../../services/network-connectivity.md#vpc-lattice)

### 問6 {#q6}

ECS のサービス群に Service Connect を導入しました。同じ VPC の EC2 で動く夜間のバッチが、`orders:8080` に接続できなくなりました。ECS のサービス同士は問題なく通信できています。バッチは EC2 のまま動かします。どう対処しますか。

- A. VPC の `enableDnsHostnames` を有効にし、VPC の DNS から短い名前を解決できるようにする
- B. バッチの EC2 を Cloud Map の名前空間にインスタンスとして登録し、Service Connect のプロキシを経由して接続する
- C. プライベートホストゾーンに `orders` のレコードを作り、Service Connect のプロキシの IP へ向ける
- D. `orders` サービスに内部 ALB を追加して、バッチはそこへ接続する

??? success "答えと解説"
    **正解: D**

    Service Connect は同じ名前空間の ECS サービス間の機能です。名前空間の外から接続するには、ALB などの別の接続方法を用意します。

    - A: 誤り。名前はタスク内のプロキシ用で、VPC の DNS には登録されない。
    - B: 誤り。プロキシは ECS のタスクに追加されるもので、EC2 を参加させる仕組みはない。
    - C: 誤り。プロキシはタスクの中で動き、別のホストから接続する宛先にはならない。
    - D: 正しい。

    **スキル:** [1.1.7](../domain1.md#skill-1-1-7) / **参照:** [ECS](../../../services/containers.md#ecs)

### 問7 {#q7}

100 を超える ECR リポジトリがあり、作成はチームに任せています。OS と言語のパッケージの脆弱性を調べ、新しい CVE が公開されたときも既存のイメージを再評価します。重大な検出結果はセキュリティチームに自動で通知します。設定漏れを防ぎたいです。どの構成が最も適切ですか。

- A. レジストリのレベルで拡張スキャンを有効にし、重大な検出結果の EventBridge イベントで通知する
- B. リポジトリごとにプッシュ時の基本スキャンを有効にし、CI の結果をセキュリティチームへメールで送る
- C. レジストリのレベルで基本スキャンを有効にし、週に 1 回すべてのイメージを手動でスキャンする Lambda を動かす
- D. 各チームのビルドで OSS のスキャナーを実行し、結果を S3 に集めて Athena で週次に確認する

??? success "答えと解説"
    **正解: A**

    拡張スキャンは Amazon Inspector と連携し、OS と言語のパッケージを継続的に調べます。レジストリのレベルで設定すれば漏れを防げます。

    - A: 正しい。
    - B: 誤り。基本スキャンは OS の脆弱性だけで、設定漏れも起こる。
    - C: 誤り。基本スキャンでは言語のパッケージを調べられない。
    - D: 誤り。ビルドのない既存のイメージは再評価されず、通知も自動にならない。

### 問8 {#q8}

開発の過程で ECR のイメージが増え続け、ストレージの費用が問題になっています。開発用のイメージは最新の 20 個だけ残し、本番が使うイメージは消さないようにします。誤って本番のイメージを消す事故は避けたいです。必要な対応を選んでください。（2つ選択）

- A. 環境ごとのタグの接頭辞でライフサイクルルールを分ける

### 問9 {#q9}

ビルド用のアカウントの ECR から、本番のアカウントの別のリージョンへイメージを自動で複製します。リージョン障害のときも本番がイメージを取得できるようにします。CI のパイプラインは変更したくありません。必要な設定はどれですか。

- A. ビルド用のアカウントでレジストリのレプリケーションを設定し、本番のアカウントのレジストリの権限ポリシーで許可する
- B. ビルド用のアカウントのリポジトリポリシーで本番のアカウントにプルを許可し、本番のアカウントの定期ジョブでコピーする

EKS で、Horizontal Pod Autoscaler により Pod を増やしています。ノードグループは固定のインスタンスタイプで長年運用されており、構成の変更は監査の手続きが重くなるので、変えたくありません。負荷は安定しており、急増はほとんどありません。今後 Pod が Pending にならないよう、ノードの数を自動で調整します。どれを選びますか。

- A. Karpenter を導入し、既存のノードグループを廃止して NodePool へ移す

### 問11 {#q11}

EKS のクラスターの負荷は急増が多く、多様なインスタンスタイプとスポットで短時間にノードを増やしたいです。一方で、セキュリティの方針により、各ノードのルートファイルシステムへ独自の監視エージェントを導入し、起動スクリプトも自社で管理します。ノード関連のコントローラーを自分で運用することは受け入れます。どれを選びますか。

- A. Karpenter を導入し、カスタムの AMI と起動スクリプトを指定する
- B. Cluster Autoscaler と、インスタンスタイプごとの多数の Auto Scaling グループ
- C. EKS Auto Mode と、既定の NodePool の編集

### 問12 {#q12}

チケット販売の API は Lambda で動きます。販売開始の時刻は事前に決まっていて、開始直後に同時実行が数千まで跳ね上がります。コールドスタートによる遅延が問題になっています。通常時の費用はなるべく増やしたくありません。どの対策が最も適切ですか。

- A. 関数に予約済み同時実行を設定して、販売開始の時刻に必要な実行環境を確保する
- B. 関数の前に SQS キューを置き、リクエストを非同期に処理して、応答の遅延を隠す
- C. Lambda のメモリを最大にして、初期化が必ず 1 ミリ秒未満で終わるようにする
- D. Application Auto Scaling のスケジュールで、販売開始の前に Provisioned Concurrency を増やす

??? success "答えと解説"
    **正解: D**

    Provisioned Concurrency は初期化済みの実行環境を用意し、待機中も課金されます。開始の前だけ増やせば費用を抑えられます。

    - A: 誤り。予約済み同時実行は枠を確保して上限にするだけで、実行環境を事前に初期化しない。
    - B: 誤り。同期の API の応答が返せなくなり、要件に合わない。
    - C: 誤り。初期化は速くなりうるが、遅延がなくなることは保証されない。
    - D: 正しい。

    **スキル:** [1.1.9](../domain1.md#skill-1-1-9) / **参照:** [予約済みと Provisioned の違い](../../../services/lambda.md#reserved-provisioned)

### 問13 {#q13}

- C. Horizontal Pod Autoscaler を ECS のサービスに設定して、タスクの数を変える
- D. Cluster Autoscaler を ECS のクラスターに導入して、Auto Scaling グループを調整する
- E. 毎日決まった時刻にタスクを増やすスケジュールだけを設定する

??? success "答えと解説"
    **正解: A, B**

    タスクの数はサービスの Auto Scaling、インスタンスの数はキャパシティプロバイダーで調整します。2 段で考えます。

    - A: 正しい。
    - B: 正しい。
    - C: 誤り。HPA は Kubernetes の機能である。
    - D: 誤り。Cluster Autoscaler は Kubernetes のコンポーネントである。
    - E: 誤り。バックログの増加に追従できない。

### 問15 {#q15}

EKS で 40 のマイクロサービスがあり、サービスごとに `Ingress` を作ったところ、ALB が 40 台できて費用が増えました。チームごとに `Ingress` の定義を持つ方法は変えたくありません。同じ入口の HTTPS で、ホスト名ごとに振り分けます。どうしますか。

- A. `Service`（`type: LoadBalancer`）に変えて、サービスごとの NLB にする
- B. AWS Load Balancer Controller を削除して、古いクラウドプロバイダーのロードバランサーを使う
- C. API Gateway の HTTP API をサービスごとに作り、各 API から VPC リンクで Pod へ接続する
- D. `IngressGroup` で複数の `Ingress` を 1 つの ALB にまとめる

??? success "答えと解説"
    **正解: D**

    Controller の `IngressGroup` を使うと、複数の `Ingress` の定義を 1 つの ALB に統合できます。

    - A: 誤り。ロードバランサーの数は減らず、ホスト名での振り分けもできない。
    - B: 誤り。Classic Load Balancer になり、`Ingress` からの ALB の管理ができなくなる。
    - C: 誤り。入口の数は減らず、API の管理機能も要件にない。
    - D: 正しい。

    **スキル:** [1.1.10](../domain1.md#skill-1-1-10) / **参照:** [EKS](../../../services/containers.md#eks)

### 問16 {#q16}

EKS の Pod を Fargate で動かし、TCP のサービスとして公開します。`type: LoadBalancer` の `Service` を作りましたが、想定と違うロードバランサーができ、Pod へ直接振り分けられません。NLB で Pod の IP へ直接振り分け、設定は Kubernetes の定義で管理します。どうしますか。

- A. `Ingress` を作って、ALB のターゲットタイプをインスタンスにする
- B. AWS Load Balancer Controller を導入し、`Service` のアノテーションでターゲットタイプを IP にする
- C. Fargate のプロファイルに NodePort の範囲を追加し、Classic Load Balancer から各ノードへ接続する
- D. 手動で NLB を作り、Pod の IP アドレスをターゲットグループへスクリプトで登録する

??? success "答えと解説"
    **正解: B**

    Controller がない場合は、古いクラウドプロバイダーが Classic Load Balancer を作ります。Controller は NLB を作成し、Fargate では IP ターゲットを使います。

    - A: 誤り。TCP のサービスには合わず、Fargate はインスタンスターゲットを使えない。
    - B: 正しい。
    - C: 誤り。Fargate の Pod はノードのポートを公開する方式を使えない。
    - D: 誤り。Pod の IP は変わるので、スクリプトの保守が必要で、Kubernetes の定義で管理する条件にも反する。

### 問17 {#q17}

社内の Lambda の API は JSON を返すだけで、毎秒 2 万リクエストが常時流れています。API キー、使用量プラン、キャッシュは使っていません。API Gateway のリクエスト課金が費用の大部分になっています。パスで 2 つの関数へ振り分ける機能は必要です。費用を下げる入口として最も適切なものはどれですか。

- A. NLB を置いて、Lambda の関数へ直接振り分ける
- B. API Gateway の REST API に変え、キャッシュを有効にする
- C. Lambda の関数 URL を 2 つ公開し、呼び出し元がパスに応じて接続先を選ぶようにする
- D. ALB のパスベースのルーティングで、Lambda をターゲットにする

??? success "答えと解説"
    **正解: D**

    API の管理機能が要らず、負荷が高いなら、Lambda をターゲットにできる ALB が候補です。

    - A: 誤り。NLB は Lambda を直接のターゲットにできず、パスでの振り分けもできない。
    - B: 誤り。REST API のリクエスト課金はさらに高く、キャッシュの要件もない。
    - C: 誤り。振り分けの責任が呼び出し元に移り、入口の統一が失われる。
    - D: 正しい。

    **スキル:** [1.1.10](../domain1.md#skill-1-1-10) / **参照:** [ALB と NLB の違い](../../../services/networking.md#alb-vs-nlb)

### 問18 {#q18}

取引先の機器が、独自のバイナリプロトコルの TCP で接続してきます。取引先は接続先を固定 IP で許可リストに載せます。別の事業部のアカウントへは、VPC をつながずにこのサービスを PrivateLink で公開します。どの入口が最も適切ですか。

- A. ALB に Elastic IP を割り当てて、エンドポイントサービスの背後に置く
- B. API Gateway のプライベート API を作り、VPC リンクでサービスへ接続する
- C. NLB に Elastic IP を割り当て、PrivateLink のエンドポイントサービスの背後に置く
- D. Gateway Load Balancer を作り、各リスナーでバイナリプロトコルを解釈する

??? success "答えと解説"
    **正解: C**

    NLB は TCP を扱い、Elastic IP を割り当てられ、PrivateLink のエンドポイントサービスの背後に置けます。

    - A: 誤り。ALB は HTTP の入口で、Elastic IP を割り当てられない。
    - B: 誤り。API Gateway は HTTP と WebSocket の API の機能で、独自の TCP を扱えない。
    - C: 正しい。
    - D: 誤り。GWLB は第三者のネットワーク機器へ通信を渡すためのものである。

    **スキル:** [1.1.10](../domain1.md#skill-1-1-10) / **参照:** [ALB と NLB の違い](../../../services/networking.md#alb-vs-nlb)
