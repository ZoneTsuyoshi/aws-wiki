# データレイクと分析の問題集

対象の解説: [データエンジニアリング](../../../services/data-engineering.md)、[ストリーミング](../../../services/streaming.md)

### 問1 {#q1}

保険会社の S3 データレイクを、複数のチームが Athena と Redshift Spectrum で読みます。人事のチームには顧客テーブルの一部の列だけ、地域の担当者には自分の地域の行だけを見せます。現在の S3 バケットポリシーと IAM では、オブジェクトの単位でしか制御できません。どうしますか。

- A. 列や行のサブセットを別のバケットへコピーし、チームごとにバケットポリシーを設定する
- B. Lake Formation の権限に移行し、列と行のフィルターを設定する
- C. Glue Data Catalog のリソースポリシーで、テーブルの列を IAM プリンシパルごとに制限する
- D. S3 Object Lambda で Athena の読み取りの結果を編集して返す

??? success "答えと解説"
    **正解: B**

    Lake Formation は列、行、タグの単位でデータレイクのアクセスを制御でき、S3 と IAM だけより細かく管理できます。

    - A: 誤り。データのコピーと同期が増え、費用と不整合の原因になる。
    - B: 正しい。
    - C: 誤り。カタログのリソースポリシーはメタデータの操作の制御で、列や行の単位にはならない。
    - D: 誤り。独自の変換の実装が増え、エンジンの統合された権限にならない。

    **スキル:** [1.5.1](../domain1.md#skill-1-5-1) / **参照:** [権限](../../../services/data-engineering.md#lake-formation-permissions)

### 問2 {#q2}

小売のデータレイクは、Hive 形式の Parquet を日次で差し替えています。顧客からの削除の依頼に対応するため、特定の行の `DELETE` が必要になりました。差し替え中のクエリが不整合な結果を返すこともあり、スキーマの変更や過去時点の監査も求められています。どの対応が最も適切ですか。

- A. Glue のクローラーを毎時実行して、パーティションの情報を常に最新にする
- B. S3 のバージョニングを有効にして、差し替える前のオブジェクトを保持する
- C. テーブルを Apache Iceberg に移行し、行の削除とスナップショットを使う
- D. 全データを毎日 Redshift へロードして、そこで行を削除してから S3 へ出力する

??? success "答えと解説"
    **正解: C**

    Iceberg は ACID、行の更新と削除、スキーマの進化、タイムトラベルを提供します。

    - A: 誤り。カタログの更新で、行の削除や ACID には対応しない。
    - B: 誤り。オブジェクトの版の管理で、行の削除やクエリの整合性は解決しない。
    - C: 正しい。
    - D: 誤り。処理と費用が大きく、差し替え中の不整合も解決しない。

    **スキル:** [1.5.1](../domain1.md#skill-1-5-1) / **参照:** [Apache Iceberg](../../../services/data-engineering.md#iceberg)

### 問3 {#q3}

分析チームは Iceberg を使い始めましたが、小さなファイルが増えてクエリが遅くなりました。ファイルの圧縮や古いスナップショットの整理のジョブを自分たちで作り、運用するのが負担です。Iceberg の形式と SQL のエンジンは変えずに、メンテナンスの手間をなくしたいです。どれを選びますか。

- A. S3 Tables のテーブルバケットへ移し、自動のメンテナンスに任せる
- B. Hive 形式へ戻し、ファイルの差し替えを週 1 回にする
- C. S3 のライフサイクルルールで、小さなファイルを低頻度アクセスのストレージクラスへ移す
- D. EMR on EC2 のクラスターを常時動かし、圧縮のジョブを毎時実行する

??? success "答えと解説"
    **正解: A**

    S3 Tables は Iceberg のマネージドなテーブルで、ファイルの圧縮とスナップショットの管理を自動で行います。

    - A: 正しい。
    - B: 誤り。Iceberg の利点を失い、形式を変えないという条件にも反する。
    - C: 誤り。ストレージクラスを変えてもファイルの数は変わらず、遅さは解決しない。
    - D: 誤り。圧縮はできるが、運用の負担が残る。

    **スキル:** [1.5.1](../domain1.md#skill-1-5-1) / **参照:** [S3 Tables](../../../services/data-engineering.md#s3-tables)

### 問4 {#q4}

Redshift の DWH には直近 1 年のデータがあり、古い 8 年分は S3 に Parquet であります。アナリストは同じ SQL で新旧を結合して集計したいです。古いデータの利用は少なく、クラスターにロードする費用は避けます。どうしますか。

- A. 古いデータを Redshift に再ロードし、クラスターのノードを増やす
- B. 古いデータを S3 からダウンロードし、集計の前にアナリストの手元で結合する
- C. Athena で古いデータを集計し、結果を手作業で Redshift のテーブルへ追加する
- D. Redshift Spectrum の外部テーブルで S3 のデータを参照する

??? success "答えと解説"
    **正解: D**

    Spectrum は Redshift の SQL から S3 のデータを参照し、ローカルのテーブルと結合できます。ロードは不要です。

    - A: 誤り。ロードとノードの費用がかかる。
    - B: 誤り。8 年分のデータでは現実的でなく、同じ SQL の要件も満たさない。
    - C: 誤り。手作業が発生し、同じ SQL で結合できない。
    - D: 正しい。

    **スキル:** [1.5.1](../domain1.md#skill-1-5-1) / **参照:** [Spectrum](../../../services/data-engineering.md#redshift-spectrum)

### 問5 {#q5}

広告配信の会社は、自社のデータセンターで Kafka のプロデューサー、コンシューマー、Kafka Streams のアプリを多数運用しています。AWS へ移しますが、アプリのコードと運用のツールはそのまま使います。ブローカーのパッチ適用と障害の対応は AWS に任せます。どれを選びますか。

- A. Kinesis Data Streams へ移し、KPL と KCL でアプリを書き直す
- B. EC2 に Kafka のクラスターを自分で構築する
- C. Amazon MSK のクラスターへ移し、既存の Kafka クライアントのまま接続する
- D. SQS の FIFO キューへ移し、トピックごとにキューを分ける

??? success "答えと解説"
    **正解: C**

    MSK は Kafka の API のままで使えます。ブローカーの運用を AWS に任せられます。

    - A: 誤り。統合は簡単になるが、アプリの書き直しが必要である。
    - B: 誤り。ブローカーの運用が残る。
    - C: 正しい。
    - D: 誤り。アプリの書き直しが必要で、Kafka のエコシステムも使えない。

    **スキル:** [1.5.2](../domain1.md#skill-1-5-2) / **参照:** [Kinesis Data Streams と MSK の違い](../../../services/data-engineering.md#msk-vs-kinesis)

### 問6 {#q6}

ゲーム会社は、EMR の Spark クラスターで、毎日大規模なログの集計をしています。個々のタスクの失敗は再実行で吸収できますが、クラスターごと止まると最初からやり直しになり、その日の納期に間に合いません。データは S3 に置いてあり、クラスターの制御は続けたいです。クラスターの停止を避けながら、費用を最も下げる設定はどれですか。

- A. プライマリ、コア、タスクのすべてのノードをスポットにする
- B. プライマリとコアはオンデマンドのまま、タスクノードをスポットにする
- C. プライマリだけをスポットにし、コアとタスクをオンデマンドにする
- D. すべてのノードをオンデマンドにし、ノードの数を減らして実行時間を延ばす

??? success "答えと解説"
    **正解: B**

    タスクノードは HDFS を持たないので、中断の影響が小さく、スポットに向きます。プライマリとコアが中断されると、クラスターやデータに影響します。やり直しを許容でき、費用を最優先する一時的なクラスターなら全ノードをスポットにする方法もありますが、この問題の条件には合いません。

    - A: 誤り。プライマリやコアの中断で、クラスターの停止やデータの喪失につながる。
    - B: 正しい。
    - C: 誤り。プライマリが中断されるとクラスターが止まるうえ、節約の効果も小さい。
    - D: 誤り。スポットを使わないので、節約の効果が小さい。

    **スキル:** [1.5.2](../domain1.md#skill-1-5-2) / **参照:** [EMR](../../../services/data-engineering.md#emr)

### 問7 {#q7}

新しい BI の基盤は、複雑な結合を含む定型のレポートを SQL で実行します。利用は月末の数日に集中し、その他の日はほとんどありません。インフラの管理者はおらず、読み込みの性能も必要です。どれが最も適切ですか。

- A. Redshift Serverless で DWH を作り、SQL でレポートを実行する
- B. Redshift のプロビジョンドクラスターを RI で 3 年間契約する
- C. EMR のクラスターを常時動かし、Spark SQL でレポートを実行する
- D. DynamoDB のテーブルに集計結果を保存し、Scan でレポートを作る

??? success "答えと解説"
    **正解: A**

    断続的な DWH の負荷には Redshift Serverless が向きます。容量の管理が不要で、使った分だけ課金されます。

    - A: 正しい。
    - B: 誤り。常時の負荷に向き、ほとんど使わない日も費用がかかる。
    - C: 誤り。クラスターの運用と常時の費用がかかる。
    - D: 誤り。キーでのアクセスに向くサービスで、複雑な結合の SQL は実行できない。

    **スキル:** [1.5.2](../domain1.md#skill-1-5-2) / **参照:** [Redshift](../../../services/data-engineering.md#redshift)

### 問8 {#q8}

組織のデータレイクアカウントの Glue Data Catalog のテーブルを、分析アカウントの Athena から読みます。データはコピーせず、列の単位で権限を制限します。分析アカウントでは自分のカタログのように参照したいです。適切な構成はどれですか。

- A. Lake Formation で共有し、分析アカウントでリソースリンクを作る
- B. S3 のバケットポリシーで分析アカウントに読み取りを許可し、分析アカウントでテーブルの定義を作り直す
- C. S3 のクロスリージョンレプリケーションで分析アカウントのバケットへデータを複製する
- D. Redshift のデータ共有で、S3 のテーブルを分析アカウントの Athena へ公開する

??? success "答えと解説"
    **正解: A**

    Lake Formation のクロスアカウント共有は内部で RAM を使います。Athena で参照するには、共有先でリソースリンクを作ります。

    - A: 正しい。
    - B: 誤り。列の単位で制限できない。
    - C: 誤り。データをコピーしないという条件に反する。
    - D: 誤り。データ共有は Redshift のデータの共有である。

    **スキル:** [1.5.7](../domain1.md#skill-1-5-7) / **参照:** [クロスアカウント共有](../../../services/data-engineering.md#lake-formation-cross-account)

### 問9 {#q9}

データレイクには数千のテーブルがあり、毎週増えています。「機密度」「部門」の分類に応じて、どのチームがどの列を読めるかを決めています。テーブルごとに権限を付与する現在の方法では、追加のたびに作業が発生します。どう変更しますか。

- A. テーブルごとの付与を自動化するスクリプトを作り、毎晩実行する
- B. 列ごとに IAM ポリシーを作り、チームのロールへ関連付ける
- C. チームごとにデータベースをコピーし、見せる列だけを残す
- D. LF タグを列やテーブルに付け、タグの式で権限を付与する

??? success "答えと解説"
    **正解: D**

    LF-TBAC ならタグの式で権限を付与でき、新しいテーブルにもタグを付けるだけで適用されます。

    - A: 誤り。動くが、スクリプトの保守が増え、規模に対して脆い。
    - B: 誤り。IAM のポリシーの数が増え、列の単位の制御にも合わない。
    - C: 誤り。コピーの費用と不整合が発生する。
    - D: 正しい。

    **スキル:** [1.5.7](../domain1.md#skill-1-5-7) / **参照:** [LF タグ](../../../services/data-engineering.md#lake-formation-lf-tags)

### 問10 {#q10}

本社の Redshift の売上テーブルを、別のアカウントの事業部の Redshift Serverless から参照します。夜間の ETL で作るコピーの遅延が問題になっています。常に最新のデータを読み、本社のクエリの性能には影響させません。どれを選びますか。

- A. `UNLOAD` で S3 へ出力し、事業部で `COPY` するジョブを毎時実行する
- B. Redshift のデータ共有で、事業部の Serverless から本社のデータを読む
- C. Glue のジョブで本社の Redshift のデータを読み、事業部の Redshift へ毎分書き込む
- D. 事業部のユーザーを本社のクラスターに作り、同じクラスターでクエリを実行する

??? success "答えと解説"
    **正解: B**

    データ共有は、コピーせずにライブのデータをアカウントやクラスターをまたいで読めます。事業部の計算資源で実行するので、本社に影響しません。

    - A: 誤り。コピーで遅延が残る。
    - B: 正しい。
    - C: 誤り。コピーの処理が増え、本社の負荷にもなる。
    - D: 誤り。本社の計算資源を使うので、性能に影響する。

    **スキル:** [1.5.7](../domain1.md#skill-1-5-7) / **参照:** [データの共有](../../../services/data-engineering.md#choosing-sharing)

### 問11 {#q11}

小売業と食品メーカーは、顧客の重なりと広告の効果を共同で分析します。どちらも相手に生データを見せられず、データのコピーも避けたいです。集計の結果だけを、許可された列と最小の人数の条件で出力します。どれが適切ですか。

- A. Lake Formation のクロスアカウント共有で、相手のアカウントへ列を共有する
- B. Redshift のデータ共有で、両社のテーブルを相手に読み取り専用で公開する
- C. Clean Rooms のコラボレーションを作り、分析ルールで制限する
- D. 両社のデータを第三者のアカウントの S3 へコピーし、匿名化してから Athena で分析する

??? success "答えと解説"
    **正解: C**

    Clean Rooms はデータの元の場所から読み取り、分析ルールで許す集計や出力を制限します。互いの生データを見せずに共同で分析できます。

    - A: 誤り。共有された列の生データを相手が読める。
    - B: 誤り。相手がライブの生データを読める。
    - C: 正しい。
    - D: 誤り。データのコピーが発生する。

    **スキル:** [1.5.7](../domain1.md#skill-1-5-7) / **参照:** [Clean Rooms](../../../services/data-engineering.md#clean-rooms)
