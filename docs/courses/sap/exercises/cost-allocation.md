# コストの配分と可視化の問題集

対象の解説: [コスト管理](../../../services/cost-management.md#cost-allocation-tags)

### 問1 {#q1}

ある会社の組織では、8 か月前から `CostCenter` タグを各リソースに付けています。昨日、管理アカウントでこのタグをコスト配分タグとして有効にしました。財務部門は、過去 6 か月の費用を `CostCenter` ごとに Cost Explorer で見たいと求めています。最も適切な方法はどれですか。

- A. 管理アカウントから過去 6 か月のバックフィルを依頼する
- B. 全リソースのタグを付け直して、過去の利用にも反映させる
- C. 各メンバーアカウントでもタグを有効にし、請求データを再計算させる
- D. 過去のデータは得られないので、今月以降の明細だけで報告する

??? success "答えと解説"
    **正解: A**

    管理アカウントは、最大 12 か月のバックフィルを依頼できます。当時リソースにタグが付いていれば、その期間のデータに反映されます。

    - A: 正しい。
    - B: 誤り。タグの付け直しは過去の費用に影響しない。
    - C: 誤り。有効化は請求の担当である管理アカウントで行う。
    - D: 誤り。バックフィルで遡れる。

    **スキル:** [3.3.1](../domain3.md#skill-3-3-1) / **参照:** [コスト配分タグ](../../../services/cost-management.md#cost-allocation-tags)

### 問2 {#q2}

ある会社の費用レポートには、`Env` と `env`、`prod` と `Prod` が別々に集計されています。リソースは CloudFormation と Terraform で作成しており、複数のチームが独自にタグを付けています。今後同じ問題が起きないようにしつつ、担当者の手作業を増やさない方法はどれですか。（2つ選択）

- A. タグのキーと値の形式を標準として決め、IaC の共通設定で既定のタグを付ける
- B. 毎月の締めの後に、財務の担当者が Excel で表記の揺れをまとめる
- C. タグポリシーでキーの大文字小文字と使える値を定める
- D. コスト配分タグを無効にして、アカウント単位の集計にそろえる
- E. Tag Editor で年に 1 度すべてのタグを一括で修正する運用にする

??? success "答えと解説"
    **正解: A, C**

    タグのキーと値は大文字小文字を区別します。標準を決めて IaC で一括して付け、タグポリシーで組織全体の形式をそろえます。

    - A: 正しい。
    - B: 誤り。手作業が続き、原因も残る。
    - C: 正しい。
    - D: 誤り。プロジェクトや環境の単位で見られなくなる。
    - E: 誤り。年 1 回の修正では、その間の揺れが費用データに残る。

    **スキル:** [3.3.1](../domain3.md#skill-3-3-1) / **参照:** [タグ戦略](../../../services/governance.md#tagging-strategy)、[タグポリシー](../../../services/governance.md#tag-policies)

### 問3 {#q3}

ある会社は事業部ごとに費用を報告したいと考えています。ところが、古いアカウントにはタグのないリソースが多く残っています。また、事業部の専用アカウントもあれば、複数の事業部が同居するアカウントもあります。タグの整備には 1 年かかる見込みですが、報告は来月から必要です。最も適切な方法はどれですか。

- A. タグの整備が終わるまで報告を延期する
- B. 全リソースへ `Unknown` タグを一括で付け、それを事業部の値とみなす
- C. 事業部ごとにアカウントを作り直し、全リソースを移してからアカウント単位で報告する
- D. コストカテゴリでアカウントとタグのルールを組み合わせて分類する

??? success "答えと解説"
    **正解: D**

    コストカテゴリは、アカウント、タグ、サービスなどのルールを組み合わせて分類できます。専用アカウントはアカウントで、同居するアカウントはタグで分類でき、タグが揃う前から使えます。

    - A: 誤り。来月からの要件を満たせない。
    - B: 誤り。事業部を区別できない。
    - C: 誤り。来月に間に合わず、移行の費用も大きい。
    - D: 正しい。

    **スキル:** [3.3.1](../domain3.md#skill-3-3-1) / **参照:** [Cost Categories](../../../services/cost-management.md#cost-categories)

### 問4 {#q4}

ある会社の FinOps チームは、組織全体の明細を行単位で SQL により分析したいと考えています。列は分析に必要なものだけにして、スキャン量も抑えたいです。追加のサーバーの運用は避けます。最も適切な構成はどれですか。

- A. Cost Explorer の API を毎日呼び、結果を RDS へ保存する
- B. CUR 2.0 を Parquet で S3 へ出力し、Athena で問い合わせる
- C. 請求書の PDF を毎月 S3 に保存して、テキストを抽出して集計する
- D. Budgets の通知の内容を DynamoDB に保存して、SQL 互換のツールで集計する

??? success "答えと解説"
    **正解: B**

    行単位の分析は CUR 2.0 です。SQL で出力する列と行を選べ、Parquet にすると Athena のスキャン量も減ります。Athena はサーバーの運用が要りません。

    - A: 誤り。集計の API で行単位の明細ではなく、API の料金も DB の運用もかかる。
    - B: 正しい。
    - C: 誤り。明細の分析に使える粒度ではない。
    - D: 誤り。通知は明細ではない。

    **スキル:** [3.3.2](../domain3.md#skill-3-3-2) / **参照:** [Data Exports と CUR](../../../services/cost-management.md#data-exports)、[S3 上のログを問い合わせる](../../../services/streaming.md#athena-logs)

あるグローバル企業の経営層は、事業部とプロダクトごとの費用を、毎週見られる共有のダッシュボードで確認したいと考えています。独自の指標を SQL で定義する必要があり、閲覧者は AWS のコンソールを使いません。すでに CUR 2.0 が S3 に出力されています。最も適切な構成はどれですか。

- B. Athena で問い合わせ、Quick Sight でダッシュボードを公開する

### 問6 {#q6}

あるデータ基盤チームは、従来の CUR を取り込む ETL を運用しています。タグの追加などで列が変わるたびに、ジョブが失敗します。分析の内容は変えずに、この保守の手間を減らしたいと考えています。最も適切な変更はどれですか。

- A. 新しい列が増えるたびに通知する Lambda を作り、手で ETL を直す
- B. 列の変更を防ぐため、新しいタグの有効化を組織で禁止する
- C. スキーマが固定の Data Exports の CUR 2.0 へ移す

    - A: 誤り。手作業が残る。
    - B: 誤り。費用配分の改善を止めることになる。
    - C: 正しい。

### 問7 {#q7}

ある会社は、全アカウントでタグ `CostCenter` のない EC2 インスタンスを作成できないようにしたいと考えています。すでにタグポリシーで `CostCenter` の値を定義し、`ec2:instance` に `enforced_for` を設定しました。それでも、タグのないインスタンスが作られています。原因と対策の組み合わせとして正しいものはどれですか。

- A. タグポリシーを管理アカウントにもアタッチしていないのが原因で、全アカウントに付ければ止まる
- B. タグポリシーはタグのない作成を止めないので、`Null` 条件で拒否する SCP を足す
- C. `enforced_for` の値が誤っているのが原因で、`ec2:*` に変更すれば止まる
- D. Config の `required-tags` がないのが原因で、ルールを有効にすれば作成時に止まる

??? success "答えと解説"
    **正解: B**

    タグポリシーの基本のルールは、指定されたタグの値を検査します。タグのない作成は止めません。`aws:RequestTag/CostCenter` の `Null` 条件で `ec2:RunInstances` を拒否する SCP を使います。

    - A: 誤り。アタッチの範囲を広げても、タグのない作成は止まらない。
    - B: 正しい。
    - C: 誤り。指定の形式を変えても、タグのない作成は止まらない。
    - D: 誤り。`required-tags` は検出で、作成を防がない。

    **スキル:** [3.3.3](../domain3.md#skill-3-3-3) / **参照:** [タグポリシー](../../../services/governance.md#tag-policies)、[SCP](../../../services/governance.md#scp)

### 問8 {#q8}

ある会社は、タグの統制を設計しています。要件は 2 つあります。EC2 の作成時に `Project` タグを必須にすることと、指定された値以外の `Project` タグを持つ EC2 の作成を止めることです。この 2 つを最も直接に満たす手段はどれですか。（2つ選択）

- A. `ec2:RunInstances` でタグの `Null` 条件を使って拒否する SCP
- B. `Project` の値と `enforced_for` を定めたタグポリシー
- C. タグのないリソースを記録する Config の `required-tags` ルール

??? success "答えと解説"

    必須化は SCP の予防、値の制限はタグポリシーの `enforced_for` です。役割が違うので組み合わせます。

### 問9 {#q9}

ある会社には、タグのない既存のリソースが多数あります。作成を止めるのではなく、タグのないリソースを継続的に検出し、決まった手順で `Owner` タグを自動で補いたいと考えています。担当者は Config の `required-tags` ルールを有効にし、修復にマネージドの `AWS-SetRequiredTags` ドキュメントを指定しましたが、修復が動きません。どうすべきですか。

### 問10 {#q10}

あるプラットフォームチームは、全リソースのタグ付けを強制するため、`Action: "*"` で `aws:RequestTag/CostCenter` が `Null` なら拒否する SCP を、検証用の OU にアタッチしました。すると、S3 の読み取りや、タグに対応しない操作まで失敗するようになりました。統制を保ったまま影響を抑える修正はどれですか。

- A. ノードにチームのタグを付けて、Cost Explorer でタグごとに集計する
- B. チームごとに専用の EKS クラスターを作り、アカウントを分けて請求する
- C. 分割コスト配分データにオプトインし、CUR を `aws:eks:namespace` で集計する

### 問12 {#q12}

ある会社は、EKS の分割コスト配分データでチームへ請求しています。Pod のリクエストより実際の使用量が大きいチームが、安く請求されるという不満が出ました。リクエストと実際の使用量の大きい方で配分したいです。組織ではすべての機能が有効です。最も適切なものはどれですか。

- A. 配分方式をリソースリクエストのまま、全 Pod のリクエストの値を手で引き上げる

### 問13 {#q13}

ある会社は、共有のネットワーク基盤の費用を 3 つの事業部へ配分します。社内の合意で、比率は 60%、30%、10% に決まっています。事業部ごとのコストカテゴリの値はすでにあります。合意の比率で配分するには、分割ルールのどの方式を使いますか。

### 問14 {#q14}

ある会社は、1 つのアカウントで複数のチームが同じ Bedrock のモデルを呼んでいます。チームごとに費用を請求し、使用量も別々に監視したいと考えています。アカウントを分ける予定はありません。最も適切な方法はどれですか。

- A. 管理アカウントの予算アクションで、対象のアカウントへ SCP を適用する
- B. 管理アカウントの予算アクションで、対象のアカウントの EC2 と RDS を停止する
- C. CloudWatch の請求アラームを各リージョンに作り、Lambda でユーザーを削除する
- D. Cost Anomaly Detection のモニターに、作成を止めるアクションを設定する

??? success "答えと解説"
    **正解: A**

    管理アカウントの予算アクションは、他のアカウントへ SCP を適用できます。予測のしきい値で動かせるので、超える前に新規の作成を止められます。

    - A: 正しい。
    - B: 誤り。EC2 と RDS の指定は同じアカウントだけ。動いているものを止める要件でもない。
    - C: 誤り。請求メトリクスは米国東部（バージニア北部）だけで、予測のしきい値もない。ユーザーの削除は過剰。

### 問16 {#q16}

ある会社には、季節性のある事業を持つ 100 のアカウントがあります。アカウントごとに適切な額を決めるのが難しく、固定のしきい値では誤報が多くなっています。想定外の急増を見つけ、根本原因の手がかりも得たいです。検出したら、できるだけ早く運用チームへ通知します。最も適切な構成はどれですか。

- A. アカウントごとに固定額の予算を作り、80% で通知する
- B. CUR 2.0 を毎日 Athena で集計し、前月比が 10% を超えたらメールを送る
- C. Trusted Advisor のコストの点検の結果を毎週確認する
- D. 管理アカウントで連結アカウントのモニターを作り、個別のアラートを SNS へ送る

??? success "答えと解説"
    **正解: D**

    Cost Anomaly Detection は機械学習で季節性や自然な成長を考慮し、根本原因を示します。連結アカウントのモニターは管理アカウントで作ります。個別のアラートの通知先には SNS が必要です。

    - A: 誤り。固定のしきい値の課題が残る。
    - B: 誤り。集計の仕組みの自作で、季節性を考慮しない。
    - C: 誤り。急増の検出の機能ではなく、週次では遅い。
    - D: 正しい。

    **スキル:** [3.3.5](../domain3.md#skill-3-3-5) / **参照:** [Cost Anomaly Detection](../../../services/cost-management.md#cost-anomaly-detection)

### 問17 {#q17}

ある会社は、Compute Savings Plans を大量に購入しました。適正化やワークロードの移行が進むと、確約を使い切れなくなるおそれがあります。使用率が 90% を切ったら、財務の担当者へ自動で通知したいと考えています。カスタムの開発は避けます。最も適切なものはどれですか。

- A. Compute Optimizer のレポートを週次で確認する
- B. Cost Anomaly Detection のしきい値を 90% に設定する
- C. Savings Plans の使用率の予算を Budgets に作成する
- D. CloudWatch の `EstimatedCharges` にアラームを設定する

??? success "答えと解説"

    Budgets には Savings Plans の使用率とカバレッジの予算があり、しきい値を下回ると通知できます。

    - A: 誤り。リソースのサイズの推奨で、使用率の通知ではない。
    - B: 誤り。費用の急増の検出で、使用率は監視しない。
    - C: 正しい。
    - D: 誤り。請求額の見積もりで、確約の使用率は分からない。

### 問18 {#q18}

ある運用担当者は、東京リージョンの CloudWatch で `EstimatedCharges` のアラームを作ろうとしましたが、メトリクスが見つかりません。組織全体の請求額を、簡単に監視したいだけです。どうすべきですか。

- A. Billing の設定で請求アラートを有効にし、`us-east-1` で作る
- B. CloudWatch エージェントを導入し、東京でメトリクスを発行する

- D. Cross-Account Observability を有効にし、全リージョンのメトリクスを集める

??? success "答えと解説"

    - B: 誤り。エージェントは OS やアプリのメトリクスを送るもので、請求は関係ない。
    - C: 誤り。不要な開発で、請求の値を取得する手間も増える。
    - D: 誤り。原因はリージョンと有効化。
