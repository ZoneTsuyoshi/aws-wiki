# データベースとストレージの問題集

対象の解説: [データベース](../../../services/databases.md)、[目的別データベース](../../../services/databases-specialized.md)、[DynamoDB](../../../services/dynamodb.md)、[ストレージの応用](../../../services/storage-advanced.md)

### 問1 {#q1}

カード会社は、口座、端末、加盟店のつながりから不正の連鎖を検出します。「3 段階以内につながる不審な口座」を、数十ミリ秒で問い合わせたいです。現在の RDB では、結合の段数が増えるとクエリが遅くなります。マネージドサービスを使います。どれが最も適切ですか。

- A. Aurora PostgreSQL のリードレプリカを増やす
- B. Redshift で夜間に関係を集計したテーブルを作り、結果を参照する
- C. DynamoDB に隣接リストを設計し、段数の分だけアプリから繰り返し読む
- D. Neptune にグラフを置き、openCypher で問い合わせる

??? success "答えと解説"
    **正解: D**

    関係をたどる問い合わせにはグラフデータベースが合います。

    - A: 誤り。読み取りの数は増えるが、多段の結合の遅さは解決しない。
    - B: 誤り。夜間の集計では、数十ミリ秒の最新の判定に使えない。
    - C: 誤り。動くが、段数に応じて読み取りが増え、実装の負担も大きい。
    - D: 正しい。

    **スキル:** [1.5.3](../domain1.md#skill-1-5-3) / **参照:** [データベースの選び方](../../../services/databases-specialized.md#choosing)

### 問2 {#q2}

既存のアプリは、MongoDB のドライバーとクエリで JSON の文書を扱います。AWS へ移すときにコードの変更を最小にし、マネージドの高可用性を使いたいです。Cassandra の利用はなく、データの形も変えません。どれを選びますか。

- A. DynamoDB。文書をアイテムへ変換し、SDK に書き換える
- B. Keyspaces
- C. DocumentDB
- D. RDS for PostgreSQL の JSONB

??? success "答えと解説"
    **正解: C**

    DocumentDB は MongoDB 互換で、ドライバーとクエリを活かせます。

    - A: 誤り。コードの書き換えが必要になる。
    - B: 誤り。Keyspaces は Cassandra 互換である。
    - C: 正しい。
    - D: 誤り。SQL への書き換えが必要になる。

    **スキル:** [1.5.3](../domain1.md#skill-1-5-3) / **参照:** [全エンジンの比較表](../../../services/databases-specialized.md#decision-table)

### 問3 {#q3}

ゲームのランキングと在庫のカウンターには Redis のデータ構造を使っています。応答はマイクロ秒の読み取りが必要です。現在は ElastiCache の前に RDB があり、構成が複雑です。データベースとしてメモリのストアだけを使いたく、AZ 障害でもデータを失えません。どれを選びますか。

- A. ElastiCache の Memcached をノードの数を増やして使う
- B. DAX を DynamoDB の前に置き、Redis のコードを DynamoDB の API に書き換える
- C. ElastiCache の Redis OSS を、レプリカなしで複数のシャードに分けて使う
- D. MemoryDB を主データベースにして、Redis のデータ構造を活かす

??? success "答えと解説"
    **正解: D**

    MemoryDB は Valkey と Redis OSS に互換で、耐久性のあるインメモリの主データベースです。

    - A: 誤り。Memcached には耐久性がなく、Redis のデータ構造も使えない。
    - B: 誤り。コードの書き換えが必要になる。
    - C: 誤り。レプリカなしでは障害時にデータを失う。
    - D: 正しい。

    **スキル:** [1.5.3](../domain1.md#skill-1-5-3) / **参照:** [紛らわしい組み合わせ](../../../services/databases-specialized.md#confusable)

### 問4 {#q4}

工場の新しいシステムは、機器ごとの温度を毎秒記録し、時間窓での集計を行います。チームは InfluxDB のクエリと Telegraf の経験があります。データベースの運用はしたくありません。2026 年時点の新規の構成として、どれが最も適切ですか。

- A. Timestream for LiveAnalytics
- B. Timestream for InfluxDB
- C. DynamoDB に時刻をソートキーとして保存し、集計はアプリで行う
- D. Aurora PostgreSQL のテーブルに記録し、時間窓の SQL を毎回実行する

??? success "答えと解説"
    **正解: B**

    時系列には Timestream を選びますが、LiveAnalytics は 2025 年 6 月 20 日に新規の受付を終了しました。InfluxDB の経験も活かせます。

    - A: 誤り。新規顧客の受付を終了している。
    - B: 正しい。
    - C: 誤り。集計の実装が必要で、時系列の機能を使えない。
    - D: 誤り。この規模の時系列に向かず、チームの経験も活かせない。

    **スキル:** [1.5.3](../domain1.md#skill-1-5-3) / **参照:** [データベースの選び方](../../../services/databases-specialized.md#choosing)

### 問5 {#q5}

銀行の勘定系は Aurora MySQL にあります。書き込みは東京だけで構いませんが、大阪からも低遅延で読みます。東京のリージョン障害では、大阪を書き込み可能にします。RPO はできるだけ小さくし、アプリの書き込みの処理は変えません。どれを選びますか。

- A. Aurora グローバルデータベースを東京をプライマリ、大阪をセカンダリで作る
- B. 東京の Aurora に Multi-AZ のレプリカを増やす
- C. 大阪に別の Aurora を作り、AWS Backup のクロスリージョンコピーを毎時で実行する
- D. DMS の継続的なレプリケーションで、大阪の RDS for MySQL へ複製する

??? success "答えと解説"
    **正解: A**

    グローバルデータベースは、1 つのプライマリと読み取り専用のセカンダリのリージョンで構成します。障害時はセカンダリに切り替えられます。

    - A: 正しい。
    - B: 誤り。リージョン障害に耐えられない。
    - C: 誤り。毎時では RPO が大きく、大阪から読み取りもできない。
    - D: 誤り。動くが、遅延と運用の負担が大きい。

    **スキル:** [1.5.4](../domain1.md#skill-1-5-4) / **参照:** [Aurora グローバルデータベース](../../../services/databases.md#aurora-global-database)

### 問6 {#q6}

新しい決済システムは、東京と大阪の DynamoDB に書き込み、どちらのリージョンから読んでも常に最新の値が必要です。書き込みの遅延は多少増えても構いません。シンガポールにデータを置くことは認められていますが、読み書きはしません。テーブルはこれから作ります。どれを選びますか。

- A. MREC のグローバルテーブルを 2 リージョンで作る
- B. MRSC のグローバルテーブルを東京と大阪のレプリカと、シンガポールの witness で作る
- C. MRSC のグローバルテーブルを東京と大阪の 2 リージョンだけで作る
- D. 東京を主として書き込み、大阪は DynamoDB Streams と Lambda で複製する

??? success "答えと解説"
    **正解: B**

    MRSC はちょうど 3 リージョンの構成で、3 レプリカか、2 レプリカと witness にします。どのレプリカからでも強い整合性で読めます。

    - A: 誤り。MREC は結果整合性で、常に最新は読めない。
    - B: 正しい。
    - C: 誤り。MRSC は 2 リージョンだけでは作れない。
    - D: 誤り。大阪で書き込めず、常に最新の読み取りも保証しない。

    **スキル:** [1.5.4](../domain1.md#skill-1-5-4) / **参照:** [グローバルテーブル](../../../services/dynamodb.md#global-tables)

### 問7 {#q7}

Lambda の関数が RDS for PostgreSQL へ接続します。アクセスの急増時に `too many connections` のエラーが発生します。DB のフェイルオーバーの時間も短くしたいです。インスタンスのサイズは変えず、アプリの変更も最小にします。どれを選びますか。

- A. リードレプリカを追加し、Lambda の接続先を分散させる
- B. Lambda の同時実行数を 1 に制限する
- C. Lambda の実行環境の外に EC2 のコネクションプーラーを自分で構築する
- D. RDS Proxy を置き、Lambda の接続先を Proxy に変える

??? success "答えと解説"
    **正解: D**

    RDS Proxy は接続をプールして再利用し、急増に対応します。フェイルオーバーの影響も抑えられます。

    - A: 誤り。書き込みの接続には効かず、読み取りでも急増の問題は残る。
    - B: 誤り。処理量が大きく落ちる。
    - C: 誤り。動くが、サーバーの運用が増える。
    - D: 正しい。

    **スキル:** [1.5.4](../domain1.md#skill-1-5-4) / **参照:** [RDS Proxy](../../../services/databases.md#rds-proxy)

### 問8 {#q8}

RDS for MySQL の Multi-AZ（1 つのスタンバイ）を運用しています。可用性は高いのですが、レポートの読み取りがプライマリの負荷になっています。障害時の切り替えを含む高可用性を保ちつつ、レポートの読み取りをプライマリから外します。レポートは数秒の遅れを許容できます。Aurora へは移行しません。条件を満たす方法を選んでください。（2つ選択）

- A. Multi-AZ DB クラスターの形式へ移行し、読み取りのエンドポイントでレポートを読む
- B. スタンバイのエンドポイントを指定して、レポートの読み取りを行う
- C. 非同期のリードレプリカを追加し、レプリケーションの遅れを許容できるレポートをそこで読む
- D. RDS Proxy を置いて、スタンバイへ読み取りを分散する
- E. 別のリージョンに RDS を手動で作成し、書き込みをアプリで二重に行う

??? success "答えと解説"
    **正解: A, C**

    Multi-AZ DB クラスターのリーダーは読み取りに使えます。遅れを許容できるレポートなら、リードレプリカも読み取りの拡張の手段です。

    - A: 正しい。
    - B: 誤り。インスタンス形式のスタンバイは読み取りに使えない。
    - C: 正しい。
    - D: 誤り。インスタンス形式のスタンバイは読み取りに使えず、Proxy でも変わらない。
    - E: 誤り。二重書き込みの実装が必要で、不整合の原因になる。

    **スキル:** [1.5.4](../domain1.md#skill-1-5-4) / **参照:** [リードレプリカと Multi-AZ](../../../services/databases.md#read-replicas)

### 問9 {#q9}

ゲノム解析の HPC は、数百の計算ノードから同じファイルを並列に読み、1 ミリ秒未満の遅延で大きな帯域を必要とします。入力は S3 に置いてあり、ジョブの間だけ高速なファイルシステムとして見せたいです。結果も S3 に戻します。どれを選びますか。

- A. EFS の Max I/O を使う
- B. FSx for Lustre を S3 と関連付ける
- C. EBS の `io2` Block Express を Multi-Attach で全ノードにマウントする
- D. FSx for Windows File Server を SMB でマウントする

??? success "答えと解説"
    **正解: B**

    FSx for Lustre は HPC と機械学習の並列処理向けで、S3 と連携できます。

    - A: 誤り。並列の HPC の帯域と遅延の要件に、Lustre ほど合わない。
    - B: 正しい。
    - C: 誤り。Multi-Attach は同じ AZ の少数のインスタンスが対象で、数百のノードに使えない。
    - D: 誤り。Windows のファイル共有向けである。

    **スキル:** [1.5.5](../domain1.md#skill-1-5-5) / **参照:** [FSx の選び方](../../../services/storage-advanced.md#fsx-selection)

### 問10 {#q10}

デザイン会社はオンプレミスの NetApp のストレージを使い、NFS と SMB で同じデータにアクセスしています。SnapMirror での移行と、既存のスナップショットの運用を続けたいです。新しい運用の手順は増やしたくありません。どれを選びますか。

- A. FSx for OpenZFS
- B. FSx for NetApp ONTAP
- C. EFS と FSx for Windows File Server を並べて、データを同期する
- D. S3 File Gateway と S3 を使い、NFS と SMB の共有を作る

??? success "答えと解説"
    **正解: B**

    ONTAP はマルチプロトコルと SnapMirror に対応し、NetApp からの移行に向きます。

    - A: 誤り。SMB と SnapMirror に対応しない。
    - B: 正しい。
    - C: 誤り。同期の仕組みが増え、運用も変わる。
    - D: 誤り。SnapMirror を使えず、ONTAP の運用を続けられない。

    **スキル:** [1.5.5](../domain1.md#skill-1-5-5) / **参照:** [FSx の選び方](../../../services/storage-advanced.md#fsx-selection)

### 問11 {#q11}

Web サーバー群は Linux で、複数の AZ のインスタンスから同じファイルを読み書きします。アクセス量は日によって大きく変わります。ストレージの容量の管理はしたくありません。Windows や NetApp の機能は不要です。どれを選びますか。

- A. EBS の `gp3` を各インスタンスに付け、rsync で定期的に同期する
- B. EC2 の 1 台で NFS サーバーを動かし、他のインスタンスからマウントする
- C. FSx for Windows File Server を Multi-AZ で作り、Linux から SMB でマウントする
- D. EFS を作り、各 AZ のマウントターゲットを通して全インスタンスからマウントする

??? success "答えと解説"
    **正解: D**

    EFS は複数の AZ の Linux から NFS で共有でき、容量は自動で増減します。

    - A: 誤り。同期の遅れがあり、書き込みの競合も解決できない。
    - B: 誤り。単一障害点になり、運用も増える。
    - C: 誤り。Windows の機能は不要で、SMB のクライアントの準備も増える。
    - D: 正しい。

    **スキル:** [1.5.5](../domain1.md#skill-1-5-5) / **参照:** [EFS の設定](../../../services/storage.md#efs-settings)

### 問12 {#q12}

ap-northeast-1a の EC2 で使っている EBS ボリュームを、AZ 障害に備えて ap-northeast-1c の新しいインスタンスでも使えるようにします。データは数 TB あります。追加のストレージサービスは使いません。正しい手順はどれですか。

- A. ボリュームをデタッチし、別の AZ のインスタンスにアタッチする
- B. Multi-Attach を有効にして、別の AZ のインスタンスにもアタッチする
- C. スナップショットを作り、1c で新しいボリュームを作成する
- D. ボリュームのプロパティで AZ を 1c に変更する

??? success "答えと解説"
    **正解: C**

    EBS は 1 つの AZ に閉じます。別の AZ で使うには、スナップショットからボリュームを作ります。

    - A: 誤り。別の AZ のインスタンスにはアタッチできない。
    - B: 誤り。Multi-Attach は同じ AZ の中の機能である。
    - C: 正しい。

### 問13 {#q13}

EC サイトの商品ページは DynamoDB を読みます。読み取りの大半は結果整合性で構わず、ピーク時にマイクロ秒の応答が必要です。SDK の呼び出しのコードはできるだけ変えません。在庫の確認だけは強い整合性で読みます。どの構成が最も適切ですか。

- A. ElastiCache を前に置き、アプリにキャッシュの読み書きのコードを追加する
- B. DAX を前に置く。強い整合性の読み取りは DynamoDB に素通しされると理解して使う
- C. DAX を前に置く。強い整合性の読み取りも DAX のキャッシュから返されると理解して使う
- D. DynamoDB のオンデマンドモードにして、読み取りの遅延をマイクロ秒に下げる

??? success "答えと解説"
    **正解: B**

    DAX は DynamoDB 互換の API でコードの変更が少なく、マイクロ秒で読めます。強い整合性の読み取りはキャッシュされず、DynamoDB に渡されます。

    - A: 誤り。動くが、アプリの実装が必要になる。
    - B: 正しい。
    - C: 誤り。強い整合性の読み取りには DAX のキャッシュが効かない。
    - D: 誤り。キャパシティモードで遅延はマイクロ秒にならない。

### 問14 {#q14}

ElastiCache の前で遅延読み込みを使っています。商品の価格を更新しても、古い値がしばらく表示されるという苦情があります。価格の更新はあまり多くなく、読み取りは大量です。更新の直後から新しい値を返し、キャッシュ全体のメモリの無駄は TTL で抑えます。どの変更が最も適切ですか。

- A. キャッシュをなくして、全リクエストで Aurora を読むようにする
- B. 価格の更新時に書き込みスルーでキャッシュも更新し、TTL も設定する
- C. キャッシュのノードを増やして、ヒット率を上げる
- D. TTL を 1 年に延ばして、キャッシュミスを減らす

??? success "答えと解説"
    **正解: B**

    遅延読み込みはデータの更新時にキャッシュを変えないので、古い値が残ります。書き込みスルーを加えれば更新の直後から正しい値を返せます。TTL で使わないデータも消えます。

    - A: 誤り。読み取りが大量なので、データベースの負荷と遅延が増える。
    - B: 正しい。
    - C: 誤り。ヒット率が上がっても古い値は残る。
    - D: 誤り。古い値がより長く残る。

    **スキル:** [1.5.6](../domain1.md#skill-1-5-6) / **参照:** [キャッシュ戦略](../../../services/databases.md#caching-strategies)

### 問15 {#q15}

天気の API は REST API の API Gateway で提供しています。応答は地域ごとに 5 分間変わらず、世界中の利用者が呼びます。バックエンドの Lambda の呼び出しを減らし、遠い利用者の遅延も下げます。データベースのキャッシュは今の問題の中心ではありません。どれが最も適切ですか。

- A. CloudFront を前に置き、地域のパラメーターをキャッシュキーにして TTL を 5 分にする
- B. DAX をバックエンドの DynamoDB の前に置く
- C. Lambda の Provisioned Concurrency を増やす
- D. ElastiCache を Lambda の後ろに置く

??? success "答えと解説"
    **正解: A**

    エッジのキャッシュは Lambda の呼び出しを減らし、利用者に近い場所で応答できます。API の応答もキャッシュできます。

    - A: 正しい。
    - B: 誤り。データベースの読み取りが速くなるだけで、Lambda の呼び出しと遠い利用者の遅延は変わらない。
    - C: 誤り。コールドスタートは減るが、呼び出しの数は減らない。
    - D: 誤り。Lambda の呼び出しは減らない。

    **スキル:** [1.5.6](../domain1.md#skill-1-5-6) / **参照:** [DAX、ElastiCache、CloudFront の使い分け](../../../services/databases.md#cache-comparison)
