# オブザーバビリティの問題集

対象の解説: [オブザーバビリティ](../../../services/observability.md)、[CloudWatch Synthetics と RUM](../../../services/operations.md#synthetics)、[生成 AI の監視](../../../services/genai-apps.md#genai-metrics)

### 問1 {#q1}

ある企業は、ECS と Lambda で動く 50 の新しいサービスの計装を標準化します。将来、トレースの送り先を別の製品へ変える可能性があり、特定のベンダーの SDK に依存したくありません。トレースは当面 CloudWatch で確認します。既存の教材では X-Ray SDK とデーモンを使う手順が紹介されています。最も適切な標準はどれですか。

- A. X-Ray SDK とデーモンを標準にする。新規の開発でも推奨され、機能追加も続くからである
- B. ADOT で計装し、Lambda には ADOT のレイヤーを使う
- C. 各サービスが構造化ログだけを出し、Logs Insights の結合でサービス間の呼び出しを推測するので、トレースの計装は作らない
- D. サービスごとに自由に SDK を選び、送り先の違いは中央の変換用の Lambda で吸収する

??? success "答えと解説"
    **正解: B**

    X-Ray SDK とデーモンはメンテナンスモードで、新規の計装には OpenTelemetry が推奨されています。ADOT ならベンダーに依存せず、CloudWatch でも確認できます。

    - A: 誤り。2026 年 2 月 25 日からセキュリティ修正のみです。
    - B: 正しい。
    - C: 誤り。ログからの推測では、呼び出しの経路と遅い箇所を正確に追えません。
    - D: 誤り。標準化にならず、変換の部品を運用する負荷が増えます。

    **スキル:** [5.3.1](../domain5.md#skill-5-3-1) / **参照:** [SDK と OpenTelemetry](../../../services/observability.md#xray-opentelemetry)

### 問2 {#q2}

組織には 1 つのリージョンで動く 60 のアカウントがあり、毎月アカウントが増えます。運用チームは 1 つの監視アカウントから、各アカウントのメトリクス、ログ、トレースを、切り替えなしで検索したいです。データのコピーは増やしたくありません。新しいアカウントも自動で対象にします。最も適切な方法はどれですか。

- A. 各アカウントのログとメトリクスをストリームで監視アカウントへコピーし、トレースは定期的にエクスポートする
- B. 監視アカウントの担当者に各アカウントのスイッチロールを許可し、ブラウザのブックマークを共有する
- C. 監視アカウントにダッシュボードを作り、各アカウントの API を Lambda で定期的に呼んでカスタムメトリクスとして保存する
- D. 監視アカウントにシンクを作り、Organizations でソースアカウントをリンクする

??? success "答えと解説"
    **正解: D**

    CloudWatch のクロスアカウントオブザーバビリティです。シンクにソースアカウントをリンクします。Organizations を使うと、新しいアカウントも自動で対象になります。

    - A: 誤り。データのコピーが増え、費用と複雑さも増えます。
    - B: 誤り。切り替えなしで見るという要件に反します。
    - C: 誤り。ログとトレースを扱えず、独自のコードも増えます。
    - D: 正しい。

    **スキル:** [5.3.1](../domain5.md#skill-5-3-1) / **参照:** [ロギング、モニタリング、オブザーバビリティの違い](../../../services/observability.md#logging-monitoring-observability)、[クロスアカウントオブザーバビリティ（公式）](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Unified-Cross-Account.html)

### 問3 {#q3}

障害の調査に時間がかかっています。アラームで遅延の増加に気づいても、どのサービスが遅いのかが分からず、ログも自由な形式の文字列で、該当のリクエストの行を探せません。調査の流れを標準化します。どの設計が最も適切ですか。

- A. メトリクスで異常に気づき、トレースで遅い箇所を特定し、トレース ID を含む JSON のログで原因を調べる
- B. すべての行を DEBUG レベルにして、Live Tail で障害の発生中に目視で確認する
- C. 全サービスのログを 1 つのログストリームに書き込み、時刻で並べて確認する
- D. メトリクスの解像度を 1 秒にして、平均の遅延を全サービスの共通のダッシュボードに並べ、遅いものを順に調べる

??? success "答えと解説"
    **正解: A**

    メトリクスは「何が」、トレースは「どこで」、ログは「なぜ」に答えます。JSON の構造化ログにトレース ID を含めると、シグナルをつなげられます。

    - A: 正しい。
    - B: 誤り。費用が増え、目視に頼ります。経路も分かりません。
    - C: 誤り。検索が難しくなり、リクエストのつながりも分かりません。
    - D: 誤り。平均だけでは一部の遅いリクエストが隠れ、原因にも届きません。

    **スキル:** [5.3.1](../domain5.md#skill-5-3-1) / **参照:** [ロギング、モニタリング、オブザーバビリティの違い](../../../services/observability.md#logging-monitoring-observability)、[構造化ログ](../../../services/observability.md#structured-logging)

### 問4 {#q4}

ECS on Fargate で 80 のサービスを動かしています。タスクは頻繁に入れ替わり、タスク ID ごとのダッシュボードはすぐに役に立たなくなります。運用チームは、クラスターとサービスの単位で CPU、メモリ、ネットワークの使用状況を見て、アラームも設定したいです。エージェントの導入の手間は最小にします。最も適切な方法はどれですか。

- A. 各コンテナのアプリから `PutMetricData` でタスク ID ごとにカスタムメトリクスを送る
- B. 各タスクの ENI に VPC フローログを有効にして、通信量から負荷を推定する
- C. クラスターの Container Insights を有効にする
- D. EC2 ホストの CloudWatch エージェントを Systems Manager で配布し、ホスト単位で集計する

??? success "答えと解説"
    **正解: C**

    Container Insights は、クラスター、サービス、タスクの単位でメトリクスを集約します。短命なタスクはサービスの単位で見ます。

    - A: 誤り。実装が増え、タスク ID の単位では高コストで役に立ちにくくなります。
    - B: 誤り。通信量だけでは CPU やメモリは分かりません。
    - C: 正しい。
    - D: 誤り。Fargate では利用者がホストを管理しません。

    **スキル:** [5.3.2](../domain5.md#skill-5-3-2) / **参照:** [logConfiguration](../../../services/containers.md#log-configuration)、[Container Insights（公式）](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/ContainerInsights.html)

### 問5 {#q5}

ECS のアプリは標準出力へログを書きます。アプリのコードは変更せずに、ログを Firehose と協力会社の監視製品の両方へ送ります。チームが FireLens のログルーターをタスク定義に追加したところ、ルーターのコンテナは起動しますが、Firehose へのログの送信だけが失敗します。最も可能性の高い原因はどれですか。

- A. FireLens は Fargate で使えないので、`awslogs` ドライバーに戻す必要がある
- B. タスク実行ロールに `logs:CreateLogGroup` がなく、ログを中継できない
- C. アプリのコンテナの `dependsOn` がなく、ルーターより後に起動できない
- D. タスクロールに `firehose:PutRecordBatch` がない

??? success "答えと解説"
    **正解: D**

    FireLens では、ログの宛先を呼ぶ権限はタスクロールに必要です。Firehose へ送るなら `firehose:PutRecordBatch` です。

    - A: 誤り。FireLens は Fargate でも使えます。
    - B: 誤り。Firehose への送信に必要な権限ではありません。実行ロールはイメージの取得などに使います。
    - C: 誤り。ECS は既定で、ルーターが先に起動する依存関係を設定します。
    - D: 正しい。

    **スキル:** [5.3.2](../domain5.md#skill-5-3-2) / **参照:** [logConfiguration](../../../services/containers.md#log-configuration)、[FireLens（公式）](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/using_firelens.html)

### 問8 {#q8}

費用の削減のため、昨年作成したアプリのロググループはすべて Essentials クラスです。今回、これらのログを中央のアカウントへ集めることになり、サブスクリプションフィルターの作成を試みましたが、作成できません。ログの取り込みを止める時間は短くしたいです。最も適切な対応はどれですか。

- A. 既存のロググループのクラスを Standard に変更してから、フィルターを作成する

### 問9 {#q9}

ログストリームの少ない大量のログを、プロビジョンドの Kinesis Data Streams へサブスクリプションフィルターで送っています。`DeliveryThrottling` が増えていて、シャード全体の容量には余裕があるのに、一部のシャードだけが混んでいます。ログの欠落は避けたいです。正しい理解と対応はどれですか。

- A. スロットリングされた配信は無期限に再試行されるので、欠落の心配はなく、対応は不要である
- B. スロットリングされたログは直ちに破棄される。Firehose へ切り替えるしか対応がない

全アカウントのログについて、2 つの要件があります。セキュリティチームは、認証のログを準リアルタイムで検索します。監査部門は、全ログを 7 年間保管し、まれに SQL で調べます。保管の費用は最小にします。最も適切な組み合わせはどれですか。（2つ選択）

- A. 全ログを CloudWatch Logs の Standard のまま 7 年間保持し、Logs Insights で調べる

### 問11 {#q11}

当番の担当者は、CPU、遅延、エラー率の 3 つのアラームから別々に呼び出され、夜間の呼び出しが多すぎます。CPU が高いだけなら、利用者に影響はありません。エラー率か遅延が高く、かつデプロイ中でないときだけ呼び出したいです。個別のアラームはダッシュボードに残します。最も適切な方法はどれですか。

- A. 3 つのアラームの期間を 1 時間に延ばし、夜間だけ SNS のサブスクリプションを無効にするスクリプトを作る
- B. 子のアラームから通知を外し、複合アラームにだけ SNS を設定する
- C. 子のアラームの通知を残したまま複合アラームを追加する

    - B: 正しい。
    - C: 誤り。子の通知が残ると、呼び出しは減りません。

### 問12 {#q12}

EC の受注数は、平日の昼に多く、深夜に少ないパターンです。深夜に受注が急に止まる障害があっても、深夜の通常の水準が低いので、固定のしきい値では検知できませんでした。しきい値を時間帯ごとに手で調整し続けるのは避けたいです。最も適切なアラームはどれですか。

- A. M out of N を 1 out of 1 にした固定のしきい値のアラーム
- B. 時間帯ごとに固定のしきい値を変える Lambda を EventBridge Scheduler で実行する
- C. 帯の下側を下回ったときに鳴る異常検知のアラーム
- D. `treatMissingData` を `breaching` にした固定のしきい値のアラーム

??? success "答えと解説"
    **正解: C**

    異常検知は、時間と曜日の周期を考慮して「普通の帯」を学習します。下側を下回る条件なら、その時間帯の水準に対する急減で鳴ります。

    - A: 誤り。評価の回数を変えても、固定のしきい値の問題は残ります。
    - B: 誤り。手で調整する作業をコードに移すだけで、周期の変化にも追従しません。
    - C: 正しい。
    - D: 誤り。受注数が 0 でもデータが来ていれば欠落ではなく、急減の検知になりません。

    **スキル:** [5.3.4](../domain5.md#skill-5-3-4) / **参照:** [異常検知](../../../services/observability.md#anomaly-detection)

### 問13 {#q13}

常駐の処理は、動いている間だけ 1 分ごとにカスタムメトリクスのハートビートを送ります。アラームは `notBreaching` にしていて、値が 1 未満で鳴る設定です。ある夜、プロセスが止まりましたが、アラームは `OK` のままで、翌朝まで誰も気づきませんでした。最小の変更で検知するにはどうしますか。

- A. アラームの評価の期間を 1 分から 1 時間に延ばす
- B. `treatMissingData` を `breaching` にする
- C. `treatMissingData` を `ignore` にする
- D. アラームをメトリクスの異常検知に変え、学習の期間を 2 週間にして帯の幅を広げる

??? success "答えと解説"
    **正解: B**

    データが来ないこと自体が障害なので、欠落を異常として扱います。`notBreaching` では止まっても `OK` のままです。

    - A: 誤り。欠落の扱いが変わらないので鳴りません。検知も遅れます。
    - B: 正しい。
