# エッジ、リアルタイム、マルチテナントの問題集

対象の解説: [エッジ関数](../../../services/networking.md#edge-functions)、[WebSocket API](../../../services/api-gateway.md#websocket)、[マルチテナントのデータアクセス](../../../services/secrets.md#multi-tenant)

### 問1 {#q1}

世界向けのニュースサイトは、毎秒数十万のリクエストを CloudFront で受けています。すべてのリクエストで国コードのヘッダーを追加し、URL を正規化してキャッシュヒット率を上げます。外部の呼び出しはありません。追加する遅延と費用を最小にします。どれを選びますか。

- A. ビューワーリクエストの Lambda@Edge で処理する
- B. オリジンリクエストの Lambda@Edge で処理し、キャッシュミスのときだけ実行する
- C. ビューワーリクエストの CloudFront Functions で処理する
- D. オリジンの ALB の前に Lambda を置き、ヘッダーの追加と URL の正規化を行う

??? success "答えと解説"
    **正解: C**

    ヘッダーの変更と URL の正規化は CloudFront Functions の用途です。1 ミリ秒未満で動き、毎秒数百万リクエストまで扱えます。

    - A: 誤り。動くが、遅延と費用が大きい。公式の比較表では、規模はリージョンあたり毎秒 10,000 リクエストまでである。
    - B: 誤り。キャッシュキーの正規化は、キャッシュを見る前に行う必要がある。
    - C: 正しい。
    - D: 誤り。CloudFront のキャッシュキーの前に処理できず、キャッシュヒット率を上げられない。

    **スキル:** [1.1.11](../domain1.md#skill-1-1-11) / **参照:** [Lambda@Edge と CloudFront Functions](../../../services/networking.md#edge-functions)

### 問2 {#q2}

多国展開の EC サイトは、利用者ごとの契約先を DynamoDB で調べ、その結果に応じて CloudFront のオリジンを切り替えます。参照はキャッシュミスのときだけで構いません。処理には AWS SDK が必要です。どの方式が適切ですか。

- A. オリジンリクエストの Lambda@Edge で DynamoDB を参照し、オリジンを切り替える
- B. ビューワーリクエストの CloudFront Functions から AWS SDK で DynamoDB を呼び、オリジンのドメインを書き換える
- C. CloudFront の継続的デプロイのステージングディストリビューションで、利用者の割合に応じてオリジンを振り分ける
- D. オリジングループを作り、契約先ごとのオリジンをフェイルオーバーの順に並べる

??? success "答えと解説"
    **正解: A**

    外部の呼び出しや SDK が必要なら Lambda@Edge です。オリジンリクエストのイベントなら、キャッシュミスのときだけ実行されます。

    - A: 正しい。
    - B: 誤り。CloudFront Functions は外部へ通信できない。
    - C: 誤り。継続的デプロイは新しい設定を割合で試す機能で、契約先による選択はできない。
    - D: 誤り。オリジングループは障害時のフェイルオーバーの機能である。

    **スキル:** [1.1.11](../domain1.md#skill-1-1-11) / **参照:** [エッジ関数の制限](../../../services/networking.md#edge-function-limits)

### 問3 {#q3}

オリジンは古いシステムで、`Cache-Control` を正しく返しません。オリジンのコードは変更できません。CloudFront がレスポンスをキャッシュする前にヘッダーを修正し、キャッシュされた結果にもその修正を反映させます。修正の処理はキャッシュミスのときだけ動かします。どれを選びますか。

- A. ビューワーレスポンスの CloudFront Functions でヘッダーを書き換える
- B. ビューワーリクエストの CloudFront Functions でヘッダーを追加する
- C. オリジンレスポンスの Lambda@Edge でヘッダーを書き換える
- D. WAF のカスタムレスポンスのルールを作り、オリジンからのレスポンスのヘッダーを変更する

??? success "答えと解説"
    **正解: C**

    キャッシュの前にレスポンスを変えるのはオリジンレスポンスのイベントです。CloudFront Functions はオリジンのイベントを扱えません。

    - A: 誤り。ビューワーレスポンスはキャッシュの後で動くので、キャッシュの動作を変えられない。
    - B: 誤り。リクエストの処理で、オリジンのレスポンスのヘッダーを修正できない。
    - C: 正しい。
    - D: 誤り。WAF はリクエストの検査の機能で、オリジンのレスポンスのヘッダーを修正しない。

    **スキル:** [1.1.11](../domain1.md#skill-1-1-11) / **参照:** [Lambda@Edge と CloudFront Functions](../../../services/networking.md#edge-functions)

### 問4 {#q4}

共同編集のサービスは、API Gateway の WebSocket API を使っています。利用者から「ちょうど 2 時間で切断される」「操作しないと 10 分ほどで切断される」という報告があります。接続を維持している体験を保ちます。適切な対応を選んでください。（2つ選択）

- A. クライアントに、切断を検知して自動で再接続する処理を入れる
- B. Service Quotas で接続時間の上限の引き上げを申請する
- C. クライアントから 10 分より短い間隔でメッセージを送る
- D. CloudFront を前段に置いて、接続時間の上限を回避する
- E. WebSocket API を REST API に変更して、長時間の接続を維持する

??? success "答えと解説"
    **正解: A, C**

    接続時間 2 時間とアイドルタイムアウト 10 分は調整できない上限です。再接続と定期的なメッセージで対応します。

    - A: 正しい。
    - B: 誤り。どちらの値も引き上げられない。
    - C: 正しい。
    - D: 誤り。API Gateway の上限は残り、回避にならない。
    - E: 誤り。REST API は WebSocket の接続を維持する仕組みではない。

    **スキル:** [1.1.12](../domain1.md#skill-1-1-12) / **参照:** [WebSocket API](../../../services/api-gateway.md#websocket)

### 問5 {#q5}

金融情報の配信で、WebSocket API を通じて最大 500 KB のレポートをクライアントへ渡します。128 KB を超えると送信できません。送信の頻度は 1 時間に数回で、接続の数は数万です。どう設計しますか。

- A. レポートを S3 に置き、署名付き URL を WebSocket で送る
- B. レポートを 128 KB を超える単位のフレームに分け、順番に送って結合する
- C. Service Quotas で、WebSocket のメッセージの上限を 500 KB に引き上げる
- D. API Gateway の前に NLB を置き、TCP のレベルで大きなメッセージを中継する

??? success "答えと解説"
    **正解: A**

    フレームは 32 KB、メッセージは 128 KB が上限で、引き上げられません。大きなデータは S3 に置いて URL を送ります。

    - A: 正しい。
    - B: 誤り。128 KB はメッセージの上限で、超える単位では送れない。また、フレーム自体は 32 KB までである。
    - C: 誤り。調整できない上限である。
    - D: 誤り。API Gateway の上限は変わらない。

    **スキル:** [1.1.12](../domain1.md#skill-1-1-12) / **参照:** [WebSocket API](../../../services/api-gateway.md#websocket)

### 問6 {#q6}

配送の状況をリアルタイムに通知します。`$connect` の Lambda は、接続 ID を実行環境のメモリの配列に保存しています。別のサービスの配送イベントで起動する Lambda が送信しますが、通知が届かない利用者がいます。発生元と配信を疎結合にします。どう設計し直しますか。

- A. Lambda の同時実行数を 1 に制限して、すべての処理を同じ実行環境で行い、配列を共有する
- B. 接続 ID を DynamoDB に保存し、配送イベントを EventBridge で受けた Lambda が `@connections` で送る
- C. Lambda の SnapStart を有効にして、接続 ID の配列を含む実行環境を保存し、全実行環境で共有する
- D. クライアントが数秒ごとに REST API をポーリングする方式に変える

??? success "答えと解説"
    **正解: B**

    実行環境のメモリは他の実行環境と共有されません。接続 ID を外部に置き、イベントで配信の処理を動かします。

    - A: 誤り。スケールせず、実行環境が入れ替わると配列は失われる。
    - B: 正しい。
    - C: 誤り。スナップショットは初期化の時点の状態で、実行中の更新は共有されない。
    - D: 誤り。リアルタイムの要件を満たさず、呼び出しの量も増える。

    **スキル:** [1.1.12](../domain1.md#skill-1-1-12) / **参照:** [ファンアウト](../../../services/messaging.md#fanout)

### 問7 {#q7}

WebSocket API で、`$connect` ルートに Lambda オーソライザーを設定しています。契約を解約した利用者が、接続を保ったまま配信を受け続けていることが分かりました。解約の時点で配信を止める必要があります。どうしますか。

- A. オーソライザーのキャッシュの TTL を 0 にして、以降のメッセージごとに認可を実行させる
- B. カスタムルートごとにオーソライザーを設定して、送信される配信にも認可を適用する
- C. 解約のイベントを受けた処理で、接続 ID へ `@connections` の `DELETE` を呼ぶ
- D. WAF のルールで解約した利用者の IP アドレスを拒否する

??? success "答えと解説"
    **正解: C**

    認可は `$connect` のときだけ判定され、接続後は再評価されません。解約時にサーバー側から切断します。

    - A: 誤り。接続後のメッセージではオーソライザーは実行されない。
    - B: 誤り。オーソライザーは `$connect` ルートだけに設定する。
    - C: 正しい。
    - D: 誤り。IP アドレスは変わり、確立済みの接続の配信も止められない。

    **スキル:** [1.1.12](../domain1.md#skill-1-1-12) / **参照:** [WebSocket API](../../../services/api-gateway.md#websocket)

### 問8 {#q8}

B2B の SaaS は、Lambda、DynamoDB、S3 をテナントで共有しています。現在は 1 つの実行ロールを全テナントで使い、コードの条件でテナントを分けています。開発者のミスがあっても、他のテナントのデータに触れないようにします。テナントの数は数千で、今後も増えます。どの設計が最も適切ですか。

- A. テナントごとに AWS アカウントを作り、アカウントごとに Lambda、DynamoDB、S3 をデプロイする
- B. テナントのタグを付けた STS セッションを使い、`dynamodb:LeadingKeys` と S3 のプレフィックスを制限する
- C. コードレビューと静的解析を必須にして、すべてのクエリにテナント ID の条件があることを確認する
- D. API Gateway のリソースポリシーで、テナントごとに呼び出せるパスを制限する

??? success "答えと解説"
    **正解: B**

    JWT のテナント ID から、セッションタグ付きの一時認証情報を作ります。ポリシーの変数で、触れるキーとプレフィックスを制限します。

    - A: 誤り。分離は強いが、数千のテナントでは費用と運用の負荷が大きすぎる。
    - B: 正しい。
    - C: 誤り。ミスを減らすだけで、仕組みとして防いでいない。
    - D: 誤り。入口の制限で、関数内のデータアクセスは分離されない。

    **スキル:** [1.1.13](../domain1.md#skill-1-1-13) / **参照:** [動的なセッション](../../../services/secrets.md#tenant-sessions)

### 問9 {#q9}

SaaS の利用者には、多数の小規模なテナントと、規制を受ける数社の大口があります。大口はデータベースの分離と、自社のキーの失効で即時にデータを読めなくする機能を求めています。小規模なテナントの費用は低く保ちます。どのモデルが最も適切ですか。

- A. 全テナントをサイロにする
- B. 全テナントをプールにし、1 つの KMS キーで暗号化する
- C. 全テナントをプールにし、行レベルセキュリティと監査ログで大口の要件に説明をつける
- D. ブリッジにする。大口には専用のデータベースと専用の KMS キーを割り当てる

??? success "答えと解説"
    **正解: D**

    層やプランごとに分離の度合いを変えるブリッジのモデルです。大口はサイロに近く、小規模はプールで費用を抑えます。

    - A: 誤り。小規模なテナントの費用が高くなる。
    - B: 誤り。テナント単位の失効も監査もできない。
    - C: 誤り。データベースの分離とキーの失効の要件を満たさない。
    - D: 正しい。

    **スキル:** [1.1.13](../domain1.md#skill-1-1-13) / **参照:** [パターンの比較](../../../services/secrets.md#tenant-patterns)

### 問10 {#q10}

共有の Aurora PostgreSQL の同じテーブルに、3,000 のテナントのデータがあります。アプリのクエリで `WHERE` の条件を書き忘れると、他のテナントの行が見えてしまいます。テナントごとにデータベースを分ける費用は負担できません。データベース側で分離を強制します。どれを選びますか。

- A. IAM データベース認証を有効にして、テナントごとのトークンで接続する
- B. RDS Proxy を置いて、テナントごとに接続を分ける
- C. 行レベルセキュリティを有効にし、セッションのテナント ID でポリシーを適用する
- D. Aurora のカスタムエンドポイントをテナントごとに作り、接続先のインスタンスを分ける

??? success "答えと解説"
    **正解: C**

    PostgreSQL の行レベルセキュリティなら、クエリの条件を忘れても、データベースが行を制限します。

    - A: 誤り。認証の方法であり、見える行は制限されない。
    - B: 誤り。接続の管理の機能で、行は分離されない。
    - C: 正しい。
    - D: 誤り。エンドポイントは接続先のインスタンスを選ぶ機能で、行は分離されない。

    **スキル:** [1.1.13](../domain1.md#skill-1-1-13) / **参照:** [マルチテナントのデータアクセス](../../../services/secrets.md#multi-tenant)

### 問11 {#q11}

共有の API で、一部のテナントが大量に呼び出し、他のテナントの応答が遅くなっています。契約プランごとに毎秒の呼び出し数と月間の上限を決めたいです。API は API Gateway の REST API で、Lambda と DynamoDB につながっています。どの対策が適切ですか。

- A. プランごとの使用量プランを作り、テナントの API キーを関連付ける
- B. Lambda の予約済み同時実行を、プランの数に合わせて増やす
- C. WAF のレートベースルールを送信元 IP アドレスの単位で設定し、テナントの呼び出しを制限する
- D. DynamoDB をプロビジョンドモードに変えて、テーブル全体の読み書きの容量を固定する

??? success "答えと解説"
    **正解: A**

    使用量プランは API キーの単位でスロットリングとクォータを設定できます。騒がしい隣人への対策です。

    - A: 正しい。
    - B: 誤り。関数の単位の枠で、テナントごとの制限にならない。
    - C: 誤り。テナントと IP アドレスは対応せず、月間の上限も設定できない。
    - D: 誤り。全テナントで容量を共有するので、1 社の急増で他も影響を受ける。

    **スキル:** [1.1.13](../domain1.md#skill-1-1-13) / **参照:** [使用量プラン](../../../services/api-gateway.md#usage-plans)

### 問12 {#q12}

Cognito で認証する SaaS の API が、リクエストの `X-Tenant-Id` ヘッダーの値でテナントを判定しています。セキュリティの診断で、ヘッダーを書き換えると他のテナントのデータを取得できると指摘されました。テナントの文脈を改ざんできないようにします。どうしますか。

- A. ヘッダーの値を API Gateway のリクエスト検証の機能でテナント ID の形式と照合する
- B. Cognito の属性に持たせたテナント ID を、検証済みの JWT のクレームから取得する
- C. ヘッダーの値を TLS で保護し、通信の途中での書き換えができないようにする
- D. WAF のルールで、自社のテナント ID に一致しない形式のヘッダーを持つリクエストを拒否する

??? success "答えと解説"
    **正解: B**

    テナントの文脈は認証から伝えます。署名された JWT のクレームなら、利用者は書き換えられません。

    - A: 誤り。形式を確かめるだけで、他のテナントの正しい ID には効かない。
    - B: 正しい。
    - C: 誤り。書き換えているのは利用者自身で、TLS では防げない。
    - D: 誤り。形式の検査で、他のテナントの正しい ID を拒否できない。

    **スキル:** [1.1.13](../domain1.md#skill-1-1-13) / **参照:** [グループとカスタム属性](../../../services/cognito.md#groups-attributes)
