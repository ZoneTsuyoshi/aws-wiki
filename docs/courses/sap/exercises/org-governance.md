# マルチアカウントのガバナンスの問題集

### 問1 {#q1}

ある持株会社は、事業会社ごとに OU を作り、その下に本番と開発のアカウントを混ぜて置いています。結果として、本番だけに必要な SCP を事業会社ごとに何度も関連付けています。ログの保管と監査のアカウントもありません。ランディングゾーンを作り直します。推奨される構造はどれですか。

- A. 組織図に合わせて OU を保ち、SCP はアカウントごとに直接関連付けて差を吸収する
- B. Security OU に Log Archive と Audit のアカウントを置き、ワークロードは適用するポリシーの違いで OU を分ける
- C. 共通のワークロードは管理アカウントに置き、他のアカウントは事業会社ごとの OU の下に並べる
- D. すべてのアカウントを組織のルート直下に置いて、タグでの ABAC だけでアカウントごとの違いを表現する

??? success "答えと解説"
    **正解: B**

    OU は組織図ではなく、適用するポリシーの違いで分けます。セキュリティとログのアカウントは Security OU に分離します。

    - A: 誤り。関連付けの数の上限に当たりやすく、差の管理が複雑になります。
    - B: 正しい。
    - C: 誤り。管理アカウントには SCP や RCP が効かないので、ワークロードを置きません。
    - D: 誤り。OU でまとめて適用する利点を失います。

    **スキル:** [2.3.1](../domain2.md#skill-2-3-1) / **参照:** [OU の設計](../../../services/governance.md#org-ous)、[ランディングゾーンの構造](../../../services/governance.md#ct-landing-zone)

### 問2 {#q2}

あるプラットフォームチームは、Control Tower のランディングゾーンで年に約 60 のアカウントを発行します。アカウントの要求は Git の Pull Request でレビューし、ネットワークや初期のロールなどのカスタマイズも Terraform で管理したいと考えています。既存の標準は Terraform です。最も適切な方法はどれですか。

- A. Organizations の `CreateAccount` を呼ぶ Terraform を独自に作り、Control Tower への登録は後から手動で行う
- B. コンソールの Account Factory で発行し、カスタマイズの CloudFormation を手順書どおりに実行する
- C. Account Factory for Terraform を使い、アカウントの要求とカスタマイズを Git で管理する
- D. アプリのリソースも含めて Customizations for Control Tower の 1 つのマニフェストへ集約し、Terraform はやめる

??? success "答えと解説"
    **正解: C**

    Account Factory for Terraform（AFT）は、Terraform と Git でアカウントを発行し、カスタマイズします。

    - A: 誤り。Control Tower の管理から外れた発行になり、後の登録の手作業も残ります。
    - B: 誤り。手作業が残り、Git での管理という要件を満たしません。
    - C: 正しい。
    - D: 誤り。既存の標準である Terraform をやめることになります。アプリのリソースのデプロイは目的に合いません。

    **スキル:** [2.3.1](../domain2.md#skill-2-3-1) / **参照:** [ドリフトと拡張](../../../services/governance.md#ct-drift)

### 問3 {#q3}

ある会社の開発者は CloudFormation でリソースを作ります。「S3 バケットはアクセスログの設定を持つこと」という規定があります。違反したテンプレートは、リソースが作られる前に失敗させたいと考えています。作ってから検出して直す方式は認められません。Control Tower で最も適切なコントロールの種類はどれですか。

- A. Config ルールによる検出的コントロールを有効にして、違反があれば自動で修復する
- B. SCP による予防的コントロールで、`s3:CreateBucket` をすべて拒否する
- C. Security Hub CSPM の標準を有効にして、検出結果を開発者へ通知する
- D. CloudFormation Hooks によるプロアクティブコントロールを有効にする

??? success "答えと解説"
    **正解: D**

    プロアクティブコントロールは、CloudFormation でリソースを作る前にプロパティを確認し、不適合なら作りません。

    - A: 誤り。作成の後に検出します。要件に反します。
    - B: 誤り。正しいバケットの作成も止まります。
    - C: 誤り。これも作成後の検出です。
    - D: 正しい。

    **スキル:** [2.3.1](../domain2.md#skill-2-3-1) / **参照:** [コントロール](../../../services/governance.md#ct-controls)

### 問4 {#q4}

ある管理者は緊急の対応として、Control Tower が管理する SCP を Organizations のコンソールから直接編集しました。その後、Control Tower に OU のドリフトが表示されました。追加したかった制限は、今後も残す必要があります。最も適切な対応はどれですか。

- A. ドリフトは無視し、次回のランディングゾーンの更新で自動的に解消されるのを待つ
- B. ランディングゾーンを削除して作り直し、全アカウントを再度登録する
- C. Control Tower が管理する SCP を手で元の内容へ戻し続け、変更履歴を別に記録する
- D. OU を再登録して修復し、独自の制限は別の SCP にする

??? success "答えと解説"
    **正解: D**

    ドリフトの検出は自動ですが、解消は手動です。Re-register OU で修復します。独自の制限を入れるには、Control Tower が管理するものとは別の SCP を作って関連付けます。

    - A: 誤り。ドリフトは自動で解消されません。
    - B: 誤り。影響が大きすぎます。修復の手順があります。
    - C: 誤り。Control Tower の外での変更が続くので、再びドリフトになります。
    - D: 正しい。

    **スキル:** [2.3.1](../domain2.md#skill-2-3-1) / **参照:** [ドリフトと拡張](../../../services/governance.md#ct-drift)

### 問5 {#q5}

ある組織は 300 のアカウントの API の操作を監査します。メンバーアカウントの管理者であっても記録を止められないようにします。ログは専用のアカウントに集め、書き換えられないようにします。将来のアカウントも自動で対象に含めます。最も適切な構成はどれですか。

- A. Log Archive の S3 に送る組織の証跡を作り、バケットに Object Lock を設定する
- B. 各アカウントの証跡を StackSets で配り、それぞれのアカウントの S3 に保存する
- C. 各アカウントのイベント履歴を、毎日 Lambda で Log Archive へコピーする
- D. CloudWatch Logs のアカウントレベルのサブスクリプションで、中央の Kinesis へ送る

??? success "答えと解説"
    **正解: A**

    組織の証跡は全メンバーアカウントのイベントを記録し、将来のアカウントも含みます。メンバーアカウントは証跡を止められません。保管先を別のアカウントにして Object Lock を使います。

    - A: 正しい。
    - B: 誤り。各アカウントの管理者が証跡やバケットを変更できてしまいます。
    - C: 誤り。イベント履歴は 90 日の管理イベントだけです。処理の漏れもありえます。
    - D: 誤り。API の監査の証跡を作る構成ではありません。CloudTrail の設定が別に必要です。

    **スキル:** [2.3.2](../domain2.md#skill-2-3-2) / **参照:** [証跡とイベント履歴](../../../services/observability.md#cloudtrail-trails)、[Object Lock](../../../services/s3.md#object-lock)

### 問6 {#q6}

ある会社は東京リージョンで GuardDuty の委任管理者を指定し、組織の自動有効化を設定しました。大阪リージョンも使っていますが、そこで検出結果が出ていないことが分かりました。全アカウントの全使用リージョンを対象にしたいと考えています。最も適切な対応はどれですか。

- A. 東京の検出結果のエクスポートの設定に大阪を追加して、データソースを広げる
- B. 使用する各リージョンでも委任管理者を指定し、自動有効化を設定する
- C. 大阪の各メンバーアカウントで GuardDuty を個別に有効にして、スタンドアロンのまま運用する
- D. Security Hub のリージョンの集約を有効にして、GuardDuty が自動で大阪も監視するようにする

??? success "答えと解説"
    **正解: B**

    GuardDuty はリージョンのサービスです。委任管理者の指定と有効化は、そのリージョンにしか効きません。使用するリージョンごとに設定します。

    - A: 誤り。エクスポートは検出結果の送り先の設定で、検出の範囲を広げません。
    - B: 正しい。
    - C: 誤り。組織で一元管理ができなくなり、新しいアカウントも漏れます。
    - D: 誤り。集約は検出結果を集めるだけです。検出そのものは有効になりません。

    **スキル:** [2.3.2](../domain2.md#skill-2-3-2) / **参照:** [GuardDuty の複数アカウント](../../../services/threat-detection.md#guardduty-multi-account)

### 問7 {#q7}

あるセキュリティチームは、CloudTrail、VPC フローログ、WAF ログを全アカウントと複数のリージョンから集めます。データは自社のアカウントの S3 に、標準のスキーマで保存します。既存の SIEM は新しいログの通知を受けて取り込みます。各リージョンのログを 1 か所からまとめて渡したいと考えています。最も適切な構成はどれですか。

- A. Security Hub のホームリージョンへすべてのログを送って、検出結果として SIEM へ渡す
- B. CloudTrail Lake のイベントデータストアへ全ログを取り込み、SIEM から SQL で定期的に問い合わせる
- C. Security Lake のロールアップリージョンで集め、そこでデータアクセスのサブスクライバーを作る
- D. 各リージョンの Security Lake にサブスクライバーを作り、SIEM からそれぞれのリージョンへ接続する

??? success "答えと解説"
    **正解: C**

    Security Lake はログを Parquet と OCSF に変換して自社の S3 に保存します。サブスクライバーは作成したリージョンのデータしか見えないので、ロールアップリージョンで作ります。

    - A: 誤り。Security Hub は検出結果の集約で、生のログの保管ではありません。
    - B: 誤り。CloudTrail Lake は新規顧客の受付を終了しました。
    - C: 正しい。
    - D: 誤り。動作はしますが、1 か所からまとめて渡すという要件を満たしません。

    **スキル:** [2.3.2](../domain2.md#skill-2-3-2) / **参照:** [Security Lake](../../../services/threat-detection.md#security-lake)

### 問8 {#q8}

- A. 組織全体の設定を管理アカウントで 1 回有効にすれば、全メンバーアカウントのログが中央へ届く

- A. 各アカウントの Config の結果を、S3 に出力して Athena で結合するパイプラインを作る

    - C: 誤り。API の呼び出しの集計は準拠状況の確認になりません。

- A. 1 つの VPC のサブネットを RAM で各アカウントへ共有する
- B. 各アカウントに VPC を作り、すべての組み合わせを VPC ピアリングで接続する

### 問13 {#q13}

ある組織は次の 2 つの統制を全メンバーアカウントへ入れます。社内の管理者が CloudTrail を止められないようにすること。S3 のバケットポリシーを誤って公開しても、組織の外の主体から読めないようにすることです。それぞれに合う方法はどれですか。（2つ選択）

    - C: 正しい。
    - D: 誤り。SCP は組織の外の主体には効きません。
    - E: 誤り。事後の修復で、公開している間の読み取りを防げません。

ある組織のルートに、未承認のリージョンの操作を拒否する SCP を関連付けました。後日、未承認のリージョンで動く EC2 が見つかりました。そのインスタンスは管理アカウントのもので、起動したのはその管理者です。同じことを起こさない設計はどれですか。

- A. ワークロードをメンバーアカウントへ移し、管理アカウントの利用を絞る
- B. SCP に管理アカウントの ID を明示して、対象に含める
- C. 管理アカウントに同じ内容の権限境界を付けて、既存の管理者の権限はそのままにする
- D. SCP を OU ではなくルートへ関連付けたのが原因なので、すべての OU へ関連付け直す

??? success "答えと解説"
    **正解: A**

    SCP は管理アカウントのユーザーとロールに効きません。指定の方法で変えることもできません。だからワークロードを管理アカウントに置かず、利用を絞ります。

    - A: 正しい。
    - B: 誤り。ID を書いても、SCP は管理アカウントに効きません。
    - C: 誤り。権限境界は対象のユーザーやロールごとに付けるもので、組織の統制になりません。管理者が外すこともできます。
    - D: 誤り。ルートへの関連付けは組織全体の適用として正しく、管理アカウントの例外とは無関係です。

### 問15 {#q15}

ある組織の構造は「ルート → Sandbox OU → アカウント X」です。ルートとアカウント X には `FullAWSAccess` が関連付けられています。Sandbox OU からは `FullAWSAccess` を外し、`ec2:*` と `s3:*` だけを許可する SCP を関連付けました。X の管理者ロールは `AdministratorAccess` を持っています。このロールが DynamoDB を操作すると、どうなりますか。また、その理由はどれですか。

- A. 成功する。アカウント X に直接関連付けた `FullAWSAccess` が OU の制限より優先される
- B. 成功する。SCP の Allow はあくまで参考で、Deny の文だけが評価される
- C. 拒否される。SCP の許可は階層のすべてのレベルで必要で、Sandbox OU で許可されていない

- A. RCP に取引先のアカウントを許可する Allow の文を追加する
