# 暗号化と鍵管理の問題集

対象の解説: [AWS KMS](../../../services/kms.md)、[証明書と WAF](../../../services/certificates.md)、[CloudHSM](../../../services/identity-directory.md#cloudhsm)

### 問1 {#q1}

ある会社は RDS の本番データベースを AWS 管理キー（`aws/rds`）で暗号化しています。規制への対応で、スナップショットを別アカウントのバックアップ専用アカウントへ共有します。共有しようとするとエラーになります。データベースを止める時間は最小にしたいと考えています。最も適切な手順はどれですか。

- A. `aws/rds` のキーポリシーにバックアップ用アカウントを追加してから、スナップショットを共有する
- B. スナップショットをカスタマー管理キーでコピーし、キーポリシーで相手を許可して共有する
- C. スナップショットを復元して暗号化なしの DB を作り、そのスナップショットを共有してから相手のアカウントで暗号化する
- D. バックアップ用アカウントに同じ別名のカスタマー管理キーを作り、`aws/rds` の代わりに自動で使われるようにスナップショットの属性を変更する

??? success "答えと解説"
    **正解: B**

    AWS 管理キーのポリシーは変更できず、共有できません。スナップショットのコピー時に別のキーで再暗号化できるので、カスタマー管理キーへ切り替えて共有します。

    - A: 誤り。AWS 管理キーのキーポリシーは変更できません。
    - B: 正しい。
    - C: 誤り。暗号化された DB から暗号化なしのものは作れません。規制にも反します。
    - D: 誤り。別名を揃えても別のキーで、スナップショットの暗号化キーは変わりません。

    **スキル:** [2.2.1](../domain2.md#skill-2-2-1) / **参照:** [KMS キーの種類](../../../services/kms.md#key-types)、[アカウントをまたぐ暗号化](../../../services/kms.md#cross-account)

### 問2 {#q2}

ある会社の規定では、暗号鍵の鍵素材を 180 日ごとに更新する必要があります。対象は KMS が生成した鍵素材を持つ、対称のカスタマー管理キーです。多数の AWS サービスがこのキーを使っており、アプリの変更や既存データの再暗号化は避けます。最も適切な方法はどれですか。

- A. 180 日ごとに新しいキーを作り、別名を切り替えて、古いキーを削除する
- B. EventBridge のスケジュールで Lambda を動かして、`RotateKeyOnDemand` を 180 日ごとに呼ぶ
- C. 対象のカスタマー管理キーで自動ローテーションを有効にし、周期を 180 日に設定する
- D. AWS 管理キーへ移行して、AWS のローテーションの周期を 180 日に変更するようサポートへ依頼する

??? success "答えと解説"
    **正解: C**

    自動ローテーションの周期は既定 365 日で、90〜2,560 日で指定できます。キー ID や ARN は変わらず、古い暗号文も復号できます。

    - A: 誤り。古いキーを消すと、そのキーの暗号文を復号できなくなります。
    - B: 誤り。オンデマンドの実行はキーあたり 25 回までで、定期のローテーションには公式も自動を勧めています。
    - C: 正しい。
    - D: 誤り。AWS 管理キーの周期は変更できません。

    **スキル:** [2.2.1](../domain2.md#skill-2-2-1) / **参照:** [キーのローテーション](../../../services/kms.md#key-rotation)、[ローテーションの設定](../../../services/kms.md#rotation-settings)

### 問3 {#q3}

ある決済サービスは、2 つのリージョンでアクティブ/アクティブに動いています。アプリはクライアント側で暗号化してから DynamoDB グローバルテーブルに保存します。あるリージョンで暗号化したデータを、もう一方のリージョンで復号します。リージョン間の KMS 呼び出しはなくし、片方のリージョンの障害時にも復号できるようにします。最も適切な設計はどれですか。

- A. 各リージョンに別々のカスタマー管理キーを作り、データキーを両方で暗号化して、2 つの暗号文を保存する
- B. 一方のリージョンのキーだけを使い、もう一方のリージョンからはエンドポイントを指定して呼び出す
- C. 一方のリージョンのキーの鍵素材をエクスポートして、もう一方のリージョンのキーへインポートする
- D. マルチリージョンのプライマリキーを作り、もう一方のリージョンにレプリカキーを作って各リージョンで復号する

??? success "答えと解説"
    **正解: D**

    マルチリージョンキーは同じ鍵素材とキー ID を持ち、各リージョンで独立して使えます。別のリージョンで暗号化したデータを、リージョン間の呼び出しなしで復号できます。自動ローテーションの設定はプライマリで行います。

    - A: 誤り。実現はできますが、処理と保存が増えます。マルチリージョンキーで解決できる複雑さです。
    - B: 誤り。リージョン間の呼び出しが残り、そのリージョンの障害で復号できません。
    - C: 誤り。KMS が生成した鍵素材はエクスポートできません。
    - D: 正しい。

    **スキル:** [2.2.1](../domain2.md#skill-2-2-1) / **参照:** [マルチリージョンキー](../../../services/kms.md#multi-region-keys)

### 問4 {#q4}

ある銀行の規定では、S3 と EBS の暗号化の鍵素材を社内の HSM で生成する必要があります。また、契約の解除時には、待機期間なしで AWS の中の鍵素材を消せることが求められます。鍵素材を AWS の外で保持し続けますが、AWS サービスとの統合は保ち、外部の鍵管理システムの可用性には依存したくありません。最も適切な方法はどれですか。

- A. `Origin=EXTERNAL` のキーに鍵素材をインポートし、`DeleteImportedKeyMaterial` を使う
- B. CloudHSM キーストアのキーを作り、解除時に `ScheduleKeyDeletion` を最短の 7 日で実行する
- C. 外部キーストアのキーを作り、解除時に外部の鍵管理システムからプロキシを切断する
- D. KMS が生成したキーを使い、解除時に `DisableKey` を実行する

??? success "答えと解説"
    **正解: A**

    鍵素材のインポートなら、自社で生成した鍵素材を使えて、`DeleteImportedKeyMaterial` ですぐに消せます。KMS の中に鍵素材があるので、普段は外部の可用性に依存しません。インポートしたキーは自動ローテーションできない点は承知しておきます。

    - A: 正しい。
    - B: 誤り。CloudHSM キーストアの鍵素材は KMS がクラスターで生成します。キーの削除にも待機期間があります。
    - C: 誤り。外部の鍵管理システムの可用性に依存します。
    - D: 誤り。社内で生成するという要件に合いません。無効化は鍵素材の削除でもありません。

    **スキル:** [2.2.1](../domain2.md#skill-2-2-1) / **参照:** [鍵素材のインポート](../../../services/kms.md#imported-key-material)

### 問5 {#q5}

あるデータレイクでは、数十億のオブジェクトを 1 つのカスタマー管理キーによる SSE-KMS で保存しています。読み取りの増加で KMS の費用が大きくなりました。また `ThrottlingException` も出ています。既存のオブジェクトにも効果を出す必要があります。暗号化の方式やキーは変えられません。最も適切な対応はどれですか。

- A. バケットの設定で S3 バケットキーを有効にするだけで、既存のオブジェクトも次の読み取りから対象になる
- B. バケットキーを有効にし、既存のオブジェクトは S3 バッチ操作などでコピーし直して適用する
- C. アプリの呼び出しをマルチリージョンキーへ切り替えて、リージョン間で要求を分散する
- D. SSE-S3 へ変更し、KMS の呼び出しをなくして、キーの管理を S3 に任せる

??? success "答えと解説"
    **正解: B**

    S3 バケットキーはバケットレベルのキーを使い、KMS の呼び出しを減らします。有効にした後の新しいオブジェクトが対象です。既存のオブジェクトはコピーすると対象になります。

    - A: 誤り。既存のオブジェクトには自動で適用されません。
    - B: 正しい。
    - C: 誤り。同じデータを読む限り、KMS の呼び出しは減りません。
    - D: 誤り。方式を変えられないという条件に反します。

    **スキル:** [2.2.1](../domain2.md#skill-2-2-1) / **参照:** [S3 Bucket Key](../../../services/s3.md#bucket-key)、[S3 バケットキー](../../../services/kms.md#s3-bucket-key-settings)

### 問6 {#q6}

ある EC サイトは、CloudFront を東京リージョンの ALB の前に置いています。独自ドメインの証明書は無料で、人手なしで更新されることが求められます。DNS は Route 53 です。ビューワーから ALB までを暗号化します。最も適切な証明書の構成はどれですか。

- A. 東京リージョンの ACM で 1 つの証明書を発行して、CloudFront と ALB の両方へ関連付ける
- B. `us-east-1` の ACM で 1 つの証明書を発行し、ALB へはクロスリージョンの参照で関連付ける
- C. 外部の CA で 1 枚の証明書を購入して、両方のリージョンの ACM へインポートし、期限を監視する
- D. CloudFront 用に `us-east-1`、ALB 用に東京の ACM で、DNS 検証の証明書を発行する

??? success "答えと解説"
    **正解: D**

    CloudFront の証明書は `us-east-1` に置きます。ALB の証明書は ALB と同じリージョンです。DNS 検証なら CNAME を残すだけで自動で更新されます。

    - A: 誤り。CloudFront は東京の証明書を使えません。
    - B: 誤り。ALB は他のリージョンの証明書を参照できません。
    - C: 誤り。インポートした証明書は自動で更新されず、無料でもありません。
    - D: 正しい。

    **スキル:** [2.2.2](../domain2.md#skill-2-2-2) / **参照:** [リージョンのルール](../../../services/certificates.md#region-rules)、[自動更新](../../../services/certificates.md#auto-renewal)

### 問7 {#q7}

ある工場の機器は、第三者の CA が発行したクライアント証明書を持ち、ALB の背後の HTTP サービスへ接続します。無効な証明書の接続は、ターゲットに届く前に止めます。失効した証明書も拒否します。アプリの改修はできません。最も適切な構成はどれですか。

- A. ALB の mTLS のパススルーモードを有効にして、ターゲット側で証明書を検証する
- B. ALB の mTLS の検証モードで、CA と失効リストをトラストストアへ登録する
- C. ALB の前に AWS WAF を置き、クライアント証明書のシリアル番号の一覧をカスタムルールで照合する
- D. NLB へ置き換え、TCP リスナーで通過させて、ターゲット側のミドルウェアで証明書を確認する

??? success "答えと解説"
    **正解: B**

    ALB の mTLS には 2 つのモードがあります。検証モードは ALB が X.509 の認証を行い、トラストストアの CA と失効リストで判定します。

    - A: 誤り。パススルーモードは ALB が検証せず、チェーンをヘッダーで渡します。ターゲットでの検証にアプリの改修が必要です。
    - B: 正しい。
    - C: 誤り。WAF はクライアント証明書を検証する機能ではありません。
    - D: 誤り。ターゲットでの検証が必要になり、改修できないという条件に反します。

    **スキル:** [2.2.2](../domain2.md#skill-2-2-2) / **参照:** [mTLS](../../../services/certificates.md#mtls)、[転送時の TLS](../../../services/certificates.md#tls-in-transit)

### 問8 {#q8}

あるカード決済のサービスでは、利用者の端末からコンテナのアプリまで、途中で平文にならないことが監査の要件です。ロードバランサーの中でも復号してはいけません。アプリは自分の証明書で TLS を終端でき、TCP の処理も問題ありません。L7 のルーティングは不要です。最も適切な構成はどれですか。

- A. ALB の HTTPS リスナーで終端し、ターゲットグループも HTTPS にして再暗号化する
- B. ALB の前に CloudFront を置いて、オリジンプロトコルポリシーを HTTPS のみに設定する
- C. NLB の TCP リスナーで TLS を復号せずに通過させ、コンテナのアプリが自分の証明書で終端する
- D. NLB の TLS リスナーで ACM の証明書を使って終端し、ターゲットへ TLS で接続する

??? success "答えと解説"

    - B: 誤り。CloudFront でも ALB でも復号されます。
    - C: 正しい。
    - D: 誤り。NLB の TLS リスナーはロードバランサーで終端します。

### 問9 {#q9}

ある会社は契約の都合で、外部の CA が発行した証明書を ACM にインポートして ALB で使っています。昨年、この証明書の期限切れで障害が起きました。外部の CA は変更できません。全アカウントで再発を防ぎ、同じ ALB の設定を保ったまま証明書を差し替えます。最も適切な方法はどれですか。

- A. インポートした証明書の自動更新を ACM の設定で有効にする
- B. 証明書をメール検証へ切り替えて、更新の通知を担当者へ送るよう登録する
- C. 期限の近いことを知らせる ACM のイベントを EventBridge で受け、同じ ARN へ再インポートする
- D. 証明書を ACM から削除して、ターゲットのアプリで外部の CA の証明書を読み込むようにする

    - A: 誤り。インポートした証明書にそのような設定はありません。
    - B: 誤り。検証方法は ACM が発行する証明書の話です。

### 問10 {#q10}

ある医療機関は、記録を 30 年間秘匿する必要があります。データは S3 の SSE-KMS（AES-256-GCM）で保存し、オンプレミスから AWS の API へ TLS で送っています。経営層から量子計算機への備えを求められました。予算は限られています。最初に取り組むべき対策はどれですか。

- A. 全オブジェクトを別の方式で再暗号化できるよう、S3 のデータを RSA の KMS キーで暗号化し直す
- B. 全通信の TLS を、RSA の鍵長を 4096 ビットに上げた証明書へ交換する
- C. 通信の鍵交換に ML-KEM を含むハイブリッドの耐量子 TLS を使う
- D. KMS のキーのローテーションの周期を最短の 90 日へ短縮して、暗号文の寿命を減らす

??? success "答えと解説"
    **正解: C**

    今の通信を保存して将来解読される攻撃があるので、長期の秘匿が必要なデータの鍵交換を優先します。AES-256-GCM は公式が耐量子と位置づけており、変更は不要です。

    - A: 誤り。AES-256 の保存データは優先度が低いです。RSA はむしろ量子計算機の影響を受ける方式です。
    - B: 誤り。RSA の鍵長を上げても、量子計算機に対する根本的な対策になりません。
    - C: 正しい。
    - D: 誤り。ローテーションは既存の暗号文を再暗号化しません。量子計算機への対策になりません。

    **スキル:** [2.2.4](../domain2.md#skill-2-2-4) / **参照:** [キーの仕様](../../../services/kms.md#key-specs)、[転送時の TLS](../../../services/certificates.md#tls-in-transit)

### 問14 {#q14}

ある機器メーカーは、15 年間使われる機器のファームウェアに署名します。機器は出荷後も公開鍵で署名を検証します。量子計算機が現れても署名が偽造されないようにします。秘密鍵は AWS の外へ出しません。最も適切な KMS キーはどれですか。

- A. `ML_DSA_65` のキーで、`ML_DSA_SHAKE_256` の署名を使う
- B. `HMAC_512` のキーで、`GenerateMac` の結果を署名として配布する
- C. `ML_KEM_768` のキーで、カプセル化した共有秘密を署名の代わりに使う
- D. `ECC_NIST_P521` のキーで、`ECDSA_SHA_512` の署名を使う

??? success "答えと解説"
    **正解: A**

    長期間検証する署名は ML-DSA へ移します。KMS は `ML_DSA_44`、`ML_DSA_65`、`ML_DSA_87` に対応し、署名アルゴリズムは `ML_DSA_SHAKE_256` です。

    - A: 正しい。
    - B: 誤り。HMAC の検証には同じ鍵が必要で、機器が公開鍵で検証できません。
    - C: 誤り。ML-KEM は鍵の確立の方式で、署名には使えません。
    - D: 誤り。楕円曲線の署名は量子計算機の影響を受けます。

    **スキル:** [2.2.4](../domain2.md#skill-2-2-4) / **参照:** [キーの仕様](../../../services/kms.md#key-specs)、[対称と非対称の違い](../../../services/kms.md#symmetric-vs-asymmetric)

### 問15 {#q15}

ある組織は耐量子への移行を進めています。ある OU では、新しく作る非対称の署名キーを ML-DSA に限定します。対称キーの作成は引き続き許可します。すでにある RSA の署名キーは使い続けます。設定の手間が少なく、作成前に止める方法はどれですか。

- A. 既存の RSA キーの仕様を `UpdateKeyDescription` で ML-DSA へ変更し、Config のルールで準拠を確認する
- B. OU の SCP で `kms:CreateKey` を、`kms:KeySpec` の条件で許可の仕様以外を拒否する
- C. キーの自動ローテーションを有効にして、次の更新のときに新しい仕様へ切り替わるようにする
- D. Config のルールで RSA の新しいキーを検出し、Automation の Runbook でキーの削除を予約する

??? success "答えと解説"
    **正解: B**

    `kms:KeySpec` の条件キーで、作成できる仕様を制限できます。OU 全体の予防には SCP を使います。条件には対称キーの `SYMMETRIC_DEFAULT` も許可に含めます。

    - A: 誤り。キー仕様は作成後に変更できません。
    - B: 正しい。
    - C: 誤り。非対称キーは自動ローテーションに対応しません。仕様も変わりません。
    - D: 誤り。作成後の検出で、作成前に止められません。

    **スキル:** [2.2.4](../domain2.md#skill-2-2-4) / **参照:** [主な条件キー](../../../services/kms.md#kms-condition-keys)、[SCP](../../../services/governance.md#scp)

### 問16 {#q16}

ある会社は公開 API を ALB で提供しています。新しいクライアントには ML-KEM を含むハイブリッドの耐量子の鍵交換を使わせます。ただし、TLS 1.2 しか話せない古いクライアントも当面は接続できる必要があります。最も適切な HTTPS リスナーの設定はどれですか。

- A. 既存の TLS 1.2 のポリシーのままにして、ターゲットとの間だけ耐量子の方式にする
- B. `ELBSecurityPolicy-TLS13-1-3-PQ-2025-09` を設定する
- C. `ELBSecurityPolicy-TLS13-1-2-Res-PQ-2025-09` を設定する
- D. HTTPS リスナーを TCP リスナーへ変更して、新しいクライアントの方式をターゲット側のソフトウェアに任せる

??? success "答えと解説"
    **正解: C**

    名前に PQ を含むポリシーは、従来の鍵交換と ML-KEM の両方に対応します。`TLS13-1-2` は TLS 1.2 も受け入れるので、古いクライアントが接続できます。`TLS13-1-3` は TLS 1.3 だけです。

    - A: 誤り。クライアントとの区間の鍵交換が耐量子になりません。
    - B: 誤り。TLS 1.3 だけなので、古いクライアントが接続できません。
    - C: 正しい。
    - D: 誤り。ALB の機能を失います。ポリシーの変更で足りる要件に対して過剰です。

    **スキル:** [2.2.4](../domain2.md#skill-2-2-4) / **参照:** [転送時の TLS](../../../services/certificates.md#tls-in-transit)
