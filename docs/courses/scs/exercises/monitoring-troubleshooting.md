# 監視とログのトラブルシューティングの問題集

対象の解説: [どのログを見るか](../../../services/threat-detection.md#log-sources)、[CloudWatch エージェント](../../../services/operations.md#cloudwatch-agent)、[Lambda のログ設定](../../../services/lambda.md#logging-config)、[API Gateway のログ](../../../services/api-gateway.md#logging-metrics)

### 問1 {#q1}

新しい Lambda 関数を作成し、最小権限のカスタムの実行ロールを付けました。関数は正常に動いていますが、CloudWatch Logs にロググループが作られません。関数のコードは標準出力に書き込んでいます。

最も可能性の高い原因と対策はどれですか。

- A. 関数の URL が無効なので、ログの配信が始まっていない。URL を有効にする
- B. 実行ロールにログを書く権限がない。`logs:CreateLogGroup`、`logs:CreateLogStream`、`logs:PutLogEvents` を付ける
- C. 呼び出し元の IAM ユーザーに権限がない。呼び出し元のユーザーに `AWSLambdaBasicExecutionRole` とログの読み取りの権限を付ける
- D. Lambda のログには別途 CloudWatch エージェントのインストールが必要である

??? success "答えと解説"
    **正解: B**

    ログを書くのは関数の実行ロールです。必要な権限は `AWSLambdaBasicExecutionRole` に含まれています。カスタムのロールでは付け忘れやすい点です。

    - A: 誤り。関数の URL はログと関係ありません。
    - B: 正しい。
    - C: 誤り。呼び出し元の権限は関係ありません。
    - D: 誤り。Lambda にエージェントは不要です。

    **スキル:** [1.3.1](../domain1.md#skill-1-3-1) / **参照:** [Lambda の実行ロール](../../../services/lambda.md#execution-role)

### 問2 {#q2}

Lambda の本番関数で、費用を抑えるためアプリケーションのログレベルを `WARN` にしました。しかし `INFO` のログが変わらず CloudWatch Logs に出続けています。コードは組み込みのロガーを使っています。

何を確認して直しますか。

- A. 同時実行数の予約がないと設定が反映されないので、予約を追加する
- B. ロググループのクラスが Standard なので、Essentials に変更する
- C. ログの形式が既定の `Text` のままである。`JSON` に変更する
- D. ログレベルの変更は新しいバージョンの発行後、24 時間経たないと反映されない

??? success "答えと解説"
    **正解: C**

    ログレベルのフィルターを使うには、関数を JSON のログ形式にする必要があります。マネージドランタイムの既定は plain text です。

    - A: 誤り。同時実行とログの設定は関係ありません。
    - B: 誤り。ログクラスとログレベルは別の設定で、作成後のクラスの変更もできません。
    - C: 正しい。
    - D: 誤り。そのような待ち時間はありません。

    **スキル:** [1.3.1](../domain1.md#skill-1-3-1) / **参照:** [Lambda のログ設定](../../../services/lambda.md#logging-config)

### 問3 {#q3}

東京リージョンの REST API は実行ログが CloudWatch Logs に出ています。同じ手順で大阪リージョンに API を作り、ステージの `loggingLevel` を `INFO` にしましたが、ログが出ません。呼び出し元の権限には問題がありません。

最も可能性の高い原因はどれですか。

- A. 実行ログは東京リージョンにしか保存できない
- B. API キーを必須にしていないので、実行ログが記録されない
- C. 呼び出し元の IAM ユーザーに `logs:PutLogEvents` が付いていないので、大阪の API を呼ぶときだけログを書き込めない
- D. 大阪のアカウント設定で `cloudWatchRoleArn` を設定していない。この設定はリージョンごとに必要である

??? success "答えと解説"
    **正解: D**

    API Gateway がログを書くためのロールは、アカウント設定の `cloudWatchRoleArn` で指定し、リージョンごとに別に設定します。ロールは `apigateway.amazonaws.com` を信頼します。

    - A: 誤り。リージョンの制限はありません。
    - B: 誤り。API キーの有無はログの有効化に関係しません。
    - C: 誤り。ログを書くのは呼び出し元ではなく API Gateway です。
    - D: 正しい。

    **スキル:** [1.3.1](../domain1.md#skill-1-3-1) / **参照:** [API Gateway のログ](../../../services/api-gateway.md#logging-metrics)

CloudFront に関連付けたウェブ ACL のログを、東京リージョンの Firehose `waf-stream` に送ろうとしました。コンソールの送信先の一覧に、このストリームが表示されません。

### 問6 {#q6}

CloudFront の標準ログを不正の検知に使っていますが、一部のリクエストの記録が遅れて届き、ときには見つからないことがあります。担当者は数秒以内にリクエストの情報を受け取り、不審なパターンに対応したいと考えています。

最も適切なものはどれですか。

- A. 標準ログの出力先のバケットを利用者の近くのリージョンに移して、ログの配信の遅れとリクエストの記録の抜けを根本からなくす
- B. リアルタイムアクセスログを Kinesis Data Streams へ送り、サンプリング率を要件に合わせて設定する
- C. CloudTrail のデータイベントで CloudFront のリクエストを記録する
- D. 標準ログのプレフィックスを細かく分けて配信の遅延をなくす

    - A: 誤り。バケットの場所は配信の方式を変えません。
    - B: 正しい。
    - C: 誤り。CloudTrail は API の記録で、ビューワーのリクエストは記録しません。
    - D: 誤り。プレフィックスで配信の性質は変わりません。

    **スキル:** [1.3.1](../domain1.md#skill-1-3-1) / **参照:** [CloudFront のログ](../../../services/networking.md#cloudfront-logs)

### 問14 {#q14}

### 問15 {#q15}

あるインスタンスへの ping が失敗します。VPC フローログには、受信の `ACCEPT` の記録と、応答の送信の `REJECT` の記録があります。担当者はセキュリティグループのアウトバウンドルールが原因だと考えています。

最も適切な判断はどれですか。

- A. セキュリティグループのアウトバウンドに ICMP を追加する
- B. フローログの記録は遅れて届くので、最新の結果を見るために 10 分待ってから同じ操作をもう一度試して結果を比較する
- C. Amazon DNS が応答をブロックしているので、DNS の設定を変更する
- D. セキュリティグループはステートフルなので応答は許可される。ネットワーク ACL のアウトバウンドルールを確認する

??? success "答えと解説"
    **正解: D**

    セキュリティグループはステートフルで、許可された通信の応答はアウトバウンドのルールに関係なく通ります。戻りだけの `REJECT` はステートレスのネットワーク ACL を疑います。

    - A: 誤り。応答はセキュリティグループで止まりません。
    - B: 誤り。記録はすでに届いていて、遅延の問題ではありません。
    - C: 誤り。ping と DNS は関係ありません。
    - D: 正しい。
