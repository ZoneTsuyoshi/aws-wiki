# 認証の問題集

対象の解説: [IAM Identity Center](../../../services/identity-directory.md#identity-center)、[Cognito](../../../services/cognito.md)、[STS の API の比較](../../../services/iam.md#sts-api-compare)

### 問1 {#q1}

ある会社は 40 のアカウントを持ち、社員 3,000 人は社外の IdP で認証しています。各アカウントの IAM ユーザーを廃止し、社員には IdP のサインインだけで必要なアカウントに入らせます。入社と退社は IdP の変更だけで反映したいと考えています。最も運用負荷の小さい構成はどれですか。

- A. 各アカウントに IAM の SAML プロバイダーを作り、ロールの信頼ポリシーを IdP ごとに管理して、ユーザーの割り当ては IdP 側の属性で個別に指定する
- B. IAM Identity Center の ID ソースを外部 IdP にして SCIM で同期し、権限セットをグループとアカウントに割り当てる
- C. Cognito のユーザープールに IdP をフェデレーションし、ID プールのロールマッピングで各アカウントのロールを選ぶ
- D. 管理アカウントに全員分の IAM ユーザーを作り、各アカウントのロールを引き受けさせて、MFA は必須にする

??? success "答えと解説"
    **正解: B**

    従業員の複数アカウントへのアクセスは Identity Center が第一の選択肢です。SCIM で入退社が同期され、権限セットからロールが自動で作られます。

    - A: 誤り。動きますが、アカウントごとのプロバイダーとロールの管理が残り、運用負荷が大きくなります。
    - B: 正しい。
    - C: 誤り。Cognito は Web やモバイルの一般利用者向けです。従業員のアカウントアクセスには使いません。
    - D: 誤り。長期の認証情報が残り、入退社も IdP と連動しません。

    **スキル:** [4.1.1](../domain4.md#skill-4-1-1) / **参照:** [ID ソース](../../../services/identity-directory.md#idc-identity-sources)

モバイルアプリの利用者が、サインイン後に自分専用の S3 プレフィックスへ直接ファイルをアップロードします。利用者は Google アカウントでサインインし、アプリのバックエンドは経由しません。アプリに長期の認証情報を入れないことが条件です。適切な組み合わせはどれですか。

- A. ユーザープールだけを使い、受け取った ID トークンを S3 の PutObject の `Authorization` ヘッダーに設定する
- B. IAM Identity Center に Google を接続し、権限セットの一時認証情報をアプリから取得する
- C. アプリに専用の IAM ユーザーのアクセスキーを暗号化して組み込み、S3 のプレフィックスは利用者ごとにポリシーで分ける
- D. ID プールで一時的な AWS 認証情報を取得し、ロールのポリシーで `${cognito-identity.amazonaws.com:sub}` のプレフィックスに限定する

??? success "答えと解説"
    **正解: D**

### 問3 {#q3}

会社は AWS Managed Microsoft AD を 1 つのアカウントで運用しています。次に社内の別チームが、AWS 上で IAM Identity Center の ID ソースを Active Directory に変更する提案を出しました。現在の ID ソースは Identity Center ディレクトリで、ユーザーとグループ、権限セットの割り当てがあります。変更の前に認識すべきことはどれですか。

- A. 変更すると既存のユーザー、グループ、割り当てが完全に削除されるので、構成を控えて割り当てを後で設定し直す必要がある
- B. 既存のユーザーとグループは AD の同名のオブジェクトへ自動で移行されるが、権限セットだけは設定し直す必要がある
- C. Simple AD にも同じ手順で変更でき、そちらなら既存の割り当てを保持したまま切り替えられる

### 問5 {#q5}

GitHub Actions から AWS へデプロイしています。現在は IAM ユーザーのアクセスキーをリポジトリのシークレットに保存しています。監査で長期の認証情報の削除を求められました。別のリポジトリから同じロールを使えないようにすることも条件です。正しい手順の組み合わせはどれですか。（2つ選択）

- A. キーのローテーションを 30 日ごとに自動化し、シークレットの値を API で更新する
- B. GitHub の OIDC の ID プロバイダーを IAM に登録し、ロールで `AssumeRoleWithWebIdentity` を使う
- C. 信頼ポリシーの条件で、トークンの `sub` を対象のリポジトリとブランチに絞る
- D. 信頼ポリシーでは `aud` だけを確認し、リポジトリの制限はワークフローのコードで行う
- E. GitHub の Runner の IP アドレス範囲を `aws:SourceIp` で許可する

    - B: 正しい。
    - C: 正しい。
    - D: 誤り。`aud` はリポジトリを区別しません。ワークフローのコードは統制になりません。
    - E: 誤り。リポジトリを区別できません。IP の範囲も共有されています。

    **スキル:** [4.1.1](../domain4.md#skill-4-1-1), [4.1.2](../domain4.md#skill-4-1-2) / **参照:** [信頼ポリシー](../../../services/iam.md#trust-policy)、[フェデレーション](../../../services/iam.md#federation)

### 問6 {#q6}

バッチが IAM ユーザーの認証情報で STS を呼びます。ロール A の `MaxSessionDuration` は 8 時間です。ジョブは A を引き受けたセッションからさらにロール B（同じく 8 時間）を引き受け、`DurationSeconds=14400` を指定しました。結果として正しいものはどれですか。

- A. B のセッションは 4 時間で発行される。ロールチェーンでも各ロールの設定が適用される
- B. B のセッションは A の残り時間に合わせて自動で短縮され、エラーにはならない
- C. B の `MaxSessionDuration` を 12 時間まで増やせば、この呼び出しは成功する
- D. ロールチェーンのセッションは最大 1 時間なので、1 時間を超える指定は失敗する

??? success "答えと解説"
    **正解: D**

    ロールチェーンのセッションは、ロールの最大セッション時間に関係なく最大 1 時間です。1 時間を超える `DurationSeconds` を指定すると失敗します。

    - A: 誤り。ロールチェーンには 1 時間の上限があります。
    - B: 誤り。自動で短縮されるのではなく、指定が上限を超えると失敗します。
    - C: 誤り。ロールの設定を変えてもチェーンの上限は変わりません。
    - D: 正しい。

    **スキル:** [4.1.2](../domain4.md#skill-4-1-2) / **参照:** [最大セッション時間](../../../services/iam.md#max-session-duration)

### 問13 {#q13}

ある朝、運用チームが Identity Center の権限セットで KMS キーを使えなくなりました。前日に別の担当者が、割り当ての整理のためにこの権限セットを外して再度割り当てていました。キーポリシーは、以前のロールの ARN を完全一致で指定しています。原因と恒久的な対策はどれですか。

- A. AD Connector は VPN 経由の AD に接続できないので、Direct Connect に切り替える
- B. SRV レコードの解決に必要な DNS と、TCP/UDP 53、88、389 の許可が足りないので追加する
- C. AD Connector は証明書認証だけを使うので、LDAPS 用に 636 だけを開ける
- D. AD Connector は AWS Managed Microsoft AD の前提が必要なので、先にそれを作成して信頼関係を結ぶ

??? success "答えと解説"
    **正解: B**

    AD Connector は `_ldap._tcp` と `_kerberos._tcp` の SRV レコードを DNS で引きます。必要なポートは TCP/UDP 53、88、389 です。

    - A: 誤り。VPN でも Direct Connect でも接続できます。
    - B: 正しい。
    - C: 誤り。証明書認証だけを使うわけではありません。
    - D: 誤り。AD Connector は既存の AD へのプロキシで、Managed AD は前提ではありません。

    **スキル:** [4.1.3](../domain4.md#skill-4-1-3) / **参照:** [AD Connector](../../../services/identity-directory.md#ad-connector)

### 問15 {#q15}

Cognito ID プールで、ID トークンの `cognito:roles` に複数のロールがあるユーザーが一時認証情報を取得できません。グループの `Precedence` はすべて同じ値です。ロールマッピングは「トークンから選択」、ロールの解決の設定は「拒否」です。`CustomRoleArn` は指定していません。最も適切な修正はどれですか。

- A. グループの `Precedence` に差を付けて、`cognito:preferred_role` が設定されるようにする
- B. ユーザープールの MFA を `Required` にして、トークンにロールの情報が追加されるようにする
- C. ID プールを基本フローに切り替えると、複数のロールの中から最初のものが自動で選ばれる
- D. ユーザーをすべてのグループから外し、ID プールの認証されたロールを管理者ロールに変更する

??? success "答えと解説"
    **正解: A**

    同じ優先度のロールが複数あると `cognito:preferred_role` が設定されず、ロールの解決の設定に従います。ここでは「拒否」なので失敗します。

    - A: 正しい。
    - B: 誤り。MFA はトークンのロールの情報に影響しません。
    - C: 誤り。基本フローでも自動で選ばれません。指定は呼び出し側の責任になり、問題は解決しません。
    - D: 誤り。権限が広がります。

    **スキル:** [4.1.3](../domain4.md#skill-4-1-3) / **参照:** [ロールマッピング](../../../services/cognito.md#role-mapping)
