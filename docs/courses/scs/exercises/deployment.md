# 一貫した展開の問題集

対象の解説: [StackSets の設定](../../../services/iac.md#stacksets-settings)、[タグ戦略](../../../services/governance.md#tagging-strategy)、[Firewall Manager](../../../services/threat-detection.md#firewall-manager)、[Service Catalog](../../../services/governance.md#service-catalog)

### 問1 {#q1}

標準のロールと Config ルールを全アカウントへ CloudFormation で配ります。アカウントは OU に分かれ、毎月増えます。新しいアカウントにも人手なしで展開します。適切な StackSets の設定はどれですか。

- A. セルフマネージドの権限で、各アカウントの実行ロールを手で作り、毎月アカウント ID を追加する
- B. サービスマネージドの権限で OU を対象にし、アカウントの追加時の自動デプロイを有効にする
- C. 各アカウントでスタックを個別に作成し、更新は CodePipeline のステージで順に実行する
- D. Control Tower のドリフト解消の機能で、新しいアカウントへスタックを複製する

??? success "答えと解説"
    **正解: B**

    サービスマネージドなら実行のロールが自動で作られ、OU を対象にできます。自動デプロイで新しいアカウントにも展開されます。

    - A: 誤り。アカウントの増加のたびに人手が必要です。
    - B: 正しい。
    - C: 誤り。管理の負担が増えます。
    - D: 誤り。ドリフトの解消はスタックの展開の機能ではありません。

    **スキル:** [6.2.1](../domain6.md#skill-6-2-1) / **参照:** [StackSets の設定](../../../services/iac.md#stacksets-settings)

### 問2 {#q2}

KMS で既定の暗号化をしていない S3 バケットの作成を止めます。CI のチェックに加え、パイプラインを通らずに `aws cloudformation deploy` された場合も止めます。Guard のルールは既にあります。最適な組み合わせはどれですか。

- A. CI で cfn-lint を実行し、そのテンプレートをすべて S3 に保管する
- B. CI で Guard を実行し、Guard はサーバー側で強制するので追加は不要にする
- C. CI の Guard に加え、同じルールの Hook でサーバー側で強制する
- D. CI で変更セットを作り、人が確認して、それ以外の経路は Config で検出する

??? success "答えと解説"
    **正解: C**

    Guard はサーバー側の強制を提供しません。Hook はプロビジョニングの前にブロックや警告を行い、Guard のルールで定義できます。

    - A: 誤り。cfn-lint はテンプレートの正しさを見るもので、保管も統制になりません。
    - B: 誤り。Guard 自体はサーバー側で強制しません。
    - C: 正しい。
    - D: 誤り。人の確認に頼り、直接のデプロイを止められません。

    **スキル:** [6.2.1](../domain6.md#skill-6-2-1) / **参照:** [検証方法のまとめ](../../../services/iac.md#validate-iac)

### 問3 {#q3}

Terraform も使うチームが、CloudFormation と同じ組織の基準でプランを検証したいと考えています。Terraform のプランを JSON に出力できます。また Kubernetes の設定ファイルにも同じ仕組みを使いたいと考えています。適切なものはどれですか。

- A. CloudFormation Hooks を Terraform のプランに直接適用する
- B. cfn-lint の Terraform 用のプラグインで Kubernetes の設定も検証する
- C. Config のプロアクティブ評価で Kubernetes の設定を評価する
- D. CloudFormation Guard で JSON と YAML のデータを検証する

??? success "答えと解説"
    **正解: D**

    Guard は汎用の policy-as-code ツールで、JSON や YAML の構造化データを検証できます。Terraform の JSON のプランや Kubernetes の設定にも使えます。

    - A: 誤り。Hooks は CloudFormation と Cloud Control API の操作に効きます。
    - B: 誤り。cfn-lint は CloudFormation のテンプレート向けです。
    - C: 誤り。Config のプロアクティブ評価は AWS リソースの設定の評価です。
    - D: 正しい。

    **スキル:** [6.2.1](../domain6.md#skill-6-2-1) / **参照:** [検証方法のまとめ](../../../services/iac.md#validate-iac)

### 問4 {#q4}

本番のスタックで、IAM ロールの置き換えが起きないかを、デプロイの前に確認したいと考えています。別の担当者は、誰かが手で変更したセキュリティグループの差異も知りたいと考えています。それぞれの手段の組み合わせはどれですか。

- A. 変更セットで何が変わるかを確認し、ドリフト検出で手動の変更との差異を確認する
- B. Hook で変更内容を確認し、StackSets で手動の変更との差異を確認する
- C. cfn-lint で変更内容を確認し、Guard で手動の変更との差異を確認する
- D. ドリフト検出で置き換えの有無を確認し、変更セットで手動の変更との差異を確認する

??? success "答えと解説"
    **正解: A**

    変更セットは適用の前に何が変わるかを示します。ドリフト検出はテンプレートと実際の構成の差異を示します。

    - B: 誤り。Hook は検証、StackSets は展開です。

    - D: 誤り。役割が逆です。

### 問5 {#q5}

費用の配賦のため、全アカウントのタグの `CostCenter` の値を統一します。`costcenter` や `Cost-Center` が混在しています。ある担当者はタグポリシーを有効にすれば、タグなしのリソースの作成も止まると考えています。正しい説明と対応はどれですか。

- A. タグポリシーを有効にすれば、タグなしの作成も止まるので、追加の統制は不要である
- B. タグポリシーはタグを自動で正しく書き換えるので、既存のリソースも一括で修正され、タグなしの作成も同時に止まる
- C. 表記はタグポリシーで統一し、作成時の強制は SCP の `aws:RequestTag` を使う

??? success "答えと解説"
    **正解: C**

    - B: 誤り。自動で書き換えません。

### 問6 {#q6}

チームの要望が 3 つあります。作成済みのリソースのタグの漏れを見つける、タグを費用のレポートに反映する、タグでリソースをまとめて検索する、の 3 つです。組み合わせとして正しいものはどれですか。

- A. Config の `required-tags`、Tag Editor の関連付け、Service Catalog のポートフォリオの順に使う
- B. Config の `required-tags`、コスト配分タグの有効化、Resource Groups と Tag Editor の順に使う
- C. Firewall Manager の監査、Cost Explorer の自動集計、CloudTrail Lake の順に使う
- D. SCP の `aws:RequestTag`、請求コンソールでの自動反映、GuardDuty の順に使う

??? success "答えと解説"
    **正解: B**

    `required-tags` は作成済みのリソースを評価します。費用に反映するにはコスト配分タグの有効化が必要で、まとめての操作には Resource Groups と Tag Editor が使えます。

    - A: 誤り。Tag Editor は費用のレポートに反映する機能ではなく、Service Catalog は検索用ではありません。
    - B: 正しい。
    - C: 誤り。Firewall Manager はタグの監査の機能ではありません。
    - D: 誤り。SCP は作成時に止めるもので、既存のタグの漏れを見つけません。

    **スキル:** [6.2.2](../domain6.md#skill-6-2-2) / **参照:** [Resource Groups](../../../services/governance.md#resource-groups)、[コスト配分タグ](../../../services/cost-management.md#cost-allocation-tags)

あるチームが、リソースの `Customer` タグに取引先の担当者のメールアドレスを入れて運用しています。監査がこの運用に懸念を示しました。正しい判断はどれですか。
