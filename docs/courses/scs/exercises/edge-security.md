# エッジのセキュリティの問題集

対象の解説: [WAF](../../../services/certificates.md#waf)、[Shield](../../../services/threat-detection.md#shield)、[CloudFront](../../../services/networking.md#cloudfront)

すべてオリジナルの問題で、実際の試験問題ではありません。基準は SCS-C03 です。

### 問1 {#q1}

ある会社は、インターネット向け ALB で EC サイトを公開しています。最近、HTTP フラッドと SQL インジェクションの試行が増えました。予算は限られ、24 時間の専門チームの支援や攻撃時の費用の補償は要件にありません。ネットワーク層の DDoS にも備える必要があります。最も適切な構成はどれですか。

- A. Shield Advanced を契約して ALB を保護対象に指定し、SRT に WAF ルールの作成を依頼する
- B. CloudFront を前に置いて Shield Standard の効果を高め、ウェブ ACL でレート制限と SQL インジェクションのルールを使う
- C. VPC に Network Firewall を置き、Suricata のルールで HTTP フラッドと SQL インジェクションを検査して、ALB の前で遮断する
- D. ALB のサブネットのネットワーク ACL に、攻撃元の IP アドレスを見つけるたびに拒否のエントリーを追加する運用にする

??? success "答えと解説"
    **正解: B**

    ネットワーク層は Shield Standard が自動で守り、CloudFront の前置きで効果が高まります。L7 の攻撃は WAF で扱います。費用の補償と SRT が要件にないので Shield Advanced は過剰です。

    - A: 誤り。要件にない SRT とコスト保護のために年単位の契約をすることになる。
    - B: 正しい。
    - C: 誤り。Network Firewall は VPC の境界の検査で、L7 の HTTP フラッド対策としては WAF のレート制限のほうが適する。
    - D: 誤り。NACL は IP を変える攻撃に追従できず、エントリー数にも限りがあり、SQL インジェクションは検査できない。

    **スキル:** [3.1.1](../domain3.md#skill-3-1-1) / **参照:** [Shield](../../../services/threat-detection.md#shield)、[アプリケーション層の防御](../../../services/threat-detection.md#shield-l7)

### 問2 {#q2}

金融機関の公開サイトは CloudFront と Route 53 で配信しています。経営層は次を求めています。大規模な DDoS の最中に AWS の専門チームが対応を支援すること、攻撃によるスケールアウトで増えた費用について補償を受ける機会があること。サポートプランは Enterprise です。追加で必要なものはどれですか。

- A. WAF の Anti-DDoS マネージドルールグループをウェブ ACL に追加する
- B. Shield Standard の詳細設定で、CloudFront と Route 53 を保護対象に登録する
- C. Shield Advanced を契約し、CloudFront とホストゾーンを保護対象に指定する
- D. Firewall Manager の Shield Advanced ポリシーを管理者アカウントなしで展開する

??? success "答えと解説"
    **正解: C**

    SRT の支援とコスト保護は Shield Advanced の機能です。SRT には Business か Enterprise のサポートプランが必要で、保護は指定したリソースにだけ効きます。

    - A: 誤り。L7 の緩和には役立つが、SRT の支援も費用の補償も得られない。
    - B: 誤り。Shield Standard は自動で適用され、保護対象の登録はなく、SRT とコスト保護もない。
    - C: 正しい。
    - D: 誤り。Firewall Manager には管理者アカウントの指定が必要で、Shield Advanced の契約も別に要る。

    **スキル:** [3.1.1](../domain3.md#skill-3-1-1) / **参照:** [Shield Advanced](../../../services/threat-detection.md#shield-advanced)、[Shield Response Team](../../../services/threat-detection.md#shield-srt)

### 問3 {#q3}

会員制サイトのログイン画面に、他社から漏えいしたユーザー名とパスワードの組を次々に試す攻撃が来ています。送信元 IP は分散し、1 つの IP からの試行は少数です。正しいログインとの見分けが要件で、レート制限だけでは止まりません。サイトは CloudFront で配信し、すでにウェブ ACL を使っています。最も直接的な対策はどれですか。

- A. `AWSManagedRulesCommonRuleSet` を追加し、ログインのパスに対してブロックで動かす
- B. ログインのパスに `AWSManagedRulesSQLiRuleSet` を適用して、不正な入力値を止める
- C. CloudFront の地理的制限で、攻撃の多い国からの配信をすべて拒否する
- D. `AWSManagedRulesATPRuleSet` で盗まれた認証情報を検査する

??? success "答えと解説"
    **正解: D**

    Account Takeover Prevention は、盗まれた認証情報のデータベースとの照合やログインの異常を検査します。

    - A: 誤り。OWASP に関連する一般的な攻撃のルールで、認証情報の照合はしない。
    - B: 誤り。正しい形式のログイン試行は SQL インジェクションに一致しない。
    - C: 誤り。分散した攻撃を国で止めきれず、正規の利用者まで止める。
    - D: 正しい。

    **スキル:** [3.1.1](../domain3.md#skill-3-1-1) / **参照:** [WAF と似た機能の比較](../../../services/certificates.md#waf-comparison)、[アプリケーション層の防御](../../../services/threat-detection.md#shield-l7)

### 問4 {#q4}

あるアプリは CloudFront の背後のインターネット向け ALB で動いています。監査で、ALB の DNS 名に直接アクセスすると WAF を迂回できると指摘されました。チームは、ALB にパブリック IP を持たせず、共有の秘密の値を管理せず、運用の手間を減らしたいと考えています。最も適切なものはどれですか。

- A. ALB を内部向けにしてプライベートサブネットに移し、CloudFront の VPC オリジンで接続する
- B. CloudFront にカスタムヘッダーを追加し、ALB のリスナールールで値を検査して、定期的に値を更新する
- C. ALB に OAC を設定して、CloudFront の署名付きリクエストだけを受け付ける
- D. ALB のセキュリティグループに CloudFront のマネージドプレフィックスリストを設定し、ALB は公開したままにする

??? success "答えと解説"
    **正解: A**

    VPC オリジンを使うと、ALB をプライベートサブネットに置いたまま CloudFront を唯一の入り口にできます。

    - A: 正しい。
    - B: 誤り。秘密の値の管理が残り、ALB も公開のまま。
    - C: 誤り。OAC は S3 などのオリジン向けで、この構成の ALB を守る手段としては使えない。
    - D: 誤り。ALB にパブリック IP が残る。

    **スキル:** [3.1.1](../domain3.md#skill-3-1-1) / **参照:** [OAC](../../../services/networking.md#oac)、[CloudFront](../../../services/networking.md#cloudfront)

### 問5 {#q5}

監査で、CloudFront から配信する複数のアプリの応答に `Strict-Transport-Security` と `X-Frame-Options` がないと指摘されました。オリジンの開発チームは別会社で、コードをすぐには変更できません。追加の処理の実行基盤も増やしたくありません。一部のオリジンがすでに同じヘッダーを返す場合は、CloudFront の値を優先させます。どう設定しますか。

- A. ビューワーレスポンスの Lambda@Edge 関数を全ビヘイビアに付け、ヘッダーを書き込んで応答する処理を実装する
- B. WAF のカスタムレスポンスでヘッダーを追加し、すべてのルールのアクションを `Allow` にして全応答に適用する
- C. オリジンリクエストポリシーにセキュリティヘッダーを追加し、オリジンから返すように CloudFront に転送させる
- D. レスポンスヘッダーポリシーで設定し、オリジンの上書き（Origin override）を有効にする

??? success "答えと解説"
    **正解: D**

    レスポンスヘッダーポリシーなら、関数を作らずにセキュリティヘッダーを付けられます。上書きを有効にすると、オリジンの値よりポリシーの値を優先します。

    - A: 誤り。動作はするが、要件に反して実行基盤が増える。
    - B: 誤り。カスタムレスポンスはブロックされた応答の設定で、通常の応答には付かない。
    - C: 誤り。オリジンリクエストポリシーはオリジンへ送る内容の設定で、応答のヘッダーは変わらない。
    - D: 正しい。

    **スキル:** [3.1.2](../domain3.md#skill-3-1-2) / **参照:** [CloudFront の HTTPS](../../../services/networking.md#cloudfront-https)、[CloudFront と WAF](../../../services/networking.md#cloudfront-waf)

### 問6 {#q6}

CloudFront の背後のインターネット向け ALB について、CloudFront を経由しないリクエストを拒否します。ALB はこの構成のまま使い、すぐに対応します。必要な設定を選んでください。（2つ選択）

- A. CloudFront のオリジンの設定で、推測されにくいカスタムヘッダーを追加する
- B. ALB の前にゲートウェイロードバランサーを置き、CloudFront の IP 範囲以外の通信を落とす
- C. ALB のリスナールールで、そのヘッダーを持つリクエストだけを転送し、既定のアクションで 403 を返す
- D. ALB のターゲットグループのヘルスチェックに、そのヘッダーを追加して検査させる
- E. CloudFront のレスポンスヘッダーポリシーで、そのヘッダーを応答に付与する

??? success "答えと解説"
    **正解: A, C**

    CloudFront がオリジンへのリクエストにヘッダーを付け、ALB がリスナールールで検査します。ヘッダーの名前と値は秘密にします。

    - A: 正しい。
    - B: 誤り。GWLB はアプライアンスへの中継の仕組みで、この目的の手段ではない。
    - C: 正しい。
    - D: 誤り。ヘルスチェックはターゲットの状態確認で、利用者のリクエストを止めない。
    - E: 誤り。応答のヘッダーは利用者へ返るもので、オリジンへのリクエストには付かない。

### 問7 {#q7}

ウェブ ACL に次のルールがあります。社内の IP から送られた、SQL インジェクションの文字列を含むリクエストはどうなりますか。

優先度 1 は SQL インジェクションのルールでアクションは `Count`、優先度 2 は社内の IP セットでアクションは `Allow`、優先度 3 は SQL インジェクションのルールでアクションは `Block` です。既定のアクションは `Allow` です。

- A. 優先度 1 に一致した時点で評価が終わり、記録だけされてオリジンに転送される
- B. 優先度 3 まで評価され、`Block` が `Allow` より優先されて 403 が返る
- C. 優先度 1 で数えられ、優先度 2 の `Allow` で評価が終わって、オリジンに転送される
- D. `Count` と `Allow` が矛盾するので、既定のアクションが適用され、ログには残らない

??? success "答えと解説"
    **正解: C**

    ルールは優先度の小さい順に評価します。`Count` は終端しないアクションで、`Allow` と `Block` は評価を終わらせます。

    - A: 誤り。`Count` では評価は終わらない。
    - B: 誤り。優先度 2 で評価が終わるので、優先度 3 には進まない。IAM のように拒否が優先される仕組みではない。
    - C: 正しい。
    - D: 誤り。矛盾という扱いはなく、順に評価する。

    **スキル:** [3.1.2](../domain3.md#skill-3-1-2) / **参照:** [ウェブ ACL](../../../services/certificates.md#web-acl)、[ルールのアクション](../../../services/certificates.md#waf-actions-details)

### 問8 {#q8}

ALB に関連付けたウェブ ACL で、JSON の本文を SQL インジェクションのルールで検査しています。オーバーサイズの処理は `Continue` です。ペネトレーションテストで、9 KB の無害な文字列の後ろに攻撃文字列を置くと通過することが分かりました。正規のリクエストの本文は 2 KB 未満です。CloudFront は使っておらず、構成も変えません。最も適切な修正はどれですか。

- A. ウェブ ACL の本文の検査の上限を 64 KB に引き上げ、9 KB の本文も全体を検査するようにする
- B. 本文の検査のオーバーサイズの処理を `Match` にして、上限を超える本文を `Block` のルールに一致させる
- C. SQL インジェクションのルールのテキスト変換に `URL_DECODE` を追加して、後ろの文字列も読めるようにする
- D. 本文ではなくすべてのヘッダーを検査の対象に変更して、攻撃文字列の位置に左右されないようにする

??? success "答えと解説"
    **正解: B**

    ALB の本文の検査は 8 KB で固定です。`Continue` では上限内だけを検査するので、後ろの文字列は検査されません。正規の本文は小さいので、超過分をルールに一致させて止めます。

    - A: 誤り。引き上げられるのは CloudFront や API Gateway などで、ALB は 8 KB で固定。
    - B: 正しい。
    - C: 誤り。テキスト変換は検査できる範囲を広げない。
    - D: 誤り。本文の中の攻撃文字列はヘッダーの検査では見つからない。

    **スキル:** [3.1.2](../domain3.md#skill-3-1-2) / **参照:** [容量と本文の検査](../../../services/certificates.md#waf-capacity-body)

- B. 評価期間を 30 秒、レート制限を 10、集約を送信元 IP にして、全パスを対象に数え、アクションは `Block` にする
- C. 評価期間を 60 秒、レート制限を 20、集約を「すべてカウント」にして、スコープダウンなしでアクションを `Count` にする
- D. 評価期間を 300 秒、レート制限を 100、集約をカスタムキーの URI パスにして、アクションを `Allow` にする

??? success "答えと解説"
    **正解: A**

    評価期間は 60、120、300、600 秒から選びます。スコープダウンで数える対象を絞ります。

    - A: 正しい。
    - B: 誤り。30 秒は選べず、全パスを数えてしまう。
    - C: 誤り。「すべてカウント」にはスコープダウンが必須で、IP ごとの制限にならず、`Count` では止まらない。
    - D: 誤り。レートベースルールに `Allow` は使えず、URI の集約では IP ごとに数えない。

### 問14 {#q14}

- A. ALB のウェブ ACL の集約を「ヘッダーの IP アドレス」に変え、`X-Forwarded-For` の先頭のアドレスで数える
