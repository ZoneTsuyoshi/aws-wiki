# 認可の問題集

対象の解説: [IAM](../../../services/iam.md)、[Verified Permissions](../../../services/identity-directory.md#verified-permissions)、[権限境界と SCP](../../../services/iam.md#boundaries-scp)

### 問1 {#q1}

SaaS の開発チームが、自社アプリの中で「文書の所有者と同じ部署のマネージャーだけが承認できる」という認可を実装します。判定のロジックをアプリのコードから切り離し、拒否のルールを監査しやすくします。利用者の認証は Cognito で行っています。最も適切なサービスはどれですか。

- A. IAM のアイデンティティポリシーで利用者ごとに許可を書き、アプリから `SimulatePrincipalPolicy` で判定する
- B. Verified Permissions の Cedar ポリシーを `IsAuthorizedWithToken` で評価する
- C. API Gateway のリソースポリシーに部署の条件を書き、アプリ内の操作ごとに別のステージを作って切り替える
- D. Cognito の ID プールで部署ごとのロールを発行し、アプリの承認操作を IAM の条件で判定する

??? success "答えと解説"
    **正解: B**

    自作アプリの細かい認可は Verified Permissions です。Cedar は既定で拒否、`forbid` が `permit` より優先されます。JWT から主体を作るなら `IsAuthorizedWithToken` です。

    - A: 誤り。シミュレーターはアプリの実行時の判定用ではなく、利用者ごとの IAM ポリシーも増えすぎます。
    - B: 正しい。
    - C: 誤り。リソースポリシーでは文書の属性を使った判定はできません。
    - D: 誤り。IAM は AWS リソースの認可で、アプリ内の操作は判定できません。

    **スキル:** [4.2.1](../domain4.md#skill-4-2-1) / **参照:** [Verified Permissions](../../../services/identity-directory.md#verified-permissions)

### 問2 {#q2}

オンプレミスのサーバーのアプリが S3 を読みます。アクセスキーの配布をやめたいと考えています。社内の PKI が証明書を発行しています。同じアカウントには、用途の異なる別のトラストアンカーもあります。最小権限にするとき、必要な設定の組み合わせはどれですか。（2つ選択）

- A. 社内 CA をトラストアンカーに登録し、IAM Roles Anywhere を信頼するロールとプロファイルを作る
- B. 社内 CA の証明書を IAM のユーザーに関連付け、ユーザーのアクセスキーを証明書で暗号化して配布する
- C. ロールの信頼ポリシーに `aws:SourceArn` の条件を書き、使えるトラストアンカーを限定する
- D. トラストアンカーの信頼は作成したリソースの間で閉じているので、ロール側の条件は不要にする
- E. サーバーに Systems Manager のハイブリッドアクティベーションを行えば、証明書なしで S3 を読める

??? success "答えと解説"
    **正解: A, C**

    トラストアンカーの信頼はアカウント単位です。条件がないと、同じアカウントの他のトラストアンカーの証明書でもロールを引き受けられます。

    - A: 正しい。
    - B: 誤り。長期のキーが残ります。
    - C: 正しい。
    - D: 誤り。信頼はアカウント単位なので、条件が必要です。
    - E: 誤り。ハイブリッドアクティベーションはノードの管理を目的としたもので、問題の統制を満たす選択ではありません。

    **スキル:** [4.2.1](../domain4.md#skill-4-2-1) / **参照:** [認証情報プロバイダーチェーン](../../../services/iam.md#credential-chain)

### 問3 {#q3}

監視の SaaS を提供する第三者に、自社アカウントのロールを引き受けさせます。その第三者は多数の顧客を抱えており、他の顧客が自社の ARN を入力して、第三者のシステム経由で自社の情報を取得することを防ぎます。適切な統制はどれですか。

- A. 信頼ポリシーの `Principal` に第三者のアカウントの root を指定するだけで、他の顧客は区別されるので十分である
- B. 第三者に IAM ユーザーのアクセスキーを渡し、ロールは使わず、キーを定期的にローテーションする
- C. 信頼ポリシーの条件で第三者が顧客ごとに発行した `sts:ExternalId` を確認する
- D. 信頼ポリシーの条件で `aws:SourceIp` を第三者の全リージョンの範囲にして、接続元で区別する

??? success "答えと解説"
    **正解: C**

    混乱した代理の問題です。第三者が顧客ごとに一意の値を発行し、信頼ポリシーで確認すると、他の顧客が自社のロールを指定しても引き受けに失敗します。

    - A: 誤り。第三者のシステムはすべての顧客の依頼で同じ主体として呼ぶので、区別できません。
    - B: 誤り。長期の認証情報を渡すことになり、問題の解決にもなりません。
    - C: 正しい。
    - D: 誤り。第三者のどの顧客の依頼かは IP では分かりません。

    **スキル:** [4.2.1](../domain4.md#skill-4-2-1) / **参照:** [ExternalId](../../../services/iam.md#external-id)

### 問4 {#q4}

チームごとに作るロールを整理します。`iam:PassRole` を「チーム A のロールだけ」に絞りたいと考えています。ロールは API で作成しています。担当者は `role/team-a/` のパスを付ける案を出しました。この案の評価として正しいものはどれですか。

- A. パスを付けるだけで権限の境界になり、チーム A の主体は他のロールを渡せなくなる
- B. パスを使うと同じパスのユーザーとグループが自動で関連付けられるので、割り当ての作業が減り、権限の整理も一度に済む
- C. パスはコンソールからだけ設定でき、API で作成したロールには付けられない
- D. `Resource` に `role/team-a/*` と書けば絞れるが、パス自体に権限の効果はない

??? success "答えと解説"
    **正解: D**

    IAM パスはポリシーの `Resource` でまとめて指定するのに便利です。パスそのものは権限を与えも制限もしません。

    - A: 誤り。パスに境界の効果はありません。
    - B: 誤り。自動の関連付けはありません。
    - C: 誤り。逆です。パスは API や CLI で指定し、コンソールでは作れません。
    - D: 正しい。

    **スキル:** [4.2.1](../domain4.md#skill-4-2-1) / **参照:** [PassRole](../../../services/iam.md#passrole)

### 問5 {#q5}

別アカウントのチームが 200 個の S3 オブジェクトを自分のアカウントへコピーします。コピーを実行するのは取得側のアカウントの主体です。取得側の主体が元のバケットを読みつつ、宛先のバケットにも書く必要があります。最小の変更で実現するにはどうしますか。

- A. 元のバケットポリシーと取得側の IAM ポリシーの両方で、必要な操作を許可する
- B. 元のアカウントのロールを引き受け、そのセッションだけで元のバケットと宛先のバケットの両方を操作するようにして、権限の管理を 1 か所にまとめる
- C. 元のバケットのポリシーだけで許可すれば、IAM ポリシーは不要である
- D. AWS RAM で元のバケットを取得側のアカウントに共有する

??? success "答えと解説"
    **正解: A**

    ロールを引き受けると元のアカウントの権限に切り替わり、自分のアカウントの権限を使えなくなります。リソースポリシーなら元の権限を維持して両方を操作できます。別のアカウントなので、両方の許可が必要です。

    - A: 正しい。
    - B: 誤り。引き受けたセッションには宛先への書き込みの許可がなく、宛先のポリシーの追加が別に必要です。
    - C: 誤り。別のアカウントでは IAM ポリシーの許可も必要です。
    - D: 誤り。S3 バケットは RAM の共有の対象ではありません。

    **スキル:** [4.2.1](../domain4.md#skill-4-2-1) / **参照:** [クロスアカウントアクセス](../../../services/iam.md#cross-account)

### 問6 {#q6}

新しいプロジェクトが月に 10 件増えます。現在はプロジェクトごとに IAM ポリシーとロールを作っており、管理が追いつきません。プロジェクトのリソースにはすでに `Project` タグが付いており、社員のプロジェクトの所属は IdP の属性で管理されています。最も適切な変更はどれですか。

- A. プロジェクトごとにロールのパスを分けて、`Resource` を `*` にしたポリシーをパスごとに 1 つだけ作るように統一する
- B. グループに所属を入れて、プロジェクトの一覧を毎月更新する Lambda で各ロールのポリシーを書き換える
- C. SCP をプロジェクトごとに作成し、許可するプロジェクトのリソースを OU ごとに列挙する
- D. IdP の属性をセッションタグで渡し、`aws:ResourceTag/Project` と `aws:PrincipalTag/Project` の一致で許可する

??? success "答えと解説"
    **正解: D**

    ABAC なら、ポリシーを増やさずにプロジェクトを追加できます。タグを付けるだけで権限が決まるので、増減が多い環境に向きます。

    - A: 誤り。パスに権限の効果はなく、`Resource` が `*` だと全リソースに届きます。
    - B: 誤り。管理の負担を自動化で隠すだけで、ポリシーの上限にも当たります。
    - C: 誤り。SCP は許可を与えず、ポリシーの数の制限にも当たります。
    - D: 正しい。

    **スキル:** [4.2.2](../domain4.md#skill-4-2-2) / **参照:** [セッションタグ](../../../services/iam.md#session-tags)

### 問7 {#q7}

ABAC を導入した後の監査で、開発者が自分の EC2 インスタンスの `Project` タグを他のプロジェクトの値に書き換え、他のプロジェクトの権限で操作できることが判明しました。原因を踏まえ、もっとも効果的な対策はどれですか。

- A. インスタンスのタグをすべて削除し、ABAC をやめて RBAC に全面的に戻す
- B. `ec2:CreateTags` を `aws:RequestTag` と `aws:TagKeys` で制限する
- C. CloudTrail のデータイベントで `ec2:CreateTags` を記録し、月次で変更を確認する
- D. セッションタグを推移的にして、変更後のタグがセッションに反映されないようにする

??? success "答えと解説"
    **正解: B**

    ABAC ではタグが権限そのものです。タグを変更する権限を厳しく管理します。

    - A: 誤り。統制を足すだけで解決でき、過剰です。
    - B: 正しい。
    - C: 誤り。検出だけで防げません。`CreateTags` は管理イベントでもあります。
    - D: 誤り。推移的なタグはロールチェーンのためのもので、リソースのタグとは関係しません。

    **スキル:** [4.2.2](../domain4.md#skill-4-2-2) / **参照:** [条件とアクセス制御](../../../services/iam.md#conditions)

### 問8 {#q8}

ロール A でセッションタグ `Department=finance` を付けて `AssumeRole` し、そのセッションからロール B を引き受けます。B のセッションでは `aws:PrincipalTag/Department` が空になり、タグの条件を満たしません。修正として正しいものはどれですか。

- A. A を引き受けるときに `TransitiveTagKeys` で `Department` を指定する
- B. B の `MaxSessionDuration` を 12 時間に増やし、セッションの間だけ保持されるタグの有効期間を延ばす
- C. B の信頼ポリシーから `sts:TagSession` を外し、自動の引き継ぎを許可する
- D. A のロール自体のタグを削除し、セッションタグとの衝突をなくす

??? success "答えと解説"
    **正解: A**

    セッションタグは既定で次のセッションへ渡りません。推移的にするには `TransitiveTagKeys` を指定します。B の信頼ポリシーは `sts:TagSession` を許可している必要があります。

    - A: 正しい。
    - B: 誤り。期間はタグの引き継ぎと関係しません。
    - C: 誤り。逆です。タグの引き継ぎには `sts:TagSession` の許可が必要です。
    - D: 誤り。衝突が原因ではありません。

    **スキル:** [4.2.2](../domain4.md#skill-4-2-2) / **参照:** [セッションタグ](../../../services/iam.md#session-tags)

### 問9 {#q9}

10 人の役割が明確で、3 年間ほぼ変わらない経理チームがあります。監査では「誰がどの権限を持つか」をポリシーの一覧で説明することが求められます。別の部門では ABAC を採用しています。経理チームについて、この状況に合う判断はどれですか。

- A. 全社の統一のために経理にも ABAC を強制し、タグだけで権限が決まるようにする
- B. 役割が固定で説明が求められるので、役割ごとのポリシーを持つ RBAC を選ぶ
- C. 経理の人数が少ないので、全員に同じ IAM ユーザーを共有させて、ポリシーを 1 つにする
- D. ABAC も RBAC も監査に使えないので、権限は SCP にだけ記述する

??? success "答えと解説"
    **正解: B**

    役割が固定で権限の確認を明確にしたい場面は RBAC に向きます。両方の方式を場面に応じて組み合わせられます。

    - A: 誤り。ABAC の利点は増減が多い場面です。監査の要件に合いません。
    - B: 正しい。
    - C: 誤り。共有すると本人を特定できず、監査の要件に反します。

### 問10 {#q10}

開発チームに Lambda の実行ロールを自分で作らせます。ただし、作るロールの権限が決められた範囲を超えないことと、チームが作ったロール自身が境界を外せないことが条件です。ポリシーの組み合わせとして適切なものはどれですか。（2つ選択）

- A. `iam:CreateRole` に `iam:PermissionsBoundary` の条件を付け、指定の境界付きでだけ作成を許可する
- B. `iam:DeleteRolePermissionsBoundary` を拒否し、境界のポリシーの変更も拒否する
- C. 開発チームのロールに `AdministratorAccess` を付け、SCP で IAM のすべての操作を拒否する
- D. 作ったロールの信頼ポリシーを `lambda.amazonaws.com` にすれば、権限の範囲も自動で制限される
- E. `iam:PassRole` の `Resource` を `*` にして、チームが Lambda にどのロールでも渡せるようにする

??? success "答えと解説"
    **正解: A, B**

    権限境界の定番です。作成時に境界を強制し、外す操作と書き換える操作を止めます。

### 問11 {#q11}

マルチテナントの SaaS です。バックエンドは共通のロールを引き受け、S3 の `data/<テナント ID>/` を読みます。テナントは 5,000 あり、テナントごとのロールは作りたくありません。別のテナントのデータを読めないことを、アプリのコードの正しさに頼らず保証したいと考えています。どうしますか。

- A. アプリのコードでキーの先頭のテナント ID を検査し、一致しない場合に例外を投げる
- B. テナントごとに IAM ユーザーを作成し、アクセスキーを Secrets Manager で管理する

### 問12 {#q12}

共通のロールに `s3:*` を許可し、セッションポリシーで `s3:GetObject` だけを許可しました。さらに権限境界で `s3:GetObject` と `s3:PutObject` を許可しています。同じアカウントのバケットに、バケットポリシーの設定はありません。このセッションで `s3:PutObject` を呼ぶと結果はどうなりますか。

- A. セッションポリシーが許可していないので、暗黙に拒否される
- B. ロールのポリシーと権限境界の両方が許可しているので、成功する
- C. 権限境界が優先されるので、成功する

    - B: 誤り。セッションポリシーの許可も必要です。
    - C: 誤り。権限境界は上限を決めるだけで、他のポリシーより優先されるわけではありません。
    - D: 誤り。許可がなければ暗黙の拒否になります。

新しいバッチのロールは最初に広めの権限で動かしました。本番の前に、実際に使った操作に基づいて最小権限のポリシーを作り、以後は使われなくなった権限も定期的に見つけたいと考えています。手間の少ない組み合わせはどれですか。
