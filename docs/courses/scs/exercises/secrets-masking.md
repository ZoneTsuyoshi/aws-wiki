# シークレットとマスキングの問題集

対象の解説: [3 つのサービスの比較](../../../services/secrets.md#comparison)、[ローテーション](../../../services/secrets.md#rotation)、[データ保護ポリシー](../../../services/observability.md#logs-data-protection)

### 問1 {#q1}

RDS for MySQL のマスターユーザーの認証情報を 30 日ごとに自動でローテーションします。ローテーションの実装と運用はできるだけ持ちたくありません。アプリはローテーションのたびに認証情報を再読み込みできます。最も適切な選択はどれですか。

- A. Parameter Store の SecureString に保存し、EventBridge のスケジュールでパラメータの値を自作の Lambda で更新する
- B. RDS にマスターユーザーのシークレットを管理させ、マネージドローテーションを使う
- C. Secrets Manager に保存し、4 段階の Lambda の関数を自分で実装して 30 日ごとに実行する
- D. アプリのコンテナイメージにパスワードを入れ、30 日ごとにイメージを作り直してデプロイする

??? success "答えと解説"
    **正解: B**

    RDS が管理するマスターユーザーのシークレットはマネージドローテーションに対応し、Lambda が不要です。

    - A: 誤り。Parameter Store に自動ローテーションはなく、自作の運用が残ります。
    - B: 正しい。
    - C: 誤り。動きますが、実装の運用が残ります。
    - D: 誤り。イメージにシークレットを入れるのは避けます。

    **スキル:** [5.3.1](../domain5.md#skill-5-3-1) / **参照:** [ローテーション](../../../services/secrets.md#rotation)

### 問2 {#q2}

24 時間動く決済アプリでは、ローテーションの瞬間にも接続を失敗させられません。データベースにはテーブルを所有するロールとアクセス用のロールがあります。ローテーションの戦略はどれですか。

- A. シングルユーザーで、パスワードの更新の後に接続のリトライを 1 回だけ実装する
- B. シングルユーザーで、ローテーションの間隔を 4 時間にして影響を分散する
- C. 交代ユーザーで、別に管理者の権限を持つ `superuser` のシークレットを用意する
- D. マスターユーザーをアプリに直接使わせ、自動ローテーションをやめて手動で変える

??? success "答えと解説"
    **正解: C**

    交代ユーザーは 2 つのユーザーを交互に更新するので、高い可用性に向きます。ユーザーを作成するための別の管理者のシークレットが必要です。

    - A: 誤り。短時間の拒否があり、条件に反します。
    - B: 誤り。瞬間の拒否は残ります。
    - C: 正しい。
    - D: 誤り。最小権限にもローテーションの要件にも反します。

    **スキル:** [5.3.1](../domain5.md#skill-5-3-1) / **参照:** [Lambda ローテーションの動き](../../../services/secrets.md#lambda-rotation-steps)

### 問3 {#q3}

別のアカウントの Lambda に、自アカウントの Secrets Manager のシークレットを読ませます。シークレットのリソースポリシーと、相手のロールの IAM ポリシーは許可しました。それでも `GetSecretValue` が失敗します。シークレットは `aws/secretsmanager` で暗号化されています。修正はどれですか。

- A. `aws/secretsmanager` のキーポリシーに相手のロールを追加する
- B. カスタマー管理キーに変更し、両側で `kms:Decrypt` を許可する
- C. シークレットを Parameter Store の標準パラメータに移し、組織全体に公開して読み取らせる
- D. 相手のアカウントにシークレットをレプリケートして、同じキーのまま読み取らせる

??? success "答えと解説"
    **正解: B**

    `aws/secretsmanager` はクロスアカウントで使えません。シークレットのリソースポリシー、相手の IAM ポリシー、カスタマー管理キーのキーポリシーの 3 つが条件です。

    - A: 誤り。AWS 管理キーのポリシーは変更できません。
    - B: 正しい。
    - C: 誤り。必要以上に公開し、暗号化の問題も解決しません。
    - D: 誤り。レプリケートはリージョン間の機能で、アカウント間ではありません。

    **スキル:** [5.3.1](../domain5.md#skill-5-3-1) / **参照:** [クロスアカウント](../../../services/secrets.md#secrets-cross-account)

### 問4 {#q4}

VPC 内のサブネットで動くカスタムのローテーション関数が、`createSecret` のステップでタイムアウトします。サブネットにはインターネットへの経路がなく、DB には接続できます。最も適切な修正はどれですか。

- A. Lambda のタイムアウトを最大の 15 分へ延ばし、DB への接続のプールを増やす
- B. シークレットを別のリージョンにレプリケートし、そこで関数を実行する
- C. Secrets Manager のローテーション間隔を 4 時間から 24 時間に変更する
- D. Secrets Manager のインターフェイスエンドポイントを追加する

??? success "答えと解説"
    **正解: D**

    ローテーションの関数は Secrets Manager の API を呼びます。経路がないとタイムアウトするので、VPC エンドポイントか NAT が必要です。

    - A: 誤り。経路がなければ、延ばしても届きません。
    - B: 誤り。関数の経路の問題は解決しません。
    - C: 誤り。実行の間隔は経路に関係しません。
    - D: 正しい。

    **スキル:** [5.3.1](../domain5.md#skill-5-3-1) / **参照:** [ローテーション](../../../services/secrets.md#rotation)

### 問5 {#q5}

アプリの設定値を保存します。一覧の中で、機能フラグの文字列と API の接続先の URL は暗号化不要で、社外の決済 API のキーだけは暗号化が必要です。決済キーの自動ローテーションはベンダー側の制約でできません。費用を最小にする組み合わせはどれですか。

- A. 設定値は Parameter Store の String、決済キーは SecureString に保存する
- B. すべてを Secrets Manager に保存し、決済キーはローテーションの設定なしで保存する
- C. 設定値は S3、決済キーは Secrets Manager の 2 か所に保存する
- D. すべてを Parameter Store の Advanced の SecureString に保存する

??? success "答えと解説"
    **正解: A**

    自動ローテーションが不要で、費用を抑えたいなら Parameter Store です。SecureString で KMS による暗号化ができ、標準パラメータは無料です。

    - A: 正しい。
    - B: 誤り。シークレットごとに課金され、費用が増えます。
    - C: 誤り。Secrets Manager の費用がかかり、保存先も増えます。
    - D: 誤り。Advanced は有料で、不要です。

    **スキル:** [5.3.1](../domain5.md#skill-5-3-1) / **参照:** [3 つのサービスの比較](../../../services/secrets.md#comparison)

### 問6 {#q6}

アプリのログにメールアドレスが出力されていました。CloudWatch Logs のアカウント全体のデータ保護ポリシーを本日設定しました。翌日、昨日のログを Logs Insights で開くとメールアドレスが見えます。正しい説明はどれですか。

- A. アカウント全体のポリシーは既存のロググループに適用されないので、ロググループごとに設定し直す必要がある
- B. Logs Insights はマスクの対象外なので、サブスクリプションフィルターで確認する必要がある
- C. マスクは取り込み時に行うので、設定前のログには効かない。保持期間の短縮などで別に対処する
- D. 反映に 24 時間かかるので、もう 1 日待てば過去のログもマスクされる

??? success "答えと解説"
    **正解: C**

    機密データは取り込み時に検出してマスクします。ポリシーの設定前に取り込まれたログはマスクされないので、保持期間の短縮などで別に対処します。

    - A: 誤り。アカウント全体のポリシーは既存と将来のロググループに適用されます。
    - B: 誤り。Logs Insights でもマスクされます。
    - C: 正しい。
    - D: 誤り。過去のログは待ってもマスクされません。

    **スキル:** [5.3.4](../domain5.md#skill-5-3-4) / **参照:** [データ保護ポリシー](../../../services/observability.md#logs-data-protection)

### 問7 {#q7}

CloudWatch Logs のデータ保護ポリシーを、セキュリティチームの一部の調査員だけがマスクの解除を行えるように設計します。解除の権限と検知の数の監視について、正しい組み合わせはどれですか。（2つ選択）

- A. 調査員のロールにだけ `logs:Unmask` を許可する
- B. `logs:Unmask` は KMS のキーポリシーの権限で、IAM では許可できない
- C. `AWS/Logs` 名前空間の `LogEventsWithFindings` メトリクスでアラームを作る
- D. 検知の数はロググループの `IncomingBytes` メトリクスの増加から計算する
- E. マスクされたログは S3 にエクスポートすると、権限なしで元の値を読める

??? success "答えと解説"
    **正解: A, C**

    マスクされていないデータを見られるのは `logs:Unmask` を持つ主体です。`LogEventsWithFindings` で検知の数を監視できます。

    - A: 正しい。
    - B: 誤り。IAM の権限です。
    - C: 正しい。
    - D: 誤り。`IncomingBytes` はデータ量で、検知の数を表しません。
    - E: 誤り。そのような権限の抜け道は、機能として案内されていません。

    **スキル:** [5.3.4](../domain5.md#skill-5-3-4) / **参照:** [CloudWatch Logs のデータ保護](../../../services/secrets.md#cloudwatch-data-protection)

### 問8 {#q8}

Web のフォームで入力されたクレジットカード番号を、エッジで暗号化し、オリジンのアプリのログに平文が残らないようにします。カード番号を見られるのは社内の特定のサービスだけです。最も適切な方法はどれですか。

- A. CloudFront のビューワープロトコルポリシーを HTTPS のみにして、全区間の通信を暗号化する
- B. WAF の Web ACL でカード番号のパターンをブロックし、オリジンに届かないようにする
- C. ALB で TLS を終端し、アプリのログに出さないようにコードを修正して、平文の扱いを各チームに任せる
- D. CloudFront のフィールドレベル暗号化を使い、特定のサービスだけが秘密鍵を持つ

??? success "答えと解説"
    **正解: D**

    フィールドレベル暗号化は指定のフィールドをエッジで公開鍵により暗号化します。秘密鍵を持つアプリだけが復号できます。

    - A: 誤り。HTTPS の終端の後は平文になります。
    - B: 誤り。カード番号を受け取れなくなります。
    - C: 誤り。統制をコードに頼り、平文がアプリに届きます。
    - D: 正しい。

    **スキル:** [5.3.4](../domain5.md#skill-5-3-4) / **参照:** [フィールドレベル暗号化](../../../services/networking.md#field-level-encryption)

### 問9 {#q9}

既存の SNS トピックにメッセージデータ保護を設定しています。組織は発行時に個人情報を含むメッセージを拒否し、配信時には個人情報をマスクします。また、新しい環境で同じ統制を作る担当者から相談を受けました。正しい判断はどれですか。

- A. 既存は Inbound の Deny と Outbound の De-identify を使い、新規は代替を検討する
- B. 新旧を問わず機能が利用できないので、既存のトピックも直ちに移行する必要がある
- C. 発行時の拒否は Audit の操作で行い、配信時のマスクは Inbound の De-identify の操作で行う
- D. 1 つのトピックに複数のデータ保護ポリシーを付けて、新しい顧客でも Audit の文だけを使う

??? success "答えと解説"
    **正解: A**

    発行は `Inbound`、配信は `Outbound` です。2026 年 4 月 30 日で新規顧客の受付を終了し、既存の顧客は使い続けられます。公式の代替案は Lambda と Bedrock Guardrails の構成です。

    - A: 正しい。
    - B: 誤り。既存の顧客は使い続けられます。
    - C: 誤り。Audit は中断せず記録するだけです。配信時は `Outbound` です。
    - D: 誤り。ポリシーはトピックごとに 1 つで、新規の受付も終わっています。

    **スキル:** [5.3.4](../domain5.md#skill-5-3-4) / **参照:** [サニタイズとマスキング](../../../services/secrets.md#sanitization-masking)

### 問10 {#q10}

WAF のログに `Authorization` ヘッダーが残っており、監査で指摘されました。また、S3 に保存された過去のファイルに個人情報が含まれているかも調べる必要があります。それぞれの対応の組み合わせはどれですか。

- A. WAF のログの配信をすべて止め、S3 のファイルは Macie のマスク機能で置き換える
- B. WAF のログの設定でヘッダーのフィールドを編集（redaction）し、S3 のファイルは Macie で機密データを検出する
- C. WAF にヘッダーを削除するルールを追加し、S3 のファイルは Lambda のコード署名で検査する
- D. WAF のログを CloudWatch Logs に送ってマスクし、S3 のファイルは Bedrock Guardrails で自動的に置き換える

??? success "答えと解説"
    **正解: B**

    WAF のログはフィールドの編集で隠せます。Macie は機密データの検出で、マスクはしません。

    - A: 誤り。ログを止めると調査の手がかりを失います。Macie はマスクしません。
    - B: 正しい。
    - C: 誤り。ルールでログの値は消えません。コード署名は無関係です。
    - D: 誤り。Guardrails は S3 のファイルの置き換えを行いません。

    **スキル:** [5.3.4](../domain5.md#skill-5-3-4) / **参照:** [WAF のログ](../../../services/certificates.md#waf-logging)
