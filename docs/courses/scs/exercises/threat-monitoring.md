# 脅威の監視の問題集

対象の解説: [脅威検出とインシデント対応](../../../services/threat-detection.md)、[Config](../../../services/governance.md#config)、[ヘルスチェックとプローブ](../../../services/observability.md#health-checks)

### 問1 {#q1}

ある企業は 40 のアカウントに数千の S3 バケットを持っています。まず全バケットのどこに機密データがありそうかを費用を抑えて把握し、そのうえで規制対象の 3 つのバケットは毎週、新しいオブジェクトを確実に検査したいと考えています。

最も適切な構成はどれですか。

- A. 全バケットを対象にした Macie の定期ジョブを毎日実行し、サンプリング深度を 100% にする
- B. GuardDuty の S3 保護を有効にし、検出結果の種類から機密データの有無を判断する
- C. Access Analyzer の外部アクセスの分析ツールで全バケットを調べ、共有の有無で機密度を分ける
- D. Macie の自動検出で全体を把握し、3 つのバケットには週次の定期ジョブを設定する

??? success "答えと解説"
    **正解: D**

    自動検出は全バケットから日々オブジェクトを選んで分析するので、全体を安く見渡せます。特定のバケットの詳しい検査は、日次、週次、月次で実行できるジョブが向いています。

    - A: 誤り。全バケットを毎日全量で検査すると費用が大きくなり、要件の「費用を抑えて」に反します。
    - B: 誤り。GuardDuty は脅威を検出するもので、オブジェクトの中身の機密データは調べません。
    - C: 誤り。Access Analyzer は共有の状態を見るもので、中身の機密度は分かりません。
    - D: 正しい。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [Macie の検出方法](../../../services/threat-detection.md#macie-discovery)

### 問2 {#q2}

ある企業は EKS と EC2 でコンテナを運用しています。監査の指摘を受けて、次の 2 つを監視の要件にしました。

実行中のプロセスやファイルの操作から暗号通貨の採掘などの不審な振る舞いを検出すること。イメージと OS パッケージの既知の CVE を継続的に洗い出すこと。どのサービスを組み合わせますか。（2つ選択）

- A. Macie の自動検出
- B. GuardDuty の Runtime Monitoring
- C. Trusted Advisor のセキュリティチェック
- D. Amazon Inspector の EC2 と ECR のスキャン
- E. AWS Config のマネージドルール

??? success "答えと解説"
    **正解: B, D**

    Runtime Monitoring は OS レベル、ネットワーク、ファイルのイベントから「今攻撃されているか」を見ます。Inspector は「弱点があるか」を見ます。問いが違うので、両方が必要です。

    - A: 誤り。Macie は S3 の機密データが対象です。
    - B: 正しい。
    - C: 誤り。Trusted Advisor は環境の設定の点検で、実行時の振る舞いや CVE の継続的な検出はしません。
    - D: 正しい。
    - E: 誤り。Config は設定の評価で、プロセスの振る舞いや CVE は見ません。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [保護プラン](../../../services/threat-detection.md#guardduty-protection-plans)、[Inspector のスキャンの種類](../../../services/threat-detection.md#inspector-scan-types)

### 問3 {#q3}

小規模なセキュリティチームが、IAM ユーザーのアクセスキーの漏えいと、普段と違う場所からの利用を検出したいと考えています。CloudTrail の証跡はまだ作っておらず、検出のためのルールやログ基盤を自分たちで保守する余裕はありません。

運用の負荷が最も小さい方法はどれですか。

- A. 証跡を作って CloudWatch Logs に送り、送信元 IP ごとのメトリクスフィルターとアラームを作る
- B. GuardDuty を有効にする。CloudTrail の管理イベントは独立した経路で分析される
- C. 証跡を S3 に出力し、Athena で送信元 IP を集計するクエリを毎時実行する
- D. Config のカスタムルールで、アクセスキーの最終利用の場所を定期的に評価する

??? success "答えと解説"
    **正解: B**

    GuardDuty は有効にすると、CloudTrail の管理イベントを独立した複製のストリームで分析します。証跡の作成は検出の前提ではありません。

    - A: 誤り。動きますが、ルールの作成と保守が要件に反します。送信元ごとの基準も自分で決める必要があります。
    - B: 正しい。ただし、記録を自分で保持したいなら別に証跡が必要です。
    - C: 誤り。クエリの作成と定期実行の保守が必要です。
    - D: 誤り。Config は設定を評価するもので、利用場所のような活動は評価できません。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [GuardDuty のデータソース](../../../services/threat-detection.md#guardduty-data-sources)

### 問4 {#q4}

組織に数百のバケットがあります。担当者は、公開設定になっているバケットのうち、機密データを含む可能性が高いものから順に確認したいと考えています。オブジェクトを自分で読むスクリプトは作りたくありません。

最も適切なものはどれですか。

- A. S3 の Storage Lens のダッシュボードで、バケットごとのオブジェクト数を比較する
- B. CloudTrail のデータイベントで `GetObject` の回数を集計して、多いものを機密と判断する
- C. Macie の自動検出を有効にし、バケットの機密度スコアと公開設定を一覧で確認する
- D. Inspector のネットワーク到達性の検出結果から、インターネットに開いたバケットを探す

??? success "答えと解説"
    **正解: C**

    Macie はバケットのインベントリで公開設定などを示し、自動検出の結果を機密度スコアとして表示します。優先順位付けに使えます。

    - A: 誤り。Storage Lens は使用状況の分析で、機密性は分かりません。
    - B: 誤り。アクセス回数は機密性の指標ではありません。
    - C: 正しい。
    - D: 誤り。Inspector のネットワーク到達性は EC2 が対象で、S3 バケットには使えません。

    **スキル:** [1.1.1](../domain1.md#skill-1-1-1) / **参照:** [Macie の検出結果](../../../services/threat-detection.md#macie-findings)

### 問5 {#q5}

ある企業は CloudFront と ALB の Web アプリを Shield Advanced で保護しています。攻撃時に Shield Response Team（SRT）から連絡を受けられるようにし、攻撃の検出の精度も高めたいと考えています。サポートプランは Enterprise です。

追加で必要な設定はどれですか。

- A. Route 53 ヘルスチェックを作成して保護対象に関連付け、プロアクティブエンゲージメントと連絡先を設定する
- B. ALB のターゲットグループのヘルスチェック間隔を短くして、Shield Advanced のメトリクスに自動で反映させる
- C. CloudWatch Synthetics のカナリアを作成し、失敗したときに SRT へ自動でケースを起票する Lambda を置く
- D. GuardDuty の検出結果を SRT に共有する EventBridge ルールを作成する

??? success "答えと解説"
    **正解: A**

    ヘルスベースの検出は Route 53 ヘルスチェックを保護に関連付けて使います。プロアクティブエンゲージメントの前提でもあり、SRT はチェックの状態で連絡の要否を判断します。

    - A: 正しい。
    - B: 誤り。ターゲットグループのヘルスチェックは Shield Advanced のヘルスベース検出には使われません。
    - C: 誤り。カナリアの結果は検出の精度に反映されず、プロアクティブエンゲージメントの条件も満たしません。
    - D: 誤り。GuardDuty の検出結果は DDoS の検出にもエンゲージメントの判断にも使われません。

    **スキル:** [1.1.2](../domain1.md#skill-1-1-2) / **参照:** [Shield Advanced](../../../services/threat-detection.md#shield-advanced)、[Route 53 ヘルスチェック](../../../services/networking.md#route53-health-checks)

### 問6 {#q6}

WAF のルールを変更したあと、ログイン画面の入力から完了までの操作だけが失敗する事象がありました。ALB のヘルスチェックは正常のままで、気づくのに数時間かかりました。

利用者と同じ操作を定期的に実行して、失敗を早く検知するにはどうしますか。

- A. ターゲットグループのヘルスチェックのパスをログイン画面の URL に変更する
- B. Route 53 ヘルスチェックの文字列照合で、トップページの応答を確認する
- C. VPC フローログで ALB への通信量が減ったらアラームを出すよう、メトリクスフィルターとダッシュボードを作る
- D. CloudWatch Synthetics のカナリアでログインの操作を再現し、失敗のアラームを設定する

??? success "答えと解説"
    **正解: D**

    カナリアは利用者と同じ経路と操作を定期的に実行する設定可能なスクリプトです。WAF を含む外側からの経路も通ります。

    - A: 誤り。ALB から直接ターゲットを確認するので WAF を通らず、操作の手順も再現しません。
    - B: 誤り。1 回の応答の確認で、ログインの手順は再現できません。
    - C: 誤り。通信量の減少は間接的な兆候で、ログインの失敗を特定できません。
    - D: 正しい。

    **スキル:** [1.1.2](../domain1.md#skill-1-1-2) / **参照:** [Synthetics](../../../services/operations.md#synthetics)、[ヘルスチェックとプローブ](../../../services/observability.md#health-checks)

### 問7 {#q7}

インシデント対応の演習で、誤った変更によりターゲットのセキュリティグループが ALB からの通信を拒否し、全ターゲットが異常になりました。しかし ALB はリクエストの転送を止めず、担当者への通知もありませんでした。

この動作と対策の説明として正しいものはどれですか。

- A. 全ターゲットが異常になると ALB は全ターゲットへ転送する。`UnHealthyHostCount` などのメトリクスにアラームを設定する
- B. 全ターゲットが異常になると ALB は 503 を返して停止する。Shield Advanced の保護を追加して自動で通知させる
- C. ヘルスチェックの失敗は CloudTrail の管理イベントとして記録される。そのイベントで EventBridge ルールを起動する
- D. ヘルスチェックの間隔の既定が 5 分と長いことが原因である。間隔を短くすれば自動で通知される

??? success "答えと解説"
    **正解: A**

    ターゲットグループに異常なターゲットしかないと、ALB はヘルス状態にかかわらず全ターゲットへ転送します。ヘルスチェックは自動で通知しないので、メトリクスへのアラームが必要です。

    - A: 正しい。
    - B: 誤り。この場合は全ターゲットへ転送します。Shield Advanced は通知の手段として適切ではありません。
    - C: 誤り。ヘルスチェックの結果は API の呼び出しではなく、CloudTrail のイベントになりません。
    - D: 誤り。インスタンスと IP のターゲットの既定の間隔は 30 秒です。間隔を変えても通知はされません。

    **スキル:** [1.1.2](../domain1.md#skill-1-1-2) / **参照:** [ALB のヘルスチェック](../../../services/networking.md#alb-health-checks)

### 問8 {#q8}

社内向けのアプリは VPC のプライベートサブネットだけで動いています。異常を Route 53 のヘルスチェックの状態としても扱い、既存の通知の仕組みにつなげたいと考えています。インスタンスにパブリック IP を付けることは認められていません。

適切な方法はどれですか。

- A. Route 53 ヘルスチェックのエンドポイントにインスタンスのプライベート IP を直接指定する
- B. VPC にインターフェイスエンドポイントを作成して、Route 53 のチェッカーを VPC の中から動かすように設定を変更する
- C. カナリアの結果を S3 に出力し、Route 53 ヘルスチェックの監視対象に S3 のオブジェクトを指定する
- D. CloudWatch のメトリクスとアラームを作り、そのアラームを監視する Route 53 ヘルスチェックを作る

??? success "答えと解説"
    **正解: D**

    Route 53 のチェッカーは VPC の外にあるので、VPC 内の IP に直接は届きません。CloudWatch アラームのデータストリームを監視するヘルスチェックなら、公開せずに状態を扱えます。

    - A: 誤り。チェッカーはプライベート IP に届きません。
    - B: 誤り。チェッカーを VPC の中で動かす仕組みはありません。
    - C: 誤り。S3 のオブジェクトはヘルスチェックの監視対象ではありません。
    - D: 正しい。

    **スキル:** [1.1.2](../domain1.md#skill-1-1-2) / **参照:** [Route 53 ヘルスチェック](../../../services/networking.md#route53-health-checks)

### 問9 {#q9}

組織の GuardDuty を、東京リージョンで委任管理者のアカウント A に任せ、全メンバーが見えています。後日、大阪リージョンで作られたリソースの検出結果が A に届いていないことが分かりました。担当者は大阪でだけ、別のアカウント B を委任管理者にして権限を分けることを提案しています。

最も適切な対応はどれですか。

- A. Organizations の委任はグローバルなので、東京で委任をやり直せば大阪にも反映される
- B. 提案どおり大阪では B を委任管理者に指定し、検出結果を東京へ複製する
- C. 大阪でも同じアカウント A を委任管理者に指定し、メンバーを自動有効化する
- D. GuardDuty のクロスリージョン集約を東京で有効にして、大阪のメンバーを集約する

??? success "答えと解説"
    **正解: C**

    GuardDuty の委任管理者はリージョンごとに指定します。組織で全リージョンに同じアカウントを使う必要があるので、別のアカウントは指定できません。

    - A: 誤り。GuardDuty はリージョンのサービスで、リージョンごとの指定が必要です。
    - B: 誤り。リージョンごとに違うアカウントを委任管理者にはできません。
    - C: 正しい。
    - D: 誤り。GuardDuty にこの設定はありません。リージョンごとに有効にし、集約は別の手段で行います。

    **スキル:** [1.1.3](../domain1.md#skill-1-1-3) / **参照:** [GuardDuty の複数アカウント](../../../services/threat-detection.md#guardduty-multi-account)、[委任管理者](../../../services/governance.md#delegated-admin)

### 問10 {#q10}

Security Hub CSPM の委任管理者がいる組織で、これまでローカル設定を使ってきました。既存の全アカウントと複数のリージョンで標準を統一し、テスト用の OU だけ別の標準にしたいと考えています。各アカウントでの個別の作業は避けます。

最も適切なものはどれですか。

- A. ローカル設定の「新しいアカウントを自動で有効化」をオンにして、既存のアカウントに広げる
- B. 中央設定に切り替え、ホームリージョンとリンクリージョンを指定して、設定ポリシーを OU に関連付ける
- C. 各リージョンで別々に委任管理者を指定し、スクリプトで `BatchEnableStandards` を全アカウントに実行する
- D. Config アグリゲーターを作り、標準の有効化を組織全体へ展開する

    中央設定は、委任管理者が設定ポリシーで OU やアカウントごとに標準とコントロールを決めます。ポリシーはホームリージョンとリンクリージョンで有効です。

    - A: 誤り。ローカル設定は新しいアカウントと現在のリージョンだけが対象で、既存のアカウントには効きません。
    - B: 正しい。
    - C: 誤り。個別の作業が残り、設定の維持も自動になりません。
    - D: 誤り。アグリゲーターは読み取り専用の集約で、展開はできません。

### 問11 {#q11}

300 のメンバーアカウントを持つ組織で GuardDuty の委任管理者が自動有効化を `NEW` に設定しています。買収で組織に入れた古いアカウントの一部で GuardDuty が無効のままでした。新しいアカウントにも、既存のアカウントにも漏れなく適用したいと考えています。

どの設定にしますか。

- A. `NONE` に変更し、委任管理者が各アカウントを個別に管理する
- B. `NEW` のまま、無効のアカウントで管理者が手動で招待を送信する
- C. `ALL` に変更する。全メンバーへの反映には最大 24 時間かかることがある
- D. SCP で `guardduty:DisableGuardDuty` を拒否すると、無効のアカウントも自動で有効になる

??? success "答えと解説"
    **正解: C**

    `ALL` は既存と新規の全メンバーが対象です。`NEW` は新しく参加するアカウントだけが対象です。

    - A: 誤り。`NONE` は新しいアカウントで有効にしない設定で、漏れがさらに増えます。
    - B: 誤り。Organizations で管理するアカウントに招待は不要で、新規と既存を自動でそろえられません。
    - C: 正しい。
    - D: 誤り。SCP は操作を拒否するだけで、サービスを有効にしません。無効化の防止として別途は有用です。

    **スキル:** [1.1.3](../domain1.md#skill-1-1-3) / **参照:** [GuardDuty の複数アカウント](../../../services/threat-detection.md#guardduty-multi-account)

### 問12 {#q12}

GuardDuty の検出結果に応じた通知と自動対応を、組織全体で一か所に置きたいと考えています。メンバーは 100 アカウントあり、利用しているリージョンは東京と大阪の 2 つです。

運用の負荷が最も小さい構成はどれですか。

- A. 各メンバーの各リージョンに、StackSets で EventBridge ルールと Lambda を展開する
- B. 委任管理者の東京と大阪の EventBridge にルールを作る。メンバーの検出結果のイベントも届く
- C. 委任管理者の東京にだけルールを作る。全リージョンの検出結果のイベントが届く
- D. 管理アカウントの EventBridge にルールを作る。組織の検出結果は管理アカウントに集まる

??? success "答えと解説"
    **正解: B**

    管理者アカウントの EventBridge には、メンバーの検出結果のイベントも届きます。GuardDuty はリージョンのサービスなので、ルールはリージョンごとに置きます。

    - A: 誤り。動きますが、各アカウントに展開すると運用の負荷が大きくなります。
    - B: 正しい。
    - C: 誤り。イベントはそのリージョンの EventBridge に届くので、大阪の検出結果が漏れます。
    - D: 誤り。委任管理者を置いた場合の集約先は委任管理者です。管理アカウントで日常の運用をしないのが基本です。

    **スキル:** [1.1.3](../domain1.md#skill-1-1-3) / **参照:** [イベント連携](../../../services/threat-detection.md#guardduty-events)

### 問13 {#q13}

監査チームは、組織の全アカウントと全リージョンの Config ルールの準拠状況を 1 つのアカウントから見たいと考えています。また、ある担当者は「それを設定すれば、同じ画面から非準拠のリソースも修復できる」と話しています。

正しい理解はどれですか。

- A. Config アグリゲーターで閲覧を集約できるが、読み取り専用で修復はできない
- B. Config アグリゲーターで閲覧と修復の両方を各アカウントへ実行できる
- C. CloudTrail の組織の証跡を有効にすると準拠状況が 1 か所に集まり、修復も実行できる
- D. Security Lake のロールアップリージョンに Config の評価結果を集めれば修復も実行できる
