# コンピューティングの強化の問題集

対象の解説: [Systems Manager](../../../services/operations.md#systems-manager)、[EC2 Image Builder](../../../services/operations.md#image-builder)、[IAM](../../../services/iam.md)

すべてオリジナルの問題で、実際の試験問題ではありません。基準は SCS-C03 です。

### 問1 {#q1}

ある会社は EC2 Image Builder で標準 AMI を作ります。次の要件があります。ビルドで作成した AMI を Inspector で検査し、許容を超える重要度の検出結果があればイメージを失敗にすること。このビルド用のアカウントでは Inspector を有効にしたくないこと。スキャンの種類として最も適切なものはどれですか。

- A. `TEST_INSTANCE_CVE` を選び、テストインスタンスの検出結果をビルド後に手で確認する
- B. Inspector を有効にせず、ライフサイクルポリシーの重要度の条件で失敗させる
- C. `ON_DEMAND_AMI_CVE` を選び、スキャン結果の条件を設定する
- D. コンテナイメージのスキャンを選び、AMI を ECR にプッシュしてから検査する

??? success "答えと解説"
    **正解: C**

    オンデマンドの AMI スキャンは、出力の AMI を検査します。Inspector の有効化が不要で、結果の条件でイメージを失敗にできます。

    - A: 誤り。テストインスタンスのスキャンは Inspector の有効化を前提とし、手の確認では要件を満たさない。
    - B: 誤り。ライフサイクルポリシーは古いイメージの廃棄のためのもの。
    - C: 正しい。
    - D: 誤り。AMI は ECR にプッシュするものではない。

    **スキル:** [3.2.1](../domain3.md#skill-3-2-1) / **参照:** [EC2 Image Builder](../../../services/operations.md#image-builder)

### 問2 {#q2}

EC2 Image Builder のパイプラインが、ビルドの段階で失敗するようになりました。ビルド用インスタンスは起動しますが、コンポーネントが実行されないまま失敗します。チームは最近、インフラストラクチャの設定で使うインスタンスプロファイルを最小権限のものに作り直しました。最初に確認すべき点はどれですか。

- A. ロールに `EC2InstanceProfileForImageBuilder` と `AmazonSSMManagedInstanceCore` が付いているか
- B. 組織の SCP で、Image Builder のサービスリンクロールの動作が止められていないか
- C. 配布設定の宛先のアカウントで、AMI の起動の権限が許可されているか
- D. ライフサイクルポリシーで、作成前の古いイメージがまだ削除されていないか

??? success "答えと解説"
    **正解: A**

    Image Builder は Systems Manager でビルド用インスタンスを操作します。インスタンスのロールにこの 2 つのポリシーがないと、コンポーネントを実行できません。

    - A: 正しい。
    - B: 誤り。SCP はサービスリンクロールに効かない。作り直したインスタンスプロファイルが変更点でもある。
    - C: 誤り。配布はビルドの後の段階。
    - D: 誤り。ライフサイクルポリシーはビルドの実行に関わらない。

    **スキル:** [3.2.1](../domain3.md#skill-3-2-1) / **参照:** [EC2 Image Builder](../../../services/operations.md#image-builder)

### 問3 {#q3}

ある組織は標準 AMI を毎週ビルドし、複数のアカウントとリージョンへ配布しています。古いバージョンから新しいインスタンスが起動される監査指摘がありました。古いバージョンの非推奨化、無効化、削除を、配布先のアカウントとリージョンを含めて自動化し、独自のコードは書きません。何を使いますか。

- A. Lambda 関数と EventBridge のスケジュールで、各アカウントの `DeregisterImage` を呼ぶ
- B. Data Lifecycle Manager の EBS スナップショットポリシーで、古いスナップショットを削除する
- C. S3 のライフサイクルルールで、AMI の保存先のオブジェクトを失効させる
- D. EC2 Image Builder のライフサイクルポリシーで、廃棄の規則と配布先を含めて定義する

??? success "答えと解説"
    **正解: D**

    Image Builder のライフサイクルポリシーは、古いイメージと関連リソースの非推奨化、無効化、削除を自動化します。別のアカウント、組織、OU に配布したものやリージョンをまたぐものも対象にできます。

    - A: 誤り。動くが、要件に反してコードを書くことになる。
    - B: 誤り。AMI の非推奨化や配布先の扱いを一括では定義できない。
    - C: 誤り。AMI は利用者が見える S3 オブジェクトとして管理するものではない。
    - D: 正しい。

    **スキル:** [3.2.1](../domain3.md#skill-3-2-1) / **参照:** [EC2 Image Builder](../../../services/operations.md#image-builder)、[AMI の管理](../../../services/operations.md#amis)

### 問4 {#q4}

本番の ECS サービスは ECR の `app:release` というタグでイメージを取得しています。ある開発者のロールが侵害されたときに、検査済みのイメージが同じタグのまま別のイメージに置き換えられるリスクが指摘されました。検査したイメージとタグの対応を保ち、同じタグでのプッシュをレジストリ側で失敗させます。どうしますか。

- A. ECR のライフサイクルポリシーで、`release` タグのイメージの保持数を 1 にする
- B. リポジトリのタグを不変（`IMMUTABLE`）にし、既存のタグでのプッシュを失敗させる
- C. 拡張スキャンをプッシュ時のみに設定して、重大な検出結果があるプッシュを ECR に自動で拒否させる
- D. リポジトリの暗号化をカスタマー管理キーに変更し、キーの利用を本番のロールに限定する

??? success "答えと解説"
    **正解: B**

    タグを不変にすると、既存のタグでプッシュしたときに `ImageTagAlreadyExistsException` が返ります。

    - A: 誤り。古いイメージの整理で、上書きは止まらない。
    - B: 正しい。
    - C: 誤り。スキャンは結果を報告するもので、プッシュの拒否はしない。
    - D: 誤り。保存時の暗号化で、タグの上書きとは関係がない。

    **スキル:** [3.2.1](../domain3.md#skill-3-2-1) / **参照:** [タグと不変タグ](../../../services/containers.md#image-tags)

### 問5 {#q5}

中央のアカウントで作った強化済み AMI を、組織の Workloads OU の全アカウントに使わせます。スナップショットの保管費用は中央のアカウントで負担し、OU に加わった新しいアカウントでも追加の設定なしで使えるようにします。Image Builder の配布設定として適切なものはどれですか。

- A. Workloads OU に起動の権限を与え、AMI は所有者のアカウントに残す
- B. 各アカウントを `targetAccountIds` に列挙して、それぞれのアカウントへ AMI をコピーする
- C. AMI を S3 にエクスポートし、OU の全アカウントにバケットの読み取りを許可する
- D. AMI を公開にしたうえで、各アカウントの利用者に AMI ID を文書で伝える

??? success "答えと解説"
    **正解: A**

    起動の権限を与えると AMI は所有者に残り、スナップショットの費用も所有者が払います。組織と OU にはコピーではなくこの方法で届けます。

    - A: 正しい。
    - B: 誤り。コピーは各アカウントが所有して費用も負担し、新しいアカウントには自動で届かない。
    - C: 誤り。エクスポートしたディスクイメージは、そのまま起動できる AMI の共有にならない。
    - D: 誤り。公開すると組織の外にも見え、強化済みイメージの統制に反する。

    **スキル:** [3.2.1](../domain3.md#skill-3-2-1) / **参照:** [EC2 Image Builder](../../../services/operations.md#image-builder)、[AMI の管理](../../../services/operations.md#amis)

### 問6 {#q6}

Fargate の ECS タスクを起動すると、イメージの取得とシークレットの注入は成功します。しかしコンテナのアプリが S3 を呼ぶと `AccessDenied` になります。アプリの権限はアプリの必要な範囲だけに絞り、ECS エージェントの権限とは分けます。どの設定を変更しますか。

- A. タスク実行ロールに、S3 の読み取りのポリシーを追加する
- B. S3 のバケットポリシーで、ECS のサービスプリンシパルにバケット全体を許可する
- C. ECS のサービスリンクロールに、S3 のポリシーをインラインで追加する
- D. タスクロールを作って S3 の権限を付け、`taskRoleArn` に指定する

??? success "答えと解説"
    **正解: D**

    コンテナのアプリが使うのはタスクロールです。タスク実行ロールは ECS エージェントがイメージの取得やシークレットの注入に使います。

    - A: 誤り。アプリの権限にならない。実行ロールを広げても要件に反する。
    - B: 誤り。サービスプリンシパルへの許可では、アプリの主体の権限にならず、範囲も広い。
    - C: 誤り。サービスリンクロールのポリシーはサービスが定義し、自由に変更できない。
    - D: 正しい。

    **スキル:** [3.2.2](../domain3.md#skill-3-2-2) / **参照:** [タスクロールと実行ロール](../../../services/containers.md#task-role-vs-execution-role)

### 問7 {#q7}

開発者は Lambda 関数をデプロイするときに、チームのロールを渡します。監査で、開発者のポリシーの `iam:PassRole` の `Resource` が `*` なので、管理者ロールを関数に渡して権限を昇格できると指摘されました。デプロイの手順は変えません。最小権限にする修正として正しいものはどれですか。

- A. `iam:PassRole` の `Resource` を対象ロールの ARN にし、`iam:PassedToService` を `lambda.amazonaws.com` に絞る
- B. `iam:PassRole` を外し、開発者に `sts:AssumeRole` を許可して、Lambda の実行ロールを引き受けさせる
- C. `iam:PassRole` に `aws:ResourceTag` の条件を付け、タグが `team=dev` のロールだけを渡せるようにする
- D. Lambda の実行ロールの信頼ポリシーから、`lambda.amazonaws.com` を削除して開発者の主体だけを信頼させる

??? success "答えと解説"
    **正解: A**

    渡せるロールを ARN で限定し、`iam:PassedToService` で渡し先のサービスを絞ります。

    - A: 正しい。
    - B: 誤り。ロールの受け渡しには `iam:PassRole` が必要で、ロールの引き受けでは関数の作成はできない。
    - C: 誤り。公式ドキュメントは、`iam:PassRole` を `ResourceTag` 条件で制御しても確実な結果にならないとしている。
    - D: 誤り。Lambda がロールを引き受けられなくなり、関数が動かない。

    **スキル:** [3.2.2](../domain3.md#skill-3-2-2) / **参照:** [PassRole](../../../services/iam.md#passrole)、[Lambda の実行ロール](../../../services/iam.md#lambda-execution-role)

### 問8 {#q8}

EKS クラスターに、EC2 のマネージドノードの Pod と Fargate の Pod があります。セキュリティレビューで次を求められました。各アプリの Pod に別々の権限を与えること。EC2 ノードの Pod がノードのインスタンスプロファイルを取得できないようにすること。正しい対応を選んでください。（2つ選択）

- A. Fargate の Pod には IRSA を使う
- B. Fargate の Pod には EKS Pod Identity を使う
- C. ノードの起動テンプレートで IMDSv2 を必須にし、ホップ制限を 1 にする
- D. ノードのインスタンスプロファイルに全アプリの権限をまとめて付ける
- E. Pod のセキュリティグループで TCP 443 の送信を拒否して、IMDS への接続を止める

??? success "答えと解説"
    **正解: A, C**

    EKS Pod Identity は Fargate の Pod に対応しないので、IRSA を使います。IMDSv2 とホップ制限 1 にすると、コンテナから IMDS に届かなくなります。

    - A: 正しい。
    - B: 誤り。Fargate の Pod は Pod Identity の対象外。
    - C: 正しい。
    - D: 誤り。全 Pod が同じ権限を持ち、要件に反する。
    - E: 誤り。IMDS はリンクローカルアドレスの HTTP で、443 の拒否では止まらず、AWS の API の呼び出しも止まる。

    **スキル:** [3.2.2](../domain3.md#skill-3-2-2) / **参照:** [Pod の IAM](../../../services/containers.md#pod-identity)、[IMDS](../../../services/iam.md#imds)

### 問9 {#q9}

ある Web アプリに SSRF の脆弱性が見つかり、IMDS からロールの認証情報が取られるリスクが報告されました。セキュリティチームは、リージョン内で新しく起動するインスタンスをすべて IMDSv2 にします。あるチームの起動テンプレートは `HttpTokens=optional` を明示していて、この場合は起動自体を失敗させます。どの設定が最も適切ですか。

- A. AMI の `ImdsSupport` を `v2.0` にして、組織の標準 AMI に登録する
- B. アカウントの既定の `HttpTokens` を `required` にして、優先順位で全インスタンスに適用させる
- C. アカウントレベルの IMDSv2 の強制（`httpTokensEnforced`）を有効にする
- D. Config ルールで `HttpTokens` を評価して、非準拠のインスタンスを記録する

??? success "答えと解説"
    **正解: C**

    起動時の指定は、アカウントの既定や AMI の設定より優先されます。アカウントレベルの強制は優先順位の決定の後に評価され、IMDSv1 が有効なインスタンスの起動を失敗させます。

    - A: 誤り。起動テンプレートの明示の値が優先される。
    - B: 誤り。既定値も起動テンプレートの明示の値に上書きされる。
    - C: 正しい。
    - D: 誤り。検出するだけで、起動は止めない。

    **スキル:** [3.2.2](../domain3.md#skill-3-2-2) / **参照:** [IMDS](../../../services/iam.md#imds)、[インスタンスプロファイル](../../../services/iam.md#instance-profile)

### 問10 {#q10}

組織の SCP で `ec2:RunInstances` を特定の AMI 以外で拒否しました。ところが、あるアカウントで Auto Scaling のサービスリンクロールによるインスタンスの起動は、この SCP に止められませんでした。担当者は原因を調べています。説明として正しいものはどれですか。

- A. SCP はリージョンごとの設定で、Auto Scaling を使うリージョンでは未適用だった
- B. SCP はサービスリンクロールに効かないので、この操作は SCP の対象にならない
- C. Auto Scaling グループの起動テンプレートが `AdministratorAccess` を持つと SCP は無視される
- D. Auto Scaling はサービスリンクロールの代わりにユーザーの権限を使うので、ユーザーが明示的に許可されていれば通る

??? success "答えと解説"
    **正解: B**

    サービスリンクロールは SCP の制限を受けません。ガードレールを設計するときの例外として押さえます。

    - A: 誤り。SCP はグローバルに定義して組織の単位に付ける。リージョン単位の適用ではない。
    - B: 正しい。
    - C: 誤り。どのような許可があっても SCP の上限は超えられないので、説明にならない。
    - D: 誤り。SCP の拒否は明示的な許可より優先されるので、説明にならない。

    **スキル:** [3.2.2](../domain3.md#skill-3-2-2) / **参照:** [サービスロール](../../../services/iam.md#service-linked-roles)、[権限境界と SCP](../../../services/iam.md#boundaries-scp)

### 問11 {#q11}

20 のアカウントと 4 つのリージョンで EC2 を運用しています。パッチのスキャンと適用を組織全体で一元管理し、新しいアカウントにも同じ設定を適用します。AWS の推奨に沿い、各リージョンの個別の設定はできるだけ避けます。どの方法を選びますか。

- A. 各アカウントとリージョンに、Maintenance Windows を CloudFormation で作成する
- B. 各アカウントとリージョンに、State Manager の関連付けを手動で作成する
- C. Quick Setup のパッチポリシーを作り、組織の対象のアカウントとリージョンに展開する
- D. 中央のアカウントから毎週 Patch now を実行して、全アカウントを順に指定する

??? success "答えと解説"
    **正解: C**

    Maintenance Windows、State Manager の関連付け、Patch now は 1 つのアカウントとリージョンの組に限られます。パッチポリシーは組織の複数アカウントと複数リージョンを扱え、AWS が推奨しています。

    - A: 誤り。リージョンごとの構成が増え、新しいアカウントへの展開も別に要る。
    - B: 誤り。1 つのアカウントとリージョンの組に限られる。
    - C: 正しい。
    - D: 誤り。Patch now も単一のアカウントとリージョンの組で、定期の統制に向かない。

    **スキル:** [3.2.4](../domain3.md#skill-3-2-4) / **参照:** [Patch Manager](../../../services/operations.md#patch-manager)、[実行の方法](../../../services/operations.md#patch-methods)

### 問12 {#q12}

- B. カスタムパッチベースラインを作り、Critical のセキュリティパッチの自動承認の待機を短くする

ゼロデイの脆弱性の修正パッチが公開されました。1 つのアカウントとリージョンの数十台に、次の定期実行を待たず今すぐ適用します。スケジュールを新しく作りたくありません。修正の承認に使うベースラインは準備済みです。最も適切なものはどれですか。

### 問14 {#q14}

Auto Scaling グループの Web サーバーは数日で入れ替わるので、起動時に古い AMI へ戻ると、パッチが当たっていない状態に戻ります。監査では、脆弱性の修正が実際に完了したことも継続的に確認するよう求められました。運用の手間が少ない組み合わせを選んでください。（2つ選択）

- A. EC2 Image Builder でパッチ済み AMI を定期的に作り、インスタンスの更新で入れ替える
- B. 各インスタンスの起動時のユーザーデータで `yum update` を実行し、失敗は無視する
- C. Inspector を有効にし、修正された脆弱性の検出結果が Closed になることで確認する
- D. Config の `required-tags` ルールで、パッチ済みを示すタグのないインスタンスを検出する
- E. インスタンスに終了保護を付けて入れ替えを止め、手作業でパッチを当て続ける

??? success "答えと解説"
    **正解: A, C**

    パッチ済みイメージで入れ替えると、起動のたびに古い状態へ戻ることを防げます。Inspector は修正を確認すると検出結果を Closed にします。

    - A: 正しい。
    - B: 誤り。起動ごとに差が出て、失敗を無視すると未適用のまま動く。
    - C: 正しい。
    - D: 誤り。タグは自己申告で、脆弱性の修正の確認にならない。
    - E: 誤り。終了保護は Auto Scaling による終了を防がず、手作業は運用の手間を増やす。

    **スキル:** [3.2.4](../domain3.md#skill-3-2-4) / **参照:** [インスタンスの更新](../../../services/operations.md#instance-refresh)、[検出結果と管理](../../../services/threat-detection.md#inspector-findings)

### 問15 {#q15}

プライベートサブネットの Linux サーバーに管理者がアクセスします。監査の要件は、インバウンドポートを開けないこと、SSH 鍵を配らないこと、実行したコマンドと出力を S3 に残すことです。管理者の接続方法として正しいものはどれですか。

- A. Session Manager のシェルのセッションを使い、セッションのログの出力先に S3 を設定する
- B. Session Manager の SSH セッションを使い、セッションのログの出力先に S3 を設定する
- C. EC2 Instance Connect Endpoint を使い、VPC フローログを S3 に保存する
- D. 踏み台サーバーを置き、CloudTrail のデータイベントを有効にして S3 に保存する

    Session Manager のシェルのセッションはポートも SSH 鍵も不要で、コマンドと出力をログに残せます。ログは既定でオフなので、設定が必要です。

### 問16 {#q16}

Session Manager のログを S3 に残しています。監査で、一部の管理者のセッションの内容がログにないと指摘されました。調べると、彼らは `AWS-StartSSHSession` と `AWS-StartPortForwardingSession` を使っていました。管理者に使わせるのはシェルのセッションだけにします。最も適切な修正はどれですか。

- A. S3 バケットの暗号化をカスタマー管理キーに変更し、キーの権限を監査チームに限定する
- B. セッションの設定のアイドルタイムアウトを 5 分に短くして、長いセッションが起きないようにする

### 問18 {#q18}

パブリック IP を持たない Windows インスタンスに、運用者が手元の RDP クライアントで接続します。VPN と踏み台は使いません。権限は特定の運用者に、RDP のポートだけ、接続は 30 分までに絞ります。適切な構成はどれですか。

### 問19 {#q19}

Linux の開発環境で EC2 Instance Connect を使っています。SSH クライアントは既存のものを使い続けます。長期の SSH 鍵は配りません。開発者は `ec2-user` でのみ、`Env=dev` のタグが付いたインスタンスにだけ接続できるようにします。正しい設定はどれですか。

- A. 共通の秘密鍵を Secrets Manager に置き、開発者には取得の権限だけを与える
- B. `ec2:RunInstances` に `ec2:osuser` の条件を付け、`Env=dev` のインスタンスだけを起動させる
- C. `SendSSHPublicKey` を許可し、`ec2:osuser` とリソースタグの条件で絞る
- D. `ssm:StartSession` を `ec2-user` に限定し、セッションのドキュメントで鍵を指定する

    - B: 誤り。接続ではなく起動の権限。
    - C: 正しい。
    - D: 誤り。Session Manager の権限で、既存の SSH クライアントでの接続の認可にならない。
