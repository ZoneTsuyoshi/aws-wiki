# 検出結果の検証と封じ込めの問題集

対象の解説: [インシデント対応](../../../services/threat-detection.md#incident-response)、[GuardDuty の検出結果](../../../services/threat-detection.md#guardduty-findings)、[ランサムウェアと誤削除の防止](../../../services/resilience.md#immutable-compare)

### 問1 {#q1}

VPC のインターネット向けの通信を、VPN 経由でオンプレミスのゲートウェイから出す構成にしました。その後、`UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS` が繰り返し出ています。送信元はすべて自社のゲートウェイの IP で、活動も正当だと確認できました。今後の通知だけを減らします。最も適切なものはどれですか。

- A. 検出結果の型と API 呼び出し元の IP の 2 つを条件に抑制ルールを作り、この結果だけをアーカイブする
- B. GuardDuty の検出器を対象のリージョンで一度停止して、不要な通知が止まったら再開する運用にする
- C. `UnauthorizedAccess:IAMUser` で始まるすべての検出結果の型を、抑制ルールでアーカイブする
- D. 担当者の通知メールを受信トレイのルールで振り分けて、検出結果自体は今までどおり Security Hub に送る

??? success "答えと解説"
    **正解: A**

    GuardDuty は、この構成の誤検知に、型と API 呼び出し元の IP の 2 つの条件を使う抑制ルールを勧めています。繰り返し誤検知と確認してから、絞った条件で作ります。

    - A: 正しい。
    - B: 誤り。その間のすべての検出ができなくなります。
    - C: 誤り。本物の攻撃の検出結果まで抑制します。
    - D: 誤り。ノイズが SIEM や Security Hub に残り、根本的に減りません。

    **スキル:** [2.2.3](../domain2.md#skill-2-2-3) / **参照:** [抑制ルールとリスト](../../../services/threat-detection.md#guardduty-suppression)

### 問2 {#q2}

EKS クラスターの定期ジョブが、GuardDuty の検出結果を毎日数件出しています。担当者は、EKS に関連する検出結果をすべて抑制する案を出しました。多段階の攻撃の検出は維持したいと考えています。この案の評価と代案として正しいものはどれですか。

- A. 抑制しても Extended Threat Detection は関連付けに使えるので、案のとおりで問題ない
- B. 検出結果の保持が 90 日から短くなるので、案を採用するなら先に全件を S3 へエクスポートする
- C. EKS の Runtime Monitoring を止めれば検出結果がなくなるので、抑制より簡単でよい
- D. 抑制した検出結果は関連付けに使われなくなるので、案は採用せず、ジョブの特定の振る舞いだけに条件を絞る

??? success "答えと解説"
    **正解: D**

    抑制された検出結果は、攻撃シーケンスの関連付けのシグナルになりません。広い抑制は多段階の攻撃の検出を損なうので、特定の振る舞いに絞ります。

    - A: 誤り。アーカイブされた検出結果は関連付けに使われません。
    - B: 誤り。抑制された検出結果もアーカイブの状態で 90 日残ります。また S3 へも送られません。
    - C: 誤り。実行時の脅威を検出できなくなり、要件に反します。
    - D: 正しい。

    **スキル:** [2.2.3](../domain2.md#skill-2-2-3) / **参照:** [抑制ルールとリスト](../../../services/threat-detection.md#guardduty-suppression)、[Extended Threat Detection](../../../services/threat-detection.md#guardduty-extended)

### 問3 {#q3}

GuardDuty が、ある IAM ユーザーのキーについて Medium の検出結果を出しました。普段と違う API の呼び出しです。担当者は、誤検知かどうかを検証します。GuardDuty の案内に沿った判断はどれですか。

- A. Medium は試みだけを示す重要度なので、記録だけ残して、High になるまでは調査を始めなくてよい
- B. 本人に API、時刻、IP を確認して承認された活動かを確かめ、正当と確認できなければ侵害として扱う
- C. 検出結果が出た時点で侵害と確定しているので、本人に確認せず、すぐアカウントを閉鎖する
- D. 検出結果の 90 日の保持が切れるまで待ち、再び同じ検出結果が出なければ誤検知として閉じる

??? success "答えと解説"
    **正解: B**

    Medium は通常からの逸脱です。承認された活動かを確かめ、原因を特定できなければ侵害されたものと考えます。確認する項目は API、時刻、送信元 IP です。

    - A: 誤り。試みだけを示すのは Low です。
    - B: 正しい。
    - C: 誤り。検証せずに閉鎖するのは過剰で、証拠も失う恐れがあります。
    - D: 誤り。待っている間に被害が広がります。

    **スキル:** [2.2.3](../domain2.md#skill-2-2-3) / **参照:** [検出結果](../../../services/threat-detection.md#guardduty-findings)、[認証情報の漏えい](../../../services/threat-detection.md#ir-credentials)

### 問4 {#q4}

ある EC2 のロールの認証情報について、外部の IP からの利用を示す `InstanceCredentialExfiltration.OutsideAWS` が先週出ました。今週は同じ IP からの活動が CloudTrail に続いていますが、新しい検出結果は出ていません。担当者は「検出結果が止まったので収束した」と報告しています。正しい評価はどれですか。

- A. 検出結果が止まったので収束しており、CloudTrail の活動は検出結果と無関係なので調査を閉じてよい
- B. 同じ IP の活動は重要度が下がるだけで、新しい検出結果として Low で必ず出るはずなので、検索し直す
- C. 収束とは言えない。継続する活動は想定内と学習され、検出結果が止まることがあるので、CloudTrail で調べる
- D. 検出結果が止まるのは Extended Threat Detection が有効なときだけなので、まずこの機能を無効にする

??? success "答えと解説"
    **正解: C**

    同じリモートホストからの活動が続くと、機械学習のモデルが想定内と判断し、そのホストでは検出結果を出さなくなることがあります。CloudTrail で活動を確認します。

    - A: 誤り。検出結果がないことは、活動がないことを意味しません。
    - B: 誤り。必ず Low で出るという仕組みではありません。
    - C: 正しい。
    - D: 誤り。この動きは Extended Threat Detection とは関係なく、無効にもしません。

    **スキル:** [2.2.3](../domain2.md#skill-2-2-3) / **参照:** [検出結果](../../../services/threat-detection.md#guardduty-findings)、[CloudTrail の調査](../../../services/threat-detection.md#investigate-cloudtrail)

### 問5 {#q5}

漏えいが確認されたロールについて、影響の範囲を評価します。このロールで実際に何をされたか、さらにこのロールで何ができたかを整理します。使うものを選んでください。（2つ選択）

- A. CloudTrail を、このロールと一時キーで検索する
- B. Inspector の検出結果を、対象のロールの名前で検索する
- C. IAM の権限と Access Advisor で、付与された権限と利用状況を確認する
- D. Trusted Advisor の点検結果で、このロールが操作したリソースの一覧を確認する
- E. WAF のログで、このロールが呼んだ API の一覧と結果を確認する

??? success "答えと解説"
    **正解: A, C**

    実際の操作は CloudTrail で調べます。できたことは、付与された権限と Access Advisor で確認します。

    - A: 正しい。
    - B: 誤り。Inspector はソフトウェアの脆弱性などを見つけるもので、ロールの活動は分かりません。
    - C: 正しい。
    - D: 誤り。Trusted Advisor はロールごとの操作を記録しません。
    - E: 誤り。WAF のログは HTTP リクエストの記録で、IAM の API は記録しません。

    **スキル:** [2.2.3](../domain2.md#skill-2-2-3) / **参照:** [認証情報の漏えい](../../../services/threat-detection.md#ir-credentials)

### 問6 {#q6}

Security Hub に複数の検出結果があります。同じ EC2 に、既知の脆弱性、パブリックからの到達性、機密データへの権限が重なっています。担当者は、実際に悪用されうるものから先に対応したいと考えています。最も役に立つものはどれですか。

- A. Security Hub の露出の検出結果で、脆弱性、到達性、権限のシグナルの組み合わせを確認する
- B. Security Hub CSPM の標準のセキュリティスコアで、数値が低いアカウントから順に対応する
- C. それぞれの検出結果の CVSS スコアを個別に比べて、数値の高い順に作業の順番を決める
- D. Trusted Advisor のセキュリティの点検で、優先度の高いインスタンスを 1 つずつ確認する

??? success "答えと解説"

    露出の検出結果は、脆弱性、設定、脅威、リソースの関係を関連付けて、潜在的なリスクの理解と優先付けに使えます。

    - A: 正しい。
    - B: 誤り。基準への準拠の全体を示すもので、この EC2 のシグナルの組み合わせは分かりません。
    - C: 誤り。個別のスコアでは、組み合わせによるリスクが分かりません。

### 問7 {#q7}

攻撃者のリバースシェルが接続中の EC2 で、隔離用のセキュリティグループに置き換えましたが、接続が切れません。メモリの取得は終わっています。元のルールは特定の IP からの SSH だけを許可していました。すぐに通信を止めるには、どうしますか。

- A. サブネットのネットワーク ACL で攻撃者の IP を拒否する。ステートレスなので追跡中の接続でも通信が止まる
- B. Route 53 の DNS Firewall で攻撃者のドメインを拒否して、確立済みの TCP 接続も切断する
- C. 隔離用のセキュリティグループのルールをもう一度置き換え、インバウンドとアウトバウンドの全ルールを削除し直す
- D. インスタンスのタグを `Isolated` に変えて、Config ルールで隔離の状態を評価して記録する

??? success "答えと解説"
    **正解: A**

    セキュリティグループを変えても、追跡中の接続はタイムアウトするまで切れません。すぐに止めるには、ステートレスのネットワーク ACL を使います。

    - A: 正しい。
    - B: 誤り。名前解決を止めるだけで、確立済みの接続は切れません。
    - C: 誤り。追跡中の接続は、ルールを変えても切れません。
    - D: 誤り。評価するだけで、通信は止まりません。

    **スキル:** [2.2.4](../domain2.md#skill-2-2-4) / **参照:** [EC2 の隔離](../../../services/threat-detection.md#ir-ec2-isolation)、[セキュリティグループとネットワーク ACL](../../../services/networking.md#security-groups-nacls)

### 問8 {#q8}

Auto Scaling グループのインスタンスが侵害されました。担当者は終了保護を有効にして隔離用のセキュリティグループに置き換えました。その後、ヘルスチェックの失敗でインスタンスが終了し、証拠も失われました。次回に向けた正しい手順はどれですか。

- A. 終了保護に加えて停止保護も有効にすれば、Auto Scaling による終了を防げる
- B. 隔離の前にインスタンスをスタンバイにするかデタッチし、ELB の対象からも外す
- C. ヘルスチェックの猶予期間を延ばし、調査が終わるまでは異常と判定されない状態にする
- D. Auto Scaling グループの希望する容量を 0 にして、全インスタンスの置き換えを止めて調査する

??? success "答えと解説"
    **正解: B**

    終了保護と停止保護は、Auto Scaling による終了を防ぎません。スタンバイやデタッチで Auto Scaling の管理から外します。

    - A: 誤り。どちらの保護も Auto Scaling による終了を防ぎません。
    - B: 正しい。
    - C: 誤り。猶予期間は起動直後のための設定で、隔離の手順にはなりません。
    - D: 誤り。容量を 0 にするとインスタンスが終了し、サービスも止まります。

    **スキル:** [2.2.4](../domain2.md#skill-2-2-4) / **参照:** [EC2 の隔離](../../../services/threat-detection.md#ir-ec2-isolation)

### 問9 {#q9}

IAM ユーザーの `AKIA` のキーが漏えいしました。CloudTrail には、そのキーで `CreateUser`、`CreateAccessKey`、`AttachUserPolicy` が呼ばれた記録があります。封じ込めと根絶の対応として最も適切なものはどれですか。

- A. 漏えいしたキーをローテーションし、新しいキーを本人に渡せば、攻撃者の権限もすべて失効する
- B. IAM ユーザーのパスワードだけを変更して、攻撃者のセッションを切断してから経過を監視する
- C. キーを無効化し、攻撃者の作ったユーザー、キー、ポリシーも削除する
- D. `AWSRevokeOlderSessions` のインラインポリシーをユーザーに付け、キーはそのまま利用を続ける

??? success "答えと解説"
    **正解: C**

    長期キーは無効化します。攻撃者は永続化のためにユーザーとキーを作っているので、それらも取り除きます。

    - A: 誤り。攻撃者の作ったユーザーとキーは残ります。
    - B: 誤り。パスワードの変更ではアクセスキーは止まりません。
    - C: 正しい。
    - D: 誤り。セッションの取り消しは、ロールの一時認証情報に使うものです。

    **スキル:** [2.2.4](../domain2.md#skill-2-2-4) / **参照:** [認証情報の漏えい](../../../services/threat-detection.md#ir-credentials)

### 問10 {#q10}

複数の担当者とアプリが同じ IAM ロールを使っています。そのロールの `ASIA` の一時キーが外部で使われていると分かりました。12 時間の長いセッションも残っています。IAM コンソールで **Revoke active sessions** を実行するときの説明として正しいものはどれですか。

- A. 盗まれた一時キーの ID を指定して失効させる操作なので、他の担当者とアプリのセッションには影響しない
- B. ロールを削除して同じ名前で作り直す操作なので、作り直すまでは誰もこのロールを引き受けられない
- C. ロールのポリシーを空にする操作なので、付与していた権限をすべて手で戻すまで新しいセッションも拒否される
- D. 取り消しより前に発行された全セッションを拒否する。正当な利用者も認証情報の再取得が必要になる

??? success "答えと解説"
    **正解: D**

    `AWSRevokeOlderSessions` のインラインポリシーが、指定時刻より前に引き受けたセッションのすべての操作を拒否します。ロールを使う全員が対象で、その後に引き受ければ影響を受けません。実行には `iam:PutRolePolicy` が必要です。

    - A: 誤り。キーの単位ではなく、ロールのセッション全体が対象です。
    - B: 誤り。ロールは削除しません。
    - C: 誤り。新しいセッションは影響を受けません。
    - D: 正しい。

    **スキル:** [2.2.4](../domain2.md#skill-2-2-4) / **参照:** [認証情報の漏えい](../../../services/threat-detection.md#ir-credentials)

### 問11 {#q11}

IAM Identity Center の権限セットから作られたロールのセッションが不正に使われた疑いがあります。担当者はそのアカウントの IAM コンソールでセッションの取り消しを試みましたが、ロールを編集できません。正しい対応はどれですか。

- A. そのロールを IAM で削除して、同じ権限のロールを手作業で作り直してから権限セットと関連付ける
- B. IAM Identity Center で、対象のユーザーのアクティブな権限セットのセッションを取り消す

    - D: 誤り。取り消す方法があります。

### 問12 {#q12}

メンバーアカウントで管理者権限が奪われ、攻撃者がリソースを次々に作っています。調査のため、ログと既存のリソースは残したまま、そのアカウントでの新たな操作を組織の側からすぐに止めます。最も適切な方法はどれですか。

- A. アカウントを閉鎖して、全リソースと証拠を消した後に新しいアカウントで作り直す
- B. アカウントを組織から削除すれば、SCP の制限なしで調査を始められ、攻撃者の権限もなくなる
- C. 全アクションを拒否する SCP をアカウントに適用するか、Suspended OU へ移す
- D. Config の適合パックを適用し、攻撃者が作ったリソースの非準拠を担当者へ通知する

    - A: 誤り。証拠を残す条件に反します。
    - B: 誤り。組織の統制から外れ、攻撃者の権限も残ります。
    - C: 正しい。

### 問13 {#q13}

ランサムウェアの攻撃者が本番アカウントの管理者権限を得て、通常のバックアップボールトの復旧ポイントを削除しました。別に用意していた論理的にエアギャップされたボールトには、復旧ポイントが残っています。本番アカウントはまだ信頼できません。正しい復旧の進め方はどれですか。

- A. 本番アカウントで同じ権限のまま復旧ポイントから復元して、そのままサービスを再開する
- B. ボールトの Vault Lock を解除して復旧ポイントをコピーし、攻撃者の権限を外してから本番へ戻す
- C. Recycle Bin から本番の復旧ポイントを戻し、通常のボールトへ再びコピーしてから復元する
- D. AWS RAM などでボールトを別の復旧用アカウントへ共有し、そこで復元して検証する

??? success "答えと解説"
    **正解: D**

    論理的にエアギャップされたボールトのバックアップは、AWS RAM や Multi-party approval で別のアカウントへ共有し、そこから復元できます。信頼できないアカウントの外で復元します。

    - A: 誤り。攻撃者の権限が残るアカウントに戻すと、再び侵害されます。
    - B: 誤り。このボールトにはコンプライアンスモードの Vault Lock が自動で適用され、解除できません。
    - C: 誤り。Recycle Bin の対象は EBS ボリューム、EBS スナップショット、EBS-backed AMI で、バックアップボールトの復旧ポイントは戻せません。
    - D: 正しい。

    **スキル:** [2.2.4](../domain2.md#skill-2-2-4) / **参照:** [論理的にエアギャップされたボールト](../../../services/resilience.md#logically-air-gapped)

### 問14 {#q14}

Web サーバーが、既知の脆弱性を突かれて侵害されました。調査と証拠の取得は終わりました。ロールには Secrets Manager の DB の認証情報を読む権限があり、読み取りの記録が攻撃者の IP で残っています。根絶と復旧として適切なものを選んでください。（2つ選択）

- A. 検証済みの AMI から作り直し、脆弱性を修正したイメージを使う
- B. マルウェアを手で削除し、同じインスタンスを隔離から戻してサービスを再開する
- C. 読み取られた DB の認証情報をローテーションする
- D. 検出結果をアーカイブして、今後の通知が出ないようにすれば根絶の完了とする
- E. 侵害の直前に取得したスナップショットから、検査や修正をせずに同じ設定で起動する

??? success "答えと解説"
    **正解: A, C**

    取り除けたと確信できないインスタンスは作り直します。脆弱性を直さなければ再び侵害されます。読まれた認証情報は漏えいしたものとして扱います。

    - A: 正しい。
    - B: 誤り。見つかっていない不正なものが残る恐れがあります。
    - C: 正しい。
    - D: 誤り。通知を消しても原因は残ります。
    - E: 誤り。脆弱性が残るので、同じ方法で再び侵害されます。
