# 保存時のデータの問題集

対象の解説: [S3 の暗号化オプション](../../../services/kms.md#s3-encryption)、[Object Lock](../../../services/s3.md#object-lock)、[AWS Backup](../../../services/resilience.md#backup)

### 問1 {#q1}

規制の要件で、S3 のオブジェクトに 2 層の暗号化を適用し、鍵の利用を CloudTrail で監査します。担当者は費用削減のため S3 バケットキーの併用も提案しています。正しい判断はどれですか。

- A. SSE-KMS を 2 回適用する設定にして、バケットキーで費用を抑える
- B. DSSE-KMS を選び、バケットキーは DSSE-KMS で使えないので費用は別の方法で検討する
- C. SSE-S3 と SSE-C を同じオブジェクトに同時に適用して、それぞれの鍵で 2 層にする
- D. クライアント側で 2 回暗号化し、CloudTrail の監査はアプリのログで代替する

??? success "答えと解説"
    **正解: B**

    DSSE-KMS は 2 層の暗号化を適用します。S3 バケットキーは DSSE-KMS に対応していません。

    - A: 誤り。SSE-KMS を 2 回適用する設定はありません。
    - B: 正しい。
    - C: 誤り。同じオブジェクトに同時には適用できません。
    - D: 誤り。CloudTrail での鍵の監査の要件を満たしません。

    **スキル:** [5.2.1](../domain5.md#skill-5-2-1) / **参照:** [S3 の暗号化オプション](../../../services/kms.md#s3-encryption)

### 問2 {#q2}

S3 の SSE-KMS の暗号化コンテキストをオブジェクトの ARN に限定する IAM 条件を、既存のロールで使っています。KMS の費用を下げるため、バケットで S3 バケットキーを有効にしました。その後、新しいオブジェクトの読み書きでアクセス拒否が出ました。原因と対応はどれですか。

- A. バケットキーを有効にすると、既存のオブジェクトの再暗号化が始まり、完了までアクセスできなくなる
- B. 暗号化コンテキストがバケットの ARN に変わるので、条件を合わせて変更する
- C. バケットキーでは KMS の権限が不要になるので、ロールの KMS の権限を外すと解決する
- D. バケットキーは AWS 管理キーでだけ有効なので、カスタマー管理キーからの切り替えが必要になる

??? success "答えと解説"
    **正解: B**

    バケットキーを使うと、KMS に渡す暗号化コンテキストがオブジェクトの ARN からバケットの ARN に変わります。依存するポリシーを修正します。

    - A: 誤り。既存のオブジェクトは自動で再暗号化されません。
    - B: 正しい。
    - C: 誤り。バケットキーの生成などに KMS の権限が必要です。
    - D: 誤り。カスタマー管理キーで使えます。

    **スキル:** [5.2.1](../domain5.md#skill-5-2-1) / **参照:** [S3 バケットキー](../../../services/s3.md#bucket-key)

### 問3 {#q3}

データベースベンダーの製品で TDE を使います。ベンダーの製品は PKCS#11 で鍵を扱う必要があり、単一テナントの HSM が条件です。S3 や EBS のような AWS サービスとの統合は問いません。最も適切なものはどれですか。

- A. KMS のカスタマー管理キーを使い、キーポリシーで製品のロールだけを許可する
- B. 2 台以上の CloudHSM クラスターを PKCS#11 で使う
- C. KMS の外部キーストアを作成し、社内の HSM をベンダー製品に接続する
- D. KMS の AWS 所有キーを使い、製品に鍵の管理を任せる

??? success "答えと解説"
    **正解: B**

    PKCS#11 と単一テナントの HSM が条件なら CloudHSM です。可用性の設計は利用者の責任なので、2 台以上にします。

    - A: 誤り。KMS は PKCS#11 のインターフェイスを提供しません。
    - B: 正しい。
    - C: 誤り。外部キーストアは KMS の API の統合のためのもので、この要件には合いません。
    - D: 誤り。AWS 所有キーは製品から使えず、単一テナントでもありません。

    **スキル:** [5.2.1](../domain5.md#skill-5-2-1) / **参照:** [KMS との比較](../../../services/identity-directory.md#cloudhsm-vs-kms)

### 問4 {#q4}

ある会社は、S3 に保存する医療データを AWS に平文で渡さないことを求められています。処理は社内のアプリだけが行います。鍵の管理は KMS に任せてもかまいません。2026 年に新しく作ったバケットです。最も適切な方式はどれですか。

- A. SSE-C で、リクエストごとに自社の鍵を渡す。新しいバケットでは既定で使える
- B. SSE-KMS で、カスタマー管理キーのキーポリシーで社内のアプリだけに許可する
- C. AWS Encryption SDK でアプリ内で暗号化してから S3 へアップロードする
- D. DSSE-KMS で 2 層に暗号化して、AWS の担当者が見られないようにする

??? success "答えと解説"
    **正解: C**

    AWS に平文を渡さないならクライアント側の暗号化です。SDK が KMS のデータキーを使うので、鍵の管理は KMS に任せられます。

    - A: 誤り。SSE-C は平文を S3 へ送ります。2026 年 4 月以降の新しいバケットでは既定で無効です。
    - B: 誤り。サーバー側の暗号化なので、平文が S3 に届きます。
    - C: 正しい。
    - D: 誤り。サーバー側の暗号化なので、平文が S3 に届きます。

    **スキル:** [5.2.1](../domain5.md#skill-5-2-1) / **参照:** [クライアント側とサーバー側](../../../services/kms.md#client-vs-server-side)

### 問5 {#q5}

金融の規制で、取引記録を 7 年間、ルートユーザーを含めて誰も削除できないようにします。また、別の訴訟案件で、一部のオブジェクトを期限なしで保全し、案件が終われば外せるようにします。Object Lock の設定の組み合わせはどれですか。（2つ選択）

- A. 取引記録にコンプライアンスモードで 7 年の保持期間を設定する
- B. 取引記録にガバナンスモードで 7 年の保持期間を設定し、`s3:BypassGovernanceRetention` をルートにだけ許可する
- C. 訴訟の対象にリーガルホールドを設定し、`s3:PutObjectLegalHold` を持つ担当者が案件後に外す

- E. バケットのバージョニングを無効にしてから Object Lock を有効にする

    - C: 正しい。

### 問6 {#q6}

Lambda 関数に AWS Signer の署名を必須にしました。コード署名の設定を関数に追加しましたが、未署名のコードのデプロイが成功し続け、すでに動いている未署名のコードも止まりません。説明と修正の組み合わせとして正しいものはどれですか。

- A. 既定の `Warn` を `Enforce` に変える。動いているコードは次のデプロイから検証される
- B. コード署名は Lambda の実行のたびに検証されるので、未署名のコードは次の呼び出しから自動で止まり、未署名のデプロイも順に拒否されるのを待つ
- C. コード署名の設定はレイヤーにしか適用されないので、関数のコードをレイヤーに移す
- D. KMS キーでコードを暗号化すれば、未署名のコードが自動で拒否されるようになる

??? success "答えと解説"
    **正解: A**

    既定の `Warn` は記録するだけです。`Enforce` にするとデプロイをブロックします。署名の設定は新しいデプロイを制御するので、既存の未署名のコードは次のデプロイまで動きます。

    - A: 正しい。
    - B: 誤り。検証はデプロイ時で、実行時ではありません。
    - C: 誤り。関数のコード自体が対象で、レイヤーにも署名が求められます。
    - D: 誤り。暗号化と署名の検証は別です。

    **スキル:** [5.2.2](../domain5.md#skill-5-2-2) / **参照:** [Lambda のコード署名](../../../services/lambda.md#code-signing)

### 問7 {#q7}

監査人が「CloudTrail のログが配信後に変更または削除されていないこと」の証明を求めています。ログは S3 にあります。適切な方法はどれですか。

- A. ログのバケットのバージョニングの履歴をすべてエクスポートし、変更がないことを手で確認して報告書にする
- B. ログファイルの検証を有効にし、ダイジェストを使って `validate-logs` で確認する
- C. S3 のサーバーアクセスログから、ログのオブジェクトへの書き込みがないことを確認する
- D. KMS でログを暗号化すれば、暗号文が壊れないことをもって完全性の証明にする

??? success "答えと解説"
    **正解: B**

    ログファイルの検証は SHA-256 のハッシュと RSA の署名を使い、ログの変更や削除を検出します。

    - A: 誤り。バージョニングは署名付きの証明にはなりません。
    - B: 正しい。
    - C: 誤り。サーバーアクセスログはベストエフォートで、証明になりません。
    - D: 誤り。暗号化は改ざんの有無の証明になりません。

    **スキル:** [5.2.2](../domain5.md#skill-5-2-2) / **参照:** [CloudTrail の調査](../../../services/threat-detection.md#investigate-cloudtrail)

### 問8 {#q8}

オンプレミスの NAS から EFS へ DataSync で規制データを移行します。監査は「転送したファイルが宛先で一致すること」の確認を求めています。ただし宛先の全ファイルの走査で時間が延びるのは避けます。適切な設定はどれですか。

- A. `VerifyMode` を `ONLY_FILES_TRANSFERRED` にする
- B. 転送後に Athena で両方のファイル一覧を比較し、結果を CloudWatch のメトリクスへ送信する
- C. `VerifyMode` を `NONE` にして、転送中のチェックサムの結果だけをログに残す

EBS ボリュームのバックアップを AWS Backup で別のアカウントへコピーしたところ、失敗しました。送信元のボリュームは `aws/ebs` の AWS 管理キーで暗号化されています。修正として最も適切なものはどれですか。

- A. `aws/ebs` のキーポリシーを編集し、送信先のアカウントに使用を許可する
- B. 送信先のボールトを送信元と同じリージョンに作り直すと、キーの制約がなくなる
- C. カスタマー管理キーのボリュームに移し、キーを送信先と共有する
- D. バックアップ計画のコピー設定に、送信先のアカウントのアクセスキーを指定する

??? success "答えと解説"
    **正解: C**

    AWS 管理キーのポリシーは変更できず、別のアカウントに共有できません。カスタマー管理キーで暗号化し、キーを共有します。

    - A: 誤り。AWS 管理キーのポリシーは変更できません。
    - B: 誤り。リージョンの問題ではありません。
    - C: 正しい。
    - D: 誤り。コピーの設定にアクセスキーは使いません。
