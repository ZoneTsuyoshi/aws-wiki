# フォレンジックとログ調査の問題集

対象の解説: [フォレンジックの証拠](../../../services/threat-detection.md#ir-forensics)、[ログの調査](../../../services/threat-detection.md#log-investigation)、[Detective](../../../services/threat-detection.md#detective)

### 問1 {#q1}

GuardDuty が本番の EC2 で暗号通貨の採掘を検出しました。法務部は、メモリ上の証拠を含めて保全するよう求めています。インスタンスは SSM Agent で管理されています。最初の取得の進め方として最も適切なものはどれですか。

- A. 被害を止めるためインスタンスを停止し、起動し直してからメモリのダンプを取得する
- B. EBS スナップショットだけ取得してインスタンスを終了し、メモリの内容はディスクから復元する
- C. 再起動でプロセスの状態を整理してから、Session Manager で手作業のダンプを取得する
- D. 実行中のまま Run Command で取得ツールを実行し、メモリの内容を証拠用の S3 に保存する

??? success "答えと解説"
    **正解: D**

    メモリの内容は停止すると失われます。停止や終了の前に、実行中のまま取得します。

    - A: 誤り。停止した時点でメモリの内容が消えます。
    - B: 誤り。メモリの内容は EBS スナップショットに含まれません。
    - C: 誤り。再起動でメモリの内容が失われます。
    - D: 正しい。

    **スキル:** [2.2.1](../domain2.md#skill-2-2-1) / **参照:** [フォレンジックの証拠](../../../services/threat-detection.md#ir-forensics)、[Run Command](../../../services/operations.md#run-command)

### 問2 {#q2}

侵害された EC2 の EBS スナップショットを、同じリージョンのフォレンジック用アカウントへ渡します。ボリュームは既定の AWS 管理キー（`aws/ebs`）で暗号化されています。共有の操作でエラーになりました。正しい手順はどれですか。

- A. `aws/ebs` のキーポリシーを編集してフォレンジック用アカウントを追加し、そのまま共有する
- B. カスタマー管理キーで暗号化したスナップショットのコピーを作り、キーとコピーの両方を共有する
- C. スナップショットをパブリックに共有し、フォレンジック用アカウントがコピーしたら元に戻す
- D. ボリュームの暗号化を解除した平文のスナップショットを作成して、暗号化なしで共有する

??? success "答えと解説"
    **正解: B**

    AWS 管理キーで暗号化したスナップショットは共有できません。カスタマー管理キーで暗号化したコピーを作り、スナップショットとキーを共有します。

    - A: 誤り。AWS 管理キーのポリシーは変更できません。
    - B: 正しい。
    - C: 誤り。パブリックに共有できるのは暗号化されていないスナップショットだけで、証拠を公開することにもなります。
    - D: 誤り。この手順では暗号化を解除できず、証拠を平文で扱うことも避けます。

    **スキル:** [2.2.1](../domain2.md#skill-2-2-1) / **参照:** [フォレンジックの証拠](../../../services/threat-detection.md#ir-forensics)、[スナップショット](../../../services/storage.md#ebs-snapshots)

### 問3 {#q3}

東京リージョンの EC2 が侵害されました。調査環境は大阪リージョンのフォレンジック用アカウントにあります。スナップショットはカスタマー管理キーで暗号化されています。証拠を調査環境へ渡す方法として正しいものはどれですか。

- A. 東京のスナップショットを大阪のアカウントと共有すれば、大阪のリージョンでもそのまま一覧に現れる
- B. 東京のキーをマルチリージョンキーへ変換してから、スナップショットを共有すれば大阪から直接使える
- C. Recycle Bin にスナップショットを移せば、リージョンをまたいでフォレンジック用アカウントから復元できる
- D. スナップショットを大阪のリージョンへコピーし、コピーと、その暗号化に使ったカスタマー管理キーを共有する

??? success "答えと解説"
    **正解: D**

    スナップショットは作成したリージョンに限られます。別のリージョンで使うには、そのリージョンへコピーしてからコピーを共有します。暗号化されたものを共有するときは、使ったカスタマー管理キーも共有します。

    - A: 誤り。共有はリージョンを越えません。
    - B: 誤り。既存のキーはマルチリージョンキーに変換できません。
    - C: 誤り。Recycle Bin は削除したものを復元する機能です。
    - D: 正しい。

    **スキル:** [2.2.1](../domain2.md#skill-2-2-1) / **参照:** [スナップショット](../../../services/storage.md#ebs-snapshots)、[フォレンジックの証拠](../../../services/threat-detection.md#ir-forensics)

### 問4 {#q4}

GuardDuty の Malware Protection for EC2 を使っています。マルウェアが見つかったときのスナップショットを証拠に残したいのですが、前回の事象ではスキャンの後に残っていませんでした。正しい理解と設定はどれですか。

- A. 既定で保持されるので、スナップショットを消した主体を CloudTrail で調べ、その権限を SCP で拒否する
- B. スキャンの完了後に保持の設定を有効にすれば、直前のスキャンのスナップショットも遡って保持される
- C. スキャンの前に保持の設定を有効にする。マルウェアが見つかった場合に保持され、費用が発生する
- D. 保持の設定を有効にすると、マルウェアの有無を問わず全スキャンのスナップショットが永久に残る

??? success "答えと解説"
    **正解: C**

    保持の設定は既定でオフです。スキャンの開始前に有効にしていて、マルウェアが見つかった場合にだけ残ります。保持には EBS スナップショットの費用がかかります。

    - A: 誤り。既定はオフなので、消されたわけではありません。
    - B: 誤り。スキャンの開始前に有効にしておく必要があります。
    - C: 正しい。
    - D: 誤り。マルウェアが見つからなければ残りません。

### 問5 {#q5}

訴訟に備えて、CloudTrail のログが配信の後に変更も削除もされていないことを示し、保存期間中は誰にも消されないようにします。組織の証跡はログ専用アカウントの S3 に出力しています。どの対策が必要ですか。（2つ選択）

- A. ログファイルの検証を有効にし、`validate-logs` で確認する
- B. 証跡のログを SSE-KMS で暗号化すれば、ダイジェストがなくても改ざんの有無を証明できる
- C. バケットをコンプライアンスモードの Object Lock で保護する
- D. CloudWatch Logs に配信して、データ保護ポリシーを設定することで証拠の完全性を保証する
- E. Config のタイムラインにログファイルの変更履歴を記録し、これを証拠として提出する

??? success "答えと解説"
    **正解: A, C**

    ログファイルの検証は SHA-256 と署名で変更や削除を検出します。有効にするだけでなく、コマンドで確認します。コンプライアンスモードの Object Lock は、ルートユーザーでも保持期間中は消せません。

    - A: 正しい。
    - B: 誤り。暗号化は機密性の対策で、改ざんの証明にはなりません。
    - C: 正しい。
    - D: 誤り。データ保護ポリシーは機密データのマスクで、完全性の証明にはなりません。
    - E: 誤り。ログファイルの変更履歴の証明にはならず、検証の代わりになりません。

    **スキル:** [2.2.1](../domain2.md#skill-2-2-1) / **参照:** [CloudTrail の調査](../../../services/threat-detection.md#investigate-cloudtrail)、[Object Lock](../../../services/s3.md#object-lock)

### 問6 {#q6}

フォレンジック用アカウントで、侵害された EC2 のディスクを分析します。分析中に、マルウェアが外部と通信したり、本番へ広がったりしないようにします。最も適切な環境はどれですか。

- A. 侵害されたインスタンスにログインし、調査ツールを導入してその場で分析を実行する
- B. 本番の VPC にピアリングした VPC で、元のボリュームから調査用インスタンスを起動する
- C. 隔離された VPC で調査用 EC2 を起動し、スナップショットから作ったボリュームを接続する
- D. インターネットに公開したサブネットで調査用 EC2 を起動し、最新の定義ファイルで検査する

??? success "答えと解説"
    **正解: C**

    調査はフォレンジック用アカウントの隔離された VPC で行います。スナップショットから作ったボリュームなら、元の証拠も変わりません。

    - A: 誤り。ツールの導入と操作で証拠が変わります。
    - B: 誤り。本番への経路があり、元のボリュームから起動すると不審なコードも動きます。
    - C: 正しい。
    - D: 誤り。外部と通信できる環境では条件を満たしません。

### 問7 {#q7}

Auto Scaling グループのインスタンスは、数時間で入れ替わることがあります。アプリケーションと OS のログはローカルのディスクにあり、前回の事象では、調査の前にインスタンスと一緒に失われました。事前の準備として最も適切なものはどれですか。

- A. 事象が起きたら Run Command で全インスタンスからログを集める手順を作り、入れ替え前に担当者が実行する
- B. CloudWatch エージェントでログを常時送り、ログ保管アカウントの S3 にエクスポートして Object Lock で保護する
- C. インスタンスの終了保護を有効にすれば、Auto Scaling の入れ替えの対象から外れ、ログもディスクに残り続ける
- D. CloudTrail のデータイベントを全サービスで有効にして、インスタンスのログファイルも証跡に記録する

??? success "答えと解説"
    **正解: B**

    短命なインスタンスのログは、失われる前に外へ送り続けます。保管先を別のアカウントにして Object Lock で保護すれば、攻撃者にも消されません。

    - A: 誤り。事象の検知より先に入れ替わると失われます。
    - B: 正しい。
    - C: 誤り。終了保護は Auto Scaling による終了を防ぎません。
    - D: 誤り。CloudTrail は API の記録で、OS やアプリのログファイルは記録しません。

    **スキル:** [2.2.1](../domain2.md#skill-2-2-1) / **参照:** [CloudWatch エージェント](../../../services/operations.md#cloudwatch-agent)、[Object Lock](../../../services/s3.md#object-lock)

### 問9 {#q9}

CloudTrail に `ASIA` で始まるキーの不審な操作が残っていました。どのロールから発行された一時認証情報かを特定し、同じロールの他のセッションも調べます。どのフィールドを使いますか。

- A. `userIdentity.sessionContext.sessionIssuer`
- B. `requestParameters.roleArn` の値は、すべてのイベントに必ず含まれる発行元のロールなので、これを使う
- C. `tlsDetails.clientProvidedHostHeader` の値から、発行元のロールとアカウントを推定して絞り込む
- D. `sourceIPAddress` の値を IAM のロール名に対応付けて、同じ IP のものを同じセッションとする

??? success "答えと解説"

    - C: 誤り。TLS 接続の情報で、ロールとは関係ありません。
    - D: 誤り。IP はロールと対応せず、同じセッションの証明にもなりません。

### 問11 {#q11}

EC2 からの DNS トンネリングが疑われます。VPC のフローログを調べましたが、Amazon DNS への通信がどこにも見当たりません。インスタンスは VPC の既定のリゾルバーを使っています。どの判断が正しいですか。

- A. Route 53 Resolver クエリログを調べ、`srcids` のインスタンス ID で関連付ける
- B. フローログのカスタム形式に `pkt-dstaddr` を追加すれば、Amazon DNS への通信も記録されるようになる
- C. Amazon DNS への通信が記録されていないので、このインスタンスからの DNS トンネリングはなかったと判断する

- B. Detective の検出結果グループで、関連する検出結果とエンティティを確認する
- C. 検出結果を S3 にエクスポートして、担当者ごとに分担してスプレッドシートで突き合わせる
- D. GuardDuty の信頼リストにロールの IP を登録し、新しい検出結果が止まるかどうかで判断する

??? success "答えと解説"
    **正解: B**

    検出結果グループは、関連する検出結果と関与するエンティティをまとめ、一連の事象として図示します。同じロールのセッションや同じ IP は、まとめる手がかりになります。

    - A: 誤り。抑制した検出結果は調査や関連付けに使えなくなります。
    - B: 正しい。
    - C: 誤り。手間がかかり、関連付けの機能もありません。
    - D: 誤り。証拠を消すことになり、攻撃者の IP を信頼する危険もあります。

    **スキル:** [2.2.5](../domain2.md#skill-2-2-5) / **参照:** [Detective](../../../services/threat-detection.md#detective)

### 問15 {#q15}

Detective を導入します。担当者の理解を確認しています。VPC にはフローログを設定していないアカウントもあり、Fargate のタスクも動いています。正しい説明を選んでください。（2つ選択）

- A. Detective は独立したストリームでデータを取得するので、既存のフローログの設定は不要で影響も受けない
- B. Detective はフローログを有効にしたアカウントだけを対象にするので、先に全 VPC でフローログを有効にする
- C. Detective のフローログのデータは EC2 のものだけで、Fargate や NAT ゲートウェイの通信は含まれない
- D. Detective は根本原因が判明すると、対象のロールのセッションを自動で取り消して修復する
- E. Detective は検出結果を生成するサービスなので、GuardDuty を止めて置き換えることができる

??? success "答えと解説"
    **正解: A, C**

    Detective は CloudTrail とフローログのイベントを独立した複製のストリームで取得します。フローログのデータは EC2 のものだけです。

    - A: 正しい。
    - B: 誤り。既存の設定を使いません。
    - C: 正しい。
    - D: 誤り。調査のサービスで、修復はしません。
    - E: 誤り。検出は GuardDuty などが担います。

    **スキル:** [2.2.5](../domain2.md#skill-2-2-5) / **参照:** [Detective](../../../services/threat-detection.md#detective)

### 問16 {#q16}

先週、本番のセキュリティグループに `0.0.0.0/0` の SSH が追加され、その後に侵入がありました。根本原因の報告には、ルールがいつどう変わり、誰の操作だったのかが必要です。最小の手間で調べるには、どうしますか。

- A. Config のリソースタイムラインで変更を確認し、関連する CloudTrail のイベントで主体を確認する
- B. Inspector のネットワーク到達性の検出結果から、変更前後の設定と操作した IAM ユーザーを確認する
- C. VPC フローログの `action` を調べ、`ACCEPT` に変わった時刻と IP から変更した担当者を特定する
- D. GuardDuty の `Recon` の検出結果のアーカイブを確認し、変更した主体とルールの差分を読み取る

??? success "答えと解説"
    **正解: A**

    Config は設定がどう変わったかを記録し、タイムラインから CloudTrail のイベントへたどれます。CloudTrail は誰がどの API を呼んだかを示します。

    - A: 正しい。
    - B: 誤り。開いた経路は分かりますが、変更の履歴や主体は分かりません。
    - C: 誤り。フローログは通信の記録で、設定の変更や主体は分かりません。
    - D: 誤り。探査の検出結果で、ルールの変更の記録ではありません。

    **スキル:** [2.2.5](../domain2.md#skill-2-2-5) / **参照:** [Config と CloudTrail の違い](../../../services/governance.md#config-vs-cloudtrail)
