# 鍵と証明書の管理の問題集

対象の解説: [鍵素材のインポート](../../../services/kms.md#imported-key-material)、[マルチリージョンキー](../../../services/kms.md#multi-region-keys)、[Private CA](../../../services/certificates.md#private-ca)

### 問1 {#q1}

規制により、鍵を AWS の外に置き、外部の鍵マネージャーへの接続を切ることでデータを即座に使えなくする必要があります。S3 と EBS は通常の暗号化の統合のまま使います。最も適切な選択はどれですか。

- A. KMS に鍵素材をインポートし、`ValidTo` を短くして定期的に再インポートする
- B. KMS の CloudHSM キーストアを作り、CloudHSM のクラスターで鍵を管理する
- C. KMS の外部キーストアを作り、XKS プロキシで外部の鍵マネージャーと接続する
- D. クライアント側で AWS Encryption SDK を使い、S3 と EBS の暗号化は無効にする

??? success "答えと解説"
    **正解: C**

    外部キーストアは鍵素材を AWS の外に置いたまま KMS の API とサービスの統合を使えます。接続を切ると復号できなくなります。

    - A: 誤り。インポートすると鍵素材のコピーが KMS に渡るので、要件を満たしません。
    - B: 誤り。CloudHSM は AWS の中にあります。
    - C: 正しい。
    - D: 誤り。EBS の暗号化の統合が使えず、条件に反します。

    **スキル:** [5.3.2](../domain5.md#skill-5-3-2) / **参照:** [CloudHSM キーストア](../../../services/identity-directory.md#cloudhsm-key-store)

### 問2 {#q2}

既存の HSM で生成した鍵素材を KMS にインポートします。正しい手順の順序はどれですか。

- A. `ImportKeyMaterial` を呼び、作成されたキーの `Origin` を `EXTERNAL` に変更して、`GetParametersForImport` で検証する
- B. `CreateKey` を既定の `Origin` で呼び、鍵素材を上書きするため `ImportKeyMaterial` を呼ぶ
- C. `GetParametersForImport` でトークンを取り、その後 `CreateKey` で鍵素材を指定して作成する
- D. `CreateKey` を `Origin=EXTERNAL` で呼び、`GetParametersForImport` の公開鍵で鍵素材を暗号化して `ImportKeyMaterial` を呼ぶ

??? success "答えと解説"
    **正解: D**

    鍵素材なしのキーを作り、ラッピング用の公開鍵とインポートトークンを取得し、暗号化した鍵素材をアップロードします。

    - A: 誤り。`Origin` は作成後に変更できず、順序も違います。
    - B: 誤り。`AWS_KMS` のキーには鍵素材をインポートできません。
    - C: 誤り。トークンの取得にはキーが必要です。
    - D: 正しい。

    **スキル:** [5.3.2](../domain5.md#skill-5-3-2) / **参照:** [鍵素材のインポート](../../../services/kms.md#imported-key-material)

### 問3 {#q3}

外部キーストアの導入を検討しています。経営層に、責任の変化を説明します。正しい説明を選んでください。（2つ選択）

- A. 鍵のセキュリティ、可用性、耐久性、遅延の責任が利用者に移り、責任共有モデルが大きく変わる
- B. XKS プロキシは KMS が提供して運用するので、外部の鍵マネージャーだけを管理すればよい
- C. 外部の鍵を失うと、その鍵で保護した暗号文は復元できない
- D. KMS は外部の鍵マネージャーを直接管理し、必要に応じて鍵を作成または削除する
- E. AWS は外部キーストアの可用性について、標準キーストアと同じ SLA を提供する

??? success "答えと解説"
    **正解: A, C**

    外部キーストアは責任共有モデルからの大きな転換です。XKS プロキシも利用者が用意します。KMS は外部の鍵マネージャーと直接やり取りしません。

    - A: 正しい。
    - B: 誤り。プロキシは利用者が用意して運用します。
    - C: 正しい。
    - D: 誤り。KMS はプロキシとだけ通信し、外部の鍵を作成も削除もできません。
    - E: 誤り。公式の比較では、標準キーストアの SLA は 99.999% で、外部キーストアに SLA はありません。

    **スキル:** [5.3.2](../domain5.md#skill-5-3-2) / **参照:** [CloudHSM キーストア](../../../services/identity-directory.md#cloudhsm-key-store)

### 問4 {#q4}

カスタムキーストアの利用を検討している 3 つの要望が出ました。「非対称キーで署名する」「HMAC キーでメッセージを認証する」「マルチリージョンキーで東京と大阪で使う」です。KMS の標準キーストアとカスタムキーストアのどちらを使うかを判断します。正しいものはどれですか。

- A. すべてカスタムキーストアで実現できるので、外部キーストアに統一してよい
- B. 3 つともカスタムキーストアでは作れないので、標準キーストアを使う
- C. 非対称キーだけカスタムキーストアで作れないので、それだけ標準キーストアを使う
- D. マルチリージョンキーだけカスタムキーストアで作れないので、それだけ標準キーストアを使う

??? success "答えと解説"
    **正解: B**

    カスタムキーストアで作れるのは対称の暗号化キーで、非対称キー、HMAC キー、マルチリージョンキー、インポートした鍵素材は使えません。

    - A: 誤り。どれもカスタムキーストアでは作れません。
    - B: 正しい。
    - C: 誤り。HMAC とマルチリージョンも同じです。
    - D: 誤り。非対称と HMAC も同じです。

    **スキル:** [5.3.2](../domain5.md#skill-5-3-2) / **参照:** [CloudHSM キーストア](../../../services/identity-directory.md#cloudhsm-key-store)

### 問5 {#q5}

重要なデータを暗号化しているキーについて、インシデントの発生時に待機期間なしで鍵素材を消し、後で元に戻せるようにします。自動ローテーションは不要です。適切な選択とその注意点はどれですか。

- A. AWS 生成のキーを無効にする。元に戻すときは `EnableKey` を呼ぶが、鍵素材は消えない
- B. インポートした鍵素材を使い、すぐ消せるが元のコピーは利用者が保管する
- C. AWS 生成のキーを `ScheduleKeyDeletion` で消す。待機期間を 0 日に設定すれば、すぐ消える
- D. 外部キーストアのキーを `DisableKey` で止める。待機期間はないが、鍵素材も AWS に残る

??? success "答えと解説"
    **正解: B**

    `DeleteImportedKeyMaterial` は待機期間なしで鍵素材を消せます。同じ鍵素材を再度インポートすれば戻ります。耐久性は利用者の責任です。

    - A: 誤り。鍵素材を消す要件を満たしません。
    - B: 正しい。
    - C: 誤り。待機期間は 7〜30 日で、0 日にはできません。
    - D: 誤り。外部キーストアの鍵素材は AWS にありません。

    **スキル:** [5.3.3](../domain5.md#skill-5-3-3) / **参照:** [キーの無効化と削除](../../../services/kms.md#disable-delete)

### 問6 {#q6}

インポートした鍵素材に `ValidTo` を設定したキーで、期限が過ぎるとアプリが暗号化も復号もできなくなりました。キーの状態を調べ、復旧します。正しい説明はどれですか。

- A. キーの状態は `Disabled` で、`EnableKey` を呼べば戻る
- B. キーの状態は `PendingDeletion` で、`CancelKeyDeletion` を呼べば戻る
- C. キーの状態は `Enabled` のままで、復号だけが拒否されるので、IAM ポリシーを修正する
- D. キーの状態は `PendingImport` で、同じ鍵素材を再度インポートすれば戻る

??? success "答えと解説"
    **正解: D**

    期限切れや削除の後は `PendingImport` になり、使えなくなります。同じ鍵素材をインポートし直すと復旧します。

    - A: 誤り。`Disabled` ではありません。
    - B: 誤り。キーの削除とは別です。
    - C: 誤り。状態が変わり、権限の問題ではありません。
    - D: 正しい。

    **スキル:** [5.3.3](../domain5.md#skill-5-3-3) / **参照:** [鍵素材のインポート](../../../services/kms.md#imported-key-material)

### 問7 {#q7}

担当者は「鍵素材をインポートすれば、KMS で暗号化した対称の暗号文を社内の HSM でも復号できる」と考えています。鍵のローテーションは毎年必須で、自動化したいとも考えています。この計画の評価として正しいものはどれですか。

- A. 暗号文の形式は公開されておらず外で復号できない。インポートのキーでは自動ローテーションもできない
- B. 外で復号でき、オンデマンドのローテーションも `EnableKeyRotation` で自動にできる
- C. 外で復号はできないが、自動ローテーションは `EnableKeyRotation` で毎年に設定できる
- D. 外で復号できるが、ローテーションの要件には外部キーストアへの移行が必要になる

??? success "答えと解説"
    **正解: A**

    KMS の対称の暗号文の形式は公開されていないので、KMS の外で復号できません。インポートした鍵素材のキーは自動ローテーションに対応せず、対称キーならオンデマンドで新しい鍵素材をインポートしてローテーションします。

    - A: 正しい。
    - B: 誤り。どちらの点も誤りです。
    - C: 誤り。自動ローテーションはできません。
    - D: 誤り。外で復号できません。

    **スキル:** [5.3.3](../domain5.md#skill-5-3-3) / **参照:** [鍵素材のインポート](../../../services/kms.md#imported-key-material)

### 問8 {#q8}

インポートする鍵素材を検討するときの、次の 4 つの要望があります。この中で、AWS 生成の鍵素材では満たせず、インポートを選ぶ理由になるものはどれですか。

- A. CloudTrail で全ての鍵の利用を記録したい
- B. 鍵素材の生成元のエントロピーを自社で証明したい
- C. 鍵の管理者と利用者を分離し、キーポリシーで制御したい
- D. 毎年、自動的に鍵素材をローテーションしたい

??? success "答えと解説"
    **正解: B**

    インポートは、生成元の証明、すぐに消して後で戻すこと、外部に元のコピーを持つことが主な理由です。

    - A: 誤り。AWS 生成のキーでも記録されます。
    - B: 正しい。
    - C: 誤り。どちらのキーでも実現できます。
    - D: 誤り。逆で、自動ローテーションはインポートではできません。

    **スキル:** [5.3.3](../domain5.md#skill-5-3-3) / **参照:** [鍵素材のインポート](../../../services/kms.md#imported-key-material)

### 問9 {#q9}

マルチリージョンキーのプライマリを東京に作り、大阪にレプリカを作りました。セキュリティチームは東京のキーポリシーを変更しましたが、大阪のアプリの権限が変わりません。原因として正しいものはどれですか。

- A. キーポリシーはレプリカに同期されるが、最大 24 時間の遅延がある
- B. レプリカの鍵素材がプライマリと別なので、ポリシーの共有もできない
- C. キーポリシーは各リージョンで別々に管理するので、大阪のキーポリシーも変更する
- D. レプリカはプライマリのキーポリシーだけを参照するので、大阪のアプリの IAM ポリシーに原因がある

??? success "答えと解説"
    **正解: C**

    共有されるのはキー ID、鍵素材、キーの仕様、自動ローテーションの設定などです。キーポリシー、グラント、別名、タグ、有効と無効は別々です。

    - A: 誤り。キーポリシーは同期されません。
    - B: 誤り。鍵素材は共有されます。
    - C: 正しい。
    - D: 誤り。各リージョンのキーポリシーがそのキーに適用されます。

    **スキル:** [5.3.5](../domain5.md#skill-5-3-5) / **参照:** [マルチリージョンキー](../../../services/kms.md#multi-region-keys)

### 問10 {#q10}

既存の単一リージョンのカスタマー管理キーで暗号化したデータを、別のリージョンでも再暗号化なしで復号できるようにしてほしいという要望が来ました。担当者はキーをマルチリージョンに変換する提案をしました。正しい判断はどれですか。

- A. `UpdateKeyDescription` で `MultiRegion` を `true` にすると変換でき、既存の暗号文は別のリージョンで復号できる
- B. 既存のキーは変換できない。新しいマルチリージョンキーを作り、データを再暗号化する必要がある
- C. 別のリージョンに同じ別名を作ると、KMS が自動で元のリージョンへ転送して復号する
- D. レプリカを作る操作 `ReplicateKey` は単一リージョンのキーにも使えるので、それを呼ぶ

??? success "答えと解説"
    **正解: B**

    単一リージョンのキーはマルチリージョンキーに変換できません。データの所在の性質を保つための設計です。新しいキーでの再暗号化が必要です。

    - A: 誤り。この属性は作成時に決まり、変更できません。
    - B: 正しい。
    - C: 誤り。そのような転送はありません。
    - D: 誤り。`ReplicateKey` はマルチリージョンのプライマリキーが対象です。

    **スキル:** [5.3.5](../domain5.md#skill-5-3-5) / **参照:** [マルチリージョンキー](../../../services/kms.md#multi-region-keys)

### 問11 {#q11}

東京の ALB と、グローバルな CloudFront に同じドメインのパブリック証明書を付けます。Web の担当者が東京の ACM で 1 枚だけ証明書を発行しました。CloudFront で選択肢に出ません。どう対応しますか。

- A. 東京の証明書を CloudFront の設定に ARN で直接指定する
- B. 東京の証明書を `us-east-1` にコピーする API を呼び、同じ ARN で使う
- C. CloudFront のディストリビューションを東京のリージョンに作り直す
- D. `us-east-1` の ACM でも証明書を発行し、CloudFront にはそれを使う

??? success "答えと解説"
    **正解: D**

    CloudFront の証明書は `us-east-1` の ACM のものだけです。ALB は同じリージョンの証明書を使います。

    - A: 誤り。別のリージョンの証明書は使えません。
    - B: 誤り。ACM の証明書はリージョン間でコピーできません。
    - C: 誤り。CloudFront はリージョンのサービスではありません。
    - D: 正しい。

    **スキル:** [5.3.5](../domain5.md#skill-5-3-5) / **参照:** [リージョンのルール](../../../services/certificates.md#region-rules)

### 問12 {#q12}

社内のマイクロサービスの mTLS に数千の証明書が必要で、毎日発行します。有効期間は 3 日で十分で、失効の仕組みを省略しつつ費用も下げたいと考えています。ALB は使わず、コンテナ内に直接配置します。適切なものはどれですか。

- A. ACM のパブリック証明書を発行し、エクスポートしてコンテナに配置する
- B. Private CA の短期証明書モードで `IssueCertificate` する
- C. Private CA を汎用モードで作成し、ACM の自動更新で 3 日ごとに更新する
- D. 自己署名の証明書をコンテナ起動時に生成し、信頼の確認はセキュリティグループに任せる

??? success "答えと解説"
    **正解: B**

    短期証明書モードは有効期間が 7 日までの証明書を低コストで発行します。期間が短いので、失効の仕組みを省ける場合があります。

    - A: 誤り。公開の認証局の証明書を内部の mTLS に使うのは不要で、期間の要件にも合いません。
    - B: 正しい。
    - C: 誤り。汎用モードは費用が高く、ACM の自動更新で 3 日の期間にはなりません。
    - D: 誤り。信頼の確認ができず、mTLS の意味がありません。

    **スキル:** [5.3.5](../domain5.md#skill-5-3-5) / **参照:** [Private CA の設定](../../../services/certificates.md#private-ca-settings)

### 問13 {#q13}

東京の Private CA で発行した証明書を、シンガポールのサービスでも使いたいと考えています。担当者は「CA をシンガポールにコピーする」と言っています。また、ACM の統合サービスに証明書を置くとき、自動更新を維持したいと考えています。正しい組み合わせはどれですか。（2つ選択）

- A. CA はコピーできない。シンガポールで使う CA は、そのリージョンに作る計画にする
- B. CA はリージョン間でコピーでき、失効リストも自動で同期される
- C. ACM から Private CA を指定して証明書を要求すると、統合サービスで使え、自動更新の対象になる
- D. Private CA の `IssueCertificate` で発行した証明書は、ACM が自動で検出して更新する
- E. ACM へインポートした証明書は、発行元が Private CA であれば自動更新される

??? success "答えと解説"
    **正解: A, C**

    Private CA はリージョンのリソースで、コピーできません。自動更新は ACM で要求した証明書が対象です。

    - A: 正しい。
    - B: 誤り。コピーできません。
    - C: 正しい。
    - D: 誤り。`IssueCertificate` で発行したものは自分で管理します。
    - E: 誤り。インポートした証明書は自動更新されません。

    **スキル:** [5.3.5](../domain5.md#skill-5-3-5) / **参照:** [自動更新](../../../services/certificates.md#auto-renewal)、[Private CA](../../../services/certificates.md#private-ca)
