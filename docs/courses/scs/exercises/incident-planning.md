# インシデント対応計画の問題集

対象の解説: [インシデント対応](../../../services/threat-detection.md#incident-response)、[AWS Resilience Hub](../../../services/resilience.md#resilience-hub)、[FIS](../../../services/resilience.md#fis)、[ARC](../../../services/resilience.md#arc)

### 問1 {#q1}

あるセキュリティチームは、Security Hub CSPM の重大なアラートと CloudWatch アラームの両方を、担当者が調査して閉じるまで 1 か所で追跡したいと考えています。作業項目ごとに、関連する Config の変更と CloudTrail のログを同じ画面で確認し、必要ならその場からランブックを実行します。独自の開発は避けます。新しく採用するものとして最も適切なものはどれですか。

- A. EventBridge ルールと CloudWatch アラームから Systems Manager OpsCenter の OpsItem を作る
- B. Step Functions と DynamoDB でチケット管理の仕組みを作り、独自の画面から状態を更新する
- C. Security Lake にすべてのイベントを取り込み、Athena の保存クエリを担当者ごとに用意して、結果を手で突き合わせる
- D. Systems Manager Incident Manager のレスポンスプランを新しく作り、すべてのアラートをインシデントとして起票する

??? success "答えと解説"
    **正解: A**

    OpsCenter は EventBridge と CloudWatch アラームから OpsItem を自動で作り、Config、CloudTrail の情報を集めて表示します。OpsItem からランブックも実行できます。

    - A: 正しい。
    - B: 誤り。動きますが、独自の開発を避ける条件に反します。
    - C: 誤り。ログの検索はできますが、作業項目の追跡にはなりません。
    - D: 誤り。Incident Manager は新規受付を終了しています。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [OpsCenter](../../../services/operations.md#opscenter)、[プレイブックと実行基盤](../../../services/threat-detection.md#ir-playbooks)

### 問2 {#q2}

調査チームは、不審なロールの活動を調べる手順を残したいと考えています。手順の説明、Athena へのクエリ、結果の表やグラフを 1 つの文書にまとめ、次の事象では値を変えて同じ分析を再実行します。分析の内容は事象ごとに担当者が判断して変えます。最も適した手段はどれですか。

- A. Systems Manager Automation のランブックに分析の全手順を定義し、EventBridge から無人で実行する
- B. SageMaker AI のノートブックに手順とクエリを書き、対話的に実行する
- C. S3 に手順書の PDF を置き、Athena のコンソールへクエリを毎回貼り付ける運用にする
- D. Config のカスタムルールにクエリを実装し、評価の結果を分析結果として残す

??? success "答えと解説"
    **正解: B**

    手順の説明、実行できるコード、結果を一緒に残せるのがノートブックです。試験ガイドも対応計画の例に SageMaker AI のノートブックを挙げています。

    - A: 誤り。Automation は決まった手順の実行に向き、担当者が判断しながら進める分析には向きません。
    - B: 正しい。
    - C: 誤り。手順と結果が分かれ、再実行のたびに手作業が増えます。
    - D: 誤り。Config ルールはリソースの準拠を評価するもので、調査の分析には使えません。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [プレイブックと実行基盤](../../../services/threat-detection.md#ir-playbooks)

### 問3 {#q3}

EC2 の隔離手順を実行できる形で用意します。要件は 4 つです。実行前に影響を確認できること。隔離前のセキュリティグループの設定を保存すること。インスタンスが Auto Scaling グループにあっても動くこと。調査後に元の設定へ戻せること。開発を最小にするには、どれを使いますか。

- A. `AWS-StopEC2Instance` をランブックとして実行し、調査が終わったら `AWS-StartEC2Instance` で元に戻す
- B. Lambda で全セキュリティグループを外す処理を書き、元の設定は担当者が変更前にコンソールで控えておく
- C. セキュリティグループの変更を Config の修復として登録し、非準拠になったインスタンスから順に隔離する
- D. `AWSSupport-ContainEC2Instance` を `DryRun` で確認し、`Contain` で実行し、調査後に `Restore` で戻す

??? success "答えと解説"
    **正解: D**

    このランブックは、設定を S3 に保存してから隔離用のセキュリティグループへ移し、Auto Scaling グループのインスタンスはスタンバイにします。`DryRun` で変更なしに確認できます。

    - A: 誤り。停止するとメモリの証拠が失われ、設定の保存もしません。
    - B: 誤り。開発が必要で、元に戻す手順が人の記録に頼ります。
    - C: 誤り。Config の修復は非準拠のリソースを直す仕組みで、選んだインスタンスを必要なときに隔離する手順ではありません。
    - D: 正しい。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [EC2 の隔離](../../../services/threat-detection.md#ir-ec2-isolation)、[Automation](../../../services/operations.md#automation)

### 問4 {#q4}

ある会社の対応計画は、検出結果の種類ごとに人が読む Word の文書です。深夜の対応で手順の抜けが続いたので、見直します。本番を止める手順の前では、必ず人が判断します。プレイブックを一から書く負担も減らしたいと考えています。適切なものを選んでください。（2つ選択）

- A. 手順を Systems Manager Automation のランブックにし、本番を止める手順の前に `aws:approve` を入れる
- B. Security Hub CSPM の自動化ルールで、隔離とスナップショットの取得まで実行する
- C. 文書を Trusted Advisor の点検項目として登録し、未対応の手順を自動で検出する
- D. AWS Customer Playbook Framework の公開サンプルを出発点にして、自社向けに直す
- E. Audit Manager のカスタムフレームワークに手順を登録し、担当者に委任して実行する

??? success "答えと解説"
    **正解: A, D**

    実行できる形にして承認の手順を入れれば、抜けを減らしながら人の判断も残せます。公開サンプルは書き始めの負担を減らします。

    - A: 正しい。
    - B: 誤り。自動化ルールは検出結果の更新や抑制をするもので、リソースは操作しません。
    - C: 誤り。Trusted Advisor は環境を点検するサービスで、社内の手順を登録して検出する機能ではありません。
    - D: 正しい。
    - E: 誤り。Audit Manager は監査の証拠を集めるサービスで、対応の手順は実行しません。

    **スキル:** [2.1.1](../domain2.md#skill-2-1-1) / **参照:** [プレイブックと実行基盤](../../../services/threat-detection.md#ir-playbooks)、[Automation](../../../services/operations.md#automation)

### 問5 {#q5}

中央のアカウントから、複数のアカウントとリージョンへ隔離のランブックを実行する計画です。途中に `aws:approve` の手順を入れたところ、この構成では承認の手順が使えないと分かりました。承認の要件は残します。最も適切な設計はどれですか。

- A. `timeoutSeconds` を 30 日まで延ばし、対象のアカウント数と同じ値を `MinRequiredApprovals` に指定する
- B. `AWS-SystemsManager-AutomationExecutionRole` に承認の権限を足して、各アカウントで `aws:approve` を動かせるようにする
- C. ランブックの外に承認を置き、Step Functions の `waitForTaskToken` で承認を受けてから実行する
- D. 実行するアカウントを組織の管理アカウントに替えれば、複数アカウントの実行でも `aws:approve` が使える

??? success "答えと解説"
    **正解: C**

    - A: 誤り。タイムアウトや承認者の数の問題ではありません。
    - B: 誤り。権限を足しても、このアクション自体が対応していません。
    - C: 正しい。
    - D: 誤り。どのアカウントから実行しても制限は変わりません。

会社は Shield Advanced に登録しました。ALB への攻撃で可用性が落ちたときに、Shield Response Team（SRT）から直接連絡を受けられるよう、プロアクティブエンゲージメントを設定します。事前に必要なものを選んでください。（3つ選択）

- A. 保護対象の ALB の保護に、Route 53 ヘルスチェックを関連付ける

- D. Firewall Manager の Shield Advanced ポリシーで ALB を保護対象に含める

### 問7 {#q7}

SRT に調査を頼むため、ロールを `AssociateDRTRole` で渡しました。SRT は WAF のログは読めましたが、ALB のアクセスログは読めません。ALB のログは、同じアカウントの S3 バケットに SSE-KMS で保存しています。どう直しますか。

- A. WAF のログと同じ扱いなので、ロールの信頼ポリシーに `s3.amazonaws.com` を追加すれば読めるようになる
- B. KMS のキーポリシーで `drt.shield.amazonaws.com` に `kms:Decrypt` を許可すれば、そのまま読めるようになる
- C. ログをログ専用の別アカウントのバケットへ移し、そのバケットのポリシーで SRT のロールに読み取りを許可する

    - D: 正しい。

### 問10 {#q10}

メンバーアカウントで管理者権限を奪われても、CloudTrail の記録を止められず、保存済みのログも消せないようにします。どの対策が必要ですか。（2つ選択）

- A. 同じアカウントのバケットでバージョニングを有効にし、過去のバージョンも残す
- B. SCP で `cloudtrail:StopLogging` と `cloudtrail:DeleteTrail` を拒否する
- C. Config ルールで証跡の有効化を評価し、非準拠を担当者へ通知する

    - B: 正しい。
    - C: 誤り。Config のルールは評価するだけで、停止を防ぎません。

検知と復旧の自動化が実際に動くか、検証環境で確かめます。Web 層のインスタンス 1 台だけを止めます。エラー率が高くなったら、実験を自動で止めます。AWS Fault Injection Service のテンプレートとして正しいものはどれですか。

- B. `selectionMode` を `ALL` にし、対象のタグを 1 台にだけ付けておけば、停止条件は省略して問題ない
